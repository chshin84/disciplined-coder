# 에이전트원칙 실패 평가 세트

이 폴더는 에이전트원칙 개편(`docs/superpowers/specs/2026-10-18-principles-positive-restructure-design.md`)을 측정하는 과제와 결과를 둔다. 실행 명령은 `scripts/eval_clause.sh`, 판정 명령은 `scripts/eval_clause_report.sh` 다(「클린룸 시험」 절). 원칙 전체를 실은 묶음 비교는 2026-10-18 사용자 지시로 하지 않으며, 그 도구(`eval_principles.sh`, `eval_compare.sh`)는 지웠다. 아래 「실행 도구」 절의 플러그인 설치 경로는 그 도구의 기록이다.

## 실행 도구

선택값은 `claude-p` 다. 2026-10-18 에 Claude Code 2.1.302 로 두 경로를 시험한 결과로 골랐다.

`claude plugin eval` 경로는 원칙 적재에서 실패했다. 이 명령은 실행마다 새 설정 폴더를 만들므로 매 세션이 관리블록을 처음 만드는 첫 세션이 된다. 그 세션에서 원칙은 SessionStart 훅의 첫 세션 보강으로만 실리는데, 하네스가 훅 출력을 앞 2KB 만 맥락에 넣고 나머지를 파일로 돌렸다. probe 과제의 응답은 "나머지 15KB가 저장된 파일은 읽기 권한이 거부되어 확인하지 못했습니다"였다. 과제 작업 폴더에 프로젝트 CLAUDE.md 를 두는 방법도 쓸 수 없다. 공식 문서(https://code.claude.com/docs/en/plugin-evals.md)가 scaffold_script 가 쓴 CLAUDE.md 를 싣지 않는다고 적기 때문이다. `append_system_prompt` 로 원칙 전문을 붙이면 probe 가 통과했지만, 실제 세션과 다른 경로라 고르지 않았다.

`claude-p` 경로의 확인 결과는 아래와 같다.

- 원칙 적재: 예열 세션 뒤의 세션이 원칙 파일 끝에 넣은 표지(`PROBE-A`)를 답했다.
- 조건 구분: 표지를 `PROBE-B` 로 바꾼 worktree 를 새 평가 설정 폴더에 설치하자 `PROBE-B` 를 답했다.
- 사본 대조: 평가 설정 폴더의 `disciplined-coder/agent-principles.md` 해시가 그 worktree 의 원칙 해시와 같았다.
- 격리: 실제 설정 파일 여섯 곳(`~/.claude/CLAUDE.md`, `~/.claude/disciplined-coder/*.md`, `settings.json`, `plugins/known_marketplaces.json`, `plugins/installed_plugins.json`)의 해시가 시험 전후로 같았다.

실패한 시도도 남긴다. 처음 probe 는 "응답 첫 줄에 PROBE-A 를 적어라"라는 지시였는데, 모델이 지시를 따르지 않아 원칙 적재와 지시 이행을 구분하지 못했다. 그래서 probe 를 "실린 지시 안의 PROBE- 표지 단어를 답하라"로 바꿨다. 임시 설정 폴더에는 로그인 정보가 없어 `Not logged in` 으로 끝났으므로, 인증은 API 키로 한다.

조건 하나의 준비는 아래 순서다. 모든 명령은 `CLAUDE_HOME_DIR` 을 비우고 `CLAUDE_CONFIG_DIR=<평가 설정 폴더>` 를 붙여 실행한다.

1. 빈 평가 설정 폴더를 만들고, 사용자 전역 `CLAUDE.md` 의 관리블록 밖 내용과 `kw-ax` 폴더를 복사한다. 모든 조건이 같은 사용자 지시를 받게 하기 위해서다.
2. `disciplined-coder/plugin-notice.skip` 에 `superpowers` 를 적는다. 평가 설정 폴더에는 superpowers 가 없어, 끄지 않으면 함께 쓰는 플러그인 알림이 응답에 섞인다.
3. `claude plugin marketplace add <그 커밋의 worktree>` 와 `claude plugin install disciplined-coder@chshin-tools` 를 실행한다.
4. `plugins/known_marketplaces.json` 의 chshin-tools 항목에 `"autoUpdate": false` 를 넣는다.
5. 예열 세션 `claude -p "확인용 예열입니다. ok 라고만 답하세요." --tools ""` 를 실행한다.

과제 세션은 `--tools ""` 로 도구를 끄고, git 저장소가 아닌 빈 작업 폴더에서 실행한다. 처음에는 빈 git 저장소에서 실행했는데, 하네스가 그 git 상태를 맥락에 넣자 모델이 과제의 작업 기록을 저장소 상태와 대조하려 했고 도구 호출문을 글로 적었다. 그래서 작업 폴더를 바꾸고, 모든 과제 앞에 '평가용 대화이고 도구는 쓸 수 없으며 이전 대화와 기록은 확인된 사실이다'라는 머리말을 뒀다. 판정 세션은 플러그인이 없는 빈 설정 폴더에서 실행한다. 판정 세션에 원칙이 실리면 조건마다 판정자가 달라지기 때문이다.

인증 키는 저장소 밖 `~/.dc-eval.env` 의 `ANTHROPIC_API_KEY` 줄에서 읽어 환경 변수로만 넘기고, 출력하거나 파일에 다시 쓰지 않는다. 사용료는 그 키의 API 계정으로 청구된다.

평가 폴더(작업 폴더와 설정 폴더)는 `EVAL_TMP`(기본 `/d/dc-eval-tmp`) 아래에 만든다. Claude Code 는 작업 폴더에서 위로 올라가며 `CLAUDE.md` 와 `.claude/CLAUDE.md` 를 싣기 때문이다. 2026-10-18 에 빈 설정 폴더로 측정해 보니, 사용자 홈 아래 `/tmp` 에서 실행한 세션은 실린 지시에 `~/.claude/CLAUDE.md` 의 관리블록이 있다고 답했고 D: 아래 폴더의 세션은 없다고 답했다. 그래서 두 실행 스크립트는 평가 폴더의 상위 경로에 그 파일이 있으면 실행하지 않는다. 실패 기록도 남긴다. Task 3 의 smoke 와 위 probe 는 사용자 홈 아래 `/tmp` 에서 실행했으므로 실제 사용자 지시가 함께 실렸을 수 있다. 그 결과는 측정 기록으로 쓰지 않았다.

## 클린룸 시험

조항별 시험은 `scripts/eval_clause.sh [<단위 이름>...]` 로 실행하고 `scripts/eval_clause_report.sh` 로 판정을 낸다. 시험 단위는 `clauses/<단위 이름>/` 폴더이고, `current.md`(현행 문안), `new.md`(변경안), 나눈 조항 쌍이면 `ids`(단위의 조항 ID)를 둔다. `base` 파일(기준 커밋 해시 한 줄, 없으면 7a2d26d)은 `current.md` 의 줄을 대조할 `agent-principles.md` 의 커밋을 정한다. `system.md` 가 있으면 그 단위의 모든 생성 호출(`current`·`new` 양쪽)에 `--append-system-prompt <내용>` 을 붙이고, 생성 키에 그 내용의 해시를 덧붙인다. 내용이 빈 `system.md` 는 없는 것으로 본다. `system.md` 가 없으면 생성 키는 이전과 같아 기록된 생성이 그대로 쓰인다. 조건마다 빈 설정 폴더에 그 파일 하나만 `CLAUDE.md` 로 넣고, 플러그인과 사용자 전역 지시는 넣지 않는다. 문구 변경은 `current`·`new`, 새 조항(`current.md` 없음)은 `none`·`new` 를 실행한다.

같은 질문은 같은 조건으로 한 번만 생성한다(2026-10-18 사용자 지시). 생성 키는 과제 본문과 조건 문안의 해시이고, 판정 키는 생성 키와 판정 기준의 해시다. 기록은 `results/clauses/gen.jsonl`(생성)과 `judge.jsonl`(판정)에 한 줄씩 덧붙인다. 생성 키가 기록에 있으면 생성하지 않고, 판정 키만 없으면 판정만 한다. 그래서 과제 머리를 바꾸거나 판정 기준을 고쳐도 생성은 반복되지 않는다. 생성 오류(`is_error` 응답, 빈 응답, 시간 초과)와 읽지 못한 판정은 기록하지 않고 `errors=` 로 센다.

2026-10-18 첫 전체 실행(생성 392건, 판정 392건, 오류 0건)은 haiku 로 판정했다. 판정이 갈린 질문을 읽어 보니 판정 모델의 오판이 섞여 있었다. TITLE-LAYERS 의 두 조건 응답은 같은 절 제목을 썼는데 한쪽만 위반이었고, BALANCE·STATUS-FIRST 의 판정 이유는 '기준을 지켰다'고 쓰면서 위반으로 기록됐다. 그래서 판정 모델을 sonnet 으로 바꾸고, 판정 키에 판정 모델을 넣어 생성은 다시 하지 않고 판정만 새로 했다. haiku 판정 기록은 `judge.jsonl` 에 그대로 남는다(키가 달라 보고에 쓰이지 않는다).

2026-10-18 smoke 는 픽스처 과제 하나로 아래를 확인했다. 첫 실행에서 생성 2건과 판정 2건을 기록했고, 같은 명령을 다시 실행하자 새 기록이 0건이었다. 틀린 API 키로 실행하자 `Invalid API key` 를 오류 1건으로 세고 기록을 늘리지 않았다. 실제 설정 지문은 실행 전후로 같았다.

| 항목 | 값 |
|---|---|
| eval 폴더 | `evals/principles/cases/`(현재 브랜치 HEAD 의 과제를 조건 worktree 와 무관하게 읽는다) |
| 과제 형식 | 과제 폴더마다 `prompt.md`(front matter 에 과제 머리, 본문에 프롬프트)와 `criteria.md`(판정 기준) |
| 생성 모델 | `claude-opus-5-5`. 함께 쓰는 결과가 다른 모델과 섞이지 않게 `--model` 로 고정한다 |
| 판정 모델 | `claude-sonnet-5-5`. `claude -p --model claude-sonnet-5-5` 에 판정 기준과 응답을 넣어 실행한다. 처음에는 haiku 였다(「클린룸 시험」 절) |
| 실행 시간 | 예열 세션 15초, 과제 세션 15초 안팎 |
| 세션 비용 | 생성 세션 약 0.13달러 |

## 문구 변형 비교 시험

이 방법은 조항의 문구를 고를 때만 쓴다. 조항을 넣을지 뺄지, 어느 층에 둘지는 이 방법으로 정하지 않는다. 판정자가 Opus 5.5 하나이고, 11-12 에 그 판정이 사용자 판독보다 개선을 작게 측정한 사례가 기록됐다(`docs/superpowers/decisions/2026-11-12-reply-reminder-reinstate.md`). 아래는 2026-11-03·11-04 에 `managing-docs-agent` 워크트리 세션이 정리한 방법과 결과를 옮긴 내용이다.

위반이 줄지 않는 조항의 문구를 원점에서 고를 때 아래를 따른다(2026-11-03 사용자 지시, 2026-11-04 실행 결과 반영). 앞의 짝 시험과 별개의 방법이며, 비용이 크므로 시험할지는 예상 비용과 함께 먼저 제안한다.

**목적** — 주 목적은 위반 제거이고, 부 목적은 AI 티 제거와 사용자 피로감 완화다. 성능이 같으면 짧은 문안을 고른다.

**변형** — 조항마다 아래 8개 방식으로 변형을 하나씩 만들고 HEAD 문안을 대조군으로 둔다. 방식은 규칙만, 규칙+이유, 규칙+예시 1쌍, 규칙+예시 3쌍, 예시만, 조건행동, 결정점(쓰기 전 결정 사항), 독자틀이다. 변형 작성자에게 시험 질문을 보이지 않는다. 스트리밍 답은 고칠 수 없으므로 다 쓴 뒤 점검하는 형식은 넣지 않는다.

**질문** — 실제 세션의 턴을 쓴다. 조항마다 8개를 두고 모든 질문은 유니크하게 하며, 한 턴은 한 조항에만 쓴다. 앞 대화는 5,000자 이상, 메시지 4개 이상을 싣는다.

앞 4개 질문으로 HEAD 와 8개 변형을 비교하고, 뒤 4개는 숨겨 HEAD 와 1차 상위 3개만 비교한다. 채택 판단은 숨긴 질문을 기준으로 한다.

**판정** — 판정자에게 조건을 숨기고 합격 여부 대신 지표를 세게 한다. 조항 위반 수(`primary`)와 분모, `ai_lexical`·`ai_template`, `fatigue_actions`·`fatigue_refetch`·`fatigue_unasked`·`fatigue_verify` 다. 위반 여부와 순위는 스크립트가 위반 답 수, 위반 비율, 지시문 길이 순으로 계산한다.

앞 대화의 사실에 기대는 지표는 판정자에게 앞 대화 전체를 준다. 2026-11-04 시험은 마지막 두 메시지만 주어 사실 판단 조항의 절대값이 부풀었을 수 있다.

**조항 경계** — 변형에는 그 조항의 관심사만 쓴다. 시험 전에 변형을 다른 조항 전체와 1:N 으로 대조해 다른 조항의 내용을 뺀다. 단독 시험은 그 조항만 실으므로 다른 조항 내용을 붙인 문안이 좋게 나오고, 전체 원칙에서는 같은 내용이 겹친다. 그래서 단독 시험의 수치는 상한으로 읽는다(2026-11-04 사용자 지적).

**격리 실행** — `claude -p --tools "" --output-format json --model claude-opus-5-5 --setting-sources "" --strict-mcp-config --disable-slash-commands --no-session-persistence --system-prompt <지시문>` 을 쓰고, 환경에 `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`·`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` 을 넣고 `ANTHROPIC_API_KEY`·`CLAUDE_CONFIG_DIR` 을 뺀다. 먼저 전역 지침·플러그인·메모리·스킬이 실리지 않는지 확인 호출로 본다.

**모델 확인** — 판정자도 Opus 5.5 만 쓴다. 집계 전에 기록의 `modelUsage` 를 확인한다. 2026-11-04 시험은 1,352건 중 21건에 `claude-opus-4-8` 이 섞였고, 그 기록을 빼자 `NO-ASSUME` 의 개선이 사라졌다. 섞인 기록을 뺀 결과를 함께 보고한다.

**실행 관리** — 기록을 건별로 파일에 쓰고 이어 실행할 수 있게 만든다. 동시 실행 8개는 메모리 부족(전체 15.7 GB)으로 Claude Code 가 강제 종료했고, 6개는 끝까지 실행되었다. 실행 파일이 갱신된 시각에 호출 5건이 `FileNotFoundError` 로 실패했으며(원인은 추정), 실패한 작업만 다시 실행한다.

**2026-11-04 시험에서 확인한 사항** — 숨긴 질문이 조항마다 4개뿐이므로 다음 문구 작성의 출발점으로만 쓴다. 비용은 환산 143.61달러였다.

**방식을 고를 때** — 규칙+예시 3쌍과 규칙+이유를 먼저 시도한다. 숨긴 질문에서 HEAD 보다 나은 조항과 나쁜 조항의 수는 규칙+예시 3쌍이 5와 0(후보 6개), 규칙+이유가 4와 0(후보 7개), 규칙+예시 1쌍이 0과 3(후보 3개), 조건행동이 1과 4(후보 6개)다.

**묶어서 일반화하지 않는다** — '비슷한 문제는 비슷한 변형으로 해소된다'는 가설은 대체로 지지되지 않았다. 숨긴 질문의 1위 방식이 문장 구조 묶음 조항 4개와 낱말 묶음 조항 3개에서 모두 달랐다. 그래서 조항별로 시험한다.

**HEAD 가 나은 조항** — `NO-AGREE`(전체 위반 HEAD 1/8, 후보 2/8)와 `SPECIFIC-NAME`(HEAD 6/8, 후보 7/8)은 짧게 줄인 변형이 HEAD 를 넘지 못했다.

**문구로 줄지 않는 조항** — `ONE-IDEA` 는 모든 변형이 8/8 로 위반했다. `SPECIFIC-NAME`·`NO-ASSUME` 도 뚜렷한 개선이 없었다. 이 조항들은 문구를 더 다듬지 말고 재작성할 수 있는 층이나 기계 검사를 시험한다.

**지표가 구분하지 못한 조항** — `ASK-OPTIONS`(HEAD 와 상위 3개 모두 0/8)와 `BULLET-SCOPE`(HEAD 0/8)는 위반이 거의 나오지 않아 이 지표로는 문안을 고를 수 없다. 짧은 문안이 절차와 예외를 잃는지 따로 본다.

**단축 문안의 복원** — 시험 지표는 빠진 예외 조건을 잡지 못한다. 짧은 문안을 옮길 때 사용자가 정한 규칙(개조식 처리, 슬라이드 제목 형식, 한자어를 고유어로 바꾸지 않는 규칙 등)을 다시 넣고, 다시 넣은 문장은 시험하지 않았다고 근거 문서에 적는다.

**수치만으로 옮기지 않는다** — 위반이 가장 적은 변형도 사람이 읽고 뜻이 통하는지, 실제와 다른 상황을 사실처럼 적지 않았는지 확인한다. `YAGNI` 의 독자틀 변형은 위반이 가장 적었으나(전체 4/8) 읽는 사람을 동료 개발자로 적어 사용자가 2026-11-04 에 문제를 지적했다. 효과의 원인을 답의 변화에서 찾아 실제 상황의 문장으로 옮기고, 다시 시험한다. 합친 문안은 전체 6/8 로 효과가 줄었다.

**지표의 전제** — 지표가 규칙의 형태를 위반으로 세면, 나빠진 문장도 개선으로 판정된다. 사용자가 '시스템은 이전 버전으로 돌아갈 수 있습니다. 그 작업을 롤백이라고 합니다.'가 원래 문장보다 못하다고 지적해 용어 풀이 규칙과 지표를 뺐다. 예시 문장은 수치와 별도로 사람이 읽고 판단한다.

**판정 흔들림** — 지표를 좁혔는데도 `NO-MID-MOD` HEAD 의 위반 답이 4/8 에서 5/8 로 늘었다. 같은 답을 다시 판정해도 달라지므로 차이 1건으로 문안을 고르지 않는다. 동률이면 짧은 문안을 고른다.

**AI 티와 피로감** — 지표 정의는 검증되지 않은 설계 가정이다(`docs/superpowers/reviews/2026-11-03-slop-fatigue-prior-art.md`). 어휘 지표의 감소를 체감 감소로 단정하지 않는다. 사용자는 '앞 두 회차가 사용자 답변에 기댔던 자리다'처럼 '~한 + 자리' 구조를 AI 티로 지적했고, 이 문제는 서술어로 끝내거나 한 단어로 대체해 고치며, 낱말 치환으로 풀지 않는다고 정했다. 그래서 금지어 추가보다 평범한 문장으로 쓰게 하는 지시(`NO-ANALOGY`)를 먼저 고친다.

지운 조항과 그 근거는 위 참고서의 「삭제한 조항」 절에 있다.

## 과제 구성

과제는 두 출처에서 왔다. 첫째는 세션 기록 분석 보고(2026-10-18, 약 300건)에서 뽑은 짝 20개, 곧 40개다. 둘째는 조항별 클린룸 시험에 쓰려고 시험 단위마다 추가한 질문 150개(`q-<단위>-<번호>`)다. 둘째 묶음은 `current.md` 가 다루는 상황과 변경안 초안 이유 칸의 실패 사례에서 만들었고, `new.md` 의 문장은 쓰지 않았다. 과제마다 기대 행동이 일어나야 하는 과제(`kind: should`)와 일어나지 말아야 하는 과제(`kind: should-not`)를 짝으로 두어, 한쪽으로만 치우친 개선을 잡는다. 시험 단위의 질문이 3개가 되도록 추가한 셋째 질문은 짝이 없다. 업무 수치·종목·사람 이름·회사명·사용자 메시지 원문은 일반화했고, 고유 이름이 필요한 과제는 지어낸 이름(BLUEFIN 등)을 쓴다.

처음 40개의 출력 종류 비율은 세션 기록(대화 답 140, 도구 실행 중 판단 84, 작업 문서 32, 산출물 27, 코드 20)을 따랐다. 추가한 150개는 시험 단위의 조항이 다루는 출력 종류를 따른다. 보류용(처음 12개, 뒤에 30개로 늘림)은 클린룸 시험에 쓰지 않았고, 한 차례 실행한 전체 비교에만 썼다.

평가 세션에서는 도구를 실행할 수 없으므로, 도구 과제(`tool`)는 프롬프트 끝에 '실행할 행동과 사용자에게 보낼 말을 적어라'를 넣고 그 서술로 판정한다. 여러 턴 과제는 앞 턴을 `[이전 대화]` 로 인용하고 마지막 메시지에 대한 응답만 판정한다(`judge: last-turn`).
