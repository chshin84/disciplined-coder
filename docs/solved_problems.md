# 해결된 문제 로그 (solved_problems) — 이 프로젝트 · append-only 오답노트

이 레포에서 완결한 문제의 교훈 — 차후 비슷한 작업에서 recall해 참고한다.
**완결 후 등록하는 기록이라 '상태'가 아니다**(append-only, 과거를 지우지 않는다). 메인 세션만 append.
이 프로젝트에 한정된 교훈만 둔다 — 머신 전역은 PC solved, 보편은 디시플린 원칙으로(스코프 라우팅).

항목을 적는 형식은 이렇다.

- 증상은 굵게 한 줄로 띄운다.
- 원인과 해결은 그 아래 들여쓰기로 내린다.
- 한 항목은 세 줄을 넘기지 않는다.
- 순서는 시간순이고 아래에 추가한다.
- 항목이 스무 개를 넘으면 그때 영역별로 묶는다.
- 안 쓰이는 항목도 지우지 않는다.

- **validate의 "version 미지정" 경고를 없애려 plugin.json에 version을 추가했다가 같은 날 번복했다.**
  - 원인: 공식 문서상 version 설정은 마켓플레이스 업데이트를 버전 비교로 전환해 활성 개발 중 커밋 배포가 끊긴다.
  - 해결: 다음엔 경고·린트 해소 수정이라도 동작을 바꾸는지 해당 도메인 참고서(`skills/domain-plugin` 등)를 먼저 연다 — 설계 입력 절을 건너뛰면 3렌즈 리뷰도 이런 충돌을 못 잡는다(리뷰어는 계획 내부 정합을 보지, 안 연 참고서와의 충돌은 못 본다). 이 레포의 version 정책 정본은 `domain-plugin`의 '버전 핀 주의' 절이다.
- **워크플로 스크립트(`.claude/workflows/self-audit.js` 등)를 ESM으로(`node --input-type=module --check`) 검증하면 톱레벨 `return`에서 "Illegal return statement"로 실패한다.**
  - 원인: 워크플로 스크립트 본문은 하니스가 async 함수로 감싸 실행하므로 톱레벨 `return`이 정상이다.
  - 해결: 문법 검증은 같은 방식으로 감싼다 — `{ echo 'const __wrap = async () => {'; sed 's/^export const meta/const meta/' <파일>; echo '};'; } | node --check`.
- **spec/plan을 쓰면 Stop 훅이 리뷰어 완료 전에도 턴 종료를 반복 차단한다.**
  - 원인: 정상 동작이다(하드 게이트).
  - 해결: 리뷰어를 백그라운드로 띄웠으면 마커 없이 턴을 끝내려 하지 말고, 차단 메시지에 상태만 답하며 리뷰 완료 알림을 기다린다 — 결과 없이 마커부터 다는 우회는 게이트가 막으려는 바로 그 행동이다.
- **`~/.claude/CLAUDE.md`에 관리 블록이 네 겹으로 쌓이고 고아 마커가 박힌다.**
  - 원인: `managed_block_inject`의 고아 처리가 사용자 내용을 지키려고 비파괴로 만들어졌는데, 마커 줄만 주석화하고 본문·END를 남긴 채 새 블록을 덧붙여서 관리 내용에 대해서는 `IDEMPOTENT`가 깨졌다.
  - 해결: 다음엔 관리 영역을 **기우지 말고 다시 지어라** — 삭제 대상을 마커 줄로만 한정하고(본문 줄은 절대 안 지운다, `codex-scaffold.sh`가 정본 전문을 본문으로 넘기므로 빈 줄까지 삭제 대상이 된다), 닫는 마커 없는 여는 마커는 그 줄만 지운 뒤 경고하며, 짝 없는 닫는 마커도 지운다.
- **정본이 매 세션 두 번 실린다 — `@import` 관리 블록과 `scaffold.sh` stdout 양쪽이다.**
  - 원인: 이중화의 명분이던 "홈 경로 어긋나면 `@import`가 끊긴다"는 `_resolve_home.sh`가 이미 해소한 위험이었다.
  - 해결: 보험을 걸기 전에 그 위험이 아직 살아 있는지 먼저 확인하라. 남길 레일은 압축 생존성으로 고른다 — `CLAUDE.md`는 매 요청 다시 실리지만 SessionStart stdout은 `compact` matcher가 없어 요약으로 뭉개진다. 첫 설치 세션만 stdout으로 보강하되 판정은 주입 **전에** 하고 `grep -x`를 쓰지 마라(CRLF에서 영원히 거짓이 된다). 같은 결함이 `codex-scaffold.sh`에도 대칭으로 있었다 — 쌍둥이 스크립트는 한쪽을 고칠 때 반드시 같이 본다.
- **`/add-pointer`가 빈 오답노트 템플릿을 미리 만들라고 권하고 있었다.**
  - 원인: 빈 파일은 recall이 발화해도 얻는 교훈이 0이라 만들 값어치가 없다.
  - 해결: 오답노트는 **적을 것이 생긴 시점에** 만든다. 미리 만드는 커맨드와 그것을 권하는 훅 넛지는 함께 제거한다. 원칙의 오답노트 절이 이미 "파일 존재로 도출"을 규정하므로 포인터 없이도 recall이 성립한다.
- **재사용하려던 함수의 "미관 정리" 한 줄이 사실은 유일한 커밋 경로여서 설계가 통째로 어긋났다.**
  - 원인: `_managed_block.sh`의 후행 빈 줄 정리 줄만 보고 장식으로 단정했는데, 그 한 줄 안의 `mv`가 스트립 결과를 대상 파일에 반영하는 유일한 경로이자 구분 빈 줄을 멱등하게 만드는 장치였다. "이 모드에서는 건너뛴다"고 적은 설계가 아무것도 반영하지 못하는 설계였다.
  - 해결: 기존 함수를 재사용하겠다고 결정하기 전에 **그 함수의 쓰기 경로를 처음부터 끝까지 읽어라**. 한 줄이 두 역할을 겸하는지, 어디서 임시 파일이 대상 파일로 옮겨지는지를 특정하고 나서 확장 여부를 판단한다. 리뷰어에게도 "이 줄이 무슨 역할인지 코드로 확인하라"고 명시하면 잡힌다.
- **실측 표에서 도출되지 않는 인과를 두 번이나 세워 스킬 정본에 박을 뻔했다.**
  - 원인: 네 종류만 잰 도달 표를 두고 "쓰기 도구가 없어서"라고 원인을 단정했는데, 도구 보유는 한 칸도 재지 않았고 "빌트인이라서"가 같은 데이터를 똑같이 설명했다.
  - 해결: 표본이 적을 때는 **관측만 적고 인과는 주장하지 마라**. 경쟁 설명이 같은 데이터를 설명하는지 먼저 세어 보고, 못 가리면 "왜 갈리는지는 측정하지 않았다"를 그 자리에 적는다. 이 레포는 문서가 사실과 다른 것을 고치는 중이었으므로 같은 실패를 재생산할 뻔했다.
- **여러 줄 문자열 포함 검사를 `grep -F`로 짜면 한 줄만 있어도 참이 된다.**
  - 원인: `grep -F`는 패턴의 각 줄을 별개 후보로 다루는 줄 단위 검사다. 이 레포의 기존 포함 검사가 전부 그 관용구인데 대상이 한 줄짜리라 문제가 드러난 적이 없었다(`SIMPLE`의 "주변 관례를 따른다"가 여기서는 함정이다).
  - 해결: 여러 줄 블록의 포함 여부는 `case "$내용" in *"$블록"*)`처럼 리터럴 부분일치로 본다. 그리고 **불릿 하나를 지운 픽스처로 뮤테이션 검증**해야 이 함정을 실제로 잡는다.
