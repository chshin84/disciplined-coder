# 생성 제약에 맞춘 조항 재작성 설계

## 의도

에이전트원칙(`agent-principles.md`)의 조항을 LLM 의 생성 방식에 맞게 다시 쓴다. 2026-10-12 강화 시험과 실사용 세션 분석에서 지시가 있는데도 같은 위반이 반복되었다. 실사용 답 1,851개 중 약 24% 에 굵은 라벨과 두 문장으로 된 불릿이 있었고, 영어로 잘못 나간 답에도 같은 형식이 있었다. 이 수치는 2026-10-20 세션이 세션 기록 59개를 정규식으로 센 결과이며, 집계 스크립트는 저장소에 남아 있지 않다. T9 에서 집계 방법을 `docs/domain-discipline.md` 에 적는다.

사용자는 이 현상을 "약한 모호함이 첫 토큰 선택에서 증폭된 결과"로 해석했다. 그리고 2026-10-18 재편이 생성 방식의 제약을 상위 개념으로 지정하지 않았다고 판단했다(2026-10-20). 그래서 먼저 상위 개념 「생성 제약」을 정한다. 이어서 그 기준으로 현행 조항을 대조한다. 마지막으로 커밋 8b4a05a(브랜치 `feat/clause-strengthening`)의 문안 중 방향이 맞는 후보를 시험해 2026-10-18 원칙 위에 다시 적용한다.

이 문서에서 새로 붙인 이름은 아래와 같다.

| 이름 | 뜻 |
|---|---|
| 생성 제약 | 조항을 쓰고 고칠 때 따르는 기준으로, LLM 의 생성 방식에서 나온 제약의 목록이다 |
| 결정점 | 모델이 문장이나 항목의 첫 토큰을 내기 직전의 시점이다. 결정점 지시는 그 시점에 정할 일을 지시하는 문장이다 |
| 지목형 문안 | 피할 형태를 이름이나 잘못된 예로 직접 적는 문안이다 |
| 긍정형 문안 | 피할 형태를 적지 않고 원하는 형태만 지시하는 문안이다 |

## 목표

- 조항 작성 기준인 생성 제약을 정하고 저장소 CLAUDE.md 「에이전트원칙을 고칠 때」에 둔다.
- 현행 조항을 생성 제약으로 대조해 어긋난 조항을 고친다.
- 파일에서 문자열로 잡히는 위반은 기계 검사로 찾고, 그 결과를 경고로 돌려준다.
- 커밋 8b4a05a 의 문안 중 방향이 맞는 후보를 시험한다.
- 조항의 문구 변경과 추가는 조항별 클린룸 시험(저장소 CLAUDE.md 「조항 추가와 문구 변경」의 소거 시험)을 통과한 문안만 채택한다. 사용자가 직접 정한 삭제(T1 의 `NAME-ITEMS`)는 이 시험의 대상이 아니다.

## 비목표와 반목표

원칙 전체를 한 번에 비교하는 묶음 시험은 비목표다. 사용자가 2026-10-18 에 같은 질문은 같은 조건으로 한 번만 생성하고 묶음 비교는 하지 않기로 정했다.

희석 확인도 비목표다. 사용자가 2026-10-20 에 생략하기로 정했다. 원칙 전체 비교가 2건 안팎 흔들려 판정에 쓸 수 없다는 2026-10-18 판단을 유지한 결정이다. 그래서 채택한 문안의 근거 기록에는 "조항별 클린룸 시험에서만 확인했고 원칙 전체 속의 효과는 확인하지 않았다"를 가정으로 적는다.

대화 답의 기계 검사도 비목표다. 사용자가 2026-10-20 에 파일만 검사하기로 정했다(「기계 검사」).

판정 모델과 선행연구 검증자의 모델 교체는 범위 밖이다. 사용자가 이 작업을 병합한 뒤 별도 프로젝트로 하기로 정했다.

2026-10-18 spec 15행은 "이미 같은 지시가 있었는데도 실패한 행동에는 지시 문장을 더하지 않는다"를 반목표로 정했다. 이 문서는 그 반목표를 "지시의 작용 시점과 형태를 바꾸거나 지시 대신 기계 검사를 둔다"로 바꾼다. 사용자가 2026-10-20 에 동의했다.

## 생성 제약

아래 표가 조항을 쓰고 고칠 때의 기준이다. 근거는 2026-10-20 선행연구 기록(`docs/superpowers/reviews/2026-10-20-generation-constraints-prior-art.md`)과 저장소의 측정 기록이다.

| 제약 | 모델의 실제 동작 | 조항 작성 규칙 | 근거 |
|---|---|---|---|
| 순차 생성 | 모델은 토큰을 앞에서부터 하나씩 내고 이미 낸 토큰을 되돌리지 못한다. 앞 토큰이 뒤 생성을 끌고 간다 | 생성 중에 지킬 조항은 결정점에서 정할 일을 지시하라 | 정렬 효과가 첫 몇 토큰에 몰린다는 연구(ICLR 2025, 안전 정렬 대상)가 있다. 형식 제한이 추론을 떨어뜨린다는 연구(arXiv 2408.02442)도 있다. Claude 4.6 이후 모델은 프리필을 지원하지 않아 첫 토큰을 API 로 고정할 수 없다. 결정점 지시의 효과를 측정한 연구는 찾지 못했다 |
| 재작성 가능 여부 | 대화 답은 스트리밍으로 나가 고칠 수 없다. 파일로 쓰는 글은 전달 전에 고칠 수 있다 | 다 쓴 뒤에야 판정할 수 있는 조항은 재작성할 수 있는 층에만 두어라. 그 층에서도 재확인 지시보다 기계 검사 결과를 먼저 주어라 | 스트리밍 가드레일 문서(NVIDIA NeMo)는 이미 사용자에게 간 출력을 거둘 수 없다고 적는다. Opus 5 가이드는 명시적 재확인 지시가 과잉 검증을 낳으므로 지우라고 권한다 |
| 기본 습관 | 모델은 지시와 무관하게 선호하는 형식이 있고, 그 형식은 모델 세대마다 다르다 | 습관과 반대되는 조항은 피할 형태를 정의하고 원하는 형태를 함께 주어라. 지목형과 긍정형 중 어느 쪽이 나은지는 조항별 클린룸 시험으로 확인하라 | 저장소 측정이 지목형을 지지한다. 2026-10-18 금지어 목록 시험에서 금지어를 이름으로 댄 목록은 위반 11건, 이름 없이 대체어만 준 지시형은 16건이었다. 대화 답의 금지어 빈도는 2회 대 32회였다(`docs/domain-korean.md`). 2026-10-12 시험에서 위반 형태를 정의한 `BULLET-SCOPE` 강화 문구는 위반을 64건에서 2건으로 줄였다. 외부 근거는 반대 방향이다. Anthropic 지침과 Opus 5 가이드는 지목하지 말고 원하는 형태를 말하라고 권하고, arXiv 2601.08070 은 금지 단어의 언급이 그 단어를 부른다고 보고한다. 사용자는 2026-10-20 에 저장소 측정을 우선하기로 정했다 |
| 모호함의 증폭 | 해석이 둘인 지시에서 모델은 한 해석으로 수렴한다 | 조항을 해석이 하나가 되게 써라. 판정 경계가 흐린 조항은 경계 사례를 채점 기준에 적어라 | 모호한 과제에서 모델이 한 해석으로 수렴한다는 연구가 있다. GPT-4.1 가이드는 GPT-4.1 이 이전 OpenAI 모델보다 지시를 문자 그대로 따른다고 적는다. Claude 모델에 대한 같은 근거는 찾지 못했다. "습관 쪽으로 수렴한다"는 구체적 전제는 가정이다. 2026-10-12 `COUNT-EARNS`·`SUBJECT-OBJECT` 의 채점 판정이 흔들린 사례로 확인할 수 있다 |
| 주의의 한계 | 함께 실린 지시가 많을수록 지시마다의 준수율이 떨어진다 | 상시 지시에는 행동 지시와 짧은 예시만 두고, 정의와 예외 목록은 채점 기준과 참고서로 옮겨라 | 지시 500개에서 최상위 모델의 정확도는 68% 였다(arXiv 2507.11538). 2026-10-12 시험에서 `NO-MID-MOD` 위반은 그 조항만 강화했을 때 22건, 40개 조항을 함께 강화했을 때 52건이었다. 반면 Claude Code 세션 1,650개를 본 연구(arXiv 2605.10039)는 파일 크기의 효과를 검출하지 못했고, 그 연구가 시험한 지시는 사소한 주석 하나였다. Anthropic 지침은 예시를 형식 조종의 가장 믿을 만한 방법으로 보므로 예시는 빼지 않는다 |
| 자기 판정의 한계 | 모델이 자기 출력의 문체 규칙 위반을 얼마나 찾는지는 측정되지 않았다. 문자열 규칙은 기계가 더 싸고 일정하게 판정한다 | 문자열로 잡히는 위반은 지시하지 말고 기계 검사로 찾아 그 결과를 모델에 돌려주어라 | 외부 피드백 없는 자기 교정이 어렵다는 2023년 연구(arXiv 2310.01798)가 있다. 그러나 Opus 5 가이드는 Opus 5 가 지시 없이도 자기 실수를 잘 고친다고 적고, Self-Correction Bench(arXiv 2507.02778)는 추론 모델의 자기 교정이 낫다고 보고한다. 신뢰할 외부 피드백이 있으면 자기 교정이 잘 된다는 서베이(arXiv 2406.01297)와, 저장소의 "판단 앞에 기계 검사를 둔다" 규칙(`skills/dispatching-lenses/SKILL.md`)이 이 작성 규칙을 받친다 |

### 이 기준을 둘 위치

생성 제약은 저장소 CLAUDE.md 「에이전트원칙을 고칠 때」의 퇴고 기준에 질문으로 들어간다. 질문은 "이 조항은 결정점에서 작용하는가, 아니면 재작성할 수 있는 층이나 기계 검사에 있는가"와 "습관과 반대되는 조항이면 피할 형태와 원하는 형태를 함께 주는가"다. 표와 근거는 `docs/domain-discipline.md` 의 새 절에 둔다.

원칙 본문에는 생성 제약을 넣지 않는다. 원칙 본문에 넣으면 실행 중인 모델에게 자기 한계를 설명하는 문장이 늘어 주의의 한계 제약을 어기기 때문이다.

## 현행 조항 대조

아래는 2026-10-18 원칙을 생성 제약으로 대조한 결과다. 각 행의 변경안은 담당 과제의 조항별 클린룸 시험을 통과해야 채택한다.

| 조항 | 어긋난 제약 | 현행의 문제 | 변경 방향 | 담당 과제 |
|---|---|---|---|---|
| `BULLET-SCOPE` | 순차 생성 | "한 항목이 여러 문장이 되면 산문으로 써라"는 둘째 문장을 쓰기 시작할 때에야 해당 여부가 정해지고, 그때는 이미 불릿 안이다 | 불릿을 시작하기 전에 항목마다 한 문장으로 끝나는지 정하고, 아니면 처음부터 산문으로 쓰게 한다 | T4 |
| `NO-MID-MOD` | 순차 생성, 규칙 충돌 | 용어 풀이 문장("X는 ~하는 Y다")이 `TERM-EXPLAIN` 을 따르면 긴 관형절이 된다 | 용어 풀이를 앞 문장에서 동작으로 먼저 쓰고 그 이름을 다음 문장에 두게 한다 | T4 |
| `SECTION-HEAD` | 순차 생성 | "문단이 넷 이상이거나 25줄이 넘는 글"은 다 쓴 뒤에야 해당 여부가 정해진다 | 답을 시작할 때 다룰 주제가 둘 이상이면 절 제목으로 시작하게 한다 | T5 |
| `COUNT-EARNS` | 모호함의 증폭 | "결정이 바뀔 때만"의 경계가 흐려 채점이 흔들렸다 | 행동 지시는 "목록 앞에 개수를 예고하지 마라"처럼 결정점 문장으로 남기고, 경계 사례는 채점 기준으로 옮긴다 | T5 |
| `EDIT-PRIORITY` | 재작성 가능 여부, 자기 판정의 한계 | 다 쓴 뒤 모델이 스스로 「공통」 위반을 다시 찾는다 | 기계 검사 경고를 받은 위반을 고치게 하고, 문자열로 잡히지 않는 위반만 모델이 본다 | T5(T6 뒤) |
| `CHECKABLE` | 규칙 충돌 | 단계마다 "확인:"을 붙이게 해 2026-10-12 위반이 15건에서 0건이 되었으나, 그 형태가 굵은 라벨 불릿을 만들어 `BULLET-SCOPE` 와 충돌한다 | 확인 방법을 단계 문장 안에 쓰게 한다 | T7 |

`BULLET-SCOPE`·`SECTION-HEAD` 는 2026-10-18 spec 이 "쓰는 순간에 판단할 수 있어 고치지 않는다"고 판단한 조항이다. 이 문서는 그 판단을 바꾼다. 실사용 답의 약 24% 가 `BULLET-SCOPE` 를 어긴 관찰과, 위 표의 "현행의 문제" 칸이 근거다.

### 커밋 8b4a05a 의 후보 문안

2026-10-12 강화 시험은 8b4a05a 문안을 측정하지 않았다. 그 시험의 강화 문구는 8b4a05a 와 다른 문안이다. 그래서 8b4a05a 문안은 모두 측정되지 않은 후보이고, 사용자가 2026-10-20 에 방향이 맞는 후보만 시험하기로 정했다.

| 조항 | 8b4a05a 문안 | 처분 |
|---|---|---|
| `SUBJECT-OBJECT` | 주체를 확인할 수 없으면 짐작해 채우지 말고 모른다고 적어라 | T8 에서 시험한다 |
| `NO-MID-MOD` | 용어 풀이 예시 | T4 의 문안 재료로 쓴다 |
| `YAGNI` | 요청 밖 개선 제안 | T8 에서 시험한다 |
| `VOCAB-PREF` | 번역할 때 직역하지 마라 | T8 에서 시험한다 |
| `ANTI-LIMIT` | "A 빼고 B만" 대구 | T8 에서 시험한다 |
| `BULLET-SCOPE` | 항목마다 굵은 라벨을 붙여라 | 시험하지 않는다. 이 작업이 줄이려는 형식을 지시하는 문안이다 |
| `SECRETS` | 환경 변수 이름이나 가린 값(`sk-***`)으로 적어라 | 시험하지 않는다. 비밀을 적는 범위를 넓히는 허용 문안이다 |

2026-10-12 기록의 YAGNI 1→6, VOCAB-PREF 0→3, ANTI-LIMIT 0→2 는 다른 15개 조항만 강화한 조건(half)의 결과다. 그 조건에서 이 세 조항은 원래 문구였으므로, 이 수치는 세 조항 문안의 효과가 아니다. 원본은 main 저장소의 미추적 폴더 `D:\projects\disciplined-coder\docs\superpowers\reviews\2026-10-12-clause-strengthening-check\half10.log` 에 있다.

## 기계 검사

기계 검사는 파일에만 적용한다. 파일은 전달 전에 고칠 수 있으므로 검사 결과가 수정으로 이어질 수 있다. 대화 답은 기계 검사 없이 결정점 지시로만 다룬다. 이 범위는 사용자가 2026-10-20 에 정했다.

대화 답을 검사하지 않는 이유는 아래와 같다. Stop 훅은 턴이 끝난 뒤 실행되므로 이미 나간 답을 고칠 수 없고, 다음 답에 넛지를 주는 일만 할 수 있다. 그 넛지는 위반 형태를 다시 맥락에 싣는다. 또 Stop 훅 입력의 `last_assistant_message` 는 턴의 마지막 텍스트만 담아, 도구 호출 사이의 중간 답을 보지 못한다(https://code.claude.com/docs/en/hooks, 2026-10-20 확인).

검사 대상 형태는 굵은 라벨로 시작하는 두 문장 이상의 불릿, 목록 앞의 개수 예고, 제목의 개수다. 금지어는 기존 훅이 이미 검사하므로 새 검사에 넣지 않는다. 펜스 코드 블록, 백틱 안, `>` 인용 줄은 검사하지 않는다. 원칙의 「공통」이 인용과 코드를 대상에서 빼기 때문이다.

기존 훅의 구조는 아래와 같다(`hooks/hooks.json`).

| 훅 | 실행 시점 | 하는 일 |
|---|---|---|
| `hooks/doc_word_pretooluse.sh` | Write·Edit 실행 전 | 금지어가 든 쓰기를 거부한다 |
| `hooks/doc_word_posttooluse.sh` | Bash 실행 뒤 | Bash 가 쓴 파일(`bash_write_targets`)에서 금지어를 찾아 알린다 |

Bash 로 고친 파일은 모드와 무관하게 Write·Edit 훅에 걸리지 않는다. 그래서 Bash 쪽 검사는 기존 Bash 훅에 붙인다. Write·Edit 쪽 검사는 기존 PostToolUse 훅 중 하나에 붙여 프로세스 수를 늘리지 않는다. 어느 훅에 붙일지는 구현자가 `hooks/hooks.json` 을 보고 정한다.

새 검사는 경고만 내고 거부하지 않는다. 개수 예고 같은 정규식은 오탐이 많을 수 있어, 거부하면 정상 문서의 저장을 방해하기 때문이다. 새 검사는 기존 스위치 `DISCIPLINED_CODER_REPLY_CHECK` 로 함께 꺼진다. 이 두 결정은 이 문서 작성자의 판단이다.

검사 대상 경로는 `hooks/_spec_marker.sh` 의 `path_is_banned_target` 을 쓰지 않는다. 그 함수는 spec·plan·Claude 메모리·이 저장소의 문서를 빼는데, 그러면 작업 지시서 대부분이 검사에서 빠진다. 새 검사는 `.md` 파일 전부를 대상으로 하되, 봉인된 리뷰 기록(`docs/superpowers/reviews/`)과 Claude 메모리만 뺀다. 경고만 내므로 범위를 넓혀도 저장을 막지 않는다. 이 결정도 이 문서 작성자의 판단이다.

경고를 받은 세션이 실제로 고치는지는 이 문서의 과제로 확인하지 않는다. 그래서 목표는 "경고를 돌려준다"까지만 주장한다.

`skills/domain-plugin/SKILL.md` 35행은 "Stop 훅은 방금 쓴 답을 인자로 받지 않는다"를 전제로 적는다. 현행 문서는 `last_assistant_message` 를 제공하므로 이 전제는 낡았다. 대화 답 검사를 만들지 않으므로 그 항목의 결론은 유지하고, T6 에서 전제 문장만 고친다.

## 측정

조항 변경은 조항별 클린룸 시험으로 확인한다. 도구는 `scripts/eval_clause.sh` 이고, 단위는 `evals/principles/clauses/<조항>/` 의 current.md·new.md 다. 과제는 `evals/principles/cases/` 에 둔다. 생성 모델은 claude-opus-5-5, 판정 모델은 claude-sonnet-5-5 다. 이 시험은 조항 파일 하나만 `CLAUDE.md` 로 싣는다(`evals/principles/README.md`).

2026-10-12 강화 시험의 과제와 채점 기준(`clauses/<조항>/tasks.json·rubric.md`)은 cases 형식으로 옮겨 쓴다. 원본은 main 저장소의 미추적 폴더 `D:\projects\disciplined-coder\docs\superpowers\reviews\2026-10-12-clause-strengthening-check\` 에만 있다. 구현자는 그 폴더를 읽기만 하라.

T4 는 형태를 고르는 과제가 아니라, `BULLET-SCOPE`·`NO-MID-MOD` 의 문안을 정하는 과제다. 구현자는 결정점 문안, 지목형 문안, 긍정형 문안을 각각 현행과 짝지어 조항별 클린룸 시험을 실행하라. 채택 조건을 통과한 문안 중 위반이 가장 적은 문안을 채택하고, 위반 수가 같으면 짧은 문안을 채택하라. T5 는 T4 결과를 문안 초안의 방향으로만 참고하고, 조항마다 따로 조항별 클린룸 시험을 거친다. 위반 1~2건 차이가 측정 흔들림 안에 들기 때문이다(`evals/principles/README.md` 86행).

`EDIT-PRIORITY` 의 변경안은 평가 세션이 도구를 끄고 실행되므로(`scripts/_eval_run.py`) 훅 경고를 받을 수 없다. 그래서 구현자는 T6 검사기의 경고 문구를 과제 프롬프트에 넣어 시험하라.

T7 의 Concise 조건은 시험 도구가 생성 호출에 시스템 프롬프트를 덧붙여야 실행된다. 지금 `scripts/_eval_run.py` 에는 그 인자가 없으므로 T7 에서 추가한다.

Concise 는 Claude Code 의 출력 스타일 설정이다. 이 PC 세션에서 켜져 있고, 그 시스템 프롬프트는 "다른 지침과 충돌하면 이 규칙이 이긴다"고 선언한다. 반대로 원칙 머리 문단은 하네스 기본 지침보다 원칙을 우선하라고 선언한다. T7 은 이 두 선언의 충돌을 다룬다. 원칙 조항 `REVIEW-DELIVERABLE` 의 "남에게 전달할 산출물"은 조항 문구 변경이라 T10 의 용어 정리에 넣지 않는다.

과제의 선후는 아래와 같다.

- T1 은 T3 보다 먼저 끝나야 한다. 기준선이 T3 의 측정 대상이기 때문이다.
- T2 는 T3·T4·T5·T7·T8 보다 먼저 끝나야 한다. 시험 도구가 API 키를 쓰기 때문이다.
- T6 은 T5 의 `EDIT-PRIORITY` 시험보다 먼저 끝나야 한다. 그 시험이 T6 의 경고 문구를 쓰기 때문이다.
- T4 의 `NO-MID-MOD` 문안과 T7 의 `NO-MID-MOD`×`TERM-EXPLAIN` 처방은 같은 문안을 다루므로 T4 에서 함께 시험한다.
- T10 은 다른 모든 과제 뒤에 한다.
- T1·T6·T9 는 API 키 없이 진행할 수 있다.
