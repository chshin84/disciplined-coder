# 선행연구 에이전트의 계획 수립과 탐색 방식 개선 설계

## 용어

이 문서의 용어는 아래 뜻으로 쓴다.

| 용어 | 뜻 |
|---|---|
| 오케스트레이터 | `agent-prior-art` 스킬을 따르는 메인 세션이다. 프로토콜을 쓰고 워크플로를 실행하고 보고한다 |
| 프로토콜 | 오케스트레이터가 실행 전에 쓰고 사용자에게 승인받는 연구 계획이다. 워크플로 `args`로 넘어간다 |
| contrast·survey | 프로토콜의 `mode` 값이다. contrast 는 대조 대상의 문제(이슈)만 찾고, survey 는 이슈와 근거 지도를 함께 낸다 |
| 근거 지도 | survey 연구자가 사례마다 한 행씩 채우는 표(`evidence_map`)다 |
| 네 축 | 근거 지도 행의 `axes`다. 목적·메커니즘·평가·적용 대상마다 선행 사례 쪽 서술(`prior`)과 대조 대상과 같은지(`same`)를 적는다 |
| 결정 근거 탐색 | 「상황별 전략」의 상황 하나다. 사용자가 고르려는 결정 후보안의 근거를 찾는다 |
| 프롬프트 모드 | 연구자 프롬프트 첫 줄 `MODE:`의 값이다. 현행 값은 `explore`·`synthesize`이고, 이 설계가 `scout`를 추가한다 |
| 실행 차례 | 프로토콜의 `round` 값이다. 현행은 첫 탐색이 1, 공백 라운드가 2 이고, 이 설계가 둘러보기 0 을 추가한다 |

## 의도

선행연구 에이전트(`agent-prior-art`)의 검증 단계는 2026-10-20·10-22 측정으로 모델과 묶음 크기까지 정해졌다. 그러나 앞쪽 단계인 프로토콜 수립과 연구자 탐색은 측정을 거치지 않았다. 이 PC의 세션 기록에서 그 단계의 결함이 드러났다.

2026-10-24 리뷰 점검 항목 실행(세션 `75d7bf26`)에서 사용자는 결과의 용도를 두 번 다시 설명했다. 13:18 발언은 "연구를 토대로, 렌즈를 어떻게 개선해야, 한국인 비개발자가 클로드 코드 활용을 전박적으로 나아질수있도록 서포트 할수 있을지"이고, 13:24 발언은 "에너지와 시간을 적게, 토큰 사용 최적화 등의 멀티 오브젝트를 per task 단위로"다. 프로토콜에는 용도를 적을 칸이 없다.

그래서 오케스트레이터는 "사용자는 비개발자"라는 제약을 `target` 문자열에 끼워 넣었다. 이미 확인한 자료는 하위 질문의 `exclude`에 끼워 넣었다. 또 오케스트레이터는 13:18 발언을 승인으로 해석하고 하위 질문 sq5 를 추가한 뒤, 바뀐 프로토콜을 다시 보이지 않고 실행했다.

같은 실행에서 survey 연구자는 contrast 용 틀을 그대로 썼다. sq5 연구자의 `notes`는 "검토한 관점은 다섯 가지다. 기시감… 결말… 전이… 기준선… 붐빔"으로 시작한다. sq2 연구자는 survey 인데도 반박형 이슈 여섯 건을 냈다.

종합 결과의 Perry·Stieg 행은 네 축이 모두 `same: false`였다. 그런데도 오케스트레이터는 그 행을 핵심 결론 근거로 썼다. 원인은 연구자 지시문(`agents/prior-art-researcher.md` 「explore 모드」)이 모드와 무관하게 하나라는 데 있다.

질의 금지 목록에도 결함이 있었다. 사용자 승인 화면의 목록은 "…, chshin, 사용자 이름, 파일 경로 일체"였으나, 실행 args 의 `forbidden_terms`에서는 "사용자 이름"과 "파일 경로 일체"가 빠졌다. 범주는 문자열 검사에 넣을 수 없기 때문이다.

경로는 워크플로의 경로 형태 정규식이 대신 검사한다. 그러나 사람 이름 범주를 검사하는 기계 장치는 없다. 그리고 워크플로의 `checkQueries`는 검색이 나간 뒤에 위반을 기록만 하므로, 빠진 낱말이 검색어에 들어가면 되돌릴 수 없다.

2026-10-20 실행과 2026-10-21 실행은 상황별 분해표대로 진행했고 `overall_status`가 `ok`였다. 그래서 고정 분해가 결과를 나쁘게 했다는 근거는 기록에 없다.

사용자는 2026-10-25 에 방향을 정했다. 사용자는 훑은 뒤 세부로 들어가기와 나누어 풀기를 기본 전략으로 쓰되, 오케스트레이터와 연구자의 동작을 제한하는 방향은 원하지 않는다고 했다. 이어서 사용자는 작성자가 대화에서 제안한 항목(용도 칸, 제약 칸, 재승인, survey 지시문 분리, 금지 목록 펼치기, 먼저 둘러보기, 선택형 탐색 전술)을 모두 넣으라고 했다.

## 설계 원칙

사용자는 2026-10-25 에 "되돌릴 수 없는 일만 규칙으로 강제하고, 조사 방법은 기본값으로 둔다"를 원칙으로 정했다.

규칙으로 남기는 대상은 질의 금지, 사용자 승인 없이 실행하지 않기, 인용 원문 확인이다. 질의 금지는 검색어가 연구자 안에서 만들어지므로 검색 전에 기계로 차단할 수 없다. 그래서 질의 금지는 연구자 지시, 오케스트레이터의 실행 직전 목록 대조, 워크플로의 사후 검출로 지킨다.

기본값으로 두는 대상은 먼저 둘러보기, 상황별 하위 질문 분해, 연구자의 탐색 전술이다. 오케스트레이터가 기본값과 다르게 하면 그 이유를 프로토콜에 한 줄로 적는다.

연구자에게는 방법을 지시하지 않고 목표·출력 형식·도구 안내·과제 경계를 준다. 이 구성은 Anthropic 의 다중 에이전트 연구 시스템 글이 하위 에이전트에게 주라고 한 요소를 따른다("Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries.", https://www.anthropic.com/engineering/multi-agent-research-system, 2026-10-25 원문 확인).

## 목표

- 사용자가 생략한 용도와 제약이 연구자와 종합 단계까지 전달된다.
- 오케스트레이터가 프로토콜을 바꾸면 사용자가 바뀐 내용을 보고 다시 승인한다.
- survey 연구자가 결정에 쓸 간접 근거를 버리지 않는다.
- 사용자에게 보인 질의 금지 목록과 실행 args 의 목록이 같다.

## 비목표

아래 항목은 작성자가 근거 사례가 없거나 측정을 마친 항목이라 판단해 범위에서 뺐다.

- 검증 단계(추출 검증자, 판정 에이전트, 지도 대조 에이전트)와 최종 판정 순서는 바꾸지 않는다.
- 상한 값(연구자 통상 2·최대 20, 턴 20, 공백 라운드 1회, 판정 묶음 20)은 바꾸지 않는다.
- 발동 넛지(`hooks/prior_art_nudge_userpromptsubmit.sh`)는 바꾸지 않는다.
- 공백 판단 때 용도 대비 커버리지를 따로 보는 절차는 넣지 않는다.
- 과제를 구성요소(DAG)로 고정 분해하는 절차는 넣지 않는다.

## 실패로 보는 결과

아래 결과가 나오면 기능이 동작해도 실패로 본다.

- 새 칸 때문에 사용자가 승인하는 데 드는 시간이 늘어난다.
- 둘러보기만을 위한 승인 턴이 생긴다.
- 새 지시문이 연구자의 탐색 순서를 고정한다.

새 칸은 오케스트레이터가 채우고, 사용자는 틀린 칸만 고친다.

## 변경 범위

### A. 프로토콜의 내용

프로토콜에 아래 칸을 추가한다. `purpose`는 근거 지도의 `axes.purpose`와 이름이 겹치므로 쓰지 않는다.

| 칸 | 내용 | 빈 값 |
|---|---|---|
| `intended_use` | 이 결과로 누가 무엇을 정하는지와, 그 결정에서 최적화할 기준을 적은 문자열이다 | 허용하지 않는다. 오케스트레이터가 추론해 채우고 추론이라고 표시한다 |
| `constraints` | 대화에서 이미 정한 조건, 기각한 대안, 이미 확인한 자료를 적은 문자열 배열이다 | 빈 배열을 허용한다 |

작성자는 `intended_use`를 객체 대신 문자열 하나로 정했다. 칸이 적을수록 승인 화면이 짧기 때문이다.

워크플로는 `intended_use`와 `constraints`를 탐색 입력, 둘러보기 입력, 종합 입력에 넘긴다. `target`에는 대조 대상만 적는다. `exclude`에는 그 하위 질문의 범위 밖만 적고, 이미 확인한 자료는 `constraints`에 적는다. 결정 근거 탐색에서 기각한 후보안은 `target`에서 빼고 `constraints`에 적는다.

오케스트레이터는 대화 맥락에서 `question`·`target`·`intended_use`·`constraints`를 도출한다. 승인 화면에서 오케스트레이터는 칸마다 사용자 발언과 자기 추론을 나눠 보인다. 근거가 된 사용자 발언이 있으면 그 발언을 인용한다.

질의 금지 목록에는 범주를 쓰지 않고 낱말로 펼친다. 경로는 워크플로의 경로 형태 정규식이 맡으므로 목록에 넣지 않는다. 오케스트레이터는 승인 화면의 목록과 실행 args 의 `forbidden_terms`가 같은 문자열 목록인지 실행 직전에 대조한다.

사람 이름처럼 식별성이 큰 낱말을 펼치면, 오케스트레이터는 기록 파일에 범주 이름과 펼친 낱말의 개수만 적고 낱말 자체는 적지 않는다(2026-10-25 사용자 결정). 리뷰 기록은 커밋되고 봉인되므로, 원격으로 보내면 낱말을 지울 수 없기 때문이다. 실행 args 는 기록 폴더에 저장하지 않는다. 다만 워크플로 반환값의 `query_violations[].query`와 연구자 출력의 `queries`에는 위반 검색어가 원문으로 남는다. 그래서 오케스트레이터는 원본을 기록 폴더에 쓰기 전에 그 두 칸에서 금지 낱말을 범주 이름으로 가린다(2026-10-25 plan 리뷰 반영, 사용자 결정의 적용 범위를 작성자가 원본 파일까지 넓혔다).

### B. 프로토콜의 합의

사용자의 답이 프로토콜의 칸을 하나라도 바꾸면, 오케스트레이터는 바뀐 칸만 다시 보이고 승인을 받은 뒤 실행한다. 오케스트레이터는 사용자가 실행을 말한 메시지("이대로 실행", "진행해" 같은 메시지)만 승인으로 본다. 목적이나 조건을 답한 메시지는 승인으로 보지 않는다.

이 재승인은 현행 1단계의 불변 조건("승인이 없으면 실행하지 않는다")을 바뀐 프로토콜에도 적용하는 규칙이다. 그래서 사용자가 선택 질문을 원하지 않는다고 지시했어도 오케스트레이터는 재승인을 생략하지 않는다. 그때 오케스트레이터는 선택 도구 대신 산문으로 바뀐 칸을 보이고 실행해도 되는지 한 문장으로 묻는다(작성자 판단).

오케스트레이터는 승인받은 프로토콜을 승인마다 기록 파일에 추가한다. 앞 승인의 전문은 지우지 않고, 뒤 승인에는 바뀐 칸과 승인 사실을 적는다.

### C. 먼저 둘러보기

먼저 둘러보기는 하위 질문을 나누기 전에 주제의 자료 지형을 확인하는 단계다. 오케스트레이터는 첫 승인 화면에 `intended_use`·`constraints`·질의 금지 목록·연구자 수 상한과 하위 질문 초안을 함께 보인다. 둘러보기는 그 첫 승인 안에 포함하고, 둘러보기만을 위한 승인 턴을 따로 두지 않는다.

사용자는 2026-10-25 에 둘러보기를 기본으로 켜기로 정했다. 리뷰는 이 기본값이 대부분의 실행에서 워크플로 실행 하나, 연구자 하나, 승인 턴 하나를 늘린다고 지적했고, 사용자는 그 비용을 알고 정했다. 아래 조건에서는 오케스트레이터가 둘러보기를 생략하고 이유를 프로토콜에 적는다(작성자 판단).

- 대화에서 이미 그 주제의 자료를 확인했다.
- 상황이 사실 확인이다.
- 상황이 spec 대조이고, spec 이 메커니즘을 이미 나눠 두었다.

둘러보기 실행은 프로토콜 `round`를 0 으로 둔 워크플로 실행이다. 워크플로는 `round`가 0 이면 연구자 하나를 프롬프트 모드 `scout`로 실행한다. 검증 단계와 종합 단계는 실행하지 않고, 질의 경계 검사는 실행한다.

둘러보기 연구자의 입력은 `{ question, situation, target, intended_use, constraints, draft_subquestions, forbidden_terms }`다. 지시문은 목표와 출력과 경계만 준다. 목표는 주제의 자료 묶음과 하위 질문 후보를 찾는 일이고, 경계는 질의 금지와 도구 호출 상한이다. 상한은 10회다. Anthropic 의 같은 글이 "Simple fact-finding requires just 1 agent with 3-10 tool calls"라고 적었고, 둘러보기는 연구자 하나가 넓고 얕게 찾는 단계이기 때문이다(2026-10-25 원문 확인, 작성자 판단).

둘러보기 연구자의 출력은 주제 묶음, 묶음마다 대표 출처, 하위 질문 후보와 그 근거, `queries`, `principles_applied`다. 키 이름은 구현자가 정한다.

`round`가 0 인 워크플로 반환값은 `{ round, researchers, query_violations, scout }`다. `researchers`는 `[{ id: "scout", output }]`이고 `scout`는 둘러보기 출력이며, 실패하면 `null`이다. 검증을 실행하지 않으므로 `passed`·`coverage`·`overall_status` 같은 검증 칸은 두지 않는다.

둘러보기 결과는 검증하지 않으므로 판정과 결론에 쓰지 않는다. 오케스트레이터는 둘러보기 결과에서 주제어와 범위만 하위 질문으로 옮긴다. 사례 이름과 결말 서술은 하위 질문 문장에 옮기지 않는다.

둘러보기 출처는 `constraints`의 '이미 확인한 자료'로 보지 않는다. 그 출처를 연구자가 다시 찾아 보고해야 검증 단계를 거치기 때문이다. 워크플로의 둘러보기 출력 스키마는 정해진 칸 밖의 칸을 허용하지 않는다(`additionalProperties: false`). 그래서 둘러보기 연구자가 사례 칸을 내도 반환값에 남지 않는다(2026-10-25 plan 리뷰 반영, 작성자 판단).

둘러보기 결과로 하위 질문이 바뀌면 오케스트레이터는 B 의 규칙대로 바뀐 하위 질문만 보이고 실행 승인을 받는다. 하위 질문이 그대로면 오케스트레이터는 둘러보기 직후 `round` 1 로 본 탐색을 실행한다.

「상황별 전략」 표의 「하위 질문 분해」 열은 기본값으로 바꾼다. 오케스트레이터는 둘러보기 결과에 맞춰 다르게 나눌 수 있고, 다르게 나누면 이유를 프로토콜에 적는다.

둘러보기 연구자는 「실행할 때 지킬 상한」의 탐색 모드 연구자 수에 세지 않는다. 종합 모드 연구자와 같이 실행 수가 하나로 정해져 있기 때문이다. 공백 라운드는 둘러보기를 다시 실행하지 않고, 첫 탐색과 같은 `intended_use`·`constraints`를 넘긴다.

### D. 연구자의 탐색

탐색 모드(`MODE: explore`) 지시문을 프로토콜 `mode`에 따라 contrast 지시문과 survey 지시문으로 나눈다.

contrast 지시문에서는 체크리스트와 판정 규약을 바꾸지 않는다. 바뀌는 내용은 둘이다. survey 분기 문장("입력의 `mode`가 `survey`이면 …")을 빼고, `intended_use`·`constraints`를 읽으라는 문장을 추가한다.

survey 지시문은 결정에 쓸 근거를 모으는 지시로 새로 쓴다. 지시문에 넣을 내용은 아래와 같다.

- 연구자는 `intended_use`를 근거의 우선순위 기준으로 쓴다.
- 연구자는 `intended_use`와 맞지 않아 뺀 근거를 `notes`에 사유와 함께 남긴다.
- 연구자는 네 축이 대조 대상과 모두 같지 않은 행도 근거 지도에 넣는다.
- 연구자는 다른 축을 `note`에 적고, 그 차이가 근거의 이전 가능성에 주는 영향을 적는다.
- 결정 근거 탐색이면 연구자는 행마다 `bearing`에 그 근거가 어느 후보안을 어느 방향으로 움직이는지 적는다.
- 체크리스트(기시감·결말·전이·기준선·붐빔)는 survey 에서 강제하지 않는다.
- 연구자는 반박이나 실패를 발견했을 때만 `issues`에 올린다.

survey 지시문은 탐색 전술을 고를 수 있는 방법으로만 소개한다. 연구자는 하위 질문에 맞는 방법을 고르고, 고른 방법을 `notes`에 적는다. 소개할 전술은 아래와 같다.

- 짧고 넓은 검색어로 시작해 좁혀 가기를 소개한다. 근거는 앞의 Anthropic 글이다("start with short, broad queries").
- 후보안마다 사용 사례와 결말 찾기를 소개한다. 작성자 제안이며 출처를 확인하지 않았다.
- 인용 따라가기를 소개한다. 찾은 출처의 참고문헌과 그 출처를 인용한 자료를 따라가는 방법이다. 작성자는 소프트웨어공학 문헌 연구의 snowballing 이라고 기억하지만, 출처는 구현 전에 확인한다.
- 실패·포기·회고 자료 찾기를 소개한다. 작성자 제안이며 출처를 확인하지 않았다.

contrast 지시문과 survey 지시문 모두 `constraints`의 기각한 대안과 이미 확인한 자료를 다시 찾아 보고하지 않게 한다.

종합 모드 지시문은 `intended_use`에 비추어 결론을 쓰게 한다. 결정 근거 탐색이면 종합 연구자는 결론마다 지지하는 후보안을 `conclusions[].supports`에 적는다.

종합 연구자는 결론에 쓴 행의 축 차이를 결론 문장에 함께 적는다. 네 축이 모두 다른 행은 결론의 단독 근거로 쓰지 않는다. 이 규칙은 10-24 의 Perry·Stieg 사례를 막으려고 작성자가 넣었다.

`bearing`과 `supports`는 대조 대상 쪽 판단이다. 2026-10-18 에 사용자는 대조 대상 쪽 판단(`same`, `note`)을 연구자가 책임지고 검증 단계가 판정하지 않게 정했다. 작성자는 그 결정을 `bearing`과 `supports`에도 적용했다. 그래서 검증 단계의 판정 대상(사례 이름, `outcome`, 각 축의 `prior`)과 입력 형식은 바뀌지 않는다.

## 리뷰 뒤 사용자 결정

2026-10-25 spec 리뷰가 `🔴`로 올린 결정을 사용자가 아래와 같이 정했다.

**둘러보기의 기본값.** 사용자가 기본 켜짐으로 정했다. 작성자가 권한 기본 꺼짐과, 워크플로 분기 없이 공백 라운드로 대신하는 안은 기각되었다.

**펼친 식별 낱말의 기록.** 사용자가 기록에는 범주 이름과 개수만 적는 안으로 정했다. 펼친 문자열을 그대로 적는 안은 되돌릴 수 없는 노출이라 기각되었다. 이름 범주를 펼치지 않는 안은 검색어에 이름이 들어가도 기계 검출이 없어 기각되었다.

## 구현자에게 맡기는 결정

- 둘러보기 출력의 키 이름은 구현자가 정한다.
- 레퍼런스 프롬프트 절에 survey 지시문을 둘째 `- system:` 줄로 둘지 다른 형식으로 둘지는 구현자가 정한다. `scripts/test_docs_drift.sh`는 현재 첫 `- system:` 줄만 연구자 정의와 대조하므로, 구현자는 contrast 지시문을 첫 줄에 두고 둘째 줄의 대조를 추가한다.
- 워크플로의 coverage·overall_status 계산은 `round` 0 에서 실행하지 않는다. 구현자는 그 분기가 계산 함수에 닿기 전에 반환하도록 둔다.

## 확인 방법

구현자는 아래 순서로 확인하라.

1. `scripts/` 아래 검사 스크립트를 모두 실행해 FAIL=0 인지 확인하라. 이어서 `claude plugin validate ./`가 `Validation passed`를 내는지 확인하라.
2. `test_workflow.sh`의 고정 입력으로 `round` 0 실행이 검증 단계 에이전트와 종합 에이전트를 실행하지 않는지, 반환값이 `{ round, researchers, query_violations, scout }`인지 확인하라.
3. 같은 고정 입력으로 탐색·둘러보기·종합 프롬프트에 `intended_use`·`constraints`가 들어가는지 확인하라.
4. 2026-10-24 실행의 프로토콜을 새 칸으로 다시 써 보라. 13:18·13:24 발언의 내용이 `intended_use`에, "비개발자"와 CheckEval·TICK 이 `constraints`에 들어가는지 확인하라. 이 확인은 실행 없이 문서로만 하라.
5. 같은 실행의 13:18 발언을 B 의 규칙에 비추어 보라. 그 발언이 승인으로 분류되지 않고 재승인 대상이 되는지 확인하라.
6. 같은 실행의 질의 금지 목록을 A 의 규칙으로 펼쳐 보라. 펼친 목록에 범주 문자열이 남지 않는지 확인하라.
7. survey 지시문과 종합 지시문에 「D. 연구자의 탐색」의 규칙(축이 다른 행 포함, 축이 모두 다른 행의 단독 근거 금지)이 들어 있는지 확인하라. 연구자의 실제 동작은 다음 실사용 실행에서 확인하라.
8. 실사용 효과는 다음 실사용 실행에서 확인하라. 사용자가 용도를 다시 설명했는지와 승인 턴 수가 늘었는지를 본다. 측정용 반복 실행은 하지 마라(2026-10-18 사용자 지시: 같은 질문 반복 시험 금지).
