# ultracode 검증 토글 설계 (ultracode-review)

## 배경 — 무엇이 문제였나
검증 레이어(§가)는 "단독 LLM 출력으로 끝내지 마라"를 트리거 표로 운용하는데, 멀티에이전트 워크플로
(ultracode)의 산출물이 표에 정의돼 있지 않았다. 실사용에서 관찰된 공백은 두 가지다 — (1) 워크플로
산출물에 검증 레이어가 적용되는지가 작성자 재량 판단으로 남는 **정의 공백**, (2) 검증 렌즈가
`reviewer-*` SKILL.md(정본)에서 도출되지 않고 즉석 프롬프트로 재작성되는 **SSOT 위반 위험**.

강제 수위는 판정 패널(3안 옹호 + 훅 타당성 조사 + 적대 판정)로 검토했다: 차단 훅(C안)은 전면 기각
(Workflow 도구의 훅 표면이 미문서화·위반 0건에 차단은 비례성 위반), 넛지 훅(B안)은 표면이 실측될
때까지 보류. 채택안은 **표 행 추가(A안 골격) + 사용자 토글(사용자 제안 D안)**이다 — 강제 수위를
플러그인이 박제하지 않고 사용자가 정하며, 전달 레일은 이미 검증된 issue-mode 패턴(세션 시작 주입)을
재사용해 미확인 훅 표면을 아예 우회한다.

## 결정 (요구사항)
- **R1. §가 트리거 표에 행을 추가한다.** 트리거는 '멀티에이전트 워크플로 작성·실행(발견·결론을
  산출하는 오케스트레이션)', 검증 대상은 '워크플로 에이전트의 발견·결론', 호출자는 기존 행들과 같은
  계약(호출자 열 = 방법 상세를 소유한 스킬)을 지켜 **`reviewer-*` 렌즈 스킬**을 가리킨다 — 렌즈
  스킬들이 이미 레퍼런스 프롬프트와 출력 스키마(방법 상세)를 소유하며, 워크플로 검증 단계는 그것을
  읽어 도출한다(즉석 재작성 금지). '문서 작성' 행의 괄호 병기 전례를 따라 셀에 "(워크플로 검증
  단계가 SKILL.md에서 렌즈를 도출)"을 병기한다. 강제 방식은 '상시 로드 원칙 + ultracode 검증
  모드(토글)'로 정직하게 적는다. 트리거를 '실행'이 아니라 '작성·실행'으로 두는 이유: 워크플로
  스크립트를 서브에이전트가 작성하는 경로에서도, 스펙을 넘기는 메인(원칙이 항상 로드됨)이 검증
  단계를 스펙에 포함시킬 책임을 지게 하기 위해서다.
- **R2. PC 전역 토글을 둔다.** 모드 값은 동작을 이름에 드러낸다(`EXPLICIT`) — `required`(워크플로에
  reviewer-* 렌즈 검증 단계 필수)와 `discretion`(기본 — Claude가 리스크에 비례해 재량 판단하되,
  결과 보고에 어떤 검증을 적용했는지·생략했다면 왜인지를 명시한다). on/off 같은 무의미 값은 쓰지 않는다.
- **R3. issue-mode 레일을 그대로 탄다.** 상태 파일은 `~/.claude/disciplined-coder/ultracode-review`
  한 줄, 토글 스크립트와 커맨드는 issue-mode 쌍(`scripts/issue-mode.sh`·`commands/issue-mode.md`)의
  패턴을 미러하고, 세션 시작 시 scaffold가 현재 모드 라인을 주입한다. 다음 세션부터 적용된다는 한계도
  issue-mode와 동일하게 안내한다.
- **R4. discretion이 기본값이다.** 현행 동작(재량 판단)을 기본으로 유지하고 required는 옵트인이다 —
  토큰 비용을 감수할지는 사용자가 정한다(위반 0건 상태에서 기본 강제는 비례성 위반이라는 패널 판정).
- **R5. 강제 메커니즘의 한계를 정직하게 남긴다.** required의 강제는 훅 차단이 아니라 세션 시작 주입
  지시(작성 시점 강제)다. 한계는 두 겹이다 — (1) 모드 라인은 scaffold stdout(additionalContext)으로
  **메인 세션에만** 들어가고 @import 관리블록에는 없으므로, 워크플로 스크립트를 서브에이전트가 작성하는
  경로에서는 지시가 작성자에게 아예 도달하지 않는다. 그 경로에서 required의 실효는 메인이 검증 단계를
  스펙에 옮겨 적는 릴레이(그 자체도 미강제)에 의존한다. (2) 지시가 도달한 작성자가 무시해도 막을 수
  없다(마커 게이트의 기존 한계와 동급). 또한 required는 §가의 리스크 비례 기본에 대한 **사용자 옵트인에
  의한 의도적 예외**다 — 리스크와 무관하게 항상 렌즈를 요구하는 것이 모순이 아니라 선택이다.
  Workflow 도구의 훅 표면(matcher·tool_input)이 공식 문서화되면 B안 넛지 훅으로의 승급을 재검토한다.

## 설계 (파일별)
- `agent-principles.md` — §가 표에 R1의 행을 추가한다. 표 아래 본문에 방법을 재진술하지 않는다.
  방법 상세의 소유는 이 spec이 아니다(spec은 아카이브되는 설계 기록이지 살아있는 SSOT가 아니다) —
  렌즈 정의는 `reviewer-*` 스킬이(기존 소유), 모드의 의미는 토글 코드(주입 문구·커맨드 description)가
  각각 소유한다.
- `scripts/_scaffold_common.sh` — `SCAFFOLD_WHITELIST`에 `ultracode-review`를 추가하고,
  `scaffold_resolve_ultracode_review()` 함수를 issue-mode 판정 함수와 같은 꼴로 둔다(부재 시
  `discretion` 결정론 생성 + 첫 설치 1회 안내, 불명값은 discretion 폴백 + WARNING). 두 scaffold가
  자동으로 공유한다(공통 헬퍼가 SSOT). **출력 변수는 issue-mode의 `mode_line`/`mode_note`와 절대
  공유하지 않고 `ucr_mode_line`/`ucr_mode_note`로 분리한다** — 같은 변수를 쓰면 나중 resolve가 먼저
  값을 덮어써 첫 토글의 라인·1회 안내가 조용히 유실된다(`EXPLICIT`·`FAIL-LOUD`).
- `scripts/scaffold.sh` — 헬퍼 호출 한 줄과 모드 라인 stdout 주입을 추가한다. **주입 순서는
  issue-mode 라인 바로 뒤로 고정한다**(구현자 임의 결정 방지). **codex-scaffold.sh에는 추가하지
  않는다** — Codex 런타임에는 Workflow 도구가 없어 주입이 무동작(inert)이고, 공유 화이트리스트
  등재만으로 파일이 존재하게 될 경우의 위생 오탐이 방지되므로 미러의 실근거가 패리티(미관)뿐이다
  (adversarial 렌즈 리뷰 반영 — 비대칭은 codex-scaffold 주석 한 줄로 명시한다, `EXPLICIT`).
  주입 문구: required면 "ultracode(멀티에이전트 워크플로) 검증 모드: required — 워크플로에
  reviewer-* 렌즈 검증 단계를 반드시 포함한다", discretion이면 "ultracode(멀티에이전트 워크플로)
  검증 모드: discretion(기본) — 리스크에 비례해 판단하되 보고서에 검증 내역을 명시한다". 라벨에
  괄호 부연을 넣는 이유: 'ultracode 검증 모드'만으로는 'ultracode라는 모드'로 오독될 수 있다.
- `scripts/ultracode-review.sh` — `issue-mode.sh`를 미러한다(인자 없으면 현재 모드 표시,
  `required`/`discretion`만 수용, 그 외 비정상 종료, 자기완결 mkdir).
- `commands/ultracode-review.md` — issue-mode 커맨드를 미러한다(완결 문장 description).
- `scripts/test_scaffold.sh` — issue-mode 케이스(12)의 패턴을 미러하는 케이스를 추가한다: 부재 시
  discretion 생성·주입·1회 안내, 토글 후 required 주입, 불명값 폴백+경고, 커맨드 스크립트의
  set/show/reject/자기완결. codex 테스트에도 모드 미러 체크를 추가한다.
- `README.md` — 커맨드 절(정본 열거 한 곳)에 `/ultracode-review` 한 줄을 추가한다(케이스 13 가드가
  누락을 잡는다).
- `docs/DESIGN-NOTES.md` — R5의 강제 한계(주입 지시 기반 — 무시를 막을 수 없음, 훅 표면 문서화 시
  넛지 승급 재검토)를 '한계 / 주의' 절에 한 줄 남긴다. spec은 아카이브되므로 한계의 지속 홈이
  필요하다.

## 열린 결정
- **토글 이름.** 작업명은 `ultracode-review`다(무엇을 검증하는 모드인지 이름에 드러남). 사용자가
  다른 이름을 원하면 구현 전에 바꾼다 — 이름 외 설계는 이름에 의존하지 않는다. 단 **배포 후 개명은
  비용이 있다**: 구 상태 파일이 새 화이트리스트에 없는 내용 있는 파일로 남아 scaffold 위생이 매 세션
  '비관리 파일 잔존' WARNING을 내고(자동삭제 안 함), 값 이름 변경은 불명값 폴백으로 사용자의 required
  선택을 조용히 discretion으로 되돌린다 — 이름은 구현 전에 확정한다(`REVERSIBLE`의 단방향 문 기록).

## 범위 밖
- B안 넛지 훅·C안 차단 훅 — 판정 패널 결론대로 보류·기각. Workflow 훅 표면이 문서화되면 재검토한다.
- 워크플로 스크립트 정적 검사(검증 단계 존재 확인) — 미확인 표면 + 오탐 위험으로 기각됨.
- `.claude/workflows/self-audit.js`는 이미 렌즈를 SKILL.md에서 도출하므로 이 토글과 무관하게 R1을
  충족한다 — 수정 불요.

## 검증 기준 (구현 계획이 상속한다)
- 테스트 3종 FAIL=0 유지 + 새 토글 케이스가 issue-mode 케이스와 같은 커버리지(생성·주입·토글·폴백·
  커맨드 계약)를 가진다.
- **§가 표 행 추가도 계약으로 가드한다** — 정본에 신규 트리거 행(트리거 문자열·호출자 열)이
  존재하는지 grep하는 체크를 test_scaffold.sh에 추가한다(표 행만 무검증으로 남기지 않는다).
- 두 토글이 공존할 때 issue-mode 라인과 ultracode-review 라인이 **둘 다** 주입되는지 테스트로
  확인한다(변수 분리 검증).
- 새 세션에서 모드 라인이 실제로 주입되는지 수동 확인 1회(scaffold stdout).
- README 커맨드 절 추가는 케이스 13이 계약으로 검증한다.
- **required의 효과 자체는 검증 불가함을 계약으로 오해하지 않는다** — 검증 가능한 것은 문자열
  주입뿐이고, 위반(작성자가 검증 단계를 뺌) 시 정의된 조치는 없다. 구현 계획은 required에 대해
  존재하지 않는 거동 성공 기준을 만들지 않는다(한계는 R5가 소유한다).
- 모드 값을 읽을 수 없는 주체(서브에이전트 등 — @import에는 §가 행만 있고 현재 모드는 없다)는
  discretion(리스크 비례 재량)을 기본으로 가정한다 — §가 서문의 기본 교리와 같다.
