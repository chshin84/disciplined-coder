# 세션 기록 기반 원칙 퇴고 — 설계

이 설계는 2026-10-03에 썼다. 대상은 에이전트원칙 `agent-principles.md` 의 조항, 참고서인
`skills/lens-fit/domain-discipline.md` 와 `skills/lens-readability/domain-korean.md`, 이 저장소 `CLAUDE.md` 의
「에이전트원칙을 고칠 때」 절, 이 PC의 Claude 메모리다. 이 PC의 세션 기록에서 사용자의 지적과 결정을 모아 원칙에
빠진 행동 지시를 찾고, 원칙 조항을 한 조항씩 퇴고하는 절차를 정한다. 같은 날 렌즈 리뷰
(`docs/superpowers/reviews/2026-10-03-principle-revision-from-sessions-review.md`) 뒤에 다시 썼고, 무엇이 왜
바뀌었는지는 「리뷰가 바꾼 것」에 적는다.

## 용어

- **클린룸 시험:** 원칙이 실리지 않은 모델과 시험할 문안만 실은 모델에게 같은 과제를 주고 결과를 비교하는 시험이다.
  저장소 `CLAUDE.md` 가 "클린룸 소거 시험"이라고 부르는 시험과 같다.
- **빈 모델:** 클린룸 시험에서 원칙을 싣지 않은 조건이다. 2026-10-03에 Explore 서브에이전트에게 조항 ID 가
  컨텍스트에 있는지 물었고, 없다고 답했다. 이 확인은 모델의 자기 보고다.
- **퇴고 기준:** 조항 문구를 고칠 때 보는 점검 질문이다.
- **조항 후보:** 세션 기록에서 찾았고 원칙에 아직 없는 행동 지시다.

## 바꾸는 이유

2026-10-03 세션에서 `COUNT-EARNS` 조항을 넣고 문구를 한 번 고쳤다. 사용자가 "문장의 판단이 맞나? 문장이
주체인가?"라고 물었고, 판단 주체를 "결론이나 결정"으로 바꾼 문안은 재시험에서 trial 수를 근거와 함께 남겼다.
조건마다 1회라 이 차이가 문구 효과인지 실행 변동인지는 가리지 못했다.

사용자는 같은 형태의 퇴고를 다른 조항에도 적용할 수 있는지 물었다. 이어서 원칙과 가이드를 재정리하며 쓴
기준을 찾고, 대화에서 드러난 뉘앙스와 암묵지를 형상화하라고 요청했다.

원칙을 고치는 기준은 지금 여러 곳에 흩어져 있다. 저장소 `CLAUDE.md` 는 명령형 문장, 지시와 근거의 분리,
클린룸 시험을 정한다. 참고서는 조항마다 사용자 발언을 근거로 인용하고, 이 PC의 Claude 메모리에는 feedback
기록이 있다. 그런데 `COUNT-EARNS` 퇴고에 쓴 주체 호응과 범위의 정확성은 어디에도 적혀 있지 않다.

## 목표

- **퇴고 기준 명문화:** 퇴고 기준을 이 저장소 `CLAUDE.md` 「에이전트원칙을 고칠 때」 절에 적는다.
- **조항 후보 발견:** 세션 기록의 사용자 발화에서 조항 후보와 새 퇴고 기준을 찾는다.
- **조항 퇴고:** 퇴고 기준에 걸리는 기존 조항과 조항 후보를 한 조항씩 클린룸 시험을 거쳐 처리한다.

## 범위

대상 자료는 이 PC의 `~/.claude/projects` 아래 세션 기록 파일(`*/*.jsonl`, 서브에이전트 폴더 제외)이다.
2026-10-03 측정에서 이 파일들은 합계 372MB 였고, 여기서 뽑은 사용자 발화는 18만 6천 자였다. 원문 대부분이
도구 출력이므로 발화만 대상으로 삼는다. 발화에는 직접 입력한 발화, 작업 도중 보낸 발화, 선택 도구의 답이 들고,
클린룸 시험이 만든 임시 세션은 사용자 발화가 아니므로 뺀다. 다른 PC의 세션과 claude.ai 웹 세션은 이 PC에 없어 범위 밖이다.

메모리 규칙 `other-sessions-message-only` 는 다른 세션이 맡은 저장소의 파일을 읽지 말라고 정한다. 세션
기록은 어느 저장소의 파일도 아니고 이 PC의 Claude Code 가 남긴 대화 기록이다. 사용자가 이 작업에서 모든 세션
기록을 보라고 지시했으므로 기록을 읽는다.

## 산출물을 둘 곳

산출물마다 둘 곳을 에이전트원칙의 `DOC-PLACE` 와 「문서 타입과 수명」으로 정한다. 별도 문서를 새로 만들지 않는다.

| 산출물 | 둘 곳 | 이유 |
|---|---|---|
| 퇴고 기준 | 저장소 `CLAUDE.md` 「에이전트원칙을 고칠 때」 | 원칙을 고칠 때만 쓰는 작업 방법이라, 모든 프로젝트 세션에 실리는 `agent-principles.md` 에 둘 이유가 없다 |
| 채택한 조항 문안 | `agent-principles.md` | 행동을 바꾸는 지시는 원칙이 소유한다 |
| 조항의 근거와 측정 | 참고서의 조항 절 | 저장소 규칙이 지시와 근거를 나눈다 |
| 기각하거나 지운 조항의 근거 | 가장 가까운 조항 절, 없으면 참고서 「삭제한 조항」 절 | 저장소 `CLAUDE.md` 가 지운 조항의 근거를 이 절에 둔다 |
| 행동 지시가 아닌 사용자 맥락 | Claude 메모리 | 업무와 관점 같은 맥락은 지시가 아니어서 클린룸 시험 대상이 아니다 |
| 발화 추출 결과와 조항 후보 목록 | 저장소 밖 고정 폴더 `~/.claude/dc-principle-revision/` | 사용자 발화를 그대로 담고, 원격 저장소가 공개(PUBLIC)라 커밋하지 않는다 |
| 새 퇴고 기준 | 이 설계의 「퇴고 기준」 표에 행으로 넣고, 근거 발화의 요지는 「발화에서 찾은 퇴고 기준」 절 | 퇴고 기준은 조항이 아니어서 참고서에 절이 없다. 발화는 요지만 적는다 |

암묵지 목록을 별도 docs 문서로 남기지 않는다. 처분 규칙 없이 쌓이는 목록 문서는 `NO-TODO-DOC` 가 금지하는
형태이고, 원칙과 참고서에 이미 있는 내용을 두 곳에 만든다.

## 퇴고 기준

저장소 `CLAUDE.md` 「에이전트원칙을 고칠 때」 절에는 명령형 문장과 지시와 근거의 분리가 이미 있다. 이 설계는
아래 기준을 그 절에 추가한다.

| 기준 | 점검 질문 | 2026-10-03 사례 |
|---|---|---|
| 주체 호응 | 판단하거나 행동하는 주체가 문장 안에서 맞게 놓였는가 | "문장의 판단"을 "결론이나 결정"으로 고쳤다 |
| 범위의 정확성 | 낱말이 의도보다 넓거나 좁은가, 한쪽이 다른 쪽에 포함되는 중복이 있는가 | "숫자와 개수"를 "숫자"로 줄였다 |
| 한 조항 한 관심사 | 서로 다른 관심사가 한 조항에 섞였는가 | `FOCUSED` 가 구성 단위 설계와 다른 세션 간섭을 함께 다룬다 |
| 원칙의 자기 적용 | 조항과 근거 문장이 다른 조항을 지키는가 | `5f976c5` 커밋 전 검사에서 참고서의 "A가 아니라 B" 대구가 `ANTI-LIMIT` 한도를 넘었다 |

## 절차

### 발화 추출

세션 기록에서 사용자 발화만 뽑는다. 도구 결과, 훅과 시스템이 넣은 글, 압축 요약, 서브에이전트 대화는 뺀다.
추출 스크립트는 작업 폴더에 두고 저장소에 싣지 않는다. 확인 방법은 표본 20건을 원문과 대조해
빠뜨리거나 잘못 넣은 발화가 없는지 보는 방식이다.

### 기존 기록과 대조

행동 지시가 들어 있는 발화만 골라 같은 뜻끼리 묶고, 묶음마다 나온 세션 수를 센다. 작업 지시("이거 해줘")와
단순 질문은 고르지 않는다. 묶음마다 원칙 조항, 참고서의 근거 절과 「삭제한 조항」 절, 메모리 feedback 파일과
대조해 아래로 처분한다.

| 처분 | 조건 | 다음 단계 |
|---|---|---|
| 반영됨 | 같은 뜻의 조항이나 근거가 있다 | 대응하는 조항 ID 를 적고 마친다 |
| 삭제 이력 있음 | 「삭제한 조항」에 같은 기준이 있다 | 삭제 근거가 지금도 맞는지 사용자에게 보고한다 |
| 퇴고 기준 | 조항 문구를 고치는 방법에 관한 지시다 | 「퇴고 기준」 표와 `CLAUDE.md` 에 추가한다 |
| 조항 후보 | 행동 지시이고 두 세션 이상에서 나왔다 | 조항 퇴고로 넘긴다 |
| 맥락 | 행동 지시가 아닌 사용자 업무와 관점이다 | 메모리 갱신 후보로 사용자에게 보고한다 |
| 일회성 | 한 세션에서만 나온 행동 지시다 | 요지를 한 줄씩 사용자에게 보고한다 |

두 세션 기준은 가정이다. 한 세션의 과제에만 맞는 지시를 원칙으로 올리지 않으려는 기준이다. 일회성 묶음은
대화 보고에만 싣고 문서로 남기지 않으며, 사용자가 고른 묶음은 조항 후보로 올린다.

### 조항 퇴고

대상은 조항 후보와 퇴고 기준에 걸리는 기존 조항이다. 2026-10-03 조사에서 걸린 기존 조항과 걸린 기준은 아래와 같다.

| 조항 | 걸린 기준 |
|---|---|
| `FOCUSED` | 한 조항 한 관심사, 범위의 정확성("작업"이 "사소한 작업"의 작업과 뜻이 부딪힌다) |
| `NAME-ITEMS` | 지시와 근거의 분리("번호는 거짓 우선순위를 만든다") |
| `REPORT-DEAD` | 주체 호응("내 변경"의 '내') |
| `YAGNI` | 원칙의 자기 적용("50줄로 될 일을 200줄로") |
| `REWRITE-TO-ADD` | 범위의 정확성(확인할 수 없는 "자연스럽게") |
| `DOC-TYPE` | 범위의 정확성(구어 "만지기 전에", 뜻이 흐린 "진실인 코드") |
| `RESOLVE-NOW` | 주체 호응(무엇을 하라는지 대상이 없다) |

출력지시 머리말의 "직역체는 대화의 품질을 극도로 떨어뜨린다"도 지시와 근거의 분리에 걸린다. 머리말에는
조항 ID 가 없어 측정을 적을 조항 절이 없으므로, `domain-korean.md` 머리 문단에 기록한다.

한 차례에 조항 하나만 고치고 다른 조항은 참고만 한다. 조항마다 아래 단계를 차례로 밟는다.

1. **문안:** 퇴고 기준으로 새 문안을 쓰고, 걸린 기준과 바꾼 이유를 적는다.
2. **시험:** 그 조항이 다루는 행동이 드러나는 과제 3개를 만든다. 빈 모델, 현행 문안, 새 문안을 Explore
   서브에이전트로 1회씩 실행하고, 조항 후보면 현행 문안 조건을 뺀다. 과제에는 세션 발화를 옮기지 않고 지어낸
   예시를 쓴다. 확인 방법은 과제마다 위반 수를 세어 조건끼리 비교하는 방식이다.
3. **판정:** 새 문안의 위반이 현행 문안보다 적고 지켜야 할 내용을 잃지 않았으면 채택한다. 위반이 같으면 과제
   2개를 더 실행하고, 다섯 과제 합계가 현행보다 나쁘지 않으면 채택한다. 조항 후보는 빈 모델보다 위반이 적어야
   채택한다. 다섯 과제 모두 빈 모델도 지키면, 조항 후보는 넣지 않고 기존 조항은 삭제 후보로 올린다.
4. **확인:** 채택한 문안이 「사용자에게 올리는 결정」에 해당하면 측정 결과와 함께 사용자에게 묻는다.
5. **반영:** 채택한 문안을 `agent-principles.md` 에, 근거와 측정을 참고서 조항 절에 적는다. 기각한 결과는
   「산출물을 둘 곳」 표의 기각 행에 따라 적는다. 확인 방법은 저장소 `CLAUDE.md` 「변경 뒤 실행」의 검사 전체
   통과와 `claude plugin validate ./` 다.
6. **커밋:** 조항 하나를 커밋 하나로 만들고, 메시지 첫 줄을 조항 ID 로 시작한다. 조항 단위로 되돌리고 재개할
   때 끝난 조항을 가려내기 위해서다.

### 푸시

조항 커밋은 바로 푸시하지 않는다. 원격 저장소는 공개이고, 세션이 시작될 때 자동 갱신이 원칙 사본을 덮어쓰므로
푸시 하나가 모든 프로젝트 세션에 퍼진다. 조항 퇴고를 모두 마치면 조항별 결과와 푸시할 diff 전체를 한 번에 사용자에게
보이고, 승인을 받은 뒤 한 번에 푸시한다. 사용자가 거부한 조항은 revert 하지 않고 현행 문안을 되살리는 새 커밋으로
처리하며, 참고서의 측정 기록은 거부 사유와 함께 남긴다. 이웃한 조항 커밋을 revert 하면 충돌하고 기각 기록까지
지워지기 때문이다. 퇴고 기준은 조항 판정이 쓰므로 묶음 끝이 아니라 조항 퇴고 전에 따로 승인받는다.

### 사용자에게 올리는 결정

아래는 자율로 처리하지 않고 사용자에게 묻는다.

- **기존 조항 삭제:** 빈 모델도 지키는 조항의 삭제다. 되돌리기 어렵고, 근거가 사용자 발언인 조항이 많다.
- **조항 의미 변경:** 지시가 적용되는 상황이나 대상이 넓어지거나 좁아지는 변경이다. 범위의 정확성으로 고친
  문안은 낱말이 바뀌어도 적용 대상이 같을 때만 문구 정리로 본다. 판정이 서지 않으면 의미 변경으로 본다.
- **조항 후보 채택:** 새 조항의 추가다.
- **메모리 갱신:** 맥락 묶음을 메모리에 쓰는 일이다.
- **푸시:** 「푸시」 절의 승인이다.

## 확인 방법

- **발화 추출:** 표본 20건이 원문과 일치한다.
- **대조:** 모든 묶음에 처분이 있고, 반영됨 묶음에는 조항 ID 가 있다. 보고 대상 처분(삭제 이력 있음, 맥락,
  일회성)은 대화 보고에 모두 실린다.
- **퇴고 기준:** 「에이전트원칙을 고칠 때」 절에 기준이 있고, 「변경 뒤 실행」의 검사 전체와 `claude plugin validate ./` 가 통과한다.
- **조항 퇴고:** 처리한 조항마다 참고서에 측정 결과가 있고 커밋이 하나 있다.
- **푸시:** 사용자 승인 뒤 원격 `main` 이 로컬과 같다.

## 발화에서 찾은 퇴고 기준

발화 대조에서 처분이 퇴고 기준인 묶음이 나오면 이 절에 기준 이름과 발화 요지와 날짜를 적는다. 발화 원문은
옮기지 않는다.

2026-10-03 대조에서 새 기준은 나오지 않았고, 「퇴고 기준」 표의 기준을 받치는 발화가 두 세션에서 나왔다.
2026-09-19 세션에서 사용자는 원칙을 정리하는 목적을 "중복을 없앤다, 하나의 항목은 하나의 지시사항만"으로
정했고, 한 조항이 "실질적으로 너무 지시가 광범위하다"며 나누자고 했다. 2026-09-23 세션에서는 원칙을 고칠 때
중복을 없애고 명확하지 않은 기준에는 임계값을 제시하라고 했다. 두 발화는 한 조항 한 관심사와 범위의 정확성의 근거다.

## 한계와 가정

채점은 메인 세션 하나가 한다. 과제 선택과 문안과 채점이 한 세션에 몰리므로, 의미 변경과 조항 후보와 삭제는
모두 사용자 확인을 거치게 했다. 클린룸 시험은 조건마다 1회라 문구 효과와 실행 변동을 가리지 못한다.

발화 뒤의 의도는 추정이다. 추정으로 만든 조항 후보는 사용자 확인 전에 넣지 않는다. 한 번도 지적하지 않은
선호는 기록에 없어 찾지 못한다.

발화에는 경로와 계정 정보와 사내 업무 내용이 섞여 있다. 참고서와 이 설계와 클린룸 과제에는 발화 요지만 옮기고,
비밀과 개인정보와 사내 식별자를 빼야 한다(`SECRETS`).

참고서 근거 절이나 원칙 조항 문구를 고치면 kw-plugins 에 알려야 한다(메모리 `kw-subset-sync`). 거부될 문구가
퍼지지 않도록 알림은 푸시 뒤에 푸시된 커밋만 대상으로 한다. 그 저장소를
맡은 세션이 없으면 알리지 못했다고 보고한다.

## 계획과의 경계

조항 후보는 발화 대조를 마쳐야 나온다. 그래서 계획 문서는 발화 추출, 대조, 퇴고 기준 반영, 기존 조항 퇴고를
작업으로 적고, 조항 후보 처리는 「조항 퇴고」 단계를 그대로 반복하는 작업 하나로 적는다. 조항 후보 목록은
스크래치 폴더에 두고 계획 문서를 고치지 않는다.

## 리뷰가 바꾼 것

- **푸시 시점:** 조항마다 푸시하던 안을 묶음 끝 승인 뒤 한 번 푸시로 바꿨다. 공개 원격과 자동 갱신 때문에
  푸시가 곧 배포라는 지적(adversarial, consistency)을 따랐고, 2026-10-03에 사용자가 이 안을 골랐다.
- **자율 반영 범위:** 의미 변경의 판정 기준을 적용 대상의 변화로 정하고, 판정이 서지 않으면 묻게 했다.
- **판정 규칙:** 동점이면 과제를 추가하도록 고쳐 채택 조건과의 겹침을 없앴다.
- **비밀 처리:** 후보 목록을 계획 문서에서 스크래치로 옮기고, 비밀 제거 규칙을 과제와 설계까지 넓혔다.
- **처분 표:** 발화 네 분류와 근거 후보 처분을 지우고, 퇴고 기준 처분을 추가했으며, 일회성을 보고하게 했다.
- **사실 정정:** 원문 크기, 메모리 규칙의 범위, kw-plugins 알림 조건, 퇴고 기준 표의 사례 출처를 고쳤다.
- **계획 리뷰 반영:** 작업 파일을 고정 폴더로 옮기고, 커밋 메시지의 조항 ID, 거부 처리 방식, 퇴고 기준의 별도 승인,
  푸시 뒤 알림을 계획 리뷰(`2026-10-03-principle-revision-from-sessions-plan-review.md`)에 따라 정했다.
- **이름 정리:** 클린룸 시험, 빈 모델, 조항 후보, 참고서의 이름을 하나로 맞추고 「용어」 절을 두었다.
