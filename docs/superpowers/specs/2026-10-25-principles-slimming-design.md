# 에이전트원칙 경량화 설계

## 목적

에이전트원칙(`agent-principles.md`)은 매 세션 모든 프로젝트에 실린다. 이 설계는 문서를 만들거나 고칠 때만 필요한 조항을 원칙에서 스킬로 옮겨, 매 세션 실리는 양을 줄인다. 판단 기준은 한국인 사무직 비개발자의 작업당 비용(에너지·시간·토큰)이다(2026-10-24 사용자 지시).

같은 브랜치에서 조항 삭제가 먼저 끝났다. 조항 없음 시험으로 조항 11개와 「`REVISE-ORDER`」 절을 지웠고, 원칙 파일은 13,009자에서 11,759자가 되었다(Python `len` 으로 센 글자 수, 2026-10-25). 삭제 근거는 `docs/domain-discipline.md` 「삭제한 조항」 절에 있다. 이 설계는 남은 조항의 배치만 다룬다.

같은 규칙은 2026-09-21 커밋 54ee432 가 `domain-docs` 스킬에서 원칙으로 옮겼다. 그 커밋은 "문서를 만지는 모든 세션에 걸리는 규칙인데 스킬로 두면 여는 판단을 매번 해야 했고, 안 열었을 때의 누락이 조용했다"고 적었다(`scripts/test_docs_drift.sh` 103~105행). 그 뒤 사용자는 2026-10-25 에 스킬이 설명만으로도 잘 열린다고 보았다. 두 판단이 다르므로, 사용자는 옮기기 전에 열림 시험을 먼저 하고 그 결과로 옮길지 정하기로 했다(2026-10-25, 선택 도구로 답함).

사용자는 2026-10-25 대화에서 다음도 정했다.

- 특정 조건에서만 의미가 있는 조항은 원칙에서 스킬로 옮긴다.
- 훅으로 스킬을 강제하는 일은 반드시 실행되어야 하는 동작(spec 리뷰 게이트 같은 것)에만 둔다.
- 스킬 안의 문서는 층으로 나눠, 스킬이 열려도 그 상황에 필요한 파일만 읽게 한다.
- 렌즈는 렌즈 개편 세션(e4, 브랜치 `worktree-lens-agent-restructure`)이 에이전트 정의로 옮긴다.

## 목표와 비목표

**목표**

- 1부: 「문서 관리」 절과 「읽기 위한 문서」 절, `REVIEW-DELIVERABLE` 을 담은 스킬 `managing-docs` 를 만들고, 그 스킬이 문서 과제에서 열리는지와 작업당 비용이 어떻게 바뀌는지 측정하라.
- 2부(사용자가 1부 결과를 보고 승인한 때만): 원칙에서 그 절을 지우고 저장소의 포인터를 새 위치로 바꿔라.
- 실사용 경로의 층 규칙(훅·스킬·스크립트)을 저장소 CLAUDE.md 에 적어라.

**비목표**

- 조항의 뜻을 바꾸지 마라. 옮기는 조항은 「옮길 때 허용하는 문구 차이」에 적은 차이만 두고 원문 그대로 옮겨라.
- `skills/lens-*` 와 `dispatching-lenses`·`aggregating-lenses` 를 이 브랜치에서 고치지 마라. 고칠 곳은 e4 세션에 메시지로 맡겨라(「2부」).
- `domain-plugin`·`domain-pruning`·`domain-readme` 는 스킬로 둬라. 설명으로 열리는 스킬을 참고 문서로 바꾸면 자동으로 열리지 않는다.
- `DELEGATED-SCORE`·`TOP-DOWN`·`NO-RAW-OUTPUT`·`LENS-ALLOWED` 는 원칙에 둬라. 이유는 「1차 리뷰 뒤 바뀐 곳」에 있다.
- 조항 끝의 이유 문장은 그대로 둬라. 시험 없이 한꺼번에 빼면 준수가 떨어져도 알아챌 장치가 없다(1차 리뷰 지적 7).
- 절 도입 문장 삭제는 하지 마라. 「출력」 아래 도입문은 적용 범위를 정하는 지시를 포함해, 지울 범위를 문장마다 가려야 한다(2차 리뷰 지적 6). 줄어드는 양에 비해 뜻이 바뀔 위험이 크다.

**실패로 볼 상황**

- 문서 과제에서 `managing-docs` 가 열리지 않거나, 열려도 보고서·발표자료·README 과제에서 `reading-docs.md` 를 읽지 않는다.
- 문서와 무관한 과제에서 `managing-docs` 가 열린다.
- 문서 과제 한 건의 토큰이나 도구 호출이 지금 원칙보다 늘어, 원칙에서 줄인 양을 넘어선다.
- 검사 스크립트(`scripts/test_*.sh`)나 `claude plugin validate ./` 가 실패한다.

## 층 규칙

저장소 CLAUDE.md 「훅과 봉인」 절 첫머리에 아래 문단을 그대로 추가하라. 이 단계는 1부 결과와 무관하게 진행하라.

> 실사용 경로에서 훅은 감지를, 스킬은 절차를, 스크립트는 실행을 맡는다. 훅은 스킬을 열게 하거나 스크립트를 실행하고, 스킬은 스크립트를 실행한다. 판단이 필요 없는 실행은 훅이 스크립트를 바로 실행한다. 호출 방향은 이 순서 하나로 두어라. 스크립트에서 훅이나 스킬을, 스킬에서 훅을 직접 호출하지 마라. 훅으로 스킬을 강제하는 일은 반드시 실행되어야 하는 동작에만 두고, 나머지 스킬은 설명과 원칙의 포인터로 열리게 하라. 검사 스크립트(`scripts/test_*.sh`)는 실사용 경로가 아니다.

## 새 스킬 `managing-docs`

| 옮길 대상 | 원칙의 현재 위치 | 새 위치 |
|---|---|---|
| 「문서 관리」 절 전체(`DOC-TYPE`·`MANAGED-BLOCK`·`DOC-PLACE`, 「문서 타입과 수명」, 「메모리와 문서 맵」) | 「실행」 아래 40~65행, 1,758자(뒤 빈 줄 포함) | `skills/managing-docs/SKILL.md` |
| 「읽기 위한 문서」 절 전체(`MD-FIRST`, 「`TITLES`」 묶음의 `TITLE-LAYERS`·`TITLE-CLAIM`과 용어 표) | 「출력」 아래 141~158행, 1,363자(뒤 빈 줄 포함) | `skills/managing-docs/references/reading-docs.md` |
| `REVIEW-DELIVERABLE` | 「검증」 72행, 170자 | `skills/managing-docs/references/reading-docs.md` |

`SKILL.md` 에는 「문서 관리」 절의 조항과 표를 두고, 끝에 상황별로 더 읽을 파일을 한 줄씩 적은 목차를 둬라. 남에게 전달하거나 사용자가 읽으려고 만드는 문서(보고서·제안서·발표자료·README·.html·.pptx·.docx·.hwp(x))이면 `references/reading-docs.md` 를 읽으라고 가리켜라. README 이면 `domain-readme` 도 열라고 가리켜라.

`description` 에는 문서를 새로 만들거나 고칠 때 연다고 적어라. 대상으로 마크다운·HTML·발표자료·워드 문서·README·CLAUDE.md·스킬·메모리 파일을 이름으로 넣어라.

서브에이전트와 Skill 도구가 없는 에이전트도 규칙을 읽을 수 있어야 한다. 그래서 `scripts/scaffold.sh` 가 원칙 사본을 덮어쓸 때 `skills/managing-docs/` 의 두 파일도 `~/.claude/disciplined-coder/managing-docs/` 에 덮어쓰게 하라. 원칙의 포인터는 스킬 이름과 이 사본 경로를 함께 적는다. `korean-banned-words.md` 사본과 같은 방식이다.

**옮길 때 허용하는 문구 차이.** 옮긴 문구는 원문과 아래 차이만 두어라.

- 자기 위치 표현: 145행 `MD-FIRST` 의 "이 절이 맡는"(두 곳)과 149행 TITLES 도입의 "이 절의 용어"는 "이 파일이 맡는", "이 파일의 용어"로 바꿔라.
- 원칙에 남는 절을 가리키는 표현: 143행의 "「작업 지시서」가 맡는 글"은 "에이전트원칙 「작업 지시서」가 맡는 글"로 바꿔라.
- `작은 변경` 면제: `REVIEW-DELIVERABLE` 문장 끝에 "파일 하나를 20줄 이하로 고치고 되돌리기 쉬운 작업이면 이 렌즈 검증을 생략하라."를 넣어라.

## 1부 — 열림과 비용 시험

1부에서는 원칙 파일 원본을 고치지 마라. 시험용 원칙 사본만 만들어라.

1. `skills/managing-docs/` 의 두 파일을 만들어라. 확인: 두 파일의 조항 문구를 원칙 원문과 `diff` 로 대조해, 차이가 「옮길 때 허용하는 문구 차이」의 항목뿐이다.
2. 시험용 원칙 사본을 스크래치 폴더에 만들어라. 원본에서 세 대상을 지우고 아래 포인터 두 줄을 넣은 사본이다. 원칙 안에서 옮긴 조항을 가리키는 두 곳도 고쳐라. `작은 변경`(9행) 면제 목록에서 `REVIEW-DELIVERABLE` 을 빼고, `DELEGATED-SCORE`(25행)의 "「문서 타입과 수명」"을 "`managing-docs` 「문서 타입과 수명」"으로 바꿔라. 확인: 사본의 글자 수를 Python `len` 으로 세어 보고에 적었다.
   - 「실행」 아래: "문서를 새로 만들거나 고치기 전에 `managing-docs` 를 열어라(Skill 도구가 없으면 `~/.claude/disciplined-coder/managing-docs/SKILL.md` 를 읽어라). 문서의 타입·수명·위치 규칙이 거기 있다."
   - 「출력」 아래: "사용자가 읽거나 남에게 전달할 문서를 쓰면 `managing-docs` 의 `references/reading-docs.md`(사본 `~/.claude/disciplined-coder/managing-docs/reading-docs.md`)를 따르라. 제목·목차 규칙과 전달 전 렌즈 검증이 거기 있다."
3. 시험 과제를 실행하라. 시험은 이 저장소 밖의 빈 임시 폴더에서 실행하라. 이 저장소의 CLAUDE.md 와 훅 안내가 스킬 이름을 알려 주면 실사용과 조건이 달라지기 때문이다. 조건은 두 가지다. 현행 조건은 지금 원칙 파일을 싣고 플러그인 없이 실행하고, 변경 조건은 시험용 원칙 사본을 싣고 이 브랜치의 플러그인을 실은 채 실행하라. 플러그인을 싣는 방법은 실행 전에 CLI 도움말에서 확인하라(가정: `claude --plugin-dir`). 과제는 아래와 같고, 각 과제를 조건마다 한 번씩 실행하라.
   - 열려야 하는 과제: 새 README 작성, 보고서 HTML 작성, 기존 마크다운 수정, 발표자료 초안 작성, 메모리 파일 작성, 보고서 초안을 서브에이전트에게 맡기는 과제.
   - 열리지 말아야 하는 과제: 짧은 질문에 답하기, 코드의 버그 하나 고치기.
   확인: 변경 조건의 세션 기록(stream-json)에서 과제마다 `managing-docs` 를 열었는지, 보고서·발표자료·README 과제에서 `reading-docs.md` 를 읽었는지, 서브에이전트 과제에서 서브에이전트가 사본 경로를 읽었는지를 표로 적었다. 두 조건의 과제별 입력·출력 토큰과 도구 호출 수도 같은 표에 적었다.
4. 결과를 「시험으로 정한 값」 절에 적고 사용자에게 보여라. 옮길지는 사용자가 정한다. 이 설계는 통과 기준값을 정하지 않는다. 근거 있는 기준값이 없기 때문이다(`EVIDENCE-FIRST`). 확인: 사용자의 결정을 「시험으로 정한 값」 절에 적었다.

## 2부 — 옮기기와 의존 수정

사용자가 1부 결과로 옮기기를 승인한 때만 진행하라. 승인하지 않으면 `skills/managing-docs/` 와 scaffold 변경을 지우고, 이 spec 에 superseded 를 표시하라.

1. 원칙 파일에 1부 2단계의 시험용 사본과 같은 변경을 적용하라. 확인: 원칙 파일과 시험용 사본을 `diff` 로 대조해 차이가 없다.
2. `scripts/scaffold.sh` 에 `managing-docs` 사본 복사를 넣어라. 확인: `scripts/test_scaffold.sh` 에 사본 두 파일이 생기는지 보는 검사가 있고 통과한다.
3. `hooks/doc_format_pretooluse.sh` 를 고쳐라. 28행의 "에이전트원칙의 「문서 관리」 절로"를 "`managing-docs` 를 열어"로 바꾸고 "에이전트원칙은 @import 로 이미 실려 있다" 문장을 지워라. 2·17행 주석의 '에이전트원칙의 타입·수명 판단', '에이전트원칙의 양식'도 `managing-docs` 로 바꿔라. 거부나 새 훅은 만들지 마라. 확인: 그 파일에서 '에이전트원칙'을 grep 해 0건이다.
4. 저장소 안의 포인터를 고쳐라. 확인: 아래 파일마다 옮긴 절 이름이나 조항 ID 가 `managing-docs` 를 가리킨다.
   - 저장소 CLAUDE.md 46행, `korean-banned-words.md` 73행, `skills/domain-pruning/SKILL.md` 25·76행, `skills/nested-orchestration/SKILL.md` 162행, `docs/domain-korean.md` 242행.
   - `hooks/rules_nudge_pretooluse.sh` 8행 주석: 문서 규칙 일부가 `managing-docs` 에 있다는 사실에 맞게 고쳐라.
   - `skills/review-docs/SKILL.md` 「`lens-fit`에 넘기는 계약」: `skills/managing-docs/references/reading-docs.md` 를 계약에 넣고, 11행의 '둘의 경로'·'같은 둘' 같은 개수 표현을 계약 목록에 맞게 고쳐라. `review-specs` 도 이 계약을 쓴다.
   - `docs/domain-discipline.md`: 옮긴 조항 절마다 새 위치를 한 줄로 적어라.
5. `scripts/test_docs_drift.sh` 를 고쳐라. 확인: 아래를 고친 뒤 이 스크립트가 FAIL=0 이다.
   - 103~105행 주석: 원칙 소유 근거 문장을 지우고, 2026-10-25 열림 시험 결과로 `managing-docs` 로 옮겼다고 적어라. 349·354·736행 주석과 217행 검사의 「문서 타입과 수명」·「읽기 위한 문서」 소유자를 `managing-docs` 로 바꿔라.
   - 793~795행 canon-realign 주석·echo 와 812·813행 검사 이름: "원칙 전부" 표현을 "원칙과 `managing-docs`"로 바꿔라.
   - `missing_clause_ids`, 133~151행 DC_IDS·DC_DUP, 지운 조항 되살림 검사: 원칙과 `skills/managing-docs/` 를 함께 보게 하라.
   - `scripts/audit_topics.sh` 와 `scripts/test_audit.sh` 337행이 원칙에서 이름표를 뽑는 곳도 `skills/managing-docs/` 를 함께 보게 하라.

## 1차 리뷰 뒤 바뀐 곳

1차 리뷰 기록은 `docs/superpowers/reviews/2026-10-25-principles-slimming-review.md` 다. 그 뒤 설계가 바뀐 곳과 근거는 아래와 같다.

1차 설계는 문서 Write 를 한 번 거부해 스킬을 열게 했다. 그런데 사용자가 훅 강제를 반드시 실행되어야 하는 동작에만 두기로 정했다. 그래서 거부 훅·Skill 매처 훅·생성물 감지·위임 감지를 모두 뺐다. 이 결정으로 지적 5·6(훅이 프로젝트 밖과 .html 을 못 봄)과 지적 8~11(fail-open, 셸 우회, 과검출, 서브에이전트 표시 키)이 대상을 잃었다. 대신 1부에서 스킬이 열리는지를 시험한다.

`DELEGATED-SCORE`·`TOP-DOWN`(합계 576자)은 원칙에 둔다. 두 조항을 옮기려면 새 스킬과 낱말 감지가 필요했고(지적 2·3), 다른 조항이 두 조항을 ID 로 가리키기 때문이다. `NO-RAW-OUTPUT` 도 원칙에 둔다. Stop 게이트는 기존 파일의 기능 수정을 보지 않고(지적 4), e4 세션이 이 조항의 문구를 따로 고친다. `LENS-ALLOWED` 는 원칙이 `@import` 로 실려야 세션 기본 지침의 서브에이전트 제한을 열므로 원칙에 둔다(지적 1).

스킬을 참고 문서로 바꾸는 일은 이 설계에서 뺐다. 렌즈와 렌즈 실행 스킬은 e4 세션이 에이전트 정의로 옮기고, `domain-*` 스킬은 설명으로 열리기 때문이다. 그래서 지적 12·15 는 대상을 잃었다. 지적 21 의 의존 누락과 지적 22 의 `domain-pruning` 76행은 2부 4·5단계가 다시 다룬다. 이유 문장을 근거 문서로 옮기는 일은 지적 7 대로 뺐다.

새 스킬 이름은 `managing-docs` 로 정했다. `domain-docs` 는 되돌린 영어 재작성의 대응표(`docs/superpowers/rewrite-map/domain-docs.md`)와 이름이 같기 때문이다(지적 23). 지적 24(토큰 수의 출처)는 토큰 수를 쓰지 않고 Python `len` 글자 수만 써서 해소했다. 1차 설계의 '27,837자'는 원본을 `wc -c` 로 센 바이트 수와 같다.

## 2차 리뷰 뒤 바뀐 곳

2차 리뷰 기록은 `docs/superpowers/reviews/2026-10-25-principles-slimming-review-2.md` 다. 지적 1(2026-09-21 선행 결정)과 지적 2(작업당 비용)에 대해 사용자는 열림 시험을 먼저 하고 정하기로 했다. 그래서 설계를 1부(시험)와 2부(옮기기)로 나눴고, 시험이 실패할 때 되돌릴 범위가 스킬 폴더 하나가 되었다(지적 9).

나머지 지적은 아래처럼 반영했다. 층 규칙 문단에서 "원칙에는 모든 답과 작업에 적용되는 행동만 둔다"를 뺐다(지적 7). "설명이 유일한 신호"라는 문장을 지우고, 시험은 실사용과 같은 조건(설명과 포인터)으로 하되 저장소 밖에서 실행하게 했다(지적 8). 서브에이전트와 Skill 도구 없는 에이전트를 위해 scaffold 사본 경로를 포인터에 넣었다(지적 10). `lens-readability` 는 e4 에 맡겨 비목표와 맞췄다(지적 3). 허용하는 문구 차이를 정했고(지적 4·5), 절 도입 문장 삭제는 뺐다(지적 6). writing-html-reports 의 고칠 줄과 거절 시 처리(지적 11), 누락된 의존(지적 12), 단계별 확인(지적 13·14), 병합 뒤 재시작 안내(지적 15), 1차 리뷰 처분 서술(지적 16), 평서문 지시와 줄 범위(지적 17)도 고쳤다.
