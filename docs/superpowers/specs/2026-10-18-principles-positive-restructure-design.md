# 에이전트원칙 긍정형 재작성과 출력 종류별 재분류 — 설계

2026-10-18 에 메인 세션이 이 설계를 썼다. 개편은 에이전트원칙(`agent-principles.md`)의 조항을 '무엇을 어떻게 하라'로 다시 쓰고, 목차를 출력 종류별 층으로 재분류한다. 사용자는 이 작업을 하는 이유를 "출력 지시구분이 이상하게 된건지, 에이전트 원칙이 잘 지켜지지 않았어"라고 밝혔고, "원칙은 무엇을 하지 말라 가 아니라, 무엇을 어떻게 해라가 되어야해. 많은 문제점은 금지에서, 금지를 피하다 더 큰 잘못을 저지르는 구조로 갔거든"이라고 진단했다.

근거는 같은 날 메인 세션이 수행한 전체 세션 기록 분석과 선행연구 렌즈 조사다. 선행연구 렌즈는 웹에서 선행 사례를 찾아 이 설계와 대조하는 서브에이전트이며(`skills/lens-prior-art`), 그 기록은 `docs/superpowers/reviews/2026-10-18-principles-positive-restructure-prior-art.md` 에 있다. 이 spec 의 리뷰 기록은 `docs/superpowers/reviews/2026-10-18-principles-positive-restructure-review.md` 와 2차 리뷰 기록 `docs/superpowers/reviews/2026-10-18-principles-positive-restructure-review-2.md` 다.

## 용어

| 이름 | 뜻 |
|---|---|
| 판단 조항 | 언제 묻고, 확인하고, 멈추고, 진행할지처럼 상황에 따라 행동이 달라지는 조항이다 |
| 불변 조건 | 상황과 무관하게 지켜야 하는 조항이다. 어기면 되돌리기 어렵거나 피해가 밖으로 나간다 |
| 결정 규칙 | 판단 조항을 쓰는 형식이다. 상황(관찰 가능한 사건) → 행동 → 멈출 조건으로 쓴다 |
| 이유 한 줄 | 조항 끝에 붙이는 목적 문장이다. "~하기 위해서다" 또는 "~이기 때문이다"로 쓴다 |
| 층 | 조항이 적용되는 출력 종류로 나눈 절이다. 모든 작업, 모든 답, 남에게 전달하는 산출물, 작업 문서·지시문, 코드다 |
| 실패 평가 세트 | 세션 기록의 실제 실패에서 뽑은 과제 묶음이다. 개편 전후의 원칙 전체를 같은 과제로 비교하는 데 쓴다 |
| 기준 원칙 | 개편을 시작하기 전의 `agent-principles.md` 이며, 커밋 `7a2d26d` 의 파일이다. 모든 단계는 이 파일과 비교한다 |
| 검사기 트랙 | 금지어 목록에서 만든 금지어·제외어·적용 대상의 목록이다. 훅만 읽고 세션에는 실리지 않는다 |
| 지시형 트랙 | 금지어 목록에서 만든 '어떤 상황에서 어떤 말을 써라' 지시다. 세션에 실린다 |
| 빌더 | 이 spec 으로 plan 을 쓰고 구현하는 세션이다 |

## 세션 기록에서 확인한 것

메인 세션은 전체 프로젝트의 세션 기록 170개(2.3GB)에서 사용자가 직접 입력한 메시지 약 1,300개를 뽑았고, 분석 서브에이전트가 사용자가 Claude 를 바로잡은 사례 약 300건을 분류했다. 시험용 임시 세션은 뺐다.

실패가 난 출력의 종류는 대화 답 140건, 도구 실행 중 판단 84건, 작업 문서 32건, 남에게 전달하는 산출물 27건, 코드 20건이었다. 현행 출력지시는 대화 답에 퇴고 순서(`REVISE-ORDER`)를 적용하지 않고, 「원칙」 절의 `TITLES` 묶음도 대화 답을 대상에서 뺀다. 그런데 실패의 대부분은 대화 답과 행동에서 났다.

약 60건은 금지를 피하려다, 또는 확인·질문 의무를 멈추지 않고 적용하다 더 큰 잘못으로 이어졌다. 그 구조는 아래 유형으로 나뉜다.

- **언어 압력** — 금지어 표와 '한국어로 써라'와 '고유어로 바꾸지 마라'가 함께 실려, Claude 가 표준 한자어나 원어를 피하다 아무도 쓰지 않는 고유어·직역·음차·지어낸 말을 만들었다. 그 말이 다시 금지어가 되는 순환이 있었다.
- **확인 의무의 무한 적용** — `REVERSIBLE`·`ASK-OPTIONS`·`TELL-NOW`·`RESOLVE-NOW` 에 멈출 조건이 없어, Claude 가 위임 뒤에도 승인을 다시 청하고 푸시마다 확인받았다. 승인을 피하려고 저장소 밖에 파일을 만들거나 명령을 사용자에게 넘긴 사례도 있다.
- **배제 압력** — `YAGNI`, 중복 금지, 다른 세션 참견 금지, 렌즈 재실행 금지, `SECRETS`, 웹 렌즈 승인이 빼기·멈추기·생략으로 이어졌다. Claude 는 지켜야 할 실패 기록을 지우고, 시험 후보를 줄이고, 단순 웹 검색도 하지 않고, 금지 주제를 부정문으로 다시 적었다.
- **형식 압력** — `TITLE-CLAIM`(40자·수치·단정)과 `LABEL-NOUN`(명사구)을 함께 지키려다 Claude 가 결론을 압축하고 방향 없는 표 머리를 썼다.

가장 자주 위반된 조항은 `NO-ASSUME`, `TERM-EXPLAIN`, `ASK-OPTIONS`, `BOTTOM-LINE`·`STATUS-FIRST`, `EVIDENCE-FIRST`, `VOCAB-PREF`, 그리고 한국어 출력이었다. 한국어 출력 위반은 압축 요약이나 서브에이전트 보고 직후에 영어로 답한 사례다. 조건부 발동도 공백을 만들었다. `STATUS-FIRST` 는 '진행 상황을 물으면'에만, `ASK-OPTIONS` 의 요약은 '묻기 전'에만, `STATE-ASSUME` 은 '확인할 수 없어 가정하면'에만 발동해 평소 보고에는 적용되지 않았다. `NO-ASSUME` 은 확인 대상을 '코드와 데이터와 환경'으로 열거해 이전 결정(spec·메모리·대화 합의)이 빠졌다.

## 선행연구에서 확인한 기준

메인 세션이 아래 인용을 원문에서 열어 확인했다. 렌즈가 보고했으나 메인 세션이 확인하지 못한 수치는 근거로 쓰지 않았고, 그 목록은 선행연구 기록에 있다.

- **절대 금지는 불변 조건에만** — OpenAI 지침은 "Use ALWAYS, NEVER, must, and only for true invariants such as safety rules, required fields, or actions that should never happen", "For judgment calls, such as when to search, ask, use a tool, or keep iterating, prefer decision rules"라고 적는다([출처](https://developers.openai.com/api/docs/guides/prompt-guidance-gpt-5p6.md)). Anthropic 헌법 발표문은 규칙을 "especially high-stakes behaviors in which Claude should never engage"에 쓴다고 적는다([출처](https://www.anthropic.com/news/claude-new-constitution)).
- **지시에 이유를 붙인다** — Anthropic 지침은 지시 뒤의 동기를 설명하면 Claude 가 목표를 더 잘 이해한다고 적고, 이유 없는 "NEVER use ellipses"보다 TTS 엔진이 읽지 못한다는 이유를 붙인 문장을 낫다고 든다([출처](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). 헌법 발표문은 원하는 것을 지정하는 데 그치지 않고 설명해야 한다고 적는다.
- **금지 대상의 이름은 그 대상을 점화한다** — "Semantic Gravity Wells"(arXiv 2601.08070, n=40,000)는 "In priming failure (87.5% of violations), the instruction's explicit mention of the forbidden word paradoxically activates"라고 보고한다([출처](https://arxiv.org/abs/2601.08070)). 이 저장소의 실측도 같은 방향이다. `docs/domain-korean.md` 「지시문의 형태」는 금지어를 한 번도 적지 않고 대체어만 준 다섯 벌이 모두 목표 낱말을 썼고, 금지어와 대체어를 함께 준 다섯 벌은 둘만 목표 낱말을 썼다고 기록한다. 같은 절의 0건 대 3건은 낱말 규칙을 준 조건과 주지 않은 조건의 비교이며, 금지어를 이름으로 대는 형태와 대지 않는 형태는 목표 낱말에서 0대 0으로 비겼다. 그 절은 현행 형태를 고른 근거를 실측 밖(검사할 글자를 표에서 뽑아낼 수 있음)에 두었다.
- **충돌은 지운다** — Claude Code 문서는 "if two instructions contradict each other, Claude may pick one arbitrarily"라고 적는다([출처](https://code.claude.com/docs/en/memory)). OpenAI 는 "conflicting rules can create more instability than missing detail"이라고 적는다. 프롬프트로 우선순위를 밝히는 방법은 IHEval(시스템·사용자 메시지 사이의 지시 계층 벤치마크)에서 "this additional prompt does not bring noticeable improvements"였고 GPT-4o 평균이 70.0 에서 67.2 로 내려갔다([출처](https://arxiv.org/html/2502.08745v2)). IHEval 은 역할 사이의 충돌을 측정했으므로, 한 파일 안의 조항 충돌에는 방향만 참고한다.
- **분량** — Claude Code 문서는 "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence"라고 하고, import 는 "don't reduce its context cost"라고 적는다. 모범 사례 문서는 "Would removing this cause Claude to make mistakes? If not, cut it", "If you emphasize many lines, none of them stands out", "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic"라고 적는다([출처](https://code.claude.com/docs/en/best-practices)).
- **한 번에 다시 쓰지 않는다** — OpenAI 는 "Do not rewrite a working prompt stack all at once", "Remove one group of instructions, examples, or tools at a time, then rerun the same evals"라고 적는다.
- **실패 기반 평가** — Anthropic 은 "20-50 simple tasks drawn from real failures is a great start", "One-sided evals create one-sided optimization", "Because model outputs vary between runs, we run multiple trials", "LLM-as-judge graders should be closely calibrated with human experts"라고 적는다([출처](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
- **찾지 못한 것** — 같은 조항을 금지형과 긍정형으로 짝지어 위반률을 비교한 통제 실험은 학술·벤더 자료 모두에서 찾지 못했다. 그래서 긍정형 전환의 효과는 측정되지 않은 가설이며, 빌더가 실패 평가 세트로 직접 측정한다.

## 결정

**사용자가 정한 것**(2026-10-18, 선택 도구로 답함)

- **조항 형식** — 판단 조항은 결정 규칙으로 다시 쓰고, 불변 조건만 금지문으로 남긴다.
- **이유** — 조항마다 이유 한 줄을 붙인다. 측정 기록과 출처 같은 상세 근거는 현행처럼 `docs/domain-discipline.md`·`docs/domain-korean.md` 에 둔다.
- **금지어 목록** — 금지어 목록에 상황 칸을 추가하고, 검사기 트랙과 지시형 트랙을 따로 만든다. 세션에는 지시형 트랙만 싣는다.
- **검증** — 실패 평가 세트로 기준 원칙과 개편안을 비교한다. 빌더는 개편을 단계별로 적용하고 단계마다 측정한다.
- **파일 구성** — 원칙은 한 파일에 두고 층별로 절을 나눈다.
- **금지어 원본** — 원본은 현행 마크다운 표로 두고 상황 칸을 추가한다. 세션에 실리는 지시형 트랙에는 금지어를 적지 않는다.
- **평가 과제의 보관** — 과제를 사용자 메시지 원문 대신 상황·기대 행동·판정 기준으로 다시 쓰고, 업무 수치·종목·키·사람 이름을 뺀 뒤 저장소에 커밋한다.
- **판정** — 생성과 다른 크기의 Claude 모델이 판정하고, 사용자가 단계마다 판정 10건 안팎을 확인해 일치도를 기록한다.
- **실행 방식** — 헤드리스 세션(`claude -p`)을 임시 설정 폴더(`CLAUDE_CONFIG_DIR`)로 실행해 실제 세션과 같은 경로로 원칙을 싣는다. 여러 턴 사례는 앞 턴을 스크립트로 넣어 재생한다. 반복은 3회로 하고, 단계마다 개발용 과제로 측정하며, 보류용 과제는 최종안과 기준 원칙의 비교에 한 번 쓴다. 빌더는 plan 첫 단계에서 CLI 의 `claude plugin eval` 을 시험 실행해, SessionStart 훅이 그 조건의 원칙을 싣는지, 실제 `~/.claude` 를 고치지 않는지, 두 플러그인 경로를 비교할 수 있는지를 확인한다. 셋 모두 되면 그 명령으로 실행하고, 하나라도 안 되면 위의 `claude -p` 방식으로 실행한다(2차 리뷰 뒤 결정).
- **시험 규칙** — CLAUDE.md 의 클린룸 소거 시험은 조항 하나의 추가와 변경에 그대로 쓰고, 구조 개편과 여러 조항의 동시 변경에는 실패 평가 세트를 쓴다. 평가 세트가 생긴 뒤에는 조항 하나를 고칠 때도 회귀 시험으로 함께 실행한다. 단계 5 의 새 조항 후보는 구조 개편의 일부로 보고 실패 평가 세트의 개발용 과제로만 채택을 판정한다(2차 리뷰 뒤 결정). 클린룸 소거 시험은 병합 뒤의 조항 하나 변경에 쓴다.
- **`REVERSIBLE` 의 불변 조건 범위** — 복구할 수 없는 삭제·덮어쓰기(커밋·백업이 없는 파일과, git 이 추적하더라도 커밋하지 않은 수정이 있는 파일, 원격 브랜치·저장소 삭제, 이력 재작성)와 사용자 밖으로 나가는 전송(메일·메시지·공개 게시·남의 저장소)만 불변 조건으로 둔다. 사용자 자기 저장소로의 푸시와 커밋된 상태로 되돌릴 수 있는 추적 파일의 덮어쓰기는 판단 조항으로 내리고, 세션 안에서 한 번 승인받은 같은 작업은 다시 묻지 않는다.
- **개편 범위** — `skills/review-specs`, `skills/review-docs`, `skills/dispatching-lenses` 에서 새 결정 규칙과 같은 상황에 부딪히는 문장만 고쳐 원칙의 멈출 조건을 가리키게 한다. 다른 세션이 선행연구 에이전트 개발로 `review-specs`·`dispatching-lenses` 를 고치고 있으므로, 빌더는 병합 전에 그 변경과 대조한다. 대조는 그 세션에 메시지로 묻거나 main 에 병합된 커밋만 읽어서 한다. 그 세션의 작업 중인 브랜치와 worktree 는 읽지 않는다.
- **병합 방식** — 이 worktree 브랜치에서 단계 1~5 를 모두 측정하고, 최종안이 보류용 과제에서 기준 원칙보다 나을 때만 main 에 한 번 병합한다. 빌더는 보류용 비교 직전에 main 을 브랜치로 가져와 충돌을 해소하고, 그 결과로 보류용 비교를 실행한다. 충돌 해소로 바뀐 원칙 문안도 측정에 들어가게 하기 위해서다.

**메인 세션이 정한 것**(사용자가 읽으며 확인할 대상)

조항 사이의 우선순위 목록은 두지 않는다. 충돌하는 조항 쌍은 적용 조건을 나누거나, 한쪽 조항이 적은 수단을 그 수단이 노리는 목적으로 바꿔 적어 같은 상황에 둘이 함께 발동해도 부딪치지 않게 고친다. 세션 기록에서 확인한 충돌 쌍은 `REVERSIBLE` 과 `RUN-IT`, `ASK-OPTIONS` 와 사용자 위임, `YAGNI` 와 `KEEP-FAILED`, `TITLE-CLAIM`(40자) 과 `NO-SQUEEZE`, `TITLE-CLAIM` 과 `LABEL-NOUN`, 한국어 출력과 `VOCAB-PREF`(원어 표준 용어), 금지어 표와 `VOCAB-PREF` 다. 현행 첫 문단의 "원칙 사이에 우열은 없으니"는 지우고, "상황에 해당하는 조항을 모두 적용하라"는 "해당하는 층을 모두 적용하라"로 바꿔 남긴다. 한 출력에 여러 층이 겹쳐 적용되기 때문이다. 이 변경은 단계 2 에서 한다.

불변 조건 목록의 초안은 다음과 같다. 첫째는 `SECRETS` 로, 비밀과 개인정보를 프롬프트·로그·문서·검색어에 적지 않는 조항이다. 둘째는 `REVERSIBLE` 중 사용자가 정한 범위(복구할 수 없는 삭제와 사용자 밖으로 나가는 전송)다. 셋째는 사용자가 다른 세션이 맡았다고 한 저장소를 읽거나 검사하거나 고치지 않는 조항이며, 메모리 규칙(`other-sessions-message-only`)과 같은 범위로 적는다. 나머지 조항은 판단 조항으로 본다. 빌더는 불변 조건마다 훅으로 강제할 수 있는지 검토한다.

새 조항 후보는 세션 기록에서 반복된 공백에서 뽑았다. 물은 질문에 첫 문장으로 답하기, 위임·보류 뒤 질문 멈추기, 세션 안 결정과 새 제안 대조, 제외 항목과 기준 공개, 모르는 이름은 먼저 검색, 다른 에이전트에게 주는 지시문을 사실 진술과 긍정 명령으로 나눠 쓰기가 그것이다. 후보는 실패 평가 세트의 개발용 과제에서 개선을 보인 것만 넣는다.

## 목차 구조

원칙은 한 파일 안에 아래 층을 둔다. 첫 문단에는 하네스 기본 지침보다 이 원칙을 우선한다는 문장과 "해당하는 층을 모두 적용하라"를 둔다.

| 층 | 적용 조건 | 들어갈 묶음(현행 기준) |
|---|---|---|
| 모든 작업 | 항상 | 「균형」 문단, 현행 「원칙」의 `TITLES` 를 뺀 조항, `LENS-ALLOWED`, 「미해결의 처분」, 「병렬 오케스트레이션」 |
| 모든 답 | 사용자에게 글을 보낼 때(대화 답 포함) | 출력 언어, `PLAIN-KO`·`KO-SYNTAX`·`PROSE-FORM`·`READ-FLOW`·`UNPACK`·`REVISE-ORDER` |
| 남에게 전달하는 산출물 | 사용자가 보고서·제안서·발표자료·README 를 만들라고 하거나 다른 사람에게 보낼 글을 쓸 때 | `TITLES`, `NO-RAW-OUTPUT` 의 산출물 부분 |
| 작업 문서·지시문 | spec·plan·CLAUDE.md·스킬·메모리·다른 에이전트에게 주는 지시문을 쓸 때 | 「문서를 쓰고 관리할 때」, `NO-RAW-OUTPUT` 의 spec·plan 부분 |
| 코드 | 코드를 바꿀 때 | `EXPLAIN-STRUCTURE` |

조항 ID 는 유지한다. 근거 참고서와 검사 스크립트(`scripts/test_docs_drift.sh`)가 ID 로 연결되어 있기 때문이다. 한 조항을 두 층이나 두 형식으로 나누면, 원래 ID 는 판단 조항이나 주된 쪽에 남기고 나눈 쪽에 새 ID 를 붙인다. 새 ID 는 근거 참고서에도 같은 이름으로 올린다. 원칙 안에서 원래 ID 를 가리키는 문장(예: 「균형」 문단의 `CHECKABLE`·`NO-RAW-OUTPUT`)도 같은 단계에서 새 ID 를 함께 가리키게 고친다.

단계 1 에서는 `REVISE-ORDER` 를 '모든 답' 층에 두되 현행의 대화 답 제외 문장을 그대로 옮기고, 「검증」 묶음은 나누지 않고 '작업 문서·지시문' 층에 현행 적용 조건 문장과 함께 둔다. 표의 `REVISE-ORDER` 범위 확대와 `NO-RAW-OUTPUT` 분할은 단계 2 에서 한다.

## 조항 형식

판단 조항은 "상황 → 행동 → 멈출 조건. 이유 한 줄." 순서로 쓴다. 빌더는 상황을 EARS(요구사항 문형 표준, While·When·If 로 조건 종류를 나누는 형식)처럼 상태·사건·예외로 나눠 관찰할 수 있게 쓰고, 멈출 조건은 사용자 위임·기준 충족·횟수 같은 사건으로 쓴다. 예를 들면 다음과 같다. "사용자가 방향을 정한 뒤 되돌릴 수 있는 하위 결정이 생기면 권장안으로 실행하고 결과 보고에 적어라. 되돌리기 어렵거나 결론을 바꾸는 결정만 선택 도구로 물어라. 사용자가 같은 결정을 반복해서 받지 않게 하기 위해서다."

불변 조건은 "~하지 마라. 이유 한 줄." 형식으로 쓰고 강조어는 쓰지 않는다.

## 금지어 2트랙

원본은 현행처럼 이 저장소 루트의 `korean-banned-words.md` 마크다운 표 하나다(2026-10-06 사용자 결정). 사용자는 2026-10-18 에 이 표에 상황 칸을 추가하기로 정했다.

검사기 트랙은 표의 금지어·제외어·적용 대상이다. 상황 칸은 제외 칸 뒤의 여섯째 칸으로 추가한다. `hooks/_banned_words.sh` 의 파서가 첫째·둘째·셋째·다섯째 칸(awk 필드 `c[2]`·`c[3]`·`c[4]`·`c[6]`)을 위치로 읽으므로, 마지막 칸에 두면 기존 칸의 위치가 바뀌지 않는다. 이 파서를 쓰는 `hooks/doc_word_*.sh`·`hooks/stop_gates.sh` 와 `scripts/check_banned_words.sh` 는 지금처럼 플러그인 폴더의 원본 표를 읽고, 파서 시험(`scripts/test_hooks.sh` 의 다섯 칸 픽스처)은 여섯 칸 표도 시험하게 고친다.

지시형 트랙은 표의 상황 칸과 대체어 칸만으로 '어떤 상황에서 어떤 말을 써라'를 만든 `korean-word-guide.md` 다. `scripts/scaffold.sh` 가 원본 표에서 이 파일을 생성해 `~/.claude/disciplined-coder/` 에 두고, 관리블록(scaffold.sh 가 `~/.claude/CLAUDE.md` 에 자동으로 넣는 `@import` 구간)이 원칙 사본과 이 파일만 싣는다. 원본 `korean-banned-words.md` 는 그 폴더에 더 이상 복사하지 않는다. 그 폴더의 파일 목록과 위생 화이트리스트는 `scripts/_scaffold_common.sh` 가 소유하므로, 빌더는 거기서 복사 대상과 생성 대상을 나눠 적는다. 지시형 트랙에는 금지어를 적지 않는다. 사용자가 세션에 실리는 `@import` 에 금지어를 넣지 않으려고 이 구조를 제안했기 때문이다. 현행 목록 파일의 표 밖 지시(불릿은 같은 종류만, '것' 대신 이름, 기간은 'N내' 등)는 문자열로 검사할 수 없으므로 지시형 트랙으로 옮기고, 그 문장도 금지어를 이름으로 대지 않게 고친다.

다른 플러그인이 자기 관리블록으로 금지 표현 목록을 싣는 PC 에서는 이 변경 뒤에도 금지어가 세션에 실린다. 그 플러그인의 관리블록은 이 저장소 밖이므로 이 개편의 범위에서 뺀다. 빌더는 이 PC 의 `~/.claude/CLAUDE.md` 에 그런 import 가 있는지 확인해 사용자에게 알린다.

`docs/domain-korean.md` 「지시문의 형태」의 실측은 이 결정을 지지한다. 금지어 없이 대체어만 준 조건이 목표 낱말을 가장 많이 썼다. 그 절이 현행 형태를 고른 사유(검사할 글자를 표에서 뽑아낼 수 있음)는 검사기 트랙이 원본 표를 그대로 읽으므로 유지된다. 다만 그 실측은 금지어 문자열과 목표 낱말의 등장만 셌고 낯선 대체어를 만든 행동은 세지 않았다. 빌더는 단계 4 에서 기준 원칙과 비교해 대화 답의 금지어 빈도를 측정하고, 빈도가 늘면 단계 4 를 되돌린다. 「지시문의 형태」 절은 단계 4 결과에 맞춰 개정한다.

## 검증과 단계

**실패 평가 세트**

빌더는 세션 기록 분석의 사례에서 과제 30~50개를 뽑는다. 출력 종류별 분포는 기록의 분포에 맞추고, 과제마다 행동이 일어나야 하는 사례와 일어나지 말아야 하는 사례를 함께 둔다. 과제는 개발용과 보류용으로 나눈다. 단계마다의 측정과 새 조항 후보의 채택 판정에는 개발용만 쓰고, 보류용은 「결정」의 병합 방식대로 최종안과 기준 원칙의 비교에 한 번 쓴다.

빌더는 「결정」의 실행 방식대로 같은 과제를 조건마다 3회 실행한다. 각 단계는 기준 원칙과 직전 단계 양쪽과 비교한다. 과제는 일반화해 저장소에 커밋한다. 사례 단위 원자료는 이 spec 을 쓴 세션(741c4063)의 기록에 분석 서브에이전트 보고 여섯 건으로 남아 있다(`~/.claude/projects/D--projects-Structure-disciplined-coder--claude-worktrees-principles-positive-restructure/741c4063-350d-40b1-b4d0-2b61437b5a6d.jsonl`, 이 PC 에만 있다). 빌더는 그 보고에서 과제를 뽑아 일반화한다. Claude Code 는 오래 쓰지 않은 세션 기록을 정리 기한(`cleanupPeriodDays`, 기본 30일) 뒤 지우므로, 빌더는 plan 첫 단계에서 그 보고 여섯 건을 저장소 밖 로컬 폴더로 옮겨 두고 과제 일반화와 커밋을 단계 1 측정 전에 끝낸다. 판정은 생성 모델과 다른 모델이 하고, 사용자가 표본 일부를 확인해 판정자와 일치하는지 본다. 분량은 줄 수와 글자 수로 함께 기록한다.

판정 기준은 CLAUDE.md 「조항 추가와 문구 변경」의 비교 방식을 따른다. 빌더는 조건마다 개발용 과제 전체의 위반 합계(과제 수 × 3회)를 센다. '개선'은 비교 상대보다 위반 합계가 적은 상태이고, 같으면 개선이 아니다. '나쁘지 않다'는 위반 합계가 비교 상대 이하인 상태다.

극성 짝(같은 조항의 금지형과 긍정형) 실험은 단계 2 에서 결정 규칙으로 바꾼 판단 조항마다 바꾸기 전 문안과 비교하는 데 쓴다. 결정 규칙이 바꾸기 전 문안보다 낫지 않은 조항이 나오면, 빌더는 그 조항을 금지형으로 되돌리지 않고 결과를 사용자에게 알려 처리를 묻는다. 판단 조항은 결정 규칙으로 쓴다는 사용자 결정이 있기 때문이다.

**실행 환경**

빌더는 조건(기준 원칙과 각 단계)마다 그 조건의 커밋을 체크아웃한 별도 worktree 를 만들고, 새 임시 설정 폴더에 그 worktree 를 로컬 마켓플레이스로 등록해 플러그인을 설치한다. SessionStart 의 `scripts/scaffold.sh` 는 세션마다 설치된 플러그인 폴더의 원칙으로 사본을 덮어쓰므로, 사본만 바꿔 넣는 방법은 쓰지 않는다. 이렇게 하면 단계 2 에서 고친 스킬도 그 조건의 플러그인으로 실린다. 플러그인 자동 갱신은 끈다. 사용자 전역 `CLAUDE.md` 의 관리블록 밖 내용과 과제에 필요한 메모리는 모든 조건에 같게 넣는다.

평가 세션은 원격이 없는 일회용 복제 저장소에서 실행한다. 개편안은 자기 저장소 푸시를 판단 조항으로 내리므로, 평가 중 실제 원격에 푸시되지 않게 하기 위해서다. 임시 설정 폴더에서 로그인과 플러그인 적재가 되는지는 확인하지 않은 가정이다. 빌더는 plan 첫 단계에서 이를 확인하고, 되지 않으면 사용자에게 알린다.

여러 턴 과제는 앞 턴의 사용자 메시지와 Claude 응답을 모두 일반화한 고정 문장으로 과제에 적고, 마지막 턴의 응답 하나만 판정한다. 앞 턴 Claude 응답을 조건마다 생성하면 다음 사용자 턴이 그 응답과 맞지 않아 과제가 성립하지 않기 때문이다. 고정한 앞 턴에 잘못이 들어 있는 과제는 마지막 턴에서 그 잘못을 반복하지 않는지를 판정 기준으로 쓴다. 고정 대화를 세션에 넣는 방법은 plan 에서 정한다.

**단계**

빌더는 단계마다 측정하고, 확인 기준을 채우지 못한 단계는 되돌린다. 다음 단계는 마지막으로 남긴 상태 위에서 진행하고, '직전 단계'는 그 상태를 가리킨다. 단계 1 이나 단계 2 를 되돌리면 뒤 단계의 전제가 바뀌므로, 빌더는 다음 단계로 가기 전에 결과를 사용자에게 알리고 진행 여부를 묻는다.

1. **층 재배치** — 조항 문구와 각 묶음의 현행 적용 조건 문장을 바꾸지 않고 목차만 옮긴다. 확인: 위반 합계가 기준 원칙보다 나쁘지 않다.
2. **판단 조항의 결정 규칙화와 충돌 쌍 해소** — 이유 한 줄은 아직 붙이지 않는다. 층의 적용 조건을 사건으로 바꾸고, 첫 문단 문장, `REVISE-ORDER` 의 범위, `NO-RAW-OUTPUT` 의 분할도 이 단계에서 바꾼다. 「결정」의 개편 범위에 든 스킬 문장도 이 단계에서 고친다. 확인: '확인 의무의 무한 적용' 사례와 충돌 쌍 사례의 위반이 줄고, 발동해야 할 사례의 위반이 늘지 않는다.
3. **이유 한 줄 결합** — 판단 조항과 불변 조건 모두에 붙인다. 확인: '형식 압력' 사례의 위반이 줄고, 분량 변화를 기록한다.
4. **금지어 지시형 트랙 전환** — 확인: '언어 압력' 사례의 위반이 줄고, 대화 답의 금지어 빈도가 늘지 않는다.
5. **새 조항 후보 시험** — 확인: 후보마다 개발용 과제에서 개선을 보인다.

## 저장소 규칙의 변경

빌더는 CLAUDE.md 의 아래 항목을 고친다.

- **지시와 근거의 분리** — "에이전트원칙에는 행동 지시와 그 이유 한 줄을 적는다. 측정 기록과 출처는 참고서에 조항 ID 로 적는다"로 바꾼다.
- **조항 추가와 문구 변경** — 클린룸 소거 시험은 그대로 두고, 구조 개편과 여러 조항의 동시 변경에는 실패 평가 세트를 쓰며 평가 세트가 생긴 뒤에는 조항 하나의 변경에도 회귀 시험으로 함께 실행한다는 문장을 추가한다. 그 문장에는 평가 세트의 경로와 실행 명령을 함께 적는다.
- **명령형** — 판단 조항은 결정 규칙, 불변 조건은 금지문이라는 구분을 추가한다.

## 열린 위험

현행 원칙은 146줄이고, 금지어 목록(78줄)과 함께 세션마다 약 224줄이 실린다. 이유 한 줄을 붙이면 원칙이 늘고, 현행 조항은 한 줄에 여러 문장이 들어 있어 줄 수만으로는 증가가 드러나지 않는다. 빌더는 단계마다 줄 수와 글자 수를 기록하고, 분량 증가가 평가 점수를 떨어뜨리면 층 분리(조건부 로드)를 다시 검토한다. 사용자는 조건부 로드의 발동 누락 위험을 이유로 한 파일 구성을 택했다.

층 판정은 한 파일이라도 모델이 한다. 적용 조건을 사건으로 쓰는 것으로 위험을 줄이지만 없애지는 못한다. 빌더는 평가 세트에 대화 중 만든 산출물 과제를 넣어 측정한다.

긍정형 전환의 효과는 선행 자료에서 측정되지 않았다. 단계 2 의 결과가 개선을 보이지 않으면 빌더는 그 단계를 되돌린다. 판정 모델도 Claude 계열이면 자기 선호 편향이 남으므로, 빌더는 사용자 확인 표본으로 판정자와의 일치도를 기록한다.
