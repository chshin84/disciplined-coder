# nested-orchestration 큰 개발 분할 — 설계

이 설계는 2026-10-09에 썼다. 기능 여럿이 섞인 개발에서 현재 세션은 PM 역할만 맡고, 워크스트림마다 서브 세션이 하부 명세부터 구현까지 맡도록 `nested-orchestration`을 고친다. 사용자는 gm-dashboard 세션(`D:\test\gm_dashboard`, 2026-10-07)에 「큰 개발의 명세 분할 지시문」을 붙여 넣었고, 이 설계는 그 지시문에서 출발한다. 지시문의 초안과 선행연구는 `docs/대화전문-2026-10-06_07.md` 156행 이후에 있다.

2026-10-07에 렌즈(adversarial, consistency, grounding, fit)로 지시문을 검토했고 그 기록은 `docs/superpowers/reviews/2026-10-07-large-dev-directive-check.md`다. 사용자는 2026-10-07~09에 이 세션 대화에서 그 지적을 하나씩 처분했고, 아래 「결정」이 그 처분이다. 2026-10-09에 이 spec을 두 차례 렌즈로 리뷰했고(`docs/superpowers/reviews/2026-10-09-nested-orchestration-large-dev-review.md`, `…-review-2.md`), 리뷰로 바뀐 판단은 각 결정 안에 적었다.

## 용어

용어는 이 문서와 고칠 스킬 안에서 아래 뜻으로만 쓴다. 이름은 사용자가 2026-10-09에 정했다.

| 이름 | 뜻 | 예전 이름 |
|---|---|---|
| 현재 세션 | 사용자와 대화하며 큰 명세·계약·통합을 맡고 워크스트림의 명세·plan·구현은 직접 쓰지 않는 세션 | L1, 메인 세션 |
| 서브 세션 | 워크스트림 하나를 하부 명세부터 구현까지 맡고 사용자와 대화하지 못하는 서브에이전트 | L2, 서브오케스트레이터 |
| 워커 | 서브 세션이 실행하는 구현자와 렌즈 | L3 |
| 워크스트림 | 서브 세션 하나가 맡는 작업 단위 | 절 |
| 큰 명세 | 개발 전체를 워크스트림으로 나누고 워크스트림 사이 계약과 결정 기록을 적는 spec | 없음 |
| 하부 명세 | 워크스트림 하나의 내부 설계를 적는 spec | 절 명세 |
| 태스크 | plan 안의 실행 단계(superpowers 명칭) | 없음 |
| SDD | plan을 태스크마다 구현 워커와 리뷰어로 실행하는 superpowers `subagent-driven-development` 스킬 | 없음 |
| 🔴 | `review-specs`가 사용자 결정이 필요하다고 분류한 리뷰 지적 | 없음 |
| 클린룸 소거 시험 | CLAUDE.md가 빈 모델과 조항만 실은 모델에 같은 과제를 주어 조항의 효과를 재는 시험(저장소 CLAUDE.md 「조항 추가와 문구 변경」) | 없음 |

워크스트림이라는 뜻으로 '절'과 '섹션'을 쓰지 않는다. 이 저장소는 두 낱말을 문서 구분에 쓰고, gm-dashboard 세션에서 사용자가 "절 = 컴포넌트라고 보면 되나?"라고 되물었다. 2026-07-05 설계는 '워커'를 2층 경로 용어로 보고 3층에 쓰지 않기로 정했는데, 사용자는 읽기 편한 이름을 택해 3층에 '워커'를 쓰기로 했다.

## 바꾸는 이유

큰 개발이 들어와도 지금 구조에서는 현재 세션이 하위 시스템을 차례로 직접 진행한다. 원인은 아래와 같다.

- **에이전트원칙의 금지:** `SUB-ORCHESTRATE`는 "서로 독립된 일이 둘 이상"일 때만 서브오케스트레이터를 두게 하고 "일이 하나뿐이면 서브오케스트레이터를 두지 마라"고 적는다. 큰 개발 하나는 일 하나로 읽힌다.
- **늦은 트리거:** 스킬 description은 "멀티태스크 플랜이 둘 이상일 때"다. 플랜이 생긴 시점에는 현재 세션이 이미 명세와 plan을 썼다.
- **superpowers의 차례 진행:** `brainstorming` 203행은 큰 프로젝트를 하위 프로젝트로 나눈 뒤 "첫 하위 프로젝트를 일반 설계 흐름으로 브레인스토밍하라"고 적는다. 현재 세션은 이 문장대로 하위 프로젝트마다 spec→plan→구현을 차례로 밟는다.

사용자는 이 차례 진행이 맞지 않는다고 판단했다. 기능이 여럿 섞인 개발에서 한 세션이 모든 결정과 코드를 들고 가면 맥락이 섞이고, PM 역할과 구현 역할이 한 세션에 겹친다.

## 결정

사용자가 2026-10-07~09에 정한 처분과, spec 리뷰가 그 처분을 실행할 수 있게 보탠 규칙이다. 기각한 대안은 대화 기록에 있고 여기에는 채택안과 이유만 적는다.

**트리거.** `SUB-ORCHESTRATE`를 분해 시점을 가리키게 고치고, 스킬 description에 큰 개발 분할을 넣는다. 분해 판단은 brainstorming 대화 안에서 나오므로 그때 상시 실려 있는 에이전트원칙이 개입한다. 훅은 개발 규모를 판정하지 못해 작은 개발에도 넛지를 띄우므로 처음에는 두지 않는다. 훅을 추가할지는 「확인 방법」의 클린룸 소거 시험 결과를 보고 사용자가 정한다.

**층별 책임.** 현재 세션은 brainstorming으로 요구를 정리하고, 나눌 근거를 보여 사용자 승인을 받는다. 그다음 큰 명세와 계약 코드를 쓰고, 하부 명세를 승인하고, 통합 확인과 사용자 보고를 맡는다. 서브 세션은 자기 워크스트림의 하부 명세, 하부 명세 리뷰, plan, plan 리뷰, 구현을 맡는다.

**하부 명세 승인.** 서브 세션은 brainstorming 대화 없이 큰 명세와 계약 코드를 입력으로 하부 명세를 쓰고 `review-specs`로 렌즈 리뷰를 한다. 리뷰를 반영하면 서브 세션은 하부 명세를 커밋하고 상태 `AWAITING_APPROVAL`을 돌려주고 멈춘다. 현재 세션은 하부 명세를 큰 명세와 대조해 승인하거나 고칠 점을 보내고, 승인하면 같은 서브 세션에 이어 쓰기로 plan과 구현을 지시한다. 사용자가 직접 검토하는 문서는 큰 명세와 계약 코드 plan으로 한정한다.

**HARD-GATE 예외.** superpowers `brainstorming`의 HARD-GATE는 architectural 경로에서 사람이 spec을 승인하고 plan을 검토하고 실행 방식을 고르게 한다(46~49행). 서브 세션은 사람과 대화하지 못하므로, 스킬은 서브 세션에 한해 세 단계를 대체한다. spec 승인은 현재 세션이 맡는다. plan 검토는 `review-specs` 렌즈 리뷰가 맡는다. 실행 방식은 SDD로 고정한다. 서브 세션에 `using-superpowers`가 실려 brainstorming을 열 수 있으므로, 이 예외 문장을 스킬 본문과 디스패치 템플릿에 함께 넣는다.

**에이전트 이어 쓰기.** 하던 일이면 어느 층이든 같은 에이전트를 SendMessage로 재개하고, 새 일이면 같은 역할·같은 파일이어도 새 에이전트로 시작한다. 하던 일의 단위는 서브 세션이 워크스트림 하나, 구현 워커가 태스크 하나, 렌즈가 문서 하나의 리뷰 한 차수다. 사용자는 하던 일을 이어 가면 맥락이 증분으로 쌓이고 캐시 이득이 있다고 판단했다. SDD도 같은 일의 수정에서는 같은 구현 워커를 재개한다(75행 "R≤3 resume implementer").

**이어 쓰기의 근거와 반론.** `dispatching-lenses`는 한 에이전트 안에서 렌즈를 이어 적용하면 뒤 렌즈의 읽기 값이 첫 렌즈의 10분의 1이 된다는 배수를 정책값으로 적는다(57행). 같은 에이전트 재개와 새 에이전트에 파일을 넘기는 방식을 비교한 연구는 찾지 못했다(대화전문 1332행). spec 1차 리뷰에서 `lens-adversarial`은 사용자 답이 캐시 유지 시간보다 늦게 오는 일이 많고 재디스패치만 실측되었다며 재디스패치 하나로 두자고 지적했다. 사용자는 2026-10-09에 이어 쓰기의 이점이 캐시보다 증분 맥락에 있다고 보고 이 결정을 유지했다.

**이어 쓰기가 맡는 상황.** 하부 명세 승인 뒤 진행 지시, 사용자 답 전달, 통합 실패 수정, 그 워크스트림의 계약·공용 파일 변경 반영을 모두 그 워크스트림의 서브 세션에 이어 쓰기로 보낸다. 그래서 현재 세션은 워크스트림 코드를 직접 고치지 않는다. 메시지는 서브 세션이 끝나거나 멈춘 뒤에 보낸다. 실행 중인 서브 세션이 메시지를 받는지는 확인하지 않았다(「검증하지 않은 가정」).

**재개할 수 없을 때.** 세션이 끊겨 식별자가 사라지면 워크스트림 브랜치·하부 명세·plan과 워크트리에 남은 SDD ledger(SDD의 진행 기록 파일)를 넣어 새 서브 세션을 시작한다. 같은 워크스트림의 통합 실패가 되풀이될 때 새 서브 세션으로 바꾸는 횟수 기준은 두지 않는다. 그런 상황은 아직 관찰되지 않았으므로, 첫 큰 개발의 측정 트레일러로 필요를 확인한 뒤 정한다.

**멈추는 기준.** 서브 세션은 아래 사유에서만 멈추고 상태와 질문을 돌려준다. 그 밖의 모호함은 스스로 판정해 SDD ledger와 리포트에 적는다. 지시문의 "확인이 필요하면 멈춘다"는 SDD 19~31행의 "Rulings, not stalls"와 충돌하므로 쓰지 않는다.

- 하부 명세 리뷰를 마쳐 승인을 기다릴 때(`AWAITING_APPROVAL`)
- 하부 명세나 plan 리뷰에서 🔴가 나왔거나, 리스크상 필요한 리뷰 관점을 아무 렌즈도 보지 않았을 때(`BLOCKED`)
- 사람만 정할 수 있는 범위 밖 결정이나 계약·큰 명세·공용 파일 변경이 필요할 때(`BLOCKED`)
- SDD의 정지 사유(비가역 작업, 보안 작업, 워크트리 밖 부작용, 전부 추측인 plan)에 해당할 때(`BLOCKED`)

구현과 리뷰를 마치면 서브 세션은 상태 `DONE`을 돌려준다. 🔴는 `review-specs`가 "누구도 자율적으로 구현하지 않는다"고 정하므로 사유에 넣었다. 둘째 사유의 뒷부분은 지금 스킬의 BLOCKED 사유를 그대로 이어받았다.

**범위 밖 아이디어와 명세 분량.** 서브 세션은 범위 밖 아이디어를 리포트의 「제안」 항목에 적고, 현재 세션이 모아 사용자에게 보인다. 하부 명세에는 그 워크스트림의 책임과 계약을 구현하는 데 필요한 내용만 적고, 일어날 수 없는 예외를 늘어놓지 않는다. 두 규칙은 지시문의 「범위」와 「명세 분량」에서 가져왔고 디스패치 템플릿에 넣는다.

**계약 변경.** 서브 세션은 계약과 큰 명세를 고치지 않고 멈춰 보고한다. 현재 세션은 영향받는 워크스트림을 정리해 사용자에게 기각, 다음 개발로 미룸, 지금 채택 중 하나를 고르게 한다. 채택하면 현재 세션이 통합 브랜치에서 큰 명세와 계약 코드를 고친 뒤 영향받는 서브 세션에 이어 쓰기로 보낸다.

**공용 파일.** 라우팅 표, 진입점, 설정 등록부처럼 여러 워크스트림이 고쳐야 하는 파일은 현재 세션이 소유하고, 큰 명세의 소유 표에 적는다. 의존성 목록과 잠금 파일은 한 워크스트림에 맡기고, 그 워크스트림이 끝난 뒤에는 현재 세션이 고친다. gm-dashboard 큰 명세가 이렇게 나눴다(76~77행, 94행). 서브 세션은 소유하지 않은 공용 파일 변경이 필요하면 바꿀 내용을 적고 `BLOCKED`로 멈춘다.

**통합 브랜치의 변경 전파.** 현재 세션이 통합 브랜치에서 공용 파일이나 계약을 고치면, 영향받는 서브 세션에 이어 쓰기로 알린다. 서브 세션은 자기 워크트리에서 `git merge dev/<개발 이름>`으로 그 변경을 받은 뒤 일을 잇는다. 점 세 개 diff는 두 브랜치의 공통 조상부터 비교하므로, 이렇게 받은 변경은 범위 대조에 나오지 않는다.

**수정 범위 강제.** 큰 명세에 워크스트림마다 수정 허용 경로를 git pathspec 형식으로 적는다. 모든 워크스트림의 허용 경로에는 자기 문서 경로 셋(`docs/superpowers/specs/*-<개발 이름>-<워크스트림 id>-design.md`, `docs/superpowers/plans/*-<개발 이름>-<워크스트림 id>.md`, `docs/superpowers/reviews/*-<개발 이름>-<워크스트림 id>-*`)이 기본으로 들어간다. 패턴의 id 뒤를 닫아 두어, 한 id가 다른 id의 접두어일 때(`api`와 `apigw`) 서로의 문서를 허용하지 않는다. 현재 세션은 병합 전에 `git diff --name-only --no-renames dev/<개발 이름>...ws/<개발 이름>/<워크스트림 id>`로 변경 파일을 구해 허용 경로와 대조하고, 범위 밖 파일이 있으면 그 서브 세션에 되돌린다. `--no-renames`는 허용 경로 밖 파일을 안으로 옮긴 변경이 새 이름만 내서 통과하는 일을 차단한다.

**교집합 검사.** 동시에 진행한 워크스트림에는 지금의 브랜치 쌍 교집합 검사도 유지한다. 허용 경로 패턴이 서로 겹치는지는 사람이 보고 놓치기 쉽고, 교집합 검사는 2026-07-05 스파이크에서 실제 충돌을 잡은 가드다. 1차 반영 때 이 검사를 중복으로 보고 뺐다가, 2차 리뷰의 지적으로 되살렸다.

**경로와 브랜치 이름.** 큰 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-design.md`, 하부 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-<워크스트림 id>-design.md`, 워크스트림 plan은 `docs/superpowers/plans/YYYY-MM-DD-<개발 이름>-<워크스트림 id>.md`에 둔다. 통합 브랜치는 `dev/<개발 이름>`, 워크스트림 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 워크스트림 id는 큰 명세의 워크스트림 목록에 적은 영문 소문자 이름이다. 현재 세션은 디스패치 전에 `using-git-worktrees`로 `dev/<개발 이름>`의 끝에서 워크스트림 브랜치와 워크트리를 만든다. `Agent`의 `isolation:'worktree'`는 브랜치 이름과 기준 커밋을 정할 수 없어 쓰지 않는다.

**결정 기록.** 결정 기록은 별도 파일 대신 큰 명세의 「결정 기록」 절에 둔다. 현재 세션은 서브 세션을 처음 디스패치하기 전에 명명 관례, 오류 처리, 공용 유틸리티처럼 워크스트림마다 따로 정하면 충돌하는 결정을 이 절에 먼저 채운다. 서브 세션은 확정한 결정을 리포트에 적고, 현재 세션이 그 워크스트림을 병합한 뒤 이 절에 옮긴다. 사용자가 🔴나 범위 결정에 답하면 현재 세션이 그 답도 이 절에 적는다. 공개 인터페이스는 계약 코드에서 도출하므로 결정 기록에 옮겨 적지 않는다.

**실행 순서.** 의존 순서가 없고 수정 허용 경로가 겹치지 않는 워크스트림은 동시에 진행한다. 어떤 워크스트림이 다른 워크스트림의 산출물에 의존하면, 그 선행 워크스트림이 통합 브랜치에 들어간 뒤에 그 끝에서 시작한다. 지시문은 "다음 절은 이 확인을 통과한 뒤에 시작한다"고만 적어 동시 진행 규칙과 충돌했다.

**병합 전 검사.** 서브 세션이 `DONE`을 돌려주면 현재 세션은 범위 대조와 교집합 검사를 한다. 그다음 워크스트림 브랜치에 추가된 하부 명세·plan의 마지막 줄 `spec-review` 마커를 `git show ws/<개발 이름>/<워크스트림 id>:<경로>`로 읽어 확인한다. 현재 세션의 체크아웃에는 워크스트림 브랜치의 파일이 없으므로 작업 트리에서 읽지 않는다. 마커가 `escalated`이면 그 🔴의 사용자 답이 큰 명세 「결정 기록」에 있는지 확인하고, 없으면 병합하지 않는다.

**시험 병합과 통합.** 검사를 통과하면 현재 세션은 `dev/<개발 이름>`에서 임시 브랜치를 만들어 워크스트림 브랜치를 `--no-ff`로 병합하고, 그 위에서 계약 테스트와 큰 명세의 통합 확인을 실행한다. 통과하면 `dev/<개발 이름>`을 임시 브랜치로 fast-forward하고 임시 브랜치를 지운다. 실패하면 임시 브랜치를 지우고, 원인이 계약이면 큰 명세로, 워크스트림 내부면 그 서브 세션으로 보낸다. 통합 브랜치는 통과한 병합만 받으므로 되돌림 커밋이 생기지 않는다.

**시험 병합을 고른 이유.** 1차 반영은 통합 브랜치에 먼저 병합하고 실패하면 `git revert -m 1`로 되돌리게 했다. git은 되돌린 병합도 공통 이력으로 보므로, 고친 브랜치를 다시 병합하면 처음 병합의 변경이 빠진다(git 문서 `howto/revert-a-faulty-merge` 55~57행). 2차 리뷰가 이 결함을 찾아 시험 병합으로 바꿨다. 확인 명령의 실제 출력을 보기 전에는 완료로 보고하지 않고, 모든 워크스트림이 들어가면 현재 세션은 통합 브랜치 전체에 최종 브랜치 리뷰를 실행하고, 서브 세션들의 리포트에서 「제안」을 모아 사용자에게 보인다. 통합 브랜치를 main에 병합하는 일은 그다음 사용자 승인을 받아 한다.

**진행 위치.** 진행 위치는 상태 문서 없이 git에서 도출한다. 현재 세션은 워크스트림을 통합하는 병합 커밋 메시지에 `Workstream: ws/<개발 이름>/<워크스트림 id>` 트레일러를 적고, `git log dev/<개발 이름> --grep`으로 그 트레일러가 있는 워크스트림을 끝난 워크스트림으로 본다. `git branch --merged`는 커밋이 아직 없는 워크스트림 브랜치도 병합된 것으로 내므로 쓰지 않는다(plan 리뷰 때 스크래치 저장소에서 재현). 끝나지 않은 워크스트림 브랜치는 plan이 있으면 승인 뒤 진행 중이고, 하부 명세만 있으면 승인 대기이며, 둘 다 없으면 하부 명세 작성 중이다. 큰 명세 목록에 있는데 브랜치가 없는 워크스트림은 시작 전이다.

**문서 수명.** 에이전트원칙의 문서 수명 표를 따른다. 큰 명세와 하부 명세는 설계(spec) 타입으로 보존한다. 워크스트림 plan과 리뷰 기록은 개발 전체가 main에 병합된 뒤 보존 태그를 달고 지우되, 차수 대조에 쓰는 최근 리뷰 기록은 남긴다. 리포트는 지금처럼 프로젝트 밖 스크래치에 두고 커밋하지 않으며, 세션이 끊긴 뒤에는 리포트 없이 git과 큰 명세로 재개한다.

**측정.** 통합 실패 횟수와 원인, 서브 세션이 올린 질문 수, 워크스트림별 토큰(완료 통지의 `subagent_tokens`)을 센다. 통합 실패는 실패한 시험 병합의 수다. 현재 세션은 워크스트림을 통합 브랜치에 넣는 병합 커밋 메시지에 `Integration-Failures:`, `Questions:`, `Tokens:` 트레일러로 이 값을 적고, 개발이 끝날 때 `git log`에서 모아 사용자에게 보고한다. 검토 지적의 채택·기각 수는 출처가 없어 뺀다(`review-specs` 기록은 처분을 적지 않는다).

**계약 코드와 큰 명세.** 큰 명세는 `docs/superpowers/specs/`에 쓰는 spec이라 `review-specs`와 Stop 게이트(미리뷰 spec이 남은 채 턴을 끝내지 못하게 하는 훅)가 그대로 적용된다. 계약 코드(스텁, 타입, 계약 테스트)는 현재 세션이 큰 명세 승인 뒤 writing-plans, plan 리뷰, 사용자 plan 검토, 실행 순서로 진행한다. 현재 세션은 사람과 대화하므로 계약 코드에는 HARD-GATE 예외가 필요 없다. gm-dashboard 세션이 같은 순서로 진행했다.

**검토 범위.** 지시문의 "검토자의 지적 범위를 정확성, 명시된 요구, 계약 위반으로 한정한다"는 넣지 않는다. SDD 339행("Do not pre-judge findings for the reviewer")과, `dispatching-lenses` 「실행하는 방법」의 렌즈끼리 볼 것을 나눠 주지 않는다는 규칙과 충돌한다. 하부 명세의 비대는 「범위 밖 아이디어와 명세 분량」의 쓰는 쪽 규칙과 `lens-adversarial`의 YAGNI 지적이 맡는다.

## 이어받는 판단과 검증

2026-07-05 설계는 이 설계로 대체된다. 그 설계의 판단과 스파이크(시험 구현) 결과 중 이 설계에서도 유효한 것은 아래와 같고, 스킬은 이 절을 가리킨다.

- **Workflow 배제(R4):** `Workflow` 도구는 오케스트레이션을 스크립트에 두고 중첩을 1단계로 제한하므로, 판단으로 SDD를 실행하는 서브 세션을 수용하지 못한다. 그래서 `Workflow` 버전은 만들지 않는다.
- **관측성(R9):** 수동 `Agent` 중첩은 `/workflows` 집계 화면에 뜨지 않고, CLI의 서브에이전트 표시에서 각 서브 세션으로 들어가 본다. 집계 화면과 메트릭은 없다.
- **자율 완결(SC1):** 서브 세션이 사람 개입 없이 plan→TDD→리뷰를 끝내고 브랜치를 만들었고, 테스트를 독립 재실행해 통과했다.
- **3층 중첩(SC2):** 서브 세션 둘이 각각 구현 워커 하나와 읽기 전용 리뷰어 하나를 실행했다. 이 결과는 서브 세션의 자기보고다.
- **압축 리턴(SC3):** 서브 세션 둘 모두 상태·한 줄 요약·파일 경로만 돌려주었다.
- **BLOCKED 정직성(SC4):** 결정이 빠진 워크스트림에서 서브 세션이 추측하지 않고 질문으로 `BLOCKED`를 돌려주었다.
- **교집합 검사(SC5·SC6):** 교집합 검사가 리포트 파일 충돌을 잡았고, 가짜 겹침을 주입했을 때도 실패를 냈다.
- **BLOCKED 재디스패치(R6):** 사용자 답을 스펙에 접어 넣고 새 서브 세션을 디스패치하자 기존 커밋 위에서 남은 일을 완성했다. 이 설계에서 이 방법은 세션이 끊겼을 때의 대체 경로다.
- **리포트 위치:** 리포트를 워크트리 루트에 커밋하자 워크스트림끼리 병합 충돌이 났다. 그래서 리포트는 프로젝트 밖 스크래치에 두고 커밋하지 않는다.

이 설계가 새로 둔 규칙은 스파이크 범위 밖이다. 이어 쓰기 재개, 하부 명세 승인 대기, 수정 범위 대조, 시험 병합, 의존하는 워크스트림의 차례 진행이 여기에 해당한다. 첫 큰 개발에서 이 규칙과 아래 「검증하지 않은 가정」을 확인한 결과는 이 절에 추가한다.

## 근거와 한계

분할 구조의 근거는 엇갈리고, 이 구조를 단일 세션과 직접 비교한 연구는 찾지 못했다(대화전문 1401행, 1694행). 지시문을 쓸 때 근거 문장을 출처 없이 단정했으므로, 스킬의 큰 개발 분할 절에는 아래 범위로 출처와 한계를 함께 적는다.

| 지시문의 문장 | 출처가 보인 결과 | 스킬에 적을 문장의 범위 |
|---|---|---|
| "단위마다 새 맥락으로 작업하는 방식은 긴 개발에서 효과가 보고되었다" | Anthropic 장시간 하네스 글(2025-11)은 실패 원인(premature completion, inadequate testing)과 대책(한 번에 기능 하나)을 적었다(1210행). '기능마다 새 맥락'은 인용 없는 답에서 나왔다(1616행) | 원문을 확인하기 전에는 넣지 않는다 |
| "부분 정보만 받은 작업자는 통합에서 실패하기 쉽다" | Specification Gap(2026, 프리프린트)은 일부 정보만 받은 에이전트의 통합 정확도가 58%에서 25%로 떨어졌고 더 상세한 명세로만 회복되었다고 보고했다(1368행) | 프리프린트라는 한계와 함께 적는다 |
| "산문으로만 적은 계약은 통합에서 어긋난다" | 계약을 코드로 고정하는 방식은 CodeTeam·Contract-Coding의 설계 사례로 인용되었고, 산문과 코드를 비교한 결과는 없다(1386행) | "계약 코드는 통합 확인을 기계로 하게 한다"로 좁혀 적는다 |
| "작은 개발을 나누면 인계 비용이 이득보다 크다" | BenchAgent(2026, 프리프린트)는 벤치마크 10종을 정규화된 조건에서 실행해, 고정 역할 다중 에이전트 6종 중 5종이 단일 에이전트보다 2.56~11.29%p 뒤졌다고 보고했다(1296행). 평가가 단일 과제다(1681행) | 수치와 단일 과제 조건을 함께 적는다. Tran·Kiela(2026)는 평가가 코딩이 아니라 대화에서 버린 근거이므로 쓰지 않는다(1688행) |

## 바뀌는 파일

작업은 별도 워크트리의 브랜치에서 하고, main에는 병합으로만 들어간다. 클린룸 소거 시험을 먼저 하고, 원칙 문안 채택 여부를 사용자에게 보고한 뒤 나머지 파일을 고친다. 문안을 채택하지 않으면 스킬과 원칙이 서로 반대를 지시하게 되므로, 그때는 나머지 변경을 진행할지 사용자가 정한다.

`skills/nested-orchestration/SKILL.md`는 아래와 같이 고친다.

- description에 큰 개발 분할을 넣고 "재개는 무상태다"를 이어 쓰기 규칙으로 바꾼다.
- 「라우팅」 앞에 큰 개발 분할 절을 두고, 나눌지 판단·큰 명세·계약 코드·결정 기록·공용 파일·경로와 브랜치 이름과 「근거와 한계」 표의 문장을 넣는다.

## 확인 방법

구현하는 세션이 각 단계를 아래 기준으로 판정한다.

1. **트리거 시험:** 클린룸 소거 시험을 먼저 한다. CLAUDE.md의 과제 셋은 최소 수이고, 기존 트리거(서로 무관한 일)의 퇴행과 작은 개발에 대한 과잉 적용을 함께 보려고 과제 둘을 추가한다. 과제는 큰 개발 요청 셋, 서로 무관한 일 둘을 함께 맡기는 요청 하나, 작은 개발 요청 하나다. 조건은 CLAUDE.md가 빈 모델, 현행 「병렬 오케스트레이션」만 실은 모델, 새 문안만 실은 모델이다. 각 조건에서 모델이 차례로 직접 진행하는지, 사용자 승인을 받아 서브에이전트에 맡기는지를 센다.
2. **트리거 채택 판정:** 새 문안의 위반이 현행보다 적으면 채택한다. 같으면 큰 개발 과제 둘을 더 실행해 일곱 과제 합계가 현행보다 나쁘지 않을 때 채택하고, 나쁘면 채택하지 않는다. 새 문안이 작은 개발을 나누면 위반 수와 상관없이 채택하지 않는다. 새 문안을 채택했는데도 큰 개발 과제가 하나라도 차례로 진행되면 훅 추가를 사용자에게 제안한다.
3. **용어:** 원칙 문안을 채택했으면 `grep -nE 'L[123]|서브오케스트레이터|sub-orchestrator' skills/nested-orchestration/SKILL.md skills/dispatching-lenses/SKILL.md skills/review-specs/SKILL.md agent-principles.md scripts/test_docs_drift.sh`와 `grep -n '메인 세션' skills/nested-orchestration/SKILL.md`와 `grep -n '작업 다섯' docs/domain-discipline.md`의 출력이 비어 있다. `-w`는 조사가 붙은 `L2가`를 놓치므로 쓰지 않는다(리뷰 때 실측으로 `-w` 8줄, 없이 16줄).
4. **저장소 검사:** CLAUDE.md 「변경 뒤 실행」의 검사 묶음이 `ALL PASS`를 내고, `claude plugin validate ./`가 `version` 경고 하나만 낸다. 이번 변경에 영향받는 기존 검사는 `test_docs_drift.sh` 162행(dispatching-lenses 「한 번만 실행하는 렌즈의 규율」에 `nested-orchestration`이 있는지), 284~289행(nested-orchestration이 dispatching-lenses 「렌즈에게 에이전트원칙을 알리는 법」을 가리키는지), 786~789행(「병렬 오케스트레이션」 블록에 `nested-orchestration`과 `SUB-ORCHESTRATE`가 있는지), 867~871행(`Explore`와 관리 디렉터리 경로가 없는지)이다. 새 superseded 검사는 2026-07-05 설계의 표시를 지우면 실패해야 한다.
5. **새 가드레일:** 스크래치 git 저장소에 `dev/x` 브랜치와 `ws/x/a`·`ws/x/b` 브랜치를 만들고 스킬에 적은 명령을 그대로 실행한다. 선행 워크스트림을 시험 병합으로 넣은 뒤 그 끝에서 갈라진 브랜치가 허용 경로 안만 고쳤으면 범위 대조를 통과한다. 허용 경로 밖 파일을 추가하거나 허용 경로 밖 파일을 안으로 옮기면 그 파일이 출력된다. 마커 없는 하부 명세를 추가하면 마커 확인이 그 파일을 출력한다. 통합 확인이 실패하는 시험 병합 뒤에도 `dev/x`의 커밋이 바뀌지 않고, 고친 브랜치를 다시 시험 병합하면 처음 변경과 수정이 모두 들어간다.
6. **현장 확인:** 다음 큰 개발에서 측정 트레일러와 「검증하지 않은 가정」의 결과를 모아 「이어받는 판단과 검증」에 추가하고, 이 설계의 판단을 다시 본다.

## 검증하지 않은 가정

아래는 측정하지 못해 가정으로 둔다. 첫 큰 개발에서 확인한다.

- **끝난 서브 세션의 재개:** 하네스의 Agent 도구 설명은 SendMessage로 앞서 실행한 에이전트를 맥락을 유지한 채 이어 쓸 수 있다고 적는다. 끝난 지 오래된 서브 세션이 실제로 재개되는지는 실측하지 않았고, 재개가 실패하면 재디스패치로 넘어간다.
- **서브 세션의 SendMessage:** 서브 세션이 구현 워커를 이어 쓰려면 서브에이전트 맥락에서도 SendMessage가 제공되어야 한다. 제공되지 않으면 워커 층의 이어 쓰기는 SDD의 기본 동작에 맡긴다.
- **워커의 작업 디렉터리:** `isolation:'worktree'`를 쓰지 않으므로 서브 세션과 워커의 작업 디렉터리는 워크트리가 아닐 수 있다. 디스패치 템플릿이 워크트리 절대 경로를 넣고 모든 명령을 그 경로에서 실행하게 하며, 서브 세션도 워커 디스패치마다 같은 경로를 넣는다. 실제로 그 경로에서 실행되는지는 첫 큰 개발에서 확인한다.
- **클린룸 조건의 오염:** 클린룸 서브에이전트에도 하네스가 스킬 목록을 실으므로, 시험은 옛 `nested-orchestration` description이 실린 상태에서 실행된다. 전역 CLAUDE.md의 원칙이 서브에이전트에 실리지 않는다는 전제는 시험 전에 서브에이전트에게 물어 확인한다.
- **실행 중 메시지 수신:** 실행 중인 서브 세션에 보낸 메시지가 도착하는지 확인하지 않았으므로, 끝나거나 멈춘 뒤에 보낸다.
- **토큰 집계 범위:** 완료 통지의 `subagent_tokens`에 워커 토큰이 포함되는지 확인하지 않았다.
- **대기 중 캐시:** 이 하네스의 ScheduleWakeup 도구 설명은 프롬프트 캐시 유지 시간을 1시간으로 적는다. 사용자 답을 그보다 오래 기다린 서브 세션은 이어 써도 캐시 이득이 없을 것으로 본다.
- **클린룸 시험의 대표성:** 시험은 단발 요청으로 실행하지만 실제 분해 판단은 brainstorming 대화 여러 턴 뒤에 나오므로, 시험 결과가 실제 발동과 다를 수 있다.
