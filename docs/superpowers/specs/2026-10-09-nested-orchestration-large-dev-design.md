# nested-orchestration 큰 개발 분할 — 설계

이 설계는 2026-10-09에 썼다. 기능 여럿이 섞인 개발에서 현재 세션은 PM 역할만 맡고, 워크스트림마다 서브 세션이 하부 명세부터 구현까지 맡도록 `nested-orchestration`을 고친다. 사용자는 gm-dashboard 세션(`D:\test\gm_dashboard`, 2026-10-07)에 「큰 개발의 명세 분할 지시문」을 붙여 넣었고, 이 설계는 그 지시문에서 출발한다. 지시문의 초안과 선행연구는 `docs/대화전문-2026-10-06_07.md` 156행 이후에 있다.

2026-10-07에 렌즈(adversarial, consistency, grounding, fit)로 지시문을 검토했고 그 기록은 `docs/superpowers/reviews/2026-10-07-large-dev-directive-check.md`다. 사용자는 2026-10-07~09에 이 세션 대화에서 그 지적을 하나씩 처분했고, 아래 「결정」이 그 처분이다. 2026-10-09에 이 spec을 두 차례 렌즈로 리뷰했고(`docs/superpowers/reviews/2026-10-09-nested-orchestration-large-dev-review.md`, `…-review-2.md`), 리뷰로 바뀐 판단은 각 결정 안에 적었다.

## 용어

용어는 이 문서와 고칠 스킬 안에서 아래 뜻으로만 쓴다. 이름은 사용자가 2026-10-09에 정했다.

| 이름 | 뜻 | 예전 이름 |
|---|---|---|
| 현재 세션 | 사용자와 대화하며 큰 명세·계약·통합을 맡고 워크스트림의 명세·plan·구현은 직접 쓰지 않는 세션 | L1, 메인 세션 |
| 서브 세션 | 워크스트림 하나를 하부 명세부터 구현까지 맡고 사용자와 대화하지 못하는 서브에이전트 | L2, 서브오케스트레이터 |
| 워커 | 서브 세션이 실행하는 구현자와 렌즈 | L3 |
| 워크스트림 | 서브 세션 하나가 맡는 작업 단위 | 절 |
| 큰 명세 | 개발 전체를 워크스트림으로 나누고 워크스트림 사이 계약과 결정 기록을 적는 spec | 없음 |
| 하부 명세 | 워크스트림 하나의 내부 설계를 적는 spec | 절 명세 |
| 태스크 | plan 안의 실행 단계(superpowers 명칭) | 없음 |
| SDD | plan을 태스크마다 구현 워커와 리뷰어로 실행하는 superpowers `subagent-driven-development` 스킬 | 없음 |
| 🔴 | `review-specs`가 사용자 결정이 필요하다고 분류한 리뷰 지적 | 없음 |
| 클린룸 소거 시험 | CLAUDE.md가 빈 모델과 조항만 실은 모델에 같은 과제를 주어 조항의 효과를 재는 시험(저장소 CLAUDE.md 「조항 추가와 문구 변경」) | 없음 |

워크스트림이라는 뜻으로 '절'과 '섹션'을 쓰지 않는다. 이 저장소는 두 낱말을 문서 구분에 쓰고, gm-dashboard 세션에서 사용자가 "절 = 컴포넌트라고 보면 되나?"라고 되물었다. 2026-07-05 설계는 '워커'를 2층 경로 용어로 보고 3층에 쓰지 않기로 정했는데, 사용자는 읽기 편한 이름을 택해 3층에 '워커'를 쓰기로 했다.

## 바꾸는 이유

큰 개발이 들어와도 지금 구조에서는 현재 세션이 하위 시스템을 차례로 직접 진행한다. 원인은 아래와 같다.

- **에이전트원칙의 금지:** `SUB-ORCHESTRATE`는 "서로 독립된 일이 둘 이상"일 때만 서브오케스트레이터를 두게 하고 "일이 하나뿐이면 서브오케스트레이터를 두지 마라"고 적는다. 큰 개발 하나는 일 하나로 읽힌다.
- **늦은 트리거:** 스킬 description은 "멀티태스크 플랜이 둘 이상일 때"다. 플랜이 생긴 시점에는 현재 세션이 이미 명세와 plan을 썼다.
- **superpowers의 차례 진행:** `brainstorming` 203행은 큰 프로젝트를 하위 프로젝트로 나눈 뒤 "첫 하위 프로젝트를 일반 설계 흐름으로 브레인스토밍하라"고 적는다. 현재 세션은 이 문장대로 하위 프로젝트마다 spec→plan→구현을 차례로 밟는다.

사용자는 이 차례 진행이 맞지 않는다고 판단했다. 기능이 여럿 섞인 개발에서 한 세션이 모든 결정과 코드를 들고 가면 맥락이 섞이고, PM 역할과 구현 역할이 한 세션에 겹친다.

## 결정

사용자가 2026-10-07~09에 정한 처분과, spec 리뷰가 그 처분을 실행할 수 있게 보탠 규칙이다. 기각한 대안은 대화 기록에 있고 여기에는 채택안과 이유만 적는다.

**트리거.** `SUB-ORCHESTRATE`를 분해 시점을 가리키게 고치고, 스킬 description에 큰 개발 분할을 넣는다. 분해 판단은 brainstorming 대화 안에서 나오므로 그때 상시 실려 있는 에이전트원칙이 개입한다. 훅은 개발 규모를 판정하지 못해 작은 개발에도 넛지를 띄우므로 처음에는 두지 않는다. 훅을 추가할지는 「확인 방법」의 클린룸 소거 시험 결과를 보고 사용자가 정한다.

**층별 책임.** 현재 세션은 brainstorming으로 요구를 정리하고, 나눌 근거를 보여 사용자 승인을 받는다. 그다음 큰 명세와 계약 코드를 쓰고, 하부 명세를 승인하고, 통합 확인과 사용자 보고를 맡는다. 서브 세션은 자기 워크스트림의 하부 명세, 하부 명세 리뷰, plan, plan 리뷰, 구현을 맡는다.

**하부 명세 승인.** 서브 세션은 brainstorming 대화 없이 큰 명세와 계약 코드를 입력으로 하부 명세를 쓰고 `review-specs`로 렌즈 리뷰를 한다. 리뷰를 반영하면 서브 세션은 하부 명세를 커밋하고 상태 `AWAITING_APPROVAL`을 돌려주고 멈춘다. 현재 세션은 하부 명세를 큰 명세와 대조해 승인하거나 고칠 점을 보내고, 승인하면 같은 서브 세션에 이어 쓰기로 plan과 구현을 지시한다. 사용자가 직접 검토하는 문서는 큰 명세와 계약 코드 plan으로 한정한다.

**HARD-GATE 예외.** superpowers `brainstorming`의 HARD-GATE는 architectural 경로에서 사람이 spec을 승인하고 plan을 검토하고 실행 방식을 고르게 한다(46~49행). 서브 세션은 사람과 대화하지 못하므로, 스킬은 서브 세션에 한해 세 단계를 대체한다. spec 승인은 현재 세션이 맡는다. plan 검토는 `review-specs` 렌즈 리뷰가 맡는다. 실행 방식은 SDD로 고정한다. 서브 세션에 `using-superpowers`가 실려 brainstorming을 열 수 있으므로, 이 예외 문장을 스킬 본문과 디스패치 템플릿에 함께 넣는다.

**에이전트 이어 쓰기.** 하던 일이면 어느 층이든 같은 에이전트를 SendMessage로 재개하고, 새 일이면 같은 역할·같은 파일이어도 새 에이전트로 시작한다. 하던 일의 단위는 서브 세션이 워크스트림 하나, 구현 워커가 태스크 하나, 렌즈가 문서 하나의 리뷰 한 차수다. 사용자는 하던 일을 이어 가면 맥락이 증분으로 쌓이고 캐시 이득이 있다고 판단했다. SDD도 같은 일의 수정에서는 같은 구현 워커를 재개한다(75행 "R≤3 resume implementer").

**이어 쓰기의 근거와 반론.** `dispatching-lenses`는 한 에이전트 안에서 렌즈를 이어 적용하면 뒤 렌즈의 읽기 값이 첫 렌즈의 10분의 1이 된다는 배수를 정책값으로 적는다(57행). 같은 에이전트 재개와 새 에이전트에 파일을 넘기는 방식을 비교한 연구는 찾지 못했다(대화전문 1332행). spec 1차 리뷰에서 `lens-adversarial`은 사용자 답이 캐시 유지 시간보다 늦게 오는 일이 많고 재디스패치만 실측되었다며 재디스패치 하나로 두자고 지적했다. 사용자는 2026-10-09에 이어 쓰기의 이점이 캐시보다 증분 맥락에 있다고 보고 이 결정을 유지했다.

**이어 쓰기가 맡는 상황.** 하부 명세 승인 뒤 진행 지시, 사용자 답 전달, 통합 실패 수정, 그 워크스트림의 계약·공용 파일 변경 반영을 모두 그 워크스트림의 서브 세션에 이어 쓰기로 보낸다. 그래서 현재 세션은 워크스트림 코드를 직접 고치지 않는다. 메시지는 서브 세션이 끝나거나 멈춘 뒤에 보낸다. 실행 중인 서브 세션이 메시지를 받는지는 확인하지 않았다(「검증하지 않은 가정」).

**재개할 수 없을 때.** 세션이 끊겨 식별자가 사라지면 워크스트림 브랜치·하부 명세·plan과 워크트리에 남은 SDD ledger(SDD의 진행 기록 파일)를 넣어 새 서브 세션을 시작한다. 같은 워크스트림의 통합 실패가 되풀이될 때 새 서브 세션으로 바꾸는 횟수 기준은 두지 않는다. 그런 상황은 아직 관찰되지 않았으므로, 첫 큰 개발의 측정 트레일러로 필요를 확인한 뒤 정한다.

**멈추는 기준.** 서브 세션은 아래 사유에서만 멈추고 상태와 질문을 돌려준다. 그 밖의 모호함은 스스로 판정해 SDD ledger와 리포트에 적는다. 지시문의 "확인이 필요하면 멈춘다"는 SDD 19~31행의 "Rulings, not stalls"와 충돌하므로 쓰지 않는다.

- 하부 명세 리뷰를 마쳐 승인을 기다릴 때(`AWAITING_APPROVAL`)
- 하부 명세나 plan 리뷰에서 🔴가 나왔거나, 리스크상 필요한 리뷰 관점을 아무 렌즈도 보지 않았을 때(`BLOCKED`)
- 사람만 정할 수 있는 범위 밖 결정이나 계약·큰 명세·공용 파일 변경이 필요할 때(`BLOCKED`)
- SDD의 정지 사유(비가역 작업, 보안 작업, 워크트리 밖 부작용, 전부 추측인 plan)에 해당할 때(`BLOCKED`)

구현과 리뷰를 마치면 서브 세션은 상태 `DONE`을 돌려준다. 🔴는 `review-specs`가 "누구도 자율적으로 구현하지 않는다"고 정하므로 사유에 넣었다. 둘째 사유의 뒷부분은 지금 스킬의 BLOCKED 사유를 그대로 이어받았다.

**범위 밖 아이디어와 명세 분량.** 서브 세션은 범위 밖 아이디어를 리포트의 「제안」 항목에 적고, 현재 세션이 모아 사용자에게 보인다. 하부 명세에는 그 워크스트림의 책임과 계약을 구현하는 데 필요한 내용만 적고, 일어날 수 없는 예외를 늘어놓지 않는다. 두 규칙은 지시문의 「범위」와 「명세 분량」에서 가져왔고 디스패치 템플릿에 넣는다.

**계약 변경.** 서브 세션은 계약과 큰 명세를 고치지 않고 멈춰 보고한다. 현재 세션은 영향받는 워크스트림을 정리해 사용자에게 기각, 다음 개발로 미룸, 지금 채택 중 하나를 고르게 한다. 채택하면 현재 세션이 통합 브랜치에서 큰 명세와 계약 코드를 고친 뒤 영향받는 서브 세션에 이어 쓰기로 보낸다.

**공용 파일.** 라우팅 표, 진입점, 설정 등록부처럼 여러 워크스트림이 고쳐야 하는 파일은 현재 세션이 소유하고, 큰 명세의 소유 표에 적는다. 의존성 목록과 잠금 파일은 한 워크스트림에 맡기고, 그 워크스트림이 끝난 뒤에는 현재 세션이 고친다. gm-dashboard 큰 명세가 이렇게 나눴다(76~77행, 94행). 서브 세션은 소유하지 않은 공용 파일 변경이 필요하면 바꿀 내용을 적고 `BLOCKED`로 멈춘다.

**통합 브랜치의 변경 전파.** 현재 세션이 통합 브랜치에서 공용 파일이나 계약을 고치면, 영향받는 서브 세션에 이어 쓰기로 알린다. 서브 세션은 자기 워크트리에서 `git merge dev/<개발 이름>`으로 그 변경을 받은 뒤 일을 잇는다. 점 세 개 diff는 두 브랜치의 공통 조상부터 비교하므로, 이렇게 받은 변경은 범위 대조에 나오지 않는다.

**수정 범위 강제.** 큰 명세에 워크스트림마다 수정 허용 경로를 git pathspec 형식으로 적는다. 모든 워크스트림의 허용 경로에는 자기 문서 경로 셋(`docs/superpowers/specs/*-<개발 이름>-<워크스트림 id>-design.md`, `docs/superpowers/plans/*-<개발 이름>-<워크스트림 id>.md`, `docs/superpowers/reviews/*-<개발 이름>-<워크스트림 id>-*`)이 기본으로 들어간다. 패턴의 id 뒤를 닫아 두어, 한 id가 다른 id의 접두어일 때(`api`와 `apigw`) 서로의 문서를 허용하지 않는다. 현재 세션은 병합 전에 `git diff --name-only --no-renames dev/<개발 이름>...ws/<개발 이름>/<워크스트림 id>`로 변경 파일을 구해 허용 경로와 대조하고, 범위 밖 파일이 있으면 그 서브 세션에 되돌린다. `--no-renames`는 허용 경로 밖 파일을 안으로 옮긴 변경이 새 이름만 내서 통과하는 일을 차단한다.

**교집합 검사.** 동시에 진행한 워크스트림에는 지금의 브랜치 쌍 교집합 검사도 유지한다. 허용 경로 패턴이 서로 겹치는지는 사람이 보고 놓치기 쉽고, 교집합 검사는 2026-07-05 스파이크에서 실제 충돌을 잡은 가드다. 1차 반영 때 이 검사를 중복으로 보고 뺐다가, 2차 리뷰의 지적으로 되살렸다.

**경로와 브랜치 이름.** 큰 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-design.md`, 하부 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-<워크스트림 id>-design.md`, 워크스트림 plan은 `docs/superpowers/plans/YYYY-MM-DD-<개발 이름>-<워크스트림 id>.md`에 둔다. 통합 브랜치는 `dev/<개발 이름>`, 워크스트림 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 워크스트림 id는 큰 명세의 워크스트림 목록에 적은 영문 소문자 이름이다. 현재 세션은 디스패치 전에 `using-git-worktrees`로 `dev/<개발 이름>`의 끝에서 워크스트림 브랜치와 워크트리를 만든다. `Agent`의 `isolation:'worktree'`는 브랜치 이름과 기준 커밋을 정할 수 없어 쓰지 않는다. 현재 세션은 자기 체크아웃에서 `git worktree add`로 워크스트림 워크트리를 만들고, 큰 명세와 계약 코드는 `dev/<개발 이름>`에 커밋한다.

**결정 기록.** 결정 기록은 별도 파일 대신 큰 명세의 「결정 기록」 절에 둔다. 현재 세션은 서브 세션을 처음 디스패치하기 전에 명명 관례, 오류 처리, 공용 유틸리티처럼 워크스트림마다 따로 정하면 충돌하는 결정을 이 절에 먼저 채운다. 서브 세션은 확정한 결정을 리포트에 적고, 현재 세션이 그 워크스트림을 병합한 뒤 이 절에 옮긴다. 사용자가 🔴나 범위 결정에 답하면 현재 세션이 그 답도 이 절에 적는다. 공개 인터페이스는 계약 코드에서 도출하므로 결정 기록에 옮겨 적지 않는다.

**실행 순서.** 의존 순서가 없고 수정 허용 경로가 겹치지 않는 워크스트림은 동시에 진행한다. 어떤 워크스트림이 다른 워크스트림의 산출물에 의존하면, 그 선행 워크스트림이 통합 브랜치에 들어간 뒤에 그 끝에서 시작한다. 지시문은 "다음 절은 이 확인을 통과한 뒤에 시작한다"고만 적어 동시 진행 규칙과 충돌했다.

**병합 전 검사.** 서브 세션이 `DONE`을 돌려주면 현재 세션은 범위 대조와 교집합 검사를 한다. 그다음 워크스트림 브랜치에 추가된 하부 명세·plan의 마지막 줄 `spec-review` 마커를 `git show ws/<개발 이름>/<워크스트림 id>:<경로>`로 읽어 확인한다. 현재 세션의 체크아웃에는 워크스트림 브랜치의 파일이 없으므로 작업 트리에서 읽지 않는다. 마커가 `escalated`이면 그 🔴의 사용자 답이 큰 명세 「결정 기록」에 있는지 확인하고, 없으면 병합하지 않는다.

**시험 병합과 통합.** 검사를 통과하면 현재 세션은 `dev/<개발 이름>`에서 임시 브랜치를 만들어 워크스트림 브랜치를 `--no-ff`로 병합하고, 그 위에서 계약 테스트와 큰 명세의 통합 확인을 실행한다. 통과하면 `dev/<개발 이름>`을 임시 브랜치로 fast-forward하고 임시 브랜치를 지운다. 실패하면 임시 브랜치를 지우고, 원인이 계약이면 큰 명세로, 워크스트림 내부면 그 서브 세션으로 보낸다. 통합 브랜치는 통과한 병합만 받으므로 되돌림 커밋이 생기지 않는다.

**시험 병합을 고른 이유.** 1차 반영은 통합 브랜치에 먼저 병합하고 실패하면 `git revert -m 1`로 되돌리게 했다. git은 되돌린 병합도 공통 이력으로 보므로, 고친 브랜치를 다시 병합하면 처음 병합의 변경이 빠진다(git 문서 `howto/revert-a-faulty-merge` 55~57행). 2차 리뷰가 이 결함을 찾아 시험 병합으로 바꿨다. 확인 명령의 실제 출력을 보기 전에는 완료로 보고하지 않고, 모든 워크스트림이 들어가면 현재 세션은 통합 브랜치 전체에 최종 브랜치 리뷰를 실행하고, 서브 세션들의 리포트에서 「제안」을 모아 사용자에게 보인다. 통합 브랜치를 main에 병합하는 일은 그다음 사용자 승인을 받아 한다.

**진행 위치.** 진행 위치는 상태 문서 없이 git에서 도출한다. 현재 세션은 워크스트림을 통합하는 병합 커밋 메시지에 `Workstream: ws/<개발 이름>/<워크스트림 id>` 트레일러를 적고, `git log dev/<개발 이름> --grep`으로 그 트레일러가 있는 워크스트림을 끝난 워크스트림으로 본다. `git branch --merged`는 커밋이 아직 없는 워크스트림 브랜치도 병합된 것으로 내므로 쓰지 않는다(plan 리뷰 때 스크래치 저장소에서 재현). 끝나지 않은 워크스트림 브랜치는 plan이 있으면 승인 뒤 진행 중이고, 하부 명세만 있으면 승인 대기이며, 둘 다 없으면 하부 명세 작성 중이다. 큰 명세 목록에 있는데 브랜치가 없는 워크스트림은 시작 전이다.

**문서 수명.** 에이전트원칙의 문서 수명 표를 따른다. 큰 명세와 하부 명세는 설계(spec) 타입으로 보존한다. 워크스트림 plan과 리뷰 기록은 개발 전체가 main에 병합된 뒤 보존 태그를 달고 지우되, 차수 대조에 쓰는 최근 리뷰 기록은 남긴다. 리포트는 지금처럼 프로젝트 밖 스크래치에 두고 커밋하지 않으며, 세션이 끊긴 뒤에는 리포트 없이 git과 큰 명세로 재개한다.

**측정.** 통합 실패 횟수와 원인, 서브 세션이 올린 질문 수, 워크스트림별 토큰(완료 통지의 `subagent_tokens`)을 센다. 통합 실패는 실패한 시험 병합의 수다. 현재 세션은 워크스트림을 통합 브랜치에 넣는 병합 커밋 메시지에 `Integration-Failures:`, `Questions:`, `Tokens:` 트레일러로 이 값을 적고, 개발이 끝날 때 `git log`에서 모아 사용자에게 보고한다. 검토 지적의 채택·기각 수는 출처가 없어 뺀다(`review-specs` 기록은 처분을 적지 않는다).

**계약 코드와 큰 명세.** 큰 명세는 `docs/superpowers/specs/`에 쓰는 spec이라 `review-specs`와 Stop 게이트(미리뷰 spec이 남은 채 턴을 끝내지 못하게 하는 훅)가 그대로 적용된다. 계약 코드(스텁, 타입, 계약 테스트)는 현재 세션이 큰 명세 승인 뒤 writing-plans, plan 리뷰, 사용자 plan 검토, 실행 순서로 진행한다. 현재 세션은 사람과 대화하므로 계약 코드에는 HARD-GATE 예외가 필요 없다. gm-dashboard 세션이 같은 순서로 진행했다.

**검토 범위.** 지시문의 "검토자의 지적 범위를 정확성, 명시된 요구, 계약 위반으로 한정한다"는 넣지 않는다. SDD 339행("Do not pre-judge findings for the reviewer")과, `dispatching-lenses` 「실행하는 방법」의 렌즈끼리 볼 것을 나눠 주지 않는다는 규칙과 충돌한다. 하부 명세의 비대는 「범위 밖 아이디어와 명세 분량」의 쓰는 쪽 규칙과 `lens-adversarial`의 YAGNI 지적이 맡는다.

**서로 무관한 일.** 서로 무관한 일이 둘 이상이면 현재 세션이 일마다 brainstorming으로 요구를 정리해 큰 명세에 워크스트림별 요구로 적고 사용자 승인을 받는다. 워크스트림 사이 계약과 계약 코드는 생략하고 통합 확인은 각 워크스트림의 테스트로 대신한다. 하부 명세부터 구현까지는 큰 개발과 같이 서브 세션이 맡는다. 2026-10-10 최종 브랜치 리뷰가 이 공백을 찾았고 사용자가 위와 같이 정했다.

## 이어받는 판단과 검증

2026-07-05 설계는 이 설계로 대체된다. 그 설계의 판단과 스파이크(시험 구현) 결과 중 이 설계에서도 유효한 것은 아래와 같고, 스킬은 이 절을 가리킨다.

- **Workflow 배제(R4):** `Workflow` 도구는 오케스트레이션을 스크립트에 두고 중첩을 1단계로 제한하므로, 판단으로 SDD를 실행하는 서브 세션을 수용하지 못한다. 그래서 `Workflow` 버전은 만들지 않는다.
- **관측성(R9):** 수동 `Agent` 중첩은 `/workflows` 집계 화면에 뜨지 않고, CLI의 서브에이전트 표시에서 각 서브 세션으로 들어가 본다. 집계 화면과 메트릭은 없다.
- **자율 완결(SC1):** 서브 세션이 사람 개입 없이 plan→TDD→리뷰를 끝내고 브랜치를 만들었고, 테스트를 독립 재실행해 통과했다.
- **3층 중첩(SC2):** 서브 세션 둘이 각각 구현 워커 하나와 읽기 전용 리뷰어 하나를 실행했다. 이 결과는 서브 세션의 자기보고다.
- **압축 리턴(SC3):** 서브 세션 둘 모두 상태·한 줄 요약·파일 경로만 돌려주었다.
- **BLOCKED 정직성(SC4):** 결정이 빠진 워크스트림에서 서브 세션이 추측하지 않고 질문으로 `BLOCKED`를 돌려주었다.
- **교집합 검사(SC5·SC6):** 교집합 검사가 리포트 파일 충돌을 잡았고, 가짜 겹침을 주입했을 때도 실패를 냈다.
- **BLOCKED 재디스패치(R6):** 사용자 답을 스펙에 접어 넣고 새 서브 세션을 디스패치하자 기존 커밋 위에서 남은 일을 완성했다. 이 설계에서 이 방법은 세션이 끊겼을 때의 대체 경로다.
- **리포트 위치:** 리포트를 워크트리 루트에 커밋하자 워크스트림끼리 병합 충돌이 났다. 그래서 리포트는 프로젝트 밖 스크래치에 두고 커밋하지 않는다.
- **새 가드레일 실측(2026-10-09):** 임시 저장소에서 범위 대조·접두어 id·마커 확인·시험 병합·진행 위치 시나리오를 결함 주입으로 실행해 19개 검사를 모두 통과했다(plan Task 6).

이 설계가 새로 둔 규칙은 스파이크 범위 밖이다. 이어 쓰기 재개, 하부 명세 승인 대기, 수정 범위 대조, 시험 병합, 의존하는 워크스트림의 차례 진행이 여기에 해당한다. 첫 큰 개발에서 이 규칙과 아래 「검증하지 않은 가정」을 확인한 결과는 이 절에 추가한다.

## 근거와 한계

분할 구조의 근거는 엇갈리고, 이 구조를 단일 세션과 직접 비교한 연구는 찾지 못했다(대화전문 1401행, 1694행). 지시문을 쓸 때 근거 문장을 출처 없이 단정했으므로, 스킬의 큰 개발 분할 절에는 아래 범위로 출처와 한계를 함께 적는다.

| 지시문의 문장 | 출처가 보인 결과 | 스킬에 적을 문장의 범위 |
|---|---|---|
| "단위마다 새 맥락으로 작업하는 방식은 긴 개발에서 효과가 보고되었다" | Anthropic 장시간 하네스 글(2025-11)은 실패 원인(premature completion, inadequate testing)과 대책(한 번에 기능 하나)을 적었다(1210행). '기능마다 새 맥락'은 인용 없는 답에서 나왔다(1616행) | 원문을 확인하기 전에는 넣지 않는다 |
| "부분 정보만 받은 작업자는 통합에서 실패하기 쉽다" | Specification Gap(2026, 프리프린트)은 일부 정보만 받은 에이전트의 통합 정확도가 58%에서 25%로 떨어졌고 더 상세한 명세로만 회복되었다고 보고했다(1368행) | 프리프린트라는 한계와 함께 적는다 |

## 확인 방법

구현하는 세션이 각 단계를 아래 기준으로 판정한다.

1. **트리거 시험:** 클린룸 소거 시험을 먼저 한다. CLAUDE.md의 과제 셋은 최소 수이고, 기존 트리거(서로 무관한 일)의 퇴행과 작은 개발에 대한 과잉 적용을 함께 보려고 과제 둘을 추가한다. 과제는 큰 개발 요청 셋, 서로 무관한 일 둘을 함께 맡기는 요청 하나, 작은 개발 요청 하나다. 조건은 CLAUDE.md가 빈 모델, 현행 「병렬 오케스트레이션」만 실은 모델, 새 문안만 실은 모델이다. 각 조건에서 모델이 차례로 직접 진행하는지, 사용자 승인을 받아 서브에이전트에 맡기는지를 센다.
2. **트리거 채택 판정:** 새 문안의 위반이 현행보다 적으면 채택한다. 같으면 큰 개발 과제 둘을 더 실행해 일곱 과제 합계가 현행보다 나쁘지 않을 때 채택하고, 나쁘면 채택하지 않는다. 새 문안이 작은 개발을 나누면 위반 수와 상관없이 채택하지 않는다. 새 문안을 채택했는데도 큰 개발 과제가 하나라도 차례로 진행되면 훅 추가를 사용자에게 제안한다.
3. **용어:** 원칙 문안을 채택했으면 `grep -nE 'L[123]|서브오케스트레이터|sub-orchestrator' skills/nested-orchestration/SKILL.md skills/dispatching-lenses/SKILL.md skills/review-specs/SKILL.md agent-principles.md scripts/test_docs_drift.sh`와 `grep -n '메인 세션' skills/nested-orchestration/SKILL.md`와 `grep -n '작업 다섯' docs/domain-discipline.md`의 출력이 비어 있다. `-w`는 조사가 붙은 `L2가`를 놓치므로 쓰지 않는다(리뷰 때 실측으로 `-w` 8줄, 없이 16줄).
4. **저장소 검사:** CLAUDE.md 「변경 뒤 실행」의 검사 묶음이 `ALL PASS`를 내고, `claude plugin validate ./`가 `version` 경고 하나만 낸다. 이번 변경에 영향받는 기존 검사는 `test_docs_drift.sh` 162행(dispatching-lenses 「한 번만 실행하는 렌즈의 규율」에 `nested-orchestration`이 있는지), 284~289행(nested-orchestration이 dispatching-lenses 「렌즈에게 에이전트원칙을 알리는 법」을 가리키는지), 786~789행(「병렬 오케스트레이션」 블록에 `nested-orchestration`과 `SUB-ORCHESTRATE`가 있는지), 867~871행(`Explore`와 관리 디렉터리 경로가 없는지)이다. 새 superseded 검사는 2026-07-05 설계의 표시를 지우면 실패해야 한다.
5. **새 가드레일:** 스크래치 git 저장소에 `dev/x` 브랜치와 `ws/x/a`·`ws/x/b` 브랜치를 만들고 스킬에 적은 명령을 그대로 실행한다. 선행 워크스트림을 시험 병합으로 넣은 뒤 그 끝에서 갈라진 브랜치가 허용 경로 안만 고쳤으면 범위 대조를 통과한다. 허용 경로 밖 파일을 추가하거나 허용 경로 밖 파일을 안으로 옮기면 그 파일이 출력된다. 마커 없는 하부 명세를 추가하면 마커 확인이 그 파일을 출력한다. 통합 확인이 실패하는 시험 병합 뒤에도 `dev/x`의 커밋이 바뀌지 않고, 고친 브랜치를 다시 시험 병합하면 처음 변경과 수정이 모두 들어간다.
6. **현장 확인:** 다음 큰 개발에서 측정 트레일러와 「검증하지 않은 가정」의 결과를 모아 「이어받는 판단과 검증」에 추가하고, 이 설계의 판단을 다시 본다.

## 검증하지 않은 가정

아래는 측정하지 못해 가정으로 둔다. 첫 큰 개발에서 확인한다.

- **끝난 서브 세션의 재개:** 하네스의 Agent 도구 설명은 SendMessage로 앞서 실행한 에이전트를 맥락을 유지한 채 이어 쓸 수 있다고 적는다. 끝난 지 오래된 서브 세션이 실제로 재개되는지는 실측하지 않았고, 재개가 실패하면 재디스패치로 넘어간다.
- **서브 세션의 SendMessage:** 서브 세션이 구현 워커를 이어 쓰려면 서브에이전트 맥락에서도 SendMessage가 제공되어야 한다. 제공되지 않으면 워커 층의 이어 쓰기는 SDD의 기본 동작에 맡긴다.
- **워커의 작업 디렉터리:** `isolation:'worktree'`를 쓰지 않으므로 서브 세션과 워커의 작업 디렉터리는 워크트리가 아닐 수 있다. 디스패치 템플릿이 워크트리 절대 경로를 넣고 모든 명령을 그 경로에서 실행하게 하며, 서브 세션도 워커 디스패치마다 같은 경로를 넣는다. 실제로 그 경로에서 실행되는지는 첫 큰 개발에서 확인한다.
- **클린룸 조건의 오염:** 클린룸 서브에이전트에도 하네스가 스킬 목록을 실으므로, 시험은 옛 `nested-orchestration` description이 실린 상태에서 실행된다. 전역 CLAUDE.md의 원칙이 서브에이전트에 실리지 않는다는 전제는 시험 전에 서브에이전트에게 물어 확인한다.
- **실행 중 메시지 수신:** 실행 중인 서브 세션에 보낸 메시지가 도착하는지 확인하지 않았으므로, 끝나거나 멈춘 뒤에 보낸다.
- **토큰 집계 범위:** 완료 통지의 `subagent_tokens`에 워커 토큰이 포함되는지 확인하지 않았다.
- **대기 중 캐시:** 이 하네스의 ScheduleWakeup 도구 설명은 프롬프트 캐시 유지 시간을 1시간으로 적는다. 사용자 답을 그보다 오래 기다린 서브 세션은 이어 써도 캐시 이득이 없을 것으로 본다.
- **클린룸 시험의 대표성:** 시험은 단발 요청으로 실행하지만 실제 분해 판단은 brainstorming 대화 여러 턴 뒤에 나오므로, 시험 결과가 실제 발동과 다를 수 있다.

## 2026-10-10 개정

2026-10-10에 사용자가 이 설계의 판단 기준을 다시 보게 했다. 이 개정은 위 「결정」의 「트리거」, 「층별 책임」의 나눌지 판단, 「하부 명세 승인」, 「결정 기록」, 「공용 파일」, 「이어 쓰기가 맡는 상황」, 「멈추는 기준」, 「측정」, 「계약 코드와 큰 명세」, 「서로 무관한 일」과 「바뀌는 파일」·「확인 방법」을 고친다. 「묶는 단위」, 「요청 트리거」, 「범위 밖 결정」, 「공유 가정 전파」, 「판정 기록 확인」은 새로 둔다. 위 절의 문장은 2026-10-09 결정의 기록으로 남기며, 이 설계를 읽고 구현하는 세션은 두 절이 다르면 이 절을 따른다.

**바꾼 이유.** 첫째 이유는 기준의 중복이다. 2026-10-09 `SUB-ORCHESTRATE` 문안의 "독립된 하위 시스템 여럿, plan을 따로 둘 만큼"은 superpowers brainstorming 6.4.1의 분해 기준(202~203행 "spec 하나에 담기에 너무 큰가")과 같은 판단이었다. 그래서 현재 세션은 같은 판단을 두 번 했다. 두 판단이 다르게 나올 때 따를 쪽도 정해져 있지 않았다.

둘째 이유는 superpowers v7.0.0이다. v7.0.0은 brainstorming을 새로 썼다(원본 저장소 obra/superpowers 커밋 bb92a77, 2026-10-10). v7의 분해 기준은 "정말 독립된 프로젝트 여럿이면 순서를 합의하고 하나씩 브레인스토밍하라"(142~143행) 하나이고, v7은 설계 문서가 승인되면 "writing-plans를 실행하고 다른 스킬은 실행하지 마라"(191~192행)고 적는다. 사용자와 현재 세션은 하위 시스템이 여럿인 큰 개발 하나가 v7에서 분해되지 않아, superpowers의 분해 판단에만 기대면 트리거되지 않을 것으로 추정했다(측정하지 않은 추정이다). 참고로 6.4.1의 분해 기준은 2026-03-06(커밋 d48b14e)에, Spike·Bounded·Architectural 세 경로 분류는 v6.3.0(2026-08-12)에 들어왔다.

셋째 이유는 선행연구다. 사용자가 직접 요청한 `lens-prior-art` 대조가 모호한 기준을 드러냈고, 그 기록은 `docs/superpowers/reviews/2026-10-10-sub-orchestrate-criteria-prior-art.md`에 있다. 2차 리뷰 뒤 사용자는 분해 단위의 기준과 재현성만 따로 대조하게 했고, 그 기록은 `docs/superpowers/reviews/2026-10-10-decomposition-criteria-prior-art.md`에 있다. 뒤 기록은 앞 기록을 대체하지 않고 「묶는 단위」의 범위만 다룬다.

**판단 시점.** 현재 세션은 brainstorming을 따르다가 요청을 하위 프로젝트로 분해하기로 했을 때와, 설계 문서가 승인되어 writing-plans를 실행하기 전에 서브 세션에 맡길지 판단한다. 두 시점은 6.4.1과 v7에 모두 있다. 하위 프로젝트로 분해하지 않은 큰 개발은 둘째 시점에 현재 세션이 설계 문서에서 하위 프로젝트 목록을 만든다.

설계 문서가 승인된 뒤에 맡기기로 했으면 현재 세션은 설계 문서가 커밋된 끝에서 `dev/<개발 이름>`을 만든다. 현재 세션은 설계 문서에 스킬 「큰 명세」의 항목(워크스트림 목록, 계약, 의존 순서, 허용 경로, 소유 표, 공통 제약과 통합 확인 방법, 결정 기록)을 보강해 큰 명세로 삼은 뒤 다시 승인받는다.

**기준의 소유.** 맡기는 기준은 스킬 「맡기는 기준」이 소유한다. 현재 세션은 계약 코드를 고정한 뒤 동시에 시작할 수 있는 워크스트림이 둘 이상이고, 각 워크스트림이 plan을 따로 둘 만큼(태스크 다섯 이상으로 예상될 만큼) 크면 서브 세션에 맡긴다. 태스크 다섯은 2026-09-24 합의값이고 원칙에서 스킬로 옮겼다.

현재 세션은 근거에 하위 프로젝트 목록, 설계 의존 표와 의존 순서, 워크스트림별 예상 태스크 목록을 적어 한 번에 승인받는다. 하위 프로젝트 목록은 규칙으로 정하지 않고 이 승인으로 고정한다. 「재현성 측정」에서 superpowers 식 분해는 요청에 따라 실행마다 다른 목록을 냈고, 이름을 옮기는 규칙도 일부 요청에서 흔들렸기 때문이다.

**원칙 조항.** `SUB-ORCHESTRATE`는 기준 없이 판단 시점만 가리키는 연결 문장으로 바꾼다. `using-superpowers` 「User Instructions」는 사용자 지시(CLAUDE.md)가 스킬보다 우선한다고 정하고, 스킬끼리의 우선순위는 정하지 않는다. 그래서 superpowers의 차례 진행과 writing-plans 직행을 덮어쓰는 근거를 사용자 지시에 두려고 조항을 원칙에 남긴다. superpowers 파일은 갱신 때마다 덮어쓰이므로 고치지 않는다.

**묶는 단위.** 현재 세션은 하위 프로젝트×하위 프로젝트 표에 설계 의존(X를 설계하려면 Y의 실제 결과를 보아야 하는 관계)을 0과 1로 적는다. 주고받는 자료의 형식만 알면 되는 관계는 계약 코드로 고정하므로 0이다. 현재 세션은 설계 의존 순환에 함께 든 하위 프로젝트만 한 워크스트림으로 합치고, 남은 한 방향 의존은 큰 명세의 의존 순서에 적는다. 합친 결과는 순환 없는 그래프(DAG)이며, 선행 워크스트림이 없는 시작 워크스트림이 「맡기는 기준」의 동시에 시작할 수 있는 워크스트림이다.

두 워크스트림이 같은 파일을 고쳐야 하면 그 파일은 현재 세션이 맡는 공용 파일이 되고, 의존성 목록과 잠금 파일은 「잠금 파일」의 한 워크스트림 소유를 따른다. 스킬 「흐름」의 동시 진행 조건에서도 경로 겹침을 뺐다. 3차 리뷰가 첫 층 정의와 동시 진행 조건이 다르다고 지적했고, 같은 개정에서 '첫 층'을 3층 오케스트레이션의 '층'과 겹치지 않게 '시작 워크스트림'으로 바꿨다.

1차 리뷰 뒤의 문안은 한 방향 설계 의존과 경로 겹침도 합쳤다. 2차 리뷰와 선행연구 대조(`docs/superpowers/reviews/2026-10-10-decomposition-criteria-prior-art.md`)는 한 방향 사슬이 하나로 뭉친다고 지적했다. 같은 대조는 DSM 분할과 axiomatic design 이 순환만 합친다는 점과, 코드가 없는 단계에서는 경로 겹침을 셀 수 없다는 점도 지적했다. DSM(Design Structure Matrix)은 구성 요소 사이 의존을 행렬로 적어 순환 묶음과 순서를 찾는 설계 기법이고, axiomatic design 은 설계 변수 사이 결합을 행렬로 분석하는 설계 이론이다. 사용자는 「재현성 측정」 결과를 보고 순환만 합치는 규칙을 골랐다.

이 규칙은 "함께 바뀌는 코드를 묶는다"를 대체한다. 같은 채권 도구 요청을 첫 발동 시험의 세션들은 넷으로, 원칙 재시험의 세션은 셋으로 묶었다. 이 차이를 판정할 기준이 문장에 없었으므로 사용자는 측정할 수 있는 규칙을 요구했다.

**요청 트리거.** 사용자가 나눠 맡기라고 요구하면 현재 세션은 규모와 관계없이 스킬을 쓰고, 작은 일이면 조율 비용이 이득보다 클 수 있다고 알린다. 단위가 단일 태스크이면 현재 세션은 `dispatching-parallel-agents`를 쓴다. 사용자 요구는 원칙 없이도 지시이므로 원칙에는 넣지 않는다.

**서로 독립된 큰 작업.** 「서로 무관한 일」의 이름을 "서로 독립된 큰 작업"으로 통일한다. 큰 작업은 plan을 따로 둘 만큼(태스크 다섯 이상으로 예상될 만큼) 규모가 있는 작업이다. 2차 리뷰 뒤 사용자가 '일'보다 범위가 좁은 '작업'을 골랐다. 작업들이 같은 저장소에 있으면 현재 세션은 자료를 주고받지 않는 작업에도 결정 기록을 첫 디스패치 전에 채운다.

작업들이 다른 저장소에 있어도 현재 세션은 작업마다 서브 세션에 맡기고, 저장소마다 큰 명세와 통합 브랜치를 따로 둔다. 현재 세션은 그 저장소에 통합용 워크트리를 만들고 git 명령을 `git -C <통합용 워크트리 경로>`로 실행해, 사용자가 쓰는 그 저장소의 작업 트리를 바꾸지 않는다. 원칙 문구 재시험에서 "저장소마다 이 흐름을 따로 쓴다"는 앞 문안이 「라우팅」의 "나눌 일이 하나뿐이면 직접 진행"과 함께 읽혀, 세션 하나가 두 작업을 맡길지 묻지 않았다. 3차 리뷰 뒤 「라우팅」 넷째 불릿은 "위 불릿 어디에도 들지 않으면 직접 진행"으로 바꿨다.

**잠금 파일.** 의존성 목록과 잠금 파일은 큰 명세 소유 표에 적은 한 워크스트림만 고치고, 그 워크스트림이 끝난 뒤에는 현재 세션이 고친다. 다른 워크스트림은 기존 의존성으로 일하고, 추가가 필요하면 추가할 패키지를 적어 `BLOCKED`로 멈춘다.

소유 워크스트림이 끝났으면 현재 세션이 통합 브랜치에서 추가한다. 소유 워크스트림이 진행 중이면 현재 세션은 그 서브 세션이 멈추거나 끝날 때 요청을 보내므로, 멈춘 워크스트림은 그동안 기다린다. 단일 소유와 교집합 검사가 있으면 워크스트림 브랜치끼리 잠금 파일이 충돌하지 않으므로 충돌 해결 절차는 두지 않는다.

**하부 명세 승인 항목.** 현재 세션은 하부 명세가 계약 코드의 이름·형식·단위를 그대로 쓰는지, 수정 허용 경로 밖을 고치려 하지 않는지, 큰 명세 본문과 결정 기록에 충돌하지 않는지를 본다. 큰 명세 본문에는 두 번째 판단 시점에서 사용자가 승인한 설계 문서의 내부 방식도 들어 있다. 하부 명세나 리포트의 「스스로 판정한 모호함」에 범위 밖 결정이 들어 있으면 현재 세션은 승인하기 전에 사용자에게 묻는다.

**공유 가정 전파.** 하부 명세가 계약 코드에 없는 공유 가정을 새로 정했으면 현재 세션은 승인할 때 그 가정을 통합 브랜치의 결정 기록에 커밋한다. 현재 세션은 같은 가정을 쓸 다른 서브 세션이 멈추거나 끝나면 이어 쓰기로 알린다. 그 서브 세션이 이미 다른 가정으로 구현했으면 현재 세션은 계약 변경과 같이 사용자에게 기각, 다음 개발로 미룸, 지금 채택 중 하나를 고르게 한다. 리포트에 적힌 확정 결정을 병합 뒤 옮기는 2026-10-09 규칙은 그대로 둔다.

**범위 밖 결정.** 범위 밖 결정은 큰 명세와 결정 기록에 답이 없고 권한, 기능의 추가나 제외, 결과의 뜻, 돈과 되돌리기 어려운 자료, 보안 항목 중 하나에 드는 결정이다. 화면 배치·문구·정렬·표시 형식, 내부 이름·자료 구조·알고리즘, 큰 명세에 없는 기능을 만들지 않는 결정은 범위 안이다. 서브 세션은 이 항목에 분명히 드는 결정에서만 멈추고, 드는지 확실하지 않으면 스스로 판정해 리포트에 판정과 이유를 적는다.

이 결정은 2026-10-09 「멈추는 기준」의 "Rulings, not stalls" 판단을 유지한다. 2026-10-10 1차 리뷰 전 문안은 "확실하지 않으면 멈춘다"였으나, 사용자가 판정하고 기록하는 쪽을 골랐다.

**판정 기록 확인.** 현재 세션은 하부 명세 승인 때와 병합 전 검사에서 리포트의 「스스로 판정한 모호함」을 읽는다. plan 과 구현 단계의 판정은 하부 명세 승인 때 아직 없으므로 병합 전 검사에서 읽는다. 범위 밖 항목에 드는 판정이 있으면 현재 세션은 병합하기 전에 사용자에게 묻는다.

**측정.** 1차 리뷰 뒤 둔 `Self-Rulings:` 트레일러는 2차 리뷰에서 지웠다. 그 값으로 정하는 결정이 없고, 판정 내용은 리포트에 남아 현재 세션이 읽는다.

**근거.** 출처 URL 은 2026-10-10 세션에서 현재 세션이 응답(HTTP 200)을 확인했다. Specification Gap·CAID·Google 확장 연구의 수치와 ClarifyMT-Bench 등록일은 arXiv에서, CAID의 파일 묶기는 논문 본문에서, agent teams 문서 문장은 원문에서 대조했다.

**재현성 측정.** 사용자가 승인한 설계로 현재 세션은 하위 프로젝트 목록을 만드는 열거 단계와 그 목록을 묶는 단계를 나눠 측정했다. 요청은 채권 도구, 보고서 품질 개선, 인증 라이브러리 순차 이전, 상태 변경이 서로 오가는 주문 처리, 서로 독립된 두 일이다. 단계마다 조건 두 가지를 요청당 5회씩 서브에이전트로 실행해 모두 100회를 실행했다. 묶는 단계에는 고정한 목록을 주었다. 채점은 Python 으로 했고, 원소 4~5개를 무작위로 나눈 두 결과가 우연히 같을 확률(1/15~1/52)을 우연 기준선으로 두었다.

ARI(Adjusted Rand Index)는 두 분할이 같은 원소를 같은 묶음에 넣는 정도를 우연 수준으로 보정한 값이며, 1이 완전 일치이고 0이 우연 수준이다. 묶는 단계에서 순환만 합치는 조건은 모든 요청에서 5회가 같은 분할이었다(실행 쌍 ARI 평균 1.00). 한 방향 의존과 경로 겹침도 합치는 조건은 주문 처리와 서로 독립된 두 일에서 5회가 모두 같지는 않았고(가장 많이 나온 분할이 5회 중 4회와 2회, ARI 0.60과 0.43), 순차 이전에서는 5회 모두 하위 프로젝트 전부를 하나로 합쳤다. 순환만 합치는 조건도 의존 판정은 보고서 품질 개선, 순차 이전, 서로 독립된 두 일에서 5회 중 1회 달랐지만, 순환이 생기지 않아 분할은 바뀌지 않았다.

순환만 합치는 조건의 분할은 서로 독립된 두 일의 위키 역할 정의와 문서별 접근 제어를 합친 것 하나를 빼면 '무조건 분리' 기준선과 같았다. 주문 처리 요청에 심은 상태 변경 순환은 모든 실행이 자료 형식만 알면 되는 관계로 보고 설계 의존으로 세지 않았다.

**검증하지 않은 가정.** 설계 승인 뒤에 발동한 세션은 연결 문장 조건의 v7 채권 세션 하나였다. 원칙 없음 조건의 세션은 모두 설계 문서 전에 발동했으므로, 조항 없이 v7 HARD-GATE를 넘는지는 확인하지 못했다. 다음 큰 개발에서 원칙 없이 설계 승인 뒤 시점을 넘는 것이 확인되면 현재 세션은 조항 삭제를 사용자에게 제안한다. 현장에서 큰 개발이 하위 프로젝트를 차례로 진행하면 현재 세션은 훅 추가를 사용자에게 제안한다.

## 2026-10-11 개정 — 계약 표

2026-10-11에 사용자가 NP-bond-agg 큰 개발 세션을 근거로 이 스킬에서 정형화할 항목을 검토하게 했다. 이 개정은 스킬의 「큰 명세」 항목 목록의 계약 줄, 「계약 코드」, 「공용 파일」, 「승인 항목」, 「가드레일」의 「시험 병합」, 「측정」을 고치고 「계약 표」 문단을 새로 둔다. 분할 기준(「묶는 단위」)과 검증 의존은 같은 날 다른 세션이 맡았으므로 이 절에서 다루지 않는다. 위 절과 이 절이 다르면, 이 설계를 읽고 구현하는 세션은 이 절을 따른다.

**적용 범위.** 이 개정은 개정 뒤에 쓰기 시작하는 큰 명세에 적용한다. 개정 시점에 NP-bond-agg 세션은 큰 명세 승인을 받고 계약 코드 plan 을 쓰고 있었으므로, 그 세션은 승인된 큰 명세와 계약 코드 plan 을 다시 쓰지 않는다.

**바꾼 이유.** NP-bond-agg 큰 명세는 3차·4차 리뷰를 거쳤고, 현재 세션은 두 차수의 adversarial·consistency 지적 47건을 칸 하나씩에 대응시켰다. 그 분류에서 30건이 이번에 둔 칸과 규칙에 대응했다. 가장 많은 16건은 제공자·소비자나 함수 입력이 정해지지 않은 자료였다. 소유자 지적 3건 중 3차 C10·C11 은 기존 「공용 파일」 규칙과 소유 표에 이미 해당하므로 30건에서 뺐다. 대응표는 `docs/superpowers/reviews/2026-10-11-contract-table-prior-art.md`에 있다.

**칸.** 사용자는 2026-10-11 선택 질문에서 근거가 있는 칸만 넣는 안을 골랐고, 현재 세션은 그 안에 따라 계약 표의 칸을 이름, 제공자 → 소비자, 형식, 단위, 의미(시간·결측 포함)로 정했다. 형식 칸에는 열거값과 결과 열을 포함한다. 옛 칸 '호출 방향'은 제공자와 소비자의 이름을 적지 않아 누가 자료를 내는지 표에서 드러나지 않았으므로, 현재 세션이 그 칸을 '제공자 → 소비자'로 바꿨다.

같은 질문에서 사용자는 다른 안을 고르지 않았다. 표준 필드를 전부 넣는 안은 버전·정확도·보안·변경 이력에 대응하는 리뷰 지적이 0~1건이었다. 칸을 그대로 두고 제공자 확인 규칙만 넣는 안은 16건에는 대응하지만 시간 의미·결측 의미·결과 열 지적을 놓쳤다.

**의미 칸.** 처음 문안은 시간·결측 의미만 두었다. 다른 세션(disciplined-coder-f0)의 리뷰에서 lens-consistency 와 lens-adversarial 이 규칙 상태의 뜻 같은 일반 의미를 적을 칸이 없다고 지적했다(`docs/superpowers/reviews/2026-10-11-nested-orchestration-large-dev-review.md`, 그 세션의 브랜치). 사용자는 칸을 의미로 넓히되 시간과 결측은 비우지 않게 정했다. 일반 의미를 「결정 기록」에 두면 같은 자료의 뜻이 두 곳에 나뉘기 때문이다.

2차 리뷰에서 lens-adversarial 은 넓은 의미 칸이 자유 서술이 된다고 지적했다. 그래서 현재 세션은 의미 칸에 서브 세션이 바꾸면 안 되는 뜻만 적게 했다. 여러 행이 같은 관례를 쓰면 의미 칸은 「결정 기록」의 관례 이름을 가리킨다. 그 관례는 큰 명세 리뷰 전에 「결정 기록」에 있어야 하고, 관례를 고치는 일은 계약 변경으로 다룬다. 관례 수정이 계약 변경 절차를 거치지 않고 계약 의미를 바꾸는 길을 닫기 위해서다.

**원본.** 이름과 형식은 계약 코드가 원본이고, 단위와 의미는 계약 표가 원본이다. 단위와 의미는 타입에 드러나지 않을 수 있기 때문이다. 그래서 현재 세션은 「승인 항목」도 계약 코드의 이름·형식과 계약 표의 단위·의미를 대조하게 고쳤다.

**제공자 행 확인.** 현재 세션은 큰 명세를 리뷰에 넘기기 전에 두 종류의 자료에 제공자 행이 있는지 확인한다. 각 워크스트림의 맡는 일에 필요한 자료와 통합 확인이 읽는 자료다. 1차 리뷰에서 lens-adversarial 은 이 자기 확인이 흔적을 남기지 않아 형식에 그쳐도 드러나지 않는다고 지적했다. 사용자는 자기 확인을 유지하고 독립 검증은 review-specs 의 렌즈에 맡기기로 했다.

사용자가 고르지 않은 안은 lens-consistency 에 대조 항목을 넣는 안과 N2 chart 를 산출물로 요구하는 안이다. N2 chart 는 구성 요소 사이 입출력을 표로 적어 빈 칸을 찾는 시스템공학 표다. 렌즈 대조 항목 안은 모든 프로젝트에 쓰는 렌즈에 이 스킬 전용 항목을 넣는다. N2 chart 안은 계약 표와 같은 자료를 두 번 적는다. 효과는 스킬 「측정」에 둔 계약 공백 지적 수로 다음 큰 개발에서 본다.

**계약 코드의 연결.** 계약 코드는 함수 계약마다 공개 함수의 모듈 경로와 시그니처를 정하고, 현재 세션은 계약 코드의 경로를 소유 표에 적는다. 그 모듈 파일은 제공 워크스트림의 서브 세션이 자기 허용 경로 안에 처음 만든다. 현재 세션이 빈 모듈 파일을 먼저 만들면 생략이 일어나지 않아 첫 시험 병합이 실패하기 때문이다. 계약 테스트는 통합 브랜치에 없는 워크스트림의 모듈을 그 워크스트림 id 를 사유에 적어 생략한다. 현재 세션은 시험 병합에서 생략 사유에 병합 대상 id 가 있으면 실패로 보고, 마지막 시험 병합에서는 생략이 없어야 통과로 본다. 모듈 경로를 계약과 다르게 둔 구현이 생략으로 통과하는 길을 닫기 위해서다.

2차 리뷰에서 lens-adversarial 은 소비자가 제공자보다 먼저 병합되면 소비자 모듈이 import 할 때 제공자 모듈이 없어 계약 테스트가 생략되지 않고 실패한다고 지적했다. NP-bond-agg plan(1004~1010행)은 대조 대상 모듈 자체가 없을 때만 생략하고 다른 모듈이 없으면 오류를 다시 던지기 때문이다. 그래서 현재 세션은 생략 조건을 넓혀, 대조 대상이 읽는 다른 워크스트림의 모듈이 없을 때도 그 워크스트림 id 를 사유에 적어 생략하게 했다. 처음에는 제공자를 소비자보다 먼저 병합하는 순서 규칙을 두었다. 그러나 다른 세션(disciplined-coder-f0)이 서로 자료를 제공하는 쌍에서 그 순서를 만족할 수 없다고 지적했으므로, 현재 세션은 순서 규칙을 기각했다. 제공자 구현이 있어야 끝나는 확인은 그 세션이 정한 검증 의존이 맡는다. 테스트 대역(test double)은 실제 구현 대신 테스트에 쓰는 구현이다. 현재 세션은 계약 코드 plan 을 쓸 때 필요한 테스트 대역을 정해 계약 코드에 두고, plan 리뷰에서 테스트 대역이 계약 표의 단위·의미를 따르는지 대조한다. 소비자 서브 세션은 다른 워크스트림 함수의 테스트 대역을 따로 만들지 않고, 필요하면 `BLOCKED`로 요청한다. 파일 계약은 현재 세션이 통합 확인에서 열 이름과 형식을 대조하고, 단위와 의미는 하부 명세 승인 때 계약 표와 대조한다. CLI·HTTP 계약은 이번 근거에 사례가 없어 다루지 않았다.

이 연결 방식은 NP-bond-agg 계약 코드 plan(`dev/npb`의 `docs/superpowers/plans/2026-10-11-npb-contracts.md`)이 쓴 방식이다. 그 plan 은 `check_api`로 시그니처를 대조하고(1123행), 통합 브랜치에 없는 모듈의 검사를 생략하며(1009행), 테스트 대역을 계약 코드 경로의 `stubs.py`에 둔다(58행). 처음 문안은 호출되면 예외를 던지는 스텁을 워크스트림 경로에 두게 했고, 1차 리뷰에서 렌즈들이 그 문안의 문제를 지적했으므로 현재 세션은 그 문안을 기각했다.

- 첫 시험 병합의 실패: 처음 시험 병합되는 워크스트림의 계약 테스트가 다른 워크스트림의 스텁 때문에 실패한다(lens-consistency, lens-adversarial)
- 소비자 테스트 불가: 예외 스텁은 소비자의 단위 테스트에 쓸 수 없다(lens-adversarial)
- import 와 실행의 차이: import 만으로는 스텁이 실행되지 않는다(lens-grounding, lens-fit)

**공용 설정.** 공용 파일 중 설정 파일에는 사용자 지정값과 공유값만 둔다. 한 워크스트림만 읽는 파라미터는 그 워크스트림의 설정 파일에 두고, 그 워크스트림이 자기 허용 경로 안의 코드로 읽는다. 1차 리뷰에서 lens-adversarial 은 공용 로더가 워크스트림 설정을 읽으면 `BLOCKED`가 그대로 생긴다고 지적했고, 현재 세션은 읽는 주체를 워크스트림으로 정했다.

**선행 근거.** 현재 세션은 칸을 NASA 소프트웨어 공학 핸드북과 데이터 계약 표준 ODCS 의 필드에서 골랐다. NASA 핸드북의 인터페이스 설계 기술 항목은 출처와 수신자, 자료형, 단위, 범위와 열거값, 시점·빈도·순서를 적게 한다. ODCS 는 필드마다 필수 여부를 두며, 이 스킬은 필수 여부를 결측 의미의 일부로 다룬다. 두 출처는 사람 조직의 시스템과 데이터 플랫폼을 대상으로 하므로, 현재 세션은 필드 집합만 가져왔다.

제공자 행 확인은 N2 chart 에 대응한다. 연결 규칙은 Contract-Coding(2026, 프리프린트)의 보고에 대응한다. Contract-Coding 은 LLM 다중 에이전트 코드 생성 연구이며, 비교 대상 도구의 실패로 빈 뼈대 파일, 호출되지 않는 구현, import 경로 불일치를 보고했다. 출처별 필드 목록과 인용 URL 은 선행연구 대조 기록의 렌즈 원본(`docs/superpowers/reviews/2026-10-11-contract-table-prior-art/`)에 있다.

**미룬 것.** 서브 세션 상태 값(`BLOCKED`의 사유 구분, 실패·거절·취소)과 1층·2층 메시지 형식, 리포트 스키마는 선행연구 근거만 있다. NP-bond-agg 에서 서브 세션이 아직 실행되지 않았으므로, 사용자는 그 단계를 관찰한 뒤 정하기로 했다. 병행 변경(Parallel Change)은 옛 계약과 새 계약을 함께 두는 기법이며, 현재 세션은 이 기법을 비교되지 않은 기준선으로 기록만 했다.

**검증하지 않은 가정.** 칸이 있으면 큰 명세 작성 때 공백이 드러나리라는 효과는 측정하지 않았다. 47건 대응은 현재 세션의 분류이고, 재분류하면 30건이 달라질 수 있다. 계약 필드를 늘린 효과를 필드 단위로 측정한 연구도 렌즈가 찾지 못했다. 그래서 현재 세션은 스킬 「측정」에 큰 명세 리뷰의 계약 공백 지적 수를 세어 이번 30건과 비교해 보고하는 문장을 두었다.

## 2026-10-11 개정 — 묶는 단위

2026-10-11에 사용자가 분할 기준을 다시 보게 했다. 구현하는 세션은 스킬의 「묶는 단위」와 그 근거 문단, 「맡기는 기준」의 승인 근거, 「큰 명세」 항목 목록의 의존 순서 줄과 통합 확인 줄, 「결정 기록」, 「흐름」의 통합·마무리 단계와 의존 순서 문단, 「가드레일」(「시험 병합」 앞에 새 문단), 설계 문서를 가리키는 포인터 문장을 고친다. 위 절의 문장은 기록으로 남는다. 이 설계를 읽고 구현하는 세션은 위 절과 이 절이 다르면 이 절을 따른다.

**바꾼 이유.** NP-bond-agg 세션(2026-10-11, 기록 `~/.claude/projects/D--projects-Quant-NP-bond-agg/38538d4d-1094-4aed-86b5-6886010ad780.jsonl`)은 설계 의존 표를 모두 0으로 적고 다섯 워크스트림으로 나눴다(기록 943행). 큰 명세 3차 리뷰에서 `lens-adversarial`은 `rules`와 `runner`를 나눈 데서 명세 공백이 가장 크게 생긴다고 지적했다(1186행). 같은 리뷰에서 `lens-consistency`는 규칙 입력의 내용과 호출 방향이 정해지지 않았다고 지적했다(1158행).

그 세션은 다섯을 유지하려면 현재 세션이 규칙 내부 상태(정지·배율·진입)를 미리 정해야 한다고 적었다(1204행). 사용자는 두 하위 프로젝트를 합쳐 넷으로 나누는 안을 골랐다(1205행). 그 세션은 큰 명세를 다시 썼고(1208행), 사용자는 절마다 다시 승인했다(1360~1386행).

현재 세션은 현행 규칙대로 형식만 알면 되는 관계를 0으로 적는다. 그래서 현재 세션은 형식은 적을 수 있어도 의미가 한 하위 프로젝트의 내부 설계인 공유 항목을 판별하지 못한다. 2026-10-10 「재현성 측정」에서 주문 처리 요청에 심은 상태 변경 순환을 어느 실행도 설계 의존으로 세지 않은 원인도 같다.

**공유 항목 표.** 현재 세션은 사용자가 승인한 하위 프로젝트 목록을 받은 뒤, 설계 의존 표보다 먼저 공유 항목 표를 만든다. 행은 둘 이상의 하위 프로젝트가 주고받는 자료·상태·정의다. 명명 관례 같은 관례와 용어 풀이는 행으로 두지 않고, 현재 세션이 큰 명세의 「결정 기록」에 적는다.

표의 칸은 항목, 소유 하위 프로젝트, 사용 하위 프로젝트, 판정, 고정한 의미다. 소유 하위 프로젝트는 그 항목의 의미를 바꾸는 결정을 내리는 하위 프로젝트다. 사용 하위 프로젝트는 소유 하위 프로젝트를 뺀, 그 항목을 받는 하위 프로젝트다.

**판정.** 현재 세션은 모든 행에 "어느 하위 프로젝트의 내부 설계도 정하지 않고 이 항목의 이름·형식·단위·의미(시간 의미와 결측 의미 포함)를 지금 고정할 수 있는가"를 묻는다. 고정할 수 있으면 판정은 떼어냄이고, 현재 세션은 고정한 의미를 그 행에 한 줄로 적는다. 고정할 수 없으면 현재 세션은 사용 하위 프로젝트마다 "그 하위 프로젝트의 설계가 이 항목의 의미를 함께 정해야 하는가"를 묻는다. 소유 하위 프로젝트가 둘 이상이면 판정은 합침이다. 소유가 하나이면 함께 정해야 하는 사용 하위 프로젝트가 있을 때 판정은 합침이고, 없을 때 판정은 순서다.

소유 하위 프로젝트가 없는데 고정할 수 없으면, 현재 세션은 그 항목을 바꾸는 하위 프로젝트를 모두 소유 하위 프로젝트로 적고 판정한다. 합침 행에서 현재 세션은 소유 하위 프로젝트를 모두 합치고, 의미를 함께 정해야 하는 사용 하위 프로젝트도 같은 워크스트림으로 합친다. 합침·순서 행에서 의미를 받기만 하는 사용 하위 프로젝트는 합치지 않으며, 현재 세션은 소유 쪽 접근 절차를 계약으로 떼어내고 설계 의존 표에 사용 쪽→소유 쪽 1을 적는다. 그 계약의 의미 칸은 소유 워크스트림이 통합 브랜치에 들어갈 때 현재 세션이 확정한다.

합침 행끼리 하위 프로젝트가 겹치면 현재 세션은 겹친 행의 하위 프로젝트를 모두 한 워크스트림으로 묶는다. 그다음 현재 세션은 합친 묶음과 남은 하위 프로젝트로 설계 의존 표를 만들고 순환을 합친다.

**NP-bond-agg 에 적용한 판정.** 규칙 상태의 소유 하위 프로젝트는 `rules`다. `runner`가 받는 값은 정지·배율·진입 상태이고, 그 의미를 고정하려면 `rules`의 내부 설계를 정해야 한다. `runner`의 일별 루프가 정하는 적용 순서도 상태의 뜻을 함께 정하므로, 현재 세션은 `rules`와 `runner`를 합친다. 거래일 달력은 현재 세션이 지금 의미를 고정할 수 있으므로 떼어낸다.

**승인 근거.** 현재 세션은 맡기는 승인을 받을 때 근거에 공유 항목 표를 설계 의존 표와 함께 넣는다. 사용자는 떼어냄 행의 고정한 의미를 읽고, 현재 세션이 내부 설계를 미리 정했는지 승인 전에 확인한다. 순환 누락을 사용자가 설계 의존 표로 확인하는 기존 방법을 공유 항목에도 적용한 규칙이다.

**계약 표와의 연결.** 공유 항목 표는 스킬 「계약 표」의 첫 버전이다. 현재 세션은 큰 명세 단계에서 떼어냄 행을 계약 표의 행으로 옮기고, 하위 프로젝트 이름을 워크스트림 id로 바꾼다. 소유 하위 프로젝트는 제공자가 되고 사용 하위 프로젝트는 소비자가 되며, 소유가 없는 행의 제공자는 현재 세션이다. 합침 행은 워크스트림 내부로 넘어가 표에서 빠진다. 합침·순서 행에서 떼어낸 접근 절차 계약은 계약 표의 행이 되고, 그 제공자는 소유 쪽 워크스트림이다.

이 연결 규칙은 스킬 「묶는 단위」가 소유하고 「계약 표」 절에는 다시 적지 않는다. 경계를 넘는 자료의 의미는 계약 표의 '의미(시간·결측 포함)' 칸이 원본이다. 처음에 현재 세션은 의미를 새 「공유 정의」 줄에 두는 안을 냈다. `disciplined-coder-4c` 세션은 그 안이 같은 항목을 두 곳에 적게 한다고 메시지로 검토했다.

1차 리뷰에서 `lens-consistency`는 「공유 정의」 줄이 「결정 기록」의 명명 관례와 겹친다고 지적했다. 사용자는 새 줄을 두지 않기로 했다. 그래서 구현하는 세션은 스킬 「결정 기록」 문단에 경계를 넘지 않는 관례와 용어 풀이를 적는다는 문장을 추가한다.

**검증 의존.** X의 설계와 단위 테스트는 계약 코드와 테스트 대역(test double)으로 진행할 수 있다. 그런데 X의 통합 확인에 Y의 실제 구현이 필요하면 X는 Y에 검증 의존한다. 통합 확인은 현재 세션이 큰 명세에 워크스트림마다 적는 확인 방법이다. 그래서 구현하는 세션은 스킬 「큰 명세」의 '공통 제약과 통합 확인 방법' 줄을 공통 제약과 워크스트림별 통합 확인 방법으로 고친다.

현재 세션은 큰 명세에 통합 확인 방법을 적을 때 검증 의존을 판정한다. 공유 항목 표와 설계 의존 표를 만드는 묶는 단계에서는 판정하지 않는다. 검증 의존은 시작을 늦추지 않으므로 시작 워크스트림 판정을 바꾸지 않는다.

큰 명세의 의존 순서 항목은 시작 의존과 검증 의존을 나눠 적는다. 시작 의존은 다른 워크스트림의 산출물이 있어야 시작할 수 있는 관계다. 구현하는 세션은 스킬에서 시작 시점을 뜻하는 '의존 순서'를 '시작 의존'으로 바꾼다. 시작 워크스트림 판정은 시작 의존만 본다.

NP-bond-agg 큰 명세는 `rules`·`runner`를 합친 워크스트림을 `inputs`·`market`·`stats`와 동시에 시작하도록 계획했다. 실제 자료로 끝까지 실행하는 확인은 `inputs`·`market`·`stats`가 통합 브랜치에 들어간 뒤에 하도록 계획했다. 현재 세션은 이 계획의 실행을 아직 관찰하지 못했다.

**검증 의존의 병합 순서.** 스킬의 시험 병합은 이미 모든 워크스트림에 통합 확인을 실행한다. 그래서 바뀌는 것은 병합 시점이다. 현재 세션은 검증 의존이 있는 워크스트림의 시험 병합을 그 대상이 모두 통합 브랜치에 들어올 때까지 미룬다. 그 결과 통합 브랜치에 들어간 워크스트림은 모두 통합 확인을 통과한 상태다. 스킬 「진행 위치」는 대기 중인 워크스트림을 진행 중으로 보이므로, 현재 세션은 큰 명세의 검증 의존과 통합 브랜치의 `Workstream:` 줄을 대조해 대기 여부를 판정한다.

현재 세션은 큰 명세를 승인받기 전에 시작 의존과 검증 의존을 합친 그래프에 순환이 있는지 본다. 스킬 「계약 코드」는 계약 테스트가 아직 없는 워크스트림 모듈을 생략하게 하므로 병합 순서를 정하지 않고, 제공자 구현이 있어야 끝나는 확인은 검증 의존이 맡는다. 순환이 있으면 어느 워크스트림도 병합 순서를 정할 수 없다. 그래서 현재 세션은 디스패치 전에 순환에 든 워크스트림을 합칠지 사용자에게 묻는다. 관찰된 사례가 없으므로 함께 시험 병합하는 절차는 두지 않는다.

통합 확인이 실패하면 현재 세션은 시험 병합을 버리고 원인 쪽 서브 세션에 실패 출력을 이어 쓰기로 보낸다. 원인이 이미 병합된 대상 Y에 있으면, 현재 세션은 Y의 수정을 같은 `Workstream:` 트레일러를 넣은 시험 병합으로 넣는다. 이어서 현재 세션은 Y에 검증 의존하는 워크스트림 전부의 통합 확인을 다시 실행한다. 이미 병합된 워크스트림도 그 대상에 든다.

마무리 단계는 모든 워크스트림이 이 검사를 거쳐 병합된 뒤에 시작한다.

**서브 세션 직접 확인 안.** 현재 세션은 서브 세션이 통합 브랜치를 자기 브랜치에 병합해 직접 통합 확인을 하는 안을 기각했다. 이 안에서는 그동안 서브 세션이 기다려야 하고, 판정 위치가 서브 세션과 현재 세션 두 곳이 된다. NP-bond-agg 세션은 큰 명세(dev/npb 브랜치의 `docs/superpowers/specs/2026-10-11-npb-backtest-design.md`)에서 이 안을 채택했다. 현재 세션은 그 계획의 실행 결과를 아직 관찰하지 못했다.

**트레일러 기록 안.** 현재 세션은 검증 의존 워크스트림을 먼저 병합하고 나중에 `Verified:` 트레일러를 남기는 안도 기각했다. 이 안에서는 트레일러가 하나 늘어난다. 또 검증되지 않은 워크스트림이 통합 브랜치에 있는 동안 생긴 실패를 처리하는 순서를 따로 정해야 한다.

**근거 수정.** 스킬 「묶는 단위」 근거 문단과 위 「2026-10-10 개정」 204행은 DSM 을 "구성 요소 사이 의존을 행렬로 적어 순환 묶음과 순서를 찾는 설계 기법"으로 풀이하고 'DSM 분할'을 근거로 들었다. Wikipedia 「Design structure matrix」는 "Static DSMs are usually analyzed with clustering algorithms"라고 적는다. 같은 문서는 partitioning·tearing·sequencing 을 time-based DSM 의 분석 기법으로 적는다. 그래서 그 풀이는 static DSM 을 가리키면서 time-based DSM 의 기법을 붙인 상태다.

설계 의존 표는 "X를 설계하려면 Y의 실제 결과를 보아야 하는" 설계 활동 사이 선후 관계를 적는다. 현재 세션은 그 표로 의존 순서와 시작 워크스트림을 정하므로, 그 표는 time-based DSM 이다. 그래서 순환을 한 묶음으로 찾고 나머지를 순서로 두는 근거는 partitioning 이다. 공유 항목 표는 하위 프로젝트 사이의 결합을 적으므로, 강하게 결합된 요소를 한 군집으로 묶는 clustering 이 근거다.

`disciplined-coder-4c` 세션의 선행연구 렌즈는 묶는 일 전체를 static DSM 으로 보고 partitioning 인용을 틀린 전제로 판정했다(`2026-10-11-contract-table-prior-art.md`). 이 개정 절의 1차 리뷰에서 `lens-grounding`은 설계 의존 표의 칸이 활동 선후 관계라고 지적했다. 그래서 현재 세션은 그 전제 반박을 공유 항목 표에만 적용한다. 사용자는 표마다 근거를 나누는 안을 골랐다.

**Parnas 근거.** Parnas(1972)의 권고 1번은 "A data structure, its internal linkings, accessing procedures and modifying procedures are part of a single module. They are not shared by many modules as is conventionally done."이다. 현재 세션은 이 문장을 원문 PDF 텍스트에서 확인했다. 이 권고는 자료 구조와 그 접근·수정 절차를 한 모듈에 두고, 다른 모듈이 그 구조를 공유하지 않게 한다.

그래서 의미를 함께 정하는 하위 프로젝트와 그 항목을 함께 바꾸는 소유 하위 프로젝트는 같은 구조를 정의하는 셈이므로, 현재 세션은 이 쪽만 합친다. 의미를 받기만 하는 하위 프로젝트는 접근 절차로 구조를 쓰므로 현재 세션은 순서로 둔다.

**그 밖의 근거.** 현재 세션은 한 방향 설계 의존을 합치지 않고 순서로 둔다. 검증 의존의 근거는 RUP 「Plan System Integration」의 "For each build, define which subsystems should go into it, and which other subsystems must be available as stubs."와 평가 질문 "Is the integration order coordinated with the order in which components are developed?"이다. 2026-10-10 대조(`docs/superpowers/reviews/2026-10-10-decomposition-criteria-prior-art.md`)의 `lens-prior-art`는 LLM 에 같은 개발 요청을 여러 번 분해시켜 일치도를 측정한 선행 사례를 찾지 못했다. 현재 세션은 스킬 근거 문단의 axiomatic design 문장을 대조하지 않았으므로 그대로 둔다.

**다른 세션과의 경계.** 같은 날 `disciplined-coder-4c` 세션이 스킬 「큰 명세」 항목 목록의 계약 줄, 새 「계약 표」 절, 「계약 코드」, 「공용 파일」, 「승인 항목」, 「시험 병합」을 고친다. 구현하는 세션은 그 절들을 고치지 않는다. 「큰 명세」 항목 목록에서 구현하는 세션이 고치는 줄은 의존 순서 줄과 통합 확인 줄이고, 「큰 명세」 끝에는 「검증 의존」 문단을 새로 둔다. 두 세션은 결정마다 서로 검토했다.

`disciplined-coder-4c` 세션이 먼저 main 에 병합한다. 구현하는 세션은 그 병합 위에서 스킬을 고친다.

**측정 입력.** 현재 세션은 묶는 단계만 측정한다. 요청은 채권 도구, 보고서 품질 개선, 인증 라이브러리 순차 이전, 주문 처리, 서로 독립된 두 작업, NP-bond-agg 다. 현재 세션은 NP-bond-agg 입력으로 기록 943행의 하위 프로젝트 목록과 그 시점의 설명만 준다. 넷으로 합친 뒤에 쓴 큰 명세의 내용은 주지 않는다.

2026-10-10 측정의 고정 목록은 저장소에 남지 않았다. 그래서 현재 세션은 별도 서브에이전트에 「재현성 측정」의 요청 문장만 주고 목록을 다시 만들게 한다. 현재 세션은 이 목록이 같은 입력이 아님을 결과에 밝힌다.

**기대 분할.** 현재 세션은 측정 전에 요청마다 기대 분할을 정한다. 규칙 문안을 받지 않은 별도 서브에이전트가 요청 문장과 목록을 보고, 하위 프로젝트 사이에 내부 의미를 주고받는 쌍과 기대 분할을 적는다. 현재 세션은 그 쌍과 이유를 행마다 사용자에게 보이고 승인을 받는다. NP-bond-agg 의 기대 분할은 사용자가 고른 넷이다.

현재 세션은 다시 만든 목록, 기대 분할, 사용자 승인, 실행 출력, 채점 스크립트를 `docs/superpowers/reviews/2026-10-11-shared-definition-grouping-check/`에 남긴다. 조건은 현행 규칙과 새 규칙이다. 현재 세션은 요청마다 조건별로 서브에이전트를 5회씩 실행한다.

**채택 기준.** 구현하는 세션은 측정 결과를 아래 기준으로 판정한다. 기준을 만족하지 않으면 구현하는 세션은 결과를 사용자에게 보이고 문안을 고칠지 묻는다.

1. 새 규칙을 받은 서브에이전트가 여섯 요청 각각에서 기대 분할 전체를 5회 중 4회 이상 낸다.
2. 현행 규칙을 받은 서브에이전트의 결과는 비교로만 보고하고 판정에 쓰지 않는다.

실행마다 성공 확률이 독립이라고 가정하면, 이 기준은 성공률 0.6인 규칙도 한 요청에서 약 34% 확률로 통과시킨다. 성공률 0.9인 규칙은 한 요청에서 약 8% 확률로 탈락한다. 구현하는 세션은 이 판정 오차를 결과 보고에 적는다. 검증 의존은 묶는 단계 밖에서 판정하므로 이 측정에 넣지 않고, 현재 세션이 다음 큰 개발에서 관찰한다.

**바뀌는 파일.** 구현하는 세션은 `skills/nested-orchestration/SKILL.md`, 이 설계 문서, 측정 폴더를 고친다. SKILL.md 에서 고치는 곳은 첫 문단에 적은 절이다. 원칙 조항은 고치지 않는다.

**확인 방법.** 구현한 세션은 아래 기준으로 판정한다.

1. 측정 결과가 「채택 기준」을 만족한다.
2. `grep -n '공유 항목 표' skills/nested-orchestration/SKILL.md`가 「묶는 단위」와 「맡기는 기준」의 줄을 출력한다.
3. `grep -n -E 'partitioning|clustering' skills/nested-orchestration/SKILL.md`가 「묶는 단위」 근거 문단의 줄을 출력하고, `grep -c 'DSM 분할' skills/nested-orchestration/SKILL.md`가 0을 출력한다.
4. `grep -n '검증 의존' skills/nested-orchestration/SKILL.md`가 「큰 명세」 항목 목록, 「흐름」, 「가드레일」의 줄을 출력한다.
5. `grep -n '시작 의존' skills/nested-orchestration/SKILL.md`가 「묶는 단위」, 「큰 명세」 항목 목록, 「흐름」의 줄을 출력한다.
6. `grep -n '용어 풀이' skills/nested-orchestration/SKILL.md`가 「결정 기록」의 줄을 출력한다.
7. `grep -n '2026-10-11 개정' skills/nested-orchestration/SKILL.md`가 설계 문서를 가리키는 포인터 줄을 출력한다.
8. CLAUDE.md 「변경 뒤 실행」의 검사가 ALL PASS 를 출력하고, `claude plugin validate ./`가 `Validation passed`를 출력한다.

**측정 결과.** 현재 세션은 「측정 입력」대로 실행하되, Agent 대신 저장소 밖 임시 폴더에서 도구를 끈 `claude -p`로 실행했다(`run_measure.py`). 첫 문안을 받은 실행은 기대 분할을 bond-tool 4회, report-quality 4회, auth-migration 0회, order-processing 5회, two-jobs 2회, npb 3회 냈고 판정은 NOT ADOPT 였다. 실행들은 소유 쪽이 정하고 사용 쪽은 받기만 하는 관계(인증 인터페이스, 검색 색인)를 "아직 정해지지 않아 고정할 수 없다"고 보고 합쳤다. 그래서 현재 세션은 사용자 승인을 받아 위 「판정」에 순서를 넣었다.

순서를 넣은 문안은 bond-tool 5회, report-quality 5회, auth-migration 4회, order-processing 5회, two-jobs 0회, npb 4회였다. two-jobs 의 5회는 모두 FAQ 색인과 검색을 합쳤고, 이유는 색인의 형태소 분석과 검색 질의 분석이 색인 의미를 함께 정해야 한다는 것이었다. 사용자는 결과를 본 뒤 two-jobs 의 기대 분할을 이 합침으로 정정하는 안을 골랐고, 정정한 정답으로 다시 채점한 판정은 ADOPT 였다(two-jobs 5회). 현행 규칙은 두 측정 모두 order-processing 0회, npb 0회였다.

다시 만든 목록은 2026-10-10 입력과 같지 않다. 처음 재생성한 목록은 요청 이름만으로는 나눌 근거가 없어, 현재 세션은 서브에이전트에 기능 범위를 정해 3~6개로 나누게 했다. 형식 오류로 다시 실행한 회차는 없다. 첫 측정의 `runs.log`는 61행인데, 첫 행은 본 실행 전에 `new__npb__1`을 한 번 돌린 시범 실행이고 그 출력은 본 실행이 덮어썼다. 최종 브랜치 리뷰가 소유가 둘 이상인 항목의 미합침과 받기만 하는 사용 쪽의 의존 값을 지적해, 현재 세션은 「판정」을 지금 문장으로 고쳤다. 고친 문안은 order-processing, npb, auth-migration 에서 5회 모두 기대 분할을 냈다(`-check-3/`). 기록은 `docs/superpowers/reviews/2026-10-11-shared-definition-grouping-check/`, `-check-2/`, `-check-3/`에 있다.

## 2026-10-11 개정 — 메시지 형식

2026-10-11에 사용자가 현재 세션과 서브 세션 사이에 오가는 메시지를 모두 정의하게 했다. 이 절에서 '현재 세션'과 '서브 세션'은 「용어」 표의 뜻으로만 쓰고, 이 개정을 쓴 세션은 '이 개정을 쓴 세션'으로 적는다. 이 설계를 구현하는 세션은 스킬에 「메시지 형식」 절을 새로 두고, 「반영 위치」의 절들을 그 절에 맞춘다. 위 절과 이 절이 다르면, 구현하는 세션은 이 절을 따른다.

분할 기준과 검증 의존은 다른 세션(disciplined-coder-f0)이 같은 날 고쳐 main 에 병합했다. 이 절이 그 개정과 맞닿는 곳은 둘이다. 하나는 「검증 의존 대기」가 쓰는 메시지 이름이고, 다른 하나는 「묶는 단위」가 의미를 나중에 확정하게 한 계약 행의 표기다.

**바꾼 이유.** 「2026-10-11 개정 — 계약 표」는 처음 내려보내는 큰 명세만 정형화했다. 그 뒤에 오가는 메시지는 `AWAITING_APPROVAL`, `BLOCKED`, `DONE`과 산문 리포트뿐이어서, `BLOCKED` 하나가 범위 밖 결정, 계약 변경, 의존성 추가, 리뷰 🔴 를 모두 덮었다. 그래서 현재 세션은 사유를 문장에서 읽어 구분했다.

선행연구 렌즈(`docs/superpowers/reviews/2026-10-11-contract-table-prior-art/lens-prior-art-2.json`)는 이 점을 두 선행 사례에 대조해 지적했다. MAST 는 LLM 다중 에이전트 실행 기록의 실패를 분류한 연구이고, 그중 한 범주가 에이전트 사이 불일치다. A2A 는 에이전트 사이 작업 위임 프로토콜이며 작업 상태 값을 표준으로 둔다. 처음에 사용자는 NP-bond-agg 서브 세션 단계를 관찰한 뒤 정하기로 했으나, 같은 날 지금 정의하기로 바꿨다. 그래서 이 형식은 관찰 사례 없이 정했다.

**표기.** 사용자는 머리줄과 필드 목록을 골랐다. 첫 줄은 `<종류>` 또는 `BLOCKED <사유 코드>`이고, 그 아래에 `필드: 값` 줄을 정해진 순서로 둔다. 값이 없는 필드는 `없음`으로 적어 빠뜨린 필드와 빈 필드를 구분한다.

사용자가 고르지 않은 안은 JSON 블록과 머리줄만 고정하는 안이다. JSON 은 읽는 스크립트가 없어 그 이점을 쓰지 않고 사람이 읽기 어렵다. 머리줄만 고정하는 안은 브랜치·커밋·리포트 경로 같은 필수 정보의 누락을 차단하지 못한다.

**상향 메시지.** 사용자는 `AWAITING_APPROVAL`, `BLOCKED`, `DONE`, `FAILED`, `CANCELED`와 `BLOCKED` 사유 코드를 골랐다. 사유마다 상태를 나누는 안은 사유가 늘 때마다 상태와 가드레일을 고쳐야 해서 고르지 않았다. 기존 상태 값에 사유 코드만 붙이는 안은 끝내지 못한 실패와 취소 확인을 나타낼 값이 없어 고르지 않았다.

서브 세션은 모든 상향 메시지에 `워크스트림`, `브랜치`(`ws/<개발>/<id> @ <커밋>`), `리포트`, `요약`을 공통 필드로 적는다. 판정 같은 상세는 리포트에만 적고 메시지 필드에 다시 적지 않는다. 테스트 결과는 시험 병합이 직접 실행해 판정하므로 리포트에도 적지 않는다. 같은 사실을 두 곳에 두면 서로 달라질 수 있다고 1차 리뷰의 lens-fit 과 lens-adversarial 이 지적했기 때문이다.

| 머리줄 | 추가 필드 | 보내는 때 |
|---|---|---|
| `AWAITING_APPROVAL` | `하부 명세`, `리뷰 기록`, `마커` | 하부 명세를 리뷰하고 커밋한 뒤 |
| `BLOCKED <사유 코드>` | `요청`, `이유`, `멈춘 작업` | 사유 코드 하나 이상에 해당할 때 |
| `DONE` | 없음 | 구현과 최종 리뷰를 마친 뒤 |
| `FAILED` | `원인`, `시도한 것`, `되돌릴 것` | 사유 코드 어디에도 들지 않는데 끝낼 수 없을 때 |
| `CANCELED` | `남긴 상태` | `CANCEL`을 받고 멈춘 뒤 |

서브 세션은 `FAILED`를 사유 코드 어디에도 들지 않을 때만 쓴다. 계약 불일치로 테스트가 실패하면 `BLOCKED contract-change`이고, 권한이나 도구 설치처럼 사람이 조치하면 풀리는 환경 문제는 `BLOCKED user-decision`이다. '끝낼 수 없다'의 기준은 superpowers `systematic-debugging`의 기준을 따른다. 같은 결함에 수정 시도가 세 번 실패하면 서브 세션은 고치기를 멈추고 `FAILED`를 돌려주며, `시도한 것`에 그 세 시도를 적는다.

한 번 멈출 때 사유가 둘 이상이면, 서브 세션은 머리줄에 아래 처리 표에서 먼저 나오는 사유 코드를 적고 나머지는 `요청` 필드에 줄마다 사유 코드와 함께 적는다. 현재 세션은 바로 처리할 수 있는 사유를 먼저 모두 답한다. 다른 워크스트림의 통합을 기다려야 하는 사유(`dependency-add`)는 그 통합 뒤에 `BASE-UPDATED`로 따로 알린다. 짧은 사유의 답이 긴 사유를 기다리지 않게 하기 위해서다.

이 개정을 쓴 세션은 A2A 의 작업 상태 중 입력 필요, 완료, 실패, 취소에 대응하는 값만 가져왔다. A2A 는 서로 다른 조직의 에이전트가 HTTP 로 작업을 주고받는 프로토콜이어서, 그 메시지 구조까지 가져올 필요는 없다고 이 개정을 쓴 세션이 판단했다. 이 성격 규정은 선행연구 렌즈의 네 축 대조에 있었으나 저장한 원본은 그 대목을 축약했다. A2A 의 거절(REJECTED)은 두지 않았다. 서브 세션이 맡을 수 없는 일은 큰 명세나 계약의 문제이고, 그 사유는 `BLOCKED user-decision`이나 `BLOCKED contract-change`로 나타나기 때문이다.

**BLOCKED 처리.** 이 개정을 쓴 세션은 사유 코드마다 현재 세션이 할 일을 정했다. 대부분은 기존 스킬에 흩어진 규칙을 사유별로 모은 것이다. 새 규칙은 `test-double-add`·`review-gap`의 처리, `sdd-stop`의 '전부 추측인 plan' 처리, `FAILED`·`CANCELED` 처리다.

`shared-file-change`는 공용 파일과 큰 명세 본문에 쓴다. 다만 의존성 목록·잠금 파일은 `dependency-add`에, 계약 코드의 테스트 대역은 `test-double-add`에 쓴다. 의존성 목록은 공용 파일이기도 해서, 이 구분이 없으면 서브 세션이 `dependency-add` 대신 `shared-file-change`를 골라 소유 규칙을 깰 수 있다.

| 사유 코드 | 현재 세션이 할 일 | 보낼 메시지 |
|---|---|---|
| `user-decision` | 사용자에게 하나씩 묻고 답을 「결정 기록」에 커밋한다 | 요청한 쪽에 `ANSWER` |
| `contract-change` | 사용자에게 기각·미룸·채택을 고르게 한다. 채택하면 큰 명세와 계약 코드를 고친다 | 채택이면 그 계약 행의 제공자와 소비자 모두에 `CONTRACT-CHANGED`, 기각·미룸이면 요청한 쪽에 `ANSWER` |
| `shared-file-change` | 공용 파일이면 통합 브랜치에서 고친다. 큰 명세 본문이면 사용자에게 기각·미룸·채택을 고르게 한다 | 공용 파일이면 요청한 쪽에 `BASE-UPDATED`, 큰 명세 채택이면 바뀐 절이 다루는 워크스트림 모두에 `CONTRACT-CHANGED`, 기각·미룸이면 요청한 쪽에 `ANSWER` |
| `dependency-add` | 소유 워크스트림이 통합 브랜치에 들어갔거나 `DONE`을 돌려줬으면 통합 브랜치에서 추가한다. 진행 중이면 소유 서브 세션이 멈출 때 추가를 요청한다 | 진행 중인 소유 쪽에 `DEPENDENCY-REQUEST`, 추가가 통합되면 요청한 쪽에 `BASE-UPDATED` |
| `test-double-add` | 계약 코드에 테스트 대역을 추가하고 계약 표의 단위·의미와 대조한다 | 요청한 쪽에 `BASE-UPDATED` |
| `review-red` | 🔴 를 사용자에게 알리고 답을 「결정 기록」에 적는다 | 요청한 쪽에 `ANSWER` |
| `review-gap` | 빠진 관점의 렌즈를 실행할지 사용자에게 묻는다 | 요청한 쪽에 `ANSWER` |
| `sdd-stop` | 비가역 작업, 보안 작업, 워크트리 밖 부작용이면 승인할지 사용자에게 묻는다. 전부 추측인 plan 이면 큰 명세나 「결정 기록」에 근거를 보강한다 | 요청한 쪽에 `ANSWER` |

`dependency-add`에서 소유 워크스트림이 `DONE`을 돌려줬으면 현재 세션은 그 병합을 기다리지 않고 통합 브랜치에서 바로 추가한다. 소유 워크스트림이 요청한 쪽에 검증 의존하면, 병합을 기다리는 동안 두 워크스트림이 서로를 기다리게 되기 때문이다.

`sdd-stop`에서 사용자가 작업을 거절해도 현재 세션은 `ANSWER`로 거절과 대안을 보낸다. 워크스트림을 접을지는 현재 세션이 사용자에게 따로 묻는다.

공유 가정이 서브 세션의 구현과 다르면 서브 세션은 `BLOCKED contract-change`를 돌려준다. 이때 현재 세션은 계약 행 대신 「결정 기록」의 그 가정을 대상으로 기각·미룸·채택을 고르게 하고, 채택하면 그 가정을 쓰는 서브 세션 모두에 `ASSUMPTION-ADDED`를 보낸다. 기존 「승인 항목」이 가정 충돌을 계약 변경과 같이 다루기 때문이다.

`FAILED`를 받으면 현재 세션은 원인과 되돌릴 것을 사용자에게 알리고, 같은 서브 세션에 `REVISE`, 새 서브 세션, `CANCEL` 중 하나를 고르게 한다. 새 서브 세션을 고르면 현재 세션은 디스패치 프롬프트에 그 리포트의 `원인`과 `시도한 것`을 넣는다. `CANCELED`를 받으면 현재 세션은 CLI 의 서브에이전트 화면에서 그 워크트리의 워커가 끝났는지 확인한 뒤, 브랜치와 워크트리를 남길지 지울지 사용자에게 묻는다. 사용자가 워크스트림을 접기로 하면 현재 세션은 큰 명세 「결정 기록」에 '접은 워크스트림: <워크스트림 id> — 이유' 한 줄을 커밋한다.

**하향 메시지.** 사용자는 상황마다 종류 하나를 두는 안을 골랐다. 종류 셋으로 묶고 사유 필드로 구분하는 안은 할 일을 다시 사유 필드에서 추론해야 하므로 고르지 않았다. 1차 리뷰가 소유 서브 세션에 의존성 추가를 요청하는 상황이 빠졌다고 지적했으므로, 이 개정을 쓴 세션은 같은 원칙으로 `DEPENDENCY-REQUEST`를 추가했다.

현재 세션은 모든 하향 메시지에 `워크스트림`과 `통합 브랜치`(`dev/<개발> @ <커밋>`)를 공통 필드로 적는다. 아래 표의 '다음 응답'은 일을 마쳤을 때의 응답이다. 서브 세션은 어느 하향 메시지 뒤에도 사유에 해당하면 `BLOCKED`를, 끝낼 수 없으면 `FAILED`를 돌려준다.

| 머리줄 | 추가 필드 | 서브 세션이 할 일 | 다음 응답 |
|---|---|---|---|
| `APPROVE` | `승인한 하부 명세`, `조건` | writing-plans, `review-specs`, SDD 로 진행한다 | `DONE` |
| `REVISE` | `대상`, `고칠 항목` | 고칠 항목을 처리하고 커밋한다. 대상이 하부 명세면 다시 리뷰한다 | 대상이 하부 명세면 `AWAITING_APPROVAL`, 구현이나 plan 이면 `DONE`, 응답이면 고친 같은 상향 메시지 |
| `ANSWER` | `질문`, `답`, `결정 기록` | 답을 반영해 멈춘 작업을 이어 간다 | 하던 단계의 응답 |
| `BASE-UPDATED` | `바뀐 것`, `할 일` | 통합 브랜치를 병합하고 테스트를 다시 실행한 뒤 이어 간다 | 하던 단계의 응답 |
| `CONTRACT-CHANGED` | `바뀐 항목`, `커밋` | 통합 브랜치를 병합하고 바뀐 계약 행이나 큰 명세 절에 맞춘다. 하부 명세가 바뀌면 다시 리뷰한다 | 하부 명세가 바뀌었으면 `AWAITING_APPROVAL`, 아니면 하던 단계의 응답 |
| `ASSUMPTION-ADDED` | `가정`, `결정 기록` | 통합 브랜치를 병합한다. 자기 구현이 그 가정과 다르면 고치지 않고 `BLOCKED contract-change`로 알린다 | 하던 단계의 응답 |
| `DEPENDENCY-REQUEST` | `패키지`, `요청한 워크스트림` | 의존성 목록과 잠금 파일에 패키지를 추가하고 커밋한 뒤 하던 단계로 돌아간다 | 하던 단계의 응답 |
| `INTEGRATION-FAILED` | `확인 위치`, `실패 검사`, `출력` | 원인을 고치고 커밋한다 | `DONE` |
| `CANCEL` | `이유` | 미커밋 변경을 커밋하지 않고 워크트리에 남긴 채 멈춘다 | `CANCELED` |

`INTEGRATION-FAILED`의 `확인 위치`는 시험 병합의 `try/<id>` 커밋이거나, 이미 병합된 워크스트림의 통합 확인을 다시 실행한 `dev/<개발>` 커밋이다. 「묶는 단위」는 이미 병합된 워크스트림의 통합 확인도 다시 실행하게 하므로 두 위치를 함께 둔다.

현재 세션은 하부 명세 수정 요청 말고도 아래 상황에서 `REVISE`를 쓴다.

- 허용 경로 밖 변경: 수정 범위 대조에서 허용 경로 밖 파일이 나왔을 때
- 리뷰 마커 없음: 추가된 하부 명세나 plan 의 마지막 줄에 리뷰 마커가 없을 때
- 교집합 겹침: 교집합 검사에서 두 워크스트림이 같은 파일을 고쳤을 때. 현재 세션은 사용자에게 알리고, 사용자가 그 파일을 고치지 않기로 정한 쪽에 보낸다
- 판정 번복: 하부 명세 승인이나 「판정 기록 확인」에서 사용자가 서브 세션의 판정을 뒤집었을 때
- 실패 뒤 재시도: `FAILED` 뒤 같은 서브 세션에 다시 시키기로 했을 때. 고칠 코드가 없으면 `고칠 항목`에 다시 실행할 단계를 적는다
- 형식 이탈: 상향 메시지가 판단에 필요한 필드를 빠뜨렸을 때. `대상`은 '응답'이다

리뷰 마커가 escalated 인데 「결정 기록」에 답이 없으면, 서브 세션은 그 기록을 쓸 수 없다. 그래서 현재 세션은 `REVISE`를 보내지 않고 `review-red` 처리대로 🔴 를 사용자에게 알려 답을 적는다. 현재 세션은 답을 적은 뒤 병합 전 검사를 이어 가고, 그 답이 하부 명세나 구현을 바꿔야 하면 `REVISE`를 보낸다. 시험 병합의 테스트나 통합 확인이 실패하면 현재 세션은 `INTEGRATION-FAILED`를 쓴다.

**보내는 순서.** 현재 세션은 메시지를 서브 세션이 멈춘 뒤에만 보낸다(「이어 쓰기와 재개」). 같은 서브 세션에 보낼 메시지가 여럿이면 한 번에 묶어 보내고, 통합 브랜치를 바꾸는 메시지(`BASE-UPDATED`, `CONTRACT-CHANGED`, `ASSUMPTION-ADDED`)를 앞에 둔다. 따로 보내면 둘째 메시지가 실행 중에 도착할 수 있고, 뒤에 두면 서브 세션이 옛 기준 위에서 이어 간 구현을 다시 병합해야 하기 때문이다.

현재 세션은 계약 코드와 큰 명세를 고친 뒤 받을 서브 세션이 실행 중이면 메시지를 미룬다. 미룬 사실은 현재 세션의 맥락에만 있으므로, 현재 세션은 시험 병합 전에 `log --oneline ws/<개발>/<id>..dev/<개발> -- <계약 코드 경로> <큰 명세 경로> <의존성 목록·잠금 파일 경로>`를 실행한다. 출력이 비어 있지 않으면 그 워크스트림은 바뀐 계약이나 큰 명세를 받지 않았으므로, 현재 세션은 병합하지 않고 `BASE-UPDATED`를 보낸다. 출력의 커밋이 그 워크스트림이 제공자나 소비자인 계약 행을 바꿨으면 `CONTRACT-CHANGED`를, 그 워크스트림이 쓰는 공유 가정을 추가했으면 `ASSUMPTION-ADDED`를 대신 보낸다. 커밋을 기억하지 않고 git 에서 도출하기 위해서다. 큰 명세 파일에는 「결정 기록」도 있어 통합 때마다 커밋이 생기므로, plan 리뷰의 lens-adversarial 이 계약 변경 메시지만 보내면 보낼 것이 없는 상황이 생긴다고 지적했다.

다른 세션의 「검증 의존 대기」는 서브 세션의 상태 값을 늘리지 않는다. 서브 세션은 `DONE`을 돌려준 뒤 멈춰 있고, 기다리는 주체는 현재 세션이기 때문이다. 대기 뒤 통합 확인이 실패하면 현재 세션은 `INTEGRATION-FAILED`를 보내고, 서브 세션이 대상의 통합 결과를 받아야 하면 `BASE-UPDATED`를 보낸다.

**리포트 스키마.** 서브 세션은 리포트 파일에 아래 절 제목을 이 순서로 두고, 내용이 없는 절도 `없음`으로 남긴다. 현재 세션은 절마다 정한 단계에서 그 절을 읽는다. 처음 문안에 있던 `변경 파일`과 `테스트` 절은 지웠다. 「수정 범위 대조」는 diff 로, 시험 병합은 테스트를 직접 실행해 판정하므로, 1차 리뷰의 lens-grounding 과 lens-consistency 가 그 절을 읽는 단계가 없다고 지적했기 때문이다.

| 절 제목 | 형식 | 읽는 단계 |
|---|---|---|
| `확정한 결정` | 줄마다 '결정 — 이유' | 통합 때 「결정 기록」으로 옮긴다 |
| `확정한 계약 의미` | 줄마다 '계약 행 — 칸(의미 또는 형식의 열거값) — 값' | 통합 때 계약 표의 '확정 예정' 칸을 채운다 |
| `명세 이탈` | 줄마다 '하부 명세의 위치 — 실제 구현 — 이유' | 「판정 기록 확인」 |
| `스스로 판정한 모호함` | 줄마다 '질문 — 판정 — 이유 — 범위 밖 항목에 가까운지(예·아니오)' | 하부 명세 승인, 「판정 기록 확인」 |
| `기능적 반영` | 리뷰 반영 중 동작이 바뀐 항목 | 「흐름」 마무리 보고 |
| `제안` | 범위 밖 아이디어 | 「흐름」 마무리 보고 |

현재 세션은 하부 명세 승인과 「판정 기록 확인」에서 '범위 밖 항목에 가까운지'가 '예'인 줄을 사용자에게 묻고, 「판정 기록 확인」에서는 `명세 이탈`의 줄도 묻는다. 사용자가 판정을 뒤집으면 현재 세션은 `REVISE`를 보낸다.

**계약 표의 '확정 예정'.** 「묶는 단위」는 의미를 받기만 하는 사용 쪽의 계약에서 의미를 소유 워크스트림 통합 때 확정하게 한다. 이런 행에서 현재 세션은 큰 명세에 의미 칸과 형식 칸의 열거값을 '확정 예정(<소유 워크스트림 id>)'으로 적는다. 소유 서브 세션은 그 값을 리포트의 `확정한 계약 의미`에 적고, 현재 세션은 그 워크스트림을 통합할 때 칸을 채운다. 이 확정은 계약 변경이 아니다.

사용 쪽은 설계 의존으로 소유 쪽 통합 뒤에 시작하므로, 사용 쪽 하부 명세를 승인할 때 칸은 이미 채워져 있다. 열거값까지 포함한 이유는 2차 리뷰의 lens-adversarial 이 지적했기 때문이다. 상태의 열거값은 형식 칸에 들어가는데, 의미 칸만 미루면 소유 서브 세션이 그 값을 정할 때마다 `BLOCKED contract-change`로 멈춘다. 이 예외는 다른 세션(disciplined-coder-f0)과 맞춘 것이다.

**반영 위치.** 구현하는 세션은 스킬을 아래와 같이 고친다.

- 「메시지 형식」 새 절: 「디스패치 템플릿」 바로 뒤에 둔다. 표기, 상향 메시지 표와 `FAILED` 기준, 복수 사유 규칙, BLOCKED 처리 표와 그 뒤 처리 문단, 하향 메시지 표와 `REVISE` 상황, 보내는 순서, 리포트 스키마를 이 절에 둔다
- 「디스패치 템플릿」: 현재 세션이 자기가 연 SKILL.md 의 절대 경로를 프롬프트에 넣고, 서브 세션이 시작할 때와 하향 메시지를 받을 때 그 파일의 「메시지 형식」 절을 읽게 한다. 수정 허용 경로 항목의 `BLOCKED`에 사유 코드를 붙이고, plan과 구현 항목의 승인·통합 브랜치 변경 메시지를 하향 메시지 이름으로 바꾼다. 멈추는 기준과 산출 계약 항목의 리포트 항목 목록과 '돌려주는 것' 문장은 지운다
- 「멈추는 기준」: 사유마다 사유 코드를 붙이고 `dependency-add`·`test-double-add` 불릿을 추가한다. '아래 사유에서만 멈춘다'에 `FAILED`를 예외로 적는다
- 「이어 쓰기와 재개」: 보내는 메시지 목록을 하향 메시지 표로 가리킨다
- 「공용 파일」과 「계약 코드」: `BLOCKED`를 각각 `BLOCKED dependency-add`, `BLOCKED test-double-add`로 바꾼다
- 「계약 표」: 의미 칸과 형식 칸의 열거값에 '확정 예정' 예외를 적는다
- 「승인 항목」: 공유 가정 문단은 `ASSUMPTION-ADDED`를 가리키고, 스스로 판정한 모호함은 리포트의 '예' 줄을 읽게 한다
- 「흐름」과 「진행 위치」: 마무리 전제를 접지 않은 워크스트림으로 한정하고, 「결정 기록」의 '접은 워크스트림' 줄로 접힘을 판정한다
- 「가드레일」: 수정 범위 대조, 리뷰 마커 없음, 교집합 겹침은 `REVISE`로, 시험 병합과 「검증 의존 대기」의 실패는 `INTEGRATION-FAILED`로 되돌린다고 적는다. 시험 병합 전에 바뀐 계약이나 큰 명세를 받았는지 확인하는 `log` 문장을 추가한다
- 「판정 기록 확인」: `명세 이탈` 절도 읽게 한다
- 「흐름」: 마무리 단계가 `기능적 반영` 절도 모으게 한다
- 「측정」: `Questions:`를 `BLOCKED` 응답의 사유 코드 수로 정의하고, 형식 이탈 수를 `Format-Deviations:` 트레일러로 넣는다

형식 이탈은 머리줄이 정한 종류와 사유 코드 밖이거나 정해진 필드가 빠진 응답이다. 현재 세션은 판단할 수 있으면 해석해 진행하고, 판단에 필요한 필드가 빠졌으면 `REVISE`(대상: 응답)를 보낸다. 두 상황 모두 이탈로 센다.

서브 세션에 형식을 전달하는 방법은 1차 리뷰의 🔴 였다. 처음 문안은 표를 디스패치 프롬프트에 복사하게 했고, 그 이유로 서브 세션이 스킬 파일이 아니라 프롬프트만 받는다는 점을 들었다. lens-adversarial 은 하향 메시지 표가 프롬프트에 빠졌고, 템플릿이 이미 서브 세션에게 `dispatching-lenses`를 통째로 읽게 하므로 그 이유가 맞지 않는다고 지적했다. 사용자는 서브 세션이 「메시지 형식」 절을 직접 읽게 하는 안을 골랐다. 사본이 생기지 않고, 맥락이 압축되어도 다시 읽을 원본이 남기 때문이다.

2차 리뷰의 lens-adversarial 은 개발 도중 플러그인이 갱신되면 두 세션이 다른 버전의 스킬을 읽는다고 지적했다. 그래서 현재 세션은 자기가 연 SKILL.md 의 절대 경로를 넣는다.

**검증하지 않은 가정.** 형식을 정하면 현재 세션의 사유 판단이 정확해지리라는 효과는 측정하지 않았다. 저장소의 두 기록은 MAST 를 서로 다르게 옮겼다. 선행연구 기록(`2026-10-11-contract-table-prior-art.md`)과 lens-prior-art-1 은 통신 프로토콜에 초점을 둔 해법이 에이전트 사이 불일치에 흔히 불충분하다고 MAST 가 적었다고 옮겼다. lens-prior-art-2 는 MAST 가 표준 통신 프로토콜을 처방하면서 프롬프트 수준 처방의 효과는 제한적이라고 적었다고 옮겼다. 이 개정을 쓴 세션은 원 논문을 열어 대조하지 않았다.

두 읽기 모두에서 검사 스크립트 없이 스킬 문장으로만 정한 형식의 효과는 보장되지 않는다. 그래서 현재 세션은 「측정」의 `Format-Deviations:`로 다음 큰 개발에서 서브 세션이 이 형식을 지키는지 본다. 이 트레일러는 시험 병합 커밋에만 남으므로, `FAILED`나 `CANCELED`로 끝나 병합되지 않은 워크스트림의 이탈 수는 빠진다. 현재 세션은 마무리 보고에서 그 워크스트림을 따로 적어 이 한계를 밝힌다.

## 2026-10-11 개정 — 검진 반영

2026-10-11에 사용자가 nested-orchestration 스킬을 여러 검진으로 독립 검토하게 했고, 그 결과를 보고 아래 결정을 내렸다. 이 절은 그 결정과 이유, 구현하는 세션이 스킬과 훅에서 고칠 결함, 스킬 본문에서 지운 근거를 적는다. 이 절에서 '현재 세션'과 '서브 세션'은 「용어」 표의 뜻으로만 쓴다. 검진을 실행하고 사용자 결정을 전달한 세션은 '검진을 맡은 세션'으로, 이 개정을 쓴 세션은 '이 개정을 쓴 세션'으로 적는다. 위 절의 문장은 기록으로 남는다. 위 절과 이 절이 다르면, 이 설계를 읽고 구현하는 세션은 이 절을 따른다.

**검진 구성.** 검진은 `lens-adversarial`, `lens-consistency`, `lens-grounding`과, 훅·스크립트를 실제로 실행한 검진, 서브 세션 흐름을 모의로 따라간 검진, 구조와 과도함을 본 검진이다. 발견은 명령의 실행 결함, superpowers 6.4.1 SDD 와의 불일치, 빠진 절차, 출처가 바뀌었거나 없는 근거 서술, 스킬 분량이었다. 이 개정을 쓴 세션은 검진 원본을 받지 않았다. 아래 결정과 결함 목록은 검진을 맡은 세션이 전달한 요약에 근거한다.

**판단 훅 결정.** 「2026-10-10 개정」의 「검증하지 않은 가정」은 현장에서 큰 개발이 하위 프로젝트를 차례로 진행하면 훅 추가를 사용자에게 제안한다고 적었다. 그 제안은 2026-10-11 커밋 76e6449 로 실행되었다. 커밋 메시지는 근거를 "판단 시점이 spec 승인 뒤뿐이라 plan 분할이 판단보다 먼저 정해졌다(2026-10-11 NP-bond-agg)"로 적는다. 「2026-10-10 개정」의 「판단 시점」은 분해하기로 했을 때도 판단하게 하지만, NP-bond-agg 세션에서 맡길지 판단은 사용자가 지적한 뒤에야 일어났다. 그 세션이 첫 판단 시점을 왜 거치지 않았는지는 이 개정을 쓴 세션이 확인하지 못했다.

그 커밋은 `hooks/nested_judgment_pretooluse.sh`를 추가했다. 이 훅은 프로젝트 안의 새 spec 을 처음 Write 하려 하면 세션마다 경로당 한 번 거부하고, 거부 사유로 스킬을 열어 맡길지 판단하게 한다. 그래서 「결정」의 「트리거」에서 훅을 처음에는 두지 않는다고 한 문장은 이 절이 대체한다.

사용자는 거부를 유지하기로 했다. 그 대신 거부 사유에 「맡기는 기준」 한 문장을 넣는다. 거부는 지금처럼 새 spec 경로마다 세션에서 한 번이다. 사유에 기준이 있으면 현재 세션은 작은 spec 에서 스킬(약 27k 토큰)을 열지 않고 판단할 수 있다. 맡기기로 하면 현재 세션은 큰 명세를 거부된 그 경로에 쓴다. 같은 경로를 다시 쓰면 통과하므로, 큰 명세를 다른 경로에 쓸 때 생기던 두 번째 거부가 없어진다.

남는 비용은 새 spec 마다 거부된 본문을 모델이 한 번 다시 생성하는 값이다. 작은 spec 은 사유의 기준 한 문장으로 판단하므로 스킬을 읽는 비용은 들지 않는다. 거부 사유의 기준 문장은 스킬 「맡기는 기준」의 요약이고 원본은 스킬이다. 그래서 구현하는 세션은 「맡기는 기준」을 고칠 때 훅 사유도 함께 고친다.

구현하는 세션은 같은 훅의 결함 두 가지도 고친다. 첫째로 표시 파일을 만들지 못하면 같은 거부가 되풀이될 수 있었으므로, 그때는 거부하지 않고 통과시킨다(fail-open). 둘째로 영숫자가 아닌 글자를 `_`로 바꾸고 뒤 120자만 남긴 경로 키는 서로 다른 경로를 같은 키로 만들 수 있었고, 같은 경로의 다른 표기를 다른 키로 만들 수 있었다. 그래서 표시 키는 정규화한 경로의 해시로 만든다.

사용자가 고르지 않은 안은 세션당 한 번 거부, brainstorming 넛지, 현행 유지, 훅 제거다. 사용자는 처음에 두 번째 거부를 없애려고 세션당 한 번 거부를 골랐다. 그러나 그 안은 같은 세션에서 작은 spec 뒤에 쓰는 큰 개발의 spec 을 판단 없이 통과시킨다. 훅을 만든 계기인 NP-bond-agg 는 지시만으로 판단이 일어나지 않은 사례이므로, 사용자는 그 빈틈을 받아들이지 않았다. 한 세션이 보통 spec 하나만 쓴다는 가정은 아무도 측정하지 않았다.

brainstorming 을 호출할 때 넛지를 내는 안은 거부하지 않으므로 강제력이 없다. 그 효과를 측정한 기록도 없다. 현행 유지 안은 작은 spec 마다 스킬을 읽히고 두 번째 거부를 남긴다. 훅 제거 안에 대해서는 근거가 실패 사례 한 건뿐이다. 그러나 그 사례는 지시만으로 판단이 일어나지 않았다는 관찰이므로, 사용자는 되풀이될 위험을 보고 그 안을 고르지 않았다.

**메시지 형식 통합 결정.** `BLOCKED` 사유 코드는 `user-decision`, `contract-change`, `shared-file-change`, `dependency-add`, `test-double-add`로 줄이고, 복수 사유의 머리줄 순서도 이 순서다. `review-red`, `review-gap`, `sdd-stop`은 `user-decision`에 합치고, `user-decision`에 `유형` 필드를 둔다. 유형은 범위 밖 결정, 리뷰 🔴, 리뷰 관점 부족, SDD 정지, 환경 문제다. 한 번에 `user-decision` 사유가 둘 이상이면 서브 세션은 `요청` 필드의 줄마다 유형을 적는다.

`user-decision`을 받으면 현재 세션은 유형마다 위 「메시지 형식」의 옛 처리를 따른다. 리뷰 🔴, 리뷰 관점 부족, 범위 밖 결정, 환경 문제, 비가역·보안·워크트리 밖 부작용의 SDD 정지는 사용자에게 묻는다. 전부 추측인 plan 의 SDD 정지는 현재 세션이 큰 명세나 「결정 기록」에 근거를 보강한다. 모든 유형의 답은 요청한 쪽에 `ANSWER`로 보낸다.

하향 메시지는 `APPROVE`, `REVISE`, `ANSWER`, `BASE-UPDATED`, `CONTRACT-CHANGED`, `INTEGRATION-FAILED`, `CANCEL`로 줄인다. `ASSUMPTION-ADDED`는 `CONTRACT-CHANGED`에 합치고 `DEPENDENCY-REQUEST`는 지운다. 합친 메시지가 공유 가정을 알리면, 받는 서브 세션은 옛 `ASSUMPTION-ADDED`의 행동을 따른다. 그 서브 세션은 통합 브랜치를 병합하고, 자기 구현이 그 가정과 다르면 고치지 않고 `BLOCKED contract-change`로 알린다. 공유 가정은 사용자의 채택 선택 없이 하부 명세 승인 때 커밋되므로, 받는 쪽이 맞춰 고치면 사용자 결정 없이 구현이 바뀌기 때문이다.

의존성 목록과 잠금 파일은 처음부터 현재 세션이 소유한다. `BLOCKED dependency-add`를 받으면 현재 세션은 통합 브랜치에서 패키지를 추가하고 요청한 쪽에 `BASE-UPDATED`를 보낸다. 다른 사유 코드의 처리는 위 「메시지 형식」의 처리 표 그대로다.

이 결정의 첫째 이유는 처리의 중복이다. 합친 코드는 모두 현재 세션이 판단하거나 사용자에게 물어 `ANSWER`를 보내는 처리로 끝난다. 둘째 이유는 규칙 사이의 모순이다. 「메시지 형식」은 환경 문제를 `BLOCKED user-decision`으로 보내게 했다. 그런데 「2026-10-10 개정」의 「범위 밖 결정」 정의에는 환경 문제가 없었다. `유형` 필드는 환경 문제를 따로 적게 해 이 모순을 해소한다.

셋째 이유는 잠금 파일의 소유 전환이다. 옛 규칙은 잠금 파일을 한 워크스트림이 소유하다가, 그 워크스트림이 끝나면 현재 세션에 넘겼다. 이 전환 때문에 두 워크스트림이 서로를 기다리는 상황이 생겼다(「메시지 형식」의 `dependency-add` 처리 문단). 소유 워크스트림과 현재 세션이 같은 잠금 파일을 고쳐 충돌하는 상황도 생겼다. 처음부터 현재 세션이 소유하면 두 문제가 함께 사라진다.

잃는 것은 사유 코드만으로 바로 집계하던 편의이고, 현재 세션은 `유형` 필드로 다시 셀 수 있다. 사용자가 고르지 않은 안은 잠금 파일 소유만 바꾸는 안과 현행 유지 안이다. 현행 유지는 모순마다 규칙을 추가해야 해 문서가 길어진다. 메시지 형식은 실제 실행을 한 번도 거치지 않았으므로, 현재 세션은 첫 큰 개발 기록에서 다시 나눌 필요가 보이면 나눈다.

이 결정이 대체하는 문장은 아래와 같다. 「2026-10-10 개정」 「근거」 표의 npm 근거는 잠금 파일을 고치는 주체가 하나라는 점에 대응하므로, 현재 세션의 단일 소유에도 그대로 적용된다.

- 「결정」의 「공용 파일」에서 의존성 목록과 잠금 파일을 한 워크스트림에 맡기는 문장
- 「2026-10-10 개정」의 「묶는 단위」 둘째 문단과 「잠금 파일」의 한 워크스트림 소유 규칙
- 「2026-10-11 개정 — 메시지 형식」의 사유 코드 처리 표와 하향 메시지 표의 `review-red`·`review-gap`·`sdd-stop`·`dependency-add`·`ASSUMPTION-ADDED`·`DEPENDENCY-REQUEST` 행
- 같은 절에서 환경 문제를 `user-decision`으로 보내는 문장과 `dependency-add`를 따로 알리는 복수 사유 문장
- 같은 절의 `dependency-add` 처리 문단과 `ASSUMPTION-ADDED`를 보내는 문장
- 같은 절에서 옛 코드 이름(`review-red`, `review-gap`, `sdd-stop`)으로 처리를 가리키는 문장

**근거 이동 결정.** 스킬 본문에서 행동을 바꾸지 않는 근거·측정·사건 서술을 지우고, 스킬은 이 설계 문서를 가리킨다. 측정 트레일러는 `Integration-Failures:`와 `Tokens:`만 남긴다. `Questions:`와 `Format-Deviations:`, 계약 표 효과를 다른 개정의 기준값과 비교하는 보고는 아래 「첫 큰 개발에서 측정」으로 옮긴다. 이 결정이 대체하는 문장은 아래와 같다.

- 「결정」의 「측정」에서 `Questions:` 트레일러를 두는 문장
- 「2026-10-11 개정 — 계약 표」의 「칸」 문단과 「검증하지 않은 가정」에서 계약 공백 지적 수 비교를 스킬 「측정」에 둔다는 문장
- 「2026-10-11 개정 — 메시지 형식」 「반영 위치」의 「측정」 줄과, 같은 절 「검증하지 않은 가정」의 `Format-Deviations:` 문장
