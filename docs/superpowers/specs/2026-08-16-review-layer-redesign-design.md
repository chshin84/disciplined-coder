# 리뷰 레이어 재설계 — 등급 대신 근거, 한 번만 도는 리뷰

> **일부 superseded** — 같은 날 `2026-08-16-review-procedure-design.md`가 이 문서의 "리뷰는 한 번만
> 돈다"와 마커의 뜻을 뒤집었다. 등급을 없애고 근거를 필수로 둔 부분은 그대로 살아 있다. 리뷰 횟수와
> 마커에 대해서는 새 문서를 따른다.

## 무엇을 왜 바꾸는가

지금의 리뷰 레이어는 네 곳에서 아프다. 넷은 증상이 달라 보이지만 뿌리가 둘이다.

**심각도가 부풀려진다.** 다섯 렌즈의 출력 스키마는 전부 `"severity": "critical|major|minor"`라고만
적고 각 값이 무슨 뜻인지는 어디에도 정의하지 않는다. 기준 없이 라벨을 고르라고 하면 위로 쏠린다.
그런데 `meta-aggregate`는 critical이 하나만 있어도 재작성 한 바퀴를 강제한다. 정의되지 않은 라벨
하나가 왕복을 만드는 구조다.

**첫 패스가 얕다.** 프롬프트가 전부 "찾아라"로만 되어 있고, 무엇을 근거로 삼아야 하는지도 무엇을
안 올려도 되는지도 말하지 않는다. 그래서 표면 지적이 그대로 통과하고, 문서 밖(실제 코드·기존 구현)을
봐야 보이는 모순은 첫 패스에서 잡히지 않는다.

**리뷰가 다시 발동한다.** 원인이 둘이다. `meta-aggregate`의 재작성 정책이 하나이고, 다른 하나는
훅이다. `spec_review_posttooluse.sh`는 문서 마지막 줄에 마커가 있으면 건너뛰는데, 리뷰 지적을
반영하려고 문서를 편집하는 시점에는 아직 마커가 없다. 그래서 **개선 편집 자체가 리뷰 지시를 다시
띄운다.**

**선행연구 렌즈가 기본 묶음 안에 있다.** 웹에 나가는 렌즈인데 발동 판단이 리뷰 실행에 묻혀 있어,
필요 없을 때도 판단 비용이 들고 필요할 때도 사용자가 개입할 자리가 없다.

뿌리 둘은 이렇다. 하나는 **근거 없이 라벨만 고르게 한 것**이고(부풀림과 얕음이 여기서 나온다),
다른 하나는 **리뷰를 판정과 라우팅이 달린 파이프라인으로 본 것**이다(재발동이 여기서 나온다).

이 재설계의 목적은 리뷰 품질을 유지하면서 **리뷰에 드는 시간을 줄이는 것**이다.

## 결정 요약

- 렌즈 출력에서 등급 라벨을 없애고, 각 발견이 **결과와 근거를 필수로** 갖게 한다.
- 처분은 렌즈가 아니라 **호출자**가 정한다. spec 리뷰는 사람이 근거를 읽고 가르고, 제품 런타임은
  코드가 `type`으로 맵핑한다.
- 리뷰는 **한 번만** 돈다. 재작성 왕복을 없애고, 마커를 개선보다 먼저 남겨 훅 재발동을 끊는다.
- 선행연구 렌즈는 기본 묶음에서 빼고, **제안과 승인**을 거쳐 따로 돌린다.

## 리뷰 산출물 계약

`meta-aggregate`가 이 계약의 단일 출처가 되고, 다섯 렌즈는 각자 자기 `type` 집합만 정의한 뒤
나머지는 참조한다. 지금은 같은 스키마가 다섯 파일에 복제되어 있다.

```
{
  "lens": "grounding|fit|consistency|adversarial|prior-art",
  "read": ["문서 밖에서 실제로 열어본 것 — 파일 경로나 URL"],
  "issues": [
    { "where":       "문서 내 위치",
      "type":        "<렌즈가 정의한 폐쇄 집합>",
      "claim":       "무엇이 문제인가",
      "consequence": "이대로 두면 무엇이 어떻게 잘못되는가",
      "evidence":    "그렇게 본 근거 — 문서 인용, 파일 경로와 줄, URL" } ],
  "principles_applied": ["..."],
  "notes": ""
}
```

`severity`가 사라진다. 지금의 `detail` 한 필드는 `claim`·`consequence`·`evidence` 셋으로 갈라진다.

셋으로 가르는 것이 핵심이다. 한 필드에 산문으로 뭉쳐 두면 "결과를 적었는가"를 확인할 방법이 없지만,
필드를 나누면 비어 있는 것이 그 자리에서 드러난다(`FAIL-LOUD`).

계약에 붙는 규칙은 둘이다.

- **`consequence`를 구체적으로 못 적는 발견은 올리지 않는다.** 표면 지적은 결과를 구체적으로 쓸 수
  없으므로 이 규칙 하나로 걸러진다.
- **`issues`가 빈 배열인 것은 정상적인 결과다.** 지금 다섯 프롬프트 어디에도 빈손을 허용하는 문장이
  없어서, 리뷰어가 빈손으로 돌아오기를 꺼려 억지 지적을 만든다.

`read`는 문서 밖을 실제로 읽었는지를 관측 가능하게 만든다. `principles_applied`와 같은 처방이다 —
비어 있으면 호출자가 자기 보고에 적고, 자동 재시도는 걸지 않는다. 읽지 않고 채우는 것을 막을 수
없으므로 재시도는 "비어 있지 않은 배열"로만 수렴하기 때문이다.

`reviewer-prior-art`의 `search_status`·`citations`·`not_found`·`disclosures`는 그대로 유지한다.

## 렌즈별 프롬프트와 읽기 범위

다섯 렌즈의 system 문장에 공통으로 세 줄이 들어간다. 등급을 매기지 말 것, 각 발견에 결과와 근거를
필수로 적을 것, 찾은 것이 없으면 빈 목록이 정상이라는 것이다. 기존의 "고치지 말고 지적만 하라"는
그대로 둔다.

읽기 범위는 렌즈마다 다르게 준다. 깊이가 필요한 곳에만 시간을 쓰기 위해서다.

| 렌즈 | 어디까지 읽나 | 왜 그렇게 두나 |
|---|---|---|
| `reviewer-grounding` | 문서 밖을 반드시 읽는다 — 주입된 사실, 문서가 주장하는 대상 코드, 기존 구현 | 문서 밖을 봐야 보이는 모순이 이 렌즈의 일이다 |
| `reviewer-consistency` | 짝 문서와 문서가 직접 이름을 부른 파일까지 | 정합성은 문서 쌍의 문제라 더 넓게 읽어도 얻는 것이 적다 |
| `reviewer-adversarial` | 문서 안에서 추론한다. 문서가 가리키는 파일은 확인하되 스스로 탐색하지 않는다 | 실패 모드를 상상하는 일이라 탐색이 도움이 되지 않는다 |
| `reviewer-fit` | 출력 계약과 후보만 본다 | 형식 적합성은 문서 밖과 무관하다 |
| `reviewer-prior-art` | 웹으로 나간다 | 이 렌즈만 외부에 나가며 기존 가드 다섯을 그대로 유지한다 |

## 처분 맵핑

렌즈는 처분을 고르지 않는다. 호출자가 자기 맥락의 어휘로 맵핑한다. 이렇게 두는 이유가 둘이다.

하나는 **처분 축이 맥락마다 다르기 때문**이다. 이 렌즈들은 spec 리뷰뿐 아니라 제품 런타임에도 쓰이는데,
런타임에는 "사용자에게 묻는다"라는 처분이 존재하지 않는다. 처분을 렌즈 스키마에 박으면 런타임에서
못 쓰는 필드를 렌즈가 강제로 채우게 된다.

다른 하나는 **처분이 자율성의 판단이기 때문**이다. 사용자를 멈춰 세울지 말지는 호출자의 책임이지
서브에이전트가 대신 정할 일이 아니다.

### spec 리뷰 — 사람이 근거를 읽고 가른다

`domain-spec-review`가 이 기준을 소유한다. 발견을 `🔴`와 "고칠 것" 둘로 가른다. `🔴`는 이 레포가
이미 쓰는 기호이며 `agent-principles.md`가 "즉시 사용자에게 surface하며 누구도 자율적으로 구현하지
않는다"고 규정한다. 새 어휘를 만들지 않고 그것을 재사용한다.

`🔴`로 올리는 기준은 셋이다.

- 되돌리기 어려운 결정인가(`REVERSIBLE`).
- 사용자의 가치판단이 필요한가.
- 고치는 방향이 둘 이상으로 갈리고 근거만으로는 고를 수 없는가.

셋 중 어디에도 걸리지 않으면 전부 고친다. **기본값이 고치기이고 `🔴`가 예외다.**

### 제품 런타임 — 코드가 `type`으로 맵핑한다

런타임에서는 집계가 결정론적 파이썬 함수라 산문 근거를 읽고 판단할 수 없다. 그래서 제품 코드가
자기 도메인에 맞는 `type` → 행동 표를 코드로 박는다. `type`은 이미 렌즈마다 정의된 폐쇄 집합이라
그대로 쓸 수 있고, 리뷰어의 주관적 등급에 의존하지 않으니 결정론이 유지된다.

`domain-llm-runtime`의 "critical만 regenerate를 강제한다"를 이 방식으로 교체한다. 그 스킬의 비기능
체크리스트에 붙은 `(critical)`·`(major)` 표기는 그대로 둔다 — 그것은 리뷰어가 매기는 값이 아니라
문서가 미리 박아 둔 고정 등급이라 부풀림 문제가 없다.

## 단일 리뷰

작업 순서를 고정한다. 렌즈 셋을 돌리고, 결과를 병합하고, 처분을 가르고, **마커를 남기고**, 그다음에
고칠 것을 반영하고, 마지막에 `🔴`를 사용자에게 드린다.

마커가 개선보다 앞에 온다는 것이 전부다. 개선 편집 시점에 이미 마커가 마지막 줄에 있으므로 훅이
조용하다. 기억해서 참는 것이 아니라 발동 조건 자체를 없앤다(drift-proof by construction).

마커의 뜻은 "리뷰를 통과했다"에서 **"리뷰가 한 번 돌았다"**로 바뀐다. 값은 기존 둘을 그대로 쓴다 —
`🔴`가 하나라도 있으면 `escalated`, 없으면 `passed`다. 훅 스크립트의 마커 판정 로직은 손대지 않고
안내문만 새 순서를 지시하도록 고친다.

`meta-aggregate`에서는 "critical이 하나라도 있으면 regenerate"라는 등급 기반 정책을 걷어낸다.
`decision` 필드 자체는 런타임에서 여전히 쓰이므로 남기되, **spec 리뷰 맥락에서는 결정 단계가 없다**고
명시한다. 병합과 상충 감지까지만 하고 처분은 `domain-spec-review`가 한다. `domain-spec-review`의
라우팅 표에서 regenerate 행을 삭제한다.

## 선행연구 렌즈 분리

기본 묶음에서 뺀다. `domain-spec-review`는 렌즈 셋만 돌린다.

호출자가 spec을 보고 발동 기준에 걸린다고 판단하면 — 아직 해본 적 없는 것을 하려 하고 그것이 되는지
자체가 미지수인가 — 리뷰 결과를 전달할 때 선행연구 대조를 돌릴지 함께 제안한다. 사용자가 승인하면
서브에이전트로 따로 돌린다. 웹 도구가 없으면 돌릴 수 없다고 알린다. 붙였든 안 붙였든 판단과 이유를
보고에 적는 기존 규칙은 유지한다.

**이 렌즈의 발견은 전부 `🔴`로 간다.** 지금의 "crowded와 refuted-premise의 critical은 재작성을
건너뛰고 사람에게 올린다"는 예외를 일반화한 것이다. 웹에서 읽어온 내용이 설계 문서를 자동으로 고치는
경로를 닫는 편이 안전하고, 규칙도 하나로 줄어든다.

네 축 대조 가드는 "하나라도 다르면 심각도를 한 단계 낮춘다"에서 **"하나라도 다르면 그 차이를 명시하고
같은 사례라고 단정하지 않는다"**로 바꾼다. 등급이 없어졌으므로 낮출 대상이 없다.

## 검증

`scripts/test_docs_drift.sh`에 계약 테스트를 더한다. 기대 개수를 박지 않고 불변식으로 검증한다
(`FAIL=0`).

- 다섯 렌즈 어디에도 `severity`가 남아 있지 않다.
- 다섯 렌즈 모두 `consequence` 필수와 빈손 허용을 적는다.
- `domain-spec-review`에 regenerate 라우팅이 남아 있지 않다.
- `meta-aggregate`가 spec 리뷰에서 결정 단계가 없음을 적는다.
- 두 spec 훅의 안내문이 마커를 개선보다 먼저 남기라고 지시한다.

기존 훅 테스트는 마커 문자열만 검사하므로 영향을 받지 않는다.

**이미 있는 드리프트 테스트가 하나 걸린다.** `test_docs_drift.sh`는 "`domain-spec-review`의 디스패치
목록에 있는 렌즈"와 "README·DESIGN-NOTES가 spec 리뷰 구성을 적은 줄에 이름이 있는 렌즈"가 같아야
한다고 단언한다. 선행연구 렌즈를 기본 묶음에서 빼면 그 두 산문도 함께 고쳐야 통과한다. 이것은 테스트가
설계대로 작동하는 것이지 고장이 아니다 — 산문은 호출자의 캐시이고 캐시가 낡으면 붉어지도록 만든
장치다. 렌즈 전체를 열거하는 README 트리 주석은 디렉터리가 그대로 남으므로 손대지 않는다.

## 범위 밖

- **리스크 비례 게이팅** — 문서마다 렌즈 개수를 조절하는 것은 이번에 하지 않는다. 위험 측정을
  이슈 단위 판정으로 한정하기로 정했다.
- **렌즈 통합** — `consistency`와 `adversarial`을 합치면 시간은 줄지만 독립성이 깨진다. 얕음을
  고치려는 작업에서 얕아질 구조를 새로 들이는 셈이라 하지 않는다.
- **문서 검진 넛지** — `doc_review_posttooluse.sh`는 손대지 않는다.
- **`self-audit.js`의 `red|major|minor`** — 렌즈 계약이 아니라 감사 워크플로가 사용자에게 내는
  보고서 형식이라 소비자가 다르다. 그대로 둔다.

## 기각한 대안

**등급을 셋에서 둘로 줄이고 정의만 세우기.** 부풀리기 유인이 줄기만 하고 사라지지 않는다. 라벨을
고르는 주체가 여전히 리뷰어라 눈금 이름만 바뀐 채 같은 문제가 돌아온다. 그리고 처분 축이 런타임에
맞지 않는 문제가 그대로 남는다.

**공통 계약 스킬을 새로 만들기.** 역할 분리는 깨끗하지만 스킬이 하나 늘어난다. 지금 통증은 계약이
흩어진 것이지 계약의 집이 없는 것이 아니다. 다섯 렌즈가 이미 `meta-aggregate`를 참조하고 있으므로
새로 지을 것이 없다. 렌즈를 더 늘릴 일이 생기면 그때 다시 본다(`SIMPLE`).

## 이 문서가 받은 리뷰

**독립 렌즈 리뷰를 거치지 않았다.** 작성 세션이 사용자 요청 없이는 서브에이전트를 띄우지 못하는
설정이었고, 사용자가 렌즈 리뷰 실행을 요청하지 않았다. 작성자 자신의 점검만 거쳤다. 아래 마커는 그
사실을 담아 `escalated`로 남긴 것이며 **리뷰를 통과했다는 뜻이 아니다.**
