# 대화 답과 문서의 문체를 나눠 소유하는 구조

## 목적

Claude Code 의 평시 출력은 문체를 하나로 고정한다. 남에게 전달하거나 정리용으로 만드는 문서를 다룰 때만, 문서 종류와 청자와 내용으로 문체와 형식을 정한다. 두 범위의 형식 규칙을 겹치지 않게 나눠, 한 조항이 다른 조항의 예외를 품지 않게 한다.

이 spec 은 `docs/superpowers/specs/2026-10-27-tone-manner-design.md`(조절 축 `TONE-AXIS`)의 축 구조와 축 조건을 대체한다. 그 spec 에서 이어받는 결정은 아래 「확정 spec 에서 이어받는 결정」에 적는다.

## 배경

2026-10-28 에 확정 spec 대로 구현한 원칙(커밋 `a1ec1d41`)은 축 조건을 여러 조항에 나눠 두었다. 「출력」 머리 문장·`ASK-OPTIONS`·`WRITTEN-ONLY` 는 `TONE-AXIS` 를 직접 가리키고, `FULL-SENTENCE`·`BULLET-SCOPE`·`NO-SQUEEZE`·`KO-SYNTAX` 머리는 '밀도 축'을, `ONE-IDEA` 는 '개조식 항목'을 조건으로 둔다.

사용자는 2026-10-28 에 조항의 독립성이 사라진다며 이 구조를 불편하다고 했다. 사용자가 밝힌 방향은 원칙은 방향만 주고 수행은 에이전트가 판단한다는 방향이다. 기계로 강제할 규칙만 금지어 목록처럼 목록으로 두고, 평시 출력의 문체는 바꾸지 않는다.

### 시험 결과

2026-10-28 조항별 클린룸 시험의 결과는 아래 표와 같다. 질문은 `c27-tone-axis` 와 같은 47개이고, 조건마다 한 번씩 실행했으며, 판정자는 Sonnet 5.5 다. 시험 단위는 `evals/principles/clauses/c28-reader-tone`·`c29-reader-tone-explicit`·`c30-reader-tone-macro` 다.

| 조건 | 문안 요지 | 위반 |
|---|---|---|
| A 현행 | `TONE-AXIS` 와 여러 조항에 나눠 둔 축 조건 | 9 |
| B | 축 조건을 지운 조항 문안과 `READER-TONE`("청자와 매체가 기대하는 문체로 써라", 청자 추정과 한 줄 알림 포함) | 7 |
| C | B 의 `READER-TONE` 에 청자·게재처·상황을 먼저 뽑아 본문 밖에 밝히라는 지시를 더한 문안 | 11 |
| D | B 의 `READER-TONE` 을 문서 명세와 오버라이드("다른 조항과 부딪치면 독자 쪽을 따르라")로 바꾼 문안(청자 추정·알림 문장 없음) | 10 |

위반 합계의 차이는 2~4건이라 한 번씩 실행한 흔들림과 구분되지 않는다(저장소 CLAUDE.md 「조항 추가와 문구 변경」). 그래서 이 설계의 근거로 합계의 순서를 쓰지 않는다.

근거로 쓰는 결과는 `q-tone-axis-2` 다. 이 질문은 사내 발표자료의 근거 항목을 고치게 하며, A 만 통과했다. B·C·D 는 모두 원문의 '~다' 종결을 유지해 실패했다.

B 는 "발표자료에 흔히 쓰는 '~다' 평서문"이라고 이유를 댔다. C 는 게재처를 사내 발표자료로, 청자를 동료와 관련 팀으로 맞게 뽑고도 '~다'로 썼다. A 의 `FULL-SENTENCE`·`BULLET-SCOPE` 는 명사형 종결('~함'·'~임')을 문안에 직접 적었고, B·C·D 는 그 문안을 지웠다.

`docs/domain-korean.md` 「`TONE-AXIS`」 절의 2026-10-27 진단에서도 축 이전 문안은 '~다' 완결 문장을 냈다. 그 진단은 모델의 기본값이 작용한다고 결론지었다. 그래서 이 설계는 원하는 형태를 문안에 직접 적지 않으면 모델이 기본값('~다' 유지)으로 돌아간다고 본다. 청자를 뽑게 하는 지시만으로는 그 기본값이 바뀌지 않았다.

### 적대 렌즈 지적

2026-10-29 적대 렌즈(`lens-adversarial`, design)가 이 spec 의 백본 초안을 검토했다. 반영한 지적은 「설계」에 녹였고, 결정이 바뀐 지적은 「사용자 결정」에 적었다. 리뷰 기록은 `docs/superpowers/reviews/2026-10-29-reader-docs-tone-review.md` 다.

그 리뷰와 2026-10-30 사용자 결정으로 바뀐 절은 「사용자 결정」·「문서 명세」·「확인과 기본값」·「명세의 보관」·「렌즈」·「바꿀 파일」·「검증」이며, 그 절만 다시 리뷰했다(`2026-10-29-reader-docs-tone-review-2.md`). 다시 리뷰의 지적을 반영한 수정은 같은 절 안의 보완이라 설계를 바꾸지 않으므로 더 리뷰하지 않는다.

## 사용자 결정

2026-11-02 에 사용자가 6하 명세를 뺐다("오케이 효과가 없으면 빼야지"). 아래 2026-10-29·10-30 결정 중 명세와 기본 청자 표와 보관소에 관한 결정은 이 결정으로 대체되었다.

2026-10-29 에 사용자가 아래 결정을 내렸다.

- 오버라이드를 두지 않고 두 범위를 상호 배타로 나눈다("오버라이드는 안될때도 있는듯. 차라리 mutual exclusive 하게 분리").
- 문서의 문서 명세는 `managing-docs` 가 지시하고 메인 세션이 수행하며, 대화를 보지 못하는 하이쿠 서브에이전트에는 맡기지 않는다.
- 지시는 방향 지시로 두고, 모델이 관례를 따르지 못한 것으로 측정된 매체에만 관례 예시를 둔다.
- 문서 명세의 작성을 강제하는 훅은 두지 않는다.
- 독자를 알 수 없어도 사용자에게 묻지 않는다.
- 문서 명세는 Claude Code 창에 보이지 않게 한다("굳이 클로드 코드 창에 보일 필요는 없을꺼야").
- 독자를 정하는 절차가 디시플린코더의 `NO-ASSUME`(확인하고 행동한다)과 충돌하지 않게 한다.

훅을 뺀 이유는 렌즈 지적에 있다. 바이너리 산출물은 마크다운 초안 다음에 만들어져 훅이 집필 뒤에 발동한다.

사용자는 위 결정 가운데 `NO-ASSUME` 충돌 조치를 따로 요구하고 나머지는 권장안대로 하라고 했다("그거 빼곤 권장안"). 이어서 "spec 개정안 작성해"로 이 spec 을 지시했다.

2026-10-30 에 사용자가 문서 명세를 아래와 같이 정했다.

- 6하 항목을 모두 명세에 둔다. 근거는 암묵적 파악이 생성마다 확률적으로 다시 이루어져 한 작업 안에서도 하나로 고정되지 않는다는 점이다.
- 명세는 산출물 단위로 업무 폴더 밖 보관소에 두고 세션을 넘어 다시 쓴다("따로 떨어뜨릴", "메타 자료로 활용할 수 있잖어").
- 문서를 다루면 명세를 반드시 만든다. 대화 안 초안도 명세를 만들되, 파일이 없으므로 보관소에 저장하지 않는다.
- 사용자는 명세를 직접 고치지 않는다. 고칠 일이 생기면 Claude 가 명세를 대화에 보이고, 사용자가 동의하지 않는 항목을 말하면 Claude 가 고친다.
- 명세는 문서의 spec 시트이며 렌즈 검진 대상이 아니다("검진하라는 말 아니야").

2026-10-30 에 사용자가 기본 청자 표(행마다 사용자 확인), 시험의 실행, 원래 작업 트리에 남은 시험 파일의 정리를 권장안대로 하라고 했다("진행해").

명세가 낡지 않는다고 본 근거는 명세의 내용에 있다. 청자·게재처·목적은 본문을 고쳐도 바뀌지 않는 문서의 사실이다. 또 명세에 적는 출처(예: RFP 의 평가표)는 완성된 문서에 남지 않으므로 원본에서 되살릴 수 없다.

## 확정 spec 에서 이어받는 결정

확정 spec 의 아래 결정은 그대로 둔다.

- 목표 '입력의 문체를 문체의 근거로 쓰지 않는다'와 「반목표」 전체를 이어받는다.
- 비목표 '어조·종결·목록 문형의 기계 검사를 새로 만들지 않는다'와 '사후 렌즈 재작성만으로 해결하지 않는다'를 이어받는다.
- '항상 지키는 규칙' 목록과 「직역투와 AI 상투 표현」 절을 이어받는다.
- `ASK-OPTIONS` 의 문체 예외(산출물의 문체는 사용자에게 묻지 않는다)를 이어받는다.

비목표 '장르별 문체 목록은 만들지 않는다'는 이 spec 이 좁힌다. 측정된 실패가 있는 매체에 한해 관례 예시를 둔다(아래 「관례 예시」). 이 축소는 2026-10-29 사용자 결정(측정된 매체에만 관례 예시)에 따른다.

## 설계

### 두 범위

| 범위 | 대상 | 형식 규칙을 소유하는 곳 |
|---|---|---|
| 평시 출력 | 대화 답, 대화로 하는 작업 보고, 저장소 작업 문서(에이전트원칙·스킬·spec·plan·프롬프트·리뷰 기록·결정 기록·핸드오프·근거 문서) | 에이전트원칙 「출력」의 평시 형식 절 |
| 문서 | `reading-docs.md` 가 맡는 문서(작업 정리용 마크다운·.html·보고서·제안서·발표자료·공지·게시글·README·파일로 쓰는 작업 보고)와 대화 안 초안 | `managing-docs` 의 `references/reading-docs.md` |

경계는 문서 종류의 목록으로 정한다. '읽는 사람' 기준을 쓰면 spec·plan 이 두 범위에 모두 든다. 사용자가 승인하려고 읽고 에이전트도 따르는 글이기 때문이다.

대화 안 초안은 사용자가 남에게 보낼 글이나 문서에 넣을 글을 대화로 요청해 받은 답의 본문이다. 새로 써 달라는 요청과 붙여 넣은 글을 고쳐 달라는 요청이 모두 든다. 설명·분석·정리를 대화로 해 달라는 요청의 답은 대화 안 초안이 아니며, 대화 안 초안을 감싸는 설명도 평시 출력이다.

이 판별 문장은 원칙과 `reading-docs.md` 에 함께 둔다. C·D 조건이 대화 설명 요청(`slidetitle-chat`)에서 문서식 절 제목을 써 실패했기 때문이다.

대화 안 초안에는 `reading-docs.md` 의 「문서 명세」와 `TITLES` 를 적용한다. `MD-FIRST` 와 `REVIEW-DELIVERABLE` 은 파일 산출물에만 적용한다.

### 평시 출력의 문체

대화 답과 대화로 하는 작업 보고는 합쇼체 산문으로 쓴다. 저장소 작업 문서는 '~다'·'~하라' 산문으로 쓴다. 사용자가 문체를 지시하면 따른다.

이 범위에는 청자 판단이 없다. 읽는 사람이 늘 같은 사용자이거나 에이전트이기 때문이다.

### 「출력」의 재배치

에이전트원칙 「출력」을 두 절로 나눈다. 「공통」 절은 모든 글에 적용하고, 「평시 형식」 절은 평시 출력에만 적용한다. 범위는 각 절의 머리에 한 번만 적고, 조항 문안에는 범위를 적지 않는다.

「공통」 절에는 확정 spec 의 '항상 지키는 규칙'을 둔다. 금지어 목록, `VOCAB-PREF`(직역 금지 포함), `SPECIFIC-NAME`, `SUBJECT-OBJECT`, `TERM-ONE`, `NO-ANALOGY`, `STATE-ASSUME`, `BOTTOM-LINE`, `COUNT-EARNS`, `ONE-ENDING`, `SECTION-HEAD` 가 해당한다. 여기에 `NO-SQUEEZE` 를 더한다.

`NO-SQUEEZE` 는 축 조건만 지운다. 문안은 "산문은 형식이나 분량에 맞추려고 압축하지 마라. 목록 항목을 줄여 쓸 때는 인과의 근거와 한정어(조건·범위·추정 표시·측정 대상)를 남기고, 남길 수 없으면 항목을 나누어라. 분량이 넘치면 문장·절·슬라이드를 나누어라."다.

「평시 형식」 절에는 `WRITTEN-ONLY`, `NO-MIRROR`, `FULL-SENTENCE`, `BULLET-SCOPE`, `ONE-IDEA`, `NO-MID-MOD`, `NO-STACK-MOD`, `KEEP-CONNECT`, `ANTI-LIMIT` 를 둔다. 문안은 축 조건이 들어가기 전의 문안(커밋 `a38f5e5b`)으로 되돌린다. 다만 '모든 글을'처럼 범위를 품은 낱말은 지워 절 머리의 범위와 부딪치지 않게 한다.

「출력」 첫 문장 "Claude 가 쓰는 모든 글 … 에 적용하라"는 두 절의 범위를 안내하는 문장으로 바꾼다. 둘째 문단의 "한국어 문어체로 써라"는 "한국어로 써라"로 바꾸고, 평시 출력의 고정 문체는 「평시 형식」 절 머리에 적는다.

남에게 전달할 문서에는 「공통」 절과 `reading-docs.md` 가 적용되고, 「평시 형식」 절은 적용되지 않는다. 그래서 우선순위 규칙이 필요 없다.

### 문서의 문체와 형식

`reading-docs.md` 「문체와 형식」이 문서 종류, 청자, 내용으로 문체와 형식을 정하라고 지시한다. 입력의 문체는 근거로 쓰지 않는다. 청자를 확인하지 못해도 문체를 묻지 않고, 짐작한 청자는 대화 답에 가정으로 한 줄 밝힌다.

2026-10-30 까지 이 절에는 6하 문서 명세와 기본 청자 표와 보관소 설계가 있었다. 2026-11-02 에 사용자가 측정 결과를 보고 뺐다(아래 「검증」). 그 설계는 이 파일의 git 이력에 있다.

### 관례 예시

`reading-docs.md` 에 모델이 관례를 따르지 못한 것으로 측정된 매체의 예시를 둔다. 예시는 피할 형태와 원하는 형태를 함께 준다(저장소 CLAUDE.md 퇴고 기준의 습관 반대 조항). 지금은 사내 발표자료 한 줄이다. "사내 발표자료의 항목은 '~다'로 끝나는 완결 문장 대신 명사형('~함'·'~임')이나 명사구로 끝나는 개조식으로 쓴다."

다른 매체에서 실패가 측정되면 그때 한 줄씩 추가하고, 측정 없이 미리 채우지 않는다.

### 렌즈

렌즈에 넘기는 청자 계약은 대상의 범위에 따라 다르다. 문서는 문서 종류와 청자 한 줄을 넘기고, 평시 출력(spec·plan·스킬 같은 저장소 작업 문서)은 「평시 형식」 절의 고정 문체를 넘긴다. `lens-fit`·`lens-readability` 는 청자를 받지 못하면 문체 선택만 판정하지 않고 그 사실을 `notes` 에 적으며, 청자를 짐작하지 않는다.

### 스킬 열기의 계기

대화 안 초안은 파일 쓰기가 없으므로 `managing-docs` 를 열게 하는 계기를 따로 둔다.

- 에이전트원칙 「문서 관리」 포인터의 "문서를 새로 만들거나 고치기 전에"에 대화 안 초안을 포함한다.
- 에이전트원칙 「읽기 위한 문서」 포인터를 위 「두 범위」의 문서 목록과 판별 문장으로 바꾸고, `references/reading-docs.md` 를 읽으라고 적는다.
- `managing-docs` 의 description 실행 조건에 대화 안 초안 요청(새로 쓰기와 고치기)을 넣는다.

`reading-docs.md` 5행의 적용 범위 문장은 「두 범위」의 문서 목록과 판별 문장으로 바꾼다.

### 조항 ID

에이전트원칙에서 `TONE-AXIS` 를 지우고 새 조항 ID 는 만들지 않는다.

## 바꿀 파일

원칙은 「출력」 재배치와 포인터를, `reading-docs.md` 는 적용 범위와 「문체와 형식」을, `managing-docs` 는 description 을 바꾼다. 렌즈와 `review-docs`·`dispatching-lenses` 는 「렌즈」의 청자 계약을 받게 한다. 근거 문서는 `TONE-AXIS`·`DOC-SPEC` 을 「삭제한 조항」으로 옮긴다. 기존 시험 단위의 `ids` 와 질문의 `clause` 는 기록 재현을 위해 고치지 않는다.

## 검증

2026-11-02 에 사용자가 전체 위반 합계로 채택을 정하던 시험을 목적별 시험으로 바꾸라고 지시했다("그럼 테스트를 바꿔야 하지 않냐"). 그래서 이 작업에는 저장소 CLAUDE.md 의 합계 채택 규칙을 적용하지 않는다. 그 전 단위 `c31-doc-spec` 의 위반은 현행 9건, 변경안 14건이었으나, 합계는 대부분 이 설계와 무관한 조항의 흔들림을 셌다.

| 목적 | 시험 | 결과 |
|---|---|---|
| 조항 독립성 | 문안 검사 | 에이전트원칙에 축 조건 없음 |
| 평시 문체 고정 | `c32-plain-chat` | 절 제목 퇴행 질문 2개 통과. 변경안만 위반 1개, 현행만 위반 2개 |
| 쓰기 전 명세의 효과 | 명세 시험(문서 과제 9개) | 첫 초안 적중 7개 대 7개. 개선을 확인하지 못해 명세를 뺌 |
| 관례 예시 한 줄 | `c33-doc-form` | 예시만 둔 조건에서 발표자료 항목이 명사형으로 나오는지 확인 |

명세 시험의 방법과 수치는 `docs/domain-discipline.md` 「삭제한 조항」의 `DOC-SPEC` 에 있다. 흐름 시험에서 대화 안 초안 요청은 두 조건 모두 `managing-docs` 를 열었고, 설명 요청은 열지 않았다.
