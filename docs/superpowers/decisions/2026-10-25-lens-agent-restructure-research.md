# 렌즈·에이전트 개편 조사

이 문서는 렌즈 개선, 새 렌즈, 구조 통합, 에이전트 정의 전환을 판단하기 위한 조사 기록이다. 판정 기준을 먼저 정하고, 과거 실측을 그 기준에 대입하고, 결정 분기마다 시나리오를 만들어 권장안을 낸다. 사용자는 2026-10-25 "그 판단에 기준을 미리 만들라", "토큰 효율성, 시간 소모, 그리고 리뷰잉 커버리지 … 과거의 실측을 바바"라고 지시했다.

## 결론

권장안은 시나리오 S3(대상별 에이전트 1:N, 분리 규칙 적용)에 주장 반박 에이전트 하나를 추가하는 안이다. 이 안은 런타임 시험을 먼저 하고 구조를 정리한 뒤 에이전트로 전환하는 차례로 진행한다.

토큰을 가장 많이 쓴 원천은 렌즈의 실행 형태보다 다시 리뷰한 차수였다. 선행연구 에이전트 개발은 렌즈 4개 리뷰를 17차수 실행했고, 다시 리뷰한 지적 수는 0으로 수렴하지 않았다. 그래서 다시 리뷰 정책이 실행 형태보다 큰 절감 수단이다.

adversarial 과 consistency 를 합치면 반영된 단독 발견을 잃는다. 두 렌즈의 단독 반영률은 모두 89% 였다. 반면 fit 지적의 약 85% 는 문체·표기 지적이고, fit 의 반영률은 63% 로 가장 낮다(추정 포함).

어느 렌즈도 보지 않은 공백 중 가장 많은 주제는 런타임 동작 실측(기록 14건)이다. 읽기 전용 렌즈로는 이 공백을 메울 수 없다. 또한 적대 렌즈의 자동 실행 52건은 모두 spec·plan 이 대상이었다. 목적 밖 사용은 사용자가 직접 요청한 주장 반박, 외부 비교, 개선안 탐색에서만 나왔다.

세션 기록의 실행 수와 리뷰 기록의 지적 수는 모집단이 다르다. 그래서 두 값을 나눈 "1건당 토큰"은 추정치다. 중간 산출물과 스크립트는 세션 스크래치 폴더에 있고 저장소에 넣지 않았다.

## 판정 기준

판정 기준은 현행 구조를 기준선으로 두고 축마다 나빠지는지와 좋아지는지를 비교하는 규칙이다. 근거 없는 임계값은 두지 않는다(`EVIDENCE-FIRST`). 축은 사용자가 지정한 토큰·시간·커버리지에 메모리의 최우선 목표(작업당 사용자 에너지, 2026-10-24)와 유지비·되돌리기를 추가했다.

| 축 | 측정값 | 현행 기준선 |
|---|---|---|
| 토큰 | 리뷰 한 차수의 토큰, 반영된 단독 발견 1건당 토큰, 작업 하나의 리뷰 차수 수 | 차수당 약 49만 토큰(렌즈 4개 중앙값 합) |
| 시간 | 차수의 대기 시간(가장 느린 렌즈), 사용자가 답해야 하는 질문 수 | 약 3~3.5분, 렌즈는 동시에 실행된다 |
| 커버리지 | 반영된 단독 발견의 유지, 되풀이된 공백의 처리, 사용자 직접 요청의 처리 | 아래 「실측」 절의 값 |
| 사용자 에너지 | 사용자에게 올라가는 기술 지적과 질문의 수 | 선행연구 개발 세션의 개발 질문 31건 중 25건이 권장안 그대로 채택되었다 |
| 유지비 | 함께 고칠 파일 수, 다른 세션과 겹치는 파일 수 | 1:1 전제가 박힌 곳 약 20곳 |
| 되돌리기 | 되돌릴 때 고칠 파일 수 | — |

판정 규칙은 다음과 같다.

- **채택:** 어느 축도 나빠지지 않고 한 축 이상 좋아지면 채택한다.
- **질문:** 나빠지는 축이 하나라도 있으면 그 축과 크기를 적어 사용자에게 묻는다.
- **통합:** 두 렌즈를 합치려면 한쪽의 반영된 단독 발견이 다른 쪽 지적에 포함되어야 한다.
- **분리(1:N):** 대상에 따라 도구나 출력 계약이 다를 때만 별도 에이전트로 나누고, 입력만 다르면 한 에이전트 안의 모드로 둔다.
- **신설:** 공백이 여러 기록에 되풀이되거나 사용자의 직접 요청이 반복되고, 기존 렌즈·기계 검사·절차로 처리할 수 없을 때만 새 에이전트를 만든다.
- **기계화:** 결정론 검사가 답할 수 있는 질문은 렌즈에서 뺀다(`dispatching-lenses` 「판단 앞에 기계 검사를 둔다」의 기존 규칙).

분리 규칙의 근거는 선행연구 개발이다. 그 개발은 판정 에이전트를 단계별로 나눴다가 결국 하나로 묶었다(검증자 구성 기록 -1, -4).

## 실측

렌즈 네 개는 모두 반영되는 지적을 냈지만, 반영된 단독 발견 1건당 토큰은 렌즈마다 두 배 넘게 차이 났다.

| 렌즈 | 1회 토큰(중앙값) | 1회 시간(중앙값) | 단독 발견 | 반영률 | 단독 반영률 | 반영된 단독 발견 1건당 토큰(추정) | 문체·표기 비율(추정) |
|---|---|---|---|---|---|---|---|
| adversarial | 115k | 192초 | 249 | 82% | 89% | 약 24k | 약 5% |
| consistency | 132k | 185초 | 202 | 81% | 89% | 약 34k | 약 15% |
| grounding | 132k | 191초 | 178 | 88% | 94% | 약 48k | 약 10% |
| fit | 109k | 131초 | 302 | 63% | 60% | 약 21k(설계 지적만 세면 약 120k) | 약 85% |
| readability | 116k | 236초 | 기록 없음 | 기록 없음 | 기록 없음 | 측정 불가 | — |

렌즈 1회의 도구 호출 수는 세션 기록 기준으로 adversarial 중앙값 10·최댓값 33, consistency 11·26, fit 8·14, grounding 18·48 이었다. fit 원본 json(자기감사 제외)의 `principle` 칸에 가장 많이 적힌 조항은 COUNT-EARNS 98건, ONE-IDEA 67건, SUBJECT-OBJECT 60건, TERM-ONE 55건, INSTRUCTION-FORM 51건이었다.

반영률은 spec·plan 표본 10건(지적 241건)에서 셌다. 1건당 토큰은 세션 기록의 렌즈별 토큰 합을 "단독 발견 × 단독 반영률"로 나눈 값이다. 문체 비율은 렌즈 원본의 `type` 분포와 claim 표본을 읽어 추정했다.

adversarial 과 consistency 는 함께 잡은 지적이 가장 많다(110~162건). 함께 잡은 표본 15건 중 10건은 같은 원인을 잡았다. 그러나 두 렌즈의 서술 방향이 다르다. adversarial 은 실패 결과와 완화안을 적고, consistency 는 상충하는 상대 문서와 행을 적는다. 표본 3건에서는 한쪽만 하위 지적을 냈다.

다시 리뷰는 지적 수를 거의 줄이지 못했다. 2차가 있는 대상 9개를 합치면 2차 지적은 1차의 92% 였고, 3차는 2차의 88% 였다. 2차 지적의 상당수는 1차 반영이 만든 해법의 결함이었다. 지적 수가 줄어든 대상은 새 절만 보거나 렌즈를 줄인 차수뿐이었다.

어느 렌즈도 보지 않은 공백(「커버리지 공백」 절 48건)은 주제가 몇 가지로 모인다.

| 공백 주제 | 기록 수 | 처리 방향 |
|---|---|---|
| 런타임·하네스 동작 실측(SendMessage 재개, worktree 기준 커밋, model 우선순위 등) | 14 | 읽기 전용 렌즈로는 확인할 수 없다. plan 의 첫 작업으로 실측하게 한다 |
| 원문 접근 실패·미대조 | 11 | 렌즈 공백이 아니다. 호출자가 원문을 공급하지 못한 공백이다 |
| 처방의 방향이나 층을 판정할 렌즈가 없음 | 4 | 약한 신설 후보다 |
| 대화 안에만 있는 결정·원본 | 3 | 호출자가 대화 결정을 렌즈 입력에 넣어야 한다 |

사용자가 적대 렌즈를 직접 요청한 사례는 모두 설계 문서 밖이었다.

| 날짜·프로젝트 | 요청 | 정의와의 대조 |
|---|---|---|
| 09-27 quant-structure | 제안서 자료의 부족한 점을 해외 업체 접근과 비교해 찾기 | 외부 비교가 필요하지만 렌즈는 탐색하지 않는다 |
| 10-05 writing-html-reports | 국고채 커브 플랫 투자 주장을 반박하기 | 대상이 설계가 아닌 투자 논증이다 |
| 10-25 claude-mods | 장기 맥락에서 토큰을 아낄 방법 찾기 | 대상이 코드다. 단순화 제안이므로 가드와 충돌하지 않는다 |
| 10-25 claude-mods | 테스트 결과를 보고 다각도로 검토하기 | Claude 가 적대 렌즈를 관점별로 5개 실행했다. 1:N 의 첫 실사용이다 |

## 결정 분기

개편에서 정할 결정은 다섯 분기로 나뉜다. 위 층의 결정이 아래 층의 선택지를 바꾸므로 B1 부터 정한다(`TOP-DOWN`).

**B1 실행 형태.** 현행 방식은 메인 세션이 렌즈 SKILL.md 를 읽은 뒤 그 프롬프트를 general-purpose 서브에이전트에 다시 쓰는 방식이다. 선택지는 현행 유지, 에이전트 정의 1:1, 에이전트 정의 1:N, 스킬의 `context: fork` 와 `agent:` 필드다. `context: fork` 는 공식 문서상 스킬이 특정 에이전트를 실행하는 경로이지만, `agent:` 에 플러그인 에이전트 이름을 쓸 수 있는지는 문서에 없다. 또한 포크된 스킬은 대화 기록을 보지 못하고 기본으로 백그라운드에서 실행된다.

**B2 렌즈 구성.** 선택지는 adversarial·consistency 통합, fit 의 문체 지적 기계화, readability 처분(유지, review-docs 퇴고 단계로 흡수, 렌더링 화면 리뷰로 재정의)이다. grounding·fit 통합은 사용자가 2026-10-05 분리 유지로 정했으므로 다루지 않는다.

**B3 신규 에이전트.** 후보는 주장 반박(WebSearch 필요), 산출물 적대(코드·실험 결과 대상), 렌더링 화면 리뷰(Playwright 필요), 런타임 실측이다.

**B4 구조 통합.** 저장소 구조 지도에서 다음 중복을 찾았다.

- **호출자×렌즈 정의:** 다섯 곳에 흩어져 있다(`dispatching-lenses:67-73`, `:110-112`, `test_docs_drift.sh:284,872`, 호출자 스킬의 렌즈 목록).
- **리뷰 기록 규칙:** `review-specs:100-106` 과 `review-docs:80-82` 에 두 벌로 있다.
- **승인이 필요한 실행 규칙:** readability 의 「필요할 때」 그룹 규칙(`dispatching-lenses:90-100`)과 `agent-prior-art:70-82` 가 같은 구조다.
- **aggregating-lenses:** 「하는 일」은 dispatching-lenses 가 이미 가리키는 다섯 줄이고, 나머지는 계약과 처분이다.

**B5 다시 리뷰 정책.** 선택지는 현행 유지와 "바뀐 절만, 설계를 바꾸는 지적이 남았을 때만"이다. 이 분기는 원칙 `NO-RAW-OUTPUT` 과 `review-specs` 에 닿는다. 원칙 경량화 세션이 같은 조항과 파일을 고칠 예정이다.

S3 의 분리 규칙을 현행 렌즈에 적용하면 결과는 다음과 같다.

| 렌즈 | 대상에 따른 도구·계약 차이 | 결과 |
|---|---|---|
| adversarial | 주장 반박은 WebSearch 가 필요하다. 설계 문서와 코드·실험 결과는 같은 도구(Read·Grep)를 쓴다 | 설계·산출물용 에이전트 하나(대상 모드 둘)와 주장 반박용 에이전트 하나로 나눈다 |
| grounding | 출처가 세 종류(런타임, spec, 문서·감사)로 나뉘지만 도구와 출력 계약이 같다 | 에이전트 하나에 모드를 둔다 |
| consistency | spec·plan 과 감사로 나뉘지만 도구와 출력 계약이 같다 | 에이전트 하나에 모드를 둔다 |
| fit | 대상 타입을 렌즈 안에서 이미 판정한다(`lens-fit:18-20`) | 에이전트 하나로 둔다. 문체 검사 중 결정론으로 답할 수 있는 항목을 기계 검사로 옮긴다 |

## 선행연구 에이전트에서 옮길 교훈

선행연구 에이전트 개발에서 효과가 확인된 장치는 에이전트의 연구 능력보다 후단의 강제 장치였다. 사용자는 10-18 "리서치 자체를 강화한게 아니라 후단을 강화한거"라고 평했다. 렌즈 전환의 이득도 도구 강제, 모델 고정, 출력 계약에서 나온다고 본다(추정).

그대로 쓸 장치는 먼저 frontmatter 의 전체 명시다. 정의마다 `tools`(쓰기 도구와 Agent 제외), `model`, `effort`, `maxTurns` 를 적는다. 검증자 정의에 model 이 없어 Opus 를 물려받았고, 그래서 실사용에서 검증자 42개가 캐시 쓰기 토큰 약 136만을 썼다. 리뷰 모델은 사용자가 2026-10-17 Opus 로 정했다.

description 에는 실행 조건을 가드로 적는다. 선행연구 에이전트는 "이 절차에서만 실행한다"는 문장으로 메인 세션이 다른 대화에서 고르지 않게 했다. 렌즈는 사용자가 직접 실행하기도 하므로 "리뷰 스킬 안에서, 또는 사용자가 이름으로 요청할 때"로 적는다. 출력 스키마는 계약 JSON 한 곳을 원본으로 두고 정의 안의 예시 블록과 테스트로 대조한다. 선행연구에서는 두 워크스트림이 따로 구현해도 형식 불일치가 없었다.

피할 함정의 첫째는 단독 시험이다. 대상별 에이전트를 따로 최적화하면 조립한 구성의 성적을 예측하지 못하고, 선행연구에서는 이 문제로 재측정을 세 번 했다. 그래서 운영 경로 하나로 조립해 측정한다.

둘째는 도달할 수 없는 병합 조건이다. "기준선이 맞힌 항목을 모든 실행에서 맞힌다"는 조건은 실행 사이 변동 때문에 도달할 수 없었다. 병합 조건은 오류 총량을 기준선과 비교하는 대칭 지표로 처음부터 정한다.

셋째는 반복 질문이다. 권장안 그대로 채택된 질문 25건은 대부분 '다음 단계', '다시 리뷰', '승인', '삭제'였다. 이런 질문은 착수 때 진행 규칙으로 한 번 승인받는다.

## 먼저 시험할 런타임 사실

공식 문서에 없는 사실은 구현 전에 시험해야 한다. 선행연구 개발 때 확인한 사실은 다시 시험하지 않는다.

| 사실 | 상태 |
|---|---|
| Agent 도구와 워크플로 agentType 의 플러그인 에이전트 이름 해석 | 10-18 확인했다(prior-art spec:545) |
| Agent 도구로 실행할 때 frontmatter model 적용 | 10-21 확인했다(검증자 구성 기록 -3) |
| `@agent-disciplined-coder:<이름>` 직접 실행 | 문서에 형식이 있다. 이 플러그인에서는 시험하지 않았다 |
| 스킬 `agent:` 필드에 플러그인 에이전트 이름 지정 | 문서에 없다. 시험이 필요하다 |
| 플러그인 에이전트의 `tools` 에 세션 MCP 도구(Playwright) 지정 | 문서에 없다. 플러그인 에이전트는 `mcpServers` 를 무시한다. 렌더링 리뷰 에이전트의 선행 조건이다 |
| 플러그인 에이전트가 사용자 CLAUDE.md 와 @import 를 받는지 | 문서에 없다. 받지 않는다고 놓고 원칙 경로를 프롬프트로 넘긴다 |

## 권장 차례

권장안은 아래 차례로 진행한다. 단계마다 확인 방법을 함께 적었다.

1. 「먼저 시험할 런타임 사실」의 미확인 항목을 `--plugin-dir` 로 적재한 세션에서 시험하고, 결과를 결정 기록에 적는다.
2. B4 구조 통합을 한다. 원칙 경량화 세션이 main 에 병합한 뒤 그 커밋을 기준으로 시작하고, 테스트 전체가 FAIL=0 인지 확인한다.
3. 렌즈 네 개를 에이전트 정의로 바꾸고 출력 계약 JSON 과 대조 테스트를 만든다. 같은 spec 하나에 현행 렌즈와 새 에이전트를 실행해 반영된 단독 발견 수를 비교한다.
4. 주장 반박 에이전트를 만든다. 10-05 투자 주장 사례를 다시 실행해 결과를 사용자가 판정한다.
5. fit 의 문체 검사 중 결정론으로 답할 수 있는 항목을 기계 검사로 옮긴다. 옮긴 뒤 fit 지적 중 문체 비율이 줄었는지 확인한다.
6. B5 다시 리뷰 정책은 원칙 경량화 세션과 조율한 뒤 정한다.

## 사용자가 정할 사항

사용자는 2026-10-25 개편 방향을 S3 와 주장 반박 에이전트 하나로 정했다(선택 도구로 답함). 이 방향 아래에서 다음 결정이 차례로 남는다.

런타임 청사진의 위치는 사용자가 2026-10-25 에이전트 정의가 겸하는 안으로 정했다. `review-llm-calls:7` 은 렌즈를 "제품 코드가 구현할 청사진"으로 정하므로, 앞으로 `agents/lens-*.md` 본문이 원본이 되고 `review-llm-calls` 는 그 본문을 가리킨다. frontmatter 와 원칙 경로 지시는 제품에서 빼라고 적는다. readability 의 처분은 사용자가 2026-10-25 렌더링 리뷰로의 재정의로 정했다. 이 렌즈의 실행 기록은 감사 세 차수(14건)뿐이고 review-docs 검진에서는 한 번도 실행되지 않았다. 그래서 글 검토는 review-docs 의 퇴고 단계로 흡수하고, readability 는 렌더링 화면을 보는 에이전트로 다시 만든다. 런타임 시험에서 플러그인 에이전트가 브라우저 도구를 쓸 수 없으면 글 검토 에이전트로 남긴다.

spec 리뷰 뒤 사용자는 두 가지를 더 정했다(2026-10-25). 레포 문서 감사(`audit-repo-docs`)는 "맥락없이 자가 감사해줘는 접근이 잘못됐다"는 이유로 지우고, 그래서 렌즈 묶기 예외도 함께 지운다. 주장 반박 에이전트의 인용은 메인 세션이 URL 원문에서 구절이 있는지 확인한다. 선행연구 검증자를 범용으로 넓히는 안을 한 번 골랐으나, 검증자 본문과 합치기 절차까지 고쳐야 하고 에이전트를 이어 부르는 구조가 위험하다는 이유로 보류했다.

다시 리뷰 정책은 사용자가 2026-10-25 이번 개편에 넣되 원칙 경량화 세션이 병합된 뒤에 하기로 정했다. 원칙 경량화 세션은 `NO-RAW-OUTPUT` 을 바꾸지 않는다고 답했다. 그래서 이 개편이 "다시 리뷰는 바뀐 절만, 설계를 바꾸는 지적이 남았을 때만 하고, 그 판단은 묻지 않고 기록한다"는 변경안을 클린룸 시험한 뒤 채택 여부를 정한다.
