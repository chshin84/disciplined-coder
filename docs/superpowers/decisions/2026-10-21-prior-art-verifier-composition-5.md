## 병합 조건 판정

새 구성(추출·판정·보충·재판정·지도 대조 Haiku 5.5 high, 상향 판정 Opus 5.5 medium)은 병합 조건 두 가지 중 비용 조건만 채웠다.

| 조건 | 결과 | 값 |
|---|---|---|
| 구성 전체의 `total_cost_usd` 가 기준선보다 낮다 | 충족 | 새 구성 $0.4853·$0.2974, 기준선 $3.3023·$2.9478 |
| 기준선이 두 실행 모두 맞힌 항목은 새 구성도 두 실행 모두 맞힌다 | 미충족 | 비교한 항목·칸 45개 중 4개(`acc-t1`, `dir-t1`, `sco-t3`, `hard-tbl-t1`)를 새 구성이 한 번 이상 틀렸다 |

기준선은 `results-v2/runs.jsonl` 의 두 실행이고, `cases-v3.json` 으로 다시 채점했다. 기준선은 `cases-v2.json` 의 주장으로 실행되었으므로, v3 에서 새로 만든 참 항목(`quo-t4`·`quo-t5`·`quo-t6`·`quo-t7`·`acc-t4`·`hard-f200-t2`)에는 기준선 판정이 없다. 그래서 이 항목들은 병합 조건 비교에서 빠졌다. 라벨을 오류로 고친 `quo-t1`·`quo-t3`·`hard-f200-t1` 은 기준선이 두 실행 모두 통과시켜 틀렸으므로 역시 비교에서 빠졌다.

보충은 실행 1 에서 주장 5개, 실행 2 에서 주장 1개에 실행되었다. 보충 출력은 여섯 주장 모두 추출 기준(접근 성공, 존재 일치, 구절 있음)을 통과했다.

`num-t3` 실행 1 의 재판정은 "크기 변수가 검출되지 않은 네 구조 변수에 속한다는 서술" 이 없다며 방향 칸을 정보 부족으로 냈다. 이 항목은 오류 항목이라 검증 실패도 맞힘으로 센다. `num-t3` 실행 2 는 처음 판정에 정보 부족과 범위 불일치가 함께 있어, 보충 없이 `unsupported` 가 되었다.

Opus 상향은 실행 1 의 `dir-t2` 한 건에만 실행되었다. 처음 판정은 수치·조건 칸을 `조건 얽힘` 판정 불가로 냈고, Opus 5.5 medium 은 세 칸을 모두 일치로 내 최종 판정이 `supported` 였다. `dir-t2` 는 참 항목이지만 기준선이 한 번 틀린 항목이라 병합 조건 비교에서 빠졌다. 실행 2 에는 상향 대상이 없었다. `hard-ctx-t1` 실행 2 는 방향 칸이 판정 불가였으나 범위 칸이 불일치여서 상향 없이 `unsupported` 가 되었다.

## 새로 틀린 항목과 원인

아래 표는 이번 재측정에서 틀렸고 앞 재측정의 같은 실행에서는 맞았던 항목과 실행이다. 원인 칸은 판정 원본의 `reason` 에서 확인한 사실이다.

| 항목(실행) | 최종 판정 | 단계 출력에서 확인한 사실 |
|---|---|---|
| `acc-t1`(2) | unsupported | 처음 판정이 범위를 불일치로 냈다. 사유는 구절의 "In the context of reasoning" 한정을 주장이 뺐다는 문장이다. 결정 기록 4 가 `acc-t1` 실행 1 에서 적은 범위 불일치와 같은 사유다 |
| `dir-t1`(1) | unsupported | 처음 판정이 범위를 불일치로 냈다. 사유는 `context` 의 베이즈 근거 한정(위치 귀무는 기각 실패일 뿐이다)을 주장이 "차이를 내지 않았다" 로 단정했다는 문장이다. 실행 2 도 같은 사유로 틀렸고, 결정 기록 4 가 앞 재측정 실행 2 에서 적은 사유와 같다 |
| `hard-tbl-t1`(2) | verify_failed | 처음 판정은 표 행 구절에 열 머리 100 이 지시 100개를 뜻한다는 설명이 없다며 수치·조건을 정보 부족으로 냈다. 보충은 같은 표 행을 다시 옮기고, 열 머리의 뜻은 요약 도구가 옮긴 본문 문장에서만 읽힌다고 `context` 에 적었다. 재판정도 같은 칸을 정보 부족으로 내 검증 실패가 되었다. 실행 1 은 처음 판정이 세 칸 모두 일치였다 |

`sco-t3` 실행 2 는 앞 재측정 실행 2 에서도 틀렸으나 원인이 바뀌었다. 이번 처음 판정은 방향을 정보 부족으로, 범위를 불일치로 냈다. 범위 사유는 `context` 의 조건(두 TypeScript 코드베이스, 세 모델, 다섯 과제)을 주장이 밝히지 않았다는 문장이다. 불일치가 있어 보충 없이 `unsupported` 가 되었다.

`acc-t1`(2)·`dir-t1`·`sco-t3`(2) 는 모두 범위 칸의 불일치로 틀렸다. 세 건 모두 구절이나 `context` 의 한정을 주장이 뺐다는 사유이며, 결정 기록 4 의 「의역 엄격 판정」과 같은 종류로 보인다(가정). 이 가정은 같은 입력으로 판정 에이전트를 여러 번 실행해 범위 불일치의 빈도를 세면 확인할 수 있다.

## 카테고리별 오류 통과

주장 항목의 오류 통과는 실행 1 에서 0건, 실행 2 에서 1건(`quo-t3`, 구절 카테고리)이었다. 앞 재측정의 새 구성은 같은 정답 자료(`cases-v3.json`)로 채점해도 두 실행 모두 0건이다. 그래서 이번 구성은 앞 재측정보다 오류 통과가 실행 2 에서 1건 늘었다. 지도 대조 칸의 오류 통과는 두 실행 모두 0건이다.

| 카테고리 | 앞 재측정 새 구성(실행 1·2) | 이번 새 구성(실행 1·2) |
|---|---|---|
| 접근 | 0, 0 | 0, 0 |
| 존재 | 0, 0 | 0, 0 |
| 구절 | 0, 0 | 0, 1 |
| 수치·조건 | 0, 0 | 0, 0 |
| 방향 | 0, 0 | 0, 0 |
| 범위 | 0, 0 | 0, 0 |

`quo-t3` 는 Task 1 에서 라벨을 오류로 고친 항목이다. 원문의 완화 표현 "tend to be more effective" 를 주장이 "더 효과적" 으로 단정했다. 두 실행 모두 추출 단계가 같은 `quote` 와 `context` 를 옮겼다. 실행 1 의 판정은 "tend to" 를 단정으로 바꿔 일반화했다며 범위를 불일치로 냈다. 실행 2 의 판정은 "tend to 가 빠졌으나 적용 대상은 넓어지지 않았다" 며 범위를 일치로 냈다. 같은 구절에서 판정이 실행마다 달랐다.

## ref 이름이 정답을 드러내는 한계

시험 자료의 ref 는 항목 id(`acc-t1`, `quo-f1` 같은 것)이고, `-t`·`-f` 가 참·오류를 드러낸다. 판정 에이전트와 상향 판정 에이전트는 입력에서 이 ref 를 본다. 기준선도 같은 ref 로 측정했으므로 비교 대칭을 위해 바꾸지 않았다. ref 이름이 판정에 영향을 주었는지는 측정하지 않았다(가정). ref 를 정답과 무관한 이름으로 바꾼 자료로 같은 단계를 다시 실행해 판정을 비교하면 확인할 수 있다.

## 실행 조건과 비용

- 실행 조건은 결정 기록 3 의 run.py 실행과 같다. `build_cmd` 의 플래그(`--setting-sources "" --strict-mcp-config --disable-slash-commands --no-session-persistence`)를 붙였고, 실행 폴더는 `D:/dc-eval-tmp` 아래이며, 자식 환경에서 `CLAUDE_CODE_EFFORT_LEVEL` 을 지웠다.
- 각 `-def` 단계는 같은 차례의 앞 단계 출력 중, 앞 단계의 입력과 정의로 다시 계산한 key 가 같은 줄만 썼다(`run.def_output`).
- 실행 줄은 추출 34개, 판정 26개, 보충 4개, 재판정 4개, 상향 판정 1개, 지도 대조 2개로 모두 71개다. 오류 줄·시간 초과·모델 불일치는 없었다. 판정 줄이 차례마다 13개인 이유는 URL 17개 중 4개에서 추출을 통과한 주장이 없었기 때문이다.
- 이번 재측정의 전체 비용은 $0.7827 이다. 그중 Opus 상향 판정 한 건이 $0.1491 이었다. 기준선은 앞 재측정의 실행을 다시 채점했으므로 새 비용이 없다.
