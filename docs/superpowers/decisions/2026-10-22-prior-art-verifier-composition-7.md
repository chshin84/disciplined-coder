# 선행연구 검증자 구성 결정 기록 7(2026-10-22)

이 파일은 기록 타입이다. 앞 기록 `2026-10-21-prior-art-verifier-composition.md`·`-2.md`~`-6.md` 를 고치지 않고, Opus 묶음 판정 구성의 재측정 결과를 여기 남긴다. 절차는 `docs/superpowers/plans/2026-10-22-prior-art-verifier-batch-judge.md` 의 Task 2 이고, 원자료와 보고는 `evals/prior-art-verifier/results-v4/` 에 있다(`report.md` 가 집계 결과다). 이 기록은 결정을 적지 않으며, 다음 설계는 사용자가 정한다.

## 병합 조건 판정

새 구성(추출·보충·지도 대조 Haiku 5.5 high, 판정·재판정 Opus 5.5 medium 묶음 호출)은 병합 조건 두 가지 중 비용 조건만 채웠다.

| 조건 | 결과 | 값 |
|---|---|---|
| 구성 전체의 `total_cost_usd` 가 기준선보다 낮다 | 충족 | 새 구성 $1.0468·$0.9614, 기준선 $3.3023·$2.9478 |
| 기준선이 두 실행 모두 맞힌 항목은 새 구성도 두 실행 모두 맞힌다 | 미충족 | 비교한 항목·칸 45개 중 4개(`acc-t1`, `exi-t1`, `dir-t1`, `sco-t1`)를 새 구성이 한 번 이상 틀렸다 |

기준선은 `results-v2/runs.jsonl` 의 두 실행이고, `cases-v3.json` 으로 다시 채점했다. 비교에서 빠진 항목·칸 13개는 결정 기록 5 와 같다.

판정·재판정 입력의 ref 는 이번 새 구성에서만 정답이 드러나지 않는 번호(`c1`, `c2` …)로 바꿨다. 기준선(`results-v2/runs.jsonl`)과 앞 재측정(`results-v3/`)은 항목 id(`acc-t1`, `quo-f1` 같은 것)를 ref 로 실행했다. 그래서 ref 조건이 기준선·앞 재측정과 이번 측정 사이에서 다르다. 추출·보충 입력의 ref 는 이번에도 항목 id 다.

| `dir-t1` | 참 | unsupported, unsupported | verify_failed, supported | 실행 1 이 틀렸고 실행 2 는 맞혔다 |

`acc-t1`(2)와 `dir-t2`(2)는 앞 재측정과 같은 사유로 틀렸다. 처음 판정이 범위를 불일치로 냈고, 사유는 구절의 "In the context of reasoning" 한정을 주장이 뺐다는 문장이다. 두 항목 모두 실행 2 의 추출이 이 한정을 포함한 초록 문장을 구절로 옮겼다. 실행 1 의 추출은 한정이 없는 짧은 구절을 옮겼고, 판정은 세 칸 모두 일치였다.

## 새로 틀린 항목과 원인

아래 표는 이번에 틀렸고 앞 재측정의 같은 실행에서는 맞았던 항목과 실행이다. 원인 칸은 판정 원본의 `reason` 과 판정 입력에서 확인한 사실이다.

| 항목(실행) | 정답 | 앞 재측정 | 이번 최종 판정 | 병합 조건 비교 | 단계 출력에서 확인한 사실 |
|---|---|---|---|---|---|
| `exi-t1`(2) | 참 | supported | unsupported | 대상 | 실행 2 의 추출이 논문 제목 대신 `acc-t1` 과 같은 초록 문장("In the context of reasoning, ... struggle to self-correct ... without external feedback")을 구절로 옮겼다. 처음 판정은 범위를 불일치로 냈다. 사유는 구절의 'struggle to' 와 'without external feedback' 조건을 주장이 빼고 '교정하지 못한다' 로 넓혔다는 문장이다. 실행 1 의 구절은 제목("Large Language Models Cannot Self-Correct Reasoning Yet")이었고 세 칸 모두 일치였다 |
| `sco-t1`(1) | 참 | supported | unsupported | 대상 | 실행 1 의 구절은 "than previous GPT models" 였다. 처음 판정은 주장의 '이전 OpenAI 모델' 이 GPT 계열 밖의 모델까지 넓혔다며 수치·조건과 범위를 불일치로 냈다. 실행 2 의 구절은 "than its predecessors" 였고 세 칸 모두 일치였다 |
| `num-t3`(1) | 오류 | verify_failed | supported(오류 통과) | 빠짐(기준선이 두 실행 모두 틀렸다) | 처음 판정이 세 칸 모두 일치로 냈다. 사유에 "같은 URL 의 다른 context 에 'Size ... nulls' 가 있으므로 크기가 그 변수에 든다" 는 문장이 있다. 이 구절은 `num-t3` 자신의 `context` 에 없고, 같은 묶음의 같은 URL 원소에 든 `dir-t1` 의 `context` 에 있다 |
| `num-t3`(2) | 오류 | unsupported | supported(오류 통과) | 빠짐 | 처음 판정이 세 칸 모두 일치로 냈다. 실행 2 의 `context` 는 "after multiple-testing correction" 을 포함한 문장을 옮겼고, 판정은 주장에 그 조건이 빠진 점을 사유에 적지 않았다 |
| `hard-ctx-t1`(1) | 참 | supported | unsupported(판정 불가 기각) | 빠짐(기준선이 두 실행 모두 틀렸다) | 처음 판정이 세 칸 모두 정보 부족이었다. 보충 뒤 재판정은 범위를 `언어 해석` 판정 불가로 냈고, 워크플로가 이 주장을 기각했다. 앞 재측정에서는 Opus 상향 판정이 supported 를 냈다 |

`dir-t1`(1)은 앞 재측정에서도 틀렸으나 원인이 바뀌었다. 실행 1 의 처음 구절에 "after multiple-testing correction" 이 없어 처음 판정이 수치·조건을 정보 부족으로 냈다. 보충은 그 조건을 포함한 구절을 옮겼다. 그러나 재판정은 "Claude Code 세션이라는 적용 조건이 구절과 맥락에 없다" 며 수치·조건을 다시 정보 부족으로 내 검증 실패가 되었다.

병합 조건 비교 대상인 네 항목(`acc-t1`(2), `exi-t1`(2), `dir-t1`(1), `sco-t1`(1))은 모두 실행마다 추출 구절이 달랐다. 그리고 한정이나 조건이 더 많은 구절을 받은 실행에서 틀렸다. 추출 구절의 실행 간 차이가 판정 결과를 바꾼 원인으로 보인다(가정). 이 가정은 같은 추출 출력을 고정하고 판정만 여러 번 실행해, 구절별 판정이 실행마다 같은지 보면 확인할 수 있다.

## URL 사이의 구절 섞임

판정·재판정 출력의 `reason` 에서 따옴표로 인용한 영문 구절 64개를 그 주장의 `text`·`quote`·`context`·`source_note` 와 대조했다. 57개는 그 주장의 입력에 그대로 있었다. 다른 URL 의 입력에만 있는 구절은 없었다. 나머지 7개는 줄임표로 줄인 인용(`'Cannot ... Yet'`, `'Size ... nulls'` 등), 마크다운 링크와 백틱을 뺀 인용, 동사형을 바꾼 인용이었다.

그중 `num-t3`(1)의 `'Size ... nulls'` 는 같은 URL 의 다른 주장(`dir-t1`)의 `context` 에서 온 구절이다. 판정 정의는 "주장마다 그 주장과 같은 `items` 원소의 구절·맥락만 보고 판정하라" 고 적는다. 그래서 이 섞임은 URL 사이가 아닌 같은 URL 안의 주장 사이에서 일어났다. 이 판정이 오류 항목 `num-t3` 을 통과시켰다.

## 카테고리별 오류 통과

주장 항목의 오류 통과는 실행 1·2 에서 각각 1건(`num-t3`, 수치·조건 카테고리)이었다. 앞 재측정의 새 구성은 같은 정답 자료로 채점해 0건·1건(`quo-t3`)이고, 기준선은 4건·4건이다. 지도 대조 칸의 오류 통과는 두 실행 모두 0건이다.

| 카테고리 | 기준선(실행 1·2) | 앞 재측정 새 구성(실행 1·2) | 이번 새 구성(실행 1·2) |
|---|---|---|---|
| 접근 | 1, 1 | 0, 0 | 0, 0 |
| 존재 | 0, 0 | 0, 0 | 0, 0 |
| 구절 | 2, 2 | 0, 1 | 0, 0 |
| 수치·조건 | 1, 1 | 0, 0 | 1, 1 |
| 방향 | 0, 0 | 0, 0 | 0, 0 |
| 범위 | 0, 0 | 0, 0 | 0, 0 |

`num-t3` 은 결정 기록 2 에서 라벨을 오류로 고친 항목이고, 기준선도 두 실행 모두 통과시켰다. 결정 기록 5 의 「ref 이름이 정답을 드러내는 한계」 절은 ref 이름(`-t`·`-f`)이 판정에 영향을 주었는지 측정하지 않았다고 적었다. 이번 측정은 판정 입력의 ref 를 중립 번호로 바꿨고, 앞 재측정에서 기각된 `num-t3` 이 두 실행 모두 통과했다. 다만 판정 모델과 묶음 입력도 함께 바뀌었으므로, 이 차이가 ref 이름 때문인지는 확인하지 않았다(가정). 같은 판정 모델과 입력으로 ref 만 바꿔 실행하면 확인할 수 있다.

## 판정 누락, 판정 불가 기각, 틀리게 확신함

- 판정 누락은 두 실행의 판정 묶음·재판정 묶음 모두 0건이었다. 출력에서 버린 판정(입력에 없던 URL·ref, 같은 주장의 중복 판정)도 0건이었다.
- 판정 불가로 기각한 주장은 실행 1 에서 참 항목 1건(`hard-ctx-t1`, 재판정 범위 `언어 해석`), 실행 2 에서 0건이었다. 오류 항목은 두 실행 모두 0건이다. 처음 판정에는 판정 불가가 없었다.
- 처음 판정의 틀리게 확신함은 실행 1 에서 2건(`num-t3`, `sco-t1`), 실행 2 에서 4건(`acc-t1`, `exi-t1`, `num-t3`, `dir-t2`)이었다. 최종 판정을 정한 판정으로 세도 같다.
- 보충은 실행 1 에서 2건(`dir-t1`, `hard-ctx-t1`), 실행 2 에서 2건(`acc-t3`, `hard-ctx-t1`)에 실행되었다. 판정한 주장 대비 비율은 5.4%·5.6% 이다. 보충 출력은 네 건 모두 추출 기준을 통과했다. 재판정 결과는 `acc-t3` supported(맞힘), `dir-t1` 정보 부족으로 검증 실패(틀림), `hard-ctx-t1` 실행 1 판정 불가 기각·실행 2 범위 불일치(둘 다 틀림)였다.

## 묶음 크기와 출력 토큰

묶음은 워크플로 `batchClaims` 와 같은 규칙(크기 20)으로 만들었다. 판정 묶음은 실행마다 둘이었고, 재판정 묶음은 실행마다 하나였다.

| 단계 | 실행 | 묶음 | URL 수 | 주장 수 | 출력 토큰 | 비용(USD) |
|---|---|---|---|---|---|---|
| 판정 | 1 | batch:1 | 6 | 20 | 7,936 | 0.3471 |
| 판정 | 1 | batch:2 | 7 | 17 | 6,479 | 0.3165 |
| 재판정 | 1 | batch:1 | 2 | 2 | 2,070 | 0.1610 |
| 판정 | 2 | batch:1 | 5 | 18 | 5,456 | 0.2881 |
| 판정 | 2 | batch:2 | 8 | 18 | 6,237 | 0.3191 |
| 재판정 | 2 | batch:1 | 2 | 2 | 1,339 | 0.1435 |

출력 토큰은 `usage.output_tokens`(생각 포함)다. 판정 묶음의 출력은 주장 하나에 약 300~400 토큰이었다. spec 「Opus 일괄 판정」 은 주장 하나에 약 700 토큰, 20개에 약 1.4만 토큰을 가정했다. 측정한 묶음은 주장 20개·출력 7,936 토큰이 최대다. 그보다 큰 묶음(운영에서 생길 수 있는 묶음 셋 이상의 실행, 한 URL 에 주장이 20개를 넘는 묶음)은 이 측정의 범위 밖이다.

## 비용과 spec 의 가정

spec 「Opus 일괄 판정」 은 판정을 실행 한 번에 약 $0.8, 재판정과 추출을 포함해 약 $1.2 로 가정했다. 측정값은 아래와 같다.

| 항목 | spec 의 가정 | 실행 1 | 실행 2 |
|---|---|---|---|
| 판정 묶음 합계 | 약 $0.8 | $0.6636 | $0.6072 |
| 재판정 묶음 | 가정에 따로 적지 않음 | $0.1610 | $0.1435 |
| 구성 전체(추출·판정·보충·재판정·지도 대조) | 약 $1.2 | $1.0468 | $0.9614 |

재판정 묶음은 주장 2개에 $0.14~0.16 이었다. spec 이 계산한 호출마다의 고정 입력 비용(약 $0.15)과 같은 크기다. 이번 재측정의 결과 파일 전체 비용은 $2.0081 이다(오류 줄과 다시 실행한 줄은 없다). 기준선은 앞 재측정의 실행을 다시 채점했으므로 새 비용이 없다.

## 실행 조건과 오류

- 실행 조건은 결정 기록 5 와 같다. `build_cmd` 의 플래그(`--setting-sources "" --strict-mcp-config --disable-slash-commands --no-session-persistence`)를 붙였고, 실행 폴더는 `D:/dc-eval-tmp` 아래이며, 자식 환경에서 `CLAUDE_CODE_EFFORT_LEVEL` 을 지웠다. CLI 버전은 2.1.308 이다(plan 은 2.1.305 를 적었다).
- 각 단계는 같은 차례의 앞 단계 출력을 `run.UPSTREAM` 의 단계별 설정 줄 중 key 가 같은 줄에서 골랐다(`run.pipeline`).
- 실행 줄은 추출 34개, 판정 묶음 4개, 보충 4개, 재판정 묶음 2개, 지도 대조 2개로 모두 46개다. 오류로 끝난 시도는 일괄 호출을 포함해 0건이었고, 다시 실행한 줄도 없다. 출력 잘림도 없었다.
