# 에이전트 호출 정책 검토

이 기록은 에이전트가 다른 에이전트를 부르는 일을 어떻게 제한할지 정하기 위한 검토다. 선행연구 개선 세션(c6)이 2026-10-25 그쪽 사용자 지시로 "상위 에이전트로 규정된 것만 에이전트를 호출할 수 있다"는 정책을 제안했다. 사용자는 같은 날 하위 에이전트를 지정할지 상위 에이전트를 지정할지 판단을 요청했다.

## 확인한 사실

아래 사실은 공식 문서(code.claude.com/docs/en/sub-agents)와 이 저장소에서 확인했다.

| 사실 | 출처 |
|---|---|
| 서브에이전트는 기본으로 자기 서브에이전트를 실행할 수 있고, 메인 대화 아래 3층까지 내려간다. 한도는 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 가 정한다 | 공식 문서 「Spawning subagents」 |
| 정의의 `tools` 를 생략하면 쓸 수 있는 도구를 모두 물려받고, 그 안에 Agent 도구도 든다. `tools` 허용 목록이나 `disallowedTools` 로 막을 수 있다 | 공식 문서 |
| `Agent(agent_type)` 로 부를 수 있는 종류를 제한하는 구문은 `claude --agent` 로 메인 스레드에서 시작한 에이전트에만 적용된다 | 공식 문서 |
| frontmatter 의 모르는 필드는 경고 없이 무시된다 | 공식 문서 |
| 플러그인의 에이전트 정의는 `agents/prior-art-*.md` 네 개뿐이고, 네 개 모두 tools 에 Agent 가 없다 | 저장소 |
| 선행연구의 단계 사이는 메인 세션이 실행한 워크플로 스크립트가 잇는다. 플러그인 안에 다른 에이전트를 부르는 에이전트 정의는 없다 | `workflows/prior-art-search.js`, `skills/agent-prior-art/SKILL.md` |
| 현행 렌즈는 general-purpose 로 실행되므로 Agent 도구를 물려받는다. 렌즈를 막는 장치는 프롬프트의 "서브에이전트를 새로 열지 마라" 지시뿐이다 | `skills/dispatching-lenses/SKILL.md` 「한 번만 실행하는 렌즈의 규율」 |

## 시나리오

검토한 시나리오는 상위 지정, 하위 지정, 전면 금지, 깊이 한도 설정이다.

| 시나리오 | 규칙 | 장점 | 단점 |
|---|---|---|---|
| A 상위 지정(허용 목록) | 오케스트레이터로 선언한 정의만 tools 에 Agent 를 둔다. 나머지 정의는 Agent 없는 tools 를 반드시 둔다 | 기본이 금지라서 새 정의를 만들 때 선언을 잊어도 안전한 쪽으로 실패한다. 부를 수 있는 정의가 목록으로 보인다 | 선언 방식(필드나 표지)을 새로 정해야 한다. frontmatter 의 모르는 필드는 무시되므로 검사 스크립트가 표지를 읽어야 한다 |
| B 하위 지정(금지 목록) | 하위로 선언한 정의만 Agent 를 막는다. 나머지는 기본 허용이다 | 지금 정의 네 개에 선언만 추가하면 된다 | 기본이 허용이라서 선언을 잊은 새 정의와 tools 를 생략한 정의가 Agent 를 물려받는다. 실패가 위험한 쪽으로 난다 |
| C 전면 금지 | 플러그인의 모든 에이전트 정의는 Agent 없는 tools 를 둔다. 에이전트를 부르는 주체는 메인 세션과 워크플로 스크립트뿐이다 | 선언 방식이 필요 없다. 지금 구조(오케스트레이션은 스킬과 워크플로가 맡는다)와 같다 | 나중에 오케스트레이터 에이전트가 필요해지면 규칙을 고쳐야 한다 |
| D 깊이 한도 | 사용자 설정의 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 를 1로 둔다 | general-purpose 를 포함한 모든 서브에이전트의 중첩을 하네스가 막는다 | 플러그인이 사용자 설정을 바꿔야 하고, 사용자가 다른 작업에서 쓰는 중첩까지 막는다 |

A 와 C 는 같은 규칙이다. C 는 A 의 허용 목록이 비어 있는 형태다. 차이는 선언 방식을 지금 정하는지뿐이다.

## 판단

사용자는 2026-10-25 정책의 목적을 "사전에 정의된 호출만 허용하고, 에이전트가 임의로 다른 에이전트를 호출하는 일을 금지한다"로 정했다. 선행연구 에이전트는 메인 세션이 연구 계획을 사용자에게 승인받은 뒤 워크플로 스크립트가 정해진 정의를 차례로 실행하는 구조다. 따라서 이 목적 안의 호출이다. 서브에이전트 안에서는 실행할 에이전트 종류를 제한할 수 없다(위 「확인한 사실」의 `Agent(agent_type)` 행). 그래서 사전 정의 호출은 호출 목록이 고정된 스킬 절차와 워크플로 스크립트로만 만들고, 정의 파일에는 Agent 를 두지 않는다. 이 장치가 시나리오 C 와 같다. 정책 이름은 "사전 정의 호출만 허용"으로 한다.

계획을 세우는 오케스트레이터는 메인 세션의 스킬과 워크플로 스크립트로 만든다. 에이전트 정의가 그 일을 맡아야 하는 상황이 처음 생기면 A 의 선언 방식을 검토한다. 지금 플러그인에는 다른 에이전트를 불러야 하는 정의가 없으므로, 선언 방식을 미리 만들면 쓰지 않는 장치가 된다(`YAGNI`). 선행연구 개선 세션(c6)도 같은 날 메시지로 다음 사실을 확인해 주었다. 그 브랜치(HEAD 4c9ef93)의 정의 네 개에는 Agent 가 없고, 그런 정의를 만들 계획도 없다. `workflows/prior-art-search.js` 의 agent() 호출 여덟 곳은 모두 agentType 을 준다.

B 를 기각하는 이유는 기본값의 방향이다. 아래 검사를 B 에도 붙이면 tools 생략 문제는 같이 사라진다. 그래도 B 에서는 하위로 선언하지 않은 정의가 tools 에 Agent 를 적어도 통과하고, A·C 에서는 실패한다. 하위 지정이 나은 구성은 대부분의 정의가 다른 에이전트를 불러야 하는 구성이고, 지금은 그런 정의가 하나도 없다.

D 를 기각하는 이유는 플러그인이 사용자 설정 파일을 고쳐야 한다는 점이다. 그 값은 이 플러그인과 무관한 작업의 중첩에도 적용된다. 사용자가 다른 작업에서 중첩을 쓰는지는 확인한 근거가 없으므로, D 는 사용자가 원할 때 직접 켜는 설정으로 남긴다.

에이전트 정의가 오케스트레이터를 맡아야 하면 그 세션은 진행을 멈추고 선언 방식을 사용자에게 설계 결정으로 묻는다. 검사에 예외 한 줄을 넣거나 tools 에 Agent 를 적는 방법으로 대신하지 않는다.

검사는 아래 항목을 확인한다.

- `agents/` 아래 모든 정의의 frontmatter 에 한 줄 쉼표 목록 형식의 `tools:` 줄이 있다. tools 생략과 YAML 배열 형식은 위반으로 본다.
- 그 목록에 `Agent`, `Agent(...)`, 옛 이름 `Task` 가 없다.
- `workflows/` 아래 스크립트의 `agent()` 호출이 모두 `agentType` 을 준다. agentType 을 빼면 기본 에이전트가 실행되고, 그 에이전트가 Agent 를 물려받는다고 가정했다(공식 Workflow 문서의 agent() 기본 종류로 확인한다).

2026-10-25 구현 Task 3 에서 Workflow 작성 참고서(`workflow-authoring` 스킬)를 확인했다. 그 문서는 agentType 이 "the default workflow subagent" 대신 사용자 정의 종류를 쓰게 한다고 적고, 워크플로 에이전트가 세션의 MCP 도구에 ToolSearch 로 닿는다고 적는다. 기본 에이전트가 Agent 도구를 받는지는 적지 않는다. 그래서 이 가정은 확인되지 않은 채 남았다. 검사 비용이 작고 지금 호출이 모두 agentType 을 주므로 셋째 검사는 그대로 둔다.

선행연구 정의 네 개는 `scripts/test_docs_drift.sh` 가 이미 tools 줄을 구성값과 정확히 대조한다. 그 검사는 구성값을 지키는 검사라 그대로 두고, 새 검사는 정확 대조가 없는 정의(렌즈 정의와 앞으로의 정의)까지 덮는 일반 규칙으로 둔다.

## 유의사항

이 규칙은 플러그인이 정의한 에이전트에만 적용된다. 메인 세션이 tools 를 정하지 않은 general-purpose 를 실행하면 그 서브에이전트는 Agent 를 받으므로 중첩이 생길 수 있고, 이 경로는 정책을 따른 뒤에도 남는다. Explore 와 Plan 은 하네스가 Agent 를 빼 두어 이 공백에 들지 않는다. 남는 경로를 줄이려고, 플러그인 스킬이 서브에이전트를 실행할 때는 플러그인 정의나 Explore 처럼 Agent 없는 종류를 쓰라고 지시한다. 렌즈는 렌즈 전환 spec 의 7단계(스킬 삭제) 이후에 이 공백에서 빠지고, 그전까지는 general-purpose 로 실행된다.

`nested-orchestration` 의 서브 세션은 서브에이전트가 아니라 별도 Claude 세션이므로 이 규칙과 무관하다.

넘겨받기(한 에이전트의 출력을 다른 에이전트의 입력으로 쓰는 일)는 메인 세션이나 워크플로 스크립트가 사이에 선다. C 에서는 에이전트가 다른 에이전트를 부르지 못하므로, 넘겨받기는 구조상 항상 메인 세션이나 스크립트를 거친다.

규칙을 둘 곳은 `domain-plugin` 스킬과 검사 스크립트다. 에이전트원칙에 두면 모든 프로젝트 세션에 실리고 조항별 클린룸 시험이 필요하다. 이 배치의 효과는 이 플러그인을 개발하는 세션과 배포된 정의 파일에만 미친다. 다른 프로젝트의 `.claude/agents` 와 다른 플러그인의 에이전트에는 효과가 없다.

적대 렌즈 검토 결과는 `docs/superpowers/reviews/2026-10-25-agent-call-policy-review/lens-adversarial-1.json` 에 있고, 지적 8건을 모두 이 문서에 반영했다.
