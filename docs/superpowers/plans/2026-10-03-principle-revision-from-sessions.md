# 세션 기록 기반 원칙 퇴고 — 계획

설계는 `docs/superpowers/specs/2026-10-03-principle-revision-from-sessions-design.md` 다. 이 계획은 설계의 절차를
실행 단위로 나눈다.

사용자 발화를 담은 작업 파일은 저장소 밖의 고정 폴더 `~/.claude/dc-principle-revision/`(아래 작업 폴더)에 둔다.
세션 스크래치 폴더는 세션마다 경로가 바뀌어 재개할 수 없기 때문이다. 작업 폴더는 커밋하지 않는다. 이 계획과
설계와 리뷰 기록은 작업 5의 커밋에 함께 넣는다.

## 작업

1. **발화 추출:** 작업 폴더의 `extract.py` 로 `~/.claude/projects/*/*.jsonl` 에서 사용자 발화를 뽑아
   `utterances.json` 에 쓴다. 직접 입력한 발화, 작업 도중 보낸 발화(`queued_command` 첨부), 선택 도구의 답을
   담는다. 도구 결과, 태그로 시작하는 시스템 글, 압축 요약, 서브에이전트 대화, 클린룸 시험이 만든 임시 세션
   (폴더 이름에 `-Temp-` 가 든 세션)은 뺀다. 확인 방법은 무작위 표본 20건을 원문 jsonl 과 대조해 오삽입이 없는지
   보고, 작업 도중 보낸 발화가 들어 있는지 이 세션의 기록으로 보는 방식이다.
2. **행동 지시 선별과 묶기:** 발화를 읽어 행동 지시가 든 발화만 고르고, 같은 뜻끼리 묶는다. 묶음마다 요지와
   나온 세션 수를 작업 폴더의 `groups.md` 에 적는다. 확인 방법은 모든 묶음에 요지와 세션 수가 있는지 보는 방식이다.
3. **대조와 처분:** 묶음마다 원칙 조항, 참고서 근거 절과 「삭제한 조항」, 메모리 feedback 파일과 대조해 설계의
   처분 표대로 처분을 `groups.md` 의 그 묶음에 적는다. 확인 방법은 모든 묶음에 처분이 있고 반영됨 묶음에 조항
   ID 가 있는지 보는 방식이다.
4. **대조 보고:** 보고 대상 처분의 묶음과 조항 후보 목록을 사용자에게 대화로 보고한다. 보고 대상 처분은 삭제
   이력 있음, 맥락, 일회성이다. 일회성 중 조항 후보로 올릴 묶음과 메모리에 쓸 맥락을 묻고, 답을 `groups.md` 의
   처분 칸에 적는다. 확인 방법은 보고 대상 묶음이 모두 보고에 실렸고 사용자 답이 `groups.md` 에 적혔는지 보는 방식이다.
5. **퇴고 기준 반영과 승인:** 설계 「퇴고 기준」 표의 기준과 처분이 퇴고 기준인 묶음을 저장소 `CLAUDE.md`
   「에이전트원칙을 고칠 때」 절에 추가한다. 같은 절의 「조항 추가와 문구 변경」 항목도 설계의 시험 조건(현행 문안
   조건, 동점이면 과제 추가)에 맞춘다. 새 기준은 설계 「퇴고 기준」 표에 행으로 넣고, 근거 발화의 요지는 설계
   「발화에서 찾은 퇴고 기준」 절에 적는다. 그다음 `CLAUDE.md` 의 바뀐 부분을 사용자에게 보이고 승인을 받는다.
   작업 6의 판정이 이 기준을 쓰므로 묶음 끝까지 미루지 않는다. 확인 방법은 저장소 `CLAUDE.md` 「변경 뒤 실행」의
   검사 스크립트 전체 통과, `claude plugin validate ./` 통과, 사용자 승인이다. 커밋 하나로 만든다.
6. **기존 조항 퇴고:** 설계 「조항 퇴고」 표의 조항을 표 순서대로 처리하고, 출력지시 머리말은 표의 마지막
   조항 뒤에 처리한다. 조항마다 설계의 문안, 시험, 판정, 확인, 반영, 커밋 단계를 밟는다. 판정이 삭제 후보이면
   그 자리에서 사용자에게 묻고, 승인되면 원칙에서 조항을 지우고 근거를 참고서 「삭제한 조항」 절로 옮긴다.
   확인 방법은 조항마다 참고서 측정 기록과 커밋이 있는지 보는 방식이다.
7. **조항 후보 처리:** 작업 4에서 확정한 조항 후보를 작업 6과 같은 단계로 하나씩 처리한다. 후보 목록은
   `groups.md` 에 두고 이 계획을 고치지 않는다. 확인 방법은 `groups.md` 의 조항 후보마다 채택이나 기각의 결과와
   커밋이 있는지 보는 방식이다.
8. **메모리 갱신:** 작업 4에서 사용자가 고른 맥락을 이 PC의 Claude 메모리 파일로 쓰고 `MEMORY.md` 에 한 줄을 더한다.
   확인 방법은 고른 맥락마다 메모리 파일과 `MEMORY.md` 의 줄이 있는지 보는 방식이다.
9. **묶음 승인과 푸시:** 조항별 결과와 퇴고 기준 커밋을 한 번에 보고한다. 이어서 `git diff origin/main..` 전체와
   커밋 메시지를 보이고, 사내 식별자와 개인정보가 없는지 확인받는다. 거부된 조항은 커밋을 revert 하지 않고, 그
   조항의 현행 문안을 되살리는 새 커밋으로 처리한다. 참고서의 측정 기록은 남기고 거부 사유를 더한다. 그다음
   「변경 뒤 실행」의 검사 스크립트 전체와 `claude plugin validate ./` 를 실행하고 푸시한다. 확인 방법은 원격
   `main` 이 로컬과 같은지 보는 방식이다.
10. **kw-plugins 알림:** 푸시된 커밋 중 참고서 근거 절이나 원칙 조항 문구를 고친 커밋을 메시지로 알린다. 받을
    쪽은 kw-plugins 를 맡은 세션이다. 그 세션이 없으면 알리지 못했다고 보고한다. 확인 방법은 메시지를 보냈거나
    보내지 못한 사실을 보고에 적었는지 보는 방식이다.

## 순서

작업 1부터 5까지는 차례로 실행한다. 작업 6은 작업 5의 승인 뒤에 시작하고, 작업 7과 작업 8은 작업 4의 답을 받은
뒤 시작한다. 작업 9는 작업 6, 7, 8을 마친 뒤 실행하고, 작업 10은 푸시 뒤에 실행한다.

## 커밋 규칙

조항 커밋의 메시지 첫 줄은 조항 ID 로 시작한다. 재개할 때 `git log origin/main..` 에서 끝난 조항을 조항 ID 로
가려내기 위해서다. 한 조항의 편집을 커밋하기 전에 세션이 끊기면, 재개한 세션은 `git status` 로 미완료 편집을 찾아
되돌리고 그 조항을 처음부터 다시 처리한다.

## 조항 하나의 시험 규격

과제는 그 조항이 다루는 행동이 드러나는 지어낸 예시로 3개를 만들고, 세션 발화와 사내 식별자를 넣지 않는다.
판정에서 위반이 같으면 같은 규칙으로 과제 2개를 더 만든다.

조건은 빈 모델, 현행 문안, 새 문안이고, 조항 후보는 빈 모델과 새 문안만 둔다. 문안 조건에는 "다음은 글을 쓸 때
지킬 지시다" 뒤에 그 조항 한 줄만 싣는다.

실행은 Explore 서브에이전트로 조건마다 1회씩 하며, 도구를 쓰지 말고 답하라고 지시해 동시에 실행한다. 채점은
과제마다 조항 위반 수와 지켜야 할 내용의 손실을 세어 작업 폴더의 `score-<이름>.md` 에 적는다. 이름은 조항 ID 이고,
출력지시 머리말은 `output-header` 다.
