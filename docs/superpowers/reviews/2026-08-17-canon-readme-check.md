# 정본과 README — 문서 검진 기록

검진 대상 둘: `agent-principles.md`(디시플린 정본), `README.md`.

렌즈 넷을 읽기 전용 서브에이전트로 띄웠다. `reviewer-grounding`과 `reviewer-fit`은 두 문서를 함께
받아 한 번씩 돌았고, `reviewer-readability`는 문서마다 목적이 달라 각각 한 번씩 돌아 모두 두 번
돌았다. 네 리턴 모두 `principles_applied`가 비어 있지 않았고, 가독성 렌즈 둘 다 `purpose`가 채워져
있어 판정으로 썼다.

가독성 렌즈는 원래 참조물에 자동으로 걸지 않는다. 정본에 건 것은 사용자가 명시로 요청했기
때문이며, 그 근거는 "정본이 가끔 안 먹히고 대화가 길어질수록 소실되는 느낌이 있다"였다. 그 느낌은
측정값이 아니므로 어디를 볼지 정하는 데만 쓰고 판정 근거로는 쓰지 않았다.

렌즈에 준 목적은 이렇다.

- **정본** — 대화가 길어진 뒤에도 일하고 있는 에이전트가, 지금 하려는 일에 걸리는 원칙을 스스로
  떠올려 그대로 적용하게 한다.
- **README** — 이 플러그인을 처음 보는 Claude Code 사용자가, 이게 자기 문제를 푸는지를 훑어서
  판단하고, 그대로 따라 설치해 셋업이 됐는지까지 스스로 확인하게 한다.

지적은 스물일곱 건이 나왔다(근거 여섯, 계약 열, README 가독성 일곱, 정본 가독성 넷). 메인 세션이
원문과 코드를 열어 전부 대조했고 반려한 것은 없다. **스물둘을 고쳤고, 셋은 일부만 고쳤으며, 둘은
넘겼다.**

## 코드까지 고친 것 둘 (사용자가 정했다)

문서만 좁힐지 코드를 고칠지가 갈림길이라 사용자에게 물었고, 코드를 고치는 쪽으로 정해졌다.

| 무엇이 문제였나 | 어떻게 고쳤나 |
|---|---|
| README가 "손대기 전에 사본을 먼저 뜬다"고 적었는데, 관리블록을 걷어내는 경로에는 사본이 없었다. 걷어내기는 마커 사이를 통째로 버리므로 사람이 그 안에 끼워 넣은 줄도 함께 사라지고, 그 파일은 git 밖일 수 있어 복구 수단이 없었다 | `managed_block_remove`가 사본 경로를 인자로 받아 직접 뜨고, 못 뜨면 아예 걷어내지 않게 했다(리턴 2). 호출자는 사유를 갈라 알린다. 사본은 프로젝트가 아니라 전역 백업에 쌓는다 |
| 머리말을 못 고친 사유가 셋(경계를 못 찾음·사본을 못 뜸·파일을 못 씀)인데 모두 같은 `refused`로 뭉개져, 언제나 "머리말의 끝을 알아볼 수 없다"고만 알렸다. 홈에 쓰기가 막힌 PC에서는 머리말이 멀쩡한데도 그 신호가 매 세션 뜨고 끄는 수단이 없다 | `solved_fix_reason`을 두어 셋을 가리고, 사유마다 사람이 할 일이 다른 안내를 낸다. 정본과 README의 그 문장도 "사유를 가려 알린다"로 맞췄다 |

계약 테스트를 여섯 더했다(사본이 남는지, 사본을 못 뜨면 안 걷어내는지, 사유를 가려 알리는지).
고치기 전에 먼저 돌려 여섯이 실패하는 것을 확인했다.

## 일부만 고친 것 셋

- **`surface한다`를 정본에 남겼다.** `PLAIN-KO`로 보면 이것도 지어낸 표현이고 '알린다'라는 한국어가
  이미 있다. 그런데 `domain-docs`·`domain-spec-review`·`nested-orchestration` 셋이 오답노트 절의
  그 문구를 그대로 인용하고 있어, 정본만 바꾸면 인용하는 쪽이 어긋난다. 처분 목록 안에서는 한국어로
  바꾸고 첫 자리에 뜻을 한 줄 달아 두었으며, 전체를 바꿀지는 사용자에게 넘긴다.
- **README의 독자 분리를 끝까지 하지 않았다.** 매니페스트 검사 설명은 「주의」로 옮겼지만, 파일별
  주석이 달린 「구성」 트리는 그대로 두었다. 사용자가 이번 범위를 문장과 절 순서까지로 정했다.
- **정본 가독성 렌즈가 짚은 굵기 손질을 오답노트 절에만 적용했다.** 다른 절의 굵기는 그 절만큼
  몰려 있지 않아 이번에는 두었다.

## 넘긴 것 둘

- **`CLEAR-COMM`이 자신을 '소통의 뿌리'라 하고 넷이 그것을 이어받는다고 적은 것.** 계약 렌즈는
  `NO-PRIORITY`와 부딪힌다고 보았다. 사용자가 그대로 두기로 정했다 — 우열을 말한 것이 아니라 넷이
  각각 무엇을 다루는지 갈라 놓은 것이라는 판단이다.
- **「절차」 절이 "언제·무엇만 둔다"고 선언해 놓고 오답노트 절이 형식 규칙의 '어떻게'를 스무 줄
  적는 것.** 같은 내용이 `domain-docs`에도 있어 한쪽만 고치면 갈라진다(`SSOT`). 상시 로드 분량을
  줄이는 효과도 있으나, 정본에서 내용을 덜어 내는 결정이라 사용자에게 물어야 한다.

## 검진이 확인해 준 것

근거 렌즈가 대조해 일치를 확인한 것들이 있다. README 「구성」 트리의 모든 경로가 실재하고,
마켓플레이스 이름과 두 설치 명령, `DISCIPLINED_CODER_REVIEW_GATE=off` 환경변수 이름, spec 리뷰
마커 계약, 훅 배선, 커맨드 셋, 두 매니페스트의 라이선스와 version 비대칭이 모두 코드와 맞았다.
정본이 "상세는 이 스킬이 SSOT"라고 가리킨 자리도 실제로 채워져 있었다.

## 반영 뒤 상태

계약 테스트 넷이 전부 통과한다(PASS 448, FAIL 0). 새로 더한 여섯을 포함한 값이다. 플러그인 검증도
통과한다(version 미지정 경고 하나는 의도된 트레이드오프다).

정본이 11,095자에서 11,995자로 900자 늘었다. 진입로 표를 더한 값이라, 떠올리기 쉬워진 대신 매 세션
실어 보내는 양이 늘었다. 사용자가 말한 "길어질수록 소실된다"와 반대 방향의 대가이므로 적어 둔다.
