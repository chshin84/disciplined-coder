# 선행연구 대조 — 레포 전체 점검에 LLM 호출부 코드 검사를 더하는 착상

- 회차 날짜: 2026-08-30
- 렌즈: `reviewer-prior-art` 두 갈래(승인된 상한은 「통상 둘」이며 그 안에 담았다)
- 검토 대상: 문서 통합 감사의 대상을 LLM 호출부 코드로 넓히는 착상과 그 CI·CD 배치
- 처분 규칙: 이 렌즈의 발견은 호출자가 전부 🔴로 처분한다(`domain-spec-review`가 SSOT). 자동 반영하지 않는다.

## 이 회차의 기계 검사

- 이 레포에는 이미 CI가 있다(`.github/workflows/ci.yml`). 트리거는 `push: [main]`과 `pull_request` 둘이고,
  도는 것은 `scripts/test_*.sh` 전부와 `claude plugin validate ./`로 모두 결정론적이다. LLM을 부르는 검사는 없다.
- 이 레포의 파일 구성은 마크다운 148개와 셸 21개다. **LLM 호출부가 하나도 없다.**
  그러므로 이 착상이 검사할 대상은 이 레포가 아니라 이 플러그인을 깐 다른 레포다.

## 갈래 하나 — 검사 메커니즘 자체의 선행 사례

`search_status`는 `ok`이고, 실제로 열어 확인한 주소는 여섯이다.

### 알려진 실패의 전이 — 정적 탐지의 재현율을 아무도 재지 않았다

가장 가까운 선행 사례는 ICSE 2026 NIER 논문 「Specification and Detection of LLM Code Smells」와
그 도구 SpecDetect4LLM이다(arXiv 2512.18020). 이 도구는 정적 규칙으로 LLM 호출부를 훑어 다섯 가지를
찾는데, 그 가운데 UMM(Unbounded Max Metrics)이 이 착상의 timeout·재시도 상한·토큰 상한 요건과 같다.

네 축 대조에서 목적과 메커니즘은 같고 평가와 응용 영역이 다르다. 논문은 공개 파이썬 저장소 200개를
대상으로 한 유행성 연구이고 학술적 정밀도만 쟀으나, 이 착상은 한 레포를 되풀이해 감사하는 운영
도구이며 사용자에게 넘길 감사 결과의 실효성을 요구한다.

결말은 성공도 실패도 아닌 판정 유보다. 정밀도는 평균 86.06퍼센트(스멜별 80~95.65퍼센트)로 측정했으나
**재현율은 "완전한 정답 집합을 만드는 것이 범위 밖"이라며 측정하지 않았고**, 정적 분석의 한계로 동적
디스패치와 문맥 기반 분석을 지원하지 못한다고 스스로 밝혔다. 공개 저장소의 채택 지표도 미미하다.

이대로 두면 이 착상도 같은 자리에서 무너진다. 래퍼 함수나 팩토리나 서브클래스를 거쳐 만들어지는 실제
SDK 호출을 놓치는데, 무엇을 놓쳤는지 모르는 채로 결과를 넘기면 통과한 코드에도 요건 미비가 남아 있는
것을 감사가 보증하는 것처럼 읽힌다.

- 근거: https://arxiv.org/html/2512.18020 (preprint, 열어 확인함)
- 근거: https://github.com/Brahim-Mahmoudi/SpecDetect4LLM_ICSE (저자 저장소, 열어 확인함)

### 붐빔 — 비밀 탐지는 이미 표준 도구가 있다

"키가 코드에 박혀 있는지" 보는 항목은 LLM과 무관하게 성숙한 시크릿 스캐너가 표준으로 자리잡은
영역이다. Gitleaks는 스타 29,000개 이상이고 GitHub Actions와 커밋 전 훅과 도커로 CI에 흔히 통합된다.
네 축 가운데 목적과 메커니즘과 평가가 같고 응용 영역만 이 착상보다 넓다.

새로 지으면 이미 정규식과 엔트로피로 검증된 도구보다 오탐률이 나쁠 가능성이 크고, 새 키 형식마다
규칙을 더하는 유지보수 부담만 떠안는다.

- 근거: https://github.com/gitleaks/gitleaks (vendor, 열어 확인함)

### 비교되지 않은 기준선 — 중앙에서 강제하는 방식

호출부마다 요건이 있는지 훑어 찾는 대신, SDK 클라이언트를 한 곳에서 감싸 기본값을 강제하거나
게이트웨이나 프록시를 앞단에 두어 애플리케이션 코드를 고치지 않고도 중앙에서 timeout과 재시도와
요율을 강제하는 방식이 이미 실무에서 쓰인다. 이 착상은 그 대안과 비교되지 않았다.

이 유형은 비교를 요구하되 구현을 요구하지 않는다 — 무엇을 만들라는 지시는 여기 적지 않는다.

- 근거: https://docs.litellm.ai/docs/proxy/load_balancing (vendor, 열어 확인함)

### 찾지 못한 것 (독창성의 근거가 아니다)

- 이 스코프를 표방하며 널리 채택된 상용 제품은 찾지 못했다. llm-seclint(스타 2개, alpha 0.1.0)와
  PromptLint는 채택 지표를 확인하지 못했고 timeout·재시도·None 가드·로깅 규칙이 명시적으로 없었다.
  따라서 이 세부 스코프에는 붐빔 판정이 성립하지 않는 것으로 보이나 확언할 근거는 못 찾았다.
- LLM 기반 코드 리뷰 제품이 "LLM 호출부의 timeout·재시도 누락"을 실제로 탐지하는지는 비교 블로그의
  스니펫만 봤고 각 제품의 방법론 문서와 룰 목록은 열지 못했다.

### 리뷰어의 불확실성

- SpecDetect4LLM의 재현율은 논문 자신이 측정하지 않았으므로, 실패 원인의 전이가 이 착상에서 얼마나
  심각할지는 추정이며 측정값이 아니다(reviewer-derived).
- `domain-llm-runtime`의 요건 목록과 SpecDetect4LLM의 다섯 스멜은 부분만 겹친다. None 가드와 계측
  로깅과 비밀 노출은 선행 사례에 없고, 선행 사례의 세 스멜은 이 레포 요건에 없다.

### 얕게 본 대목 (리뷰어 자기 보고)

상용 SAST가 LLM 호출부 전용 룰을 갖췄는지, LLM 기반 코드 리뷰 제품이 이 체크리스트를 실제로 탐지하는지
둘 다 원문 문서를 열지 못했다. 실패 원인의 전이는 논문의 자기 진술에 의존했고 실제 코드에 적용해
재현하지는 않았다.

## 갈래 둘 — CI·CD 배치 시점의 선행 사례

`search_status`는 `ok`이고, 실제로 열어 확인한 주소는 열이다.

### 붐빔 — 게이트 3단 구조는 이미 표준이다

결정론 검사를 먼저 걸고 판정이 필요한 것만 리뷰로 넘기는 배치는 정적 보안 분석 진영에서 이미
세 지점으로 표준화되어 있다. 커밋 전 훅과 풀 리퀘스트 스캔과 주 브랜치 야간 스캔이 그 셋이다.
새 코드에 집중하는 상용 분석 도구도 개발 환경과 풀 리퀘스트와 브랜치 세 단계를 두고 "이슈를
도입되는 즉시 고친다"를 근거로 든다. 백지에서 설계하면 이 구조를 다시 발명하게 된다.

- 근거: https://www.jit.io/resources/app-security/integrating-sast-into-your-cicd-pipeline-a-step-by-step-guide (vendor, 열어 확인함)
- 근거: https://docs.sonarsource.com/sonarqube-cloud/standards/about-new-code (vendor, 열어 확인함)
- 근거: https://docs.coderabbit.ai/reference/glossary (vendor, 열어 확인함)

### 알려진 실패의 전이 — 비결정 검사를 차단 게이트로 쓰면 격리된다

같은 입력에 다른 결과를 내는 검사를 필수 통과 조건으로 걸면 정당한 변경이 반복해서 막힌다.
LLM을 요구사항 적합성 판정자로 쓸 때 정상 코드를 비적합으로 판정하는 체계적 과잉교정이 보고되어
있고, 그 논문은 차단 게이트가 아니라 보조 신호로 쓰라고 권한다. 비결정으로 실패하며 다른 사람의
작업을 막는 검사에 대한 실무의 대응은 격리다 — 필수 체크에서 빼고 소유자와 기한을 붙여 추적한다.
결정론으로 잴 수 있는 것은 결정론 검사로 두고 언어 이해가 필요한 주관적 판단만 LLM 판정에 맡기라는
권고도 같은 방향이다.

이 착상은 기계 검사를 먼저 돌리기로 정했으나, **남은 것을 맡은 렌즈의 판정을 차단으로 쓸지 조언으로
쓸지는 아직 정하지 않았다.** 차단으로 쓰면 개발자가 그 게이트를 우회하는 습관이 붙어 게이트 전체의
신뢰가 무너진다.

- 근거: https://arxiv.org/pdf/2603.00539 (preprint, 열어 확인함)
- 근거: https://mergify.com/learn/test-quarantine (vendor, 열어 확인함)
- 근거: https://www.braintrust.dev/articles/what-is-llm-as-a-judge (vendor, 열어 확인함)

### 반박된 전제 — 배포 게이트는 런타임 지표만 본다

착상은 "critical 요건 누락이면 배포 차단"이 성립하는지 물었다. 확립된 배포 게이트 관행은 그 자리를
정적 코드 품질이 아니라 **런타임 지표로만 채운다** — 카나리아의 오류율과 지연과 포화도를 안정
베이스라인과 대조한다. 정적 분석 통합 지점을 다룬 가이드도 커밋 전과 풀 리퀘스트와 주 브랜치 셋만
들고 배포 시점은 그 목록에 없다.

배포 직전에 정적 검사를 다시 걸면 풀 리퀘스트에서 이미 걸렸어야 할 것을 중복으로 거는 셈이고,
비결정 검사가 정당한 변경을 막는 실패가 두 자리에서 겹친다. 정작 배포 게이트가 잡아야 할 런타임
문제를 놓칠 위험도 함께 커진다.

- 근거: https://quality.arc42.org/approaches/canary-deployment (blog, 열어 확인함)
- 근거: https://www.jit.io/resources/app-security/integrating-sast-into-your-cicd-pipeline-a-step-by-step-guide (vendor, 열어 확인함)

### 비교되지 않은 기준선 — 증분과 전수의 절충은 이미 문서화되어 있다

새로 들어온 결함만 막는 방식과 전수 훑기의 절충은 이미 근거와 함께 적혀 있다. 새 코드와 전체 코드의
등급을 나눠 보여주며 새 코드에 집중하라는 권고가 있고, 대형 코드베이스에는 증분이나 병렬 스캔을
쓰라는 권고도 있다. 견주지 않고 고르면 알려진 절충을 처음부터 다시 겪는다.

- 근거: https://docs.sonarsource.com/sonarqube-cloud/standards/about-new-code (vendor, 열어 확인함)

### 비교되지 않은 기준선 — 사람이 부르는 것과 자동으로 도는 것은 상호배타가 아니다

착상은 사람이 부를 때만 도는 절차로 둘지 CI에 걸지를 둘 중 하나로 놓았다. 감사 도구 비교 자료는
지속적 자동 감사와 주기적 사람 검토를 **표준 조합**으로 제시하며 각 주기가 필요한 이유를 든다 —
자동은 넓게 빠르게 훑고, 사람은 맥락과 의도가 필요한 깊은 것을 잡는다. 둘 중 하나를 고르는 물음으로
놓으면 이 조합 자체를 검토하지 못하고 넘어간다.

- 근거: https://www.wiz.io/academy/application-security/code-auditing (vendor, 열어 확인함)

### 찾지 못한 것 (독창성의 근거가 아니다)

- 코드 품질 검사나 LLM 검사를 배포 직전 게이트로 두었다가 실패한 구체적 사건 보고는 못 찾았다.
  배포 게이트의 표준 관행이 런타임 지표 중심이라는 정황 근거는 있으나 실패 사례 자체는 확인하지 못했다.
- 문서 감사와 LLM 호출부 코드 감사를 한 파이프라인에서 병행하는 구조와 네 축이 모두 같은 선행 사례는
  못 찾았다. 개별 요소는 각각 선행 사례가 있으나 그 조합 전체를 다룬 단일 사례는 없다.

### 리뷰어의 불확실성

- 열지 못한 문서가 하나 있어(403) 거기 언급된 표준 문서의 계층형 방어 서술은 근거로 세우지 않았다.
- 배포 성능 연구 자료는 "빠른 검사는 머지 전, 느린 검사는 머지 후"라는 일반 원칙만 확인했고 검사
  종류별 배치 기준까지는 명시하지 않아 다른 자료로 보강했다.
- 배포 게이트 축은 문서 하나에만 의존해 두께가 얇다.

## 두 갈래에 걸친 뿌리

세 갈래 지적이 같은 자리를 가리킨다. **결정론으로 잴 수 있는 것과 판단이 필요한 것을 가르지 않은 채
한 검사로 묶은 것**이 그 자리다. 정적 탐지의 재현율을 모른다는 지적도, 비결정 검사를 차단으로 쓰면
격리된다는 지적도, 증분과 전수를 못 고른다는 지적도 그 하나에서 갈라져 나온다. 무엇을 결정론으로
확정하고 무엇을 조언으로 남길지 먼저 정하면 세 지적이 함께 사라진다.

## 사용자가 정할 물음 (🔴 — 이 렌즈의 발견은 전부 사용자 결정이다)

1. LLM 렌즈의 판정을 머지 차단으로 쓸지, 조언으로만 남길지.
2. 배포 직전 게이트를 둘지 말지(선행 사례는 두지 말라고 한다).
3. 정적 탐지가 놓치는 호출부를 어떻게 다룰지 — 재현율을 모른다고 밝히고 넘길지, 아니면 중앙에서
   강제하는 방식과 견줄지.
4. 이 절차를 이 레포 CI에 넣을지, 사용자 프로젝트에 심을 것으로 만들지.

## 사용자가 내린 결정 (2026-08-30)

위 🔴 물음 가운데 셋을 사용자가 정했다. 남은 하나는 선행 사례의 권고를 그대로 따른다.

- **게이트 성격** — 결정론 검사만 머지를 막고, LLM 렌즈 판정은 조언으로만 남긴다. 신뢰가 쌓이면
  되돌릴 수 있는 방식으로 차단으로 옮기는 길을 열어 둔다(`REVERSIBLE`).
- **적용 대상** — 이 레포 CI에 넣지 않는다. 이 플러그인을 깐 사용자 프로젝트에 심을 절차와 CI 조각을
  내놓는다. 이 레포에는 LLM 호출부가 없어 여기서 돌려도 잴 것이 없다.
- **놓침 처리** — 정적 훑기가 래퍼와 팩토리를 거친 호출을 놓칠 수 있다는 것을 결과 보고서에 명시한다.
  통과가 요건 충족을 뜻하지 않는다고 적는다.
- **배포 직전 게이트** — 두지 않는다. 선행 사례가 그 자리를 런타임 지표로만 채우라고 하고, 사용자가
  이 항목을 뒤집지 않았다.

## 배치의 정리 (2026-08-30, 사용자 확인)

**추가 체크리스트는 스킬이 아니라 `domain-llm-runtime`의 청사진으로 구현한다.** CI 러너에는 사람이 앉은
세션이 없고, 검사는 코드 안에서 돌아야 한다. `domain-llm-runtime`이 이미 "리뷰어는 Claude Code
에이전트가 아니라 제품 코드가 구현할 청사진이다"라고 정해 두었으므로 그 문장이 그대로 이 자리에 걸린다.

여기에 되먹임이 하나 있다. **이 검사 자체가 LLM을 부르는 코드이므로, 이 검사도 자기가 검사하는 그
비기능 체크리스트를 지켜야 한다** — 타임아웃과 백오프와 토큰 상한과 비밀 금지가 검사 코드에도 걸린다.
지키지 않으면 자가당착이다.

배치는 이렇게 굳는다.

| 시점 | 도는 것 | 성격 |
|---|---|---|
| 풀 리퀘스트 | 결정론 검사가 바뀐 파일을 본다. | 실패하면 머지를 막는다. |
| 풀 리퀘스트나 머지 후(미결) | LLM 체크리스트가 판단이 필요한 것을 본다. | 막지 않고 보고서만 남긴다. |
| 야간 일괄 | 전수 훑기가 레포 전체를 본다. | 막지 않고 보고서만 남긴다. |
| 배포(CD) | 배포 자체와 배포 뒤 건강 확인이 돈다. | 코드 품질 검사를 걸지 않는다. |

**미결이 하나 남았다** — LLM 체크리스트를 풀 리퀘스트에 붙일지 머지 후로 미룰지다. 풀 리퀘스트에
붙이면 글쓴이가 바로 읽지만 풀 리퀘스트마다 값이 든다. 머지 후로 미루면 값이 줄지만 글쓴이가 그
보고서를 안 본다.
