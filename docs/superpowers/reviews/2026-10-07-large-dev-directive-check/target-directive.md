# 큰 개발의 명세 분할 지시문

superpowers 의 브레인스토밍 → 명세 → 계획 → 구현 흐름을 따른다. 개발이 명세 하나에 담기에 너무 크면 큰 명세를 절로 나누고, 절마다 서브에이전트가 그 흐름을 진행한다. 서브에이전트 실행 규약은 nested-orchestration 을 따른다.

## 나눌지 판단

메인 세션은 브레인스토밍으로 전체 요구를 정리한 뒤 명세 하나로 다룰 수 있는지 판단한다. 다룰 수 있으면 메인 세션이 superpowers 흐름을 직접 진행한다. 한 명세에 독립된 하위 시스템이 여럿 섞이거나 한 세션이 전체 코드와 결정을 다 들고 있을 수 없으면 절로 나눈다. 나누기 전에 사용자에게 근거를 보이고 승인받는다. 작은 개발을 나누면 인계 비용이 이득보다 크다.

## 메인 세션의 역할

절로 나누면 메인 세션은 감독만 한다. 브레인스토밍, 큰 명세와 계약 코드 작성, 서브에이전트 입력 준비와 실행, 질문 전달, 계약 변경 판정, 절별 통합 확인, 사용자 보고를 맡고, 절의 명세·계획·구현 코드는 직접 쓰지 않는다.

이 구조의 근거는 엇갈린다. 단위마다 새 맥락으로 작업하는 방식은 긴 개발에서 효과가 보고되었지만, 부분 정보만 받은 작업자는 통합에서 실패하기 쉽다. 그래서 아래 「인계」와 「측정」을 반드시 지킨다.

## 큰 명세

메인 세션은 큰 명세에 아래를 적고 사용자 승인을 받는다. 절 내부 설계는 적지 않는다.

- 절 목록과 절마다 맡는 일
- 절 사이 계약: 주고받는 자료의 이름, 형식, 단위, 호출 방향
- 의존 순서: 다른 절의 산출물이 있어야 시작할 수 있는 절
- 공통 제약: 모든 절이 지킬 규칙
- 통합 확인 방법: 전체를 합쳤을 때 무엇을 실행해 어떤 결과가 나오면 완료인지

메인 세션은 절 사이 계약을 스텁, 타입, 계약 테스트 코드로 먼저 만들어 커밋한다. 산문으로만 적은 계약은 통합에서 어긋난다.

## 인계

메인 세션은 결정 기록 파일 하나를 두고, 명명 관례, 오류 처리, 공용 유틸리티처럼 절마다 따로 정하면 충돌하는 결정을 적는다. 절이 끝날 때마다 그 절에서 확정된 결정, 바뀐 계약, 실제로 만든 공개 인터페이스를 이 파일에 추가한다.

절마다 서브에이전트에 주는 입력은 아래와 같다.

- 큰 명세 경로와 맡은 절
- 결정 기록 파일 경로
- 배경지식: 관련 코드 경로, 기존 문서, 선행연구, 브레인스토밍에서 사용자가 정한 사항
- 추가 제약: 수정할 수 있는 파일 범위, 하지 말아야 할 일, 따라야 할 사용자 원칙 파일 경로
- 진행 방법: superpowers 의 브레인스토밍 → 명세 작성 → 명세 검토 → 계획 → 구현을 이 절 범위에서 진행한다

## 진행 규칙

- **질문:** 서브에이전트는 사용자에게 직접 묻지 못한다. 확인이 필요하면 보고의 「질문」 절에 적고 멈춘다. 메인 세션이 사용자에게 하나씩 묻고, 답을 같은 서브에이전트에 이어서 전달한다(SendMessage 로 재개).
- **범위:** 서브에이전트는 맡은 절의 책임만 명세하고 구현한다. 범위 밖 아이디어는 「제안」 절에 적고, 메인 세션이 모아 사용자에게 보인다.
- **명세 분량:** 절 명세에는 그 절의 책임과 계약을 구현하는 데 필요한 내용만 적고, 일어날 수 없는 예외 사례를 늘어놓지 않는다. 사용자가 직접 검토하는 문서는 큰 명세와 계약으로 한정하고, 절 명세는 검토 서브에이전트와 메인 세션이 검토한다.
- **검토 범위:** 명세와 코드 검토 서브에이전트에게 지적 범위를 정확성, 명시된 요구, 계약 위반으로 한정하게 한다. 절 명세를 검토할 때는 큰 명세와 결정 기록을 짝 문서로 함께 준다. 검토자에게 기존 결론이나 기대하는 답은 적지 않는다.
- **계약 변경:** 서브에이전트는 절 사이 계약이나 큰 명세를 바꾸지 않고, 바꿔야 하면 멈추고 보고한다. 메인 세션은 영향받는 절을 정리해 사용자에게 기각, 다음 개발로 미룸, 지금 채택 중 하나를 고르게 하고, 채택하면 큰 명세와 계약 코드를 고친 뒤 영향받는 절에 전달한다.
- **강제:** 수정할 수 있는 파일 범위는 지시문에만 두지 않고 nested-orchestration 의 소유권 검사로 강제한다.
- **실행 순서:** 의존 순서가 없고 수정 파일 범위가 겹치지 않는 절만 동시에 진행하고, 나머지는 차례로 진행한다.

## 통합

메인 세션은 절의 구현이 끝날 때마다 계약 테스트와 통합 확인 방법을 실행한다. 앞 절의 오류가 뒤 절의 전제가 되지 않도록, 다음 절은 이 확인을 통과한 뒤에 시작한다. 실패하면 원인이 계약이면 큰 명세로, 절 내부면 해당 서브에이전트로 되돌린다. 확인 명령의 실제 출력을 보기 전에는 완료로 보고하지 않는다.

## 측정

메인 세션은 절로 나눈 개발마다 아래를 기록하고, 개발이 끝나면 사용자에게 보고한다. 이 기록으로 나누는 기준과 감독 구조를 다음 개발에서 다시 정한다.

- 통합 실패 횟수와 원인(계약 누락, 결정 충돌, 절 내부 결함)
- 서브에이전트가 보낸 질문 수(인계 정보가 부족했다는 신호)
- 검토 지적의 채택 수와 기각 수
- 절별 토큰 사용량

## 문서 보관

큰 명세, 결정 기록, 절별 명세와 계획, 검토 기록, 측정 기록은 저장소에 보존한다. 지우기 전에는 사용자 확인을 받는다. 세션이 끊기면 재개하는 세션은 이 문서들과 커밋으로 진행 위치를 판정한다.
