# managing-docs — 문서의 타입·수명·위치

각 조항의 근거는 디시플린코더 저장소 `docs/domain-discipline.md`에서 조항 ID로 찾는다. 사람이 읽을 문서의 제목과 마크다운 초안 규칙은 같은 폴더의 `references/reading-docs.md`에 있다.

## 문서 관리

- **`DOC-TYPE`** — 문서를 쓰거나 고치기 전에 아래 표에서 타입을 정하라. 이어서 진행 상태가 포함되는지, 핸드오프인지, 코드와 인프라에서 도출할 수 있는지 차례로 확인하라. 도출할 수 있는 값은 문서에 적지 말고 원본인 코드와 인프라를 가리켜라. 문서를 수명에 맞게 관리하기 위해서다.
- **`DOC-PLACE`** — 늘 적용하는 규칙은 `CLAUDE.md`에 두고 `@import`로 연결하라. 필요할 때만 여는 규칙은 스킬로 만들고, 특정 경로에만 쓰는 규칙은 rules에 두어라. 필요한 시점에만 규칙을 싣기 위해서다.

새 파일을 만들기 전에 기존 문서에 넣을 수 있는지 먼저 확인하라. 문서가 늘수록 관리할 대상이 많아져 쉽게 낡는다.

### 문서 타입과 수명

타입별 보관 방법을 무엇으로 강제할지는 프로젝트마다 정한다. 기록 파일의 이름과 차수 표기는 아래 「기록 파일 이름 규칙」에 있다. spec과 plan 작성법은 superpowers가 소유하며, 이 표에는 수명과 표시 규칙만 적었다.

| 타입 | 포함 내용 | 노후 방지 방법 |
|---|---|---|
| **상태** (roadmap) | 진행 상태와 다음 단계 | 가능하면 도출하라. 도출하지 못하면 한 곳에만 적고 나머지에서는 링크하라 |
| **절차·계약** (operations·setup·contract) | 수행 방법과 스키마 계약 | 상태는 빼고 방법만 적어라 |
| **설계** (spec·plan) | 설계 근거 | spec은 배포 뒤에도 지우지 말고, 대체된 spec에는 superseded를 표시하라. plan은 실행을 마쳐 병합한 뒤 git 보존 태그를 달고 지워라. 과거 문서는 보존만 하고 활용하지 마라 |
| **기록** (reviews) | 렌즈 실행 차수의 관찰과 지적 | 남긴 기록은 수정하지 마라. 다룬 작업이 병합되면 git 보존 태그를 달고 지우되, 차수 대조에 쓰는 최근 기록은 남겨라 |
| **핸드오프** (HANDOFF-*) | 1회성 인계 | 소비되면 곧바로 지워라 |
| **맥락** (Claude 메모리) | 세션 간 결정과 맥락 | 해당 PC에만 저장된다. 코드와 상충하면 코드를 따르라. 이슈나 백로그 관리에는 쓰지 마라 |
| **규범·인덱스** (CLAUDE.md·문서 맵) | 문서 위치와 작업 방법 | 포인터와 규칙만 적고 상태는 빼라 |

### 기록 파일 이름 규칙

이 규칙은 여기가 소유한다. 문서 검진, spec·plan 리뷰, 워크플로 검증 모두 이 규칙을 따른다.

기록 파일 경로는 `docs/superpowers/reviews/YYYY-MM-DD-<주제>-<종류>.md` 하나로 통일하라. 종류에는 spec·plan 리뷰면 `review`, 문서 검진과 워크플로 검증이면 `check`, 선행연구 대조면 `prior-art`를 넣어라.

이 저장소 밖의 프로젝트에서 전달 문서를 검진할 때는 그 프로젝트 폴더 대신 `~/.claude/disciplined-coder/reviews/` 아래에 같은 이름으로 남겨라. 함께 쓰는 폴더에 주장과 내부 수치가 남지 않게 하기 위해서다.

같은 날 같은 주제의 두 번째 차수부터는 종류 뒤에 차수를 붙여라(`-review-2.md`·`-check-2.md`). 앞 차수 파일을 덮어쓰거나 이어 붙이지 마라.

렌즈별 원본은 요약문과 이름이 같은 폴더에 `<에이전트 이름>-<순번>.json`(예: `lens-grounding-1.json`)으로 저장하라. 순번은 그 차수에서 같은 렌즈가 검토한 대상의 차례다. 대상마다 렌즈를 한 번만 실행하므로 대상이 하나면 항상 1이고, spec과 plan을 함께 보면 1과 2가 된다. 어느 대상을 검토했는지는 원본의 `target` 칸에 적는다.

에이전트 이름을 그대로 쓰므로 `lens-` 접두사를 빼지 마라. 이 규칙 이전에 남긴 기록은 이름이 달라도 고치지 마라.

`prior-art` 원본에는 위 규칙 대신 아래 표의 이름을 써라. `r<n>`은 실행 차례로, 둘러보기가 0, 첫 탐색이 1, 공백 라운드가 2다. 인용 판정 출력은 URL별 판정 배열이며, 각 판정에 그 URL을 인용한 하위 질문 ID를 적는다.

| 원본 | 이름 |
|---|---|
| 워크플로 반환값 | `search-r<n>.json` |
| 탐색 모드 연구자 출력 | `researcher-<하위 질문 ID>-r<n>.json` |
| 둘러보기 워크플로 반환값 | `search-r0.json` |
| 둘러보기 연구자 출력 | `researcher-scout-r0.json` |
| 인용 판정 출력 | `verifier-r<n>.json` |
| 종합 모드 연구자 출력 | `synthesis-r<n>.json` |

## 상황별로 더 읽을 파일

- 사용자가 읽거나 남에게 전달할 문서(보고서·제안서·발표자료·README·.html·.pptx·.docx·.hwp(x), 파일로 쓰는 작업 보고)를 쓰거나 고칠 때는 같은 폴더의 `references/reading-docs.md`를 읽고 따르라. 사용자가 고객·외부에 보낸다고 한 문서를 완성하면, 완료를 보고하기 전에 `lens-review`의 전달 문서 절차로 검진하라.
- README를 쓰거나 고칠 때는 `domain-readme`도 열어라.
- 플러그인·훅·사용자 설정 파일을 고칠 때는 `domain-plugin`을 열어라.
- 두 글을 좌우로 비교하는 페이지나 사용자 판독용 페이지를 만들 때는 `side-by-side`를 열어라.
