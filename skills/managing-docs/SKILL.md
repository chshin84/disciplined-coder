# managing-docs — 문서의 타입·수명·위치

조항 근거는 디시플린코더 저장소의 `docs/domain-discipline.md`에 조항 ID로 적혀 있다. 사람이 읽을 문서의 제목 규칙과 마크다운 초안 규칙은 같은 폴더 `references/reading-docs.md`에 있다.

## 문서 관리

- **`DOC-TYPE`** — 문서 수명에 맞게 관리하려면 문서를 만들거나 고치기 전에 아래 표에서 타입을 정하라. 이어서 진행 상태가 들어 있는지, 핸드오프인지, 코드와 인프라에서 도출할 수 있는지 차례로 확인하라. 도출할 수 있는 값은 문서에 옮기지 말고 원본인 코드와 인프라를 가리켜라.
- **`DOC-PLACE`** — 규칙이 필요할 때만 실리게 하려면 항상 필요한 규칙은 `CLAUDE.md`에 두고 `@import`로 불러오라. 필요할 때만 여는 규칙은 스킬로 만들고, 특정 경로에만 적용할 규칙은 rules에 둬라.

문서를 새로 만들기 전에 기존 문서에 넣을 수 있는지 먼저 확인하라. 문서를 늘리면 관리 대상이 많아져 쉽게 낡는다.

### 문서 타입과 수명

타입별 보관 방법을 강제할 수단은 프로젝트가 정한다. 기록 파일의 이름과 차수 표기는 아래 「기록 파일 이름 규칙」에 따른다. spec과 plan 작성법은 superpowers가 소유하며, 이 표는 수명과 표시 규칙만 정한다.

| 타입 | 적는 내용 | 노후 방지 방법 |
|---|---|---|
| **상태** (roadmap) | 진행 상태와 다음 단계 | 가능하면 도출하라. 못 하면 한 곳에만 적고 나머지에서는 링크하라 |
| **절차·계약** (operations·setup·contract) | 수행 방법과 스키마 계약 | 상태는 빼고 방법만 적어라 |
| **설계** (spec·plan) | 설계 근거 | 배포가 끝난 spec도 지우지 말고, 대체된 spec에는 superseded를 표시하라. plan은 실행 후 병합되면 git 보존 태그를 단 뒤 지워라. 과거 문서는 보존만 하고 활용하지 마라 |
| **기록** (reviews) | 렌즈 실행 차수의 관찰·지적 | 기록한 뒤에는 고치지 마라. 다룬 작업이 병합되면 git 보존 태그를 달고 지우되, 차수 대조에 쓰는 최근 기록은 남겨라 |
| **핸드오프** (HANDOFF-*) | 1회성 인계 | 소비되면 바로 지워라 |
| **맥락** (Claude 메모리) | 세션 간 결정과 맥락 | 해당 PC에만 남는다. 코드와 다르면 코드를 따르라. 이슈·백로그 관리에는 쓰지 마라 |
| **규범·인덱스** (CLAUDE.md·문서 맵) | 문서 위치와 작업 방법 | 포인터와 규칙만 두고 상태는 적지 마라 |

### 기록 파일 이름 규칙

이 규칙은 여기가 소유한다. 문서 검진, spec·plan 리뷰, 워크플로 검증 모두 이 규칙을 따른다.

기록 파일은 `docs/superpowers/reviews/YYYY-MM-DD-<주제>-<종류>.md` 형식 하나만 쓴다. `review`는 spec·plan 리뷰, `check`는 문서 검진과 워크플로 검증, `prior-art`는 선행연구 대조에 쓴다.

이 저장소 밖 프로젝트에서 전달 문서를 검진하면 기록을 해당 프로젝트 폴더가 아니라 `~/.claude/disciplined-coder/reviews/` 아래에 같은 이름으로 남겨라. 함께 쓰는 폴더에 주장과 내부 수치가 남지 않게 하기 위해서다.

같은 날 같은 주제의 두 번째 차수는 종류 뒤에 차수를 붙여라(`-review-2.md`·`-check-2.md`). 앞 차수를 덮어쓰거나 이어 붙이지 마라.

렌즈별 원본은 요약문과 이름이 같은 폴더에 `<에이전트 이름>-<순번>.json`(예: `lens-grounding-1.json`)으로 둬라. 순번은 해당 차수에서 같은 렌즈가 다룬 대상의 차례다. 렌즈는 대상당 한 번만 실행하므로 대상이 하나면 늘 1, spec과 plan을 함께 보면 1과 2다. 어느 대상인지는 원본의 `target` 칸에 적힌다.

에이전트 이름을 그대로 써야 하므로 `lens-` 접두사를 떼지 마라. 이 규칙 이전에 남긴 기록은 이름이 달라도 고치지 마라.

`prior-art` 원본에는 렌즈별 원본 규칙 대신 아래 이름을 써라. `r<n>`은 실행 차례로, 둘러보기가 0, 첫 탐색이 1, 공백 라운드가 2다. 인용 판정 출력은 URL별 판정 배열이며, 각 판정에 그 URL을 인용한 하위 질문 ID를 적어라.

| 원본 | 이름 |
|---|---|
| 워크플로 반환값 | `search-r<n>.json` |
| 탐색 모드 연구자 출력 | `researcher-<하위 질문 ID>-r<n>.json` |
| 둘러보기 워크플로 반환값 | `search-r0.json` |
| 둘러보기 연구자 출력 | `researcher-scout-r0.json` |
| 인용 판정 출력 | `verifier-r<n>.json` |
| 종합 모드 연구자 출력 | `synthesis-r<n>.json` |

## 상황별로 더 읽을 파일

- 사용자가 읽거나 남에게 전달할 문서(보고서·제안서·발표자료·README·.html·.pptx·.docx·.hwp(x), 파일로 쓰는 작업 보고)를 작성하거나 고칠 때는 같은 폴더 `references/reading-docs.md`를 읽고 따르라. 사용자가 고객·외부에 보낸다고 밝힌 문서를 완성하면 완료를 보고하기 전에 `lens-review`의 전달 문서 절차로 검진하라.
- README를 작성하거나 고칠 때는 `domain-readme`도 열어라.
- 플러그인·훅·사용자 설정 파일을 고칠 때는 `domain-plugin`을 열어라.
- 두 글을 좌우로 비교하거나 사용자 판독을 받을 페이지를 만들 때는 `side-by-side`를 열어라.
