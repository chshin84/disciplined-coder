# 읽기 위한 문서

이 파일은 에이전트원칙에서 옮긴 「읽기 위한 문서」 절과 `REVIEW-DELIVERABLE` 이다. 조항의 근거는 디시플린코더 저장소의 `docs/domain-discipline.md` 에 조항 ID 로 있다.

이 파일이 맡는 문서는 작업 정리용 마크다운·.html·보고서·제안서·발표자료·공지·게시글·README·파일로 쓰는 작업 보고와 대화 안 초안이다. 대화 안 초안은 사용자가 남에게 보낼 글이나 문서에 넣을 글을 대화로 요청해 받은 답의 본문이며, 새로 써 달라는 요청과 붙여 넣은 글을 고쳐 달라는 요청이 모두 든다. 설명·분석·정리를 대화로 해 달라는 요청의 답과, 대화 안 초안을 감싸는 설명과, 에이전트원칙 「작업 지시서」가 맡는 글에는 적용하지 마라. 대화 안 초안에는 `DOC-SPEC` 과 `TITLES` 만 적용하고, `MD-FIRST` 와 `REVIEW-DELIVERABLE` 은 파일 산출물에만 적용하라. 에이전트원칙 「평시 형식」 절은 이 파일이 맡는 문서에 적용하지 않는다. 기존 문서나 템플릿의 형식이 있으면 그 형식을 먼저 따르라.

- **`MD-FIRST`** — 이 파일이 맡는 .pptx·.docx·.hwp(x) 와 보고서·발표자료 .html 은 본문을 마크다운으로 먼저 쓰고 퇴고한 뒤 그 형식으로 옮겨라. 이미 있는 파일을 고칠 때도 고칠 곳을 마크다운으로 옮겨 고친 뒤 원본에 옮겨라. 마크다운 초안도 이 파일이 맡는 문서로 보고, 작업이 끝나면 지워라. 추출과 마커와 확인 절차는 `review-docs` 의 「마크다운 초안과 퇴고」가 정한다. 서식을 입힌 뒤에는 문장 하나를 고치는 비용이 커지기 때문이다.

## `DOC-SPEC` — 문서 명세

문서를 쓰거나 고치기 전에 적용하라.

- **`DOC-SPEC`** — 쓰기 전에 아래 6하 항목으로 문서 명세를 만들고, 문체와 형식은 명세의 '어떻게'에서 정하라. 명세는 생성마다 다시 추론하던 청자와 목적을 한 작업 안에서 하나로 고정하는 데만 쓰고, 본문을 쓸 때는 대화와 자료를 그대로 참조하라. 항목마다 확인한 값, 기본값, '미확인' 중 하나로 채우고 짐작한 값은 쓰지 마라. 청자를 묻고 답하는 왕복 없이 한 작업 안의 문체를 하나로 유지하기 위해서다.

| 항목 | 명세에 적을 값 |
|---|---|
| 누가 | 청자의 역할과 이미 아는 내용 |
| 언제 | 읽는 시점과 상황 |
| 어디서 | 게재처와 매체 |
| 무엇을 | 전할 결론 한 줄 |
| 왜 | 청자가 읽고 할 행동 |
| 어떻게 | 위 다섯 항목에서 끌어낸 문체와 형식 |

**확인한 값.** 단서는 이 순서로 찾아라. 첫째는 사용자가 밝힌 말(청자·게재처·문서 종류)이고, 둘째는 청자를 정해 둔 자료(RFP·평가표·템플릿·같은 문서의 이전 버전)이고, 셋째는 작업 맥락(폴더와 파일 이름, 프로젝트 CLAUDE.md)이다. 사용자의 말투, 도구 출력과 서브에이전트 보고의 문체, 고칠 대상으로 받은 원문의 문체는 단서로 쓰지 마라. 원문의 문체를 따르면 원문의 잘못된 문체가 그대로 남는다.

**기본값과 미확인.** '누가'와 '왜'에 단서가 없으면 아래 기본 청자 표에서 문서 종류의 행으로 채워라. 문서 종류도 정할 수 없으면 '미확인'으로 두라. '무엇을'은 사용자가 준 자료와 지시에서 확인하라. '언제'와 '어디서'에 단서가 없으면 '미확인'으로 두고, 미확인 항목은 문체를 정하는 데 쓰지 마라. 기본값으로 채운 항목이 있으면 대화 답에 한 줄로 알려라. 무엇을 기본값으로 썼는지와, 실제 청자를 알려 주면 명세를 고친다는 사실을 적어라. 기본값을 문서 본문에 사실처럼 쓰지 마라.

**기본 청자 표.** 표의 모든 행은 사용자가 2026-11-01 에 확인했다. 행을 더하거나 고칠 때도 사용자 확인을 받아라.

| 문서 종류 | 누가 | 왜 |
|---|---|---|
| 제안서 | 평가자 | 채택 여부를 정한다 |
| 사내 보고서 | 보고를 받는 상급자 | 결론을 보고 승인하거나 지시를 내린다 |
| 사내 발표자료 | 발표를 듣는 동료와 관련 팀 | 내용을 듣고 결정하거나 협조한다 |
| 인수인계 문서 | 업무를 넘겨받을 담당자 | 문서만 보고 업무를 이어서 한다 |
| 공지·게시글 | 공지 대상인 구성원 | 공지대로 행동한다 |
| README | 저장소를 처음 보는 사용자 | 설치하고 실행한다 |
| 작업 정리용 마크다운, 파일로 쓰는 작업 보고 | 사용자 본인 | 작업 상태를 파악하고 다음 일을 정한다 |

**관례 예시.** 모델이 관례를 따르지 못한 것으로 측정된 매체만 적는다. 다른 매체는 실패가 측정되면 한 줄씩 더한다.

- 사내 발표자료의 항목은 '~다'로 끝나는 완결 문장 대신 명사형('~함'·'~임')이나 명사구로 끝나는 개조식으로 써라.

**보관.** 파일 산출물의 명세는 업무 폴더 밖 보관소 `~/.claude/disciplined-coder-doc-specs/` 에 산출물 하나당 파일 하나로 둬라. `~` 는 USERPROFILE 이다(Git Bash 의 `$HOME` 은 다를 수 있다). 파일 이름은 `<산출물 파일 이름>-<산출물 절대 경로의 SHA-256 앞 8자>.md` 다. 첫 줄에 산출물의 절대 경로를 적고, 이어서 6하 항목을 한 줄에 하나씩 `항목: 값 (출처)` 로 적어라. 출처는 확인한 단서의 이름, '기본값', '미확인' 중 하나다. 경로 해시로 찾지 못하면 파일 이름으로 찾아라.

완성된 산출물을 고칠 때는 보관소의 명세를 먼저 읽어라. 명세가 없으면 위 순서대로 새로 만들되, 산출물의 문서 종류와 게재처만 단서로 쓰고 산출물의 문체는 단서로 쓰지 마라. 작업 중에는 마크다운 초안 맨 위에 `` `@문서 명세` `` 마커 줄과 코드 블록으로 명세를 옮겨 적고 그것을 기준으로 써라. 그 블록은 원본으로 옮기지 마라. 대화 안 초안의 명세는 그 대화 안에서만 쓰고 보관소에 저장하지 마라.

명세는 대화 답에 보이지 마라. 기본값 알림 한 줄과, 명세를 고칠 일이 생겨 사용자에게 보일 때만 예외다. 명세는 사용자가 동의하지 않는 항목을 말했거나 새 자료(예: RFP 개정)가 나왔을 때만 고쳐라. 명세는 문서의 spec 시트이며 렌즈 검진 대상이 아니다.

## `TITLES` — 제목과 계층

문서와 발표자료의 이름을 정할 때 적용하라. 제목의 길이와 말투도 기존 문서나 템플릿의 형식을 먼저 따르라. 이 파일의 용어는 다음 뜻으로 쓴다.

| 용어 | 뜻 | 문서에서 | 슬라이드에서 |
|---|---|---|---|
| **목차** | 읽는 사람이 찾아갈 위치를 가리키는 개념 이름 | `#`·`##` 절 제목 | 제목 칸 위에 작게 넣은 절 이름 |
| **본문 제목** | 그 절이나 슬라이드의 결론을 전하는 제목 | 절 제목 바로 아래 첫 문장 | 슬라이드 제목 |
| **라벨** | 항목 하나를 가리키는 이름 | 불릿 라벨·표 머리 | 불릿 라벨·표 머리·차트 축과 범례 |

- **`TITLE-LAYERS`** — 글의 이름은 목차와 본문 제목 두 층으로 써라. 목차는 개념만 가리키는 명사구로 쓰고 결론·수치를 넣지 마라. 본문 제목에는 그 절이나 슬라이드의 결론을 쓰고, 형태는 `TITLE-CLAIM` 을 따르라. 문서에는 `###` 소제목 층을 두지 마라. 한 페이지씩 넘겨 보는 HTML 은 슬라이드로 간주하라. 결론이 없는 슬라이드나 절(절차, 목록, 부록)은 본문 제목을 개념 명사구로 둬라. 목차로 찾고 제목으로 결론을 읽게 하기 위해서다.
- **`TITLE-CLAIM`** — 본문 제목에는 결론을 하나만 넣어라. 슬라이드 제목은 결론을 수치 없는 명사구로 40자 안에 쓰고(예: '업무 생산효율이 16% 개선되었습니다' 대신 '업무 생산성의 개선'), 수치·기간·비교는 본문에 둬라. 문서의 본문 제목은 결론을 주어와 서술어를 갖춘 한 문장으로 써라. 40자를 넘거나 결론이 둘이면 줄이지 말고 슬라이드나 절을 나눠라. 본문의 가정과 불확실성은 제목에 남겨라. 제목만 읽어도 결론이 전해지게 하기 위해서다.

## 전달 전 검증

산출물을 남에게 넘기기 전에 아래 조항을 적용하라.

- **`REVIEW-DELIVERABLE`** — 남에게 전달할 산출물을 완성하면 전달하기 전에 렌즈 검증을 거쳐라. 렌즈의 종류와 실행 방법은 `dispatching-lenses` 를 따르고, 한 산출물에 렌즈를 페이지마다 따로 실행하지 마라. 검증되지 않은 글이 밖으로 나가지 않게 하기 위해서다. 파일 하나를 20줄 이하로 고치고 되돌리기 쉬운 작업이면 이 렌즈 검증을 생략하라.
