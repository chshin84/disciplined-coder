# review-llm-calls — 런타임 LLM 검증 호출자

제품이 런타임에 LLM을 호출할 때는 단일 호출로 끝내지 말고 검증을 코드에 구현하라. 이 절차에서 렌즈는 제품 코드로 옮길 청사진이다. 청사진은 `agents/lens-*.md` 본문에서 가져오고 frontmatter는 제품 코드에서 빼라.

## 렌즈 선택
검증 기준은 호출 종류로 정하라. 출력 종류와 무관하게 대조 렌즈 `lens-grounding` 하나만 쓰며, 종류별 기준은 아래 표에 고정돼 있다. 차수마다 다시 판단하지 마라. 점수를 매기면 사람마다 값이 달라져 같은 호출에도 다른 기준이 적용된다.

| 호출 종류 | 구분 기준 | `lens-grounding` 에 넘길 기준 |
|---|---|---|
| 사용자에게 그대로 보이는 출력 | 사람이 읽는 문장이나 답변을 그대로 낸다 | 출처 |
| 다운스트림이 파싱하는 출력 | 다른 코드가 형식을 전제로 읽는다 | 형식 계약(스키마·형식·제약) |
| 둘 다인 출력 | 사람도 읽고 코드도 파싱한다 | 출처와 형식 계약 |
| 비밀이나 개인정보가 닿는 출력 | 입력이나 출력에 키·토큰·개인정보가 있다 | 출처와 형식 계약(금지사항 포함) |
| 위 항목에 해당하지 않는 호출 | 그 밖의 호출 | 렌즈를 붙이지 않고 비기능 체크리스트만 적용한다 |

- 여기서 "출처"는 원래 요청과 제공된 맥락뿐이다. 그 밖의 자료를 출처로 삼지 마라.
- 스키마와 형식은 코드 validator로 먼저 검사하고, validator가 잡지 못하는 모호한 제약에만 리뷰 호출을 써라. 이는 `lens-review` 「실행」의 결정론 검사 우선 규칙을 이 절차에 적용한 방식이다.

## 조립
1차 호출 결과를 받으면 「렌즈 선택」 표가 호출 종류에 배정한 기준으로 렌즈 리뷰를 호출하고, 아래 「런타임 집계와 결정」대로 지적을 거르도록 구현하라. 이어서 제품 코드가 `type`별 행동 표를 따라 `accept`·`regenerate`·`escalate` 중 하나를 결정하게 하라. 이 이름들은 그 절의 출력 스키마와 같다. 렌즈는 등급을 매기지 않으므로 라우팅은 폐쇄 집합인 `type` 값으로 정한다. 비기능 체크리스트는 특정 단계에만 적용하지 않고 호출 코드 전체가 항상 충족해야 할 요건이다.

렌즈는 `lens-review` 「실행」대로 한 번만 호출하고, 응답이 없거나 형식이 틀리면 같은 「실행」대로 1회만 다시 호출하라. 리뷰 호출은 제품 코드가 직접 실행하므로 서브에이전트 규율을 적용하지 않는다. 렌즈가 하나이므로 여러 렌즈의 지적을 합치는 단계가 없고, 리뷰 호출이 결과를 반환하지 않으면 커버리지 공백으로 사람에게 올려라.

렌즈 지적은 로그에 남기지 마라. 지적을 그대로 남기면 사용자 입력이 로그로 복제되고, 입력에 키나 토큰이 섞여 있으면 비밀이 로그에 남는다. 비밀이나 개인정보가 섞일 수 있는 값은 마스킹하고 원문을 남기지 마라. 리뷰 호출이 무엇을 제외했는지 확인하려면 개인정보를 뺀 집계값(어느 `type`이 몇 건 나왔는지)만 남겨라.

렌즈끼리 검토 대상을 나눠 주지 않는 규칙과 근거는 `lens-review` 「실행」이 정한다.

리뷰 결과를 반영한 뒤 다시 리뷰하지 마라. 이 규칙도 `lens-review` 「실행」이 정한다. 여기서는 1차 출력을 다시 만드는 재생성만 실행한다.

## 런타임 집계와 결정

이 절차는 여기가 소유한다. 지적을 발견으로 올리는 기준은 `lens-review` 「통합과 1차 디펜스」의 **발견의 요건** 단락만 따르고, 제품 코드에 그 기준을 결정론적 파이썬 함수로 구현하라. 같은 절의 1차 디펜스와 대조 렌즈의 확인은 메인 세션이 하는 판단이므로 제품 코드로 옮기지 마라. 런타임에서만 그 뒤에 결정 단계가 붙는다.

제품 코드에 `type`별 행동 표를 두고, 그 표에 따라 `accept`·`regenerate`·`escalate` 중 하나를 결정하게 하라. 커버리지 공백이 있으면 사람에게 올려라. 출력은 아래 형식이다.

```
{ "decision": "accept|regenerate|escalate", "reason": "...", "aggregated": [ { "type": "...", "source": "<렌즈 리턴의 lens 값>", "where": "...", "claim": "...", "consequence": "...", "file": "...", "evidence": "...", "counterpart_file": "...", "counterpart": "..." } ], "retry_count": 0 }
```

`decision`과 `retry_count`는 런타임 전용이다. 무한 루프와 비용 폭주를 방지하도록 재시도 상한(예: 1~2회)을 둬라.

## 비기능 체크리스트 (런타임 전용 — 코드 설계도)
렌즈도 LLM 호출도 아니다. 호출 코드가 충족해야 하는 요건이며, 코드 가드와 검증 테스트로 확정하라. 각 항목의 등급은 이 문서에 미리 정해 둔 고정값이다.

- 외부 호출에는 timeout을 설정하라. 설정하지 않으면 무한히 대기한다(critical).
- 일시 실패와 레이트리밋에 대비해 지수 백오프로 재시도하라(major).
- 빈 응답과 실패 응답에는 `x or {}` 같은 None 가드를 둬 빈 결과에 None을 반환하는 실제 SDK의 AttributeError를 방지하라(major).
- 에러는 문자열 하나로 뭉개지 말고 호출자가 처리할 수 있는 구조로 반환하라(major).
- 비용과 토큰 상한으로 입력·출력 토큰 한도와 재시도 횟수 상한을 정하라(major).
- 요청, 지연, 토큰, 실패율을 로깅하라. 측정하지 않으면 개선할 수 없다(major).
- 비가역이거나 위험이 큰 액션에는 사람 승인을 거치게 하라. 컴플라이언스 접점이면 반드시 적용하고, 아니면 해당 제품의 운영 문서 기준을 따르라(critical).
- 프롬프트와 로그에 비밀과 개인정보를 남기지 마라(critical).

누락 항목은 해당 등급대로 처리하고, critical 항목이 빠지면 머지와 배포를 차단하라.

## 비용
리뷰 호출은 추가 비용과 지연을 발생시키므로 「렌즈 선택」 표가 배정한 렌즈만 실행하라. 결정론으로 검증할 수 있는 스키마와 정규식은 코드로 먼저 검증하라. 재생성을 강제하는 `type`은 제품 도메인에 맞게 정하고, 그 표를 코드에 둬라.
