# review-llm-calls — 런타임 LLM 검증 호출자

런타임에 LLM을 호출하는 기능은 한 번 호출하고 끝내지 말고 코드 안에 검증 단계를 구현하라. 여기서 렌즈는 제품 코드에 옮길 청사진이다. 청사진으로는 `agents/lens-*.md` 본문을 쓰되 frontmatter는 코드에서 빼라.

## 렌즈 선택
호출 종류에 따라 기준을 정하라. 출력 종류와 상관없이 대조 렌즈는 `lens-grounding` 하나다. 호출 종류별로 넘길 기준은 아래 표에 고정돼 있다. 차수마다 새로 판단하지 마라. 점수를 매기면 평가자마다 결과가 달라져 같은 호출에 다른 기준이 붙는다.

| 호출 종류 | 판별 기준 | `lens-grounding`에 넘길 기준 |
|---|---|---|
| 사용자에게 그대로 보이는 출력 | 사람이 읽는 문장이나 답변을 그대로 노출한다 | 출처 |
| 다운스트림이 파싱하는 출력 | 다른 코드가 정해진 형식을 믿고 읽는다 | 형식 계약(스키마·형식·제약) |
| 둘 다인 출력 | 사람도 읽고 코드도 파싱한다 | 출처와 형식 계약 |
| 비밀이나 개인정보가 닿는 출력 | 입력이나 출력에 키·토큰·개인정보가 있다 | 출처와 형식 계약(금지사항 포함) |
| 위 어디에도 해당하지 않는 호출 | 그 밖 | 렌즈를 붙이지 않고 비기능 체크리스트만 적용 |

- 여기서 "출처"는 원래 요청과 제공된 맥락 하나뿐이다. 다른 것은 출처로 삼지 마라.
- 스키마와 형식은 코드 validator로 먼저 검사하고, 리뷰 호출은 validator가 못 거르는 모호한 제약에만 써라. `lens-review`의 「실행」이 정한 결정론 검사 우선 규칙을 이 절차에 이렇게 적용한다.

## 조립
1차 호출 결과를 받으면 「렌즈 선택」 표에서 호출 종류에 배정한 기준으로 렌즈 리뷰를 호출하라. 이어서 「런타임 집계와 결정」 절차대로 지적을 거른 뒤, 제품 코드의 `type`별 행동 표를 보고 `accept`·`regenerate`·`escalate` 중 하나를 결정하라. 세 이름은 아래 절의 출력 스키마와 같다. 렌즈는 등급을 매기지 않으므로 폐쇄 집합인 `type`을 라우팅 근거로 쓴다. 비기능 체크리스트는 특정 단계에만 적용하지 않는다. 호출 코드 전체가 늘 만족해야 할 속성이다.

`lens-review`의 「실행」에 따라 렌즈는 한 번만 호출하되, 응답이 없거나 형식이 맞지 않으면 같은 「실행」대로 1회만 재호출하라. 리뷰 호출은 제품 코드가 직접 실행하므로 서브에이전트 규율을 적용하지 않는다. 렌즈가 하나뿐이라 여러 렌즈의 지적을 합치는 단계가 없다. 리뷰 호출이 결과를 돌려주지 않으면 커버리지 공백으로 보고 사람에게 올려라.

렌즈 지적은 로그에 남기지 마라. 지적을 그대로 적으면 사용자 입력이 로그에 복제되고, 입력에 키나 토큰이 섞여 있으면 비밀이 그대로 유출된다. 비밀이나 개인정보가 들어갈 수 있는 값은 마스킹하고 원문을 남기지 마라. 리뷰 호출이 무엇을 제외했는지 확인해야 한다면 개인정보를 뺀 집계값(어느 `type`이 몇 건 나왔는지)만 기록하라.

렌즈끼리 검토 대상을 나누지 않는 규칙과 근거는 `lens-review`의 「실행」이 정한다.

리뷰 결과를 반영한 뒤 다시 리뷰하지 마라. 이 규칙 역시 `lens-review`의 「실행」이 정한다. 이때 실행하는 작업은 1차 출력을 새로 만드는 재생성이다.

## 런타임 집계와 결정

이 절차는 여기가 소유한다. 지적을 발견으로 올릴 때는 `lens-review` 「통합과 1차 디펜스」의 **발견의 요건** 단락만 따르고, 그 기준을 제품 코드에 결정론적 파이썬 함수로 구현하라. 같은 절의 1차 디펜스와 대조 렌즈 확인은 메인 세션이 판단할 몫이므로 제품 코드로 옮기지 마라. 그 뒤에 결정 단계가 붙는 것은 런타임뿐이다.

제품 코드에 `type` 값별 행동 표를 두고, 그 표에 따라 `accept`·`regenerate`·`escalate` 중 하나를 결정하라. 커버리지 공백이 생기면 사람에게 올려라. 출력 형식은 아래와 같다.

```
{ "decision": "accept|regenerate|escalate", "reason": "...", "aggregated": [ { "type": "...", "source": "<렌즈 리턴의 lens 값>", "where": "...", "claim": "...", "consequence": "...", "file": "...", "evidence": "...", "counterpart_file": "...", "counterpart": "..." } ], "retry_count": 0 }
```

`decision`과 `retry_count`는 런타임 전용이다. 재시도 횟수에 상한(예: 1~2회)을 두어 무한 루프와 비용 폭주를 방지하라.

## 비기능 체크리스트 (런타임 전용 — 코드 설계도)
이 항목들은 렌즈도, LLM 호출도 아니다. 호출 코드가 갖춰야 할 요건이므로 코드 가드와 검증 테스트로 확정하라. 각 항목의 등급은 이 문서가 고정한 값이다.

- 외부 호출에 timeout을 적용하라. 빠뜨리면 응답을 무한히 기다린다(critical).
- 일시 실패와 레이트리밋에 대비해 재시도는 지수 백오프로 구현하라(major).
- 빈 응답과 실패 응답에는 `x or {}` 같은 None 가드를 두라. 실제 SDK가 빈 결과로 None을 돌려줄 때 나는 AttributeError를 방지한다(major).
- 에러를 문자열 하나로 뭉개지 말고 호출자가 처리할 수 있는 구조로 반환하라(major).
- 비용과 토큰 상한으로 입력·출력 토큰 한도와 재시도 횟수 상한을 정하라(major).
- 요청, 지연, 토큰, 실패율을 로깅하라. 측정하지 않으면 개선할 수 없다(major).
- 비가역적이거나 위험이 큰 액션에는 사람 승인을 적용하라. 컴플라이언스 접점이면 반드시 적용하고, 아니면 제품 운영 문서가 정한 기준을 따르라(critical).
- 프롬프트와 로그에 비밀과 개인정보를 남기지 마라(critical).

누락된 항목은 붙은 등급대로 처리하라. critical 누락은 머지와 배포를 차단한다.

## 비용
리뷰 호출은 비용과 지연을 늘리므로 「렌즈 선택」 표에 배정된 렌즈만 실행하라. 결정론적으로 확인할 수 있는 스키마와 정규식은 코드로 먼저 검증하라. 어떤 `type`일 때 재생성을 강제할지는 제품 도메인에 맞게 정해 표로 코드에 두라.
