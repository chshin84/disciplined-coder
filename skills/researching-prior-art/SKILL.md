# researching-prior-art — 선행연구 스킬

이 스킬은 메인 세션(오케스트레이터)이 선행연구를 운영하는 절차다. 연구 계획을 작성하고, `disciplined-coder:prior-art-search` 탐색 워크플로로 연구자 서브에이전트 여럿을 실행한 뒤, 검증을 통과한 인용만 근거로 보고하라.

메인 세션이 계획을 작성하면 워크플로가 `researcher`·`citation-verifier`·`citation-judge` 에이전트 정의를 실행한다. 이 정의들은 선행연구 전용이 아니므로 다른 스킬에서도 이름으로 호출할 수 있으며, 스스로 다른 에이전트를 실행하지 않는다.

## 오케스트레이터 절차

**프로토콜 항목.** 실행 전에 연구 계획(프로토콜)을 작성하라. 항목은 연구 질문, 상황, 대조 대상, 용도(`intended_use`), 이미 정한 조건(`constraints`), 모드, 하위 질문(ID, 범위 문장, 포함·제외 기준), 질의 금지 목록, 탐색 모드 연구자 수와 산정 근거다. 연구자와 검증자는 에이전트원칙을 읽지 않으며, 접속 금지 주소나 검색어 일반화 같은 규칙은 각 에이전트 정의에 직접 들어 있다.

`intended_use`에는 이 결과로 누가 무엇을 결정하는지와 최적화 기준을 문자열로 적되 비우지 마라. `constraints`에는 대화에서 확정한 조건, 기각한 대안, 이미 확인한 자료를 문자열 배열로 적으며 빈 배열도 허용한다. `target`에는 대조 대상만, `exclude`에는 해당 하위 질문의 범위 밖만 적어라. 결정 근거 탐색에서 기각한 후보안은 `target`에서 빼고 `constraints`에 넣어라.

**워크플로 실행.** 둘러보기와 2·3단계에서 Workflow 도구로 `disciplined-coder:prior-art-search`를 실행하라. `args`에는 계약 코드 `scripts/prior_art_contract.json`의 `args` 형식에 맞춘 프로토콜 객체를 넘겨라.

아래 단계를 차례로 진행하라.

**1. 상황 판정과 프로토콜** — 「상황별 전략」에 따라 상황과 대조 대상을 정하고 프로토콜을 작성하라. 사용자 승인을 묻지 말고 즉시 기록 파일에 프로토콜 전문을 적은 뒤 실행하라(2026-11-02 사용자 결정). 실행할 때 검색어가 외부 검색 서비스 로그에 남는다는 사실을 한 줄로 알려라.

연구 질문, 대조 대상, `intended_use`, `constraints`는 대화 맥락에서 도출하라.

질의 금지 목록에는 범주 대신 개별 낱말을 펼쳐 적되, 경로는 워크플로의 경로 형태 정규식이 처리하므로 빼라. 실행 직전에 프로토콜의 금지 목록과 실행 args의 `forbidden_terms`가 동일한 문자열 목록인지 대조하라. 사람 이름처럼 식별성이 높은 낱말을 펼쳤다면 기록 파일에는 범주 이름과 개수만 적고 낱말 자체는 남기지 마라(2026-10-25 사용자 결정). 커밋되고 봉인된 리뷰 기록은 원격 전송 후 삭제할 수 없기 때문이다.

프로토콜 항목이 바뀌면 기존 전문을 지우지 말고 변경된 항목만 기록 파일에 덧붙여라.

   - **확인** — 기록 파일에 프로토콜 전문과 변경 항목이 모두 있고, 식별성이 높은 금지 낱말은 범주와 개수로만 적혀 있다.

**둘러보기(1단계와 2단계 사이)** — 하위 질문을 나누기 전에 주제의 자료 지형을 파악하는 단계다. 둘러보기를 기본으로 실행하라(2026-10-25 사용자 결정).

아래 조건에 해당하면 둘러보기를 생략하고 사유를 프로토콜에 적어라.

   - 대화에서 해당 주제의 자료를 이미 확인했다.
   - 상황이 사실 확인이다.
   - 상황이 spec 대조이고, spec이 메커니즘을 이미 나눠 두었다.

프로토콜 `round`를 0으로 두고 `disciplined-coder:prior-art-search`를 실행하라. 워크플로는 연구자 하나를 `MODE: scout`로 실행한 뒤, 검증과 종합 없이 질의 경계 검사만 거쳐 결과를 반환한다. 미검증 결과이므로 판정이나 결론에 쓰지 마라. 둘러보기 결과에서는 주제어와 범위만 하위 질문에 반영하고, 사례 이름이나 결말 서술은 하위 질문 문장에 넣지 마라. 둘러보기 출처는 `constraints`의 이미 확인한 자료로 취급하지 마라. 연구자가 그 출처를 다시 찾아 보고해야 검증을 거치기 때문이다.

둘러보기로 하위 질문이 바뀌면 바뀐 내용을 기록에 추가한 뒤 `round` 1로 2단계를 실행하라. 변동이 없으면 곧바로 `round` 1로 2단계를 실행하라. `scout`가 `null`이거나 `search_status`가 `ok`가 아니면 하위 질문 초안을 그대로 쓰고 그 사실을 기록한 뒤 `round` 1을 실행하라.

   - **확인** — 둘러보기를 실행했다면 원본이 반환 직후 기록 폴더에 있고, 생략했다면 프로토콜에 생략 사유가 적혀 있다.

**2. 탐색** — 프로토콜을 넘겨 `disciplined-coder:prior-art-search`를 실행하라. 아래 처리는 워크플로가 수행한다.

   - 하위 질문마다 탐색 모드 연구자를 실행한다.
   - 스크립트가 연구자의 `queries`를 질의 금지 목록과 경로 형태 정규식으로 검사해 위반을 기록한다.
   - 스크립트가 인용을 URL별로 묶어 URL마다 추출 검증자를 실행한다. `kofia.or.kr`과 그 하위 주소의 인용은 묶지 않고 `unverifiable`로 처리한다.
   - 추출이 끝나면 통과한 주장을 묶음으로 모아 묶음마다 판정 에이전트를 한 번씩 실행한다.
   - 1차 판정에서 `불일치` 없이 `정보 부족`이 나온 주장은 추출 검증자가 원문을 다시 열어 보충한다. 스크립트가 보충된 주장을 다시 묶으면 판정 에이전트가 보충 구절로 재판정한다.
   - 끝까지 `판정 불가`가 남은 주장은 스크립트가 `unsupported`로 확정한다.
   - 스크립트는 `supported` 판정을 받은 주장에 근거한 사례만 통과 목록에 넣는다.
   - 나머지 사례는 사유와 함께 탈락·판정 불가·검증 실패 목록으로 분류한다.
   - `survey` 모드에서는 종합 모드 연구자를 실행한다.

   - **확인** — 반환값이 계약 코드의 `result` 형식에 맞는다.
   반환 직후 원본을 기록 폴더에 저장하라.

**3. 공백 판단** — 보고에 커버리지 표와 연구자의 `saturation`·`not_found`를 적어라. 연구자 실패(`search_status`가 `failed`·`not-attempted`이거나 출력이 `null`)가 발생한 하위 질문이 있으면, 하위 질문이 4개 이하일 때만 묻지 않고 해당 하위 질문으로 공백 라운드를 실행하라(「발동과 기록」의 묻지 않는 실행의 상한). `saturation`, 검증 실패, 통과 0건은 공백 라운드 실행 신호로 삼지 마라. 앞의 둘은 재탐색으로 고치기 어려운 사정이 많고, 통과 0건은 2026-10-27 사용자 지시에 따라 공백 라운드 없이 넘어가야 하기 때문이다.

사용자가 직접 요청하면 지목한 하위 질문으로, 지목이 없으면 커버리지 공백이 남은 하위 질문으로 공백 라운드를 실행하라. 공백 라운드는 `disciplined-coder:prior-art-search`를 재실행하는 방식이며 한 연구 질문당 1회만 허용한다. 두 실행 결과는 하위 질문 ID 기준으로 합치고, 양쪽에 모두 나온 URL은 공백 라운드 판정을 채택하라. 주장 참조에는 실행 차례가 없어 서로 다른 사례를 가리킬 수 있으므로, 합친 결과에는 원본 이름의 실행 차례를 붙여 `r<n>:<참조>` 형식으로 적어라. `survey` 모드에서는 두 실행의 종합을 각각 보고하라. 공백 라운드에서는 둘러보기를 생략하고 첫 탐색과 같은 `intended_use`·`constraints`를 넘겨라.

   - **확인** — 기록에 공백 라운드 실행 여부와 사유가 적혀 있고, 공백 라운드 원본이 반환 직후 기록 폴더에 있다.

**4. 인용 확인과 보고** — 「인용 확인」 범위에 속하는 인용을 직접 열어 확인하라. 이어서 기록 파일에 결과를 적고, 결론을 맨 앞에 두어 사용자에게 보고하라. 결론의 근거로는 원문 구절로 확인한 인용만 써라. 웹에서 얻은 발견은 문서가 자동으로 수정되지 않도록 문서에 바로 반영하지 말고 사용자에게 올려라.

   - **확인** — 기록 파일과 원본의 이름이 `managing-docs`의 「기록 파일 이름 규칙」에 맞는다.

**원본 파일 규칙.** 기록 폴더의 원본 파일명은 `managing-docs`의 「기록 파일 이름 규칙」 중 `prior-art` 규칙을 따르며, 실행 차례 `r<n>`은 둘러보기 0, 첫 탐색 1, 공백 라운드 2로 붙인다. 워크플로 반환값의 `query_violations[].query`와 연구자 출력의 `queries`에는 위반 검색어가 그대로 남는다. 원본을 저장하기 전에 반환값의 `query_violations[].query`, 반환값 내 `researchers[].output.queries`, 둘러보기 반환값의 `scout.queries`, 별도 저장하는 연구자 출력 원본의 `queries`에서 금지 낱말을 범주 이름으로 가려라. 또한 기록 파일과 원본을 쓰기 전에 질의 금지 목록의 낱말을 기록 전체(프로토콜의 question·target·intended_use·constraints와 연구자 출력 포함)에서 범주 이름으로 바꿔라. 실행 args는 기록 폴더에 저장하지 마라. 4단계 기록에는 실행 판정 사유, spec과 plan의 구분 기준(spec 리뷰일 때만), 프로토콜 전문, `ok`가 아닌 `overall_status`와 하위 질문별 상태, 탈락·판정 불가·검증 실패 목록, 질의 경계 위반, 직접 확인하지 못한 인용, 그리고 연구자의 `disclosures`·`not_found` 중 결론에 영향을 주는 항목을 적어라. 사람 이름 등 식별성이 높은 금지 낱말은 1단계와 마찬가지로 범주 이름과 개수만 적어라.

### 반환값을 읽는 규칙

판정과 보고에는 `passed`의 `ref`가 가리키는 항목만 써라. `rejected`·`unverifiable`·`verify_failed` 항목은 사유와 함께 보고하되 판정에 쓰지 마라. 사례 수는 `passed`·`rejected`·`unverifiable`만 세고 `verify_failed`는 제외하라. 반환값의 원소와 사유는 아래 위치에서 읽어라.

**연구자와 검증자의 원본** — `researchers`는 하위 질문 순서의 `[{ id, output }]`, `verifiers`는 URL 묶음 순서의 `[{ url, subquestions, output, stages }]`다. `output`은 워크플로가 검증 단계 출력을 합친 인용 판정 결과이며, 실패한 연구자와 URL은 `output: null`이다. `stages`는 `{ extract, judge, refetch, rejudge }`이며 단계별 에이전트 원본 출력이 들어 있다. `refetch`는 보충, `rejudge`는 재판정 출력이고, `judge`와 `rejudge`에는 묶음 출력 중 해당 URL의 판정만 들어 있다.

**탈락과 판정 불가의 사유** — 같은 `ref`의 `verifiers[].output.judgments[]`에 있는 `verdict`와 `reason`에서 읽어라. 판정할 선행 사례 서술이 없는 항목은 검증 없이 `rejected`에 들어간다. `rejected` 원소에 해당 `ref` 판정이 없으면, `urls`가 비었을 때는 '인용에 URL 이 없다', 그 외에는 '판정할 선행 사례 서술이 없다'로 사유를 적어라.

**`stages`의 `null`** — `verifiers[].stages`의 단계 값이 `null`이면 미실행이거나 무응답이며, 값 자체로는 구별되지 않는다. URL마다 실행하는 추출·보충은 호출 label(`extract:<url>`, `refetch:<url>`)의 유무로 구별하라. 묶음마다 실행하는 판정·재판정은 해당 URL이 속한 묶음의 호출 label(`judge:<n>`, `rejudge:<n>`)과 호출 결과로 구별하라. `<n>`은 1부터 시작하는 묶음 번호이며, URL이 어느 묶음에 속하는지는 호출 프롬프트의 `items`에서 확인하라. 해당 URL이 든 묶음 호출이 없으면 미실행이고, 호출은 있으나 결과가 없으면 무응답이다. 추출 통과 주장이 없는 URL은 판정 묶음에서 빠진다. 불일치 없이 정보 부족인 주장이 없으면 보충을 실행하지 않으며, 보충 통과 주장이 없는 URL은 재판정 묶음에서 빠진다.

**검증 실패의 사유** — URL 전체 실패는 같은 `url`의 `verifiers[].output`이 `null`일 때다. 추출 무응답·판정 누락, 해당 URL 판정 묶음의 무응답, 판정 칸 누락 중 하나이며, 정확한 단계는 `stages`와 호출 label에서 찾아라. 개별 주장 실패는 `verifiers[].output.judgments[]`에서 `verdict`가 `verify_failed`일 때다. 판정 출력에서 주장이 빠졌거나 보충·재판정이 그 주장에서 실패했다는 뜻이며, 구체적 사정은 `stages`의 `judge`·`refetch`·`rejudge`에서 해당 `ref` 판정을 확인하라. 한 URL에서 실패한 주장이 여럿이면 `verify_failed`에는 `{ url, refs }` 원소 하나로 묶인다.

**종합 결론의 사용** — 종합 단계는 하위 질문 상태와 무관하게 통과한 근거 지도 행 전부를 입력받는다. 따라서 `conclusions[].refs`에 `ok`가 아닌 하위 질문 참조가 하나라도 들어 있으면 그 결론은 판정에 쓰지 말고 보고에만 적어라.

**`synthesis: null`의 두 사정** — 통과 행이 없어 종합을 실행하지 않은 사정과 종합이 실패한 사정은 `passed`에 `#case#` 항목이 있는지 확인해 구별하라.

**질의 경계 위반** — `query_violations[].rule` 값은 `forbidden-term`과 `path-shape` 두 가지다.

**상태 값.** `search_status`는 연구자마다 `ok`·`no-results`·`failed`·`not-attempted` 중 하나를 가지며, 각 뜻은 「출력 스키마」의 검색 상태 표에 따른다. `verification_status`는 하위 질문마다 `ok`·`partial` 중 하나다. 해당 하위 질문의 URL에 검증 실패(검증 에이전트 실패, 시간 초과, 속도 제한, 판정 누락, 보충 실패, 재판정 실패)가 하나라도 있으면 `partial`이다. 보충 실패는 보충이 무응답이거나 주장을 빠뜨렸을 때, 혹은 보충 출력의 `access`가 `실패`이거나 `exists`가 `불일치`이거나 `quote`가 없을 때다. 판정 누락은 판정 출력에 그 주장이 빠졌을 때다. 재판정 실패는 해당 주장이 든 재판정 묶음이 무응답이거나 재판정이 주장·칸을 빠뜨렸을 때다. 끝까지 `판정 불가`가 남은 주장과 재판정에서도 `정보 부족`이 남은 주장은 검증 실패로 세지 않고 `unsupported`로 기각한다(재판정 정보 부족은 2026-10-29 사용자 결정). 구절이 주장을 뒷받침한다는 확인이 없기 때문이다. 연구 질문 전체의 `overall_status`는 모든 하위 질문의 두 상태가 `ok`일 때만 `ok`다. `overall_status`가 `ok`가 아니면 `ok`가 아닌 하위 질문 결과는 판정에 쓰지 말고 하위 질문별 상태 값을 보고에 적어라.

**세션이 끊긴 때.** 워크플로 실행 중 중단되면 같은 세션에서 런타임의 이어 실행 기능으로 재개하라. 반환 전에 세션 자체가 끝나면 기록에는 프로토콜만 남으며, 둘러보기 이후 끊겼다면 둘러보기 검색어는 이미 외부로 나간 상태다. 다음 세션에서는 검색어가 이미 전송되었을 수 있다고 기록한 뒤 같은 프로토콜로 처음부터 다시 실행하라.

**워크플로가 꺼진 환경.** `disableWorkflows`가 켜져 있으면 같은 순서로 연구자와 검증자를 Agent 도구로 직접 실행하라. `subagent_type`에는 단계에 따라 `disciplined-coder:researcher`, `disciplined-coder:citation-verifier`(추출·보충), `disciplined-coder:citation-judge`(판정·재판정)를 지정하라. 프롬프트는 워크플로 형식(첫 줄 `MODE: <모드>`, 둘째 줄부터 입력 JSON 블록 하나)으로 작성하고, 모드별 입력은 `workflows/prior-art-search.js`의 호출과 맞추라. 이 경로에서는 질의 경계 검사, 통과 목록 분리, 단계 출력 합치기를 직접 수행하라. 검증은 추출·판정·보충·재판정 순서로 진행하고, 판정과 재판정은 「실행할 때 지킬 상한」의 묶음 크기대로 주장을 묶어 묶음마다 한 번 실행하라. 출력 합치기는 「최종 판정 순서」를 직접 적용해 접근 실패, 존재 불일치와 구절 없음, 판정 실패와 판정 누락, 처음 판정의 불일치, 보충과 재판정, 판정 불가, 칸별 불일치 순으로 구분하라. 둘러보기는 `subagent_type: disciplined-coder:researcher`와 `MODE: scout` 프롬프트로 실행하고 질의 경계 검사도 직접 수행하라. 둘러보기 출력에 계약 코드의 `scout` 칸만 있는지 확인하고, 다른 칸이 섞여 있으면 둘러보기 실패로 처리하라. 실행 전에 `intended_use`가 비어 있지 않은지 확인하고, 연구자 하나의 인용 URL이 30개를 넘으면 앞 30개만 검증한 뒤 잘라 낸 수를 기록하라. 이 경로의 검사·분리·합치기는 지시 준수에만 의존하므로 이 사실을 보고와 기록에 남겨라.

## 발동과 기록

선행연구 스킬의 발동, 직접 요청, 판정 기록, 서브 세션 처리의 규칙은 여기가 소유한다. 선행연구 스킬은 렌즈가 아니므로 `lens-review`의 「카테고리와 렌즈」를 적용하지 않는다.

**발동.** `lens-review`는 「설계 문서」와 「전달 문서」 발동 기준에 해당하면 아래 묻지 않는 실행의 상한 안에서 확인 없이 실행한다. 프로토콜 승인 없이 실행하라. 선행연구는 승인을 요구하지 말라는 2026-11-02 사용자 지시에 따라, 일반화한 검색어로 하는 웹 검색도 묻지 않는다. 렌즈가 실행 중이면 렌즈 결과를 받은 뒤에 실행해 동시 실행 4개 상한을 지켜라.

**묻지 않는 실행의 상한.** 사용자가 직접 요청하지 않은 실행(`lens-review`의 선행연구, 공백 라운드, 서브 세션 보고에 따른 실행)은 하위 질문이 4개 이하일 때만 묻지 않고 실행하라. 4개를 넘으면 `ROLES` 원칙에 따라 예상 호출 수(연구자 수와 URL당 검증 호출 2~4개)를 밝혀 사용자에게 물어라. 1회 실행의 관측 비용이 약 0.5달러여서 하위 질문이 늘면 비용이 사용자 모르게 커지기 때문이다.

**직접 요청.** 사용자가 선행연구를 직접 요청하면 곧바로 실행하라.

**판정 기록.** `lens-review`는 선행연구 스킬 실행 여부와 사유를 해당 차수 기록에 남긴다. 미실행 사실이 누락되지 않게 하기 위해서다.

**서브 세션.** `nested-orchestration`의 서브 세션은 선행연구 스킬을 실행하지 않고, 발동 기준에 해당했다는 사실만 리포트에 적어 현재 세션에 넘긴다. 여러 서브 세션이 웹 탐색을 중복 실행하지 않도록, 현재 세션이 위의 묻지 않는 실행의 상한 안에서 묻지 않고 실행하라.

## 상황별 전략

1단계에서 아래 표로 상황을 판정하고, 그에 맞춰 대조 대상·하위 질문 분해·모드를 정하라. 이 상황 목록은 2026-10-18에 사용자가 확정했다.

| 상황 | 발동 경로 | 대조 대상 | 하위 질문 분해(기본값) | 모드 |
|---|---|---|---|---|
| spec 대조 | `lens-review` 「설계 문서」 | spec의 메커니즘 | 핵심 메커니즘마다 하나 | `contrast` |
| 제안서 검진 | `lens-review` 「전달 문서」 | 문서가 주장하는 방법 | 주장하는 방법마다 하나 | `contrast` |
| 기존 도구 탐색 | 사용자 직접 요청("쓸 만한 것 없나") | 사용자가 만들려는 것 | 검색 경로마다 하나(목록 사이트, 저장소, 논문) | `survey` |
| 결정 근거 탐색 | 사용자 직접 요청("근거를 찾아 달라", "어떻게 배치해야 하나") | 사용자가 고르려는 결정 후보안 | 결정이 기대는 주제마다 하나 | `survey` |
| 사실 확인 | 사용자 직접 요청, 단일 사실 | 확인하려는 주장 | 나누지 않음 | `survey` |

상황이나 대조 대상을 하나로 특정하기 어려우면 사용자에게 물어라. 표의 하위 질문 분해 열은 기본값이며, 둘러보기 결과에 따라 다르게 나눌 수 있다. 기본값과 다르게 나누면 사유를 프로토콜에 적어라.

## 실행할 때 지킬 상한

탐색 모드 연구자 수, 연구자와 검증자의 턴 수, 공백 라운드 수는 아래 상한을 지켜라.

**상한 값.** 탐색 모드 연구자 수는 통상 2개, 최대 20개다. 2026-10-18에 사용자가 확정한 값이므로 변경하려면 사용자에게 물어라.

**통상을 넘을 때.** 통상 값 이하라면 사유 없이 정할 수 있고, 통상을 넘길 때만 프로토콜에 이유를 적어라. 하위 질문이 통상보다 많을 때는 질문을 임의로 묶지 말고 연구자 수를 늘리는 근거를 적어라.

**세는 대상.** 상한에는 탐색 모드 연구자만 포함한다. 둘러보기 연구자는 1개로 고정되어 있고, 검증자와 종합 모드 연구자는 URL 수와 모드에 따라 결정되므로 제외한다. 검증자 수는 URL마다 추출 1회·보충 0~1회, 묶음마다 판정 1회·재판정 0~1회다. 한 묶음의 주장은 최대 20개이며 같은 URL의 주장은 한 묶음에 모으고, 한 URL의 주장이 20개를 넘으면 그 URL만으로 단독 묶음을 구성한다. 이 묶음 크기는 2026-10-22 사용자 결정이며, 근거와 측정 계획은 spec 「Opus 일괄 판정」에 있다. 판정 묶음에는 추출 통과 주장만, 재판정 묶음에는 보충 통과 주장만 넣으며 보충은 주장당 1회만 수행한다. 검증자 수는 탐색 후에야 알 수 있으므로 프로토콜에는 연구자 수만 적고 실제 검증자 수는 보고에 적어라. 연구자당 인용 출처는 Anthropic cookbook의 research subagent 프롬프트가 정한 "under about 100 sources"에 따라 약 100개 이하로 둔다.

**동시 실행 상한.** 선행연구 스킬도 렌즈와 동일하게 동시 실행 상한 4개를 따른다. 2026-11-16 PC 메모리 부족으로 작업이 두 번 중단된 뒤 사용자가 정한 값으로, 2026-10-18의 예외(런타임 기본 16)를 대체한다. 워크플로는 모든 단계의 호출을 4개씩 나눠 순차 실행하며, 워크플로가 꺼진 환경에서도 같은 상한을 지켜라.

**비용 상한.** 워크플로는 하위 질문이 20개를 넘으면 실행을 거부한다. 연구자 하나의 인용 URL이 30개를 넘으면 앞 30개만 검증하고, 잘라 낸 URL은 반환값의 `url_trimmed`에 남기며 해당 인용은 `unverifiable`로 처리한다(`workflows/prior-art-search.js` 상수). 실행이 거부되면 하위 질문을 좁히거나 나눠 재실행할지 사용자에게 묻고, `url_trimmed`가 비어 있지 않으면 잘라 낸 수를 기록과 보고에 적어라.

**턴 상한.** 연구자와 검증자 정의의 `maxTurns`는 같은 cookbook 프롬프트의 절대 상한(도구 호출 20회)을 따라 20으로 둔다. 공식 문서는 `maxTurns`를 "agentic turns"로만 정의하고 도구 호출과의 관계를 명시하지 않으므로, 도구 호출 20회 상한은 연구자 프롬프트 지시에도 함께 넣는다. 상한에 도달해 출력을 내지 못한 연구자는 3단계의 연구자 실패로 처리하라.

**공백 라운드 상한.** 공백 라운드는 한 연구 질문당 1회로 제한한다. 이 PC에 설치된 Anthropic deep-research 스킬의 추가 라운드 규칙인 "This step can only be followed once"를 따른다.

## 판정 규약

아래에서 '이 설계'는 대조 대상(spec·제안서의 방법, 사용자가 만들려는 것, 사용자가 고르려는 결정 후보안)을 뜻한다. 연구자는 다음 체크리스트, 축별 대조, 가드에 따라 판정한다.

**체크리스트**

- **기시감** — 이 설계의 핵심 메커니즘에 대응하는 선행 사례가 연구·상용 제품·오픈소스에 있는가.
- **결말** — 그 사례는 성공했는가, 실패했는가, 결론에 이르지 못했는가.
- **전이** — 그 실패 원인이 이 설계에도 존재하는가.
- **기준선** — 선행 사례가 쓴 단순한 기준선이 있는데도 이 설계가 비교조차 하지 않았는가.
- **붐빔** — 이미 상용화되었거나 표준이 된 것을 처음부터 다시 만들려 하는가.

**전이** — 해당하면 그것이 곧 이슈다.

대조는 네 축으로 나눠 판정한다. 선행 사례와 이 설계가 무엇을 이루려는가(목적), 어떻게 이루는가(메커니즘), 무엇으로 성공을 판정하는가(평가), 어디에 쓰이는가(적용 대상)를 축마다 비교해 같고 다름을 적는다. 네 축이 모두 같아야 같은 사례이며, 하나라도 다르면 차이를 `evidence`에 적는다. 축을 나누지 않으면 겉모습만 닮은 사례를 선행 사례로 오인하기 쉽다. 각 축의 일치 여부는 선행 사례 전체와 대조 대상 전체를 비교해 정하며, 대조 대상의 일부 구성요소와만 일치하면 다르다고 적고 해당 구성요소를 명시한다.

`survey` 모드에서는 체크리스트가 선택 사항이다. 연구자는 축이 다른 행도 근거 지도에 포함하고, 다른 축과 그 차이가 근거 이전 가능성에 미치는 영향을 `note`에 적는다. 종합 연구자는 네 축이 모두 다른 행을 결론의 단독 근거로 쓰지 않는다.

**가드**

- 참신함은 채점하지 않는다. 선행 결과가 이 설계의 전제를 반박하거나 알려진 실패 원인이 이 설계에 남아 있을 때만 이슈로 삼는다.
- "찾지 못했다"를 "존재하지 않는다"로 바꿔 쓰지 않는다. 못 찾은 항목은 이유와 함께 `not_found`에 적되 독창성의 근거로 삼지 않는다.
- 오인도 누락만큼 철저히 차단한다. 네 축 중 하나라도 다르면 차이를 명시하고 같은 사례로 단정하지 않는다. 못 찾음은 기존 설계를 바꾸지 않지만 오인은 멀쩡한 설계를 없앤다.
- `weak-baseline`은 비교만 요구할 뿐 구현을 요구하지 않는다. 이 유형의 `claim`은 "이 기준선과 비교되지 않았다"까지만 적고 구현 지시를 덧붙이지 않는다.
- 인용한 URL은 직접 열어 확인하고 출처 성격을 구분해 적는다. 열지 못했다면 `opened`를 거짓으로 두고 `disclosures`에 남긴다. 직접 계산하거나 추론한 값은 `derived`로 표시한다.
- 질의 경계를 지킨다. 검색어에는 일반화된 기술 용어와 공개 개념만 넣고, 고유명사·파일 경로·사내 식별자·미공개 제품명·사람 이름·코드 조각은 넣지 않는다. 검색 질의는 제3자가 보관하는 로그다. 경계 안에서 대조할 수 없으면 질의를 넓히지 말고 `not_found`에 "질의 경계 때문에 확인하지 못했다"고 적는다.

연구자는 가드의 "인용한 URL은 실제로 열어 확인하고 출처의 성격을 구분해 적는다"를 그대로 따르며, 검증자는 연구자가 기록한 결과를 다시 판정한다.

## 출력 스키마

필드명과 바깥 형식의 원본은 계약 코드 `scripts/prior_art_contract.json`이다. 출력 예시는 각 에이전트 정의의 예시 블록에 들어 있으며, 연구자·종합·둘러보기는 `agents/researcher.md`, 추출·보충은 `agents/citation-verifier.md`, 판정은 `agents/citation-judge.md`에 있다. 워크플로 스키마, 프롬프트 형식, 단계 출력 합치기 코드는 `workflows/prior-art-search.js`에 있고, 세 곳과 계약 코드의 일치는 `scripts/test_prior_art_contract.sh`로 검증한다. 이 절에는 계약 코드에 없는 의미만 적는다.

**검색 상태.** `search_status`는 `issues`가 비어 있는 원인을 구분한다.

| 값 | 뜻 | 빈 `issues`의 해석 |
|---|---|---|
| `ok` | 검색을 실행했고 결과도 얻었다 | 선행 사례를 확인했으나 문제가 없었다는 뜻이므로 판정으로 쓸 수 있다 |
| `no-results` | 검색을 실행했으나 아무것도 찾지 못했다 | 판정이 아니다. 사유를 `not_found`에 적어야 한다 |
| `failed` | 도구 오류가 발생했거나 접근이 차단되었다 | 판정이 아니다. 검색 실패로 보고한다 |
| `not-attempted` | 검색을 시도하지 않았다 | 판정이 아니다. 검색을 실행하지 않은 것으로 본다 |

**주장 참조.** `<하위 질문 ID>#<issue|case>#<배열 위치>` 형식을 쓰며, 배열은 연구자 출력의 `issues` 또는 `evidence_map`이다. 종합 모드 연구자는 통과 행만으로 근거 지도를 재구성하고, 각 결론의 근거가 된 행의 주장 참조를 `refs`에 적는다.

**판정 대상과 기준.** 검증 대상은 선행 사례 측 서술에 한정한다. 이슈에서는 `prior_claim`, 근거 지도 행에서는 사례 이름·`outcome`·각 축의 `prior`가 대상이다. 판정 기준은 "옮긴 구절이 주장의 주어와 수치와 조건을 모두 포함하면 supported"로 고정한다. 대조 대상 측 판단(`same`, `note`, 이슈의 `claim`)은 연구자가 맡고 사용자가 보고에서 검토한다(2026-10-18 사용자 결정). `unverifiable`은 봇 차단·유료 장벽·무응답 같은 원문 측 사정만 가리키며 반박으로 치지 않는다. 검증은 추출·판정·보충·재판정 순으로 진행한다. 추출 검증자가 URL을 열어 주장별 접근·존재·구절을 판정하면, 판정 에이전트는 웹을 열지 않고 옮긴 구절만 보고 수치·조건, 방향, 범위 세 칸을 판정한다.

### 최종 판정 순서

최종 `verdict`는 워크플로 스크립트가 아래 순서로 확정하며 에이전트는 정하지 않는다. 워크플로가 꺼진 환경에서는 이 순서를 직접 적용하라.

1. 추출 검증자가 무응답이거나 판정이 빠졌으면 그 URL은 검증 실패다.
2. `access`가 `실패`면 `unverifiable`이다.
3. `exists`가 `불일치`이거나 `quote`가 없으면 `unsupported`다.
4. 해당 URL이 든 판정 묶음이 무응답이거나, URL 내 판정 중 하나라도 세 칸 중 빠진 칸이 있으면 그 URL은 검증 실패다. 빠진 칸을 `일치`로 간주하지 않는다. 판정 출력에서 특정 주장이 빠졌으면 그 주장만 `verify_failed`다.
5. 1차 판정에 `불일치`인 칸이 있으면 보충 없이 `unsupported`로 확정한다.
6. `정보 부족`인 칸이 있으면 보충 후 재판정한다. 보충이나 재판정이 무응답이거나 해당 주장을 누락했을 때, 혹은 보충 출력의 `access`가 `실패`이거나 `exists`가 `불일치`이거나 `quote`가 없으면 그 주장만 `verify_failed`다. 재판정 결과는 그 주장의 세 칸을 모두 덮어쓴다. 재판정에 `불일치`가 있으면 `unsupported`이고, 재판정에서도 `정보 부족`이 남으면 그 주장만 `unsupported`로 확정하며 `reason`의 `재판정 정보 부족:` 항목에 칸 이름을 남긴다.
7. 남은 칸에 `판정 불가`가 있으면 `unsupported`로 확정하고, 판정 불가 칸의 이유 유형을 합친 출력의 `reason`에 남긴다.
8. 그 밖은 `supported`다.

**판정 모델 교체.** 단계별 출력 형식은 모델에 종속되지 않으므로, 추출 검증자와 판정 에이전트 정의의 `model`만 바꾸면 단계별로 다른 모델을 쓸 수 있다. 현재 구성은 판정 에이전트 `claude-opus-5-5`(노력 수준 medium), 추출 검증자 `claude-haiku-5-5`(노력 수준 high)이며 검증 측정도 이 ID로 수행했다. Bedrock·Vertex처럼 모델 ID 형식이 다르거나 Opus를 쓸 수 없는 계정에서는 사용자가 `agents/citation-verifier.md`와 `agents/citation-judge.md`의 `model`을 바꿔야 하며, 바꾼 뒤에는 다시 측정한다. Kim 등(ICML 2025)이 제공사가 달라도 오류 상관이 높다고 보고했으므로 모델을 바꿔도 상관 오류가 줄어든다고 기대하지 마라. 사내 문서를 외부 API로 전송하는 모델은 회사 승인이 필요하므로 구성에 넣기 전에 승인받아라.

## 인용 확인

인용 확인은 검증자와 오케스트레이터가 나눠 맡는다(2026-10-18 사용자 결정). 연구자가 늘어나면 오케스트레이터 혼자 인용 수십 건을 모두 열어야 하기 때문이다.

추출 검증자가 옮긴 `quote`가 실제 원문에 있고 주장을 뒷받침하는지 원문을 직접 열어 확인하라. 합친 출력의 `quote`가 이 값이며, 보충을 거친 주장은 보충 구절을 가리킨다. 판정 불가 기각은 `reason`의 `판정 불가:` 항목에 칸과 이유 유형이, 재판정 정보 부족 기각은 `reason`의 `재판정 정보 부족:` 항목에 칸 이름이 남는다. 이 두 기각은 반박된 주장으로 보고하지 말고, 구절이 주장을 뒷받침한다는 확인이 없어 기각되었다고 밝히며 건수도 반박된 주장과 구분해 적어라. 확인 범위는 상황에 따라 다르다. spec 대조와 제안서 검진에서는 문서를 실제로 수정하게 만들었거나 처분 `사용자`로 올릴 발견, 그리고 사용자에게 전달할 발견의 근거 인용을 전부 확인하라. 기존 도구 탐색·결정 근거 탐색·사실 확인에서는 보고 결론 문장에 직접 인용한 출처만 확인하고, 근거 지도의 나머지 행은 검증자 판정을 그대로 써라.

이 절이 인용 확인 범위의 원본이다.

## 레퍼런스 프롬프트

연구자 정의에는 contrast 지시문으로 `- system:` 줄을, survey 지시문으로 `- system (survey):` 줄을, `scout` 모드 지시문으로 `- system (scout):` 줄을 각각 한 줄 그대로 싣고, 사용자 메시지 형식은 워크플로 프롬프트 형식을 따른다.

- system: "너는 선행연구 대조 검수자다. 기시감(이 설계를 누가 이미 해봤는지)과 결말(그 결과가 무엇이었는지)과 전이(그 실패 원인이 이 설계에도 있는지)를 찾아라. 선행 사례가 쓴 단순한 기준선이 있는데 이 설계가 그것과 비교조차 안 했는지, 그리고 붐빔(이미 상용화되거나 표준이 된 것을 처음부터 다시 지으려 하는지)도 함께 보라. 참신함을 채점하지 마라. 못 찾은 것은 `not_found`에 적고 독창성의 근거로 삼지 마라. 선행 사례는 목적·메커니즘·평가·적용 대상 네 축으로 대조하라. 모든 주장에 출처 URL과 그 성격을 달고 실제로 열어 확인하라. 질의에 고유명사와 경로와 사내 식별자를 넣지 마라. 체크리스트를 항목마다 따로 검토하고 그 결과를 한 번에 돌려주며, 검토한 관점을 `notes`에 적어라. 서브에이전트를 새로 열지 마라. 더 확인해야 할 것이 남으면 무엇을 왜 확인해야 하는지 `notes`에 적어라. 등급을 매기지 마라. 발견마다 이 불일치 때문에 지금 무엇이 그렇게 되어 있는지(consequence)와 그렇게 본 근거(evidence)를 적어라. 결과를 구체적으로 못 적는 것은 올리지 마라. 찾은 것이 없으면 빈 목록이 정상이다. 네 축 중 하나라도 다르면 그 차이를 적고 같은 사례로 단정하지 마라. 출처의 성격은 `citations`의 `kind`로 적고, 열지 못한 출처는 `opened`를 false 로 두어라. 입력의 `forbidden_terms`에 든 낱말도 질의에 넣지 말고, 실행한 검색어는 빠짐없이 `queries`에 적어라. 도구 호출은 20회 이하로, 인용할 출처는 약 100개 이하로 두어라. `evidence_map`은 빈 배열로 두어라. 입력의 `intended_use`와 `constraints`를 읽고, `constraints`의 기각한 대안과 이미 확인한 자료는 다시 찾아 보고하지 마라. 마지막 세 번의 검색에서 새 사례가 몇 건 나왔는지를 `saturation`에 적어라. 출력은 연구자 출력 JSON 하나로만 내고 앞뒤에 다른 글을 두지 마라."
- system (survey): "너는 결정 근거 수집자다. 입력의 `intended_use`가 정하는 결정과 기준을 먼저 읽고, 자기 하위 질문 범위에서 그 결정에 쓸 선행 사례와 근거를 찾아라. `intended_use`는 근거의 우선순위 기준으로 쓰고, `intended_use`와 맞지 않아 뺀 근거는 `notes`에 사유와 함께 남겨라. 입력의 `constraints`를 읽고, `constraints`의 기각한 대안과 이미 확인한 자료는 다시 찾아 보고하지 마라. 찾은 사례마다 `evidence_map` 행을 채워라. 축이 다른 행도 근거 지도에 넣어라. 네 축(목적·메커니즘·평가·적용 대상)이 대조 대상과 모두 같지 않아도 된다. 다른 축은 `note`에 적고, 그 차이 때문에 근거를 이 결정에 옮겨 쓰기 어려운지도 적어라. 후보안 사이의 결정이면 행마다 그 근거가 어느 후보안을 어느 방향으로 움직이는지 `bearing`에 적어라. 기시감·결말·전이·기준선·붐빔 체크리스트는 도움이 될 때만 골라 써라. 반박이나 실패를 발견했을 때만 `issues`에 올려라. 탐색 방법은 하위 질문에 맞게 네가 골라라. 고를 수 있는 방법에는 짧고 넓은 검색어로 시작해 좁혀 가기, 후보안마다 사용 사례와 결말 찾기, 인용 따라가기(찾은 출처의 참고문헌과 그 출처를 인용한 자료를 따라가는 snowballing), 실패·포기·회고 자료 찾기가 있다. 고른 방법을 `notes`에 적어라. 모든 근거에 출처 URL과 그 성격을 달고 실제로 열어 확인하라. 열지 못한 출처는 `opened`를 false 로 두어라. 못 찾은 것은 `not_found`에 이유와 함께 적고 독창성의 근거로 삼지 마라. 질의에 고유명사와 경로와 사내 식별자를 넣지 말고, 입력의 `forbidden_terms`에 든 낱말도 질의에 넣지 마라. 실행한 검색어는 빠짐없이 `queries`에 적어라. 서브에이전트를 새로 열지 마라. 도구 호출은 20회 이하로, 인용할 출처는 약 100개 이하로 두어라. 마지막 세 번의 검색에서 새 사례가 몇 건 나왔는지를 `saturation`에 적어라. 출력은 연구자 출력 JSON 하나로만 내고 앞뒤에 다른 글을 두지 마라."
- system (scout): "너는 선행연구 둘러보기 연구자다. 목표는 입력 `question`과 `target`의 주제에 어떤 자료 묶음이 있는지 확인하고 하위 질문 후보를 내는 일이다. 입력의 `draft_subquestions`는 오케스트레이터가 쓴 하위 질문 초안이고, `intended_use`와 `constraints`는 결과의 용도와 이미 정한 조건이다. 출력의 `clusters`에는 주제 묶음마다 `topic`, 대표 출처 URL 목록 `sources`, 묶음 설명 `note`를 적어라. `subquestion_candidates`에는 하위 질문 후보마다 범위 문장 `scope`와 그 후보를 낸 근거 `basis`를 적어라. 사례마다의 판정, 이슈, 근거 지도는 내지 마라. 질의에 고유명사와 경로와 사내 식별자를 넣지 말고, 입력의 `forbidden_terms`에 든 낱말도 질의에 넣지 마라. 실행한 검색어는 빠짐없이 `queries`에 적어라. 도구 호출은 10회 이하로 두어라. 서브에이전트를 새로 열지 마라. 출력은 둘러보기 출력 JSON 하나로만 내고 앞뒤에 다른 글을 두지 마라."
