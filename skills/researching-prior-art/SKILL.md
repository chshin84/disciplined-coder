# researching-prior-art — 선행연구 스킬

이 스킬을 따르는 메인 세션(오케스트레이터)은 연구 계획을 쓰고, 탐색 워크플로 `disciplined-coder:prior-art-search`로 연구자 서브에이전트 여럿을 실행한다. 보고할 때는 검증 판정을 통과한 인용만 근거로 써라.

메인 세션이 계획을 쓰면 워크플로가 에이전트 정의 `researcher`·`citation-verifier`·`citation-judge` 를 실행한다. 이 정의들은 선행연구 전용이 아니므로 다른 스킬 절차도 이름으로 지정해 실행할 수 있다. 이 정의들은 다른 에이전트를 실행하지 않는다.

## 오케스트레이터 절차

**프로토콜 항목.** 실행 전에 연구 계획(프로토콜)을 써라. 연구 질문, 상황, 대조 대상, 용도(`intended_use`), 이미 정한 조건(`constraints`), 모드, 하위 질문(ID, 범위 문장, 포함·제외 기준), 질의 금지 목록, 탐색 모드 연구자 수와 산정 근거를 모두 적어라. 연구자와 검증자는 에이전트원칙을 읽지 않으며, 접속 금지 주소나 검색어 일반화 같은 규칙은 각 에이전트 정의에 직접 들어 있다.

`intended_use`에는 이 결과로 누가 무엇을 정하는지와 최적화할 기준을 문자열로 적되 비우지 마라. `constraints`에는 대화에서 이미 정한 조건, 기각한 대안, 이미 확인한 자료를 문자열 배열로 적으며 빈 배열도 허용한다. `target`에는 대조 대상만, `exclude`에는 그 하위 질문의 범위 밖만 적어라. 결정 근거 탐색에서 기각한 후보안은 `target`에서 빼고 `constraints`에 적어라.

**워크플로 실행.** 둘러보기, 2단계, 3단계에서는 Workflow 도구로 `disciplined-coder:prior-art-search`를 실행하라. `args`에는 계약 코드 `scripts/prior_art_contract.json` 의 `args` 형식에 맞춘 프로토콜 객체를 넣어라.

아래 단계를 순서대로 진행하라.

**1. 상황 판정과 프로토콜** — 「상황별 전략」으로 상황과 대조 대상을 정하고 프로토콜을 써라. 사용자 승인을 묻지 말고 곧바로 기록 파일을 만들어 프로토콜 전문을 적은 뒤 실행하라(2026-11-02 사용자 결정). 검색어가 외부 검색 서비스 로그에 남는다는 사실은 실행할 때 한 줄로 알려라.

연구 질문, 대조 대상, `intended_use`, `constraints`는 대화 맥락에서 도출하라.

질의 금지 목록에는 범주 이름 대신 실제 낱말을 펼쳐 넣어라. 경로는 워크플로의 경로 형태 정규식이 검사하므로 목록에 넣지 마라. 실행 직전에 프로토콜의 금지 목록과 실행 args 의 `forbidden_terms`가 같은 문자열 목록인지 대조하라. 사람 이름처럼 식별성이 큰 낱말을 펼쳤다면 기록 파일에는 범주 이름과 펼친 낱말 개수만 적고 낱말 자체는 적지 마라(2026-10-25 사용자 결정). 리뷰 기록은 커밋되고 봉인되어 원격에 올라가면 지울 수 없기 때문이다.

프로토콜의 칸이 바뀌면 앞의 전문을 지우지 말고 바뀐 칸을 기록 파일에 추가하라.

   - **확인** — 기록 파일에 프로토콜 전문과 바뀐 칸이 있고, 질의 금지 목록의 식별 낱말은 범주와 개수로만 적혀 있다.

**둘러보기(1단계와 2단계 사이)** — 하위 질문을 나누기 전에 주제의 자료 분포를 확인하는 단계다. 기본으로 둘러보기를 실행하라(2026-10-25 사용자 결정).

아래 조건에 해당하면 둘러보기를 생략하고 이유를 프로토콜에 적어라.

   - 대화에서 이미 그 주제의 자료를 확인했다.
   - 상황이 사실 확인이다.
   - 상황이 spec 대조이고, spec 에 메커니즘이 이미 나뉘어 있다.

프로토콜의 `round`를 0 으로 두어 `disciplined-coder:prior-art-search`를 실행하라. 워크플로는 연구자 하나를 `MODE: scout`로 실행하고, 검증과 종합 없이 질의 경계 검사만 거쳐 결과를 반환한다. 둘러보기 결과는 검증하지 않으므로 판정과 결론에 쓰지 마라. 결과에서 주제어와 범위만 하위 질문으로 옮기고, 사례 이름과 결말 서술은 하위 질문 문장에 넣지 마라. 둘러보기에서 찾은 출처는 `constraints`의 이미 확인한 자료에 넣지 마라. 연구자가 그 출처를 다시 찾아 보고해야 검증 단계를 거칠 수 있기 때문이다.

둘러보기 결과에 따라 하위 질문이 바뀌면 바뀐 하위 질문을 기록에 추가한 뒤 `round` 1 로 2단계를 실행하라. 바뀌지 않으면 둘러보기 직후 `round` 1 로 2단계를 실행하라. `scout`가 `null`이거나 `search_status`가 `ok`가 아니면 하위 질문 초안을 그대로 쓰고 그 사실을 기록에 적은 뒤 `round` 1 을 실행하라.

   - **확인** — 둘러보기를 실행했으면 원본이 반환 직후 기록 폴더에 있고, 생략했으면 프로토콜에 생략 이유가 있다.

**2. 탐색** — 프로토콜을 넘겨 `disciplined-coder:prior-art-search`를 실행하라. 아래 단계는 워크플로가 처리한다.

   - 하위 질문마다 탐색 모드 연구자를 실행한다.
   - 스크립트가 연구자의 `queries`를 질의 금지 목록과 경로 형태 정규식으로 검사하고 위반을 기록한다.
   - 스크립트가 인용을 URL 별로 묶어 URL 마다 추출 검증자를 실행한다. `kofia.or.kr` 와 하위 주소의 인용은 묶지 않고 `unverifiable`로 둔다.
   - 추출이 끝나면 스크립트가 통과한 주장을 묶어 묶음마다 판정 에이전트를 한 번 실행한다.
   - 첫 판정에서 `정보 부족`이 있고 `불일치`가 없는 주장은 추출 검증자가 원문을 다시 열어 보충한다. 스크립트가 보충한 주장을 다시 묶고, 판정 에이전트가 보충 구절로 재판정한다.
   - 끝까지 `판정 불가`가 남은 주장은 스크립트가 `unsupported`로 처리한다.
   - 스크립트는 `supported` 판정을 받은 주장에 근거한 사례만 통과 목록에 넣는다.
   - 나머지 사례는 사유와 함께 탈락 목록, 판정 불가 목록, 검증 실패 목록으로 나눈다.
   - `survey` 모드에서는 종합 모드 연구자를 실행한다.

   - **확인** — 반환값이 계약 코드의 `result` 형식과 일치하는지 확인하고, 반환 직후 원본을 기록 폴더에 저장하라.

**3. 공백 판단** — 커버리지 표와 연구자의 `saturation`·`not_found`를 보고에 적어라. 연구자 실패(`search_status`가 `failed`·`not-attempted`이거나 연구자 출력이 `null`)가 생긴 하위 질문이 있으면 묻지 말고 그 하위 질문으로 공백 라운드를 실행하라(하위 질문 4개 이하일 때만 적용하며, 기준은 「발동과 기록」의 묻지 않는 실행의 상한이다). `saturation`, 검증 실패, 통과 0건은 공백 라운드 실행 기준으로 쓰지 마라. 앞의 두 항목은 재탐색으로 해결되지 않는 사유가 많고, 통과 0건은 2026-10-27 사용자 지시에 따라 공백 라운드 없이 넘어가기 때문이다.

사용자가 공백 라운드를 직접 요청하면 지목한 하위 질문으로, 지목이 없으면 커버리지 공백이 남은 하위 질문으로 실행하라. 공백 라운드는 `disciplined-coder:prior-art-search`를 다시 실행하는 절차이며 한 연구 질문당 1회까지다. 두 실행 결과는 하위 질문 ID 기준으로 합치되, 같은 URL 이 양쪽에 있으면 공백 라운드 판정을 써라. 주장 참조에는 실행 차례가 없어 두 실행에서 같은 참조가 다른 사례를 가리킬 수 있으므로, 합친 결과에서는 참조 앞에 실행 차례를 붙여 `r<n>:<참조>`로 적어라. `survey` 모드에서는 두 실행의 종합 결과를 따로 보고하라. 공백 라운드에서는 둘러보기를 생략하고 첫 탐색과 같은 `intended_use`·`constraints`를 넘겨라.

   - **확인** — 기록에 공백 라운드 실행 여부와 사유가 있고, 공백 라운드 원본이 반환 직후 기록 폴더에 있다.

**4. 인용 확인과 보고** — 「인용 확인」 범위에 해당하는 인용을 직접 열어 확인하라. 이어서 기록 파일에 결과를 적고 결론부터 사용자에게 보고하라. 결론의 근거로는 원문 구절로 확인한 인용만 써라. 웹에서 찾은 발견이 문서를 임의로 바꾸지 않도록 문서에 직접 반영하지 말고 사용자에게 올려라.

   - **확인** — 기록 파일과 원본 이름이 `managing-docs`의 「기록 파일 이름 규칙」을 따른다.

**원본 파일 규칙.** 기록 폴더의 원본 파일 이름은 `managing-docs`의 「기록 파일 이름 규칙」이 `prior-art` 종류에 정한 형식을 따르라. 실행 차례 `r<n>`은 둘러보기가 0, 첫 탐색이 1, 공백 라운드가 2 다. 워크플로 반환값의 `query_violations[].query`와 연구자 출력의 `queries`에는 위반 검색어가 원문 그대로 남는다. 원본을 저장하기 전에 반환값의 `query_violations[].query`, 반환값 안의 `researchers[].output.queries`, 둘러보기 반환값의 `scout.queries`, 따로 저장하는 연구자 출력 원본의 `queries`에서 금지 낱말을 범주 이름으로 가려라. 또한 기록 파일과 원본을 쓰기 전에 프로토콜(question·target·intended_use·constraints)과 연구자 출력을 포함한 기록 전체에서 질의 금지 목록의 낱말을 범주 이름으로 바꿔라. 실행 args 는 기록 폴더에 저장하지 마라. 4단계 기록에는 실행 판정 이유, spec 과 plan 의 구분 기준(spec 리뷰일 때만), 프로토콜 전문, `ok`가 아닌 `overall_status`와 하위 질문별 상태, 탈락·판정 불가·검증 실패 목록, 질의 경계 위반, 오케스트레이터가 확인하지 못한 인용, 연구자가 `disclosures`와 `not_found`에 적은 항목 중 결론에 영향을 주는 항목을 적어라. 질의 금지 목록의 식별 낱말(사람 이름 등)은 1단계대로 범주 이름과 개수만 적어라.

### 반환값을 읽는 규칙

판정과 보고의 근거로는 `passed`의 `ref`가 가리키는 항목만 써라. `rejected`·`unverifiable`·`verify_failed` 항목은 사유와 함께 보고하되 판정에는 쓰지 마라. 사례 수는 `passed`·`rejected`·`unverifiable`만 세고 `verify_failed`는 빼라. 반환값의 각 항목과 사유는 아래 위치에서 읽어라.

**연구자와 검증자의 원본** — `researchers`는 하위 질문 순의 `[{ id, output }]`이고, `verifiers`는 URL 묶음 순의 `[{ url, subquestions, output, stages }]`이다. `output`은 워크플로가 검증 단계 출력을 합친 인용 판정 결과이며, 실패한 연구자와 URL 은 `output: null`이다. `stages`는 `{ extract, judge, refetch, rejudge }` 구조로 단계별 에이전트 원본 출력을 보관한다. `refetch`는 보충, `rejudge`는 재판정 출력이고, `judge`와 `rejudge`에는 묶음 출력 중 해당 URL 의 판정만 들어 있다.

**탈락과 판정 불가의 사유** — 같은 `ref`에 해당하는 `verifiers[].output.judgments[]`의 `verdict`와 `reason`에서 읽는다. 판정할 선행 사례 서술이 없는 항목은 검증자에게 보내지 않고 바로 `rejected`에 넣는다. 따라서 `rejected` 원소에 해당 `ref`의 판정이 없으면, `urls`가 비었을 때는 '인용에 URL 이 없다', 그 밖에는 '판정할 선행 사례 서술이 없다'로 사유를 적어라.

**`stages`의 `null`** — `verifiers[].stages`의 특정 단계가 `null`이면 미실행이거나 무응답이며 값만으로는 구별할 수 없다. 추출과 보충은 URL 마다 실행하므로 호출 label(`extract:<url>`, `refetch:<url>`)의 유무로 구별하라. 판정과 재판정은 묶음마다 실행하므로 해당 URL 이 속한 묶음의 호출 label(`judge:<n>`, `rejudge:<n>`)과 호출 결과로 구별하라. `<n>`은 1 부터 시작하는 묶음 번호이며, URL 이 어느 묶음에 속하는지는 호출 프롬프트의 `items`에서 찾는다. 해당 묶음 호출이 없으면 미실행이고, 호출은 있는데 결과가 없으면 무응답이다. 추출을 통과한 주장이 없는 URL 은 판정 묶음에 넣지 않는다. 불일치 없이 정보 부족인 주장이 없으면 보충을 실행하지 않고, 보충을 통과한 주장이 없는 URL 은 재판정 묶음에 넣지 않는다.

**검증 실패의 사유** — 같은 `url`의 `verifiers[].output`이 `null`이면 URL 전체 실패다. 추출 무응답, 추출 판정 누락, 판정 묶음 무응답, 판정 칸 누락 중 하나에 해당하며 어느 단계인지는 `stages`와 호출 label 로 확인하라. 개별 주장 실패는 `verifiers[].output.judgments[]`에서 `verdict`가 `verify_failed`인 항목이다. 판정 출력에서 해당 주장이 빠졌거나 보충·재판정이 실패했다는 뜻이며, 구체적 사유는 `stages`의 `judge`·`refetch`·`rejudge`에서 해당 `ref`의 판정으로 확인하라. 한 URL 에서 여러 주장이 실패하면 `verify_failed`에는 그 URL 의 `{ url, refs }` 원소 하나로 합쳐진다.

**종합 결론의 사용** — 종합 단계는 하위 질문의 상태와 관계없이 통과한 근거 지도 행 전부를 입력받는다. 따라서 `conclusions[].refs`에 상태가 `ok`가 아닌 하위 질문 참조가 하나라도 들어 있으면 그 결론을 판정에 쓰지 말고 보고에만 적어라.

**`synthesis: null`의 두 사정** — 통과 행이 없어 종합을 실행하지 않은 상황과 종합이 실패한 상황은 `passed`에 `#case#` 항목이 있는지 확인해 구별하라.

**질의 경계 위반** — `query_violations[].rule`에는 `forbidden-term` 또는 `path-shape` 값이 들어간다.

**상태 값.** 연구자별 `search_status`는 `ok`·`no-results`·`failed`·`not-attempted` 중 하나이며 뜻은 「출력 스키마」의 검색 상태 표에 있다. 하위 질문별 `verification_status`는 `ok`·`partial` 중 하나다. 하위 질문의 URL 에서 검증 실패(검증 에이전트 실패, 시간 초과, 속도 제한, 판정 누락, 보충 실패, 재판정 실패)가 하나라도 발생하면 `partial`이 된다. 보충 실패는 보충 무응답, 주장 누락, 보충 출력의 `access`가 `실패`, `exists`가 `불일치`, `quote` 비어 있음 중 하나에 해당할 때다. 판정 누락은 판정 출력에서 해당 주장이 빠졌을 때이고, 재판정 실패는 재판정 묶음 무응답이나 주장·칸 누락일 때다. 끝까지 `판정 불가`가 남은 주장과 재판정 뒤에도 `정보 부족`이 남은 주장은 검증 실패로 세지 않고 `unsupported`로 기각된다(재판정 정보 부족 처리는 2026-10-29 사용자 결정). 구절이 주장을 뒷받침한다는 확인이 없기 때문이다. 연구 질문 전체의 `overall_status`는 모든 하위 질문의 두 상태 값이 `ok`일 때만 `ok`다. `overall_status`가 `ok`가 아니면 `ok`가 아닌 하위 질문의 결과를 판정에 쓰지 말고 하위 질문별 상태를 보고에 적어라.

**세션이 끊긴 때.** 워크플로 실행 중 중단되면 같은 세션에서 런타임의 이어 실행 기능으로 재개하라. 반환 전에 세션 자체가 종료되면 기록에는 프로토콜만 남는다. 둘러보기 뒤에 끊겼다면 둘러보기 검색어는 이미 외부로 전송된 상태다. 다음 세션의 오케스트레이터는 검색어가 이미 전송됐을 수 있다고 기록에 적은 뒤 같은 프로토콜로 처음부터 실행하라.

**워크플로가 꺼진 환경.** `disableWorkflows`가 켜져 있으면 같은 순서로 연구자와 검증자를 Agent 도구로 직접 실행하라. 단계에 맞게 `subagent_type`에 `disciplined-coder:researcher`, `disciplined-coder:citation-verifier`(추출·보충), `disciplined-coder:citation-judge`(판정·재판정)를 지정하라. 프롬프트는 워크플로 형식(첫 줄 `MODE: <모드>`, 둘째 줄부터 입력 JSON 블록 하나)으로 쓰고, 모드별 입력은 `workflows/prior-art-search.js` 의 호출과 동일하게 맞춰라. 이 경로에서는 질의 경계 검사, 통과 목록 분리, 단계 출력 통합을 오케스트레이터가 직접 수행하라. 검증은 추출, 판정, 보충, 재판정 순서로 실행하고, 판정과 재판정은 주장을 「실행할 때 지킬 상한」의 묶음 크기대로 묶어 묶음마다 한 번 실행하라. 출력을 합칠 때는 「최종 판정 순서」에 따라 접근 실패, 존재 불일치와 구절 없음, 판정 실패와 판정 누락, 처음 판정의 불일치, 보충과 재판정, 판정 불가, 칸별 불일치 순서로 판정하라. 둘러보기는 `subagent_type: disciplined-coder:researcher`와 `MODE: scout` 프롬프트로 실행하고, 검색어의 질의 경계 검사도 직접 하라. 둘러보기 출력에 계약 코드의 `scout` 칸만 있는지 확인해 다른 칸이 섞여 있으면 둘러보기 실패로 처리하라. 실행 전에 `intended_use`가 비어 있지 않은지 확인하고, 연구자 하나의 인용 URL 이 30개를 넘으면 앞의 30개만 검증한 뒤 제외한 수를 기록하라. 이 경로에서는 검사·분리·통합이 지시 준수에만 의존하므로 그 사실을 보고와 기록에 명시하라.

## 발동과 기록

선행연구 스킬의 발동, 직접 요청, 판정 기록, 서브 세션 처리 규칙은 여기가 소유한다. 선행연구 스킬은 렌즈가 아니므로 `lens-review`의 「카테고리와 렌즈」를 적용하지 않는다.

**발동.** `lens-review`의 「설계 문서」·「전달 문서」 발동 기준에 해당하면 아래 묻지 않는 실행의 상한 안에서 승인을 묻지 말고 바로 실행하라. 2026-11-02 사용자 지시에 따라 프로토콜 승인이나 일반화한 검색어의 웹 검색 승인은 묻지 않는다. 렌즈가 실행 중이면 결과를 받은 뒤 실행해 동시 실행 4개 상한을 지켜라.

**묻지 않는 실행의 상한.** 사용자가 직접 요청하지 않은 실행(`lens-review` 의 선행연구, 공백 라운드, 서브 세션 보고에 따른 실행)은 하위 질문이 4개 이하일 때만 묻지 않고 실행하라. 4개를 넘으면 원칙 `ROLES` 에 따라 예상 호출 수(연구자 수와 URL 마다 검증 호출 2~4개)를 적어 사용자에게 물어라. 한 번 실행에 약 0.5달러가 들어 하위 질문이 늘면 사용자 모르게 비용이 커지기 때문이다.

**직접 요청.** 사용자가 선행연구를 직접 요청하면 곧바로 실행하라.

**판정 기록.** `lens-review`를 실행한 차수의 기록에는 선행연구 스킬의 실행 여부와 이유를 적어라. 실행하지 않은 사실이 누락되지 않게 하기 위해서다.

**서브 세션.** `nested-orchestration`의 서브 세션은 선행연구 스킬을 직접 실행하지 말고 발동 기준에 해당한 사실만 리포트에 적어 현재 세션에 넘겨라. 현재 세션은 위 묻지 않는 실행의 상한 안에서 묻지 않고 실행하라. 여러 서브 세션에서 웹 탐색이 중복 실행되는 상황을 피하기 위해서다.

## 상황별 전략

1단계에서 아래 표로 상황을 판정하고 대조 대상, 하위 질문 분해 방식, 모드를 정하라. 상황 목록은 2026-10-18에 사용자가 확정했다.

| 상황 | 발동 경로 | 대조 대상 | 하위 질문 분해(기본값) | 모드 |
|---|---|---|---|---|
| spec 대조 | `lens-review` 「설계 문서」 | spec 의 메커니즘 | 핵심 메커니즘마다 하나 | `contrast` |
| 제안서 검진 | `lens-review` 「전달 문서」 | 문서가 주장하는 방법 | 주장하는 방법마다 하나 | `contrast` |
| 기존 도구 탐색 | 사용자 직접 요청("쓸 만한 것 없나") | 사용자가 만들려는 대상 | 검색 경로마다 하나(목록 사이트, 저장소, 논문) | `survey` |
| 결정 근거 탐색 | 사용자 직접 요청("근거를 찾아 달라", "어떻게 배치해야 하나") | 사용자가 고르려는 결정 후보안 | 결정의 근거 주제마다 하나 | `survey` |
| 사실 확인 | 사용자 직접 요청, 단일 사실 | 확인하려는 주장 | 나누지 않음 | `survey` |

상황이나 대조 대상을 하나로 정할 수 없으면 사용자에게 물어라. 표의 하위 질문 분해 열은 기본값이며, 둘러보기 결과에 따라 다르게 나눌 수 있다. 다르게 나눴다면 이유를 프로토콜에 적어라.

## 실행할 때 지킬 상한

탐색 모드 연구자 수, 연구자와 검증자의 턴 수, 공백 라운드 수는 아래 상한을 지켜라.

**상한 값.** 탐색 모드 연구자 수는 통상 2개, 최대 20개다. 2026-10-18에 사용자가 정한 값이므로 바꾸려면 사용자에게 물어라.

**통상을 넘을 때.** 통상 값까지는 이유 없이 고를 수 있고, 넘을 때는 프로토콜에 이유를 적어라. 하위 질문이 통상보다 많으면 하위 질문을 합치지 말고 연구자 수를 늘리는 근거를 적어라.

**세는 대상.** 상한에는 탐색 모드 연구자만 포함한다. 둘러보기 연구자는 하나로 고정되어 있고, 검증자와 종합 모드 연구자는 URL 수와 모드에 따라 정해지므로 상한에서 뺀다. 검증자 호출은 URL 마다 추출 1회와 보충 0~1회, 묶음마다 판정 1회와 재판정 0~1회다. 한 묶음의 주장은 20개 이하로 제한하되 한 URL 의 주장은 같은 묶음에 두고, 한 URL 의 주장이 20개를 넘으면 그 URL 만으로 별도 묶음을 만든다(2026-10-22 사용자 결정, 근거와 측정 계획은 spec 「Opus 일괄 판정」 참조). 판정 묶음에는 추출 통과 주장만, 재판정 묶음에는 보충 통과 주장만 넣으며 보충은 주장마다 한 번만 한다. 검증자 수는 탐색이 끝나야 정해지므로 프로토콜에는 연구자 수만, 보고에는 실제 검증자 수를 적어라. 연구자 하나의 인용 출처는 약 100개 이하로 제한하며, 이는 Anthropic cookbook 의 research subagent 프롬프트 기준("under about 100 sources")을 따른 값이다.

**동시 실행 상한.** 선행연구도 렌즈와 동일하게 동시 실행 상한 4개를 지켜라. 2026-11-16 PC 메모리 부족으로 작업이 두 번 중단된 뒤 사용자가 정한 상한이며, 2026-10-18 예외(런타임 기본 16)를 대체한다. 워크플로는 모든 단계의 호출을 4개씩 나눠 순차 실행하며, 워크플로가 꺼진 환경에서도 같은 상한을 지켜라.

**비용 상한.** 하위 질문이 20개를 넘으면 워크플로가 실행을 거부한다. 연구자 하나의 인용 URL 이 30개를 넘으면 앞의 30개만 검증하고, 나머지는 반환값의 `url_trimmed` 에 남기며 `unverifiable`로 집계한다(`workflows/prior-art-search.js` 상수). 실행이 거부되면 하위 질문을 좁히거나 나눠 다시 실행할지 사용자에게 물어라. `url_trimmed` 가 비어 있지 않으면 제외한 URL 수를 기록과 보고에 적어라.

**턴 상한.** 연구자와 검증자 정의의 `maxTurns`는 20 이며, 같은 cookbook 프롬프트의 도구 호출 상한 20회를 따른 값이다. 공식 문서가 `maxTurns`를 "agentic turns"로만 정의해 도구 호출과의 관계를 밝히지 않으므로, 도구 호출 20회 상한을 연구자 프롬프트 지시에도 넣어 두었다. 턴 상한에 도달해 출력을 내지 못한 연구자는 3단계 연구자 실패로 처리하라.

**공백 라운드 상한.** 공백 라운드는 연구 질문당 1회까지다. 이 PC에 설치된 Anthropic deep-research 스킬의 추가 라운드 제한("This step can only be followed once")을 따른다.

## 판정 규약

아래에서 '이 설계'는 대조 대상(spec·제안서의 방법, 사용자가 만들려는 대상, 결정 후보안)을 가리킨다. 연구자는 다음 체크리스트, 축별 대조, 가드로 판정한다.

**체크리스트**

- **기시감** — 이 설계의 핵심 메커니즘에 해당하는 선행 사례가 연구·상용 제품·오픈소스에 있는가.
- **결말** — 그 사례는 성공했는가, 실패했는가, 판정에 이르지 못했는가.
- **전이** — 그 실패 원인이 이 설계에도 남아 있는가.
- **기준선** — 선행 사례가 쓴 단순한 기준선이 있는데 이 설계가 비교하지 않았는가.
- **붐빔** — 이미 상용화되었거나 표준이 된 기술을 처음부터 다시 만들려 하는가.

**전이** — 해당하면 이슈다.

대조는 네 축으로 나눠 판정한다. 선행 사례와 이 설계의 목적(무엇을 이루려는가), 메커니즘(어떻게 이루는가), 평가(무엇으로 성공을 판정하는가), 적용 대상(어디에 쓰는가)이 같은지 다른지를 각각 적는다. 네 축이 모두 같아야 같은 사례이며, 하나라도 다르면 차이를 `evidence`에 적는다. 축을 나누지 않으면 겉만 비슷한 사례를 선행 사례로 오인하기 쉽다. 축의 일치 여부는 선행 사례 전체와 대조 대상 전체를 비교해 정하고, 대조 대상의 구성요소 하나와만 같은 축은 다르다고 적은 뒤 그 구성요소를 밝힌다.

`survey` 모드에서는 체크리스트가 선택 사항이다. 연구자는 축이 다른 행도 근거 지도에 넣고, 다른 축과 그 차이가 근거의 이전 가능성에 미치는 영향을 `note`에 적는다. 종합 연구자는 네 축이 모두 다른 행을 결론의 단독 근거로 쓰지 않는다.

**가드**

- 참신함은 채점하지 않는다. 선행 결과가 이 설계의 전제를 반박하거나 알려진 실패 원인이 이 설계에도 남아 있을 때만 이슈로 올린다.
- "찾지 못했다"를 "존재하지 않는다"로 쓰지 않는다. 찾지 못한 항목은 `not_found`에 이유와 함께 적고 독창성의 근거로 삼지 않는다.
- 못 찾음만큼 오인도 차단한다. 네 축 중 하나라도 다르면 차이를 명시하고 같은 사례로 단정하지 않는다. 못 찾음은 설계를 바꾸지 않지만 오인은 멀쩡한 설계를 지운다.
- `weak-baseline`은 비교만 요구하며 구현을 요구하지 않는다. 이 유형의 `claim`은 "이 기준선과 비교되지 않았다"까지만 적고 구현 방법을 적지 않는다.
- 인용한 URL은 실제로 열어 확인하고 출처의 성격을 구분해 적는다. 열지 못했으면 `opened`를 거짓으로 두고 `disclosures`에 적는다. 스스로 계산하거나 추론한 값은 `derived`로 표시한다.
- 질의 경계를 지킨다. 검색어에는 일반화한 기술 용어와 공개 개념만 넣고, 고유명사·파일 경로·사내 식별자·미공개 제품명·사람 이름·코드 조각은 넣지 않는다. 검색 질의는 제3자가 보관하는 로그이므로, 이 경계 안에서 대조할 수 없으면 질의를 넓히지 말고 `not_found`에 "질의 경계 때문에 확인하지 못했다"고 적는다.

연구자는 가드의 "인용한 URL은 실제로 열어 확인하고 출처의 성격을 구분해 적는다"를 그대로 따르고, 검증자는 연구자가 적은 결과를 다시 판정한다.

## 출력 스키마

필드 이름과 최상위 형식의 원본은 계약 코드 `scripts/prior_art_contract.json` 이다. 출력 예시는 각 에이전트 정의 파일에 있다(연구자·종합·둘러보기는 `agents/researcher.md`, 추출·보충은 `agents/citation-verifier.md`, 판정은 `agents/citation-judge.md`). 워크플로 스키마, 프롬프트 형식, 단계 출력 통합 코드는 `workflows/prior-art-search.js` 에 있다. 세 파일이 계약 코드와 일치하는지는 `scripts/test_prior_art_contract.sh` 가 검사한다. 이 절에서는 계약 코드에 없는 의미만 설명한다.

**검색 상태.** `search_status`는 빈 `issues`가 어떤 사유로 나왔는지 구별한다.

| 값 | 뜻 | 빈 `issues`의 해석 |
|---|---|---|
| `ok` | 검색을 실행했고 결과도 있었다 | 선행 사례를 확인했으나 문제가 없었다는 뜻이므로 판정에 쓸 수 있다 |
| `no-results` | 검색은 실행했으나 아무것도 찾지 못했다 | 판정이 아니다. `not_found`에 이유를 적어야 한다 |
| `failed` | 도구 오류나 접근 차단이 발생했다 | 판정이 아니다. 검색 실패로 보고한다 |
| `not-attempted` | 검색을 시도하지 않았다 | 판정이 아니다. 검색을 실행하지 않은 상태로 본다 |

**주장 참조.** 형식은 `<하위 질문 ID>#<issue|case>#<배열 위치>`이며, 배열은 연구자 출력의 `issues` 또는 `evidence_map`이다. 종합 모드 연구자는 통과 행만으로 근거 지도를 다시 만들고, 각 결론의 근거가 된 행의 주장 참조를 `refs`에 적는다.

**판정 대상과 기준.** 판정 대상은 선행 사례 서술에 한정한다. 이슈는 `prior_claim`, 근거 지도 행은 사례 이름·`outcome`·각 축의 `prior`다. 판정 기준은 "옮긴 구절이 주장의 주어와 수치와 조건을 모두 포함하면 supported"로 고정한다. 대조 대상 판단(`same`, `note`, 이슈의 `claim`)은 연구자가 책임지고 사용자가 보고에서 확인한다(2026-10-18 사용자 결정). `unverifiable`은 봇 차단·유료 장벽·무응답 같은 원문 접근 문제만 뜻하며 반박으로 세지 않는다. 검증은 추출, 판정, 보충, 재판정 순으로 진행한다. 추출 검증자가 URL 하나를 열어 주장마다 접근·존재·구절을 확인하면, 판정 에이전트는 웹을 열지 않고 옮긴 구절만 보고 수치·조건, 방향, 범위 세 칸을 판정한다.

### 최종 판정 순서

최종 `verdict`는 워크플로 스크립트가 아래 순서대로 정하며 에이전트는 정하지 않는다. 워크플로가 꺼진 환경에서는 오케스트레이터가 이 순서를 직접 적용하라.

1. 추출 검증자가 무응답이거나 판정이 누락됐으면 해당 URL 은 검증 실패다.
2. `access`가 `실패`이면 `unverifiable`이다.
3. `exists`가 `불일치`이거나 `quote`가 비어 있으면 `unsupported`다.
4. 해당 URL 이 속한 판정 묶음이 무응답이거나, 그 URL 의 판정에서 세 칸 중 하나라도 빠졌으면 해당 URL 은 검증 실패다. 빠진 칸을 `일치`로 간주하지 않는다. 판정 출력에서 특정 주장만 빠졌으면 그 주장만 `verify_failed`다.
5. 첫 판정에 `불일치` 칸이 있으면 보충 없이 `unsupported`로 정한다.
6. `정보 부족` 칸이 있으면 보충과 재판정을 진행한다. 보충·재판정 무응답, 주장 누락, 보충 출력의 `access` `실패`, `exists` `불일치`, `quote` 누락 중 하나에 해당하면 그 주장만 `verify_failed`다. 재판정 결과는 기존 세 칸을 모두 대체한다. 재판정에 `불일치`가 있으면 `unsupported`이고, 재판정 뒤에도 `정보 부족`이 남으면 그 주장만 `unsupported`로 처리하며 `reason`의 `재판정 정보 부족:` 항목에 칸 이름을 남긴다.
7. 남은 칸에 `판정 불가`가 있으면 `unsupported`이며, 이유 유형은 통합 출력의 `reason`에 남긴다.
8. 위 어디에도 해당하지 않으면 `supported`다.

**판정 모델 교체.** 단계별 출력 형식은 모델과 무관하므로 추출 검증자와 판정 에이전트 정의의 `model`만 바꾸면 단계별로 다른 모델을 쓸 수 있다. 현재 구성은 판정 에이전트 `claude-opus-5-5`(노력 수준 medium), 추출 검증자 `claude-haiku-5-5`(노력 수준 high)이며 검증 측정도 이 ID 로 마쳤다. Bedrock·Vertex 처럼 모델 ID 형식이 다르거나 Opus 를 쓸 수 없는 계정에서는 사용자가 `agents/citation-verifier.md`·`agents/citation-judge.md` 의 `model` 을 바꿔야 하며, 바꾼 뒤 다시 측정한다. Kim 등(ICML 2025)은 제공사가 달라도 모델 간 오류 상관이 높다고 보고했으므로 모델을 바꿔도 상관 오류가 줄어든다고 기대하지 마라. 사내 문서를 외부 API 로 보내는 모델은 구성에 넣기 전에 회사 승인을 받아라.

## 인용 확인

인용 확인은 검증자와 오케스트레이터가 나눠 맡는다(2026-10-18 사용자 결정). 연구자가 늘면 오케스트레이터 혼자 인용 수십 건을 모두 열어 확인하기 어렵기 때문이다.

추출 검증자가 옮긴 `quote`가 원문에 실제로 있고 주장을 뒷받침하는지 직접 열어 확인하라. 통합 출력의 `quote`가 확인 대상이며, 보충을 거친 주장이면 보충 구절을 본다. 판정 불가로 기각된 주장은 `reason`의 `판정 불가:` 항목에 칸과 이유 유형이, 재판정 정보 부족으로 기각된 주장은 `reason`의 `재판정 정보 부족:` 항목에 칸 이름이 적혀 있다. 이 두 유형의 기각은 반박된 주장으로 보고하지 말고, 구절이 주장을 뒷받침한다는 확인이 없어 기각됐다고 보고하며 건수도 반박된 주장과 따로 적어라. 확인할 인용 범위는 상황에 따라 다르다. spec 대조와 제안서 검진에서는 문서를 실제로 고치게 만든 발견, 처분 `사용자` 로 올릴 발견, 사용자에게 전달할 발견이 근거로 삼은 인용을 모두 확인하라. 기존 도구 탐색, 결정 근거 탐색, 사실 확인에서는 보고의 결론 문장에 직접 쓰는 인용만 확인하고 근거 지도의 나머지 행은 검증자 판정을 그대로 써라.

이 절이 인용 확인 범위의 원본이다.

## 레퍼런스 프롬프트

연구자 정의 파일의 contrast 지시문에는 아래 `- system:` 줄을, survey 지시문에는 `- system (survey):` 줄을, `scout` 모드 지시문에는 `- system (scout):` 줄을 한 줄 그대로 싣는다. 사용자 메시지 형식은 워크플로의 프롬프트 형식을 따른다.

- system: "너는 선행연구 대조 검수자다. 기시감(이 설계를 누가 이미 해봤는지)과 결말(그 결과가 무엇이었는지)과 전이(그 실패 원인이 이 설계에도 있는지)를 찾아라. 선행 사례가 쓴 단순한 기준선이 있는데 이 설계가 그것과 비교조차 안 했는지, 그리고 붐빔(이미 상용화되거나 표준이 된 것을 처음부터 다시 지으려 하는지)도 함께 보라. 참신함을 채점하지 마라. 못 찾은 것은 `not_found`에 적고 독창성의 근거로 삼지 마라. 선행 사례는 목적·메커니즘·평가·적용 대상 네 축으로 대조하라. 모든 주장에 출처 URL과 그 성격을 달고 실제로 열어 확인하라. 질의에 고유명사와 경로와 사내 식별자를 넣지 마라. 체크리스트를 항목마다 따로 검토하고 그 결과를 한 번에 돌려주며, 검토한 관점을 `notes`에 적어라. 서브에이전트를 새로 열지 마라. 더 확인해야 할 것이 남으면 무엇을 왜 확인해야 하는지 `notes`에 적어라. 등급을 매기지 마라. 발견마다 이 불일치 때문에 지금 무엇이 그렇게 되어 있는지(consequence)와 그렇게 본 근거(evidence)를 적어라. 결과를 구체적으로 못 적는 것은 올리지 마라. 찾은 것이 없으면 빈 목록이 정상이다. 네 축 중 하나라도 다르면 그 차이를 적고 같은 사례로 단정하지 마라. 출처의 성격은 `citations`의 `kind`로 적고, 열지 못한 출처는 `opened`를 false 로 두어라. 입력의 `forbidden_terms`에 든 낱말도 질의에 넣지 말고, 실행한 검색어는 빠짐없이 `queries`에 적어라. 도구 호출은 20회 이하로, 인용할 출처는 약 100개 이하로 두어라. `evidence_map`은 빈 배열로 두어라. 입력의 `intended_use`와 `constraints`를 읽고, `constraints`의 기각한 대안과 이미 확인한 자료는 다시 찾아 보고하지 마라. 마지막 세 번의 검색에서 새 사례가 몇 건 나왔는지를 `saturation`에 적어라. 출력은 연구자 출력 JSON 하나로만 내고 앞뒤에 다른 글을 두지 마라."
- system (survey): "너는 결정 근거 수집자다. 입력의 `intended_use`가 정하는 결정과 기준을 먼저 읽고, 자기 하위 질문 범위에서 그 결정에 쓸 선행 사례와 근거를 찾아라. `intended_use`는 근거의 우선순위 기준으로 쓰고, `intended_use`와 맞지 않아 뺀 근거는 `notes`에 사유와 함께 남겨라. 입력의 `constraints`를 읽고, `constraints`의 기각한 대안과 이미 확인한 자료는 다시 찾아 보고하지 마라. 찾은 사례마다 `evidence_map` 행을 채워라. 축이 다른 행도 근거 지도에 넣어라. 네 축(목적·메커니즘·평가·적용 대상)이 대조 대상과 모두 같지 않아도 된다. 다른 축은 `note`에 적고, 그 차이 때문에 근거를 이 결정에 옮겨 쓰기 어려운지도 적어라. 후보안 사이의 결정이면 행마다 그 근거가 어느 후보안을 어느 방향으로 움직이는지 `bearing`에 적어라. 기시감·결말·전이·기준선·붐빔 체크리스트는 도움이 될 때만 골라 써라. 반박이나 실패를 발견했을 때만 `issues`에 올려라. 탐색 방법은 하위 질문에 맞게 네가 골라라. 고를 수 있는 방법에는 짧고 넓은 검색어로 시작해 좁혀 가기, 후보안마다 사용 사례와 결말 찾기, 인용 따라가기(찾은 출처의 참고문헌과 그 출처를 인용한 자료를 따라가는 snowballing), 실패·포기·회고 자료 찾기가 있다. 고른 방법을 `notes`에 적어라. 모든 근거에 출처 URL과 그 성격을 달고 실제로 열어 확인하라. 열지 못한 출처는 `opened`를 false 로 두어라. 못 찾은 것은 `not_found`에 이유와 함께 적고 독창성의 근거로 삼지 마라. 질의에 고유명사와 경로와 사내 식별자를 넣지 말고, 입력의 `forbidden_terms`에 든 낱말도 질의에 넣지 마라. 실행한 검색어는 빠짐없이 `queries`에 적어라. 서브에이전트를 새로 열지 마라. 도구 호출은 20회 이하로, 인용할 출처는 약 100개 이하로 두어라. 마지막 세 번의 검색에서 새 사례가 몇 건 나왔는지를 `saturation`에 적어라. 출력은 연구자 출력 JSON 하나로만 내고 앞뒤에 다른 글을 두지 마라."
- system (scout): "너는 선행연구 둘러보기 연구자다. 목표는 입력 `question`과 `target`의 주제에 어떤 자료 묶음이 있는지 확인하고 하위 질문 후보를 내는 일이다. 입력의 `draft_subquestions`는 오케스트레이터가 쓴 하위 질문 초안이고, `intended_use`와 `constraints`는 결과의 용도와 이미 정한 조건이다. 출력의 `clusters`에는 주제 묶음마다 `topic`, 대표 출처 URL 목록 `sources`, 묶음 설명 `note`를 적어라. `subquestion_candidates`에는 하위 질문 후보마다 범위 문장 `scope`와 그 후보를 낸 근거 `basis`를 적어라. 사례마다의 판정, 이슈, 근거 지도는 내지 마라. 질의에 고유명사와 경로와 사내 식별자를 넣지 말고, 입력의 `forbidden_terms`에 든 낱말도 질의에 넣지 마라. 실행한 검색어는 빠짐없이 `queries`에 적어라. 도구 호출은 10회 이하로 두어라. 서브에이전트를 새로 열지 마라. 출력은 둘러보기 출력 JSON 하나로만 내고 앞뒤에 다른 글을 두지 마라."
