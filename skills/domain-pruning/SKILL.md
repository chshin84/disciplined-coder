# 규모와 과잉 판정 도메인 참고서

에이전트와 함께 만든 프로젝트는 세션마다 테스트·스크립트·문서가 쌓인다. 이 참고서는 무엇이 과한지 가리는 판정 질문과 그 출처를 둔다. 플러그인의 훅과 상시 지시에 대한 기준은 `domain-plugin`이 소유한다.

## 판정 질문

판정 질문은 2026-10-05에 선행연구로 모았고, 출처마다 성격이 달라 수치를 그대로 옮기지 않는다. 근거가 밝혀지지 않은 기준값(테스트를 지우는 경과 일수 등)은 두지 않는다(`EVIDENCE-FIRST`).

- **표현에 깨지는 테스트** — 동작과 계약이 그대로인데 문구만 바꿔도 실패하는 검사는 brittle test(결함 없이 실패하는 테스트)이므로 줄인다. 문서 대조 검사는 조항 ID·절 제목·소유 선언 같은 열쇠로 판정하고 문장을 박지 않는다. 금지어 목록처럼 문자열 자체가 계약인 검사는 예외다([Software Engineering at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html), [Sensitive Equality](https://test-smell-catalog.readthedocs.io/en/latest/Issues%20in%20test%20steps/Issues%20in%20assertions/Sensitive%20Equality.html)).
- **구현을 박는 테스트** — 메시지 문구, 내부 변수 이름, 입력을 읽는 방식처럼 동작이 아닌 구현 세부를 고정하는 검사는 줄인다. 이상적인 테스트는 요구사항이 바뀔 때만 바뀐다(같은 12장).
- **중복과 항진** — 다른 검사가 같은 사실을 보면 하나만 남기고, 무엇을 고쳐도 참인 단언은 지운다. 실제로 지워진 테스트 24,431건의 대부분은 대상이 사라진 테스트와 중복 테스트였다([MSR 2025](https://2025.msrconf.org/details/msr-2025-technical-papers/24/Understanding-Test-Deletion-in-Java-Applications)).
- **실패 이력** — 한 번도 실패하지 않았다는 사실은 실행 빈도를 낮출 근거이고 지울 근거가 아니다. Google 에서 테스트 대상의 91.3%가 실패한 적이 없었다([Memon 외 2017](https://huang.isis.vanderbilt.edu/cs8395-f23/paper/google-testing-icse-seip-17.pdf)). 일회성 재발 방지 검사를 지울지는 이 근거와 별개로 사용자가 정한다.
- **셸 스크립트의 길이** — 100줄을 넘거나 제어 흐름이 단순하지 않은 셸 스크립트는 구조적인 언어로 옮길지 따진다. 업체 규범이며 실증 연구는 아니다([Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html)).
- **에이전트 산출물의 비대** — 에이전트가 쓴 변경은 사람의 변경보다 컸고, 원인은 장황한 구현·범위 확장·과잉 방어 코드·과잉 문서화였다. 리뷰에서 이 네 원인을 하나씩 찾는다([arXiv 2608.12355](https://arxiv.org/pdf/2608.12355)).
- **문서와 기록의 수명** — 결정 기록은 짧게 두고 고치지 않으며 대체되면 표시한다([Microsoft ADR](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)). 쓸모가 끝난 작업 문서는 지우거나 폐기 표시한다([Software Engineering at Google 10장](https://abseil.io/resources/swe-book/html/ch10.html)). 기록은 보존 기간을 정하고, 기간이 지나면 원래 저장소 밖으로 옮긴다([NIST SP 800-92](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-92.pdf)). 에이전트원칙의 「문서 타입과 수명」이 문서 수명을 정하는 프로젝트에서는, 그 표와 다르게 처분하려면 사용자에게 묻는다.

## 분류

같은 대상을 누가 다시 봐도 같은 판정이 나오도록, 줄일 대상은 아래 분류 중 하나로만 판정한다. 분류마다 판정 질문 하나를 묻고, 근거 한 줄과 지웠을 때 잃는 보호를 함께 적는다. 검사 하나가 조건 여럿을 이어 붙였으면 조건마다 따로 판정하고, 지울 조건만 지운다. 남는 조건이 없을 때만 검사를 지운다.

| 분류 | 판정 질문 | 처분 |
|---|---|---|
| 유지 | 코드 동작이나 문서가 선언한 계약(소유 선언·ID·절 제목·사용자 설정 보호·차단 훅)을 지키는가 | 남긴다 |
| 문구고정 | 문장·굵은 라벨·낱말 하나가 있는지 없는지를 보며, 뜻을 지킨 채 표현만 바꿔도 실패하는가 | 지운다. 금지어 목록처럼 문자열 자체가 계약이면 유지로 본다 |
| 구현고정 | 동작이 아니라 메시지 문구·내부 변수·입력을 읽는 방식·코드 구조를 grep 하는가 | 지운다 |
| 중복 | 이 검사가 잡는 결함을 넣었을 때 다른 검사도 반드시 실패하는가. 파일·절이 있는지만 보는 검사는, 그 파일을 실행하거나 그 절의 내용을 보는 검사가 따로 있으면 여기 든다 | 지운다. 합치려면 새 코드가 필요하면 이번 차수에서 하지 않고 따로 적는다 |
| 항진 | 무엇을 고쳐도 참인가 | 지운다 |
| 일회성 | 옛 이름·옛 절·옛 문구가 없다는 부정 조건으로, 과거 한 번의 변경이 되돌아가지 않는지만 보는가 | 사용자가 정한다. 실패한 적이 없다는 사실은 지울 근거가 아니다 |
| 사본 | 소유자가 있는 규칙을 다른 문서가 다시 적었는가 | 소유자를 가리키는 문장으로 바꾼다 |
| 수명 끝 | 실행이 끝난 plan, 병합된 작업의 기록인가 | 보존 태그를 단 뒤 지운다. 차수 대조에 쓰는 최근 기록은 남긴다 |
| 이전 코드 | 옛 버전의 흔적을 치우는 코드인가 | 남은 흔적이 동작에 영향이 없으면 지운다. 낡은 지시를 싣는 흔적을 막으면 은퇴 조건을 적고 남긴다 |
| 판단보류 | 위 질문으로 정해지지 않는가 | 남기고 이유를 적는다 |

## 절차

감축 차수는 아래 순서를 따른다. 앞 단계의 산출물이 뒤 단계의 입력이므로 순서를 바꾸지 않는다.

1. **목록** — 대상을 파일과 줄로 늘어놓는다.
2. **판정표** — 항목마다 분류, 근거 한 줄, 지웠을 때 잃는 보호를 적는다. 판정표는 그 차수의 커밋 메시지나 보고에 싣는다.
3. **범위** — 사용자가 처분할 분류를 정한다. 문구고정·구현고정·중복·항진은 기본으로 지우고, 일회성과 판단보류는 사용자가 정한다.
4. **적용** — 정한 범위만 고친다. 쓰이지 않게 된 변수·헬퍼·주석도 함께 지운다.
5. **결함 주입** — 프로젝트의 핵심 계약마다 일부러 결함을 하나씩 넣어, 남은 검사가 실패하는지 확인하고 되돌린다. 감축 전 버전도 같은 결함에 실패하지 않으면 그 공백은 감축 전부터 있던 것으로 적는다.
6. **전체 검사** — 프로젝트의 검사 전체와 플러그인 검증을 실행한다.

## 재현성 확인

정의만 받은 다른 실행자가 감축 전 버전을 다시 판정해, 실제 처분과 지움·남김이 얼마나 일치하는지 센다. 일치하지 않은 항목이 몰린 분류는 판정 질문을 고친다. 2026-10-06 첫 측정(`test_audit.sh` 검사 115건)은 일치 78%, 카파 0.43이었고, 불일치는 중복의 범위와 조건이 섞인 검사에 몰렸다. 그래서 중복을 결함 기준으로 고쳐 묻고 섞인 검사는 조건마다 판정하게 했다. 고친 정의로 두 실행자가 따로 판정하자 서로 95% 일치했고 카파는 0.87이었다(Landis·Koch 1977 기준 거의 완전한 일치). 두 실행자 모두 실제 처분과는 78% 일치했으므로, 어긋남은 정의보다 그날의 처분이 정의를 덜 적용한 데서 나왔다. 두 실행자가 모두 지우라고 했는데 실제로 남긴 검사는 주로 다른 검사가 실행해 보는 스크립트의 존재 확인과 JSON 형식 확인이었다.

## 렌즈와 문서의 연결

이 참고서의 분류는 아래 장치가 근거를 낸다. 어느 장치도 처분을 스스로 하지 않고, 처분은 「절차」의 범위 결정을 따른다.

| 분류 | 근거를 내는 장치 |
|---|---|
| 설계 단계의 과잉(테스트·스크립트·문서·훅을 늘리는 spec) | `lens-adversarial`의 과설계 항목이 이 참고서와 `domain-plugin`을 근거로 지적한다 |
| 사본 | 레포 문서 감사에서 `lens-consistency`의 `duplication` 발견 |
| 수명 끝 | `lens-fit`이 고른 문서 타입(`doc_type`)과 에이전트원칙 「문서 타입과 수명」의 행 |
| 문구고정·구현고정·중복·항진·일회성 | 이 참고서의 「절차」를 따르는 판정표. 렌즈 없이 프로젝트의 테스트를 읽는 실행자가 낸다 |
| 결함 주입의 핵심 계약 | 프로젝트가 정한다. 이 저장소는 `CLAUDE.md`의 「변경 뒤 실행」이 적는다 |

## 판정 사례

2026-10-06 감축에서 기준을 넘었지만 유지한 판정이다. 같은 질문이 다시 나오면 이 판정을 출발점으로 쓴다.

- **셸 스크립트 100줄** — 100줄을 넘는 셸 파일 12개를 다시 쓰지 않았다. 훅은 도구 호출마다 실행되는데 이 PC에서 빈 프로세스가 8밀리초, 파이썬이 71밀리초였고, 테스트를 다시 쓰는 위험이 이득보다 컸다.
- **상시 지시 200줄** — 상황 한정 절을 스킬로 옮기지 않았다. 캐시를 쓰면 상시로 둔 지시는 요청마다 캐시 읽기 값만 들고, 옮긴 지시는 쓰는 세션에서 결국 같은 값이 든다. 문서를 자주 고치는 사용자에게는 절감이 없었다.
- **두 렌즈의 통합** — `lens-grounding`과 `lens-fit`을 합치지 않았다. 입력(출처와 계약)이 다르고, 런타임 리뷰는 출력 종류마다 둘 중 하나만 고른다.
