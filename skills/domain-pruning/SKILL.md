# 규모와 과잉 판정 도메인 참고서

에이전트와 작업하면 세션마다 테스트·스크립트·문서가 쌓인다. 과한 대상을 판별할 때 아래 판정 질문과 출처를 참고하라. 플러그인의 훅과 상시 지시 기준은 `domain-plugin`이 소유한다.

## 판정 질문

이 저장소에서 2026-10-05에 선행연구로 아래 판정 질문을 모았다. 출처마다 성격이 다르므로 수치를 그대로 쓰지 마라. 근거 없는 기준값(테스트를 지우는 경과 일수 등)도 두지 마라.

**표현에 깨지는 테스트** — 동작과 계약은 그대로인데 문구만 바꿔도 실패하는 검사는 brittle test(결함 없이 실패하는 테스트)이므로 줄여라. 문서 대조 검사는 조항 ID·절 제목·소유 선언 같은 식별자로 판정하고 문장을 고정하지 마라. 금지어 목록처럼 문자열 자체가 계약인 검사는 예외다([Software Engineering at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html), [Sensitive Equality](https://test-smell-catalog.readthedocs.io/en/latest/Issues%20in%20test%20steps/Issues%20in%20assertions/Sensitive%20Equality.html)).

**구현을 고정한 테스트** — 메시지 문구, 내부 변수 이름, 입력 읽기 방식처럼 동작이 아닌 구현 세부를 고정한 검사는 줄여라. 이상적인 테스트는 요구사항이 바뀔 때만 바뀐다(같은 12장).

**중복과 항진** — 다른 검사가 같은 사실을 확인하면 하나만 남기고, 무엇을 고쳐도 참인 단언은 지워라. 지워진 테스트 24,431건의 대다수는 대상이 사라졌거나 중복된 테스트였다([MSR 2025](https://2025.msrconf.org/details/msr-2025-technical-papers/24/Understanding-Test-Deletion-in-Java-Applications)).

**실패 이력** — 실패한 적이 없다는 사실은 실행 빈도를 낮출 근거일 뿐 지울 근거가 아니다. Google에서 테스트 대상의 91.3%가 실패한 적이 없었다([Memon 외 2017](https://huang.isis.vanderbilt.edu/cs8395-f23/paper/google-testing-icse-seip-17.pdf)). 일회성 재발 방지 검사는 지울지가 가치 판단이므로 사용자에게 물어라(「분류」의 일회성 행).

**셸 스크립트의 길이** — 100줄을 넘거나 제어 흐름이 복잡한 셸 스크립트는 구조적인 언어로 옮길지 검토하라. 실증 연구가 아닌 업체 규범이다([Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html)).

**에이전트 산출물의 비대** — 에이전트 변경은 사람 변경보다 컸고, 원인은 장황한 구현·범위 확장·과잉 방어 코드·과잉 문서화였다. 리뷰에서 이 원인을 하나씩 찾아라([arXiv 2608.12355](https://arxiv.org/pdf/2608.12355)).

**문서와 기록의 수명** — 결정 기록은 짧게 두고 고치지 말며, 대체되면 표시하라([Microsoft ADR](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)). 쓸모가 끝난 작업 문서는 지우거나 폐기 표시하라([Software Engineering at Google 10장](https://abseil.io/resources/swe-book/html/ch10.html)). 기록은 보존 기간을 정하고 지나면 원래 저장소 밖으로 옮겨라([NIST SP 800-92](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-92.pdf)). `managing-docs`의 「문서 타입과 수명」 표로 문서 수명을 정하는 프로젝트에서는 그 표대로 처분하라.

## 분류

누가 다시 봐도 같은 판정이 나오도록 아래 분류 중 하나로만 판정하라. 분류마다 판정 질문으로 확인하고, 근거 한 줄과 지웠을 때 잃는 보호를 함께 적어라. 검사 하나에 조건이 여럿이면 조건마다 판정해 지울 조건만 지우고, 남는 조건이 없을 때만 검사를 지워라.

| 분류 | 판정 질문 | 처분 |
|---|---|---|
| 유지 | 코드 동작이나 문서 계약(소유 선언·ID·절 제목·사용자 설정 보호·차단 훅)을 지키는가 | 남겨라 |
| 문구고정 | 문장·굵은 라벨·낱말 유무만 보며, 뜻을 유지한 채 표현만 바꿔도 실패하는가 | 지워라. 금지어 목록처럼 문자열 자체가 계약이면 유지로 판정하라 |
| 구현고정 | 동작이 아니라 메시지 문구·내부 변수·입력 읽기 방식·코드 구조를 grep 하는가 | 지워라. 알림이 그 분기에서 관측되는 유일한 동작이고 다른 검사가 그 알림을 보지 않으면 유지로 판정하라 |
| 중복 | 이 검사가 잡는 결함을 넣었을 때 다른 검사도 반드시 실패하는가(파일·절의 존재만 보는 검사는 그 파일을 실행하거나 내용을 보는 검사가 따로 있으면 해당한다) | 지워라. 합칠 새 코드가 필요하면 이번 차수에서 하지 말고 따로 적어라 |
| 항진 | 무엇을 고쳐도 참인가 | 지워라 |
| 일회성 | 옛 이름·옛 절·옛 문구가 없다는 부정 조건으로 과거 변경이 되돌아가지 않는지만 보는가 | 권장안을 붙여 사용자에게 물어라. 실패한 적이 없다는 사실은 지울 근거가 아니다 |
| 사본 | 소유자가 있는 규칙을 다른 문서에 다시 적었는가 | 소유자를 가리키는 문장으로 바꿔라 |
| 수명 끝 | 실행이 끝난 plan, 병합된 작업의 기록인가 | 보존 태그를 단 뒤 지워라. 차수 대조에 쓰는 최근 기록은 남겨라 |
| 이전 코드 | 옛 버전의 흔적을 치우는 코드인가 | 남은 흔적이 동작에 영향이 없으면 지워라. 낡은 지시를 싣는 흔적을 차단하면 은퇴 조건을 적고 남겨라 |
| 판단보류 | 위 질문으로 정해지지 않는가 | 남기고 이유를 적어라 |

## 절차

감축 차수는 아래 순서대로 진행하라. 앞 단계 산출물을 뒤 단계에서 쓰므로 순서를 바꾸지 마라.

**1. 목록** — 대상을 파일과 줄로 정리하라.

**2. 판정표** — 항목마다 분류, 근거 한 줄, 지웠을 때 잃는 보호를 적어라. 판정표는 그 차수의 커밋 메시지나 보고에 실어라.

**3. 범위** — 분류 표의 처분을 기본값으로 진행하라. 문구고정·구현고정·중복·항진은 지우고, 판단보류는 남기고 이유를 적어라. 일회성만 사용자에게 묻되, 지금도 유효한 계약을 지키면 유지, 아니면 삭제를 권장안으로 붙여라. 사용자가 범위를 따로 정했으면 따르라.

**4. 적용** — 정한 범위만 고쳐라. 쓰이지 않게 된 변수·헬퍼·주석도 함께 지워라.

**5. 결함 주입** — 프로젝트의 핵심 계약마다 일부러 결함을 하나씩 넣어, 남은 검사가 실패하는지 확인하고 되돌려라. 감축 전 버전에서도 실패하지 않으면 감축 전부터 있던 공백으로 적어라.

**6. 전체 검사** — 프로젝트의 전체 검사와 플러그인 검증을 실행하라.

## 재현성 확인

정의만 받은 다른 실행자에게 감축 전 버전을 다시 판정하게 하고, 실제 처분과 삭제·유지가 얼마나 일치하는지 확인하라. 불일치가 몰린 분류는 판정 질문을 고쳐라.

2026-10-06 첫 측정(`test_audit.sh` 검사 115건)은 일치 78%, 카파 0.43이었고, 불일치는 중복 범위와 조건이 섞인 검사에 몰렸다. 그래서 중복은 결함 기준으로 고쳐 묻고, 섞인 검사는 조건마다 판정하게 했다.

고친 정의로 두 실행자가 따로 판정하자 서로 95% 일치했고 카파는 0.87이었다(Landis·Koch 1977 기준 거의 완전한 일치). 두 실행자 모두 실제 처분과는 78% 일치해, 불일치는 정의보다 당시 처분에서 정의를 덜 적용한 데서 나왔다. 두 실행자 모두 지우라고 했는데 남긴 검사는 주로 다른 검사가 실행하는 스크립트 존재 확인과 JSON 형식 확인이었다.

## 렌즈와 문서의 연결

이 참고서의 분류마다 근거를 제시하는 장치는 아래와 같다. 어느 장치도 직접 처분하지 않으며, 처분은 「절차」의 범위 단계를 따르라.

| 분류 | 근거를 제시하는 장치 |
|---|---|
| 설계 단계의 과잉(테스트·스크립트·문서·훅을 늘리는 spec) | `lens-adversarial`이 과설계 항목에서 이 참고서와 `domain-plugin`을 근거로 지적한다 |
| 사본 | `lens-adversarial`의 드리프트 지적(같은 대상을 두 곳에서 다른 이름이나 값으로 적은 곳) |
| 수명 끝 | `lens-grounding`이 고른 문서 타입(`doc_type`)과 `managing-docs` 「문서 타입과 수명」의 행 |
| 문구고정·구현고정·중복·항진·일회성 | 이 참고서의 「절차」대로 만든 판정표. 렌즈 없이 프로젝트 테스트를 읽는 실행자가 작성한다 |
| 결함 주입의 핵심 계약 | 프로젝트가 정한다. 이 저장소 기준은 `CLAUDE.md`의 「변경 뒤 실행」에 있다 |

## 판정 사례

2026-10-06 감축에서 기준을 넘었지만 유지한 사례다. 같은 질문이 다시 나오면 이 판정을 출발점으로 삼아라.

**셸 스크립트 100줄** — 100줄을 넘는 셸 파일 12개를 다시 쓰지 않았다. 훅은 도구 호출마다 실행되는데 이 PC에서 빈 프로세스가 8밀리초, 파이썬이 71밀리초였고, 테스트를 다시 쓰는 위험이 이득보다 컸다.

**상시 지시 200줄** — 상황 한정 절을 스킬로 옮기지 않았다. 캐시를 쓰면 상시 지시는 요청마다 캐시 읽기 비용만 들고, 옮긴 지시도 쓰는 세션에서 결국 같은 비용이 든다. 문서를 자주 고치는 사용자에게는 절감이 없었다.

**대조 렌즈의 통합** — 처음에는 입력(출처와 계약)이 달라 근거 렌즈와 형식 렌즈를 합치지 않았다. 2026-11-17에 접근 방식과 맥락 분리 필요에 따라 렌즈를 다시 나누면서 형식 계약을 `lens-grounding`으로 옮겼다. 두 입력은 `lens-review`가 `CRITERIA` 줄에 함께 넘기고, 런타임 출력 검토도 출력 종류와 무관하게 `lens-grounding` 하나를 쓴다.

**훅 알림 문구** — 같은 날 테스트 네 파일을 다시 판정할 때, 깨진 설정·갱신 실패·재시작 요구처럼 SessionStart 훅이 알림으로만 동작을 드러내는 검사는 남겼다. 이 검사를 지우면 알림이 조용히 사라지는 회귀를 어느 검사도 잡지 못한다.

**상시 계약인 부정 조건** — README에 훅 전용 변수가 없다는 검사와 지운 조항 ID가 근거 없이 되살아나지 않는다는 검사는 남겼다. 부정 조건이지만 지금도 유효한 계약을 지키므로 일회성으로 보지 않았다.
