# 규모와 과잉 판정 도메인 참고서

에이전트와 함께 만드는 프로젝트에는 세션마다 테스트·스크립트·문서가 쌓인다. 이 참고서는 과잉 여부를 가리는 판정 질문과 출처를 정리한다. 플러그인 훅과 상시 지시 기준은 `domain-plugin`이 소유한다.

## 판정 질문

이 저장소의 작업 세션이 2026-10-05에 선행연구에서 판정 질문을 모았다. 출처마다 성격이 다르므로 수치를 그대로 옮기지 마라. 테스트를 지우는 경과 일수처럼 근거가 밝혀지지 않은 기준값도 두지 마라.

**표현에 깨지는 테스트** — 동작과 계약이 그대로인데 문구 변경만으로 실패하면 brittle test(결함 없이 실패하는 테스트)이므로 줄여라. 문서 대조 검사는 문장을 고정하지 말고 조항 ID·절 제목·소유 선언 같은 핵심 키로 판정하라. 금지어 목록처럼 문자열 자체가 계약인 검사는 예외다([Software Engineering at Google 12장](https://abseil.io/resources/swe-book/html/ch12.html), [Sensitive Equality](https://test-smell-catalog.readthedocs.io/en/latest/Issues%20in%20test%20steps/Issues%20in%20assertions/Sensitive%20Equality.html)).

**구현을 박는 테스트** — 동작 대신 메시지 문구, 내부 변수 이름, 입력 읽기 방식 같은 구현 세부를 묶어 두는 검사를 줄여라. 이상적인 테스트는 요구사항이 바뀔 때만 달라진다(같은 12장).

**중복과 항진** — 같은 사실을 확인하는 검사가 여럿이면 하나만 남기고, 무엇을 바꿔도 참인 단언은 지워라. 실제로 삭제된 테스트 24,431건의 대부분은 대상이 사라진 테스트와 중복 테스트였다([MSR 2025](https://2025.msrconf.org/details/msr-2025-technical-papers/24/Understanding-Test-Deletion-in-Java-Applications)).

**실패 이력** — 한 번도 실패하지 않았다는 사실은 실행 빈도를 낮출 이유일 뿐 삭제 근거가 아니다. Google에서도 테스트 대상의 91.3%는 실패 이력이 없었다([Memon 외 2017](https://huang.isis.vanderbilt.edu/cs8395-f23/paper/google-testing-icse-seip-17.pdf)). 일회성 재발 방지 검사의 삭제 여부는 가치 판단이므로 사용자에게 물어라(「분류」의 일회성 행).

**셸 스크립트의 길이** — 100줄을 넘거나 제어 흐름이 단순하지 않은 셸 스크립트는 구조적인 언어로 옮길지 검토하라. 업체 규범일 뿐 실증 연구는 아니다([Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html)).

**에이전트 산출물의 비대** — 에이전트가 만든 변경은 사람보다 규모가 컸고, 원인은 장황한 구현·범위 확장·과잉 방어 코드·과잉 문서화였다. 리뷰할 때 이 원인들을 하나씩 점검하라([arXiv 2608.12355](https://arxiv.org/pdf/2608.12355)).

**문서와 기록의 수명** — 결정 기록은 짧게 써서 고치지 말고, 새 결정으로 대체되면 표시하라([Microsoft ADR](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)). 쓰임이 끝난 작업 문서는 삭제하거나 폐기 표시하라([Software Engineering at Google 10장](https://abseil.io/resources/swe-book/html/ch10.html)). 기록에는 보존 기간을 정해 두고, 만료되면 원래 저장소 밖으로 옮겨라([NIST SP 800-92](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-92.pdf)). `managing-docs`의 「문서 타입과 수명」이 문서 수명을 정하는 프로젝트라면 그 표대로 처분하라.

## 분류

누가 다시 봐도 같은 판정이 나오도록 감축 대상은 아래 분류 중 하나로만 판정하라. 분류마다 판정 질문 하나를 적용하고, 근거 한 줄과 삭제 시 잃는 보호를 함께 적어라. 조건 여럿을 이어 붙인 검사는 조건별로 판정해 지울 조건만 제거하고, 남는 조건이 없을 때만 검사 전체를 지워라.

| 분류 | 판정 질문 | 처분 |
|---|---|---|
| 유지 | 코드 동작이나 문서의 계약(소유 선언·ID·절 제목·사용자 설정 보호·차단 훅)을 지키는가 | 남겨라 |
| 문구고정 | 특정 문장·굵은 라벨·낱말 유무만 확인해 뜻이 같아도 표현을 바꾸면 실패하는가 | 지워라. 금지어 목록처럼 문자열 자체가 계약이면 유지하라 |
| 구현고정 | 동작 대신 메시지 문구·내부 변수·입력 읽기 방식·코드 구조를 grep 하는가 | 지워라. 해당 분기에서 관측할 유일한 동작이 알림이고 다른 검사가 그 알림을 보지 않으면 유지하라 |
| 중복 | 이 검사가 잡는 결함을 넣으면 다른 검사도 반드시 실패하는가. 파일·절 존재만 확인하는데 해당 파일을 실행하거나 절 내용을 보는 검사가 따로 있으면 여기 속한다 | 지워라. 통합에 새 코드가 필요하면 이번 차수에 고치지 말고 따로 적어라 |
| 항진 | 무엇을 바꿔도 항상 참인가 | 지워라 |
| 일회성 | 옛 이름·옛 절·옛 문구가 없다는 부정 조건으로 과거 변경의 회귀 여부만 보는가 | 권장안을 붙여 사용자에게 물어라. 실패 이력이 없다는 사실은 삭제 근거가 아니다 |
| 사본 | 소유자가 정해진 규칙을 다른 문서에 거듭 적었는가 | 소유자를 가리키는 문장으로 바꿔라 |
| 수명 끝 | 실행이 끝난 plan이나 병합된 작업의 기록인가 | 보존 태그를 달고 지워라. 차수 대조에 쓰는 최근 기록은 남겨라 |
| 이전 코드 | 옛 버전의 흔적을 정리하는 코드인가 | 남은 흔적이 동작에 영향을 주지 않으면 지워라. 낡은 지시를 싣는 흔적을 차단한다면 은퇴 조건을 적고 남겨라 |
| 판단보류 | 위 질문으로 가려지지 않는가 | 남기고 이유를 적어라 |

## 절차

감축 차수는 아래 순서대로 진행하라. 앞 단계 산출물을 뒤 단계 입력으로 쓰므로 순서를 바꾸지 마라.

**1. 목록** — 대상을 파일과 줄 번호로 정리하라.

**2. 판정표** — 항목마다 분류, 근거 한 줄, 삭제 시 잃는 보호를 적어라. 완성한 판정표는 해당 차수의 커밋 메시지나 보고에 실어라.

**3. 범위** — 분류 표의 처분을 기본값으로 삼아라. 문구고정·구현고정·중복·항진은 지우고, 판단보류는 이유를 적어 남겨라. 일회성만 사용자에게 묻되, 지금도 유효한 계약을 지키면 유지, 아니면 삭제를 권장안으로 붙여라. 사용자가 범위를 따로 정했으면 그 범위를 따라라.

**4. 적용** — 정한 범위만 수정하라. 쓰이지 않게 된 변수·헬퍼·주석도 함께 지워라.

**5. 결함 주입** — 프로젝트의 핵심 계약마다 일부러 결함을 하나씩 넣어 남은 검사가 실패하는지 확인한 뒤 되돌려라. 감축 전 버전도 같은 결함에 실패하지 않았다면 감축 전부터 있던 공백으로 기록하라.

**6. 전체 검사** — 프로젝트 전체 검사와 플러그인 검증을 실행하라.

## 재현성 확인

정의만 받은 다른 실행자에게 감축 전 버전을 다시 판정하게 해, 실제 처분과 지움·남김 일치율을 세어라. 불일치가 몰린 분류는 판정 질문을 고쳐라.

2026-10-06 첫 측정(`test_audit.sh` 검사 115건)에서는 일치율 78%, 카파 0.43이 나왔다. 불일치는 중복 범위와 조건이 섞인 검사에 몰렸다. 이에 중복 기준을 결함 기준으로 고치고, 섞인 검사는 조건별로 판정하도록 바꿨다.

고친 정의로 두 실행자가 따로 판정하자 서로 95% 일치했고 카파는 0.87이었다(Landis·Koch 1977 기준 거의 완전한 일치). 두 실행자 모두 실제 처분과는 78% 일치했다. 불일치는 정의 문제보다 그날 처분에서 정의를 덜 적용한 데서 나왔다. 두 실행자가 모두 지우라고 판정했으나 실제로 남은 검사는 주로 다른 검사가 실행하는 스크립트의 존재 확인과 JSON 형식 확인이었다.

## 렌즈와 문서의 연결

아래 장치가 이 참고서의 분류별 근거를 만든다. 장치가 직접 처분하지는 않으므로, 처분은 「절차」의 범위 단계를 따라라.

| 분류 | 근거를 내는 장치 |
|---|---|
| 설계 단계의 과잉(테스트·스크립트·문서·훅을 늘리는 spec) | `lens-adversarial`의 과설계 항목이 이 참고서와 `domain-plugin`에 근거해 지적한다 |
| 사본 | `lens-adversarial`의 드리프트 지적(두 곳에서 같은 대상을 다른 이름이나 값으로 적은 곳) |
| 수명 끝 | `lens-grounding`이 판별한 문서 타입(`doc_type`)과 `managing-docs` 「문서 타입과 수명」의 해당 행 |
| 문구고정·구현고정·중복·항진·일회성 | 이 참고서의 「절차」대로 만든 판정표. 렌즈 없이 프로젝트 테스트를 읽는 실행자가 작성한다 |
| 결함 주입의 핵심 계약 | 프로젝트가 정한다. 이 저장소는 `CLAUDE.md`의 「변경 뒤 실행」에 적혀 있다 |

## 판정 사례

2026-10-06 감축에서 기준을 넘겼지만 유지한 사례다. 같은 질문이 다시 나오면 이 판정을 출발점으로 삼아라.

**셸 스크립트 100줄** — 100줄을 넘는 셸 파일 12개를 다시 쓰지 않았다. 훅은 도구 호출마다 실행되는데 이 PC에서 빈 프로세스는 8밀리초, 파이썬은 71밀리초가 걸렸고 테스트 재작성 위험이 이득보다 컸다.

**상시 지시 200줄** — 상황 한정 절을 스킬로 옮기지 않았다. 캐시를 쓰면 상시 지시는 요청마다 캐시 읽기 비용만 들고, 옮긴 지시도 쓰는 세션에서 결국 같은 비용이 든다. 문서를 자주 고치는 사용자에게는 절감 효과가 없었다.

**대조 렌즈의 통합** — 처음에는 입력(출처와 계약)이 다르다는 이유로 근거 렌즈와 형식 렌즈를 합치지 않았다. 2026-11-17 접근 방식과 맥락 분리 필요에 따라 렌즈를 다시 나누면서 형식 계약을 `lens-grounding`으로 옮겼다. 이제 `lens-review`가 두 입력을 `CRITERIA` 줄에 함께 넘기며, 런타임 출력 검토도 출력 종류와 무관하게 `lens-grounding` 하나로 처리한다.

**훅 알림 문구** — 같은 날 테스트 네 파일을 다시 판정할 때, 깨진 설정·갱신 실패·재시작 요구처럼 SessionStart 훅이 알림으로만 동작을 드러내는 검사는 남겼다. 이 검사를 지우면 알림이 조용히 사라지는 회귀를 잡을 검사가 없다.

**상시 계약인 부정 조건** — README에 훅 전용 변수가 없다는 검사와, 지운 조항 ID가 근거 없이 되살아나지 않는다는 검사를 남겼다. 부정 조건이지만 지금도 유효한 계약을 지키므로 일회성으로 분류하지 않았다.
