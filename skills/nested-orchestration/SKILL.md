# nested-orchestration — 워크스트림으로 나눠 맡기는 3층 오케스트레이션

이 파일은 현재 세션의 절차다. 서브 세션이 따르는 메시지 형식과 멈추는 기준과 리포트는 같은 폴더의 `references/sub-session-protocol.md`(이하 프로토콜 파일)에 있고, 현재 세션도 메시지를 쓰고 읽을 때 그 파일을 읽는다. 설계 근거와 측정 기록은 근거 문서에 있다. 근거 문서는 플러그인 루트 기준 상대 경로 `docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`이며, 다른 프로젝트에서는 사용자 저장소에 없고 플러그인 설치 폴더에 있다. 이 파일은 근거 문서를 절 이름으로 가리키고, 명세 단계와 다시 나누기의 결정과 근거는 근거 문서의 「2026-10-12 개정 — 명세 단계와 다시 나누기」에 있다.

## 용어

이 파일은 아래 이름을 아래 뜻으로만 쓴다. 메시지에 쓰는 용어(머리줄, 상향·하향 메시지, 사유 코드, 유형)는 프로토콜 파일의 「용어」에 있다.

| 이름 | 뜻 |
|---|---|
| 현재 세션 | 사용자와 대화하며 큰 명세·계약·통합을 맡고 워크스트림의 하부 명세·plan·구현은 직접 쓰지 않는 세션 |
| 서브 세션 | 워크스트림 하나를 맡고 사용자와 대화하지 못하는 서브에이전트. 큰 개발에서는 명세 서브 세션과 구현 서브 세션이 있고, 다른 저장소의 독립 작업에서는 서브 세션 하나가 하부 명세부터 구현까지 맡는다 |
| 명세 서브 세션 | 임시 워크스트림 하나의 하부 명세와 작성 기록을 쓰고 끝나는 서브 세션 |
| 구현 서브 세션 | 다시 나눈 워크스트림 하나를 「절 배정」의 하부 명세로 plan 부터 구현까지 맡는 서브 세션 |
| 워크스트림 | 서브 세션 하나가 맡는 작업 단위 |
| 임시 워크스트림 | 명세 단계에서 하부 명세를 쓰려고 나눈 워크스트림. 구현 단계에서는 쓰지 않는다 |
| 큰 명세 | 개발 전체를 워크스트림으로 묶고 워크스트림 사이 계약과 결정 기록을 적는 명세 |
| 완전체 명세 | 하부 명세를 모두 가리키고 공유 결정·경계·「겹침 판정」을 더한 큰 명세 |
| 하부 명세 | 임시 워크스트림 하나의 내부 설계를 적는 명세. 다른 저장소의 독립 작업에서는 그 작업의 내부 설계를 적는 명세 |
| 하위 프로젝트 | 큰 개발을 분해한 단위로, 워크스트림으로 묶기 전의 단위(superpowers `brainstorming`의 이름) |
| 서로 독립된 큰 작업 | 서로 자료를 주고받지 않고 각각 plan을 따로 둘 만큼 큰 작업 |
| 통합용 워크트리 | 현재 세션이 통합 브랜치 `dev/<개발 이름>`을 체크아웃해 두는 워크트리 |
| SDD | plan을 태스크마다 구현 워커와 리뷰어로 실행하는 superpowers `subagent-driven-development` 스킬 |

## 언제 쓰는가

현재 세션은 두 시점에 서브 세션에 맡길지 판단한다. 첫 시점은 superpowers `brainstorming`을 따르다가 요청을 하위 프로젝트 여럿으로 분해하기로 했을 때다. 다른 시점은 설계 문서(`docs/superpowers/specs/`의 spec)가 승인된 뒤 `writing-plans`를 실행하기 전이며, 하위 프로젝트로 분해하지 않은 큰 개발도 여기서 판단하고 현재 세션이 설계 문서에서 하위 프로젝트 목록을 만든다. 맡기기로 하면 현재 세션은 하위 프로젝트마다 하부 명세·plan·구현을 직접 진행하지 않는다. 다시 나눈 결과 맡기는 기준에 들지 않게 되면(「다시 나누기」) 맡기지 않기로 한 것이므로 현재 세션이 직접 진행한다.

`hooks/nested_judgment_pretooluse.sh`는 새 spec 경로마다 세션에서 한 번, 그 경로의 첫 `Write`를 거부하고 사유에 「맡기는 기준」 한 문장을 넣는다. 현재 세션은 이 거부를 받으면 기준에 드는지 본다. 기준에 들지 않으면 판단과 근거를 한 문장으로 사용자에게 알린 뒤 같은 `Write`를 다시 실행한다. 기준에 들어 맡기기로 하면 현재 세션은 큰 명세를 거부된 그 경로에 쓴다. 현재 세션은 그 파일 이름의 주제를 개발 이름으로 쓰므로 「큰 명세」의 경로 규칙과 맞는다.

**맡기는 기준.** 현재 세션은 계약 코드를 고정한 뒤 동시에 시작할 수 있는 워크스트림(「묶는 단위」의 시작 워크스트림)이 둘 이상이고, 각 워크스트림이 plan을 따로 둘 만큼(태스크 다섯 이상으로 예상될 만큼) 크면 서브 세션에 맡긴다. 서로 독립된 큰 작업이 둘 이상이어도 맡긴다. 다섯은 사용자 합의값이다. 현재 세션은 하위 프로젝트로 분해했는지와 관계없이 이 기준으로 판단한다.

현재 세션은 나눠 맡길 단위에 따라 쓸 스킬을 고른다.

- 단위가 plan·리뷰 루프 없는 단일 태스크이면 현재 세션은 `dispatching-parallel-agents`를 쓴다.
- 「맡기는 기준」에 들면 현재 세션은 이 스킬을 쓴다.
- 사용자가 나눠 맡기라고 요구하면 현재 세션은 단위가 단일 태스크가 아닌 한 규모와 관계없이 이 스킬을 쓰고, 작은 일이면 조율 비용이 이득보다 클 수 있다고 알린다.
- 어디에도 들지 않으면 현재 세션은 superpowers 흐름을 직접 진행한다.

맡기려면 현재 세션은 근거를 보여 사용자 승인을 받는다. 승인은 두 번이다. 처음은 임시 분할로 명세 단계에 들어갈 때이고, 다음은 「다시 나누기」의 분할로 구현 단계에 들어갈 때다. 두 번 모두 근거에는 하위 프로젝트 목록, 「묶는 단위」의 공유 항목 표와 설계 의존 표와 그 결과인 시작 의존, 워크스트림마다 맡는 일과 예상 태스크(`writing-plans`의 태스크) 목록을 적는다. 사용자는 떼어냄 행의 고정한 의미를 읽어 현재 세션이 내부 설계를 미리 정했는지 확인한다. 서로 독립된 큰 작업을 맡길 때는 작업마다 맡는 일과 예상 태스크 목록을 적는다.

승인받은 하위 프로젝트 목록이 「묶는 단위」의 입력이며, 사용자가 목록을 바꾸면 현재 세션은 표와 판정을 다시 만들어 다시 승인받는다.

## 큰 개발 분할

**묶는 단위.** 현재 세션은 승인받은 하위 프로젝트 목록으로 공유 항목 표를 먼저 만들고, 그다음 설계 의존 표를 만든다. 공유 항목 표의 행은 둘 이상의 하위 프로젝트가 주고받는 자료·상태·정의다. 현재 세션은 명명 관례 같은 관례와 용어 풀이를 행으로 두지 않고 「결정 기록」에 적는다.

공유 항목 표의 칸은 항목, 소유 하위 프로젝트, 사용 하위 프로젝트, 판정, 고정한 의미다. 소유 하위 프로젝트는 그 항목의 의미를 바꾸는 결정을 내리는 하위 프로젝트다. 사용 하위 프로젝트는 그 항목을 받는 하위 프로젝트이며, 현재 세션은 소유 하위 프로젝트를 사용 칸에 넣지 않는다.

현재 세션은 모든 행에 "어느 하위 프로젝트의 내부 설계도 정하지 않고 이 항목의 이름·형식·단위·의미(시간 의미와 결측 의미 포함)를 지금 고정할 수 있는가"를 묻는다. 고정할 수 있으면 판정은 떼어냄이고, 현재 세션은 고정한 의미를 그 행에 한 줄로 적는다. 고정할 수 없으면 현재 세션은 사용 하위 프로젝트마다 "그 하위 프로젝트의 설계가 이 항목의 의미를 함께 정해야 하는가"를 묻는다. 소유 하위 프로젝트가 둘 이상이면 판정은 합침이다. 소유가 하나이면 함께 정해야 하는 사용 하위 프로젝트가 있을 때 판정은 합침이고, 없을 때 판정은 순서다.

소유 하위 프로젝트가 없는데 고정할 수 없으면, 현재 세션은 그 항목을 바꾸는 하위 프로젝트를 모두 소유 하위 프로젝트로 적고 판정한다. 합침 행에서 현재 세션은 소유 하위 프로젝트를 모두 합치고, 의미를 함께 정해야 하는 사용 하위 프로젝트도 같은 워크스트림으로 합친다. 합침·순서 행에서 의미를 받기만 하는 사용 하위 프로젝트는 합치지 않으며, 현재 세션은 소유 쪽 접근 절차를 계약으로 떼어낸다. 그 계약의 의미 칸은 소유 워크스트림이 통합 브랜치에 들어갈 때 현재 세션이 확정한다.

합침 행끼리 하위 프로젝트가 겹치면 현재 세션은 겹친 행의 하위 프로젝트를 모두 한 워크스트림으로 묶는다. 현재 세션은 「다시 나누기」에서 떼어냄 행과, 합침·순서 행에서 떼어낸 접근 절차를 「계약 표」의 행으로 옮기고, 하위 프로젝트 이름을 워크스트림 id로 바꾼다. 소유 쪽은 제공자가 되고 사용 쪽은 소비자가 되며, 소유가 없는 행의 제공자는 현재 세션이다. 이 연결 규칙은 이 절이 소유한다.

설계 의존 표의 행과 열은 합친 묶음과 남은 하위 프로젝트다. X를 설계하려면 Y의 실제 결과(구현 결과나 조사 결과)를 보아야 하면 현재 세션은 X→Y에 1을, 그렇지 않으면 0을 적는다. 공유 항목 표에서 이름·형식·단위·의미를 고정한 관계는 0이다. 합침·순서 행에서 합치지 않은 사용 쪽의 관계는 1이므로, 그 사용 쪽은 소유 쪽 뒤에 설계한다.

현재 세션은 설계 의존 순환에 함께 든 묶음과 하위 프로젝트만 한 워크스트림으로 합치고, 나머지는 하나를 워크스트림 하나로 둔다. 순환을 합치고 나면 워크스트림 사이 의존에는 순환이 남지 않으므로, 현재 세션은 그 의존을 큰 명세 의존 순서 항목의 시작 의존에 적는다. 시작 의존에서 선행 워크스트림이 없는 워크스트림을 시작 워크스트림이라고 하며, 시작 워크스트림들은 동시에 시작할 수 있다. 시작 워크스트림이 하나뿐이면 그 개발은 「맡기는 기준」에 들지 않는다.

두 워크스트림이 같은 파일을 고쳐야 하면 현재 세션이 그 파일을 맡고 「공용 파일」대로 다룬다. 코드가 없는 단계에서는 경로 겹침을 셀 수 없으므로 합치는 조건으로 쓰지 않는다.

현재 세션은 「묶는 단위」를 두 번 실행한다. 처음은 하위 프로젝트 목록으로 임시 워크스트림을 정할 때이고, 다음은 완전체 명세로 워크스트림을 새로 나눌 때다(「다시 나누기」). 계약 표와 계약 코드는 두 번째 결과로만 만든다.

**관례 골격.** 현재 세션은 임시 분할을 적을 때 명명, 오류 처리, 추상화 수준, 디렉터리 구조를 큰 명세 「결정 기록」에 채운다. 명세 서브 세션은 이 골격을 주입 컨텍스트로 받는다. 따로 쓴 설계를 합치면 이런 암묵적 결정이 서로 달라진다는 근거는 근거 문서 「2026-10-12 개정 — 명세 단계와 다시 나누기」의 「관례 골격」에 있다.

**명세 단계.** 현재 세션은 임시 워크스트림마다 명세 서브 세션을 실행한다. 명세 서브 세션은 자기 하부 명세를 쓰고 리뷰해 커밋하고, 리포트의 `작성 기록` 절에 고른 대안과 기각 이유, 읽은 코드와 자료, 열린 질문을 적은 뒤 `DONE`을 돌려주고 끝난다. 임시 분할에도 의존 순서 표를 두고 「흐름」의 「차수」대로 진행한다. 명세 단계에서 선행은 선행 명세 서브 세션이 아래 검사를 마친 `DONE`으로 충족된다. 현재 세션은 사용 쪽 명세 서브 세션을 그 뒤에 실행하고, 선행 하부 명세의 브랜치와 경로를 주입 컨텍스트로 준다.

현재 세션은 명세 서브 세션의 `DONE`을 받으면 「리뷰 마커 확인」과 「판정 기록 확인」을 하고, `git diff --name-only dev/<개발 이름>...spec/<개발 이름>/<임시 id>`가 자기 문서 경로 밖의 파일을 내지 않는지 본다. 리포트의 `스스로 판정한 모호함`에서 마지막 칸이 '예'인 줄은 사용자에게 묻고 답을 「결정 기록」에 커밋하며, 답이 이미 「결정 기록」에 있으면 다시 묻지 않는다. 검사나 답 때문에 하부 명세를 고쳐야 하면 현재 세션은 끝난 명세 서브 세션에 `REVISE`를 보내지 않고 `RESTART`(`원인`에 고칠 항목)를 보낸다. 시험 병합과 수정 범위 대조(`ws/` 브랜치용)는 명세 서브 세션에 적용하지 않는다.

현재 세션은 모든 임시 워크스트림이 위 검사를 마친 `DONE`을 돌려주었거나 범위에서 빠진 뒤에 완전체 명세를 쓴다. 명세 서브 세션이 `FAILED`나 `CANCELED`로 끝나면 현재 세션은 `RESTART`로 다시 쓸지, 그 하위 프로젝트를 범위에서 뺄지 사용자에게 고르게 한다. 빼기로 하면 「결정 기록」에 '뺀 하위 프로젝트: <임시 id> — 이유' 한 줄을 커밋한다. 현재 세션은 빠진 하부 명세를 대신 쓰지 않는다.

**완전체 명세.** 현재 세션은 각 `spec/<개발 이름>/<임시 id>` 브랜치의 하부 명세와 그 리뷰 기록을 `git -C <통합용 워크트리> checkout spec/<개발 이름>/<임시 id> -- <경로>`로 통합용 워크트리에 옮긴다. 큰 명세 본문은 각 하부 명세를 가리키고, 공유 결정 절과 경계 절과 「겹침 판정」 절을 새로 둔다. 하부 명세 원문을 본문 한 파일에 붙이지 않는다. 붙이면 파일이 서브 세션의 읽기 상한(25k 토큰)을 넘어 잘린 채 읽힌다.

현재 세션은 관례 골격과 「결정 기록」을 기준표로 삼아 하부 명세마다 대조하고, 다르게 쓴 곳을 기준표에 맞춰 고친다. 현재 세션은 완전체 명세 본문과 현재 세션이 고친 하부 명세 파일을 `review-specs`로 리뷰한 뒤 사용자 승인을 받는다.

**겹침 판정.** 현재 세션은 하부 명세 사이의 겹침마다 '같은 동작인가'를 묻는다. 같으면 공유 결정 절로 합치고, 다르면 이름을 구분해 각 하부 명세에 둔다. 경계를 넘는 자료를 두 하부 명세가 다르게 정했으면 그 자료의 소유 하위 프로젝트 쪽 정의를 경계 절에 적고, 다른 쪽 하부 명세에서는 그 정의를 지우고 경계 절을 가리킨다. 현재 세션은 판정마다 「겹침 판정」 표(대상, 하부 명세, 판정, 이유)에 한 행을 남기고, 겹침이 없으면 '없음' 한 행을 남긴다.

**다시 나누기.** 완전체 명세가 승인되면 현재 세션은 완전체 명세의 하위 프로젝트 목록으로 「묶는 단위」를 다시 실행한다. 공유 결정과 경계는 그 항목의 소유 워크스트림 하나가 구현하고, 소유가 없는 항목은 현재 세션이 계약 코드에 둔다. 순서 행의 사용 쪽을 뺀 나머지 워크스트림은 계약 코드와 테스트 대역으로 따르며 동시에 개발한다. 현재 세션은 공통 결정만 구현하는 워크스트림을 따로 만들지 않는다. 공유 결정과 경계는 여러 워크스트림이 기다리는 항목이므로, 현재 세션은 그 소유 워크스트림이 선행 없이 1차에 들도록 나눈다. 1차에 둘 수 없으면 그 항목을 현재 세션이 계약 코드에 두고, 그것도 안 되면 사용자에게 알린다.

현재 세션은 큰 명세에 새 분할과 계약 표와 「절 배정」 표(새 워크스트림 id, 하부 명세 파일과 절, 작성 기록이 있는 리포트)를 적는다. 현재 세션은 이 분할을 리뷰하고 「언제 쓰는가」의 근거로 사용자 승인을 받는다. 다시 나눈 결과 시작 워크스트림이 하나뿐이면 현재 세션은 사용자에게 알리고, 「결정 기록」에 '직접 진행' 한 줄을 `결정 기록:` 커밋으로 남긴다. 그다음 통합용 워크트리에서 완전체 명세로 `writing-plans`부터 직접 진행하고, 끝나면 「흐름」의 마무리와 정리 단계를 거친다.

**큰 명세.** 현재 세션은 큰 명세를 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-design.md`에 쓰고, 단계마다 `review-specs`로 리뷰한 뒤 사용자 승인을 받는다. 처음에는 임시 워크스트림과 그 맡는 일, 공통 제약, 관례 골격을 채운 「결정 기록」만 적는다. 완전체 명세가 되면 하부 명세 포인터와 공유 결정·경계·「겹침 판정」 절을 더한다. 다시 나눈 뒤에는 아래 항목과 「절 배정」을 적는다. 큰 명세 본문에는 워크스트림 내부 설계를 적지 않는다.

- 워크스트림 목록: 워크스트림 id와 맡는 일
- 워크스트림 사이 계약 표: 경계를 넘는 자료마다 「계약 표」의 칸을 채운 행
- 의존 순서 표: 워크스트림마다 선행 워크스트림(시작 의존, 다른 워크스트림의 산출물이 있어야 시작할 수 있는 관계)과 검증 의존(통합 확인에 다른 워크스트림의 실제 구현이 필요한 관계)을 한 행에 적는다. 선행이 없는 워크스트림이 1차다
- 수정 허용 경로: 워크스트림마다 git pathspec 목록
- 소유 표: 현재 세션이 소유하는 공용 파일(의존성 목록·잠금 파일 포함)
- 공통 제약과 워크스트림별 통합 확인 방법
- 「결정 기록」 절

현재 세션은 다시 나눈 분할을 승인받기 전에 어느 파일 경로도 두 워크스트림의 수정 허용 경로에 함께 들지 않는지(한 패턴이 다른 패턴의 경로를 포함하지 않는지) 확인한다. 이 확인이 있으므로 「수정 범위 대조」를 통과한 워크스트림들은 같은 파일을 고치지 않는다.

설계 문서가 승인된 뒤에 맡기기로 했으면 현재 세션은 그 설계 문서를 큰 명세로 삼는다. 이 경로에서는 현재 세션이 main 대신 설계 문서가 커밋된 끝에서 통합 브랜치를 만들고(「흐름」 준비), 그 브랜치에서 설계 문서에 임시 분할을 보강해 다시 승인받은 뒤 커밋한다. 설계 문서에 사용자가 정한 워크스트림 내부 방식은 그대로 두고, 완전체 명세를 쓸 때 하부 명세와 대조한다.

**검증 의존.** X의 서브 세션은 X의 설계와 단위 테스트를 계약 코드와 테스트 대역으로 진행할 수 있다. 그런데 X의 통합 확인에 Y의 실제 구현이 필요하면 X는 Y에 검증 의존한다. 현재 세션은 큰 명세에 워크스트림별 통합 확인 방법을 적을 때 검증 의존을 판정한다. 검증 의존은 시작을 늦추지 않으므로, 현재 세션은 시작 워크스트림을 시작 의존만으로 판정한다.

현재 세션은 큰 명세를 승인받기 전에 시작 의존과 검증 의존을 합친 그래프에 순환이 있는지 본다. 순환이 있으면 현재 세션은 그 워크스트림들의 병합 순서를 정할 수 없으므로, 디스패치 전에 순환에 든 워크스트림을 합칠지 사용자에게 묻는다. 계약 테스트는 아직 없는 워크스트림 모듈을 생략하므로, 현재 세션은 병합 순서를 시작 의존과 검증 의존으로 정한다.

**계약 표.** 현재 세션은 워크스트림 경계를 넘는 자료마다 계약 표에 한 행을 두고 아래 칸을 채운다.

| 칸 | 적는 내용 |
|---|---|
| 이름 | 함수 계약이면 공개 함수가 있는 모듈 경로와 함수·타입 이름, 파일 계약이면 파일 경로 |
| 제공자 → 소비자 | 자료를 내는 워크스트림 id 와 쓰는 워크스트림 id. 계약 코드나 현재 세션이 내거나 통합 확인이 쓰면 그 이름 |
| 형식 | 자료형이나 함수 시그니처. 키가 정해진 값이면 열거값, 표나 결과 객체이면 열 이름 |
| 단위 | 값의 단위 |
| 의미(시간·결측 포함) | 서브 세션이 바꾸면 안 되는 값의 뜻, 값이 정해지는 시점과 빈도, 값이 없는 시점이나 항목의 처리(앞값, 0, 오류) |

의미 칸의 시간과 결측은 비워 두지 않고, 해당이 없으면 '없음'을 적는다. 「묶는 단위」가 의미를 소유 워크스트림 통합 때 확정하게 한 행에서, 현재 세션은 의미 칸과 형식 칸의 열거값을 '확정 예정(<소유 워크스트림 id>)'으로 적는다. 현재 세션은 그 워크스트림을 통합할 때 리포트의 `확정한 계약 의미`를 보고 칸을 채우며, 이 확정은 계약 변경이 아니다. 칸만 채운 커밋은 제목을 `계약 의미 확정:`으로 시작한다. 그 칸을 쓰는 사용 쪽은 소유 쪽 통합 뒤에 시작하므로, 이 커밋은 진행 중인 워크스트림이 받을 변경이 아니다. 여러 행이 같은 관례를 쓰면 의미 칸에는 큰 명세 「결정 기록」에 적은 관례의 이름을 적는다. 현재 세션은 그 관례를 큰 명세를 리뷰에 넘기기 전에 「결정 기록」에 적고, 그 관례를 고치는 일은 계약 변경으로 다룬다.

이름과 형식은 계약 코드가 원본이고, 단위와 의미는 계약 표가 원본이다. 현재 세션은 큰 명세를 리뷰에 넘기기 전에 두 종류의 자료에 각각 제공자 행이 있는지 확인한다. 하나는 각 워크스트림의 맡는 일에 필요한 자료이고, 다른 하나는 통합 확인이 읽는 자료다.

**계약 코드.** 다시 나눈 분할이 승인되면 현재 세션은 통합 브랜치에 큰 명세를 커밋하고 계약을 타입·시그니처·계약 테스트 코드로 만들고, 계약 코드의 경로를 소유 표에 현재 세션 소유로 적는다. 계약 코드는 함수 계약마다 공개 함수의 모듈 경로와 시그니처를 정한다. 그 모듈 파일은 제공 워크스트림의 서브 세션이 자기 허용 경로 안에 처음 만든다. 계약 테스트는 그 모듈이 시그니처를 따르는지 대조한다. 모듈을 import 할 때 통합 브랜치에 아직 없는 워크스트림의 모듈이 필요하면, 그 모듈이 대조 대상이든 대조 대상이 읽는 다른 워크스트림의 모듈이든 계약 테스트는 없는 워크스트림의 id 를 생략 사유에 적어 검사를 생략한다. 그래서 소비자가 제공자보다 먼저 병합되어도 계약 테스트가 실패하지 않는다.

테스트 대역(test double)은 실제 구현 대신 테스트에 쓰는 구현이다. 현재 세션은 계약 코드 plan 을 쓸 때 소비자의 단위 테스트에 필요한 테스트 대역을 정해 계약 코드에 두고, plan 리뷰에서 테스트 대역이 계약 표의 단위·의미를 따르는지 대조한다. 소비자 서브 세션은 다른 워크스트림 함수의 테스트 대역을 자기 경로에 따로 만들지 않고 `BLOCKED test-double-add`로 요청한다. 파일 계약은 현재 세션이 통합 확인에서 열 이름과 형식을 대조하고, 단위와 의미는 다시 나눈 분할을 승인받기 전에 계약 표와 하부 명세를 대조한다.

계약 코드의 SDD는 통합용 워크트리에서 실행한다. 계약 코드도 writing-plans, plan 리뷰, 사용자 plan 검토, 실행 순서로 진행한다. 계약 코드가 있으면 현재 세션이 통합 확인을 기계로 할 수 있다.

**결정 기록.** 큰 명세의 「결정 기록」 절은 현재 세션만 쓴다. 현재 세션은 첫 디스패치 전에 「관례 골격」과 공용 유틸리티처럼 워크스트림마다 따로 정하면 충돌하는 결정을 채운다. 사용자가 🔴(사용자 결정이 필요한 리뷰 지적)나 범위 결정에 답하면 그 답도 적는다. 현재 세션은 통합 때마다 리포트의 `확정한 결정`을 옮기지 않고, 「흐름」 마무리 단계에서 병합된 워크스트림의 `확정한 결정`을 한 커밋으로 옮긴다. 다른 워크스트림이 따라야 하는 결정은 완전체 명세와 관례 골격에 이미 있기 때문이다. 공개 인터페이스는 계약 코드에서 도출하므로 옮겨 적지 않는다. 현재 세션은 워크스트림 경계를 넘지 않는 관례와 용어 풀이(예: 구간 경계)도 여기에 적는다.

「결정 기록」만 바꾼 아래 커밋은 제목을 `결정 기록:`으로 시작한다. 사용자 답(요청한 서브 세션 하나에 `ANSWER`로 보낸 답, 「리뷰 마커 확인」에서 `escalated` 🔴에 받은 답, 명세 서브 세션 리포트의 '예' 줄에 받은 답)을 적은 커밋, '뺀 하위 프로젝트' 줄을 적은 커밋, 마무리 단계에서 `확정한 결정`을 옮긴 커밋이다. 「시험 병합」 전의 확인은 이 커밋과 `계약 의미 확정:` 커밋을 빼고 본다. 공유 가정을 추가한 커밋에는 이 제목을 쓰지 않는다.

**공용 파일.** 라우팅 표·진입점·설정 등록부·의존성 목록·잠금 파일처럼 여러 워크스트림이 고치거나 함께 쓰는 파일은 현재 세션이 소유하고 소유 표에 적는다. 서브 세션은 공용 파일을 고치지 않고 `BLOCKED shared-file-change`나 `BLOCKED dependency-add`로 요청하며, 현재 세션이 통합 브랜치에서 고친다.

공용 파일 중 설정 파일에는 사용자가 정한 값과 둘 이상의 워크스트림이 읽는 값만 둔다. 한 워크스트림만 읽는 파라미터는 그 워크스트림의 허용 경로에 둔 설정 파일(예: `configs/<워크스트림 id>.yaml`)에 두고, 그 워크스트림이 허용 경로 안의 코드로 읽는다.

**경로와 브랜치 이름.** 워크스트림 id 는 영문 소문자와 숫자로 쓰고 하이픈을 넣지 않는다. 임시 워크스트림의 id(임시 id)는 `spec`으로 시작하고, 다시 나눈 워크스트림의 id 는 `spec`으로 시작하지 않는다. 그래서 두 단계의 리포트와 문서 이름이 겹치지 않는다. 명세 서브 세션의 브랜치는 `spec/<개발 이름>/<임시 id>`이고, 기준 커밋은 임시 분할을 적은 큰 명세를 커밋한 `dev/<개발 이름>`의 끝이다. 아래 경로의 `<워크스트림 id>`는 하부 명세에서는 임시 id 이고 plan 에서는 다시 나눈 워크스트림 id 다. 하부 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-<워크스트림 id>-design.md`, 워크스트림 plan은 `docs/superpowers/plans/YYYY-MM-DD-<개발 이름>-<워크스트림 id>.md`에 둔다. 리뷰 기록의 이름은 `review-docs`의 「기록 파일 이름 규칙」을 따르며 주제는 `<개발 이름>-<워크스트림 id>`나 `<개발 이름>-<워크스트림 id>-plan`이다.

통합 브랜치는 `dev/<개발 이름>`, 워크스트림 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 모든 워크스트림의 허용 경로에는 자기 문서 경로(`docs/superpowers/specs/*-<개발 이름>-<워크스트림 id>-design.md`, `docs/superpowers/plans/*-<개발 이름>-<워크스트림 id>.md`, `docs/superpowers/reviews/*-<개발 이름>-<워크스트림 id>-*`)이 기본으로 들어간다. 현재 세션은 이 세 패턴을 `glob` pathspec 으로 써서 `*`가 한 단계 경로만 맞게 한다. 리뷰 기록과 같은 이름의 원본 폴더는 셋째 패턴 뒤에 `/**`를 붙인 패턴으로 따로 허용한다. id 에 하이픈이 없으므로 id 뒤의 `-`가 경계가 되어, 한 id가 다른 id의 접두어여도(`a`와 `ab`) 서로의 문서를 허용하지 않는다.

리포트는 `<git common dir>/nested/<개발 이름>/report-<워크스트림 id>.md`에 둔다. `<git common dir>`은 `git rev-parse --path-format=absolute --git-common-dir`의 출력이다. git 내부 폴더라 커밋되지 않고, 현재 세션이 재시작해도 같은 경로에 남는다.

**서로 독립된 큰 작업.** 서로 독립된 큰 작업이 둘 이상이면 현재 세션은 작업마다 서브 세션에 맡긴다. 현재 세션이 작업마다 brainstorming으로 요구를 정리해 큰 명세에 워크스트림별 요구로 적고 사용자 승인을 받는다. 워크스트림 사이 계약과 계약 코드는 생략하고 통합 확인은 각 워크스트림의 테스트로 대신한다. 작업들이 같은 저장소에 있으면 자료를 주고받지 않아도 명명·오류 처리·공용 함수 같은 암묵적 결정이 부딪히므로, 현재 세션은 큰 개발과 같이 명세 단계와 다시 나누기를 거친다. 작업들이 다른 저장소에 있으면 부딪힐 결정이 없으므로 현재 세션은 명세 단계를 거치지 않는다. 그때는 서브 세션 하나가 작업 하나의 하부 명세부터 구현까지 맡고, 현재 세션이 하부 명세를 「승인 항목」대로 승인한다(`AWAITING_APPROVAL`, `APPROVE`). 현재 세션은 저장소마다 큰 명세와 통합 브랜치와 통합용 워크트리를 따로 둔다. 이때 현재 세션은 통합용 워크트리를 `git -C <저장소> worktree add -b dev/<개발 이름> <경로> main`처럼 브랜치와 함께 만든다.

## 흐름

현재 세션과 서브 세션이 아래 순서로 진행한다.

1. **준비(현재 세션)** — 임시 분할을 적은 큰 명세가 승인되면 커밋하기 전에 `git worktree add -b dev/<개발 이름> <통합용 워크트리 경로> main`으로 통합 브랜치와 통합용 워크트리를 함께 만든다(설계 승인 뒤에 맡기는 경로는 보강하기 전에 main 대신 설계 문서가 커밋된 끝에서 만든다). 자기 체크아웃에서 쓰고 리뷰한 큰 명세와 그 리뷰 기록은 `cp`로 통합용 워크트리의 같은 상대 경로에 옮겨 커밋하고, 커밋한 뒤 자기 체크아웃의 원본을 지운다. 원본이 미추적 파일로 남으면 사용자 체크아웃에서 통합 브랜치를 main 에 병합할 때 git 이 같은 경로의 미추적 파일 때문에 병합을 거부한다. 판단 훅은 `Write`만 보므로, 옮길 때 `Write`를 쓰면 그 경로가 새 spec으로 보여 다시 거부된다. 그 뒤 현재 세션은 이 개발의 git 명령을 모두 `git -C <통합용 워크트리>`로 실행하고, 계약 코드도 그 워크트리의 절대 경로로 써서 커밋한다. 현재 세션은 자기 체크아웃의 브랜치를 바꾸지 않으므로 사용자의 미커밋 변경이 통합에 섞이지 않는다.
2. **명세 디스패치(현재 세션)** — 임시 워크스트림마다 `git -C <통합용 워크트리> worktree add -b spec/<개발 이름>/<임시 id> <워크트리 경로> dev/<개발 이름>`으로 브랜치와 워크트리를 만들고, 「디스패치 템플릿」으로 명세 서브 세션을 백그라운드로 실행한다. `EnterWorktree`와 `cd`는 쓰지 않는다. 현재 세션이 서브 세션의 워크트리로 들어가면 현재 세션의 쓰기가 그 브랜치에 섞이기 때문이다. `using-git-worktrees`는 워크트리 위치와 ignore 확인에만 따른다. `Agent`의 `isolation:'worktree'`는 브랜치 이름과 기준 커밋을 정할 수 없어 쓰지 않는다.
3. **하부 명세(명세 서브 세션)** — 하부 명세를 쓰고 리뷰해 커밋하고, 리포트에 작성 기록을 남긴 뒤 `DONE`을 돌려주고 끝난다.
4. **완전체 명세(현재 세션)** — 「명세 단계」, 「완전체 명세」, 「겹침 판정」대로 완전체 명세를 쓰고, 리뷰와 사용자 승인을 받은 뒤 통합 브랜치에 커밋한다. 커밋 메시지에는 명세 단계의 토큰 합과 가장 늦은 명세 서브 세션을 기다린 시간을 `Spec-Tokens:`와 `Spec-Wait:` 트레일러로 넣는다. 재시작으로 잃은 값은 `미상`으로 적는다.
5. **다시 나누기(현재 세션)** — 「다시 나누기」대로 분할과 계약 표와 「절 배정」을 큰 명세에 적고, 리뷰와 사용자 승인을 받은 뒤 커밋한다. 그다음 계약 코드를 만들어 계약 테스트까지 통합 브랜치에 커밋한다.
6. **구현 디스패치(현재 세션)** — 계약 테스트가 통합 브랜치에 커밋된 뒤, 시작할 수 있는 워크스트림마다 `git -C <통합용 워크트리> worktree add -b ws/<개발 이름>/<워크스트림 id> <워크트리 경로> dev/<개발 이름>`으로 브랜치와 워크트리를 만들고, 「디스패치 템플릿」으로 구현 서브 세션을 백그라운드로 실행한다.
7. **plan과 구현(구현 서브 세션)** — 「절 배정」이 가리키는 하부 명세와 계약 코드로 plan과 구현을 마치고 `DONE`을 돌려준다.
8. **통합(현재 세션)** — 「가드레일」의 검사와 시험 병합으로 통합 브랜치에 넣는다. 통합할 때마다 현재 세션은 시작 의존이 새로 충족된 워크스트림을 6단계대로 디스패치한다.
9. **마무리(현재 세션)** — 접지 않은 모든 워크스트림이 들어가면 현재 세션은 병합된 워크스트림의 `확정한 결정`을 「결정 기록」에 `결정 기록:` 커밋 하나로 옮기고, 통합 브랜치 전체에 최종 브랜치 리뷰를 실행한다. 리포트들의 `제안`과 `기능적 반영`과, 「판정 기록 확인」에서 묻지 않은 판정 줄을 모아 사용자에게 보이고 「측정」 값을 보고한다. 통합 브랜치를 main에 병합하는 일은 그다음 사용자 승인을 받아 한다. 워크스트림 plan과 리뷰 기록은 에이전트원칙의 문서 수명 표대로 처리한다.
10. **정리(현재 세션)** — main 병합 뒤 현재 세션은 지울 목록을 보여 사용자 확인을 한 번 받는다. 목록은 각 워크스트림 워크트리의 SDD 작업 공간(`.superpowers/sdd/`), 명세 서브 세션과 워크스트림의 워크트리, 통합용 워크트리, `spec/<개발 이름>/*`·`ws/<개발 이름>/*`·`dev/<개발 이름>`·남은 `try/*` 브랜치, 리포트 폴더 `<git common dir>/nested/<개발 이름>/`이다.

**차수.** 현재 세션은 의존 순서 표에서 선행이 없는 워크스트림을 1차로 동시에 진행한다. 워크스트림이 통합 브랜치에 들어갈 때마다 현재 세션은 그 워크스트림을 선행으로 둔 워크스트림을 보고, 선행이 모두 충족된 워크스트림을 다음 차로 통합 브랜치 끝에서 디스패치한다. 충족은 문서에 적지 않고 git 에서 도출한다(구현 단계는 「진행 위치」의 `Workstream:` 줄, 명세 단계는 「명세 단계」의 완료 조건). 현재 세션은 진행을 보고할 때 워크스트림마다 선행, 충족한 선행, 남은 선행을 표로 보인다. 같은 파일은 「공용 파일」대로 현재 세션이 맡으므로 동시 진행의 조건이 아니다.

**승인 항목.** 하부 명세 승인은 다른 저장소의 서로 독립된 큰 작업에만 있다. 그 경로에서 현재 세션은 하부 명세가 수정 허용 경로 밖을 고치려 하지 않는지, 큰 명세 본문과 결정 기록에 충돌하지 않는지를 보고 `APPROVE`나 `REVISE`를 보낸다. 승인하기 전에 현재 세션은 리포트를 「판정 기록 확인」대로 읽는다.

큰 개발에서는 사용자가 완전체 명세와 분할을 승인하므로 하부 명세 승인이 없다. 계약 코드가 고정하지 않은 공유 가정(공용 자료의 내부 표현, 결정 기록에 없는 관례)이 구현 중에 새로 드러나면, 구현 서브 세션은 `BLOCKED contract-change`로 멈추고 현재 세션은 「받은 메시지 처리」의 `contract-change` 행대로 처리한다.

**디스패치 뒤 범위 변경.** 사용자가 디스패치 뒤에 범위를 바꾸면 현재 세션은 큰 명세를 고쳐 다시 승인받고, 영향을 받는 워크스트림에 `CONTRACT-CHANGED`를 보낸다. 이미 병합된 워크스트림은 접지 않는다.

**즉시 중단.** 사용자가 실행 중인 서브 세션을 즉시 멈추라고 하면 현재 세션은 `TaskStop`으로 그 서브 세션을 종료하고, `CANCELED`를 받은 것과 같이 다룬다.

## HARD-GATE 예외

superpowers `brainstorming`의 HARD-GATE는 architectural 경로에서 사람이 명세를 승인하고 plan을 검토하고 실행 방식을 고르게 한다. 서브 세션은 사람과 대화하지 못하므로 이 스킬은 서브 세션에 한해 그 단계들을 아래처럼 대체한다. 큰 개발에서 명세 승인은 사용자가 완전체 명세와 다시 나눈 분할을 승인하는 것으로 대신하고, 다른 저장소의 독립 작업에서는 현재 세션이 맡는다. plan 검토는 `review-specs` 렌즈 리뷰가 맡는다. 실행 방식은 SDD로 고정한다.

명세 서브 세션은 brainstorming 대화를 열지 않고 큰 명세와 관례 골격을 입력으로 하부 명세를 쓴다. 사용자가 직접 검토하는 문서는 큰 명세(임시 분할, 완전체 명세, 다시 나눈 분할)와 계약 코드 plan이다. 현재 세션은 사람과 대화하므로 계약 코드에는 이 예외를 쓰지 않는다.

## 디스패치 템플릿

서브 세션은 현재 세션 외 누구와도 대화할 수 없으므로 프롬프트는 자기완결이어야 한다. 현재 세션은 프롬프트 첫머리에 프로토콜 파일이 정한 `START` 머리줄과 필드를 두고(새 서브 세션으로 바꿀 때는 `RESTART`), 그 아래에 아래 블록을 차례로 넣는다. 필드로 넣은 정보는 블록에 다시 적지 않는다. `프로토콜` 필드에는 현재 세션이 연 이 스킬 폴더의 `references/sub-session-protocol.md` 절대 경로를 넣어, 플러그인이 개발 도중 갱신되어도 두 세션이 같은 형식을 읽게 한다.

1. **역할 선언** — "너는 자율 서브 세션이다. 사용자와 대화할 수 없고, 질문은 상향 메시지로 돌려준다. 모든 명령을 `워크트리` 필드의 경로에서 실행한다. 시작할 때와 하향 메시지를 받을 때마다 `프로토콜` 필드의 파일을 통째로 읽고 따른다."
2. **임무** — 명세 서브 세션의 산출물은 하부 명세와 리포트(작성 기록 포함)다. 구현 서브 세션의 산출물은 plan, 구현, 테스트, 리포트다. 다른 저장소의 독립 작업을 맡은 서브 세션은 둘 다 낸다.
3. **수정 허용 경로(엄수)** — 명세 서브 세션은 자기 문서 경로만 고친다. 구현 서브 세션은 큰 명세에 적은 그 워크스트림의 허용 경로와 자기 문서 경로만 고친다. 공용 파일·계약·큰 명세를 바꿔야 하면 고치지 않고 프로토콜 파일의 사유 코드로 멈춘다.
4. **하부 명세** — 하부 명세에는 그 워크스트림의 책임과 계약을 구현하는 데 필요한 내용만 적고, 일어날 수 없는 예외를 늘어놓지 않는다. 하부 명세를 `review-specs`로 리뷰해 반영하고 커밋한 뒤, 명세 서브 세션은 리포트의 `작성 기록`을 채우고 `DONE`을 돌려준다(다른 저장소의 독립 작업은 `AWAITING_APPROVAL`로 멈춘다). HARD-GATE 예외 문장을 그대로 넣는다: "이 워크스트림에서 명세 승인은 사용자의 완전체 명세 승인(다른 저장소의 독립 작업은 현재 세션)이, plan 검토는 review-specs 렌즈 리뷰가 맡고, 실행 방식은 subagent-driven-development로 고정한다. brainstorming 대화를 열지 않는다." 구현 서브 세션에는 이 블록 대신 「절 배정」이 가리키는 하부 명세 파일과 절, 작성 기록이 있는 리포트 경로를 넣는다.
5. **plan과 구현** — 구현 서브 세션에는 HARD-GATE 예외 문장을 그대로 넣는다: "이 워크스트림에서 명세 승인은 사용자의 완전체 명세 승인이, plan 검토는 review-specs 렌즈 리뷰가 맡고, 실행 방식은 subagent-driven-development로 고정한다." 구현 서브 세션은 시작하자마자(다른 저장소의 독립 작업은 `APPROVE`를 받으면) writing-plans, `review-specs`, SDD(TDD, 프로젝트 테스트 규약) 순서로 진행한다. 워커를 디스패치할 때마다 워크트리 절대 경로를 넣고 모든 명령을 그 경로에서 실행하게 한다. SDD와 함께 쓸 때의 규칙은 프로토콜 파일에 있다.
6. **렌즈와 원칙** — 렌즈를 실행하기 전에 `dispatching-lenses`를 통째로 읽는다. 서브 세션은 그 규율을 여는 호출자 중 하나이고, 「렌즈에게 에이전트원칙을 알리는 법」이 `dispatching-lenses` 안에 있다. 구현 워커에게든 문서를 쓰는 서브에이전트에게든 에이전트원칙 `agent-principles.md`의 경로를 넣고, 한국어로 쓰는 서브에이전트에는 `domain-korean`의 경로를 함께 넣는다.
7. **주입 컨텍스트** — 큰 명세의 「결정 기록」 절(관례 골격 포함)과, 그 도메인에서 이미 겪은 함정을 넣어 같은 것을 다시 발견하지 않게 한다.
8. **멈추는 기준과 산출 계약** — 브랜치까지만 진행하고 병합·배포·main push는 하지 않는다. 멈추는 기준과 메시지와 리포트는 프로토콜 파일을 따르며, 리포트는 `리포트` 필드의 경로에 쓰고 커밋하지 않는다.

## 받은 메시지 처리

현재 세션은 상향 메시지를 받으면 아래대로 처리하고, 하향 메시지는 프로토콜 파일의 형식대로 쓴다. 메시지는 서브 세션이 멈춘 뒤에만 보낸다. 같은 서브 세션에 보낼 메시지가 여럿이면 한 번에 묶고, 통합 브랜치를 바꾸는 메시지(`BASE-UPDATED`, `CONTRACT-CHANGED`)를 앞에 둔다. 받을 서브 세션이 실행 중이어서 미룬 메시지는 「시험 병합」 전의 확인으로 되찾는다.

**BLOCKED 처리.** 현재 세션은 사유 코드와 `유형`마다 아래대로 처리한다. 한 번에 사유가 여럿이면 바로 처리할 수 있는 사유를 먼저 모두 답한다.

| 사유 코드(유형) | 현재 세션이 할 일 | 보낼 메시지 |
|---|---|---|
| `user-decision`(범위 밖 결정) | 사용자에게 하나씩 묻고 답을 「결정 기록」에 커밋한다 | 요청한 쪽에 `ANSWER` |
| `user-decision`(리뷰 🔴) | 🔴 를 사용자에게 알리고 답을 「결정 기록」에 커밋한다 | 요청한 쪽에 `ANSWER` |
| `user-decision`(리뷰 관점 부족) | 그 렌즈를 실행할지 사용자에게 묻는다 | 요청한 쪽에 `ANSWER` |
| `user-decision`(SDD 정지) | 비가역 작업, 보안 작업, 워크트리 밖 부작용이면 승인할지 사용자에게 묻는다. 모든 진행 방법이 추측인 plan 이면 큰 명세나 「결정 기록」에 근거를 보강한다. 사용자가 작업을 거절하면 거절과 대안을 보내고, 워크스트림을 접을지는 따로 묻는다 | 요청한 쪽에 `ANSWER` |
| `user-decision`(환경 문제) | 권한이나 도구 설치를 사용자에게 조치해 달라고 하고 결과를 확인한다 | 요청한 쪽에 `ANSWER` |
| `contract-change` | 사용자에게 기각·미룸·채택을 고르게 한다. 채택하면 큰 명세와 계약 코드(공유 가정이면 「결정 기록」)를 고친다 | 채택이면 그 계약 행의 제공자와 소비자 모두(공유 가정이면 그 가정을 쓰는 서브 세션 모두)에 `CONTRACT-CHANGED`, 기각·미룸이면 요청한 쪽에 `ANSWER` |
| `shared-file-change` | 공용 파일이면 통합 브랜치에서 고친다. 큰 명세 본문이면 사용자에게 기각·미룸·채택을 고르게 한다 | 공용 파일이면 요청한 쪽에 `BASE-UPDATED`, 큰 명세 채택이면 바뀐 절이 다루는 워크스트림 모두에 `CONTRACT-CHANGED`, 기각·미룸이면 요청한 쪽에 `ANSWER` |
| `dependency-add` | 통합 브랜치에서 의존성 목록과 잠금 파일에 패키지를 추가해 커밋한다 | 요청한 쪽에 `BASE-UPDATED` |
| `test-double-add` | 계약 코드에 테스트 대역을 추가하고 계약 표의 단위·의미와 대조한다 | 요청한 쪽에 `BASE-UPDATED` |

**FAILED와 CANCELED.** `FAILED`를 받으면 현재 세션은 원인과 되돌릴 것을 사용자에게 알리고, 같은 서브 세션에 `REVISE`, `RESTART`로 새 서브 세션, `CANCEL` 중 하나를 고르게 한다. `CANCELED`를 받으면 현재 세션은 그 워크트리의 워커가 끝났는지 CLI 의 서브에이전트 화면에서 확인해 달라고 사용자에게 요청한다. 사용자가 끝났다고 답하면 현재 세션은 브랜치와 워크트리를 남길지 지울지 사용자에게 묻는다. 명세 서브 세션이 `FAILED`나 `CANCELED`로 끝났으면 현재 세션은 이 선택지 대신 「명세 단계」의 선택지(`RESTART`로 다시 쓰기, 범위에서 빼기)를 고르게 한다.

사용자가 워크스트림을 접기로 하면 현재 세션은 「결정 기록」에 '접은 워크스트림: <워크스트림 id> — 이유' 한 줄을 커밋한다. 이어서 현재 세션은 그 워크스트림이 제공자인 계약 행을 `contract-change` 처리대로 다뤄, 행을 지우거나 제공자를 바꾼다. 그래야 계약 테스트의 생략 사유에 접은 워크스트림의 id가 남지 않는다.

**REVISE 를 쓰는 상황.** 현재 세션은 「승인 항목」, 「수정 범위 대조」, 「리뷰 마커 확인」, 「판정 기록 확인」이 고칠 것을 낼 때, 「형식 이탈」에서 판단에 필요한 필드가 빠졌을 때, `FAILED` 뒤 같은 서브 세션에 다시 시키기로 했을 때 `REVISE`를 쓴다. 실패 뒤 재시도에서 고칠 코드가 없으면 `고칠 항목`에 다시 실행할 단계를 적는다.

**형식 이탈.** 머리줄이 프로토콜 파일의 종류와 사유 코드 밖이거나 정해진 필드가 빠진 응답은 형식 이탈이다. 현재 세션은 판단할 수 있으면 해석해 진행하고, 판단에 필요한 필드가 빠졌으면 `REVISE`(대상: 응답)를 보낸다.

## 이어 쓰기와 재개

현재 세션은 하향 메시지를 모두 그 워크스트림의 서브 세션에 SendMessage 이어 쓰기로 보내고, 워크스트림 코드를 직접 고치지 않는다. 현재 세션 층에서 하던 일의 단위는 워크스트림 하나이며, 서브 세션 아래 워커의 재개 규칙은 프로토콜 파일이 정한다.

CLI의 서브에이전트 화면에는 사용자만 들어갈 수 있다. 완료 통지가 오지 않는 서브 세션이 있으면 현재 세션은 그 화면에서 그 세션의 실행 상태를 확인해 달라고 사용자에게 요청한다. 세션이 끊겨 식별자가 사라졌거나 재개가 실패해도 현재 세션은 옛 서브 세션이 끝났는지 같은 방법으로 사용자에게 확인받는다. 끝났으면 `RESTART`로 새 서브 세션을 시작하고 `이어 받을 상태`에 워크스트림 브랜치·하부 명세·plan과 워크트리에 남은 SDD 작업 공간을 적는다.

현재 세션이 재시작하면 진행 위치는 「진행 위치」로 도출하고, 답할 메시지는 그 단계의 서브 세션 리포트에서 `메시지 기록` 절 마지막 상향 메시지로 도출한다. 명세 단계가 끝났으면 명세 서브 세션의 리포트는 보지 않는다. 마지막 메시지가 `AWAITING_APPROVAL`, `BLOCKED`, `DONE`, `FAILED`, `CANCELED`이고 그 서브 세션이 실행 중이 아니면, 현재 세션은 그 메시지에 아직 답하지 않은 것으로 보고 「받은 메시지 처리」대로 처리한다. 통합용 워크트리에 병합 중인 상태나 `try/*` 브랜치가 남아 있으면 현재 세션은 `git merge --abort`와 `git switch dev/<개발>` 뒤 `try/*`를 지우고 그 시험 병합을 처음부터 한다.

## 가드레일

현재 세션은 구현 서브 세션(다른 저장소의 독립 작업은 그 서브 세션)이 `DONE`을 돌려주면 아래 검사를 차례로 한다. 명세 서브 세션의 `DONE`에는 「명세 단계」가 정한 검사만 한다. 아래 명령은 모두 `git -C <통합용 워크트리>`로 실행하며 여기서는 `git`으로 줄여 적는다. `<개발>`은 개발 이름이고 `<id>`는 워크스트림 id다.

**수정 범위 대조.** 현재 세션은 `git diff --name-only --no-renames dev/<개발>...ws/<개발>/<id> -- . ':(exclude)<허용 경로 1>' … ':(exclude,glob)docs/superpowers/specs/*-<개발>-<id>-design.md' ':(exclude,glob)docs/superpowers/plans/*-<개발>-<id>.md' ':(exclude,glob)docs/superpowers/reviews/*-<개발>-<id>-*' ':(exclude,glob)docs/superpowers/reviews/*-<개발>-<id>-*/**'`를 실행한다. 큰 명세의 허용 경로와 자기 문서 경로를 모두 exclude로 넣으므로 출력이 비어 있어야 통과한다. 출력에 파일이 나오면 병합하지 않고 그 서브 세션에 `REVISE`를 보낸다. 점 세 개는 두 브랜치의 공통 조상부터 비교하므로, 통합 브랜치에서 받은 변경은 출력에 나오지 않는다. `--no-renames`를 붙이면 허용 경로 밖 파일을 안으로 옮긴 변경이 원래 경로의 삭제로 드러난다.

**리뷰 마커 확인.** 현재 세션의 Stop 게이트(미리뷰 명세가 남은 채 턴을 끝내지 못하게 하는 훅)는 훅 입력의 작업 디렉터리가 속한 저장소만 본다. 그래서 서브 세션이 쓴 문서와, 현재 세션이 통합용 워크트리에 쓴 계약 코드 plan 에는 이 게이트가 적용되지 않는다. 현재 세션은 통합용 워크트리에서 고친 큰 명세(임시 분할, 완전체 명세, 다시 나눈 분할)와 계약 코드 plan 을 커밋하기 전에 그 파일의 마지막 비공백 줄이 아래 마커인지 직접 확인한다.

서브 세션 문서는 통합용 워크트리에 들이기 전에 확인한다. 하부 명세는 완전체 명세로 옮기기 전에 `spec/<개발>/<임시 id>` 브랜치에서, 구현 서브 세션의 plan 은 병합 전에 `git diff --name-only --diff-filter=A dev/<개발>...ws/<개발>/<id> -- docs/superpowers/specs docs/superpowers/plans`로 구한다. 통합용 워크트리에는 그 파일이 없으므로, 각 파일의 마지막 비공백 줄을 `git show <브랜치>:<경로> | grep -v '^[[:space:]]*$' | tail -n 1`로 읽어 `spec-review` 마커(`passed`나 `escalated`)인지 확인한다. 이 계약은 플러그인의 `hooks/_spec_marker.sh` `marker_is_terminal`과 같다. 마커가 없으면 옮기거나 병합하지 않고 그 서브 세션에 `REVISE`를 보낸다. 명세 서브 세션이면 `RESTART`로 리뷰를 다시 시킨다. 마커가 `escalated`이면 그 🔴의 사용자 답이 「결정 기록」에 있는지 확인하고, 없으면 병합하지 않고 `user-decision`(리뷰 🔴) 처리대로 사용자에게 묻는다. 현재 세션은 답을 적은 뒤 검사를 이어 가고, 그 답이 하부 명세나 구현을 바꿔야 하면 `REVISE`를 보낸다.

**판정 기록 확인.** 현재 세션은 명세 서브 세션의 `DONE`을 받을 때, 다른 저장소의 독립 작업에서 하부 명세를 승인할 때, 병합 전에 리포트의 `명세 이탈`, `스스로 판정한 모호함`, `SDD 판정과 남은 지적`을 읽는다. 마지막 칸이 '예'(범위 밖 항목에 가깝다)인 줄만 사용자에게 묻고, 사용자가 판정을 뒤집으면 `REVISE`를 보낸다(명세 서브 세션이면 `RESTART`). 나머지 줄은 「흐름」 마무리에서 모아 보인다. 같은 때 현재 세션은 `렌즈 그룹 판정` 절을 읽어 발동 기준에 해당한 렌즈를 사용자에게 제안하고(`dispatching-lenses`의 「렌즈 그룹」), 승인받으면 그 렌즈 실행을 `REVISE`의 `고칠 항목`으로 보낸다.

**검증 의존 대기.** 검증 의존이 있는 워크스트림이 `DONE`을 돌려줘도, 현재 세션은 그 워크스트림이 검증 의존하는 워크스트림이 모두 통합 브랜치에 들어올 때까지 시험 병합을 미룬다. 그래야 시험 병합의 통합 확인이 실제 구현으로 실행된다. 「진행 위치」는 대기 중인 워크스트림을 진행 중으로 보이므로, 현재 세션은 큰 명세의 검증 의존과 통합 브랜치의 `Workstream:` 줄을 대조해 대기 여부를 판정한다. 대기 중인 서브 세션이 대상의 통합 결과를 받아야 하면 현재 세션은 그 서브 세션에 `BASE-UPDATED`를 보낸다.

**시험 병합.** 현재 세션은 시험 병합 전에 `git log --oneline --invert-grep --grep='^결정 기록:' --grep='^계약 의미 확정:' ws/<개발>/<id>..dev/<개발> -- <계약 코드 경로> <큰 명세 경로> 'docs/superpowers/specs/*-<개발>-spec*-design.md' <의존성 목록·잠금 파일 경로>`를 실행한다. git 은 `--grep` 여럿을 OR 로 묶으므로 두 제목 중 하나로 시작하는 커밋이 빠진다. 출력이 비어 있지 않으면 그 워크스트림은 바뀐 계약이나 큰 명세를 받지 않았으므로 현재 세션은 병합하지 않는다. 현재 세션은 출력의 커밋이 무엇을 바꿨는지 본다. 바뀐 것이 그 워크스트림의 계약 행(제공자나 소비자로 든 행)이거나 그 워크스트림이 쓰는 공유 가정이면 `CONTRACT-CHANGED`를 보낸다. 그 밖이면 `BASE-UPDATED`를 보낸다.

출력이 비어 있으면 현재 세션은 `git switch -c try/<id> dev/<개발>`로 임시 브랜치를 만들고 `git merge --no-ff ws/<개발>/<id>`로 병합한다. 병합 커밋 메시지에는 「측정」의 트레일러와 `Workstream: ws/<개발>/<id>` 트레일러를 넣는다. 병합이 충돌하면 `git merge --abort` 뒤 아래 실패 처리로 간다. 충돌 파일은 「수정 범위 대조」를 통과했으므로 그 워크스트림의 허용 경로 안에 있고, 현재 세션은 그 서브 세션에 충돌 파일 목록을 `할 일`에 적은 `BASE-UPDATED`를 보낸다.

병합되면 현재 세션은 계약 테스트와 큰 명세의 통합 확인을 실행한다. 계약 테스트의 생략 사유에 병합 대상의 워크스트림 id 가 있으면 실패로 본다. 그 워크스트림의 모듈 경로가 계약 코드와 다르다는 뜻이기 때문이다. 접지 않은 모든 워크스트림이 들어가는 마지막 시험 병합에서는 생략이 하나도 없어야 한다. 통과하면 현재 세션은 `git switch dev/<개발>`, `git merge --ff-only try/<id>`, `git branch -D try/<id>`를 실행한다. 그 리포트에 `확정한 계약 의미`가 있으면 계약 표의 '확정 예정' 칸을 채워 `계약 의미 확정:` 커밋으로 남긴다. `확정한 결정`은 「흐름」 마무리 단계에서 한꺼번에 옮긴다.

실패하면 현재 세션은 `git switch dev/<개발>`과 `git branch -D try/<id>`로 임시 브랜치를 지우고 원인에 따라 처리한다. 원인이 계약이면 `contract-change` 처리대로 사용자에게 고르게 한다. 원인이 그 워크스트림 안이면 그 서브 세션에, 이미 병합된 워크스트림 Y에 있으면 Y의 서브 세션에 `INTEGRATION-FAILED`를 보낸다. 원인을 하나로 특정하지 못하면 후보 서브 세션 모두에 보낸다.

Y가 고쳐 `DONE`을 돌려주면 현재 세션은 Y의 수정을 같은 `Workstream:` 트레일러를 넣은 시험 병합으로 넣는다. 이어서 현재 세션은 Y에 검증 의존하는 워크스트림 전부의 통합 확인을 통합 브랜치에서 다시 실행하고(이미 병합된 워크스트림도 대상이다), 원래 실패한 워크스트림의 시험 병합을 다시 한다.

**되돌림을 쓰지 않는 이유.** 현재 세션은 `git revert`로 통합 실패를 처리하지 않는다. 되돌린 병합은 git이 공통 이력으로 보아 다시 병합할 때 처음 변경이 빠지기 때문이다(git 문서 `howto/revert-a-faulty-merge`).

**진행 위치.** 현재 세션은 상태 문서 없이 git에서 진행 위치를 도출한다. 현재 세션은 사용자 승인을 받은 뒤에만 큰 명세의 새 절을 `dev/<개발>`에 커밋하고, 초안은 통합용 워크트리에 커밋하지 않은 채로 둔다. 그래서 단계는 아래 표지로 정한다.

| 표지 | 단계 |
|---|---|
| 큰 개발이고 `dev/<개발>`의 큰 명세가 아직 완전체 명세가 아니다(「겹침 판정」이 없다) | 명세 단계. 리포트 `메시지 기록`의 마지막 상향 메시지가 `DONE`이고 `spec/<개발 이름>/<임시 id>` 브랜치의 하부 명세에 리뷰 마커가 있거나, 「결정 기록」에 '뺀 하위 프로젝트' 줄이 있는 임시 워크스트림은 끝났다 |
| 완전체 명세(「겹침 판정」)는 있고 「절 배정」이 없다 | 다시 나누기 단계. 「결정 기록」에 '직접 진행' 줄이 있으면 현재 세션이 직접 진행 중이다 |
| 「절 배정」은 있고 계약 테스트가 아직 커밋되지 않았다 | 계약 코드 작성 중 |
| 계약 테스트가 커밋되었다 | 구현 단계. 아래 규칙으로 워크스트림마다 도출한다 |
| 다른 저장소의 독립 작업이다 | 아래 규칙으로 작업마다 도출한다 |

구현 단계에서 `git log dev/<개발> --format=%B`에 `Workstream: ws/<개발>/<id>` 줄이 있는 워크스트림은 끝났다. `git branch --merged`는 커밋이 아직 없는 워크스트림 브랜치도 병합된 것으로 내므로 쓰지 않는다.

끝나지 않은 워크스트림 브랜치는 `git diff --name-only dev/<개발>...ws/<개발>/<id> -- 'docs/superpowers/plans/*-<개발>-<id>.md'`가 파일을 내면 구현 중이고, 내지 않으면 plan 작성 중이다. 다른 저장소의 독립 작업에서는 plan 없이 `'docs/superpowers/specs/*-<개발>-<id>-design.md'`만 나오면 승인 대기이고, 둘 다 없으면 하부 명세 작성 중이다. 큰 명세 목록에 있는데 브랜치가 없는 워크스트림은 시작 전이다. 큰 명세 「결정 기록」에 '접은 워크스트림' 줄이 있는 워크스트림은 브랜치가 있든 없든 접힘이다.

## 측정

현재 세션은 워크스트림마다 실패한 시험 병합 수와 그 서브 세션의 완료 통지들(재개할 때마다 하나씩 온다)의 `subagent_tokens` 합을 센다. 이 값은 시험 병합의 `git merge --no-ff -m`에 `Integration-Failures:`와 `Tokens:` 트레일러로 넣는다. 같은 워크스트림이 두 번 이상 병합되면 각 병합 커밋에는 앞 병합 뒤부터 그 병합까지의 증분을 적는다. fast-forward로 통합 브랜치에 들어가므로 이 커밋이 통합 브랜치에 남는다. 개발이 끝나면 현재 세션이 `git log dev/<개발>`에서 이 값을 모아 사용자에게 보고한다. 명세 단계의 토큰과 대기 시간은 「흐름」 4단계의 `Spec-Tokens:`·`Spec-Wait:` 트레일러에 있고, 구현 단계의 `BASE-UPDATED` 수는 리포트 `메시지 기록`의 받은 하향 메시지 머리줄로 센다.

`FAILED`나 `CANCELED`로 끝나 병합되지 않은 워크스트림은 트레일러가 남지 않으므로, 현재 세션은 마무리 보고에서 그 워크스트림을 따로 적는다.

## 관측성

수동 `Agent` 중첩은 `/workflows` 집계 대시보드에 뜨지 않는다. 대신 CLI가 서브에이전트를 표시하고, 사용자는 그 항목을 더블클릭해 각 서브 세션의 실행 화면으로 들어간다. 집계 대시보드와 메트릭은 볼 수 없고, 어떤 워크트리가 어느 서브 세션에 배정됐는지도 화면에 나오지 않는다.

## 재구현 금지

아이디어에서 명세까지는 `brainstorming`, plan은 `writing-plans`, 실행 루프는 `subagent-driven-development`, 병렬 디스패치 메커니즘은 `dispatching-parallel-agents`, 워크트리 격리는 `using-git-worktrees`, 리뷰 렌즈는 `lens-*`가 소유한다.

## 한계

3층은 조율 층을 추가하므로 맡길 워크스트림이나 작업이 둘 이상일 때만 값을 한다. 무엇이 검증됐고 무엇이 아직 아닌지는 근거 문서의 「이어받는 판단과 검증」, 「근거와 한계」, 「검증하지 않은 가정」, 「2026-10-10 개정」, 「2026-10-11 개정 — 묶는 단위」, 「2026-10-12 개정 — 명세 단계와 다시 나누기」에 있다.

**비목표** — `Workflow` 결정론 버전과 집계 UI 대시보드와 오케스트레이션 상태 문서는 만들지 않는다. 진행 위치는 git에서 도출한다. 4층 이상 더 깊은 중첩도 다루지 않는다.
