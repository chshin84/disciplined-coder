# nested-orchestration — 워크스트림으로 나눠 맡기는 3층 오케스트레이션

언제 이 스킬을 쓰는지는 「라우팅」이 정하고, 방법은 이 스킬이 정한다. 기존 스킬을 재구현하지 않고 조합한다. 설계 근거와 검증 결과는 `docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`에 있다.

## 용어

이 스킬은 아래 이름을 아래 뜻으로만 쓴다.

| 이름 | 뜻 |
|---|---|
| 현재 세션 | 사용자와 대화하며 큰 명세·계약·통합을 맡고 워크스트림의 명세·plan·구현은 직접 쓰지 않는 세션 |
| 서브 세션 | 워크스트림 하나를 하부 명세부터 구현까지 맡고 사용자와 대화하지 못하는 서브에이전트 |
| 워커 | 서브 세션이 실행하는 구현자와 렌즈 |
| 워크스트림 | 서브 세션 하나가 맡는 작업 단위 |
| 큰 명세 | 개발 전체를 워크스트림으로 묶고 워크스트림 사이 계약과 결정 기록을 적는 명세 |
| 하부 명세 | 워크스트림 하나의 내부 설계를 적는 명세 |
| 하위 프로젝트 | 큰 개발을 분해한 단위로, 워크스트림으로 묶기 전의 단위(superpowers `brainstorming`의 이름) |
| 서로 독립된 큰 작업 | 서로 자료를 주고받지 않고 각각 plan을 따로 둘 만큼 큰 작업 |
| SDD | plan을 태스크마다 구현 워커와 리뷰어로 실행하는 superpowers `subagent-driven-development` 스킬 |
| 머리줄(header) | 메시지의 첫 줄. 메시지 종류와, 종류가 `BLOCKED`이면 사유 코드를 적는다 |
| 상향 메시지 | 서브 세션이 현재 세션에 돌려주는 메시지 |
| 하향 메시지 | 현재 세션이 서브 세션에 보내는 메시지 |
| 사유 코드 | `BLOCKED`의 사유를 가리키는 정해진 이름(「메시지 형식」의 BLOCKED 처리 표) |

## 큰 개발 분할

**맡길지 판단하는 시점.** 현재 세션은 superpowers `brainstorming`을 따르다가 요청을 하위 프로젝트 여럿으로 분해하기로 했을 때 서브 세션에 맡길지 판단한다. `brainstorming`은 분해한 하위 프로젝트를 차례로 브레인스토밍하라고 적지만, 이 스킬을 쓰는 현재 세션은 하위 프로젝트마다 명세·plan·구현을 직접 진행하지 않는다.

현재 세션은 설계 문서(`docs/superpowers/specs/`의 spec)가 승인된 뒤 `writing-plans`를 실행하기 전에도 맡길지 판단한다. 하위 프로젝트로 분해하지 않은 큰 개발도 여기서 판단하며, 이때는 현재 세션이 설계 문서에서 하위 프로젝트 목록을 만든다. 2026-10-10에 이 시점들을 정한 이유는 `brainstorming`의 판단 문구가 버전마다 바뀌어도 이 단계들이 남기 때문이다.

현재 세션이 새 spec을 처음 쓰려 하면 `hooks/nested_judgment_pretooluse.sh`가 그 `Write`를 한 번 거부하고 맡길지 판단하라고 지시한다. 현재 세션은 이 지시를 받으면 spec을 쓰기 전에 판단하고 판단과 근거를 사용자에게 알린다. 2026-10-11에 판단 시점을 spec 승인 뒤로만 둔 세션은 plan을 둘로 나누어 차례로 진행한다고 먼저 예고했고, 사용자가 지적한 뒤에야 판단했다.

**맡기는 기준.** 현재 세션은 계약 코드를 고정한 뒤 동시에 시작할 수 있는 워크스트림(「묶는 단위」의 시작 워크스트림)이 둘 이상이고, 각 워크스트림이 plan을 따로 둘 만큼(태스크 다섯 이상으로 예상될 만큼) 크면 서브 세션에 맡긴다. 다섯은 2026-09-24에 사용자와 합의한 값이고 측정값이 아니다. 이 기준은 이 스킬이 소유한다. 현재 세션은 하위 프로젝트로 분해했는지와 관계없이 이 기준으로 판단하고, 기준에 들지 않으면 superpowers 흐름을 그대로 따른다.

맡기려면 현재 세션은 근거를 보여 사용자 승인을 한 번에 받는다. 근거에는 하위 프로젝트 목록, 「묶는 단위」의 공유 항목 표와 설계 의존 표와 그 결과인 시작 의존, 워크스트림마다 맡는 일과 예상 태스크(`writing-plans`의 태스크) 목록을 적는다. 서로 독립된 큰 작업을 맡길 때는 작업마다 맡는 일과 예상 태스크 목록을 적는다.

승인받은 하위 프로젝트 목록이 「묶는 단위」의 입력이며, 사용자가 목록을 바꾸면 현재 세션은 표와 판정을 다시 만들어 다시 승인받는다. 2026-10-10 측정에서 superpowers 식으로 분해한 목록은 요청에 따라 실행마다 달랐고, 요청 문장의 이름을 옮기는 규칙도 일부 요청에서 흔들렸다. 그래서 현재 세션은 목록을 규칙으로 정하지 않고 사용자 승인으로 고정한다.

**묶는 단위.** 현재 세션은 승인받은 하위 프로젝트 목록으로 공유 항목 표를 먼저 만들고, 그다음 설계 의존 표를 만든다. 공유 항목 표의 행은 둘 이상의 하위 프로젝트가 주고받는 자료·상태·정의다. 현재 세션은 명명 관례 같은 관례와 용어 풀이를 행으로 두지 않고 「결정 기록」에 적는다.

공유 항목 표의 칸은 항목, 소유 하위 프로젝트, 사용 하위 프로젝트, 판정, 고정한 의미다. 소유 하위 프로젝트는 그 항목의 의미를 바꾸는 결정을 내리는 하위 프로젝트다. 사용 하위 프로젝트는 그 항목을 받는 하위 프로젝트이며, 현재 세션은 소유 하위 프로젝트를 사용 칸에 넣지 않는다.

현재 세션은 모든 행에 "어느 하위 프로젝트의 내부 설계도 정하지 않고 이 항목의 이름·형식·단위·의미(시간 의미와 결측 의미 포함)를 지금 고정할 수 있는가"를 묻는다. 고정할 수 있으면 판정은 떼어냄이고, 현재 세션은 고정한 의미를 그 행에 한 줄로 적는다. 고정할 수 없으면 현재 세션은 사용 하위 프로젝트마다 "그 하위 프로젝트의 설계가 이 항목의 의미를 함께 정해야 하는가"를 묻는다. 소유 하위 프로젝트가 둘 이상이면 판정은 합침이다. 소유가 하나이면 함께 정해야 하는 사용 하위 프로젝트가 있을 때 판정은 합침이고, 없을 때 판정은 순서다.

소유 하위 프로젝트가 없는데 고정할 수 없으면, 현재 세션은 그 항목을 바꾸는 하위 프로젝트를 모두 소유 하위 프로젝트로 적고 판정한다. 합침 행에서 현재 세션은 소유 하위 프로젝트를 모두 합치고, 의미를 함께 정해야 하는 사용 하위 프로젝트도 같은 워크스트림으로 합친다. 합침·순서 행에서 의미를 받기만 하는 사용 하위 프로젝트는 합치지 않으며, 현재 세션은 소유 쪽 접근 절차를 계약으로 떼어낸다. 그 계약의 의미 칸은 소유 워크스트림이 통합 브랜치에 들어갈 때 현재 세션이 확정한다.

합침 행끼리 하위 프로젝트가 겹치면 현재 세션은 겹친 행의 하위 프로젝트를 모두 한 워크스트림으로 묶는다. 현재 세션은 큰 명세 단계에서 떼어냄 행과, 합침·순서 행에서 떼어낸 접근 절차를 「계약 표」의 행으로 옮기고, 하위 프로젝트 이름을 워크스트림 id로 바꾼다. 소유 쪽은 제공자가 되고 사용 쪽은 소비자가 되며, 소유가 없는 행의 제공자는 현재 세션이다. 이 연결 규칙은 이 절이 소유한다.

설계 의존 표의 행과 열은 합친 묶음과 남은 하위 프로젝트다. X를 설계하려면 Y의 실제 결과(구현 결과나 조사 결과)를 보아야 하면 현재 세션은 X→Y에 1을, 그렇지 않으면 0을 적는다. 공유 항목 표에서 이름·형식·단위·의미를 고정한 관계는 0이다. 합침·순서 행에서 합치지 않은 사용 쪽의 관계는 1이므로, 그 사용 쪽은 소유 쪽 뒤에 설계한다.

현재 세션은 설계 의존 순환에 함께 든 묶음과 하위 프로젝트만 한 워크스트림으로 합치고, 나머지는 하나를 워크스트림 하나로 둔다. 순환을 합치고 나면 워크스트림 사이 의존에는 순환이 남지 않으므로, 현재 세션은 그 의존을 큰 명세 의존 순서 항목의 시작 의존에 적는다. 시작 의존에서 선행 워크스트림이 없는 워크스트림을 시작 워크스트림이라 부르며, 시작 워크스트림들은 동시에 시작할 수 있다. 시작 워크스트림이 하나뿐이면 그 개발은 「맡기는 기준」에 들지 않는다.

현재 세션이 합치는 강한 결합은 설계 의존 순환과 떼어낼 수 없는 공유 항목이다. 설계 의존 표는 설계 활동 사이 선후 관계를 적는 time-based DSM(Design Structure Matrix, 의존을 행렬로 적는 설계 기법)이고, 순환을 한 묶음으로 찾고 나머지를 순서로 두는 근거는 partitioning 이다. 공유 항목 표는 하위 프로젝트 사이 결합을 적는 static DSM 이고, 강하게 결합된 요소를 한 군집으로 묶는 근거는 clustering 이다(Wikipedia 「Design structure matrix」). 순환만 합치는 기준은 axiomatic design(설계 변수 사이 결합을 행렬로 분석하는 설계 이론)과도 같다.

떼어낼 수 없는 공유 항목을 합치는 근거는 Parnas(1972)의 권고 1번이다. 이 권고에 따라 현재 세션은 자료 구조와 그 접근·수정 절차를 한 워크스트림에 두고, 다른 워크스트림이 그 구조를 공유하지 않게 한다. 의미를 함께 정하는 하위 프로젝트와 그 항목을 함께 바꾸는 소유 하위 프로젝트는 같은 구조를 정의하는 셈이므로, 현재 세션은 이 쪽만 합친다. 의미를 받기만 하는 하위 프로젝트는 접근 절차로 구조를 쓰므로 현재 세션은 순서로 둔다.

2026-10-10 측정에서 하위 프로젝트 목록을 고정한 요청 다섯을 5회씩 묶었을 때, 순환만 합치는 방식은 다섯 요청 모두에서 5회 같은 분할을 냈다. 그러나 주문 처리 요청에 일부러 넣은 상태 변경 순환은 어느 실행도 설계 의존으로 세지 않았다. 현재 세션은 공유 항목 표로 이 누락을 다룬다. 현재 세션은 두 표를 모두 승인 근거에 넣고, 사용자는 떼어냄 행의 고정한 의미를 읽어 현재 세션이 내부 설계를 미리 정했는지 확인한다.

2026-10-11 측정에서 현재 세션은 여섯 요청마다 현행 규칙과 이 규칙을 5회씩 적용하게 했다. 순서 판정을 넣은 이 규칙은 기대 분할을 NP-bond-agg 4회, 주문 처리 5회, 나머지 요청 4~5회 냈고, 현행 규칙은 NP-bond-agg 0회, 주문 처리 0회였다. 순서 판정이 없던 첫 문안은 한 방향 관계를 합쳐 미달했고, 서로 독립된 두 작업 요청의 기대 분할은 결과를 본 뒤 사용자 승인으로 정정했다. 기대 분할 기준이 이 규칙의 판정 질문과 같은 개념을 쓴다는 한계가 있다.

최종 리뷰 뒤 소유가 둘 이상인 항목을 합치도록 고친 문안은 주문 처리, NP-bond-agg, 인증 순차 이전에서 5회 모두 기대 분할을 냈다. 기록은 `docs/superpowers/reviews/` 아래 `2026-10-11-shared-definition-grouping-check/`, `-check-2/`, `-check-3/` 폴더에 있다.

두 워크스트림이 같은 파일을 고쳐야 하면 현재 세션이 그 파일을 맡고 「공용 파일」대로 다룬다. 의존성 목록과 잠금 파일은 「공용 파일」의 한 워크스트림 소유 규칙을 따른다. 코드가 없는 단계에서는 경로 겹침을 셀 수 없으므로 합치는 조건으로 쓰지 않는다.

**큰 명세.** 현재 세션은 큰 명세를 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-design.md`에 쓰고 `review-specs`로 리뷰한 뒤 사용자 승인을 받는다. 워크스트림 내부 설계는 적지 않고 아래 항목을 적는다.

- 워크스트림 목록: 워크스트림 id(영문 소문자)와 맡는 일
- 워크스트림 사이 계약 표: 경계를 넘는 자료마다 「계약 표」의 칸을 채운 행
- 의존 순서: 워크스트림마다 시작 의존(다른 워크스트림의 산출물이 있어야 시작할 수 있는 관계)과 검증 의존(통합 확인에 다른 워크스트림의 실제 구현이 필요한 관계)
- 수정 허용 경로: 워크스트림마다 git pathspec 목록
- 소유 표: 현재 세션이 소유하는 공용 파일과, 의존성 목록·잠금 파일을 고치는 워크스트림
- 공통 제약과 워크스트림별 통합 확인 방법
- 「결정 기록」 절

설계 문서가 승인된 뒤에 맡기기로 했으면 현재 세션은 그 설계 문서를 큰 명세로 삼는다. 이 경로에서는 현재 세션이 main 대신 설계 문서가 커밋된 끝에서 `dev/<개발 이름>`을 만들고, 그 브랜치에서 설계 문서에 위 항목을 보강해 커밋한 뒤 다시 승인받는다. 설계 문서에 사용자가 정한 워크스트림 내부 방식은 그대로 두고, 하부 명세를 승인할 때 대조한다.

**검증 의존.** X의 서브 세션은 X의 설계와 단위 테스트를 계약 코드와 테스트 대역으로 진행할 수 있다. 그런데 X의 통합 확인에 Y의 실제 구현이 필요하면 X는 Y에 검증 의존한다. 현재 세션은 큰 명세에 워크스트림별 통합 확인 방법을 적을 때 검증 의존을 판정한다. 검증 의존은 시작을 늦추지 않으므로, 현재 세션은 시작 워크스트림을 시작 의존만으로 판정한다.

현재 세션은 큰 명세를 승인받기 전에 시작 의존과 검증 의존을 합친 그래프에 순환이 있는지 본다. 순환이 있으면 현재 세션은 그 워크스트림들의 병합 순서를 정할 수 없으므로, 디스패치 전에 순환에 든 워크스트림을 합칠지 사용자에게 묻는다. 계약 테스트는 아직 없는 워크스트림 모듈을 생략하므로, 현재 세션은 병합 순서를 계약 테스트가 아니라 시작 의존과 검증 의존으로 정한다.

**계약 표.** 현재 세션은 워크스트림 경계를 넘는 자료마다 계약 표에 한 행을 두고 아래 칸을 채운다.

| 칸 | 적는 내용 |
|---|---|
| 이름 | 함수 계약이면 공개 함수가 있는 모듈 경로와 함수·타입 이름, 파일 계약이면 파일 경로 |
| 제공자 → 소비자 | 자료를 내는 워크스트림 id 와 쓰는 워크스트림 id. 계약 코드나 현재 세션이 내거나 통합 확인이 쓰면 그 이름 |
| 형식 | 자료형이나 함수 시그니처. 키가 정해진 값이면 열거값, 표나 결과 객체이면 열 이름 |
| 단위 | 값의 단위 |
| 의미(시간·결측 포함) | 서브 세션이 바꾸면 안 되는 값의 뜻, 값이 정해지는 시점과 빈도, 값이 없는 시점이나 항목의 처리(앞값, 0, 오류) |

의미 칸의 시간과 결측은 비워 두지 않고, 해당이 없으면 '없음'을 적는다. 「묶는 단위」가 의미를 소유 워크스트림 통합 때 확정하게 한 행에서, 현재 세션은 의미 칸과 형식 칸의 열거값을 '확정 예정(<소유 워크스트림 id>)'으로 적는다. 현재 세션은 그 워크스트림을 통합할 때 리포트의 `확정한 계약 의미`를 보고 칸을 채우며, 이 확정은 계약 변경이 아니다. 여러 행이 같은 관례를 쓰면 의미 칸에는 큰 명세 「결정 기록」에 적은 관례의 이름을 적는다. 현재 세션은 그 관례를 큰 명세를 리뷰에 넘기기 전에 「결정 기록」에 적고, 그 관례를 고치는 일은 계약 변경으로 다룬다.

이름과 형식은 계약 코드가 원본이고, 단위와 의미는 계약 표가 원본이다. 현재 세션은 큰 명세를 리뷰에 넘기기 전에 두 종류의 자료에 각각 제공자 행이 있는지 확인한다. 하나는 각 워크스트림의 맡는 일에 필요한 자료이고, 다른 하나는 통합 확인이 읽는 자료다. 계약 표가 없는 큰 명세(2026-10-11 전에 쓴 것)는 그 큰 명세의 계약 항목으로 대조한다. 칸을 둔 근거는 이 스킬의 설계 문서 `docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`의 「2026-10-11 개정 — 계약 표」에 있다.

**계약 코드.** 큰 명세 승인 뒤 현재 세션은 `dev/<개발 이름>`에 큰 명세를 커밋하고 계약을 타입·시그니처·계약 테스트 코드로 만들고, 계약 코드의 경로를 소유 표에 현재 세션 소유로 적는다. 계약 코드는 함수 계약마다 공개 함수의 모듈 경로와 시그니처를 정한다. 그 모듈 파일은 제공 워크스트림의 서브 세션이 자기 허용 경로 안에 처음 만든다. 계약 테스트는 그 모듈이 시그니처를 따르는지 대조한다. 모듈을 import 할 때 통합 브랜치에 아직 없는 워크스트림의 모듈이 필요하면, 그 모듈이 대조 대상이든 대조 대상이 읽는 다른 워크스트림의 모듈이든 계약 테스트는 없는 워크스트림의 id 를 생략 사유에 적어 검사를 생략한다. 그래서 소비자가 제공자보다 먼저 병합되어도 계약 테스트가 실패하지 않으며, 현재 세션은 병합 순서를 이 규칙으로 정하지 않는다.

테스트 대역(test double)은 실제 구현 대신 테스트에 쓰는 구현이다. 현재 세션은 계약 코드 plan 을 쓸 때 소비자의 단위 테스트에 필요한 테스트 대역을 정해 계약 코드에 두고, plan 리뷰에서 테스트 대역이 계약 표의 단위·의미를 따르는지 대조한다. 소비자 서브 세션은 다른 워크스트림 함수의 테스트 대역을 자기 경로에 따로 만들지 않는다. 필요한 테스트 대역이 계약 코드에 없으면 서브 세션은 `BLOCKED test-double-add`로 요청한다. 파일 계약은 현재 세션이 통합 확인에서 열 이름과 형식을 대조하고, 단위와 의미는 하부 명세 승인 때 계약 표와 대조한다.

계약 코드의 SDD는 `dev/<개발 이름>`에서 실행한다. 계약 코드도 writing-plans, plan 리뷰, 사용자 plan 검토, 실행 순서로 진행한다. 계약 코드가 있으면 현재 세션이 통합 확인을 기계로 할 수 있다. 계약을 코드로 고정하는 방식은 CodeTeam·Contract-Coding의 설계 사례이고, 산문 계약과 코드 계약을 비교한 결과는 없다.

**결정 기록.** 큰 명세의 「결정 기록」 절은 현재 세션만 쓴다. 현재 세션은 첫 디스패치 전에 명명 관례·오류 처리·공용 유틸리티처럼 워크스트림마다 따로 정하면 충돌하는 결정을 채운다. 워크스트림을 통합하면 그 리포트의 확정 결정을 옮기고, 사용자가 🔴(사용자 결정이 필요한 리뷰 지적)나 범위 결정에 답하면 그 답도 적는다. 공개 인터페이스는 계약 코드에서 도출하므로 옮겨 적지 않는다. 현재 세션은 워크스트림 경계를 넘지 않는 관례와 용어 풀이(예: 구간 경계)도 여기에 적는다.

**공용 파일.** 라우팅 표·진입점·설정 등록부처럼 여러 워크스트림이 고치는 파일은 현재 세션이 소유하고 소유 표에 적는다. 의존성 목록과 잠금 파일은 소유 표에 적은 한 워크스트림만 고치고, 그 워크스트림이 통합 브랜치에 들어갔거나 `DONE`을 돌려준 뒤에는 현재 세션이 고친다. 잠금 파일 충돌은 따로 설치한 두 브랜치에서 생기므로(npm 문서 「package-locks」) 소유를 하나로 둔다.

공용 파일 중 설정 파일에는 사용자가 정한 값과 둘 이상의 워크스트림이 읽는 값만 둔다. 한 워크스트림만 읽는 파라미터는 그 워크스트림의 허용 경로에 둔 설정 파일(예: `configs/<워크스트림 id>.yaml`)에 두고, 그 워크스트림이 허용 경로 안의 코드로 읽는다. NP-bond-agg 큰 명세의 4차 리뷰에서 lens-adversarial 이 공용 설정 파일에 모든 키를 두면 서브 세션이 파라미터를 추가할 때마다 `BLOCKED`로 멈춘다고 지적했다.

다른 워크스트림은 기존 의존성으로 일하고, 의존성 추가가 필요하면 추가할 패키지를 적어 `BLOCKED dependency-add`로 멈춘다. 처리는 「메시지 형식」의 BLOCKED 처리 표를 따른다.

**경로와 브랜치 이름.** 하부 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-<워크스트림 id>-design.md`, 워크스트림 plan은 `docs/superpowers/plans/YYYY-MM-DD-<개발 이름>-<워크스트림 id>.md`에 둔다. 통합 브랜치는 `dev/<개발 이름>`, 워크스트림 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 모든 워크스트림의 허용 경로에는 자기 문서 경로 셋(`docs/superpowers/specs/*-<개발 이름>-<워크스트림 id>-design.md`, `docs/superpowers/plans/*-<개발 이름>-<워크스트림 id>.md`, `docs/superpowers/reviews/*-<개발 이름>-<워크스트림 id>-*`)이 기본으로 들어간다. 패턴의 id 뒤를 닫아 두었으므로 한 id가 다른 id의 접두어여도 서로의 문서를 허용하지 않는다.

**서로 독립된 큰 작업.** 서로 독립된 큰 작업이 둘 이상이면 현재 세션은 작업마다 서브 세션에 맡긴다. 현재 세션이 작업마다 brainstorming으로 요구를 정리해 큰 명세에 워크스트림별 요구로 적고 사용자 승인을 받는다. 워크스트림 사이 계약과 계약 코드는 생략하고 통합 확인은 각 워크스트림의 테스트로 대신한다. 하부 명세부터 구현까지는 큰 개발과 같이 서브 세션이 맡는다.

작업들이 같은 저장소에 있으면 자료를 주고받지 않아도 명명·오류 처리·공용 함수 같은 암묵적 결정이 부딪히므로, 현재 세션은 「결정 기록」을 첫 디스패치 전에 채운다. 작업들이 다른 저장소에 있으면 현재 세션은 저장소마다 큰 명세와 통합 브랜치를 따로 둔다. 현재 세션은 그 저장소에 `git -C <저장소 경로> worktree add <통합용 워크트리 경로> dev/<개발 이름>`으로 통합용 워크트리를 만들고, 「흐름」과 「가드레일」의 git 명령을 `git -C <통합용 워크트리 경로>`로 실행한다. 사용자가 쓰는 그 저장소의 작업 트리를 바꾸지 않기 위해서다.

**근거와 한계.** 이 분할 구조를 단일 세션과 직접 비교한 연구는 찾지 못했다. 가까운 구조인 CAID(2026, 프리프린트)는 관리자가 스텁을 먼저 커밋하고 작업자마다 git 워크트리를 주어 단일 에이전트보다 높은 정확도를 보고했다. 같은 연구에서 작업자를 4명에서 8명으로 늘리자 성능이 내려갔고, 비용은 단일 에이전트보다 컸다.

Specification Gap(2026, 프리프린트)은 일부 정보만 받은 두 에이전트의 통합 정확도가 58%에서 25%로 떨어졌다고 보고했다. 같은 조건의 단일 에이전트는 89%에서 56%였고, 완전한 명세를 주어야 두 에이전트가 단일 에이전트 수준(89%)으로 회복했다. 그래서 계약과 결정 기록은 분할의 손실을 메울 뿐이며 단일 세션보다 낫게 만들지는 않는다.

Claude Code 문서(agent teams)는 순차 작업, 같은 파일 수정, 의존이 많은 일에는 agent teams 보다 단일 세션이나 서브에이전트가 낫다고 적는다. Parnas(1972)는 처리 흐름 순서로 모듈을 분해하는 방식을 기각했다. BenchAgent(2026, 프리프린트)는 단일 과제 벤치마크 10종에서 고정 역할 다중 에이전트 6종 중 5종이 단일 에이전트보다 2.56~11.29%p 뒤졌다고 보고했다.

그래서 현재 세션은 사용자 요구가 없으면 작은 개발을 서브 세션에 맡기지 않는다. 맡길 때는 동시에 시작할 수 있는 워크스트림이 둘 이상인지 확인하고 계약과 결정 기록을 먼저 고정한다. 출처와 대조 내용은 설계 문서의 「근거와 한계」, 「2026-10-10 개정」, 「2026-10-11 개정 — 묶는 단위」에 있다.

## 라우팅

현재 세션은 나눠 맡길 단위에 따라 쓸 스킬을 고른다.

- 단위가 plan·리뷰 루프 없는 단일 태스크이면 현재 세션은 `dispatching-parallel-agents`를 쓴다.
- 「맡길지 판단하는 시점」에서 「맡기는 기준」에 들거나 서로 독립된 큰 작업이 둘 이상이면 현재 세션은 이 스킬을 쓴다.
- 사용자가 나눠 맡기라고 요구하면 현재 세션은 규모와 관계없이 이 스킬을 쓰고, 작은 일이면 조율 비용이 이득보다 클 수 있다고 알린다. 단위가 단일 태스크이면 첫째 불릿을 따른다.
- 위 불릿 어디에도 들지 않으면 현재 세션은 superpowers 흐름을 직접 진행한다.

## 흐름

현재 세션과 서브 세션이 아래 순서로 진행한다.

1. **준비(현재 세션)** — 큰 명세를 커밋하기 전에 main에서 `dev/<개발 이름>`을 만들고(설계 승인 뒤에 맡기는 경로는 「큰 명세」 끝 문단을 따른다), 큰 명세와 계약 코드를 그 브랜치에 커밋한다. 계약 코드의 SDD도 그 브랜치에서 실행한다.
2. **디스패치(현재 세션)** — 시작할 수 있는 워크스트림마다 자기 체크아웃에 남은 채 `git worktree add <워크트리 경로> -b ws/<개발 이름>/<워크스트림 id> dev/<개발 이름>`으로 브랜치와 워크트리를 만들고, 「디스패치 템플릿」으로 서브 세션을 백그라운드로 실행한다. `EnterWorktree`와 `cd`는 쓰지 않는다. 현재 세션이 자기 체크아웃을 떠나면 시험 병합과 다른 워크트리 생성을 할 수 없기 때문이다. `using-git-worktrees`는 워크트리 위치와 ignore 확인에만 따른다. `Agent`의 `isolation:'worktree'`는 브랜치 이름과 기준 커밋을 정할 수 없어 쓰지 않는다.
3. **하부 명세(서브 세션)** — 하부 명세를 쓰고 `review-specs`로 리뷰해 반영한 뒤 커밋하고 `AWAITING_APPROVAL`을 돌려준다.
4. **승인(현재 세션)** — 하부 명세를 대조해 승인하거나 고칠 점을 같은 서브 세션에 보낸다. 대조 항목은 「승인 항목」에 있다.
5. **plan과 구현(서브 세션)** — 승인을 받으면 writing-plans, `review-specs`, SDD 순서로 진행하고 `DONE`을 돌려준다.
6. **통합(현재 세션)** — 「가드레일」의 병합 전 검사와 시험 병합으로 통합 브랜치에 넣는다. 검증 의존이 있는 워크스트림은 「검증 의존 대기」대로 넣는다.
7. **마무리(현재 세션)** — 모든 워크스트림이 「가드레일」의 검사를 통과해 들어가면 통합 브랜치 전체에 최종 브랜치 리뷰를 실행한다. 서브 세션들의 리포트에서 `제안`과 `기능적 반영`을 모아 사용자에게 보이고, 「측정」 값을 보고한다. 설계 문서 「2026-10-10 개정」의 「검증하지 않은 가정」에 적힌 판단(원칙 조항 삭제, 훅 추가, 워크스트림 수 상한)에 쓸 관찰도 함께 보고한다. 통합 브랜치를 main에 병합하는 일은 그다음 사용자 승인을 받아 한다. 워크스트림 plan과 리뷰 기록은 에이전트원칙의 문서 수명 표대로 처리한다.

시작 의존이 없는 워크스트림은 동시에 진행한다. 같은 파일은 「공용 파일」대로 현재 세션이 맡으므로 동시 진행의 조건이 아니다. 다른 워크스트림에 시작 의존하는 워크스트림은 선행 워크스트림이 통합 브랜치에 들어간 뒤 그 끝에서 시작한다.

**승인 항목.** 현재 세션은 하부 명세가 계약 코드의 이름·형식과 계약 표의 단위·의미를 그대로 쓰는지, 수정 허용 경로 밖을 고치려 하지 않는지, 큰 명세 본문과 결정 기록에 충돌하지 않는지를 본다. 현재 세션은 승인하기 전에 리포트의 `스스로 판정한 모호함`을 읽는다. 그 절의 줄이 범위 밖 항목에 가깝다고 표시되어 있으면 현재 세션은 그 줄을 사용자에게 묻고, 사용자가 판정을 뒤집으면 `REVISE`를 보낸다.

계약 코드가 고정하지 않은 공유 가정(공용 자료의 내부 표현, 결정 기록에 없는 관례)을 하부 명세가 새로 세웠으면 현재 세션은 승인할 때 그 가정을 통합 브랜치의 결정 기록에 커밋한다. 같은 가정을 쓸 다른 서브 세션에는 `ASSUMPTION-ADDED`를 보낸다. 그 서브 세션이 이미 다른 가정으로 구현했으면 `BLOCKED contract-change`를 돌려주고, 현재 세션은 「메시지 형식」의 BLOCKED 처리대로 처리한다. Specification Gap 은 통합 격차가 공유 결정 없이 호환 코드를 만드는 어려움에서 온다고 보고했다.

## HARD-GATE 예외

superpowers `brainstorming`의 HARD-GATE는 사람이 명세를 승인하고 plan을 검토하고 실행 방식을 고르게 한다. 서브 세션은 사람과 대화하지 못하므로 이 스킬은 서브 세션에 한해 세 단계를 대체한다. 명세 승인은 현재 세션이 맡는다. plan 검토는 `review-specs` 렌즈 리뷰가 맡는다. 실행 방식은 SDD로 고정한다.

서브 세션은 brainstorming 대화를 열지 않고 큰 명세와 계약 코드를 입력으로 하부 명세를 쓴다. 사용자가 직접 검토하는 문서는 큰 명세와 계약 코드 plan이다. 현재 세션은 사람과 대화하므로 계약 코드에는 이 예외를 쓰지 않는다.

## 디스패치 템플릿

서브 세션은 현재 세션 외 누구와도 대화할 수 없으므로 프롬프트는 자기완결이어야 한다. 현재 세션은 아래 블록을 차례로 넣는다.

1. **역할 선언** — "너는 자율 서브 세션이다. 사용자와 대화할 수 없고, 질문은 상태로 돌려준다. 네 워크트리는 `<워크트리 절대 경로>`이고 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 모든 명령을 그 경로에서 실행한다."
2. **임무** — 큰 명세 경로와 맡은 워크스트림 id를 적는다. 산출물은 하부 명세, plan, 구현, 테스트, 리포트다.
3. **수정 허용 경로(엄수)** — 큰 명세에 적은 그 워크스트림의 허용 경로와 자기 문서 경로만 고친다. 공용 파일이나 계약 변경이 필요하면 고치지 않고, 바꿀 내용을 적어 `BLOCKED shared-file-change`나 `BLOCKED contract-change`로 멈춘다.
4. **하부 명세** — 하부 명세에는 그 워크스트림의 책임과 계약을 구현하는 데 필요한 내용만 적고, 일어날 수 없는 예외를 늘어놓지 않는다. 하부 명세를 `review-specs`로 리뷰해 반영하고 커밋한 뒤 `AWAITING_APPROVAL`로 멈춘다. HARD-GATE 예외 문장을 그대로 넣는다: "이 워크스트림에서 명세 승인은 현재 세션이, plan 검토는 review-specs 렌즈 리뷰가 맡고, 실행 방식은 subagent-driven-development로 고정한다. brainstorming 대화를 열지 않는다."
5. **plan과 구현** — `APPROVE`를 받으면 writing-plans, `review-specs`, SDD(TDD, 프로젝트 테스트 규약) 순서로 진행한다. 워커를 디스패치할 때마다 워크트리 절대 경로를 넣고 모든 명령을 그 경로에서 실행하게 한다. 하향 메시지를 받으면 「메시지 형식」의 하향 메시지 표대로 처리한다. SDD 최종 리뷰 뒤 `finishing-a-development-branch`는 실행하지 않고 `DONE`을 돌려주며 워크트리를 지우지 않는다.
6. **렌즈와 원칙** — 렌즈를 실행하기 전에 `dispatching-lenses`를 통째로 읽는다. 서브 세션은 그 규율을 여는 호출자 중 하나이고, 「렌즈에게 에이전트원칙을 알리는 법」이 그 안에 있다. 구현자에게든 문서를 쓰는 서브에이전트에게든 에이전트원칙 `agent-principles.md`의 경로를 넣고, 한국어로 쓰는 서브에이전트에는 `domain-korean`의 경로를 함께 넣는다.
7. **주입 컨텍스트** — 큰 명세의 「결정 기록」 절과, 그 도메인에서 이미 겪은 함정을 넣어 같은 것을 다시 발견하지 않게 한다.
8. **멈추는 기준과 산출 계약(브랜치까지만 — 병합·배포·main push 금지)** — 「멈추는 기준」의 사유와 상태 값을 넣는다. 리포트는 프로젝트 밖 스크래치의 워크스트림별 고유 경로(`report-<워크스트림 id>.md`)에 쓰고 커밋하지 않는다. 리포트 경로는 현재 세션이 스크래치의 절대 경로로 정해 프롬프트에 넣는다. 리포트는 「메시지 형식」의 리포트 스키마대로 쓴다. 현재 세션은 이 SKILL.md 의 절대 경로도 넣는다. 그 경로는 현재 세션이 연 파일의 경로이며, 플러그인이 개발 도중 갱신되어도 두 세션이 같은 형식을 읽게 하기 위해서다. 서브 세션은 시작할 때와 하향 메시지를 받을 때 그 파일의 「메시지 형식」과 「멈추는 기준」을 읽는다.

## 메시지 형식

현재 세션과 서브 세션은 이 절의 형식으로만 메시지를 주고받는다. 서브 세션은 시작할 때와 하향 메시지를 받을 때 이 절과 「멈추는 기준」을 읽는다. 근거는 설계 문서 `docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`의 「2026-10-11 개정 — 메시지 형식」에 있다.

**표기.** 보내는 세션은 첫 줄에 머리줄을 적는다. 머리줄은 `<종류>` 또는 `BLOCKED <사유 코드>`다. 보내는 세션은 그 아래에 `필드: 값` 줄을 아래 표의 순서로 두고, 값이 없는 필드는 지우지 않고 `없음`으로 적는다.

**상향 메시지.** 서브 세션은 모든 상향 메시지에 `워크스트림`, `브랜치`(`ws/<개발>/<id> @ <커밋>`), `리포트`, `요약`을 공통 필드로 적는다. 판정 같은 상세는 리포트에만 적는다. 테스트 결과는 시험 병합이 직접 실행해 판정하므로 리포트에도 적지 않는다.

| 머리줄 | 추가 필드 | 보내는 때 |
|---|---|---|
| `AWAITING_APPROVAL` | `하부 명세`, `리뷰 기록`, `마커` | 하부 명세를 리뷰하고 커밋한 뒤 |
| `BLOCKED <사유 코드>` | `요청`, `이유`, `멈춘 작업` | 「멈추는 기준」의 사유에 해당할 때 |
| `DONE` | 없음 | 구현과 최종 리뷰를 마친 뒤 |
| `FAILED` | `원인`, `시도한 것`, `되돌릴 것` | 사유 코드 어디에도 들지 않는데 끝낼 수 없을 때 |
| `CANCELED` | `남긴 상태` | `CANCEL`을 받고 멈춘 뒤 |

서브 세션은 `FAILED`를 사유 코드 어디에도 들지 않을 때만 쓴다. 계약 불일치로 테스트가 실패하면 서브 세션은 `BLOCKED contract-change`를 쓴다. 권한이나 도구 설치처럼 사람이 조치해야 풀리는 환경 문제에는 `BLOCKED user-decision`을 쓴다. 같은 결함에 수정 시도가 세 번 실패하면 서브 세션은 고치기를 멈추고 `FAILED`를 돌려주며, `시도한 것`에 실패한 시도 내용을 적는다(superpowers `systematic-debugging`의 기준).

한 번 멈출 때 사유가 둘 이상이면, 서브 세션은 머리줄에 아래 처리 표에서 먼저 나오는 사유 코드를 적고 나머지는 `요청`에 줄마다 사유 코드와 함께 적는다. 현재 세션은 바로 처리할 수 있는 사유를 먼저 모두 답한다. 다른 워크스트림의 통합을 기다리는 `dependency-add`는 그 통합 뒤에 `BASE-UPDATED`로 따로 알린다.

**BLOCKED 처리.** 서브 세션은 공용 파일이나 큰 명세 본문을 바꿔야 할 때 `shared-file-change`를 고른다. 의존성 목록·잠금 파일이면 `dependency-add`를, 계약 코드의 테스트 대역이면 `test-double-add`를 고른다.

| 사유 코드 | 현재 세션이 할 일 | 보낼 메시지 |
|---|---|---|
| `user-decision` | 사용자에게 하나씩 묻고 답을 「결정 기록」에 커밋한다 | 요청한 쪽에 `ANSWER` |
| `contract-change` | 사용자에게 기각·미룸·채택을 고르게 한다. 채택하면 큰 명세와 계약 코드를 고친다 | 채택이면 그 계약 행의 제공자와 소비자 모두에 `CONTRACT-CHANGED`, 기각·미룸이면 요청한 쪽에 `ANSWER` |
| `shared-file-change` | 공용 파일이면 통합 브랜치에서 고친다. 큰 명세 본문이면 사용자에게 기각·미룸·채택을 고르게 한다 | 공용 파일이면 요청한 쪽에 `BASE-UPDATED`, 큰 명세 채택이면 바뀐 절이 다루는 워크스트림 모두에 `CONTRACT-CHANGED` |
| `dependency-add` | 소유 워크스트림이 통합 브랜치에 들어갔거나 `DONE`을 돌려줬으면 통합 브랜치에서 추가한다. 진행 중이면 소유 서브 세션이 멈출 때 추가를 요청한다 | 진행 중인 소유 쪽에 `DEPENDENCY-REQUEST`, 추가가 통합되면 요청한 쪽에 `BASE-UPDATED` |
| `test-double-add` | 계약 코드에 테스트 대역을 추가하고 계약 표의 단위·의미와 대조한다 | 요청한 쪽에 `BASE-UPDATED` |
| `review-red` | 🔴 를 사용자에게 알리고 답을 「결정 기록」에 적는다 | 요청한 쪽에 `ANSWER` |
| `review-gap` | 빠진 관점의 렌즈를 실행할지 사용자에게 묻는다 | 요청한 쪽에 `ANSWER` |
| `sdd-stop` | 비가역 작업, 보안 작업, 워크트리 밖 부작용이면 승인할지 사용자에게 묻는다. 전부 추측인 plan 이면 큰 명세나 「결정 기록」에 근거를 보강한다 | 요청한 쪽에 `ANSWER` |

`dependency-add`에서 소유 워크스트림이 `DONE`을 돌려줬으면 현재 세션은 그 병합을 기다리지 않고 통합 브랜치에서 바로 추가한다. 소유 워크스트림이 요청한 쪽에 검증 의존하면 두 워크스트림이 서로를 기다리기 때문이다. `sdd-stop`에서 사용자가 작업을 거절해도 현재 세션은 `ANSWER`로 거절과 대안을 보내고, 워크스트림을 접을지는 사용자에게 따로 묻는다.

공유 가정이 자기 구현과 다르면 서브 세션은 `BLOCKED contract-change`를 돌려준다. 현재 세션은 「결정 기록」의 그 가정을 대상으로 기각·미룸·채택을 고르게 하고, 채택하면 그 가정을 쓰는 서브 세션 모두에 `ASSUMPTION-ADDED`를 보낸다.

`FAILED`를 받으면 현재 세션은 원인과 되돌릴 것을 사용자에게 알리고, 같은 서브 세션에 `REVISE`, 새 서브 세션, `CANCEL` 중 하나를 고르게 한다. 새 서브 세션을 고르면 현재 세션은 디스패치 프롬프트에 그 리포트의 `원인`과 `시도한 것`을 넣는다. `CANCELED`를 받으면 현재 세션은 CLI 의 서브에이전트 화면에서 그 워크트리의 워커가 끝났는지 확인한다. 그 뒤 현재 세션은 브랜치와 워크트리를 남길지 지울지 사용자에게 묻는다.

**하향 메시지.** 현재 세션은 모든 하향 메시지에 `워크스트림`과 `통합 브랜치`(`dev/<개발> @ <커밋>`)를 공통 필드로 적는다. 아래 표의 '다음 응답'은 일을 마쳤을 때의 응답이다. 서브 세션은 어느 하향 메시지 뒤에도 사유에 해당하면 `BLOCKED`를, 끝낼 수 없으면 `FAILED`를 돌려준다.

| 머리줄 | 추가 필드 | 서브 세션이 할 일 | 다음 응답 |
|---|---|---|---|
| `APPROVE` | `승인한 하부 명세`, `조건` | writing-plans, `review-specs`, SDD 로 진행한다 | `DONE` |
| `REVISE` | `대상`, `고칠 항목` | 고칠 항목을 처리하고 커밋한다. 대상이 하부 명세면 다시 리뷰한다 | 대상이 하부 명세면 `AWAITING_APPROVAL`, 구현이면 `DONE` |
| `ANSWER` | `질문`, `답`, `결정 기록` | 답을 반영해 멈춘 작업을 이어 간다 | 하던 단계의 응답 |
| `BASE-UPDATED` | `바뀐 것`, `할 일` | 자기 워크트리에서 `git merge dev/<개발>`을 실행하고 테스트를 다시 실행한 뒤 이어 간다 | 하던 단계의 응답 |
| `CONTRACT-CHANGED` | `바뀐 항목`, `커밋` | 통합 브랜치를 병합하고 바뀐 계약 행이나 큰 명세 절에 맞춘다. 하부 명세가 바뀌면 다시 리뷰한다 | 하부 명세가 바뀌었으면 `AWAITING_APPROVAL`, 아니면 하던 단계의 응답 |
| `ASSUMPTION-ADDED` | `가정`, `결정 기록` | 통합 브랜치를 병합한다. 자기 구현이 그 가정과 다르면 고치지 않고 `BLOCKED contract-change`로 알린다 | 하던 단계의 응답 |
| `DEPENDENCY-REQUEST` | `패키지`, `요청한 워크스트림` | 의존성 목록과 잠금 파일에 패키지를 추가하고 커밋한 뒤 하던 단계로 돌아간다 | 하던 단계의 응답 |
| `INTEGRATION-FAILED` | `확인 위치`, `실패 검사`, `출력` | 원인을 고치고 커밋한다 | `DONE` |
| `CANCEL` | `이유` | 미커밋 변경을 커밋하지 않고 워크트리에 남긴 채 멈춘다 | `CANCELED` |

`INTEGRATION-FAILED`의 `확인 위치`는 시험 병합의 `try/<id>` 커밋이거나, 이미 병합된 워크스트림의 통합 확인을 다시 실행한 `dev/<개발>` 커밋이다.

현재 세션은 하부 명세 수정 요청 말고도 아래 상황에서 `REVISE`를 쓴다.

- 허용 경로 밖 변경: 「수정 범위 대조」가 허용 경로 밖 파일을 낸 상황
- 리뷰 마커 없음: 추가된 하부 명세나 plan 의 마지막 줄에 리뷰 마커가 없는 상황
- 교집합 겹침: 「교집합 검사」가 두 워크스트림의 같은 파일을 낸 상황
- 판정 번복: 하부 명세 승인이나 「판정 기록 확인」에서 사용자가 서브 세션의 판정을 뒤집은 상황
- 실패 뒤 재시도: `FAILED` 뒤 같은 서브 세션에 다시 시키기로 한 상황
- 형식 이탈: 상향 메시지가 판단에 필요한 필드를 빠뜨린 상황

교집합 겹침에서 현재 세션은 사용자에게 알린 뒤, 그 파일을 고치지 않기로 정한 쪽에 `REVISE`를 보낸다. 실패 뒤 재시도에서 고칠 코드가 없으면 현재 세션은 `고칠 항목`에 다시 실행할 단계를 적고, 형식 이탈에서는 `대상`에 '응답'을 적는다. 리뷰 마커가 `escalated`인데 「결정 기록」에 답이 없으면 현재 세션은 `REVISE`를 보내지 않고 `review-red` 처리대로 🔴 를 사용자에게 알려 답을 적는다. 시험 병합의 테스트나 통합 확인이 실패하면 현재 세션은 `INTEGRATION-FAILED`를 쓴다.

**보내는 순서.** 현재 세션은 메시지를 서브 세션이 멈춘 뒤에만 보낸다. 같은 서브 세션에 보낼 메시지가 여럿이면 한 번에 묶어 보내고, 통합 브랜치를 바꾸는 메시지(`BASE-UPDATED`, `CONTRACT-CHANGED`, `ASSUMPTION-ADDED`)를 앞에 둔다. 받을 서브 세션이 실행 중이어서 미룬 메시지는 「시험 병합」 전의 확인으로 되찾는다.

**리포트 스키마.** 서브 세션은 리포트 파일에 아래 절 제목을 이 순서로 두고, 내용이 없는 절도 `없음`으로 남긴다.

| 절 제목 | 형식 | 현재 세션이 읽는 곳 |
|---|---|---|
| `확정한 결정` | 줄마다 '결정 — 이유' | 통합 때의 「결정 기록」 갱신 |
| `확정한 계약 의미` | 줄마다 '계약 행 — 칸(의미 또는 형식의 열거값) — 값' | 통합 때의 계약 표 '확정 예정' 칸 |
| `명세 이탈` | 줄마다 '하부 명세의 위치 — 실제 구현 — 이유' | 「판정 기록 확인」 |
| `스스로 판정한 모호함` | 줄마다 '질문 — 판정 — 이유 — 범위 밖 항목에 가까운지(예·아니오)' | 하부 명세 승인과 「판정 기록 확인」 |
| `기능적 반영` | 리뷰 반영 중 동작이 바뀐 항목 | 「흐름」 마무리 |
| `제안` | 범위 밖 아이디어 | 「흐름」 마무리 |

**형식 이탈.** 머리줄이 이 절의 종류와 사유 코드 밖이거나 정해진 필드가 빠진 응답은 형식 이탈이다. 현재 세션은 판단할 수 있으면 해석해 진행하고, 판단에 필요한 필드가 빠졌으면 `REVISE`(대상: 응답)를 보낸다. 현재 세션은 두 상황 모두 「측정」의 `Format-Deviations:`에 센다.

## 이어 쓰기와 재개

하던 일이면 어느 층이든 같은 에이전트를 SendMessage로 재개하고, 새 일이면 같은 역할·같은 파일이어도 새 에이전트로 시작한다. 하던 일의 단위는 서브 세션이 워크스트림 하나, 구현 워커가 태스크 하나, 렌즈가 문서 하나의 리뷰 한 차수다. 사용자는 하던 일을 이어 가면 맥락이 증분으로 쌓인다고 판단했다. 같은 에이전트 재개와 새 에이전트에 파일을 넘기는 방식을 비교한 연구는 찾지 못했다.

현재 세션은 「메시지 형식」의 하향 메시지를 모두 그 워크스트림의 서브 세션에 이어 쓰기로 보낸다. 그래서 현재 세션은 워크스트림 코드를 직접 고치지 않는다. 메시지는 서브 세션이 끝나거나 멈춘 뒤에 보낸다.

세션이 끊겨 식별자가 사라졌거나 재개가 실패하면, 현재 세션은 워크스트림 브랜치·하부 명세·plan과 워크트리에 남은 SDD ledger(진행 기록 파일)를 넣어 새 서브 세션을 시작한다. 같은 워크스트림의 통합 실패가 되풀이될 때 새 서브 세션으로 바꾸는 횟수 기준은 아직 두지 않는다.

## 멈추는 기준

서브 세션은 아래 사유에서만 멈추고 「메시지 형식」의 상향 메시지를 돌려준다. 예외는 사유 코드 어디에도 들지 않는데 끝낼 수 없을 때의 `FAILED`다. 그 밖의 모호함은 스스로 판정해 SDD ledger와 리포트에 적는다.

- 하부 명세 리뷰를 마쳐 승인을 기다릴 때(`AWAITING_APPROVAL`)
- 하부 명세나 plan 리뷰에서 🔴가 나왔을 때(`BLOCKED review-red`)
- 리스크상 필요한 리뷰 관점을 아무 렌즈도 보지 않았을 때(`BLOCKED review-gap`)
- 사람만 정할 수 있는 범위 밖 결정이 필요할 때(`BLOCKED user-decision`)
- 계약을 바꿔야 할 때(`BLOCKED contract-change`)
- 공용 파일이나 큰 명세 본문을 바꿔야 할 때(`BLOCKED shared-file-change`)
- 의존성 목록·잠금 파일에 패키지를 추가해야 할 때(`BLOCKED dependency-add`)
- 계약 코드에 없는 테스트 대역이 필요할 때(`BLOCKED test-double-add`)
- SDD의 정지 사유(비가역 작업, 보안 작업, 워크트리 밖 부작용, 전부 추측인 plan)에 해당할 때(`BLOCKED sdd-stop`)

범위 밖 결정은 큰 명세와 결정 기록에 답이 없고 아래 항목 중 하나에 드는 결정이다.

- 권한: 누가 무엇을 할 수 있는지(역할, 승인, 대리)를 정하는 결정
- 기능의 추가나 제외: 큰 명세의 「맡는 일」에 없는 기능을 만들거나 적힌 기능을 빼는 결정
- 결과의 뜻: 사용자가 보는 상태·판정·알림의 뜻을 정하는 결정
- 돈과 되돌리기 어려운 자료: 금액·주문, 자료의 삭제·보존 기간·덮어쓰기를 정하는 결정
- 보안: 비밀, 인증, 외부 전송을 정하는 결정

화면 배치·문구·정렬·표시 형식과 내부 이름·자료 구조·알고리즘은 범위 안이다. 큰 명세에 없는 기능을 만들지 않는 결정도 범위 안이다.

서브 세션은 위 항목에 분명히 드는 결정에서만 멈춘다. 드는지 확실하지 않으면 스스로 판정하고 리포트의 `스스로 판정한 모호함`에 판정과 이유, 범위 밖 항목에 가까운지를 적는다. 현재 세션은 하부 명세 승인과 「판정 기록 확인」에서 그 절을 읽는다.

구현과 리뷰를 마치면 `DONE`을 돌려준다. 명세·plan 리뷰에는 `accept`나 `regenerate` 같은 결정 값이 없으므로 서브 세션은 그 값을 지어내지 않는다. 서브 세션은 리뷰 반영 뒤 다시 리뷰할지 묻지 못하므로 생략하고, 기능적 변화가 있었던 반영을 리포트에 적는다.

현재 세션은 사유 코드마다 「메시지 형식」의 BLOCKED 처리 표대로 처리한다.

## 가드레일

현재 세션은 서브 세션이 `DONE`을 돌려주면 아래 검사를 차례로 한다. 아래 명령의 `<개발>`은 개발 이름이고 `<id>`는 워크스트림 id다.

**수정 범위 대조.** 현재 세션은 `git diff --name-only --no-renames dev/<개발>...ws/<개발>/<id> -- . ':(exclude)<허용 경로 1>' … ':(exclude)docs/superpowers/specs/*-<개발>-<id>-design.md' ':(exclude)docs/superpowers/plans/*-<개발>-<id>.md' ':(exclude)docs/superpowers/reviews/*-<개발>-<id>-*'`를 실행한다. 큰 명세의 허용 경로와 자기 문서 경로 셋을 모두 exclude로 넣으므로 출력이 비어 있어야 통과한다. 출력에 파일이 나오면 병합하지 않고 그 서브 세션에 `REVISE`를 보낸다. 점 세 개는 두 브랜치의 공통 조상부터 비교하므로, 통합 브랜치에서 받은 변경은 출력에 나오지 않는다. `--no-renames`를 붙이면 허용 경로 밖 파일을 안으로 옮긴 변경이 원래 경로의 삭제로 드러난다.

**교집합 검사.** 현재 세션은 동시에 진행한 워크스트림 브랜치를 둘씩 짝지어 exclude 없는 `git diff --name-only --no-renames dev/<개발>...ws/<개발>/<id>` 출력의 교집합을 구한다. 한 쌍이라도 비어 있지 않으면 현재 세션은 병합 전에 멈추고 사용자에게 알린 뒤, 그 파일을 고치지 않기로 정한 쪽에 `REVISE`를 보낸다. 허용 경로 패턴끼리 겹치는지는 사람이 놓치기 쉬우므로 현재 세션이 이 검사를 범위 대조와 함께 한다.

**리뷰 마커 확인.** 서브 세션이 쓴 문서에는 현재 세션의 Stop 게이트(미리뷰 명세가 남은 채 턴을 끝내지 못하게 하는 훅)가 적용되지 않는다. 현재 세션은 `git diff --name-only --diff-filter=A dev/<개발>...ws/<개발>/<id> -- docs/superpowers/specs docs/superpowers/plans`로 추가된 하부 명세와 plan을 구하고, 각 파일 마지막 줄을 `git show ws/<개발>/<id>:<경로> | tail -n 1`로 읽어 `spec-review` 마커가 있는지 확인한다. 현재 세션의 체크아웃에는 워크스트림 브랜치의 파일이 없으므로 작업 트리에서 읽지 않는다. 마커가 없으면 병합하지 않고 그 서브 세션에 `REVISE`를 보낸다. 마커가 `escalated`이면 그 🔴의 사용자 답이 큰 명세 「결정 기록」에 있는지 확인하고, 없으면 병합하지 않고 `review-red` 처리대로 사용자에게 묻는다.

**판정 기록 확인.** 현재 세션은 병합하기 전에 리포트의 `스스로 판정한 모호함`과 `명세 이탈`을 읽는다. 범위 밖 항목에 가깝다고 표시된 줄과 `명세 이탈`의 줄을 현재 세션은 사용자에게 묻고, 사용자가 판정을 뒤집으면 `REVISE`를 보낸다. plan 과 구현 단계의 판정은 하부 명세 승인 때 아직 없으므로 여기서 읽는다.

**검증 의존 대기.** 검증 의존이 있는 워크스트림이 `DONE`을 돌려줘도, 현재 세션은 그 워크스트림이 검증 의존하는 워크스트림이 모두 통합 브랜치에 들어올 때까지 시험 병합을 미룬다. 그래야 시험 병합의 통합 확인이 실제 구현으로 실행되고, 통합 브랜치에 들어간 워크스트림이 모두 통합 확인을 통과한 상태가 된다. 「진행 위치」는 대기 중인 워크스트림을 진행 중으로 보이므로, 현재 세션은 큰 명세의 검증 의존과 통합 브랜치의 `Workstream:` 줄을 대조해 대기 여부를 판정한다.

통합 확인이 실패하고 그 원인이 이미 병합된 워크스트림 Y에 있으면, 현재 세션은 Y의 서브 세션에 `INTEGRATION-FAILED`를 보낸다. 대기 중인 워크스트림의 서브 세션이 대상의 통합 결과를 받아야 하면 현재 세션은 그 서브 세션에 `BASE-UPDATED`를 보낸다. 현재 세션은 Y의 수정을 같은 `Workstream:` 트레일러를 넣은 시험 병합으로 넣는다. 이어서 현재 세션은 Y에 검증 의존하는 워크스트림 전부의 통합 확인을 통합 브랜치에서 다시 실행하며, 이미 병합된 워크스트림도 그 대상에 든다.

**시험 병합.** 현재 세션은 시험 병합 전에 `git log --oneline ws/<개발>/<id>..dev/<개발> -- <계약 코드 경로> <큰 명세 경로>`를 실행한다. 출력이 비어 있지 않으면 그 워크스트림은 바뀐 계약이나 큰 명세를 받지 않았으므로, 현재 세션은 병합하지 않고 `BASE-UPDATED`를 보낸다. 출력의 커밋이 그 워크스트림이 제공자나 소비자인 계약 행을 바꿨으면 `CONTRACT-CHANGED`를, 그 워크스트림이 쓰는 공유 가정을 추가했으면 `ASSUMPTION-ADDED`를 대신 보낸다. 현재 세션은 `git switch -c try/<id> dev/<개발>`로 임시 브랜치를 만들고 `git merge --no-ff ws/<개발>/<id>`로 병합한 뒤, 계약 테스트와 큰 명세의 통합 확인을 실행한다. 계약 테스트의 생략 사유에 병합 대상의 워크스트림 id 가 있으면 현재 세션은 실패로 본다. 그 워크스트림의 모듈 경로가 계약 코드와 다르다는 뜻이기 때문이다. 마지막 워크스트림의 시험 병합에서는 생략이 하나도 없어야 한다. 병합 커밋 메시지에는 「측정」의 트레일러와 `Workstream: ws/<개발>/<id>` 트레일러를 넣는다. 통과하면 `git switch dev/<개발>`, `git merge --ff-only try/<id>`, `git branch -D try/<id>`를 실행한다. 실패하면 `git switch dev/<개발>`과 `git branch -D try/<id>`로 임시 브랜치를 지우고, 원인이 계약이면 큰 명세로, 워크스트림 내부면 그 서브 세션에 `INTEGRATION-FAILED`로 보낸다.

**되돌림을 쓰지 않는 이유.** 통합 브랜치는 통과한 병합만 받으므로 되돌림 커밋이 생기지 않는다. 되돌린 병합은 git이 공통 이력으로 보아 다시 병합할 때 처음 변경이 빠지므로(git 문서 `howto/revert-a-faulty-merge`), 현재 세션은 `git revert`로 통합 실패를 처리하지 않는다.

**진행 위치.** 현재 세션은 상태 문서 없이 git에서 진행 위치를 도출한다. `git log dev/<개발> --format=%B`에 `Workstream: ws/<개발>/<id>` 줄이 있는 워크스트림은 끝났다. `git branch --merged`는 커밋이 아직 없는 워크스트림 브랜치도 병합된 것으로 내므로 쓰지 않는다. plan이 있는지는 `git ls-tree -r --name-only ws/<개발>/<id> -- docs/superpowers/plans`로 본다. 끝나지 않은 워크스트림 브랜치는 plan이 있으면 승인 뒤 진행 중이고, 하부 명세만 있으면 승인 대기이며, 둘 다 없으면 하부 명세 작성 중이다. 큰 명세 목록에 있는데 브랜치가 없는 워크스트림은 시작 전이다.

**크래시와 멈춤.** 완료 통지가 오지 않는 서브 세션이 있으면, 현재 세션은 CLI의 서브에이전트 화면에서 그 세션으로 들어가 실행 상태를 확인한다. 종료되었으면 「이어 쓰기와 재개」대로 재개하거나 새 서브 세션을 시작한다. 타임아웃과 헬스체크 도구가 없어 현재 세션의 주의에 의존한다.

**비용.** 서브 세션마다 맥락 재확립과 워커 팬아웃이 든다. 2026-07 스파이크에서 사소한 워크스트림 하나당 약 40k 토큰이 들었다. 이 값은 워커를 포함하지만, 하부 명세와 승인 단계가 없던 흐름에서 측정한 값이다.

## 측정

현재 세션은 워크스트림마다 실패한 시험 병합 수와 그 원인, `BLOCKED` 응답의 사유 코드 수, 「메시지 형식」의 형식 이탈 수, 완료 통지의 `subagent_tokens`를 센다. 이 값은 시험 병합의 `git merge --no-ff -m`에 `Integration-Failures:`, `Questions:`(사유 코드 수), `Format-Deviations:`, `Tokens:` 트레일러로 넣는다. `Tokens:` 값은 그 서브 세션의 완료 통지들(재개할 때마다 하나씩 온다)의 `subagent_tokens` 합이다. fast-forward로 통합 브랜치에 들어가므로 이 커밋이 통합 브랜치에 남는다. 개발이 끝나면 현재 세션이 `git log dev/<개발>`에서 이 값을 모아 사용자에게 보고한다.

`FAILED`나 `CANCELED`로 끝나 병합되지 않은 워크스트림은 트레일러가 남지 않으므로, 현재 세션은 마무리 보고에서 그 워크스트림을 따로 적는다.

현재 세션은 큰 명세 리뷰 기록에서 계약 표의 칸(제공자 → 소비자, 형식, 단위, 의미)과 「계약 코드」의 연결 규칙이 다루는 공백을 지적한 수도 세어 함께 보고한다. 비교 기준은 설계 문서 「2026-10-11 개정 — 계약 표」의 30건이다.

## 관측성

수동 `Agent` 중첩은 `/workflows` 집계 대시보드에 뜨지 않는다. 대신 CLI가 서브에이전트를 표시하고, 사용자는 그 항목을 더블클릭해 각 서브 세션의 실행 화면으로 들어간다. 집계 대시보드와 메트릭은 볼 수 없고, 어떤 워크트리가 어느 서브 세션에 배정됐는지도 화면에 나오지 않는다.

## 재구현 금지

아이디어에서 명세까지는 `brainstorming`, plan은 `writing-plans`, 실행 루프는 `subagent-driven-development`, 병렬 디스패치 메커니즘은 `dispatching-parallel-agents`, 워크트리 격리는 `using-git-worktrees`, 리뷰 렌즈는 `lens-*`가 소유한다.

## 한계

3층은 조율 층을 얹으므로 맡길 워크스트림이나 작업이 둘 이상일 때만 값을 한다. 무엇이 검증됐고 무엇이 아직 아닌지는 설계 문서(`docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`)의 「이어받는 판단과 검증」, 「검증하지 않은 가정」, 「2026-10-10 개정」, 「2026-10-11 개정 — 묶는 단위」에 있다.

**비목표** — `Workflow` 결정론 버전과 집계 UI 대시보드와 오케스트레이션 상태 문서는 만들지 않는다. `Workflow`는 중첩을 1단계로 제한해 판단으로 SDD를 실행하는 서브 세션을 수용하지 못한다. 진행 위치는 git에서 도출한다. 4층 이상 더 깊은 중첩도 다루지 않는다.
