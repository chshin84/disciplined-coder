# nested-orchestration — 워크스트림으로 나눠 맡기는 3층 오케스트레이션

이 파일은 현재 세션의 절차다. 길어서 한 번에 안 읽히면 `offset`을 지정해 끝까지 이어 읽어라. 같은 폴더의 `references/sub-session-protocol.md`(이하 프로토콜 파일)에 서브 세션의 메시지 형식·멈추는 기준·리포트 규칙이 있다. 메시지를 쓰거나 읽을 때마다 그 파일을 읽어라. 설계 근거와 측정 기록은 근거 문서에 있다. 근거 문서 경로는 플러그인 루트 기준 `docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`이며, 다른 프로젝트에서는 사용자 저장소에 없고 플러그인 설치 폴더에 있다. 이 파일은 근거 문서를 절 이름으로 가리킨다. 명세 단계와 다시 나누기의 결정과 근거는 근거 문서 「2026-10-12 개정 — 명세 단계와 다시 나누기」에 있다.

## 용어

현재 세션은 사용자와 대화하며 큰 명세·계약·통합을 맡는 세션이다. 서브 세션은 사용자와 대화하지 못하는 서브에이전트로, 워크스트림(서브 세션 하나가 맡는 작업 단위) 하나를 맡는다. 큰 명세는 개발 전체를 워크스트림으로 묶고 워크스트림 사이 계약과 결정 기록을 적는 문서다. 하부 명세는 워크스트림 하나의 내부 설계를 적는 문서다. 그 밖의 용어는 처음 나오는 절에서 정의한다. 메시지에 쓰는 용어는 프로토콜 파일 「용어」에 있다.

## 언제 쓰는가

사용자가 나눠 맡기라고 요청하거나 아래 두 시점에 「맡기는 기준」을 충족하면 이 스킬을 써라. 첫째는 superpowers `brainstorming` 도중 요청을 하위 프로젝트 여럿으로 분해하기로 정한 시점이다. 둘째는 설계 문서(`docs/superpowers/specs/`의 spec)가 승인된 뒤 `writing-plans`를 실행하기 전이다. 하위 프로젝트로 나누지 않은 큰 개발도 이 시점에 판단하고, 설계 문서에서 하위 프로젝트 목록을 직접 뽑아라. 맡기기로 정했으면 하위 프로젝트의 하부 명세·plan·구현을 직접 진행하지 마라. 단, 「다시 나누기」 결과 「맡기는 기준」을 벗어나면 맡기지 않기로 한 것이므로 직접 진행하라.

### 맡기는 기준

계약 코드를 고정한 뒤 동시에 시작할 수 있는 워크스트림(「묶는 단위」의 시작 워크스트림)이 둘 이상이고 각 워크스트림이 plan을 따로 둘 규모(예상 태스크 다섯 이상)이면 서브 세션에 맡겨라. 서로 독립된 큰 작업이 둘 이상이어도 맡겨라. 다섯은 사용자와 합의한 기준값이다. 하위 프로젝트로 분해했는지와 무관하게 이 기준으로 판단하라.

나눠 맡길 단위에 따라 아래 스킬을 골라 써라.

- plan·리뷰 루프가 없는 단일 태스크면 `dispatching-parallel-agents`를 써라.
- 「맡기는 기준」을 충족하면 이 스킬을 써라.
- 사용자가 나눠 맡기라고 요구하면 단일 태스크가 아닌 한 규모와 상관없이 이 스킬을 써라. 일이 작으면 조율 비용이 이득보다 클 수 있다고 알려라.
- 어느 항목에도 들지 않으면 superpowers 흐름을 직접 진행하라.

사용자와는 분할과 입출력 계약만 정하라. 승인은 두 번 받는다. 첫째는 임시 분할로 명세 단계에 들어갈 때, 둘째는 「다시 나누기」 분할로 구현 단계에 들어갈 때다. 승인받을 때는 워크스트림마다 맡는 일(입력·출력)과 예상 태스크 수를 한 표로 보여라. 두 번째 승인에는 계약 표도 함께 보여라. 공유 항목 표와 설계 의존 표는 큰 명세에만 적고 사용자에게 따로 보이지 마라. 서로 독립된 큰 작업은 작업별 맡는 일과 예상 태스크 수를 보여라. 내부 설계·리뷰 처분·실패한 서브 세션 재시도 같은 나머지 결정은 권장안으로 진행한 뒤 보고에 적어라.

승인받은 하위 프로젝트 목록을 「묶는 단위」 입력으로 써라. 사용자가 목록을 바꾸면 표와 판정을 새로 만들어 다시 승인받아라.

## 큰 개발 분할

### 묶는 단위

승인받은 하위 프로젝트 목록으로 공유 항목 표를 먼저 만들고, 이어서 설계 의존 표를 만들어라. 공유 항목 표에는 둘 이상의 하위 프로젝트 사이를 오가는 자료·상태·정의만 행으로 넣어라. 명명 관례 같은 관례나 용어 풀이는 행으로 넣지 말고 「결정 기록」에 적어라.

공유 항목 표의 칸은 항목, 소유 하위 프로젝트, 사용 하위 프로젝트, 판정, 고정한 의미다. 소유 하위 프로젝트는 그 항목의 의미를 바꾸는 결정을 내리는 쪽이고, 사용 하위 프로젝트는 그 항목을 받는 쪽이다. 소유 하위 프로젝트는 사용 칸에 넣지 마라.

모든 행에 "어느 하위 프로젝트의 내부 설계도 정하지 않고 이 항목의 이름·형식·단위·의미(시간 의미와 결측 의미 포함)를 지금 고정할 수 있는가"를 물어라. 고정할 수 있으면 판정을 떼어냄으로 적고, 고정한 의미를 그 행에 한 줄로 적어라. 고정할 수 없으면 사용 하위 프로젝트마다 "그 하위 프로젝트의 설계가 이 항목의 의미를 함께 정해야 하는가"를 물어라. 소유가 둘 이상이면 판정은 합침이다. 소유가 하나일 때 의미를 함께 정해야 하는 사용 쪽이 있으면 합침, 없으면 순서로 판정하라.

소유가 없는데 고정할 수 없으면 그 항목을 바꾸는 하위 프로젝트를 모두 소유 칸에 적은 뒤 판정하라. 합침 행에서는 소유 쪽 전부와 의미를 함께 정해야 하는 사용 쪽을 한 워크스트림으로 합쳐라. 합침·순서 행에서 의미를 받기만 하는 사용 쪽은 합치지 말고, 소유 쪽 접근 절차를 계약으로 떼어내라. 그 계약의 의미 칸은 소유 워크스트림을 통합 브랜치에 넣을 때 확정하라.

합침 행끼리 하위 프로젝트가 겹치면 겹친 행의 하위 프로젝트를 전부 한 워크스트림으로 묶어라. 「다시 나누기」에서 떼어냄 행과 합침·순서 행에서 떼어낸 접근 절차를 「계약 표」 행으로 옮기고, 하위 프로젝트 이름을 워크스트림 id로 바꿔라. 소유 쪽은 제공자, 사용 쪽은 소비자가 되며, 소유가 없는 행의 제공자는 현재 세션이다. 이 연결 규칙은 이 절이 소유한다.

설계 의존 표의 행과 열에는 합친 묶음과 남은 하위 프로젝트를 놓아라. X를 설계할 때 Y의 실제 결과(구현 결과나 조사 결과)를 봐야 하면 X→Y에 1, 아니면 0을 적어라. 공유 항목 표에서 이름·형식·단위·의미를 고정한 관계는 0이다. 합침·순서 행에서 합치지 않은 사용 쪽은 소유 쪽에 1이 되므로 소유 쪽 뒤에 설계한다.

설계 의존 순환에 함께 든 묶음과 하위 프로젝트만 한 워크스트림으로 합치고, 나머지는 각각 워크스트림 하나로 두어라. 순환을 없앤 뒤 남은 의존을 큰 명세 의존 순서 항목의 시작 의존에 적어라. 시작 의존상 선행이 없는 워크스트림이 시작 워크스트림이며, 이들은 동시에 시작할 수 있다. 시작 워크스트림이 하나뿐이면 「맡기는 기준」에 들지 않는다.

두 워크스트림이 같은 파일을 고쳐야 하면 네가 그 파일을 맡아 「공용 파일」대로 다뤄라. 코드가 없는 단계에서는 경로 겹침을 셀 수 없으므로 합치는 기준으로 삼지 마라.

「묶는 단위」는 두 번 실행하라. 첫째는 하위 프로젝트 목록으로 임시 워크스트림을 정할 때, 둘째는 완전체 명세로 워크스트림을 새로 나눌 때(「다시 나누기」)다. 계약 표와 계약 코드는 두 번째 결과로만 만들어라.

### 관례 골격

임시 분할을 적을 때 명명·오류 처리·추상화 수준·디렉터리 구조를 큰 명세 「결정 기록」에 채워라. 명세 서브 세션은 이 골격을 주입 컨텍스트로 받는다. 따로 쓴 설계를 합칠 때 이런 암묵적 결정이 엇갈린다는 근거는 근거 문서 「2026-10-12 개정 — 명세 단계와 다시 나누기」의 「관례 골격」에 있다.

### 명세 단계

임시 워크스트림마다 명세 서브 세션을 실행하라. 명세 서브 세션은 자기 하부 명세를 쓰고 리뷰해 커밋한 뒤, 리포트 `작성 기록` 절에 고른 대안과 기각 이유·읽은 코드와 자료·열린 질문을 적고 `DONE`으로 끝난다. 임시 분할에도 의존 순서 표를 두고 「흐름」의 「차수」대로 진행하라. 명세 단계의 선행 조건은 선행 명세 서브 세션이 아래 검사를 통과한 `DONE`을 냈을 때 충족된다. 사용 쪽 명세 서브 세션은 그 뒤에 실행하며 선행 하부 명세의 브랜치와 경로를 주입 컨텍스트로 넘겨라.

명세 서브 세션이 `DONE`을 돌려주면 「리뷰 마커 확인」과 「판정 기록 확인」을 실행하고, `git diff --name-only dev/<개발 이름>...spec/<개발 이름>/<임시 id>` 출력에 자기 문서 경로 밖 파일이 없는지 확인하라. 리포트 `스스로 판정한 모호함`에서 마지막 칸이 '예'인 줄 중 지시 목적이나 입출력을 바꾸는 줄만 사용자에게 묻고 답을 「결정 기록」에 커밋하라. 답이 이미 「결정 기록」에 있으면 다시 묻지 말고, 나머지 '예' 줄은 네가 판정해 「결정 기록」에 적어라. 검사 결과나 사용자 답 때문에 하부 명세를 고쳐야 하면 끝난 명세 서브 세션에 `REVISE` 대신 `RESTART`(`원인`에 고칠 항목 기재)를 보내라. `ws/` 브랜치용인 시험 병합과 수정 범위 대조는 명세 서브 세션에 적용하지 마라.

모든 임시 워크스트림이 위 검사를 통과한 `DONE`을 냈거나 범위에서 빠진 뒤에 완전체 명세를 써라. 명세 서브 세션이 `FAILED`로 끝나면 `RESTART`로 한 번 재시도하라. 다시 실패하거나 `CANCELED`로 끝나면 출력이 바뀌는 결정이므로 그 하위 프로젝트를 범위에서 뺄지 사용자에게 물어라. 빼기로 하면 「결정 기록」에 '뺀 하위 프로젝트: <임시 id> — 이유' 한 줄을 커밋하라. 빠진 하부 명세는 대신 쓰지 마라.

### 완전체 명세

각 `spec/<개발 이름>/<임시 id>` 브랜치의 하부 명세와 리뷰 기록을 `git -C <통합용 워크트리> checkout spec/<개발 이름>/<임시 id> -- <경로>`로 통합용 워크트리에 옮겨라. 큰 명세 본문에는 각 하부 명세의 경로만 가리키고 공유 결정·경계·「겹침 판정」 절을 새로 두어라. 하부 명세 원문을 큰 명세 한 파일에 붙이지 마라. 붙이면 서브 세션의 읽기 상한(25k 토큰)을 넘어 잘린 채 읽힌다.

관례 골격과 「결정 기록」을 기준표로 삼아 하부 명세마다 대조하고, 다른 곳을 기준표에 맞춰 고쳐라. 완전체 명세 본문과 네가 고친 하부 명세 파일을 `lens-review`로 리뷰한 뒤 「다시 나누기」로 넘어가라. 사용자 승인은 다시 나눈 분할에서 받는다.

### 겹침 판정

하부 명세 사이의 겹침마다 '같은 동작인가'를 따져라. 같으면 공유 결정 절로 합치고, 다르면 이름을 구분해 각 하부 명세에 남겨라. 경계를 넘는 자료를 두 하부 명세가 다르게 정의했으면 소유 하위 프로젝트 쪽 정의를 경계 절에 적고, 다른 쪽 하부 명세에서는 그 정의를 지운 뒤 경계 절을 가리켜라. 판정마다 「겹침 판정」 표(대상, 하부 명세, 판정, 이유)에 한 행을 남기고, 겹침이 없으면 '없음' 한 행만 남겨라.

### 다시 나누기

완전체 명세 리뷰가 끝나면 그 하위 프로젝트 목록으로 「묶는 단위」를 다시 실행하라. 공유 결정과 경계는 소유 워크스트림 하나가 구현하고, 소유가 없는 항목은 네가 계약 코드에 두어라. 순서 행의 사용 쪽을 뺀 나머지 워크스트림은 계약 코드와 테스트 대역으로 맞춰 가며 동시에 개발한다. 공통 결정만 구현하는 별도 워크스트림은 만들지 마라. 공유 결정과 경계는 여러 워크스트림이 기다리므로, 소유 워크스트림이 선행 없이 1차에 들도록 나눠라. 1차에 넣을 수 없으면 그 항목을 계약 코드에 두고, 그것도 안 되면 사용자에게 알려라.

큰 명세에 새 분할·계약 표·절 배정 표(새 워크스트림 id, 하부 명세 파일과 절, 작성 기록이 있는 리포트)를 적어라. 이 분할을 리뷰한 뒤 「언제 쓰는가」 형식으로 사용자 승인을 받아라. 다시 나눈 결과 시작 워크스트림이 하나뿐이면 사용자에게 알리고 「결정 기록」에 '직접 진행' 한 줄을 `결정 기록:` 커밋으로 남겨라. 그 뒤 통합용 워크트리에서 완전체 명세로 `writing-plans`부터 직접 진행하고, 끝나면 「흐름」의 마무리·정리 단계를 거쳐라.

### 큰 명세

큰 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-design.md`에 쓰고 단계마다 `lens-review`로 리뷰하라. 사용자 승인은 임시 분할과 다시 나눈 분할에서만 받는다. 처음에는 임시 워크스트림과 맡는 일·공통 제약·관례 골격을 채운 「결정 기록」만 적어라. 완전체 명세가 되면 하부 명세 포인터와 공유 결정·경계·「겹침 판정」 절을 추가하라. 다시 나눈 뒤에는 아래 항목과 절 배정 표를 채워라. 큰 명세 본문에 워크스트림 내부 설계는 적지 마라.

- 워크스트림 목록: 워크스트림 id와 맡는 일
- 워크스트림 사이 계약 표: 경계를 넘는 자료마다 「계약 표」 칸을 채운 행
- 의존 순서 표: 워크스트림마다 시작 의존(다른 워크스트림 산출물이 있어야 시작할 수 있는 선행 워크스트림)과 검증 의존(통합 확인에 다른 워크스트림의 실제 구현이 필요한 관계)을 한 행에 적는다. 선행이 없는 워크스트림이 1차다
- 수정 허용 경로: 워크스트림별 git pathspec 목록
- 소유 표: 현재 세션이 소유하는 공용 파일(의존성 목록·잠금 파일 포함)
- 공통 제약과 워크스트림별 통합 확인 방법
- 「결정 기록」 절

다시 나눈 분할을 승인받기 전에 어느 파일 경로도 두 워크스트림의 수정 허용 경로에 겹치지 않는지(한 패턴이 다른 패턴의 경로를 포함하지 않는지) 확인하라. 이 확인 덕분에 「수정 범위 대조」를 통과한 워크스트림끼리는 같은 파일을 고치지 않는다.

승인된 설계 문서 뒤에 맡기기로 했다면 그 설계 문서를 큰 명세로 삼아라. 이 경로에서는 main 대신 설계 문서가 커밋된 끝에서 통합 브랜치를 만들고(「흐름」 준비), 그 브랜치에서 설계 문서에 임시 분할을 보강해 다시 승인받은 뒤 커밋하라. 설계 문서에 사용자가 정한 워크스트림 내부 방식은 그대로 두고, 완전체 명세를 쓸 때 하부 명세와 대조하라.

### 검증 의존

X의 서브 세션은 계약 코드와 테스트 대역으로 X의 설계와 단위 테스트를 마칠 수 있다. 그러나 X의 통합 확인에 Y의 실제 구현이 필요하면 X는 Y에 검증 의존한다. 큰 명세에 워크스트림별 통합 확인 방법을 적을 때 검증 의존을 판정하라. 검증 의존은 시작을 늦추지 않으므로, 시작 워크스트림은 시작 의존만으로 판정하라.

큰 명세를 승인받기 전에 시작 의존과 검증 의존을 합친 그래프에 순환이 없는지 확인하라. 순환이 있으면 병합 순서를 정할 수 없다. 분할이 바뀌는 결정이므로 디스패치 전에 순환에 든 워크스트림을 합친 분할을 권장안으로 사용자에게 물어라. 계약 테스트는 아직 없는 워크스트림 모듈을 생략하므로 병합 순서는 시작 의존과 검증 의존으로 정하라.

### 계약 표

워크스트림 경계를 넘는 자료마다 계약 표에 한 행을 두고 아래 칸을 채워라.

| 칸 | 적는 내용 |
|---|---|
| 이름 | 함수 계약이면 공개 함수의 모듈 경로와 함수·타입 이름, 파일 계약이면 파일 경로 |
| 제공자 → 소비자 | 자료를 내는 워크스트림 id와 쓰는 워크스트림 id. 계약 코드나 현재 세션이 내거나 통합 확인이 쓰면 그 이름 |
| 형식 | 자료형이나 함수 시그니처. 키가 정해진 값이면 열거값, 표나 결과 객체이면 열 이름 |
| 단위 | 값의 단위 |
| 의미(시간·결측 포함) | 서브 세션이 바꾸면 안 되는 값의 뜻, 값이 정해지는 시점과 빈도, 결측 시점·항목 처리(앞값, 0, 오류) |

의미 칸의 시간과 결측은 비워 두지 말고, 해당 없으면 '없음'을 적어라. 「묶는 단위」에서 소유 워크스트림 통합 때 의미를 확정하기로 한 행은 의미 칸과 형식 칸 열거값에 '확정 예정(<소유 워크스트림 id>)'을 적어라. 그 워크스트림을 통합할 때 리포트의 `확정한 계약 의미`를 보고 칸을 채워라. 이 확정은 계약 변경이 아니다. 칸만 채운 커밋 제목은 `계약 의미 확정:`으로 시작하라. 그 칸을 쓰는 사용 쪽은 소유 쪽 통합 뒤에 시작하므로, 이 커밋은 진행 중인 워크스트림이 받을 변경이 아니다. 여러 행이 같은 관례를 쓰면 의미 칸에 큰 명세 「결정 기록」의 관례 이름을 적어라. 그 관례는 큰 명세를 리뷰에 넘기기 전에 「결정 기록」에 적어 두고, 이후 고치는 일은 계약 변경으로 다뤄라.

이름과 형식의 원본은 계약 코드이고, 단위와 의미의 원본은 계약 표다. 큰 명세를 리뷰에 넘기기 전에 각 워크스트림이 맡는 일에 필요한 자료와 통합 확인이 읽는 자료 모두에 제공자 행이 있는지 확인하라.

### 계약 코드

다시 나눈 분할이 승인되면 큰 명세를 통합 브랜치에 커밋하라. 이어 계약을 타입·시그니처·계약 테스트 코드로 만들고, 계약 코드 경로를 소유 표에 현재 세션 소유로 적어라. 계약 코드는 함수 계약마다 공개 함수의 모듈 경로와 시그니처를 정의한다. 그 모듈 파일은 제공 워크스트림 서브 세션이 자기 허용 경로 안에 처음 만든다. 계약 테스트는 그 모듈이 시그니처를 지키는지 대조한다. 모듈을 import할 때 통합 브랜치에 아직 없는 워크스트림 모듈이 필요하면(대조 대상이든 대조 대상이 읽는 다른 워크스트림 모듈이든) 없는 워크스트림 id를 생략 사유에 적어 검사를 생략하도록 작성하라. 그래야 소비자가 제공자보다 먼저 병합돼도 계약 테스트가 깨지지 않는다.

테스트 대역(test double)은 실제 구현 대신 테스트에 쓰는 구현이다. 계약 코드 plan을 쓸 때 소비자 단위 테스트에 필요한 테스트 대역을 계약 코드에 넣고, plan 리뷰에서 테스트 대역이 계약 표의 단위·의미를 지키는지 대조하라. 소비자 서브 세션은 다른 워크스트림 함수의 테스트 대역을 자기 경로에 따로 만들지 않고 `BLOCKED test-double-add`로 요청한다. 파일 계약은 통합 확인에서 열 이름과 형식을 대조하고, 단위와 의미는 다시 나눈 분할을 승인받기 전에 계약 표와 하부 명세를 대조하라.

계약 코드의 SDD는 통합용 워크트리에서 실행하라. 계약 코드도 writing-plans, plan 리뷰(`lens-review`), 실행 순으로 진행하라. 계약 코드가 있어야 통합 확인을 기계적으로 돌릴 수 있다.

### 결정 기록

큰 명세의 「결정 기록」 절은 현재 세션만 쓴다. 첫 디스패치 전에 「관례 골격」과 공용 유틸리티처럼 워크스트림마다 다르게 정하면 충돌할 결정을 채워라. 리뷰에서 처분이 `사용자`인 지적이나 범위 결정에 사용자가 답하면 그 답도 적어라. 통합 때마다 리포트의 `확정한 결정`을 옮기지 말고, 「흐름」 마무리 단계에서 병합된 워크스트림들의 `확정한 결정`을 한 커밋으로 모아 옮겨라. 다른 워크스트림이 따라야 할 결정은 이미 완전체 명세와 관례 골격에 들어 있기 때문이다. 공개 인터페이스는 계약 코드에서 도출하므로 여기 옮겨 적지 마라. 워크스트림 경계를 넘지 않는 관례와 용어 풀이(예: 구간 경계)도 이 절에 적어라.

「결정 기록」만 바꾼 아래 커밋은 제목을 `결정 기록:`으로 시작하라. 사용자 답(요청한 서브 세션 하나에 `ANSWER`로 보낸 답, 「리뷰 마커 확인」의 `escalated` 항목 답, 명세 서브 세션 리포트 '예' 줄의 답)을 적은 커밋, '뺀 하위 프로젝트' 줄을 적은 커밋, 마무리 단계에서 `확정한 결정`을 옮긴 커밋이 여기 해당한다. 「시험 병합」 전 확인에서는 이 커밋과 `계약 의미 확정:` 커밋을 제외하고 본다. 공유 가정을 추가한 커밋에는 이 제목을 쓰지 마라.

### 공용 파일

라우팅 표·진입점·설정 등록부·의존성 목록·잠금 파일처럼 여러 워크스트림이 고치거나 함께 쓰는 파일은 네가 소유하고 소유 표에 적어라. 서브 세션은 공용 파일을 직접 고치지 않고 `BLOCKED shared-file-change`나 `BLOCKED dependency-add`로 요청한다. 요청을 받으면 네가 통합 브랜치에서 고쳐라.

공용 설정 파일에는 사용자가 정한 값과 둘 이상의 워크스트림이 읽는 값만 두어라. 한 워크스트림만 읽는 파라미터는 그 워크스트림 허용 경로 안 설정 파일(예: `configs/<워크스트림 id>.yaml`)에 두고, 그 워크스트림이 허용 경로 안 코드로 읽게 하라.

### 경로와 브랜치 이름

워크스트림 id는 영문 소문자와 숫자로만 짓고 하이픈을 넣지 마라. 임시 워크스트림 id(임시 id)는 `spec`으로 시작하고, 다시 나눈 워크스트림 id는 `spec`으로 시작하지 않게 지어라. 그래야 두 단계의 리포트와 문서 이름이 겹치지 않는다. 명세 서브 세션 브랜치는 `spec/<개발 이름>/<임시 id>`이며, 기준 커밋은 임시 분할 큰 명세를 커밋한 `dev/<개발 이름>`의 끝이다. 아래 경로의 `<워크스트림 id>`는 하부 명세에서는 임시 id, plan에서는 다시 나눈 워크스트림 id다. 하부 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-<워크스트림 id>-design.md`에, 워크스트림 plan은 `docs/superpowers/plans/YYYY-MM-DD-<개발 이름>-<워크스트림 id>.md`에 두어라. 리뷰 기록 이름은 `managing-docs` 「기록 파일 이름 규칙」을 따르며 주제는 `<개발 이름>-<워크스트림 id>` 또는 `<개발 이름>-<워크스트림 id>-plan`이다.

통합 브랜치는 `dev/<개발 이름>`, 워크스트림 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 모든 워크스트림 허용 경로에 자기 문서 경로(`docs/superpowers/specs/*-<개발 이름>-<워크스트림 id>-design.md`, `docs/superpowers/plans/*-<개발 이름>-<워크스트림 id>.md`, `docs/superpowers/reviews/*-<개발 이름>-<워크스트림 id>-*`)를 기본으로 넣어라. 이 세 패턴은 `glob` pathspec으로 써서 `*`가 한 단계 경로만 매칭하게 하라. 리뷰 기록과 같은 이름의 원본 폴더는 셋째 패턴 뒤에 `/**`를 붙여 따로 허용하라. id에 하이픈이 없으므로 id 뒤의 `-`가 경계 역할을 해, 한 id가 다른 id의 접두어여도(`a`와 `ab`) 서로의 문서를 허용하지 않는다.

리포트 경로는 `<git common dir>/nested/<개발 이름>/report-<워크스트림 id>.md`다. `<git common dir>`은 `git rev-parse --path-format=absolute --git-common-dir` 출력값이다. git 내부 폴더라 커밋되지 않으며 현재 세션이 재시작해도 그대로 남는다.

### 서로 독립된 큰 작업

서로 독립된 큰 작업이 둘 이상이면 작업마다 서브 세션에 맡겨라. 작업별로 brainstorming을 거쳐 요구를 정리한 뒤 큰 명세에 워크스트림별 요구로 적고 사용자 승인을 받아라. 워크스트림 사이 계약과 계약 코드는 생략하고, 통합 확인은 각 워크스트림 테스트로 대신하라. 작업들이 같은 저장소에 있으면 자료를 주고받지 않아도 명명·오류 처리·공용 함수 같은 암묵적 결정이 부딪히므로 큰 개발과 마찬가지로 명세 단계와 다시 나누기를 거쳐라. 작업들이 서로 다른 저장소에 있으면 충돌할 결정이 없으므로 명세 단계를 생략하라. 그때는 서브 세션 하나가 작업 하나의 하부 명세부터 구현까지 맡고, 네가 「승인 항목」대로 하부 명세를 승인한다(`AWAITING_APPROVAL`, `APPROVE`). 저장소마다 큰 명세·통합 브랜치·통합용 워크트리를 따로 두고, 통합용 워크트리는 `git -C <저장소> worktree add -b dev/<개발 이름> <경로> main`처럼 브랜치와 함께 만들어라.

## 흐름

현재 세션과 서브 세션은 아래 순서로 진행한다.

이 흐름에서 네가 만드는 통합 브랜치와 `ws/`·`spec/`·`dev/` 브랜치 및 워크트리는 사용자가 승인한 이 개발에 속한다. 네 작업으로 간주해 직접 만들고 병합하고 지워라. 에이전트원칙에서 바꾸지 말라는 다른 세션의 브랜치는 이 흐름 밖의 브랜치와 워크트리를 뜻한다.

**1. 준비(현재 세션)** — 임시 분할 큰 명세가 승인되면 커밋 전에 `git worktree add -b dev/<개발 이름> <통합용 워크트리 경로> main`으로 통합 브랜치와 통합용 워크트리를 함께 만들어라(설계 승인 뒤 맡기는 경로는 보강 전에 main 대신 설계 문서 커밋 끝에서 만든다). 자기 체크아웃에서 쓰고 리뷰한 큰 명세와 리뷰 기록은 `cp`로 통합용 워크트리의 같은 상대 경로에 옮겨 커밋한 뒤, 자기 체크아웃 원본을 지워라. 원본이 미추적 파일로 남으면 사용자 체크아웃에서 통합 브랜치를 main에 병합할 때 git이 같은 경로의 미추적 파일 때문에 병합을 거부한다. 이후 이 개발의 모든 git 명령은 `git -C <통합용 워크트리>`로 실행하고, 계약 코드도 통합용 워크트리의 절대 경로에 써서 커밋하라. 자기 체크아웃 브랜치를 바꾸지 않으므로 사용자의 미커밋 변경이 통합에 섞이지 않는다.

**2. 명세 디스패치(현재 세션)** — 임시 워크스트림마다 `git -C <통합용 워크트리> worktree add -b spec/<개발 이름>/<임시 id> <워크트리 경로> dev/<개발 이름>`으로 브랜치와 워크트리를 만들고, 「디스패치 템플릿」에 따라 명세 서브 세션을 백그라운드로 실행하라. `EnterWorktree`와 `cd`는 쓰지 마라. 네가 서브 세션 워크트리로 이동하면 네 쓰기가 그 브랜치에 섞이기 때문이다. `using-git-worktrees`는 워크트리 위치와 ignore 확인에만 따르고, `Agent`의 `isolation:'worktree'`는 브랜치 이름과 기준 커밋을 정할 수 없으므로 쓰지 마라.

**3. 하부 명세(명세 서브 세션)** — 하부 명세를 쓰고 리뷰해 커밋한 뒤, 리포트에 작성 기록을 남기고 `DONE`으로 끝난다.

**4. 완전체 명세(현재 세션)** — 「명세 단계」·「완전체 명세」·「겹침 판정」대로 완전체 명세를 쓰고 리뷰한 뒤 통합 브랜치에 커밋하라. 커밋 메시지에 명세 단계 토큰 합과 가장 늦은 명세 서브 세션 대기 시간을 `Spec-Tokens:`와 `Spec-Wait:` 트레일러로 넣어라. 재시작으로 잃은 값은 `미상`으로 적어라.

**5. 다시 나누기(현재 세션)** — 「다시 나누기」대로 분할·계약 표·절 배정 표를 큰 명세에 적고 리뷰와 사용자 승인을 받아 커밋하라. 이어 계약 코드를 작성해 계약 테스트까지 통합 브랜치에 커밋하라.

**6. 구현 디스패치(현재 세션)** — 계약 테스트를 통합 브랜치에 커밋한 뒤 시작할 수 있는 워크스트림마다 `git -C <통합용 워크트리> worktree add -b ws/<개발 이름>/<워크스트림 id> <워크트리 경로> dev/<개발 이름>`으로 브랜치와 워크트리를 만들고, 「디스패치 템플릿」대로 구현 서브 세션을 백그라운드로 실행하라.

**7. plan과 구현(구현 서브 세션)** — 절 배정 표가 가리키는 하부 명세와 계약 코드로 plan과 구현을 마치고 `DONE`을 돌려준다.

**8. 통합(현재 세션)** — 「가드레일」 검사와 시험 병합을 거쳐 통합 브랜치에 넣어라. 통합할 때마다 시작 의존이 새로 충족된 워크스트림을 6단계대로 디스패치하라.

**9. 마무리(현재 세션)** — 접지 않은 워크스트림이 모두 들어가면 병합된 워크스트림들의 `확정한 결정`을 「결정 기록」에 `결정 기록:` 커밋 하나로 옮기고, 통합 브랜치 전체에 최종 브랜치 리뷰를 돌려라. 리포트의 `제안`·`기능적 반영`과 「판정 기록 확인」에서 묻지 않은 판정 줄을 모아 결론부터 보고하고 「측정」 값도 함께 적어라. 통합 브랜치를 main에 병합할 때는 사용자 승인을 먼저 받아라. 워크스트림 plan과 리뷰 기록은 `managing-docs` 「문서 타입과 수명」 표대로 처리하라.

**10. 정리(현재 세션)** — main 병합 뒤 지울 목록을 보여 주고 사용자 확인을 한 번 받아라. 목록은 각 워크스트림 워크트리의 SDD 작업 공간(`.superpowers/sdd/`), 명세 서브 세션과 워크스트림의 워크트리, 통합용 워크트리, `spec/<개발 이름>/*`·`ws/<개발 이름>/*`·`dev/<개발 이름>`·남은 `try/*` 브랜치, 리포트 폴더 `<git common dir>/nested/<개발 이름>/`이다.

### 차수

의존 순서 표에서 선행이 없는 워크스트림을 1차로 동시에 실행하라. 동시 실행 에이전트 상한은 4개다(2026-11-16 PC 메모리 부족 뒤 사용자가 정한 값). 서브 세션 하나는 자기와 하위 에이전트 하나를 합쳐 2개로 센다. 따라서 동시 실행 서브 세션은 (4 − 현재 세션이 실행 중인 렌즈·선행연구 에이전트 수) ÷ 2의 몫 이하, 즉 최대 2개다. 상한을 넘는 워크스트림은 앞 서브 세션이 끝난 뒤 디스패치하라. 워크스트림 하나가 통합 브랜치에 들어갈 때마다 그 워크스트림을 선행으로 둔 워크스트림을 확인해, 선행이 모두 충족된 것을 다음 차로 통합 브랜치 끝에서 디스패치하라. 충족 여부는 문서에 적지 말고 git에서 도출하라(구현 단계는 「진행 위치」의 `Workstream:` 줄, 명세 단계는 「명세 단계」 완료 조건). 진행 보고에는 워크스트림별 선행·충족한 선행·남은 선행을 표로 보여라. 같은 파일 수정은 「공용 파일」대로 네가 맡으므로 동시 진행 조건이 아니다.

### 승인 항목

하부 명세 승인은 다른 저장소의 서로 독립된 큰 작업에서만 거친다. 이 경로에서는 하부 명세가 수정 허용 경로 밖을 건드리지 않는지, 큰 명세 본문·결정 기록과 충돌하지 않는지 확인한 뒤 `APPROVE`나 `REVISE`를 보내라. 승인 전에 리포트를 「판정 기록 확인」대로 읽어라.

큰 개발은 사용자가 완전체 명세와 분할을 승인하므로 하부 명세 승인이 없다. 계약 코드에 고정되지 않은 공유 가정(공용 자료 내부 표현, 결정 기록에 없는 관례)이 구현 도중 드러나면 구현 서브 세션이 `BLOCKED contract-change`로 멈춘다. 이때 「받은 메시지 처리」의 `contract-change` 행대로 처리하라.

### 디스패치 뒤 범위 변경

사용자가 디스패치 뒤에 범위를 바꾸면 큰 명세를 고쳐 다시 승인받고, 영향받는 워크스트림에 `CONTRACT-CHANGED`를 보내라. 이미 병합된 워크스트림은 접지 마라.

### 즉시 중단

사용자가 실행 중인 서브 세션을 즉시 멈추라고 하면 `TaskStop`으로 종료하고 `CANCELED`를 받은 것과 같이 처리하라.

## HARD-GATE 예외

superpowers `brainstorming`의 HARD-GATE는 architectural 경로에서 사람이 명세 승인·plan 검토·실행 방식 선택을 하도록 요구한다. 서브 세션은 사람과 대화하지 못하므로 서브 세션에 한해 이 단계를 아래처럼 대체한다. 큰 개발의 명세 승인은 사용자의 다시 나눈 분할·계약 표 승인으로 대신하고, 다른 저장소 독립 작업에서는 현재 세션이 맡는다. plan 검토는 `lens-review` 렌즈 리뷰가 맡고, 실행 방식은 SDD로 고정한다.

명세 서브 세션은 brainstorming 대화를 열지 않고 큰 명세와 관례 골격을 입력받아 하부 명세를 쓴다. 사용자가 직접 정하는 것은 분할(임시 분할, 다시 나눈 분할)과 계약 표다. 현재 세션은 사람과 대화하므로 계약 코드에는 이 예외를 적용하지 마라.

## 디스패치 템플릿

서브 세션은 현재 세션 외 누구와도 대화하지 못하므로 프롬프트를 자기완결적으로 써라. 첫머리에 프로토콜 파일이 정한 `START` 머리줄과 필드를 두고(새 서브 세션으로 교체할 때는 `RESTART`), 그 아래에 다음 블록을 순서대로 넣어라. 필드에 이미 적은 정보는 블록에 중복해 적지 마라. `프로토콜` 필드에는 네가 연 이 스킬 폴더의 `references/sub-session-protocol.md` 절대 경로를 넣어, 개발 중 플러그인이 갱신돼도 두 세션이 같은 형식을 읽게 하라.

**1. 역할 선언** — 아래 문장을 그대로 넣어라: "너는 자율 서브 세션이다. 사용자와 대화할 수 없고, 질문은 상향 메시지로 돌려준다. 모든 명령을 `워크트리` 필드의 경로에서 실행한다. 시작할 때와 하향 메시지를 받을 때마다 `프로토콜` 필드의 파일을 통째로 읽고 따른다."

**2. 임무** — 명세 서브 세션은 하부 명세와 리포트(작성 기록 포함)를 낸다. 구현 서브 세션은 plan·구현·테스트·리포트를 낸다. 다른 저장소 독립 작업을 맡은 서브 세션은 둘 다 낸다.

**3. 수정 허용 경로(엄수)** — 명세 서브 세션은 자기 문서 경로만 고친다. 구현 서브 세션은 큰 명세에 적힌 해당 워크스트림 허용 경로와 자기 문서 경로만 고친다. 공용 파일·계약·큰 명세를 바꿔야 하면 직접 고치지 않고 프로토콜 파일의 사유 코드로 멈춘다.

**4. 하부 명세** — 해당 워크스트림의 책임과 계약 구현에 필요한 내용만 적고, 일어날 수 없는 예외는 늘어놓지 않게 하라. 명세 서브 세션은 하부 명세를 `lens-review`로 리뷰·반영해 커밋한 뒤 리포트 `작성 기록`을 채우고 `DONE`을 돌려준다(다른 저장소 독립 작업은 `AWAITING_APPROVAL`로 멈춘다). HARD-GATE 예외 문장을 그대로 넣어라: "이 워크스트림에서 명세 승인은 사용자의 분할 승인(다른 저장소의 독립 작업은 현재 세션)이, plan 검토는 lens-review 렌즈 리뷰가 맡고, 실행 방식은 subagent-driven-development로 고정한다. brainstorming 대화를 열지 않는다." 구현 서브 세션에는 이 블록 대신 절 배정 표가 가리키는 하부 명세 파일·절과 작성 기록이 있는 리포트 경로를 넣어라.

**5. plan과 구현** — 구현 서브 세션에는 HARD-GATE 예외 문장을 그대로 넣어라: "이 워크스트림에서 명세 승인은 사용자의 분할 승인이, plan 검토는 lens-review 렌즈 리뷰가 맡고, 실행 방식은 subagent-driven-development로 고정한다." 구현 서브 세션은 시작 즉시(다른 저장소 독립 작업은 `APPROVE` 수신 뒤) writing-plans, `lens-review`, SDD(TDD, 프로젝트 테스트 규약) 순으로 진행한다. 워커를 디스패치할 때마다 워크트리 절대 경로를 넘겨 모든 명령을 그 경로에서 실행하게 하라. SDD 연계 규칙은 프로토콜 파일에 있다.

**6. 렌즈와 원칙** — 렌즈 실행 전에 `lens-review`를 통째로 읽고, 렌즈·구현 워커·리뷰어를 한 번에 하나씩 차례로 실행하게 하라. 서브 세션은 그 절차를 여는 호출자 중 하나다. 구현 워커든 문서 작성 서브에이전트든 에이전트원칙 `agent-principles.md` 경로를 넣고, 한국어로 쓰는 서브에이전트에는 `domain-korean` 경로도 함께 넣게 하라.

**7. 주입 컨텍스트** — 큰 명세 「결정 기록」 절(관례 골격 포함)과 그 도메인에서 이미 겪은 함정을 넣어 같은 문제를 다시 겪지 않게 하라.

**8. 멈추는 기준과 산출 계약** — 브랜치까지만 진행하고 병합·배포·main push는 금지하라. 멈추는 기준·메시지·리포트는 프로토콜 파일을 따르며, 리포트는 `리포트` 필드 경로에 쓰고 커밋하지 않게 하라.

## 받은 메시지 처리

상향 메시지를 받으면 아래대로 처리하고, 하향 메시지는 프로토콜 파일 형식에 맞춰 써라. 메시지는 서브 세션이 멈춘 뒤에만 보내라. 같은 서브 세션에 보낼 메시지가 여럿이면 한 번에 묶고, 통합 브랜치를 바꾸는 메시지(`BASE-UPDATED`, `CONTRACT-CHANGED`)를 앞에 두어라. 받을 서브 세션이 실행 중이라 미룬 메시지는 「시험 병합」 전 확인에서 되찾는다.

### BLOCKED 처리

사유 코드와 `유형`에 따라 아래 표대로 처리하라. 사유가 한 번에 여럿이면 바로 처리할 수 있는 것부터 모두 답하라.

| 사유 코드(유형) | 현재 세션이 할 일 | 보낼 메시지 |
|---|---|---|
| `user-decision`(범위 밖 결정) | 사용자에게 하나씩 묻고 답을 「결정 기록」에 커밋하라 | 요청한 쪽에 `ANSWER` |
| `user-decision`(리뷰 사용자 처분) | 처분이 `사용자`인 지적을 사용자에게 알리고 답을 「결정 기록」에 커밋하라 | 요청한 쪽에 `ANSWER` |
| `user-decision`(리뷰 관점 부족) | `researching-prior-art`를 실행하고(하위 질문 4개 이하면 묻지 않고, 넘으면 「발동과 기록」대로 묻는다) 결과를 「결정 기록」에 커밋하라 | 요청한 쪽에 `ANSWER` |
| `user-decision`(SDD 정지) | 비가역 작업·보안 작업·워크트리 밖 부작용이면 승인 여부를 사용자에게 물어라. 모든 진행 방법이 추측인 plan이면 큰 명세나 「결정 기록」에 근거를 보강하라. 사용자가 거절하면 거절과 대안을 보내고 워크스트림을 접을지는 따로 물어라 | 요청한 쪽에 `ANSWER` |
| `user-decision`(환경 문제) | 권한 부여나 도구 설치를 사용자에게 요청하고 결과를 확인하라 | 요청한 쪽에 `ANSWER` |
| `contract-change` | 사용자에게 기각·미룸·채택 중 고르게 하라. 채택이면 큰 명세와 계약 코드(공유 가정이면 「결정 기록」)를 고쳐라 | 채택이면 해당 계약 행의 제공자·소비자 전부(공유 가정이면 그 가정을 쓰는 서브 세션 전부)에 `CONTRACT-CHANGED`, 기각·미룸이면 요청한 쪽에 `ANSWER` |
| `shared-file-change` | 공용 파일이면 통합 브랜치에서 고쳐라. 큰 명세 본문이면 사용자에게 기각·미룸·채택 중 고르게 하라 | 공용 파일이면 요청한 쪽에 `BASE-UPDATED`, 큰 명세 채택이면 바뀐 절이 다루는 워크스트림 전부에 `CONTRACT-CHANGED`, 기각·미룸이면 요청한 쪽에 `ANSWER` |
| `dependency-add` | 통합 브랜치에서 의존성 목록과 잠금 파일에 패키지를 추가해 커밋하라 | 요청한 쪽에 `BASE-UPDATED` |
| `test-double-add` | 계약 코드에 테스트 대역을 추가하고 계약 표의 단위·의미와 대조하라 | 요청한 쪽에 `BASE-UPDATED` |

### FAILED와 CANCELED

`FAILED`를 받으면 그 워크스트림 안에서 고칠 수 있는 원인일 때 같은 서브 세션에 `REVISE`를 보내라. 같은 원인으로 또 실패하면 `RESTART`로 새 서브 세션을 시작하라. 워크스트림을 접는 결정(`CANCEL`)은 출력이 바뀌므로 사용자에게 물어라. `CANCELED`를 받으면 그 워크트리 워커가 끝났는지 CLI 서브에이전트 화면에서 확인해 달라고 사용자에게 요청하라. 브랜치와 워크트리는 지우지 말고 정리 단계의 삭제 목록에 넣어라. 명세 서브 세션이 `FAILED`나 `CANCELED`로 끝났으면 「명세 단계」대로 처리하라.

사용자가 워크스트림을 접기로 하면 「결정 기록」에 '접은 워크스트림: <워크스트림 id> — 이유' 한 줄을 커밋하라. 이어 그 워크스트림이 제공자인 계약 행을 `contract-change` 절차대로 다뤄 행을 지우거나 제공자를 바꿔라. 그래야 계약 테스트 생략 사유에 접은 워크스트림 id가 남지 않는다.

### REVISE 를 쓰는 상황

「승인 항목」·「수정 범위 대조」·「리뷰 마커 확인」·「판정 기록 확인」에서 수정 사항이 나왔거나, 「형식 이탈」로 판단에 필요한 필드가 빠졌거나, `FAILED` 뒤 같은 서브 세션에 재시도시키기로 했을 때 `REVISE`를 보내라. 실패 뒤 재시도인데 고칠 코드가 없으면 `고칠 항목`에 다시 실행할 단계를 적어라.

### 형식 이탈

머리줄이 프로토콜 파일에 없는 종류·사유 코드이거나 필수 필드가 빠진 응답은 형식 이탈이다. 내용을 파악할 수 있으면 해석해 진행하고, 판단에 필요한 필드가 빠졌으면 `REVISE`(대상: 응답)를 보내라.

## 이어 쓰기와 재개

하향 메시지는 모두 해당 워크스트림 서브 세션에 SendMessage 이어 쓰기로 보내고, 워크스트림 코드는 직접 고치지 마라. 현재 세션 층의 작업 단위는 워크스트림 하나이며, 서브 세션 아래 워커의 재개 규칙은 프로토콜 파일이 정한다.

CLI 서브에이전트 화면에는 사용자만 들어갈 수 있다. 완료 통지가 오지 않는 서브 세션이 있으면 사용자에게 그 화면에서 실행 상태를 확인해 달라고 요청하라. 세션이 끊겨 식별자가 사라졌거나 재개에 실패했을 때도 옛 서브 세션이 끝났는지 같은 방식으로 확인받아라. 끝났다면 `RESTART`로 새 서브 세션을 열고, `이어 받을 상태`에 워크스트림 브랜치·하부 명세·plan과 워크트리에 남은 SDD 작업 공간을 적어라.

현재 세션이 재시작하면 진행 위치는 「진행 위치」로, 답할 메시지는 해당 단계 서브 세션 리포트 `메시지 기록` 절의 마지막 상향 메시지로 도출하라. 명세 단계가 끝났으면 명세 서브 세션 리포트는 보지 마라. 마지막 메시지가 `AWAITING_APPROVAL`, `BLOCKED`, `DONE`, `FAILED`, `CANCELED`이고 그 서브 세션이 실행 중이 아니면 미응답 상태로 보고 「받은 메시지 처리」대로 처리하라. 통합용 워크트리에 병합 중 상태나 `try/*` 브랜치가 남아 있으면 `git merge --abort`와 `git switch dev/<개발>`을 실행해 `try/*`를 지우고 시험 병합을 처음부터 다시 하라.

## 가드레일

구현 서브 세션(다른 저장소 독립 작업은 해당 서브 세션)이 `DONE`을 돌려주면 아래 검사를 차례로 실행하라. 명세 서브 세션의 `DONE`에는 「명세 단계」가 정한 검사만 적용하라. 아래 명령은 모두 `git -C <통합용 워크트리>`로 실행하며 여기서는 `git`으로 줄여 표기한다. `<개발>`은 개발 이름, `<id>`는 워크스트림 id다.

### 수정 범위 대조

`git diff --name-only --no-renames dev/<개발>...ws/<개발>/<id> -- . ':(exclude)<허용 경로 1>' … ':(exclude,glob)docs/superpowers/specs/*-<개발>-<id>-design.md' ':(exclude,glob)docs/superpowers/plans/*-<개발>-<id>.md' ':(exclude,glob)docs/superpowers/reviews/*-<개발>-<id>-*' ':(exclude,glob)docs/superpowers/reviews/*-<개발>-<id>-*/**'`를 실행하라. 큰 명세 허용 경로와 자기 문서 경로를 모두 exclude로 넣으므로 출력이 비어야 통과다. 파일이 하나라도 나오면 병합하지 말고 그 서브 세션에 `REVISE`를 보내라. 점 세 개는 두 브랜치의 공통 조상부터 비교하므로 통합 브랜치에서 받은 변경은 잡히지 않는다. `--no-renames`를 붙여야 허용 경로 밖 파일을 안으로 옮긴 변경이 원래 경로의 삭제로 드러난다.

### 리뷰 마커 확인

현재 세션의 Stop 게이트(미리뷰 명세가 남은 채 턴을 끝내지 못하게 하는 훅)는 훅 입력 작업 디렉터리가 속한 저장소만 본다. 따라서 서브 세션 문서와 네가 통합용 워크트리에 쓴 계약 코드 plan에는 이 게이트가 작동하지 않는다. 통합용 워크트리에서 고친 큰 명세(임시 분할, 완전체 명세, 다시 나눈 분할)와 계약 코드 plan은 커밋하기 전에 마지막 비공백 줄이 아래 마커인지 직접 확인하라.

서브 세션 문서는 통합용 워크트리에 들이기 전에 확인하라. 하부 명세는 완전체 명세로 옮기기 전에 `spec/<개발>/<임시 id>` 브랜치에서, 구현 서브 세션 plan은 병합 전에 `git diff --name-only --diff-filter=A dev/<개발>...ws/<개발>/<id> -- docs/superpowers/specs docs/superpowers/plans`로 찾아라. 통합용 워크트리에 없는 파일이므로 `git show <브랜치>:<경로> | grep -v '^[[:space:]]*$' | tail -n 1`로 마지막 비공백 줄을 읽어 `spec-review` 마커(`passed` 또는 `escalated`)인지 확인하라. 이 계약은 플러그인 `hooks/_spec_marker.sh`의 `marker_is_terminal`과 같다. 마커가 없으면 옮기거나 병합하지 말고 `REVISE`를 보내라(명세 서브 세션은 `RESTART`로 리뷰를 다시 시켜라). 마커가 `escalated`이면 처분이 `사용자`인 지적의 사용자 답이 「결정 기록」에 있는지 확인하라. 없으면 병합하지 말고 `user-decision`(리뷰 사용자 처분) 절차대로 사용자에게 물어라. 답을 기록한 뒤 검사를 이어 가고, 그 답 때문에 하부 명세나 구현을 고쳐야 하면 `REVISE`를 보내라.

### 판정 기록 확인

명세 서브 세션 `DONE`을 받았을 때, 다른 저장소 독립 작업의 하부 명세를 승인할 때, 병합 직전에 리포트의 `명세 이탈`·`스스로 판정한 모호함`·`SDD 판정과 남은 지적`을 읽어라. 마지막 칸이 '예'(범위 밖 항목에 가까움)인 줄 중 지시 목적이나 입출력을 바꾸는 줄만 사용자에게 묻고, 사용자가 판정을 뒤집으면 `REVISE`(명세 서브 세션은 `RESTART`)를 보내라. 나머지 줄은 「흐름」 마무리에서 모아 보고하라. 같은 시점에 `선행연구 판정` 절도 읽어라. 선행연구 스킬이 적혀 있으면 `researching-prior-art` 「발동과 기록」대로 실행하라(하위 질문 4개 이하면 묻지 않는다). 결과 때문에 하부 명세나 구현을 고쳐야 하면 그 항목을 `REVISE`(명세 서브 세션은 `RESTART`)로 보내라. 서브 세션은 선행연구 스킬을 실행하지 않는다.

### 검증 의존 대기

검증 의존이 있는 워크스트림이 `DONE`을 돌려줘도 의존 대상 워크스트림이 모두 통합 브랜치에 들어올 때까지 시험 병합을 미뤄라. 그래야 시험 병합의 통합 확인을 실제 구현으로 실행할 수 있다. 「진행 위치」에서는 대기 중인 워크스트림도 진행 중으로 보이므로, 큰 명세의 검증 의존과 통합 브랜치의 `Workstream:` 줄을 대조해 대기 여부를 판정하라. 대기 중인 서브 세션이 의존 대상의 통합 결과를 받아야 하면 `BASE-UPDATED`를 보내라.

### 시험 병합

시험 병합 전에 `git log --oneline --invert-grep --grep='^결정 기록:' --grep='^계약 의미 확정:' ws/<개발>/<id>..dev/<개발> -- <계약 코드 경로> <큰 명세 경로> 'docs/superpowers/specs/*-<개발>-spec*-design.md' <의존성 목록·잠금 파일 경로>`를 실행하라. git은 `--grep` 여럿을 OR로 묶으므로 두 제목으로 시작하는 커밋은 제외된다. 출력이 비어 있지 않으면 바뀐 계약이나 큰 명세를 반영하지 않은 상태이므로 병합하지 마라. 커밋 변경 내용을 확인해 그 워크스트림의 계약 행(제공자·소비자)이나 쓰는 공유 가정이 바뀌었으면 `CONTRACT-CHANGED`를, 그 밖이면 `BASE-UPDATED`를 보내라.

출력이 비어 있으면 `git switch -c try/<id> dev/<개발>`로 임시 브랜치를 만들고 `git merge --no-ff ws/<개발>/<id>`로 병합하라. 병합 커밋 메시지에 「측정」 트레일러와 `Workstream: ws/<개발>/<id>` 트레일러를 넣어라. 충돌이 나면 `git merge --abort` 뒤 아래 실패 처리로 가라. 충돌 파일은 「수정 범위 대조」를 통과했으므로 그 워크스트림 허용 경로 안에 있다. 충돌 파일 목록을 `할 일`에 적어 그 서브 세션에 `BASE-UPDATED`를 보내라.

병합에 성공하면 계약 테스트와 큰 명세 통합 확인을 실행하라. 계약 테스트 생략 사유에 병합 대상 워크스트림 id가 들어 있으면 모듈 경로가 계약 코드와 다르다는 뜻이므로 실패로 처리하라. 접지 않은 워크스트림이 모두 들어가는 마지막 시험 병합에서는 생략이 하나도 없어야 한다. 통과하면 `git switch dev/<개발>`, `git merge --ff-only try/<id>`, `git branch -D try/<id>`를 차례로 실행하라. 리포트에 `확정한 계약 의미`가 있으면 계약 표 '확정 예정' 칸을 채워 `계약 의미 확정:` 커밋으로 남겨라. `확정한 결정`은 「흐름」 마무리에서 한꺼번에 옮겨라.

실패하면 `git switch dev/<개발>`과 `git branch -D try/<id>`로 임시 브랜치를 지운 뒤 원인별로 처리하라. 계약이 원인이면 `contract-change` 절차대로 사용자에게 고르게 하라. 원인이 그 워크스트림 안이면 해당 서브 세션에, 이미 병합된 워크스트림 Y에 있으면 Y의 서브 세션에 `INTEGRATION-FAILED`를 보내라. 원인을 하나로 좁히지 못하면 후보 서브 세션 전부에 보내라.

Y가 수정해 `DONE`을 돌려주면 같은 `Workstream:` 트레일러를 붙여 Y를 시험 병합하라. 이어 통합 브랜치에서 Y에 검증 의존하는 워크스트림 전부(이미 병합된 것도 포함)의 통합 확인을 다시 돌린 뒤, 원래 실패했던 워크스트림의 시험 병합을 재실행하라.

### 되돌림을 쓰지 않는 이유

통합 실패를 `git revert`로 처리하지 마라. git이 되돌린 병합을 공통 이력으로 간주해 재병합 시 처음 변경이 누락되기 때문이다(git 문서 `howto/revert-a-faulty-merge`).

### 진행 위치

상태 문서 없이 git에서 진행 위치를 도출하라. 큰 명세의 새 절 중 사용자 승인이 필요한 절(임시 분할·다시 나눈 분할)은 승인 뒤에, 완전체 명세는 리뷰 뒤에 `dev/<개발>`에 커밋하고 초안은 통합용 워크트리에 미커밋 상태로 두어라. 단계는 아래 표지로 판정한다.

| 표지 | 단계 |
|---|---|
| 큰 개발이고 `dev/<개발>`의 큰 명세가 아직 완전체 명세가 아니다(「겹침 판정」이 없다) | 명세 단계. 리포트 `메시지 기록` 마지막 상향 메시지가 `DONE`이고 `spec/<개발 이름>/<임시 id>` 브랜치 하부 명세에 리뷰 마커가 있거나, 「결정 기록」에 '뺀 하위 프로젝트' 줄이 있는 임시 워크스트림은 완료다 |
| 완전체 명세(「겹침 판정」)는 있고 절 배정 표가 없다 | 다시 나누기 단계. 「결정 기록」에 '직접 진행' 줄이 있으면 현재 세션이 직접 진행 중이다 |
| 절 배정 표는 있고 계약 테스트가 아직 커밋되지 않았다 | 계약 코드 작성 단계 |
| 계약 테스트가 커밋되었다 | 구현 단계. 아래 규칙으로 워크스트림마다 판정한다 |
| 다른 저장소의 독립 작업이다 | 아래 규칙으로 작업마다 판정한다 |

구현 단계에서 `git log dev/<개발> --format=%B`에 `Workstream: ws/<개발>/<id>` 줄이 있는 워크스트림은 완료다. `git branch --merged`는 커밋이 없는 워크스트림 브랜치도 병합된 것으로 출력하므로 쓰지 마라.

미완료 워크스트림 브랜치에서 `git diff --name-only dev/<개발>...ws/<개발>/<id> -- 'docs/superpowers/plans/*-<개발>-<id>.md'`가 파일을 출력하면 구현 중, 비어 있으면 plan 작성 중이다. 다른 저장소 독립 작업은 plan 없이 `'docs/superpowers/specs/*-<개발>-<id>-design.md'`만 나오면 승인 대기, 둘 다 없으면 하부 명세 작성 중이다. 큰 명세 목록에는 있는데 브랜치가 없으면 시작 전이다. 큰 명세 「결정 기록」에 '접은 워크스트림' 줄이 있으면 브랜치 유무와 관계없이 접힘이다.

## 측정

워크스트림마다 실패한 시험 병합 횟수와 그 서브 세션 완료 통지들(재개할 때마다 하나씩 온다)의 `subagent_tokens` 합을 세어라. 이 값을 시험 병합 `git merge --no-ff -m` 커밋에 `Integration-Failures:`와 `Tokens:` 트레일러로 넣어라. 같은 워크스트림을 두 번 이상 병합할 때는 앞 병합 이후부터 이번 병합까지의 증분만 적어라. fast-forward로 통합 브랜치에 들어가므로 이 커밋이 그대로 남는다. 개발이 끝나면 `git log dev/<개발>`에서 이 값들을 모아 사용자에게 보고하라. 명세 단계 토큰과 대기 시간은 「흐름」 4단계의 `Spec-Tokens:`·`Spec-Wait:` 트레일러에서, 구현 단계 `BASE-UPDATED` 횟수는 리포트 `메시지 기록`의 수신 하향 메시지 머리줄에서 세어라.

`FAILED`나 `CANCELED`로 끝나 병합되지 않은 워크스트림은 트레일러가 남지 않으므로 마무리 보고에 따로 적어라.

## 관측성

수동 `Agent` 중첩은 `/workflows` 집계 대시보드에 나타나지 않는다. 대신 CLI가 서브에이전트를 표시하며, 사용자는 거기서 각 서브 세션으로 들어가 본다. 별도 집계 화면이나 메트릭은 없다. 서브에이전트 표시 조작 방법과 워크트리 배정 표시 여부는 아직 확인하지 않은 가정이다. 확인하려면 CLI에서 서브 세션을 실행해 그 화면을 열어 보면 된다.

## 재구현 금지

아이디어에서 명세까지는 `brainstorming`, plan은 `writing-plans`, 실행 루프는 `subagent-driven-development`, 병렬 디스패치 메커니즘은 `dispatching-parallel-agents`, 워크트리 격리는 `using-git-worktrees`, 리뷰 렌즈는 `lens-*`가 각각 소유한다.

## 한계

3층 구조는 조율 층을 덧붙이므로 맡길 워크스트림이나 작업이 둘 이상일 때만 이득이 있다. 검증된 항목과 미검증 항목은 근거 문서 「이어받는 판단과 검증」·「근거와 한계」·「검증하지 않은 가정」·「2026-10-10 개정」·「2026-10-11 개정 — 묶는 단위」·「2026-10-12 개정 — 명세 단계와 다시 나누기」에 있다.

**비목표** — `Workflow` 결정론 버전, 집계 UI 대시보드, 오케스트레이션 상태 문서는 만들지 않는다. 진행 위치는 git에서 도출한다. 4층 이상 더 깊은 중첩도 다루지 않는다.
