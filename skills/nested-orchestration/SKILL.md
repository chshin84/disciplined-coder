# nested-orchestration — 워크스트림으로 나눠 맡기는 3층 오케스트레이션

언제 이 스킬을 쓰는지는 「라우팅」이 정하고, 방법은 이 스킬이 정한다. 기존 스킬을 재구현하지 않고 조합한다. 설계 근거와 검증 결과는 `docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`에 있다.

## 용어

이 스킬은 아래 이름을 아래 뜻으로만 쓴다.

| 이름 | 뜻 |
|---|---|
| 현재 세션 | 사용자와 대화하며 큰 명세·계약·통합을 맡고 워크스트림의 명세·plan·구현은 직접 쓰지 않는 세션 |
| 서브 세션 | 워크스트림 하나를 하부 명세부터 구현까지 맡고 사용자와 대화하지 못하는 서브에이전트 |
| 워커 | 서브 세션이 실행하는 구현자와 렌즈 |
| 워크스트림 | 서브 세션 하나가 맡는 작업 단위 |
| 큰 명세 | 개발 전체를 워크스트림으로 묶고 워크스트림 사이 계약과 결정 기록을 적는 명세 |
| 하부 명세 | 워크스트림 하나의 내부 설계를 적는 명세 |
| 하위 프로젝트 | 큰 개발을 분해한 단위로, 워크스트림으로 묶기 전의 단위(superpowers `brainstorming`의 이름) |
| 서로 독립된 큰 작업 | 서로 자료를 주고받지 않고 각각 plan을 따로 둘 만큼 큰 작업 |
| SDD | plan을 태스크마다 구현 워커와 리뷰어로 실행하는 superpowers `subagent-driven-development` 스킬 |

## 큰 개발 분할

**맡길지 판단하는 시점.** 현재 세션은 superpowers `brainstorming`을 따르다가 요청을 하위 프로젝트 여럿으로 분해하기로 했을 때 서브 세션에 맡길지 판단한다. `brainstorming`은 분해한 하위 프로젝트를 차례로 브레인스토밍하라고 적지만, 이 스킬을 쓰는 현재 세션은 하위 프로젝트마다 명세·plan·구현을 직접 진행하지 않는다.

현재 세션은 설계 문서(`docs/superpowers/specs/`의 spec)가 승인된 뒤 `writing-plans`를 실행하기 전에도 맡길지 판단한다. 하위 프로젝트로 분해하지 않은 큰 개발도 여기서 판단하며, 이때는 현재 세션이 설계 문서에서 하위 프로젝트 목록을 만든다. 2026-10-10에 이 시점들을 정한 이유는 `brainstorming`의 판단 문구가 버전마다 바뀌어도 이 단계들이 남기 때문이다.

**맡기는 기준.** 현재 세션은 계약 코드를 고정한 뒤 동시에 시작할 수 있는 워크스트림(「묶는 단위」의 시작 워크스트림)이 둘 이상이고, 각 워크스트림이 plan을 따로 둘 만큼(태스크 다섯 이상으로 예상될 만큼) 크면 서브 세션에 맡긴다. 다섯은 2026-09-24에 사용자와 합의한 값이고 측정값이 아니다. 이 기준은 이 스킬이 소유한다. 현재 세션은 하위 프로젝트로 분해했는지와 관계없이 이 기준으로 판단하고, 기준에 들지 않으면 superpowers 흐름을 그대로 따른다.

맡기려면 현재 세션은 근거를 보여 사용자 승인을 한 번에 받는다. 근거에는 하위 프로젝트 목록, 「묶는 단위」의 설계 의존 표와 그 결과인 의존 순서, 워크스트림마다 맡는 일과 예상 태스크(`writing-plans`의 태스크) 목록을 적는다. 서로 독립된 큰 작업을 맡길 때는 작업마다 맡는 일과 예상 태스크 목록을 적는다.

승인받은 하위 프로젝트 목록이 「묶는 단위」의 입력이며, 사용자가 목록을 바꾸면 현재 세션은 표와 판정을 다시 만들어 다시 승인받는다. 2026-10-10 측정에서 superpowers 식으로 분해한 목록은 요청에 따라 실행마다 달랐고, 요청 문장의 이름을 옮기는 규칙도 일부 요청에서 흔들렸다. 그래서 현재 세션은 목록을 규칙으로 정하지 않고 사용자 승인으로 고정한다.

**묶는 단위.** 현재 세션은 하위 프로젝트×하위 프로젝트 표를 만든다. X를 설계하려면 Y의 실제 결과(구현 결과나 조사 결과)를 보아야 하면 X→Y에 1을, 그렇지 않으면 0을 적는다. 주고받는 자료의 형식만 알면 되는 관계는 계약 코드로 고정하므로 0이다.

현재 세션은 설계 의존 순환에 함께 든 하위 프로젝트만 한 워크스트림으로 합치고, 나머지는 하위 프로젝트 하나를 워크스트림 하나로 둔다. 순환을 합치고 나면 워크스트림 사이 의존에는 순환이 남지 않으므로, 현재 세션은 그 의존을 큰 명세의 의존 순서에 적는다. 선행 워크스트림이 없는 워크스트림을 시작 워크스트림이라 부르며, 시작 워크스트림들은 동시에 시작할 수 있다. 시작 워크스트림이 하나뿐이면 「맡기는 기준」에 들지 않는다.

순환만 합치는 방식은 DSM 분할과 axiomatic design 이 쓰는 기준이다. DSM(Design Structure Matrix)은 구성 요소 사이 의존을 행렬로 적어 순환 묶음과 순서를 찾는 설계 기법이고, axiomatic design 은 설계 변수 사이 결합을 행렬로 분석하는 설계 이론이다. 2026-10-10 측정에서 하위 프로젝트 목록을 고정한 요청 다섯을 5회씩 묶었을 때, 이 방식은 다섯 요청 모두에서 5회 같은 분할을 냈다. 한 방향 의존도 합치던 이전 규칙은 두 요청에서 5회가 모두 같지는 않았고(가장 많이 나온 분할이 5회 중 4회, 2회), 순차 이전 요청에서는 사슬 전체를 하나로 합쳤다.

이 재현성은 합치지 않는 쪽의 재현성이다. 같은 측정에서 순환만 합치는 분할은 한 요청을 빼면 모두 분리한 결과와 같았고, 주문 처리 요청에 일부러 넣은 상태 변경 순환은 어느 실행도 설계 의존으로 세지 않았다. 순환을 놓치면 분할의 손실이 그대로 생기므로, 현재 세션은 의존 표를 승인 근거에 넣어 사용자가 보게 한다.

두 워크스트림이 같은 파일을 고쳐야 하면 현재 세션이 그 파일을 맡고 「공용 파일」대로 다룬다. 의존성 목록과 잠금 파일은 「공용 파일」의 한 워크스트림 소유 규칙을 따른다. 코드가 없는 단계에서는 경로 겹침을 셀 수 없으므로 합치는 조건으로 쓰지 않는다.

**큰 명세.** 현재 세션은 큰 명세를 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-design.md`에 쓰고 `review-specs`로 리뷰한 뒤 사용자 승인을 받는다. 워크스트림 내부 설계는 적지 않고 아래 항목을 적는다.

- 워크스트림 목록: 워크스트림 id(영문 소문자)와 맡는 일
- 워크스트림 사이 계약: 주고받는 자료의 이름·형식·단위·호출 방향
- 의존 순서: 다른 워크스트림의 산출물이 있어야 시작할 수 있는 워크스트림
- 수정 허용 경로: 워크스트림마다 git pathspec 목록
- 소유 표: 현재 세션이 소유하는 공용 파일과, 의존성 목록·잠금 파일을 고치는 워크스트림
- 공통 제약과 통합 확인 방법
- 「결정 기록」 절

설계 문서가 승인된 뒤에 맡기기로 했으면 현재 세션은 그 설계 문서를 큰 명세로 삼는다. 이 경로에서는 현재 세션이 main 대신 설계 문서가 커밋된 끝에서 `dev/<개발 이름>`을 만들고, 그 브랜치에서 설계 문서에 위 항목을 보강해 커밋한 뒤 다시 승인받는다. 설계 문서에 사용자가 정한 워크스트림 내부 방식은 그대로 두고, 하부 명세를 승인할 때 대조한다.

**계약 코드.** 큰 명세 승인 뒤 현재 세션은 `dev/<개발 이름>`에 큰 명세를 커밋하고 계약을 스텁·타입·계약 테스트 코드로 만든다. 계약 코드의 SDD는 `dev/<개발 이름>`에서 실행한다. 계약 코드도 writing-plans, plan 리뷰, 사용자 plan 검토, 실행 순서로 진행한다. 계약 코드가 있으면 현재 세션이 통합 확인을 기계로 할 수 있다. 계약을 코드로 고정하는 방식은 CodeTeam·Contract-Coding의 설계 사례이고, 산문 계약과 코드 계약을 비교한 결과는 없다.

**결정 기록.** 큰 명세의 「결정 기록」 절은 현재 세션만 쓴다. 현재 세션은 첫 디스패치 전에 명명 관례·오류 처리·공용 유틸리티처럼 워크스트림마다 따로 정하면 충돌하는 결정을 채운다. 워크스트림을 통합하면 그 리포트의 확정 결정을 옮기고, 사용자가 🔴(사용자 결정이 필요한 리뷰 지적)나 범위 결정에 답하면 그 답도 적는다. 공개 인터페이스는 계약 코드에서 도출하므로 옮겨 적지 않는다.

**공용 파일.** 라우팅 표·진입점·설정 등록부처럼 여러 워크스트림이 고치는 파일은 현재 세션이 소유하고 소유 표에 적는다. 의존성 목록과 잠금 파일은 소유 표에 적은 한 워크스트림만 고치고, 그 워크스트림이 끝난 뒤에는 현재 세션이 고친다. 잠금 파일 충돌은 따로 설치한 두 브랜치에서 생기므로(npm 문서 「package-locks」) 소유를 하나로 둔다.

다른 워크스트림은 기존 의존성으로 일하고, 의존성 추가가 필요하면 추가할 패키지를 적어 `BLOCKED`로 멈춘다. 소유 워크스트림이 끝났으면 현재 세션이 통합 브랜치에서 추가한다. 소유 워크스트림이 진행 중이면 현재 세션은 그 서브 세션이 멈추거나 끝날 때 요청을 이어 쓰기로 보내므로, 멈춘 워크스트림은 그동안 기다린다. 추가가 통합되면 현재 세션은 멈춘 워크스트림에 통합 브랜치가 바뀌었다고 알린다.

**경로와 브랜치 이름.** 하부 명세는 `docs/superpowers/specs/YYYY-MM-DD-<개발 이름>-<워크스트림 id>-design.md`, 워크스트림 plan은 `docs/superpowers/plans/YYYY-MM-DD-<개발 이름>-<워크스트림 id>.md`에 둔다. 통합 브랜치는 `dev/<개발 이름>`, 워크스트림 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 모든 워크스트림의 허용 경로에는 자기 문서 경로 셋(`docs/superpowers/specs/*-<개발 이름>-<워크스트림 id>-design.md`, `docs/superpowers/plans/*-<개발 이름>-<워크스트림 id>.md`, `docs/superpowers/reviews/*-<개발 이름>-<워크스트림 id>-*`)이 기본으로 들어간다. 패턴의 id 뒤를 닫아 두었으므로 한 id가 다른 id의 접두어여도 서로의 문서를 허용하지 않는다.

**서로 독립된 큰 작업.** 서로 독립된 큰 작업이 둘 이상이면 현재 세션은 작업마다 서브 세션에 맡긴다. 현재 세션이 작업마다 brainstorming으로 요구를 정리해 큰 명세에 워크스트림별 요구로 적고 사용자 승인을 받는다. 워크스트림 사이 계약과 계약 코드는 생략하고 통합 확인은 각 워크스트림의 테스트로 대신한다. 하부 명세부터 구현까지는 큰 개발과 같이 서브 세션이 맡는다.

작업들이 같은 저장소에 있으면 자료를 주고받지 않아도 명명·오류 처리·공용 함수 같은 암묵적 결정이 부딪히므로, 현재 세션은 「결정 기록」을 첫 디스패치 전에 채운다. 작업들이 다른 저장소에 있으면 현재 세션은 저장소마다 큰 명세와 통합 브랜치를 따로 둔다. 현재 세션은 그 저장소에 `git -C <저장소 경로> worktree add <통합용 워크트리 경로> dev/<개발 이름>`으로 통합용 워크트리를 만들고, 「흐름」과 「가드레일」의 git 명령을 `git -C <통합용 워크트리 경로>`로 실행한다. 사용자가 쓰는 그 저장소의 작업 트리를 바꾸지 않기 위해서다.

**근거와 한계.** 이 분할 구조를 단일 세션과 직접 비교한 연구는 찾지 못했다. 가까운 구조인 CAID(2026, 프리프린트)는 관리자가 스텁을 먼저 커밋하고 작업자마다 git 워크트리를 주어 단일 에이전트보다 높은 정확도를 보고했다. 같은 연구에서 작업자를 4명에서 8명으로 늘리자 성능이 내려갔고, 비용은 단일 에이전트보다 컸다.

Specification Gap(2026, 프리프린트)은 일부 정보만 받은 두 에이전트의 통합 정확도가 58%에서 25%로 떨어졌다고 보고했다. 같은 조건의 단일 에이전트는 89%에서 56%였고, 완전한 명세를 주어야 두 에이전트가 단일 에이전트 수준(89%)으로 회복했다. 그래서 계약과 결정 기록은 분할의 손실을 메울 뿐이며 단일 세션보다 낫게 만들지는 않는다.

Claude Code 문서(agent teams)는 순차 작업, 같은 파일 수정, 의존이 많은 일에는 agent teams 보다 단일 세션이나 서브에이전트가 낫다고 적는다. Parnas(1972)는 처리 흐름 순서로 모듈을 분해하는 방식을 기각했다. BenchAgent(2026, 프리프린트)는 단일 과제 벤치마크 10종에서 고정 역할 다중 에이전트 6종 중 5종이 단일 에이전트보다 2.56~11.29%p 뒤졌다고 보고했다.

그래서 현재 세션은 사용자 요구가 없으면 작은 개발을 서브 세션에 맡기지 않는다. 맡길 때는 동시에 시작할 수 있는 워크스트림이 둘 이상인지 확인하고 계약과 결정 기록을 먼저 고정한다. 출처와 대조 내용은 설계 문서의 「근거와 한계」와 「2026-10-10 개정」에 있다.

## 라우팅

현재 세션은 나눠 맡길 단위에 따라 쓸 스킬을 고른다.

- 단위가 plan·리뷰 루프 없는 단일 태스크이면 현재 세션은 `dispatching-parallel-agents`를 쓴다.
- 「맡길지 판단하는 시점」에서 「맡기는 기준」에 들거나 서로 독립된 큰 작업이 둘 이상이면 현재 세션은 이 스킬을 쓴다.
- 사용자가 나눠 맡기라고 요구하면 현재 세션은 규모와 관계없이 이 스킬을 쓰고, 작은 일이면 조율 비용이 이득보다 클 수 있다고 알린다. 단위가 단일 태스크이면 첫째 불릿을 따른다.
- 위 불릿 어디에도 들지 않으면 현재 세션은 superpowers 흐름을 직접 진행한다.

## 흐름

현재 세션과 서브 세션이 아래 순서로 진행한다.

1. **준비(현재 세션)** — 큰 명세를 커밋하기 전에 main에서 `dev/<개발 이름>`을 만들고(설계 승인 뒤에 맡기는 경로는 「큰 명세」 끝 문단을 따른다), 큰 명세와 계약 코드를 그 브랜치에 커밋한다. 계약 코드의 SDD도 그 브랜치에서 실행한다.
2. **디스패치(현재 세션)** — 시작할 수 있는 워크스트림마다 자기 체크아웃에 남은 채 `git worktree add <워크트리 경로> -b ws/<개발 이름>/<워크스트림 id> dev/<개발 이름>`으로 브랜치와 워크트리를 만들고, 「디스패치 템플릿」으로 서브 세션을 백그라운드로 실행한다. `EnterWorktree`와 `cd`는 쓰지 않는다. 현재 세션이 자기 체크아웃을 떠나면 시험 병합과 다른 워크트리 생성을 할 수 없기 때문이다. `using-git-worktrees`는 워크트리 위치와 ignore 확인에만 따른다. `Agent`의 `isolation:'worktree'`는 브랜치 이름과 기준 커밋을 정할 수 없어 쓰지 않는다.
3. **하부 명세(서브 세션)** — 하부 명세를 쓰고 `review-specs`로 리뷰해 반영한 뒤 커밋하고 `AWAITING_APPROVAL`을 돌려준다.
4. **승인(현재 세션)** — 하부 명세를 대조해 승인하거나 고칠 점을 같은 서브 세션에 보낸다. 대조 항목은 「승인 항목」에 있다.
5. **plan과 구현(서브 세션)** — 승인을 받으면 writing-plans, `review-specs`, SDD 순서로 진행하고 `DONE`을 돌려준다.
6. **통합(현재 세션)** — 「가드레일」의 병합 전 검사와 시험 병합으로 통합 브랜치에 넣는다.
7. **마무리(현재 세션)** — 모든 워크스트림이 들어가면 통합 브랜치 전체에 최종 브랜치 리뷰를 실행한다. 서브 세션들의 리포트에서 「제안」을 모아 사용자에게 보이고, 「측정」 값을 보고한다. 설계 문서 「2026-10-10 개정」의 「검증하지 않은 가정」에 적힌 판단(원칙 조항 삭제, 훅 추가, 워크스트림 수 상한)에 쓸 관찰도 함께 보고한다. 통합 브랜치를 main에 병합하는 일은 그다음 사용자 승인을 받아 한다. 워크스트림 plan과 리뷰 기록은 에이전트원칙의 문서 수명 표대로 처리한다.

의존 순서가 없는 워크스트림은 동시에 진행한다. 같은 파일은 「공용 파일」대로 현재 세션이 맡으므로 동시 진행의 조건이 아니다. 다른 워크스트림의 산출물에 의존하는 워크스트림은 선행 워크스트림이 통합 브랜치에 들어간 뒤 그 끝에서 시작한다.

**승인 항목.** 현재 세션은 하부 명세가 계약 코드의 이름·형식·단위를 그대로 쓰는지, 수정 허용 경로 밖을 고치려 하지 않는지, 큰 명세 본문과 결정 기록에 충돌하지 않는지를 본다. 하부 명세나 리포트의 「스스로 판정한 모호함」에 「멈추는 기준」의 범위 밖 항목에 드는 결정이 있으면 현재 세션은 승인하기 전에 사용자에게 묻는다.

계약 코드가 고정하지 않은 공유 가정(공용 자료의 내부 표현, 결정 기록에 없는 관례)을 하부 명세가 새로 세웠으면 현재 세션은 승인할 때 그 가정을 통합 브랜치의 결정 기록에 커밋한다. 같은 가정을 쓸 다른 서브 세션에는 멈추거나 끝날 때 이어 쓰기로 알린다. 그 서브 세션이 이미 다른 가정으로 구현했으면 현재 세션은 계약 변경과 같이 사용자에게 기각, 다음 개발로 미룸, 지금 채택 중 하나를 고르게 한다. Specification Gap 은 통합 격차가 공유 결정 없이 호환 코드를 만드는 어려움에서 온다고 보고했다.

## HARD-GATE 예외

superpowers `brainstorming`의 HARD-GATE는 사람이 명세를 승인하고 plan을 검토하고 실행 방식을 고르게 한다. 서브 세션은 사람과 대화하지 못하므로 이 스킬은 서브 세션에 한해 세 단계를 대체한다. 명세 승인은 현재 세션이 맡는다. plan 검토는 `review-specs` 렌즈 리뷰가 맡는다. 실행 방식은 SDD로 고정한다.

서브 세션은 brainstorming 대화를 열지 않고 큰 명세와 계약 코드를 입력으로 하부 명세를 쓴다. 사용자가 직접 검토하는 문서는 큰 명세와 계약 코드 plan이다. 현재 세션은 사람과 대화하므로 계약 코드에는 이 예외를 쓰지 않는다.

## 디스패치 템플릿

서브 세션은 현재 세션 외 누구와도 대화할 수 없으므로 프롬프트는 자기완결이어야 한다. 현재 세션은 아래 블록을 차례로 넣는다.

1. **역할 선언** — "너는 자율 서브 세션이다. 사용자와 대화할 수 없고, 질문은 상태로 돌려준다. 네 워크트리는 `<워크트리 절대 경로>`이고 브랜치는 `ws/<개발 이름>/<워크스트림 id>`다. 모든 명령을 그 경로에서 실행한다."
2. **임무** — 큰 명세 경로와 맡은 워크스트림 id를 적는다. 산출물은 하부 명세, plan, 구현, 테스트, 리포트다.
3. **수정 허용 경로(엄수)** — 큰 명세에 적은 그 워크스트림의 허용 경로와 자기 문서 경로만 고친다. 공용 파일이나 계약 변경이 필요하면 고치지 않고, 바꿀 내용을 적어 `BLOCKED`로 멈춘다.
4. **하부 명세** — 하부 명세에는 그 워크스트림의 책임과 계약을 구현하는 데 필요한 내용만 적고, 일어날 수 없는 예외를 늘어놓지 않는다. 하부 명세를 `review-specs`로 리뷰해 반영하고 커밋한 뒤 `AWAITING_APPROVAL`로 멈춘다. HARD-GATE 예외 문장을 그대로 넣는다: "이 워크스트림에서 명세 승인은 현재 세션이, plan 검토는 review-specs 렌즈 리뷰가 맡고, 실행 방식은 subagent-driven-development로 고정한다. brainstorming 대화를 열지 않는다."
5. **plan과 구현** — 승인 메시지를 받으면 writing-plans, `review-specs`, SDD(TDD, 프로젝트 테스트 규약) 순서로 진행한다. 워커를 디스패치할 때마다 워크트리 절대 경로를 넣고 모든 명령을 그 경로에서 실행하게 한다. 통합 브랜치가 바뀌었다는 메시지를 받으면 자기 워크트리에서 `git merge dev/<개발 이름>`으로 받은 뒤 일을 잇는다. SDD 최종 리뷰 뒤 `finishing-a-development-branch`는 실행하지 않고 `DONE`을 돌려주며 워크트리를 지우지 않는다.
6. **렌즈와 원칙** — 렌즈를 실행하기 전에 `dispatching-lenses`를 통째로 읽는다. 서브 세션은 그 규율을 여는 호출자 중 하나이고, 「렌즈에게 에이전트원칙을 알리는 법」이 그 안에 있다. 구현자에게든 문서를 쓰는 서브에이전트에게든 에이전트원칙 `agent-principles.md`의 경로를 넣고, 한국어로 쓰는 서브에이전트에는 `domain-korean`의 경로를 함께 넣는다.
7. **주입 컨텍스트** — 큰 명세의 「결정 기록」 절과, 그 도메인에서 이미 겪은 함정을 넣어 같은 것을 다시 발견하지 않게 한다.
8. **멈추는 기준과 산출 계약(브랜치까지만 — 병합·배포·main push 금지)** — 「멈추는 기준」의 사유와 상태 값을 넣는다. 리포트는 프로젝트 밖 스크래치의 워크스트림별 고유 경로(`report-<워크스트림 id>.md`)에 쓰고 커밋하지 않는다. 리포트 경로는 현재 세션이 스크래치의 절대 경로로 정해 프롬프트에 넣는다. 리포트에는 변경 파일, 테스트 최종 결과, 확정한 결정, 명세 이탈, 범위 밖 아이디어(「제안」), 스스로 판정한 모호함, 리뷰 반영 중 기능적 변화가 있었던 항목, 브랜치명을 적는다. 현재 세션에 돌려주는 것은 상태, 질문이나 블로커, 한 줄 요약, 리포트 경로뿐이다.

## 이어 쓰기와 재개

하던 일이면 어느 층이든 같은 에이전트를 SendMessage로 재개하고, 새 일이면 같은 역할·같은 파일이어도 새 에이전트로 시작한다. 하던 일의 단위는 서브 세션이 워크스트림 하나, 구현 워커가 태스크 하나, 렌즈가 문서 하나의 리뷰 한 차수다. 사용자는 하던 일을 이어 가면 맥락이 증분으로 쌓인다고 판단했다. 같은 에이전트 재개와 새 에이전트에 파일을 넘기는 방식을 비교한 연구는 찾지 못했다.

현재 세션은 하부 명세 승인 뒤 진행 지시, 사용자 답, 통합 실패 출력, 그 워크스트림의 계약·공용 파일 변경, 다른 워크스트림에서 생긴 공유 가정, 의존성 추가 요청을 모두 그 워크스트림의 서브 세션에 이어 쓰기로 보낸다. 그래서 현재 세션은 워크스트림 코드를 직접 고치지 않는다. 메시지는 서브 세션이 끝나거나 멈춘 뒤에 보낸다.

세션이 끊겨 식별자가 사라졌거나 재개가 실패하면, 현재 세션은 워크스트림 브랜치·하부 명세·plan과 워크트리에 남은 SDD ledger(진행 기록 파일)를 넣어 새 서브 세션을 시작한다. 같은 워크스트림의 통합 실패가 되풀이될 때 새 서브 세션으로 바꾸는 횟수 기준은 아직 두지 않는다.

## 멈추는 기준

서브 세션은 아래 사유에서만 멈추고 상태와 질문을 돌려준다. 그 밖의 모호함은 스스로 판정해 SDD ledger와 리포트에 적는다.

- 하부 명세 리뷰를 마쳐 승인을 기다릴 때(`AWAITING_APPROVAL`)
- 하부 명세나 plan 리뷰에서 🔴가 나왔거나, 리스크상 필요한 리뷰 관점을 아무 렌즈도 보지 않았을 때(`BLOCKED`)
- 사람만 정할 수 있는 범위 밖 결정이나 계약·큰 명세·공용 파일 변경이 필요할 때(`BLOCKED`)
- SDD의 정지 사유(비가역 작업, 보안 작업, 워크트리 밖 부작용, 전부 추측인 plan)에 해당할 때(`BLOCKED`)

범위 밖 결정은 큰 명세와 결정 기록에 답이 없고 아래 항목 중 하나에 드는 결정이다.

- 권한: 누가 무엇을 할 수 있는지(역할, 승인, 대리)를 정하는 결정
- 기능의 추가나 제외: 큰 명세의 「맡는 일」에 없는 기능을 만들거나 적힌 기능을 빼는 결정
- 결과의 뜻: 사용자가 보는 상태·판정·알림의 뜻을 정하는 결정
- 돈과 되돌리기 어려운 자료: 금액·주문, 자료의 삭제·보존 기간·덮어쓰기를 정하는 결정
- 보안: 비밀, 인증, 외부 전송을 정하는 결정

화면 배치·문구·정렬·표시 형식과 내부 이름·자료 구조·알고리즘은 범위 안이다. 큰 명세에 없는 기능을 만들지 않는 결정도 범위 안이다.

서브 세션은 위 항목에 분명히 드는 결정에서만 멈춘다. 드는지 확실하지 않으면 스스로 판정하고 리포트의 「스스로 판정한 모호함」에 판정과 이유를 적는다. 현재 세션은 하부 명세 승인과 병합 전 검사에서 그 「스스로 판정한 모호함」 목록을 읽는다.

구현과 리뷰를 마치면 `DONE`을 돌려준다. 명세·plan 리뷰에는 `accept`나 `regenerate` 같은 결정 값이 없으므로 서브 세션은 그 값을 지어내지 않는다. 서브 세션은 리뷰 반영 뒤 다시 리뷰할지 묻지 못하므로 생략하고, 기능적 변화가 있었던 반영을 리포트에 적는다.

현재 세션은 질문을 사용자에게 하나씩 알리고, 답을 큰 명세 「결정 기록」에 적은 뒤 같은 서브 세션에 보낸다. 계약 변경 요청이면 사용자에게 기각, 다음 개발로 미룸, 지금 채택 중 하나를 고르게 한다. 채택하면 현재 세션이 통합 브랜치에서 큰 명세와 계약 코드를 고친 뒤 영향받는 서브 세션에 알린다.

## 가드레일

현재 세션은 서브 세션이 `DONE`을 돌려주면 아래 검사를 차례로 한다. 아래 명령의 `<개발>`은 개발 이름이고 `<id>`는 워크스트림 id다.

**수정 범위 대조.** 현재 세션은 `git diff --name-only --no-renames dev/<개발>...ws/<개발>/<id> -- . ':(exclude)<허용 경로 1>' … ':(exclude)docs/superpowers/specs/*-<개발>-<id>-design.md' ':(exclude)docs/superpowers/plans/*-<개발>-<id>.md' ':(exclude)docs/superpowers/reviews/*-<개발>-<id>-*'`를 실행한다. 큰 명세의 허용 경로와 자기 문서 경로 셋을 모두 exclude로 넣으므로 출력이 비어 있어야 통과한다. 출력에 파일이 나오면 병합하지 않고 그 서브 세션에 되돌린다. 점 세 개는 두 브랜치의 공통 조상부터 비교하므로, 통합 브랜치에서 받은 변경은 출력에 나오지 않는다. `--no-renames`를 붙이면 허용 경로 밖 파일을 안으로 옮긴 변경이 원래 경로의 삭제로 드러난다.

**교집합 검사.** 현재 세션은 동시에 진행한 워크스트림 브랜치를 둘씩 짝지어 exclude 없는 `git diff --name-only --no-renames dev/<개발>...ws/<개발>/<id>` 출력의 교집합을 구한다. 한 쌍이라도 비어 있지 않으면 병합 전에 멈추고 알린다. 허용 경로 패턴끼리 겹치는지는 사람이 놓치기 쉬우므로 현재 세션이 이 검사를 범위 대조와 함께 한다.

**리뷰 마커 확인.** 서브 세션이 쓴 문서에는 현재 세션의 Stop 게이트(미리뷰 명세가 남은 채 턴을 끝내지 못하게 하는 훅)가 적용되지 않는다. 현재 세션은 `git diff --name-only --diff-filter=A dev/<개발>...ws/<개발>/<id> -- docs/superpowers/specs docs/superpowers/plans`로 추가된 하부 명세와 plan을 구하고, 각 파일 마지막 줄을 `git show ws/<개발>/<id>:<경로> | tail -n 1`로 읽어 `spec-review` 마커가 있는지 확인한다. 현재 세션의 체크아웃에는 워크스트림 브랜치의 파일이 없으므로 작업 트리에서 읽지 않는다. 마커가 없으면 병합하지 않는다. 마커가 `escalated`이면 그 🔴의 사용자 답이 큰 명세 「결정 기록」에 있는지 확인하고, 없으면 병합하지 않는다.

**판정 기록 확인.** 현재 세션은 리포트의 「스스로 판정한 모호함」을 읽고, 「멈추는 기준」의 범위 밖 항목에 드는 판정이 있으면 병합하기 전에 사용자에게 묻는다. plan 과 구현 단계의 판정은 하부 명세 승인 때 아직 없으므로 여기서 읽는다.

**시험 병합.** 현재 세션은 `git switch -c try/<id> dev/<개발>`로 임시 브랜치를 만들고 `git merge --no-ff ws/<개발>/<id>`로 병합한 뒤, 계약 테스트와 큰 명세의 통합 확인을 실행한다. 병합 커밋 메시지에는 「측정」의 트레일러와 `Workstream: ws/<개발>/<id>` 트레일러를 넣는다. 통과하면 `git switch dev/<개발>`, `git merge --ff-only try/<id>`, `git branch -D try/<id>`를 실행한다. 실패하면 `git switch dev/<개발>`과 `git branch -D try/<id>`로 임시 브랜치를 지우고, 원인이 계약이면 큰 명세로, 워크스트림 내부면 그 서브 세션으로 보낸다.

**되돌림을 쓰지 않는 이유.** 통합 브랜치는 통과한 병합만 받으므로 되돌림 커밋이 생기지 않는다. 되돌린 병합은 git이 공통 이력으로 보아 다시 병합할 때 처음 변경이 빠지므로(git 문서 `howto/revert-a-faulty-merge`), 현재 세션은 `git revert`로 통합 실패를 처리하지 않는다.

**진행 위치.** 현재 세션은 상태 문서 없이 git에서 진행 위치를 도출한다. `git log dev/<개발> --format=%B`에 `Workstream: ws/<개발>/<id>` 줄이 있는 워크스트림은 끝났다. `git branch --merged`는 커밋이 아직 없는 워크스트림 브랜치도 병합된 것으로 내므로 쓰지 않는다. plan이 있는지는 `git ls-tree -r --name-only ws/<개발>/<id> -- docs/superpowers/plans`로 본다. 끝나지 않은 워크스트림 브랜치는 plan이 있으면 승인 뒤 진행 중이고, 하부 명세만 있으면 승인 대기이며, 둘 다 없으면 하부 명세 작성 중이다. 큰 명세 목록에 있는데 브랜치가 없는 워크스트림은 시작 전이다.

**크래시와 멈춤.** 완료 통지가 오지 않는 서브 세션이 있으면, 현재 세션은 CLI의 서브에이전트 화면에서 그 세션으로 들어가 실행 상태를 확인한다. 종료되었으면 「이어 쓰기와 재개」대로 재개하거나 새 서브 세션을 시작한다. 타임아웃과 헬스체크 도구가 없어 현재 세션의 주의에 의존한다.

**비용.** 서브 세션마다 맥락 재확립과 워커 팬아웃이 든다. 2026-07 스파이크에서 사소한 워크스트림 하나당 약 40k 토큰이 들었다. 이 값은 워커를 포함하지만, 하부 명세와 승인 단계가 없던 흐름에서 측정한 값이다.

## 측정

현재 세션은 워크스트림마다 실패한 시험 병합 수와 그 원인, 서브 세션이 올린 질문 수, 완료 통지의 `subagent_tokens`를 센다. 이 값은 시험 병합의 `git merge --no-ff -m`에 `Integration-Failures:`, `Questions:`, `Tokens:` 트레일러로 넣는다. `Tokens:` 값은 그 서브 세션의 완료 통지들(재개할 때마다 하나씩 온다)의 `subagent_tokens` 합이다. fast-forward로 통합 브랜치에 들어가므로 이 커밋이 통합 브랜치에 남는다. 개발이 끝나면 현재 세션이 `git log dev/<개발>`에서 이 값을 모아 사용자에게 보고한다.

## 관측성

수동 `Agent` 중첩은 `/workflows` 집계 대시보드에 뜨지 않는다. 대신 CLI가 서브에이전트를 표시하고, 사용자는 그 항목을 더블클릭해 각 서브 세션의 실행 화면으로 들어간다. 집계 대시보드와 메트릭은 볼 수 없고, 어떤 워크트리가 어느 서브 세션에 배정됐는지도 화면에 나오지 않는다.

## 재구현 금지

아이디어에서 명세까지는 `brainstorming`, plan은 `writing-plans`, 실행 루프는 `subagent-driven-development`, 병렬 디스패치 메커니즘은 `dispatching-parallel-agents`, 워크트리 격리는 `using-git-worktrees`, 리뷰 렌즈는 `lens-*`가 소유한다.

## 한계

3층은 조율 층을 얹으므로 맡길 워크스트림이나 작업이 둘 이상일 때만 값을 한다. 무엇이 검증됐고 무엇이 아직 아닌지는 설계 문서(`docs/superpowers/specs/2026-10-09-nested-orchestration-large-dev-design.md`)의 「이어받는 판단과 검증」, 「검증하지 않은 가정」, 「2026-10-10 개정」에 있다.

**비목표** — `Workflow` 결정론 버전과 집계 UI 대시보드와 오케스트레이션 상태 문서는 만들지 않는다. `Workflow`는 중첩을 1단계로 제한해 판단으로 SDD를 실행하는 서브 세션을 수용하지 못한다. 진행 위치는 git에서 도출한다. 4층 이상 더 깊은 중첩도 다루지 않는다.
