# nested-orchestration 서브 세션 프로토콜

이 문서는 `nested-orchestration` 서브 세션의 메시지 형식, 멈추는 기준, 리포트, SDD 병용 규칙을 다룬다. 서브 세션은 시작할 때와 하향 메시지를 받을 때마다 이 문서 전체를 읽어라. 현재 세션도 메시지를 쓰고 읽을 때 「메시지 형식」을 따르라. 현재 세션이 메시지를 받은 뒤 할 일은 `SKILL.md`에 있다.

## 용어

이 문서에서 아래 용어는 다음 뜻으로만 쓴다.

| 이름 | 뜻 |
|---|---|
| 현재 세션 | 사용자와 대화하며 큰 명세·계약·통합을 맡고 서브 세션에 메시지를 보내는 세션 |
| 워크스트림 | 서브 세션 하나가 맡는 작업 단위 |
| 서브 세션 | 워크스트림 하나를 맡는 서브에이전트. 사용자와 대화할 수 없다 |
| 명세 서브 세션 | 임시 워크스트림 하나의 하부 명세와 작성 기록을 쓰고 끝나는 서브 세션. 브랜치는 `spec/<개발>/<임시 id>` |
| 구현 서브 세션 | 다시 나눈 워크스트림 하나를 맡아, 큰 명세의 절 배정 표가 가리키는 하부 명세로 plan부터 구현까지 진행하는 서브 세션. 브랜치는 `ws/<개발>/<id>` |
| 워커 | 서브 세션이 실행하는 구현자·리뷰어·렌즈 |
| 큰 명세 | 전체 개발을 워크스트림으로 나누고 워크스트림 간 계약과 「결정 기록」을 정리한 명세 |
| 하부 명세 | 임시 워크스트림 하나의 내부 설계 명세. 다른 저장소의 독립 작업에서는 해당 서브 세션이 직접 쓴다 |
| 계약 표 | 워크스트림 경계를 넘는 자료마다 한 행씩 정리한 큰 명세의 표 |
| 계약 코드 | 계약 표 내용을 타입·시그니처·계약 테스트로 구현해 통합 브랜치에 커밋한 코드 |
| 통합 브랜치 | 각 워크스트림을 합치는 브랜치 `dev/<개발>` |
| SDD | plan의 각 태스크를 구현 워커와 리뷰어로 실행하는 superpowers `subagent-driven-development` 스킬 |
| 머리줄 | 메시지 첫 줄에 적는 메시지 종류와 `BLOCKED` 사유 코드 |
| 상향 메시지 | 서브 세션이 현재 세션으로 보내는 메시지 |
| 하향 메시지 | 현재 세션이 서브 세션으로 보내는 메시지. 디스패치 프롬프트(`START`·`RESTART`)도 같은 형식을 따르지만, 현재 세션의 측정 집계에서는 하향 메시지 수에 넣지 않는다 |
| 사유 코드 | `BLOCKED` 사유를 나타내는 지정 이름 |
| 유형 | `user-decision`을 세분하는 `유형` 필드 값 |

## 메시지 형식

현재 세션과 서브 세션은 이 절의 형식으로만 메시지를 주고받아라.

**표기.** 보낼 때는 첫 줄에 머리줄을 적어라. 머리줄은 `<종류>` 또는 `BLOCKED <사유 코드>`다. 아래에 공통·추가 필드를 표 순서대로 `필드: 값` 줄로 적고, 빈 필드는 빼지 말고 `없음`을 적어라. 어느 메시지에서나 통합 브랜치는 `통합 브랜치` 필드에, 워크스트림 브랜치는 `브랜치` 필드에 적어라.

**상향 메시지.** 서브 세션은 모든 상향 메시지에 공통 필드로 `워크스트림`, `브랜치`(`ws/<개발>/<id> @ <커밋>`, 명세 서브 세션은 `spec/<개발>/<임시 id> @ <커밋>`), `리포트`, `요약`을 넣어라. 판정 같은 세부 내용은 리포트에만 적어라. 상향 메시지를 보내기 전에 리포트를 갱신하고, 보낼 메시지 전문을 리포트의 `메시지 기록` 절에 그대로 덧붙여라. 하향 메시지를 받으면 그 머리줄을 `메시지 기록`에 한 줄로 남겨라.

| 머리줄 | 추가 필드 | 보내는 때 |
|---|---|---|
| `AWAITING_APPROVAL` | `하부 명세`, `리뷰 기록`, `마커` | 다른 저장소의 독립 작업에서 하부 명세를 리뷰하고 커밋한 뒤 |
| `BLOCKED <사유 코드>` | `유형`, `요청`, `이유`, `멈춘 작업` | 아래 사유 코드 표에 해당할 때. `유형`은 `user-decision`일 때만 채우고 나머지 코드에는 `없음`을 적어라 |
| `DONE` | 없음 | 구현 서브 세션은 구현과 SDD 최종 리뷰를 마친 뒤. 명세 서브 세션은 하부 명세를 리뷰·커밋하고 리포트의 `작성 기록`을 채운 뒤 |
| `FAILED` | `원인`, `시도한 것`, `되돌릴 것` | 사유 코드에 해당하지 않지만 작업을 끝낼 수 없을 때 |
| `CANCELED` | `남긴 상태` | `CANCEL`을 받아 멈춘 뒤 |

**사유 코드.** 서브 세션은 아래 표에서 사유 코드를 골라라. 사유가 둘 이상이면 표에서 앞선 코드를 머리줄에 적고, 나머지는 사유 코드와 함께 `요청`에 한 줄씩 적어라. `user-decision` 사유가 둘 이상이면 `요청`의 각 줄에 유형도 함께 적어라.

| 사유 코드 | 고르는 때 |
|---|---|
| `user-decision` | 사람만 정할 수 있는 일이 생겼을 때. 아래 유형 표의 값 하나를 `유형`에 적어라 |
| `contract-change` | 계약 표 행, 계약 코드, 「결정 기록」의 공유 가정을 바꿔야 할 때. 계약 불일치로 테스트가 실패한 때도 이 코드를 골라라 |
| `shared-file-change` | 공용 파일이나 큰 명세 본문을 수정해야 할 때 |
| `dependency-add` | 의존성 목록·잠금 파일에 패키지를 추가해야 할 때. 추가할 패키지를 `요청`에 적어라 |
| `test-double-add` | 계약 코드에 없는 테스트 대역이 필요할 때 |

| 유형 | 고르는 때 |
|---|---|
| 범위 밖 결정 | 「멈추는 기준」의 범위 밖 항목에 분명히 드는 결정이 필요할 때 |
| 리뷰 사용자 처분 | 하부 명세나 plan의 `lens-review` 처분이 `사용자`인 항목이 나왔을 때. 이때 `BLOCKED user-decision`으로 멈춰라 |
| 리뷰 관점 부족 | 리스크상 필요한 관점을 렌즈로 볼 수 없어, 선행연구 스킬을 먼저 실행해야 진행할 수 있을 때 |
| SDD 정지 | SDD가 멈추고 사람에게 물으라고 정한 상황(비가역·파괴 작업, 보안 작업, 워크트리 밖 부작용, 모든 진행 방법이 추측인 plan)에 해당할 때 |
| 환경 문제 | 권한이나 도구 설치처럼 사람이 조치해야 해결되는 문제가 생겼을 때 |

렌즈로 볼 수 있는 관점이면 멈추지 말고 `lens-review` 규칙대로 해당 렌즈를 실행하라(「카테고리와 렌즈」). 선행연구 스킬의 발동 기준에 들었더라도 진행에 지장이 없으면 멈추지 말고 리포트의 `선행연구 판정`에 기록하라. 세부 기준은 `researching-prior-art`의 「발동과 기록」을 따른다.

**하향 메시지.** 현재 세션은 모든 하향 메시지에 공통 필드로 `워크스트림`과 `통합 브랜치`(`dev/<개발> @ <커밋>`)를 넣어라. `START`와 `RESTART`는 디스패치 프롬프트 첫머리에 오며, 필드 아래에 산문 지시가 이어진다. 아래 표의 '다음 응답'은 작업을 마쳤을 때 보내는 응답이다. 어떤 하향 메시지를 처리하던 중이든 사유에 해당하면 `BLOCKED`를, 끝낼 수 없으면 `FAILED`를 보내라.

| 머리줄 | 추가 필드 | 서브 세션이 할 일 | 다음 응답 |
|---|---|---|---|
| `START` | `브랜치`(`spec/<개발>/<임시 id>` 또는 `ws/<개발>/<id>`), `워크트리`(절대 경로), `리포트`, `프로토콜`(이 파일의 절대 경로), `큰 명세` | 명세 서브 세션은 하부 명세를 작성하고 `lens-review` 리뷰를 반영해 커밋한 뒤 `작성 기록`을 채워라. 구현 서브 세션은 큰 명세의 절 배정 표가 가리키는 하부 명세·작성 기록·계약 코드를 바탕으로 writing-plans, `lens-review`, SDD를 진행하라. 다른 저장소의 독립 작업에서는 하부 명세를 작성·리뷰해 커밋하라 | 명세·구현 서브 세션은 `DONE`, 다른 저장소의 독립 작업은 `AWAITING_APPROVAL` |
| `RESTART` | `START`의 추가 필드, `이전 리포트`, `원인`, `시도한 것`, `이어 받을 상태`(브랜치·하부 명세나 plan·SDD 작업 공간) | 이전 리포트를 `리포트` 경로에 이어 쓰고, 이어 받을 상태에서 멈춘 단계를 찾아 재개하라. `원인`과 `시도한 것`의 방식을 그대로 되풀이하지 마라. 명세 서브 세션은 `원인`에 적힌 수정 항목대로 하부 명세를 고쳐 다시 리뷰하라 | 이어 받은 단계의 응답 |
| `APPROVE` | `승인한 하부 명세`, `조건` | 다른 저장소의 독립 작업에서만 쓴다. writing-plans, `lens-review`, SDD를 진행하라. 이미 plan이 있으면 바뀐 하부 명세 절만 반영해 고쳐라 | `DONE` |
| `REVISE` | `대상`, `고칠 항목` | 고칠 항목을 수정하고 커밋하라. 대상이 하부 명세나 plan이면 다시 리뷰하라 | 다른 저장소의 독립 작업에서 대상이 하부 명세면 `AWAITING_APPROVAL`, 구현이나 plan이면 `DONE`, 응답이면 고친 내용으로 같은 종류의 상향 메시지를 다시 보낸다 |
| `ANSWER` | `질문`, `답`, `결정 기록` | 받은 답을 반영해 멈춘 작업을 이어 가라 | 하던 단계의 응답 |
| `BASE-UPDATED` | `바뀐 것`, `할 일` | 자기 워크트리에서 `git merge dev/<개발>`을 실행하고, 충돌이 나면 풀어 커밋하라. 테스트를 다시 실행한 뒤 작업을 이어 가라 | 하던 단계의 응답 |
| `CONTRACT-CHANGED` | `바뀐 항목`(계약 행, 큰 명세 절, 공유 가정), `커밋` | 통합 브랜치를 병합하고 바뀐 항목에 맞춰 수정하라. 공유 가정이 자기 구현과 다르면 고치지 말고 `BLOCKED contract-change`로 알려라. plan이 바뀌면 다시 리뷰하라 | 하던 단계의 응답(다른 저장소의 독립 작업에서 하부 명세가 바뀌었으면 `AWAITING_APPROVAL`) |
| `INTEGRATION-FAILED` | `확인 위치`, `실패 검사`, `출력` | 자기 워크트리에서 통합 브랜치를 병합하라. `확인 위치`에 다른 워크스트림 커밋이 있으면 임시 브랜치에 그 커밋을 함께 병합해 실패를 재현한 뒤 임시 브랜치를 지워라. 원인을 자기 브랜치에서 고쳐 커밋하라 | `DONE` |
| `CANCEL` | `이유` | 커밋하지 않은 변경 사항을 워크트리에 그대로 둔 채 멈춰라 | `CANCELED` |

`INTEGRATION-FAILED`의 `확인 위치`는 실패를 재현할 커밋이다. 시험 병합한 워크스트림이면 `ws/<개발>/<id> @ <커밋>`, 이미 병합된 워크스트림의 통합 확인을 통합 브랜치에서 다시 실행해 실패했으면 `없음`이다.

## 멈추는 기준

서브 세션은 `AWAITING_APPROVAL`(다른 저장소의 독립 작업), `DONE`, `FAILED`, `CANCELED`를 보낼 때와 「메시지 형식」의 사유 코드에 해당할 때만 멈춰라. 나머지 모호함은 스스로 판단해 리포트의 `스스로 판정한 모호함`에 적어라.

범위 밖 결정은 큰 명세와 「결정 기록」에 답이 없으면서 아래 항목에 해당하는 결정을 뜻한다.

- 권한: 누가 무엇을 할 수 있는지(역할·승인·대리) 정하는 결정
- 기능의 추가나 제외: 큰 명세의 워크스트림 목록에 적힌 담당 업무에 없는 기능을 넣거나 적힌 기능을 빼는 결정
- 결과의 뜻: 사용자에게 보이는 상태·판정·알림의 의미를 정하는 결정
- 돈과 되돌리기 어려운 자료: 금액·주문이나 자료의 삭제·보존 기간·덮어쓰기를 정하는 결정
- 보안: 비밀, 인증, 외부 전송을 정하는 결정

화면 배치·문구·정렬·표시 형식과 내부 이름·자료 구조·알고리즘은 범위 안이다. 큰 명세에 없는 기능을 만들지 않기로 하는 결정도 범위 안이다. 위 항목에 분명히 해당할 때만 멈추고, 해당 여부가 불확실하면 스스로 판단한 뒤 그 줄의 마지막 칸에 '예'를 적어라.

명세·plan 리뷰에는 `accept`나 `regenerate` 같은 결정 값이 없으니 그런 값을 지어내지 마라. 리뷰 반영 뒤 재리뷰 여부를 물을 수 없으므로 생략하고, 기능적 변화가 생긴 반영은 리포트의 `기능적 반영`에 적어라.

## SDD 와 함께 쓸 때

실행 루프는 SDD가 소유하므로 서브 세션은 SDD 규칙을 따른다. 다만 마무리 단계의 작업 공간 삭제와 `finishing-a-development-branch` 실행은 아래 문단의 규칙으로 대체한다. 수정 라운드 상한과 상한 도달 시 판정은 SDD 규칙을 따르고, SDD가 중단 후 사람에게 물으라고 정한 상황에서만 `BLOCKED user-decision`(유형: SDD 정지)을 보내라. 구현자 재개 여부도 SDD 규칙(수정 1~3라운드는 재개, 4라운드부터 새 구현자)을 따르며, 렌즈 재실행은 `lens-review` 규칙을 따르라.

SDD 최종 리뷰를 마치면 `finishing-a-development-branch`를 실행하지 말고 `DONE`을 보내라. SDD는 최종 브랜치 리뷰에 지적이 없으면 작업 공간을 지우라고 하지만, 지우지 마라. 워크트리와 SDD 작업 공간(`.superpowers/sdd/` 아래, gitignore 대상)은 `DONE` 전후 언제든 삭제하지 마라. 재개에 실패하면 새 서브 세션이 그 작업 공간을 이어 받고, 삭제는 현재 세션이 「흐름」의 정리 단계에서 처리한다.

SDD 종료 시 모으는 판정(`Ruling:` 줄) 목록과 최종 리뷰에 남은 지적은 리포트의 `SDD 판정과 남은 지적`에 옮겨 적어라.

## 리포트

서브 세션은 `리포트` 필드가 가리키는 경로에 리포트를 작성하되 커밋하지 마라. 아래 절 제목을 표의 순서대로 넣고, 쓸 내용이 없는 절도 빼지 말고 `없음`이라고 적어라. 테스트는 현재 세션이 시험 병합에서 직접 실행하므로 결과는 적지 마라. 판정을 적는 절(`명세 이탈`, `스스로 판정한 모호함`, `SDD 판정과 남은 지적`)의 마지막 칸에는 해당 줄이 「멈추는 기준」의 범위 밖 항목에 가까운지(예·아니오)를 적어라.

| 절 제목 | 줄의 형식 |
|---|---|
| `확정한 결정` | '결정 — 이유' |
| `확정한 계약 의미` | '계약 행 — 칸(의미 또는 형식의 열거값) — 값' |
| `작성 기록` | 명세 서브 세션만 작성한다. '고른 대안 — 기각한 대안과 이유', '읽은 코드와 자료', '열린 질문' 줄 |
| `명세 이탈` | '하부 명세 위치(절 배정 표의 파일과 절) — 실제 구현 — 이유 — 범위 밖(예·아니오)' |
| `스스로 판정한 모호함` | '질문 — 판정 — 이유 — 범위 밖(예·아니오)' |
| `SDD 판정과 남은 지적` | '판정이나 남은 지적 — 결정 — 틀렸을 때의 비용 — 범위 밖(예·아니오)' |
| `선행연구 판정` | '선행연구 스킬 — 대상 문서 — 발동 기준에 해당한 이유' |
| `기능적 반영` | '리뷰 반영 중 동작이 바뀐 항목 — 바뀐 동작' |
| `제안` | '범위 밖 아이디어 — 이유' |
| `메시지 기록` | 보낸 상향 메시지 전문과 받은 하향 메시지의 머리줄을 순서대로 |
