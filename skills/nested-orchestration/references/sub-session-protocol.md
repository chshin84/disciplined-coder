# nested-orchestration 서브 세션 프로토콜

이 파일은 `nested-orchestration`의 서브 세션이 따르는 메시지 형식과 멈추는 기준과 리포트와 SDD 와 함께 쓸 때의 규칙이다. 서브 세션은 시작할 때와 하향 메시지를 받을 때마다 이 파일을 통째로 읽는다. 현재 세션도 메시지를 쓰고 읽을 때 이 파일의 「메시지 형식」을 따르며, 현재 세션이 메시지를 받아 할 일은 `SKILL.md`에 있다.

## 용어

이 파일은 아래 이름을 아래 뜻으로만 쓴다.

| 이름 | 뜻 |
|---|---|
| 현재 세션 | 사용자와 대화하며 큰 명세·계약·통합을 맡고 서브 세션에 메시지를 보내는 세션 |
| 서브 세션 | 워크스트림 하나를 맡고 사용자와 대화하지 못하는 서브에이전트 |
| 명세 서브 세션 | 임시 워크스트림 하나의 하부 명세와 작성 기록을 쓰고 끝나는 서브 세션. 브랜치는 `spec/<개발>/<임시 id>` |
| 구현 서브 세션 | 다시 나눈 워크스트림 하나를 큰 명세 「절 배정」의 하부 명세로 plan 부터 구현까지 맡는 서브 세션. 브랜치는 `ws/<개발>/<id>` |
| 워커 | 서브 세션이 실행하는 구현자와 리뷰어와 렌즈 |
| 큰 명세 | 개발 전체를 워크스트림으로 묶고 워크스트림 사이 계약과 「결정 기록」을 적는 명세 |
| 하부 명세 | 임시 워크스트림 하나의 내부 설계를 적는 명세. 다른 저장소의 독립 작업에서는 그 작업을 맡은 서브 세션이 쓴다 |
| 통합 브랜치 | 워크스트림을 모으는 브랜치 `dev/<개발>` |
| SDD | plan을 태스크마다 구현 워커와 리뷰어로 실행하는 superpowers `subagent-driven-development` 스킬 |
| 머리줄 | 메시지의 첫 줄. 메시지 종류와, 종류가 `BLOCKED`이면 사유 코드를 적는다 |
| 상향 메시지 | 서브 세션이 현재 세션에 돌려주는 메시지 |
| 하향 메시지 | 현재 세션이 서브 세션에 보내는 메시지. 디스패치 프롬프트(`START`·`RESTART`)도 하향 메시지의 형식을 따르지만, 현재 세션이 측정에서 하향 메시지 수를 셀 때는 세지 않는다 |
| 사유 코드 | `BLOCKED`의 사유를 가리키는 정해진 이름 |
| 유형 | `user-decision`을 세분하는 `유형` 필드의 값 |

## 메시지 형식

현재 세션과 서브 세션은 이 절의 형식으로만 메시지를 주고받는다.

**표기.** 보내는 세션은 첫 줄에 머리줄을 적는다. 머리줄은 `<종류>` 또는 `BLOCKED <사유 코드>`다. 보내는 세션은 그 아래에 공통 필드와 추가 필드를 `필드: 값` 줄로 표의 순서대로 두고, 값이 없는 필드는 지우지 않고 `없음`으로 적는다. 통합 브랜치는 어느 메시지에서나 `통합 브랜치` 필드로, 워크스트림 브랜치는 `브랜치` 필드로 적는다.

**상향 메시지.** 서브 세션은 모든 상향 메시지에 `워크스트림`, `브랜치`(`ws/<개발>/<id> @ <커밋>`, 명세 서브 세션은 `spec/<개발>/<임시 id> @ <커밋>`), `리포트`, `요약`을 공통 필드로 적는다. 판정 같은 상세는 리포트에만 적는다. 서브 세션은 상향 메시지를 보내기 전에 리포트를 갱신하고, 리포트의 `메시지 기록` 절에 보낼 메시지를 그대로 덧붙인다. 하향 메시지를 받으면 그 머리줄을 `메시지 기록`에 한 줄로 적는다.

| 머리줄 | 추가 필드 | 보내는 때 |
|---|---|---|
| `AWAITING_APPROVAL` | `하부 명세`, `리뷰 기록`, `마커` | 다른 저장소의 독립 작업에서 하부 명세를 리뷰하고 커밋한 뒤 |
| `BLOCKED <사유 코드>` | `유형`, `요청`, `이유`, `멈춘 작업` | 아래 사유 코드 표의 사유에 해당할 때. `유형`은 `user-decision`에만 적고 다른 코드에는 `없음`을 적는다 |
| `DONE` | 없음 | 구현 서브 세션은 구현과 SDD 최종 리뷰를 마친 뒤. 명세 서브 세션은 하부 명세를 리뷰해 커밋하고 리포트의 `작성 기록`을 채운 뒤 |
| `FAILED` | `원인`, `시도한 것`, `되돌릴 것` | 사유 코드 어디에도 들지 않는데 끝낼 수 없을 때 |
| `CANCELED` | `남긴 상태` | `CANCEL`을 받고 멈춘 뒤 |

**사유 코드.** 서브 세션은 아래 표에서 사유 코드를 고른다. 한 번 멈출 때 사유가 둘 이상이면 머리줄에는 표에서 먼저 나오는 코드를 적고, 나머지는 `요청`에 줄마다 사유 코드와 함께 적는다. `user-decision` 사유가 둘 이상이면 `요청`의 줄마다 유형도 함께 적는다.

| 사유 코드 | 고르는 때 |
|---|---|
| `user-decision` | 사람만 정할 수 있는 일이 있을 때. `유형`에 아래 유형 표의 값 하나를 적는다 |
| `contract-change` | 계약 표의 행, 계약 코드, 「결정 기록」의 공유 가정을 바꿔야 할 때. 계약 불일치로 테스트가 실패할 때도 이 코드다 |
| `shared-file-change` | 공용 파일이나 큰 명세 본문을 바꿔야 할 때 |
| `dependency-add` | 의존성 목록·잠금 파일에 패키지를 추가해야 할 때. `요청`에 패키지를 적는다 |
| `test-double-add` | 계약 코드에 없는 테스트 대역이 필요할 때 |

| 유형 | 고르는 때 |
|---|---|
| 범위 밖 결정 | 「멈추는 기준」의 범위 밖 항목에 분명히 드는 결정이 필요할 때 |
| 리뷰 🔴 | 하부 명세나 plan 리뷰에서 🔴가 나왔을 때 |
| 리뷰 관점 부족 | 리스크상 필요한 관점을 상시 허용 렌즈로 볼 수 없어, 사용자 승인이 필요한 렌즈를 실행해야 진행할 수 있을 때 |
| SDD 정지 | SDD가 멈추고 사람에게 물으라고 하는 상황(비가역·파괴 작업, 보안 작업, 워크트리 밖 부작용, 모든 진행 방법이 추측인 plan)에 해당할 때 |
| 환경 문제 | 권한이나 도구 설치처럼 사람이 조치해야 풀리는 문제가 있을 때 |

상시 허용 렌즈(에이전트원칙 LENS-ALLOWED)로 볼 수 있는 관점이면 서브 세션은 멈추지 않고 그 렌즈를 직접 실행한다. 필요할 때 그룹의 발동 기준에 해당했을 뿐 진행에 지장이 없으면 멈추지 않고 리포트의 `렌즈 그룹 판정`에 적는다(`dispatching-lenses`의 「렌즈 그룹」).

**하향 메시지.** 현재 세션은 모든 하향 메시지에 `워크스트림`과 `통합 브랜치`(`dev/<개발> @ <커밋>`)를 공통 필드로 적는다. `START`와 `RESTART`는 디스패치 프롬프트의 첫머리이며, 필드 아래에 산문 지시가 이어진다. 아래 표의 '다음 응답'은 일을 마쳤을 때의 응답이다. 서브 세션은 어느 하향 메시지 뒤에도 사유에 해당하면 `BLOCKED`를, 끝낼 수 없으면 `FAILED`를 돌려준다.

| 머리줄 | 추가 필드 | 서브 세션이 할 일 | 다음 응답 |
|---|---|---|---|
| `START` | `브랜치`(`spec/<개발>/<임시 id>` 또는 `ws/<개발>/<id>`), `워크트리`(절대 경로), `리포트`, `프로토콜`(이 파일의 절대 경로), `큰 명세` | 명세 서브 세션은 하부 명세를 쓰고 `review-specs`로 리뷰해 반영한 뒤 커밋하고 `작성 기록`을 채운다. 구현 서브 세션은 큰 명세 「절 배정」이 가리키는 하부 명세와 작성 기록과 계약 코드로 writing-plans, `review-specs`, SDD 를 진행한다. 다른 저장소의 독립 작업은 하부 명세를 쓰고 리뷰해 커밋한다 | 명세·구현 서브 세션은 `DONE`, 다른 저장소의 독립 작업은 `AWAITING_APPROVAL` |
| `RESTART` | `START`의 추가 필드, `이전 리포트`, `원인`, `시도한 것`, `이어 받을 상태`(브랜치·하부 명세나 plan·SDD 작업 공간) | 이전 리포트를 `리포트` 경로에 이어 쓰고, 이어 받을 상태에서 멈춘 단계를 찾아 이어 간다. `원인`과 `시도한 것`의 방법을 그대로 되풀이하지 않는다. 명세 서브 세션은 `원인`에 적힌 고칠 항목대로 하부 명세를 고쳐 다시 리뷰한다 | 이어 받은 단계의 응답 |
| `APPROVE` | `승인한 하부 명세`, `조건` | 다른 저장소의 독립 작업에서만 쓴다. writing-plans, `review-specs`, SDD 로 진행한다. plan이 이미 있으면 바뀐 하부 명세 절만 반영해 plan을 고친다 | `DONE` |
| `REVISE` | `대상`, `고칠 항목` | 고칠 항목을 처리하고 커밋한다. 대상이 하부 명세나 plan 이면 다시 리뷰한다 | 다른 저장소의 독립 작업에서 대상이 하부 명세면 `AWAITING_APPROVAL`, 구현이나 plan 이면 `DONE`, 응답이면 고친 같은 상향 메시지 |
| `ANSWER` | `질문`, `답`, `결정 기록` | 답을 반영해 멈춘 작업을 이어 간다 | 하던 단계의 응답 |
| `BASE-UPDATED` | `바뀐 것`, `할 일` | 자기 워크트리에서 `git merge dev/<개발>`을 실행하고, 충돌이 나면 풀어 커밋한다. 테스트를 다시 실행한 뒤 이어 간다 | 하던 단계의 응답 |
| `CONTRACT-CHANGED` | `바뀐 항목`(계약 행, 큰 명세 절, 공유 가정), `커밋` | 통합 브랜치를 병합하고 바뀐 항목에 맞춘다. 공유 가정이 자기 구현과 다르면 고치지 않고 `BLOCKED contract-change`로 알린다. plan 이 바뀌면 다시 리뷰한다 | 하던 단계의 응답(다른 저장소의 독립 작업에서 하부 명세가 바뀌었으면 `AWAITING_APPROVAL`) |
| `INTEGRATION-FAILED` | `확인 위치`, `실패 검사`, `출력` | 자기 워크트리에서 통합 브랜치를 병합한다. `확인 위치`에 다른 워크스트림 커밋이 있으면 임시 브랜치에서 그 커밋을 함께 병합해 실패를 재현하고 그 임시 브랜치를 지운다. 원인을 자기 브랜치에서 고쳐 커밋한다 | `DONE` |
| `CANCEL` | `이유` | 미커밋 변경을 커밋하지 않고 워크트리에 남긴 채 멈춘다 | `CANCELED` |

`INTEGRATION-FAILED`의 `확인 위치`는 실패를 재현할 커밋이다. 값은 시험 병합한 워크스트림의 `ws/<개발>/<id> @ <커밋>`이며, 이미 병합된 워크스트림의 통합 확인을 통합 브랜치에서 다시 실행해 실패했으면 `없음`이다.

## 멈추는 기준

서브 세션은 `AWAITING_APPROVAL`(다른 저장소의 독립 작업), `DONE`, `FAILED`, `CANCELED`를 보낼 때와 「메시지 형식」의 사유 코드에 해당할 때만 멈춘다. 그 밖의 모호함은 스스로 판정해 리포트의 `스스로 판정한 모호함`에 적는다.

범위 밖 결정은 큰 명세와 「결정 기록」에 답이 없고 아래 항목 중 하나에 드는 결정이다.

- 권한: 누가 무엇을 할 수 있는지(역할, 승인, 대리)를 정하는 결정
- 기능의 추가나 제외: 큰 명세의 「맡는 일」에 없는 기능을 만들거나 적힌 기능을 빼는 결정
- 결과의 뜻: 사용자가 보는 상태·판정·알림의 뜻을 정하는 결정
- 돈과 되돌리기 어려운 자료: 금액·주문, 자료의 삭제·보존 기간·덮어쓰기를 정하는 결정
- 보안: 비밀, 인증, 외부 전송을 정하는 결정

화면 배치·문구·정렬·표시 형식과 내부 이름·자료 구조·알고리즘은 범위 안이다. 큰 명세에 없는 기능을 만들지 않는 결정도 범위 안이다. 서브 세션은 위 항목에 분명히 드는 결정에서만 멈추고, 드는지 확실하지 않으면 스스로 판정해 그 줄의 마지막 칸에 '예'를 적는다.

명세·plan 리뷰에는 `accept`나 `regenerate` 같은 결정 값이 없으므로 서브 세션은 그 값을 지어내지 않는다. 서브 세션은 리뷰 반영 뒤 다시 리뷰할지 묻지 못하므로 생략하고, 기능적 변화가 있었던 반영을 리포트의 `기능적 반영`에 적는다.

## SDD 와 함께 쓸 때

실행 루프는 SDD가 소유하므로 서브 세션은 SDD 규칙을 따른다. 다만 아래 문단이 SDD 의 마무리 단계 두 가지(작업 공간 삭제와 `finishing-a-development-branch` 실행)를 바꾼다. 수정 라운드의 상한과 상한에서의 판정은 SDD 규칙을 따르며, 서브 세션은 SDD가 멈추고 사람에게 물으라고 하는 상황에서만 `BLOCKED user-decision`(유형: SDD 정지)을 보낸다. 구현자를 재개할지 새로 시작할지도 SDD 규칙(수정 1~3라운드는 재개, 4라운드부터 새 구현자)을 따르고, 렌즈를 다시 실행하는 규칙은 `dispatching-lenses`를 따른다.

SDD 최종 리뷰 뒤 서브 세션은 `finishing-a-development-branch`를 실행하지 않고 `DONE`을 돌려준다. SDD는 최종 브랜치 리뷰가 깨끗하면 작업 공간을 지우라고 하지만, 서브 세션은 그 삭제를 하지 않는다. 서브 세션은 워크트리와 SDD 작업 공간(`.superpowers/sdd/` 아래, gitignore 대상)을 `DONE` 전에도 뒤에도 지우지 않는다. 재개가 실패하면 새 서브 세션이 그 작업 공간을 이어 받고, 지우는 일은 현재 세션이 「흐름」의 정리 단계에서 한다.

SDD가 마칠 때 모으는 판정(`Ruling:` 줄) 목록과 최종 리뷰의 남은 지적은 리포트의 `SDD 판정과 남은 지적`에 옮긴다.

## 리포트

서브 세션은 `리포트` 필드의 경로에 리포트를 쓰고 커밋하지 않는다. 리포트에는 아래 절 제목을 이 순서로 두고, 내용이 없는 절도 `없음`으로 남긴다. 테스트 결과는 현재 세션이 시험 병합에서 직접 실행하므로 적지 않는다. 판정을 적는 절(`명세 이탈`, `스스로 판정한 모호함`, `SDD 판정과 남은 지적`)의 마지막 칸은 그 줄이 「멈추는 기준」의 범위 밖 항목에 가까운지(예·아니오)다.

| 절 제목 | 줄의 형식 |
|---|---|
| `확정한 결정` | '결정 — 이유' |
| `확정한 계약 의미` | '계약 행 — 칸(의미 또는 형식의 열거값) — 값' |
| `작성 기록` | 명세 서브 세션만 쓴다. '고른 대안 — 기각한 대안과 이유', '읽은 코드와 자료', '열린 질문' 줄 |
| `명세 이탈` | '하부 명세의 위치(「절 배정」의 파일과 절) — 실제 구현 — 이유 — 범위 밖(예·아니오)' |
| `스스로 판정한 모호함` | '질문 — 판정 — 이유 — 범위 밖(예·아니오)' |
| `SDD 판정과 남은 지적` | '판정이나 남은 지적 — 결정 — 틀렸을 때의 비용 — 범위 밖(예·아니오)' |
| `렌즈 그룹 판정` | '렌즈 — 대상 문서 — 발동 기준에 해당한 이유' |
| `기능적 반영` | '리뷰 반영 중 동작이 바뀐 항목 — 바뀐 동작' |
| `제안` | '범위 밖 아이디어 — 이유' |
| `메시지 기록` | 보낸 상향 메시지 전문과 받은 하향 메시지의 머리줄을 순서대로 |
