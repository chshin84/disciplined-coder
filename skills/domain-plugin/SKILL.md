# 플러그인 관리 도메인 참고서

Claude Code 플러그인과 마켓플레이스를 만들고 배포할 때 따를 규칙이다.

## 단위 나누기

함수·파일·스킬·서브에이전트를 만들 때는 한 단위에 한 가지 역할만 맡기고, 입력과 출력만 알면 다른 단위에서 바로 쓸 수 있게 설계하라. 그래야 수정이 필요할 때 그 단위만 고치면 된다.

## 플러그인을 만들 때 지킬 것

플러그인은 다른 사용자 PC로 배포되므로, 설정값을 잘못 적으면 새 커밋이 반영되지 않거나 스킬이 열리지 않는다.

**version 비우기** — 활성 개발 중에는 plugin.json의 `version`을 비워 커밋 SHA 기반 자동 업데이트를 유지하라. version을 채우면 버전 문자열 비교 방식으로 바뀌어, 값을 올리지 않는 한 새 커밋이 사용자에게 배포되지 않는다([plugins-reference의 Version management](https://code.claude.com/docs/en/plugins-reference#version-management)). `claude plugin validate`가 version 경고를 내더라도 그대로 수용하라(CLI 버전에 따라 나오지 않기도 한다).

**marketplace.json** — `.claude-plugin/marketplace.json` 최상위에 `name`·`description`·`owner`·`plugins[]`를 넣어라. 저장소 루트가 곧 플러그인이면 `source: "./"`로 지정하라. `plugins[].description`은 `plugin.json`의 `description`과 글자 그대로 일치시켜라. 문구를 고칠 때는 `plugin.json`을 먼저 수정한 뒤 마켓플레이스 항목을 따라 고쳐라. 두 값이 같은지는 `scripts/test_docs_drift.sh`로 검사한다.

**frontmatter** — 스킬 `SKILL.md`에는 디렉터리 이름과 같은 `name`과 `description` 두 키를, 커맨드 `.md`에는 `description` 하나를 넣어라. 스킬 `description`에는 언제 여는지를, 커맨드에는 무엇을 하는지를 적어라. Claude가 스킬을 고를 때도, 사용자가 목록에서 커맨드를 고를 때도 근거는 그 값뿐이다.

에이전트 정의 `agents/*.md`에는 `name`과 `description`을 넣고, 허용 도구와 턴 상한을 `tools`·`maxTurns`로 지정하라.

모든 값은 YAML 평문 스칼라이므로 `: `와 ` #`을 쓰지 마라. 에이전트 정의의 `description`에도 똑같이 적용하라.

**validate** — `claude plugin validate ./`로 플러그인을 검증하라. `--strict`는 경고까지 실패로 처리하므로, 위 버전 정책을 따르는 저장소에서는 `--strict`가 실패하는 것이 정상이다. non-strict로 통과 여부를 확인하라.

**스킬 이름의 부류** — 이름만 보고 용도를 알 수 있게 규칙을 나눠 붙여라. 참고용 규칙집에는 `domain-` 접두사를 붙이고, 렌즈나 에이전트를 실행해 결과를 내는 절차에는 접두사 없이 동사구를 써라. 렌즈는 스킬이 아니라 에이전트 정의(`agents/lens-*.md`)이므로 `lens-` 접두사를 붙여라. 렌즈 리뷰 절차인 `lens-review`는 2026-11-13 v2 재건축 spec에서 정한 이름이라 예외로 둔다. 규칙집과 실행 절차에 같은 접두사를 쓰면 여는 쪽이 무엇을 기대해야 할지 알 수 없다.

**컴포넌트 위치** — 각 파일은 `agents/`·`skills/`·`commands/`·`workflows/`·`hooks/hooks.json`에 배치하라. 플러그인 루트에 둔 CLAUDE.md는 컨텍스트로 로드되지 않는다.

## 에이전트 호출 정책

스킬 절차나 워크플로 스크립트에 이름으로 미리 지정한 에이전트만 호출하라. 실행 중인 에이전트가 자체 판단으로 다른 에이전트를 실행하는 호출은 허용하지 마라. 판단 근거와 기각한 대안은 결정 기록 `docs/superpowers/decisions/2026-10-25-agent-call-policy.md`에 있다.

서브에이전트 내부에서는 실행할 에이전트 종류를 제한할 수 없다. `Agent(이름)` 구문은 `claude --agent`로 시작한 메인 스레드에만 적용되기 때문이다. 따라서 아래 규칙을 지켜라.

- 플러그인 에이전트 정의에는 `tools`를 한 줄 쉼표 목록으로 적고, `Agent`·`Agent(...)`·`Task`를 넣지 마라. `tools`를 생략하면 Agent 도구를 그대로 상속받는다.
- 워크플로에서 `agent()`를 호출할 때는 옵션 객체에 `agentType`을 직접 적어라. 객체를 펼쳐(`...`) 넘기면 검사 스크립트가 읽지 못하므로 위반으로 처리한다.
- 플러그인 스킬에서 서브에이전트를 실행할 때는 플러그인 정의나 Explore처럼 Agent 도구가 없는 종류만 써라. tools를 지정하지 않은 general-purpose는 Agent 도구를 받는다.

이 정책은 `scripts/test_lens_contract.sh`의 호출 정책 검사 묶음으로 검증한다. 다른 에이전트를 호출해야 하는 정의가 필요해지더라도 검사에 예외를 넣거나 tools에 Agent를 추가하지 마라. 메인 세션이나 워크플로 스크립트가 두 에이전트를 순서대로 실행하는 구성을 권장안으로 진행하고 보고에 적어라. 그 구성으로 요구사항을 충족할 수 없을 때만 사용자에게 물어라.

## 훅을 만들 때의 값

훅은 실행 비용이 든다. 자주 실행되는 훅을 만들기 전에는 소요 시간을 먼저 측정하라. 아래는 2026-09-07에 이 저장소의 작업 세션이 이 PC(윈도우 11, Git Bash)에서 측정한 수치이며, 다른 환경에서는 다시 측정하라.

| 항목 | 1회 실행 시간 |
|---|---|
| 아무 동작도 없는 훅 | 110밀리초 |
| 빈 프로세스 하나 | 8밀리초 |
| `grep` 하나 · `awk` 하나 | 45밀리초 · 47밀리초 |
| `python` 하나 | 71밀리초 |
| `python3` 하나(스토어 안내로 연결될 때) | 186밀리초 |

2026-10-21에 검진 훅(`hooks/doc_review_posttooluse.sh`)에 문서 형식 검사를 추가한 뒤 같은 PC에서 입력마다 10번 실행해 평균을 냈다. `.py`를 Write할 때는 80밀리초에서 81밀리초로, 위반 없는 `.md`는 85밀리초에서 237밀리초로, 위반 다섯 줄이 든 `.md`는 83밀리초에서 254밀리초로 늘었다. 늘어난 시간은 `.md`를 쓸 때 파이썬을 한 번 실행하는 비용이다. 이 검진 훅은 2026-11-17 v2 정리에서 삭제했다.

훅을 작성할 때는 아래 규칙을 지켜라.

**프로세스 수 관리** — 셸 반복문이 파이썬보다 빠르다고 가정하지 마라. 표의 행마다 파이프를 실행하던 훅은 13,057밀리초가 들었지만, 같은 작업을 파이썬 한 번으로 처리하자 1,108밀리초로 줄었다. 윈도우는 프로세스 생성 비용이 커서 반복 횟수가 그대로 지연 시간으로 이어진다.

**고정 문자열 검색 로케일** — 고정 문자열을 검색할 때는 로케일을 `C`로 지정하라. `C.UTF-8`에서 207밀리초 들던 `grep`과 213밀리초 들던 `awk`의 실행 시간이 크게 줄었다. `grep -F`는 문자열을 그대로 비교하므로 바이트 단위로 비교해도 UTF-8 결과가 같다.

**대화 기록 파싱 Stop 훅 금지** — 대화 기록을 파싱하는 Stop 훅은 만들지 마라. Stop 훅이 `last_assistant_message`로 마지막 답을 받기는 하지만(2026-10-20 공식 문서 확인), 이미 출력된 답은 고칠 수 없고 도구 호출 사이의 중간 답도 받지 못한다. 예전 구현은 대화 기록 파일을 열어 JSON을 파싱하느라 파이썬을 실행했고, 실제 대화 기록에서 답 하나당 1,021밀리초가 들어 삭제했다. 답에 적용할 규칙은 에이전트원칙에 적어 지시로 맡겨라. 단, git 상태만 확인하는 가벼운 게이트는 허용하되, 검사를 한 프로세스로 모으고 git status는 한 번만 실행하라(`hooks/stop_gates.sh`).

## 사용자 설정 파일을 고칠 때 지킬 것

플러그인이 `~/.claude/settings.json`처럼 사용자가 직접 관리하는 파일을 수정해야 할 때가 있다. 이 저장소에서도 마켓플레이스 자동 갱신을 켜려고 해당 파일을 수정한다(`scripts/_ensure_autoupdate.sh`). 이런 스크립트를 작성할 때는 아래 규칙을 지켜라.

**환경 변수** — OS 환경 변수는 사용자에게 먼저 묻고 설정하라. 이미 값이 있으면 건드리지 마라. 설정한 값은 열려 있는 창에는 반영되지 않고 새로 여는 창부터 적용된다는 사실을 함께 알려라.

**대상 좁히기** — 이 플러그인이 추가했다고 식별되는 항목만 수정하라. 다른 항목은 값이 같더라도 손대지 마라.

**사용자 결정 존중** — 사용자가 이미 값을 넣어 둔 키는 덮어쓰지 마라. 키가 아예 없을 때만 값을 채워라.

**사본과 재검증** — 수정 전에 `.bak` 사본을 남겨라. 새로 쓴 파일을 다시 파싱해 유효할 때만 원래 경로에 덮어써라.

**사유별 통지** — 수정에 실패하면 원인을 구분해 알려라. 설정 파일을 못 읽었을 때, 파이썬이 없을 때, 쓰기 권한이 없을 때는 사용자가 취할 조치가 서로 다르다.

**처리기 하나** — JSON을 다루는 처리기를 여럿 두지 마라. 폴백 처리기를 추가하면 실행되지 않는 중복 코드가 생기고, 실행해 보지 않은 코드에는 오류가 숨기 마련이다.

**자동 생성 구간** — 스크립트가 사용자 파일에 쓰는 구간은 BEGIN/END 마커로 감싸고, 몇 번 다시 생성해도 결과가 같도록 그 구간만 덮어써라. 사용자가 직접 쓴 내용은 마커 바깥에 두어, 재생성할 때 사용자 내용이 지워지지 않게 하라(구현은 `scripts/_managed_block.sh`).

**서식 변경 고지** — 값을 추가하면 파일 전체를 다시 쓰면서 기존 서식이 바뀔 수 있다. 바뀐 파일 경로와 사본 위치를 함께 알려라.

## 훅과 상시 지시의 과잉을 판정할 때

플러그인을 리뷰하거나 군더더기를 줄일 때는 훅과 상시 지시에 아래 기준을 적용하라. 테스트·스크립트·문서처럼 일반 프로젝트에도 적용되는 기준은 `domain-pruning`이 소유한다. 아래 판정 기준은 2026-10-05 선행연구로 정리했다.

**훅을 쓸 조건** — 예외 없이 지켜야 하고, 예·아니오로 명확히 판정할 수 있으며, 지시만으로는 지켜지지 않는 행동만 훅으로 강제하라. 상황 판단이 필요하거나 과잉 차단 비용이 가끔의 불이행보다 크다면 지시로 맡겨라. 넛지 훅이 출력하는 문구도 컨텍스트를 차지한다([hooks vs prompts](https://agentpatterns.ai/instructions/hooks-vs-prompts/), [Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

**상시 지시의 분량** — 지시 한 줄마다 그 줄을 지웠을 때 에이전트가 실수하는지 따져 보고, 그렇지 않으면 지워라. CLAUDE.md는 import한 파일까지 합쳐 200줄 미만을 목표로 삼아라. 지시 수가 늘수록 준수율이 떨어진다는 측정 결과는 키워드 지시 기준이므로 방향을 잡는 근거로만 참고하라([Claude Code memory](https://code.claude.com/docs/en/memory), [IFScale](https://arxiv.org/abs/2507.11538)).
