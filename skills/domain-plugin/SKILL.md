# 플러그인 관리 도메인 참고서

Claude Code 플러그인과 마켓플레이스 제작·배포 기준을 정리한다.

## 단위 나누기

함수·파일·스킬·서브에이전트를 만들 때 각 단위에 작업 하나만 맡겨라. 다른 단위가 입출력만 보고 호출할 수 있게 구성하라. 수정 범위를 한 단위로 제한하기 위해서다.

## 플러그인을 만들 때 지킬 것
플러그인은 다른 사람의 PC로 배포된다. 설정값이 틀리면 새 커밋이 반영되지 않거나 스킬이 열리지 않는다.

**version 비우기** — 활성 개발 중에는 plugin.json의 `version`을 비워 두라. 그래야 커밋 SHA 기반 자동 업데이트가 유지된다. version을 적으면 업데이트 방식이 버전 문자열 비교로 바뀌어, 값을 올리기 전까지 새 커밋이 사용자에게 배포되지 않는다([plugins-reference의 Version management](https://code.claude.com/docs/en/plugins-reference#version-management)). `claude plugin validate`가 version 경고를 내면 받아들여라(CLI 버전에 따라 안 나올 수도 있다).

**marketplace.json** — `.claude-plugin/marketplace.json` 최상위에 `name`·`description`·`owner`·`plugins[]`를 적어라. 레포 루트가 곧 플러그인이면 `source: "./"`로 지정하라. `plugins[].description`은 `plugin.json`의 `description`과 글자 그대로 맞춰라. 문구를 바꿀 때는 `plugin.json`을 먼저 고친 뒤 마켓플레이스 항목을 따라 고쳐라. 일치 여부는 `scripts/test_docs_drift.sh`가 확인한다.

**frontmatter** — 스킬 `SKILL.md`에는 디렉터리 이름과 같은 `name`과 `description` 두 키를 적어라. 커맨드 `.md`에는 `description` 하나만 적어라. `description`에는 스킬이면 언제 열어야 하는지를, 커맨드면 무슨 일을 하는지를 포함하라. Claude가 스킬을 열 시점을 고르는 근거도, 사용자가 목록에서 커맨드를 고르는 근거도 이 값뿐이다.

에이전트 정의 `agents/*.md`에는 `name`과 `description`을 적고, 도구와 턴 상한을 `tools`·`maxTurns`로 지정하라.

각 값은 YAML 평문 스칼라로 처리되므로 `: `와 ` #`을 넣지 마라. 에이전트 정의의 `description`에도 같은 규칙이 적용된다.

**validate** — `claude plugin validate ./`로 플러그인을 검증하라. `--strict`는 경고도 실패로 처리하므로 위 버전 정책을 쓰는 레포에서는 `--strict`가 실패하는 게 정상이다. non-strict 모드로 통과 여부를 확인하라.

**스킬 이름의 부류** — 이름 형태만 봐도 용도가 드러나게 지어라. 열어서 읽는 규칙집에는 `domain-` 접두사를 붙이고, 렌즈나 에이전트를 실행해 결과를 내는 절차에는 접두사 없이 동사구를 써라. 렌즈는 스킬이 아니라 에이전트 정의(`agents/lens-*.md`)이며 `lens-` 접두사를 붙인다. 렌즈 리뷰 절차인 `lens-review`는 2026-11-13 v2 재건축 spec이 정한 이름이라 이 분류의 예외다. 규칙집과 절차가 같은 접두사를 쓰면 호출하는 쪽이 무엇을 기대해야 할지 알 수 없다.

**컴포넌트 위치** — 각 구성 요소는 `agents/`·`skills/`·`commands/`·`workflows/`·`hooks/hooks.json`에 배치하라. 플러그인 루트의 CLAUDE.md는 컨텍스트로 로드되지 않는다.

## 에이전트 호출 정책

사전에 정의된 에이전트 호출만 사용하라. 사전 정의 호출이란 스킬 절차나 워크플로 스크립트에 에이전트 이름을 명시한 호출을 뜻한다. 실행 중인 에이전트가 자체 판단으로 다른 에이전트를 실행하게 하지 마라. 판단 근거와 기각된 안은 `docs/superpowers/decisions/2026-10-25-agent-call-policy.md`에 기록돼 있다.

서브에이전트 안에서는 실행할 에이전트 종류를 제한할 수 없다. `Agent(이름)` 구문이 `claude --agent`로 시작한 메인 스레드에만 적용되기 때문이다. 이를 보완하는 장치는 다음과 같다.

- 플러그인 에이전트 정의에서는 `tools`를 한 줄 쉼표 목록으로 적고 `Agent`·`Agent(...)`·`Task`를 빼라. `tools`를 생략하면 Agent 도구를 물려받는다.
- 워크플로에서 `agent()`를 호출할 때는 옵션 객체에 `agentType`을 직접 적어라. 객체를 펼쳐(`...`) 넘기면 검사가 값을 읽지 못하므로 위반으로 본다.
- 플러그인 스킬이 서브에이전트를 실행할 때는 플러그인 정의나 Explore처럼 Agent 도구가 없는 종류를 골라라. tools를 정하지 않은 general-purpose는 Agent를 받는다.

준수 여부는 `scripts/test_lens_contract.sh`의 호출 정책 검사 묶음이 확인한다. 다른 에이전트를 실행해야 하는 정의가 필요하더라도 검사에 예외를 넣거나 tools에 Agent를 적지 마라. 메인 세션이나 워크플로 스크립트가 두 에이전트를 순서대로 실행하는 권장안으로 진행하고 보고에 적어라. 이 구성으로 요구를 채울 수 없을 때만 사용자에게 물어라.

## 훅을 만들 때의 값

훅 실행에는 비용이 든다. 자주 호출되는 훅을 만들기 전에 실행 비용부터 측정하라. 아래 표는 2026-09-07에 이 저장소 작업 세션이 이 PC(윈도우 11, Git Bash)에서 측정한 결과다. 다른 환경에서는 다시 측정하라.

| 대상 | 한 번 실행 시간 |
|---|---|
| 아무 일도 안 하는 훅 | 110밀리초 |
| 빈 프로세스 하나 | 8밀리초 |
| `grep` 하나 · `awk` 하나 | 45밀리초 · 47밀리초 |
| `python` 하나 | 71밀리초 |
| `python3` 하나(스토어 안내판으로 풀릴 때) | 186밀리초 |

2026-10-21에 검진 훅(`hooks/doc_review_posttooluse.sh`)에 문서 형식 검사를 넣은 뒤 같은 PC에서 입력마다 10번 실행 평균을 측정했다. `.py`를 Write할 때는 80밀리초에서 81밀리초로, 위반 없는 `.md`를 Write할 때는 85밀리초에서 237밀리초로, 위반 다섯 줄이 든 `.md`를 Write할 때는 83밀리초에서 254밀리초로 늘었다. 늘어난 시간은 `.md`를 쓸 때 파이썬을 한 번 실행하는 비용이다. 이 검진 훅은 2026-11-17 v2 정리에서 지웠다.

아래 기준을 지켜라.

**프로세스 수를 세라** — 셸 반복이 파이썬보다 가볍다고 가정하지 마라. 표의 행마다 파이프를 실행한 훅은 13,057밀리초 걸렸지만, 같은 작업을 파이썬 한 번으로 처리하자 1,108밀리초로 줄었다. 윈도우는 프로세스 생성 비용이 커서 반복 횟수가 그대로 지연 시간으로 이어진다.

**고정 문자열 검색은 로케일을 `C`로 두라** — `C.UTF-8`에서 207밀리초 걸리던 `grep`과 213밀리초 걸리던 `awk`의 시간이 크게 줄었다. `grep -F`는 글자를 그대로 비교하므로 바이트로 비교해도 UTF-8 결과가 같다.

**대화 기록을 파싱하는 Stop 훅은 만들지 마라** — Stop 훅은 `last_assistant_message`로 마지막 답을 받는다(2026-10-20 공식 문서 확인). 하지만 이미 나간 답은 고칠 수 없고, 도구 호출 사이의 중간 답도 받지 못한다. 예전 구현은 대화 기록 파일을 열어 JSON을 파싱하려고 파이썬을 실행했고, 실제 대화 기록에서 답 하나당 1,021밀리초가 걸려 지웠다. 답 규칙은 에이전트원칙에 적어 지시로 맡겨라. git 상태만 보는 가벼운 게이트는 예외지만, 검사를 한 프로세스로 모으고 git status는 한 번만 실행하라(`hooks/stop_gates.sh`).

## 사용자 설정 파일을 고칠 때 지킬 것

플러그인이 `~/.claude/settings.json`처럼 사용자가 직접 관리하는 파일을 고쳐야 할 때가 있다. 이 레포도 마켓플레이스 자동 갱신을 켜느라 그 파일을 수정한다(`scripts/_ensure_autoupdate.sh`). 아래 원칙을 지켜라.

**환경 변수** — OS 환경 변수를 넣기 전에 사용자에게 물어라. 이미 값이 있으면 건드리지 마라. 새로 넣은 값은 열려 있는 창에 바로 실리지 않고 다음에 여는 창부터 적용된다고 함께 알려라.

**대상 좁히기** — 이 플러그인이 넣은 것으로 식별되는 항목만 고쳐라. 값이 같더라도 다른 곳에서 넣은 항목은 손대지 마라.

**사용자 결정 존중** — 사용자가 값을 넣어 둔 키는 덮지 마라. 키 자체가 없을 때만 채워라.

**사본과 재검증** — 고치기 전에 `.bak` 사본을 남겨라. 새로 쓴 파일을 다시 파싱해 유효할 때만 원래 경로에 반영하라.

**사유를 구분한 통지** — 고치지 못했을 때는 원인을 구분해 알려라. 설정 읽기 실패, 파이썬 미설치, 쓰기 권한 부족은 사용자가 할 일이 각각 다르다.

**처리기 하나** — JSON 처리기를 여럿 두지 마라. 폴백을 덧붙이면 한 번도 실행되지 않는 사본이 생기고, 거기에 오류가 숨는다.

**자동 생성 구간** — 스크립트가 사용자 파일에 쓰는 구간은 BEGIN/END 마커로 감싸라. 몇 번 다시 실행해도 같은 결과가 나오도록 마커 안쪽만 다시 쓰고, 사용자가 쓴 내용은 마커 바깥에 두라. 재생성이 사용자 내용을 덮지 않게 하기 위해서다(구현: `scripts/_managed_block.sh`).

**서식 변경 고지** — 값을 채우면 파일 전체가 다시 기록돼 서식이 바뀔 수 있다. 바뀐 경로와 사본 위치를 함께 알려라.

## 훅과 상시 지시의 과잉을 판정할 때

플러그인을 리뷰하거나 줄일 때는 아래 판정 질문으로 훅과 상시 지시를 점검하라. 테스트·스크립트·문서처럼 일반 프로젝트에도 해당하는 기준은 `domain-pruning`이 소유한다. 판정 질문은 2026-10-05 선행연구로 모았다.

**훅을 쓸 조건** — 예외 없이 지켜야 하고, 예·아니오로 판정이 떨어지며, 지시만으로는 지켜지지 않는 행동만 훅으로 강제하라. 판단이 필요하거나 과잉 차단 비용이 가끔의 불이행보다 크면 지시로 맡겨라. 넛지 훅이 내는 글도 컨텍스트를 쓴다([hooks vs prompts](https://agentpatterns.ai/instructions/hooks-vs-prompts/), [Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

**상시 지시의 분량** — 지시 한 줄마다 지웠을 때 에이전트가 실수하는지 따져 보고, 아니면 지워라. CLAUDE.md는 import한 파일까지 합쳐 200줄 미만을 목표로 삼아라. 지시 수가 늘면 준수율이 떨어진다는 측정은 키워드 지시 기준이라 방향의 근거로만 써라([Claude Code memory](https://code.claude.com/docs/en/memory), [IFScale](https://arxiv.org/abs/2507.11538)).
