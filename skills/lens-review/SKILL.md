# lens-review — 카테고리 적대 리뷰와 1차 디펜스

렌즈는 `agents/lens-*.md` 에 정의한 읽기 전용 에이전트다. 이 스킬은 세 진입점(직접 요청, 설계 문서, 전달 문서)에서 렌즈를 고르고 실행하고 지적을 거르는 절차를 소유한다. 기록 파일 경로와 이름은 `managing-docs` 「기록 파일 이름 규칙」을 따른다.

## 카테고리와 렌즈

이 표는 여기가 소유한다. 한 렌즈에 합치면 판정이 오염되는 세 기준(적대 자세가 대조 판정에 섞이는 문제, 출처를 읽은 렌즈가 맥락 없는 독자를 대변할 수 없는 문제, 웹 권한을 꼭 필요한 렌즈에만 제한하는 문제)으로 렌즈를 나눴다.

설계 결함·반대 근거·독자 렌즈는 적대적으로 결점을 찾고, 대조 렌즈는 출처와 다른 점만 건조하게 보고한다. 모든 렌즈는 지적마다 원문 위치와 근거를 함께 반환한다.

| 카테고리 | 렌즈 | 모드 | `CRITERIA` 로 넘기는 자료 |
|---|---|---|---|
| 대조 | `lens-grounding` | `spec`(spec·plan), `doc`(문서), `runtime`(LLM 출력) | 출처(선행 결정, 이전 spec, 검증 대상 사실, 관련 파일, 근거 대화 원문)와 형식 계약(사용자 지정 형식·양식, `skills/managing-docs/references/reading-docs.md`, README 라면 `skills/domain-readme/SKILL.md`). `doc` 에는 문서 타입 표 `skills/managing-docs/SKILL.md` 도 넘긴다 |
| 설계 결함 | `lens-adversarial` | `design`(spec·plan), `artifact`(코드·실험 결과·테스트 출력) | 짝 문서(plan 이면 spec)와 선행 결정 |
| 반대 근거 | `lens-rebuttal` | `claim` | 근거 자료. 주장 목록은 「직접 요청」에 따라 배경에 넣는다 |
| 독자 | `lens-readability` | `text`(글), `render`(화면) | `references/style-attacks.md` 하나. 배경에는 목적 한 줄(독자와 독자가 할 수 있어야 하는 일)만 넣고 출처·대화는 넘기지 마라. 대화에서 목적을 알 수 없으면 임의로 쓰지 말고 사용자에게 물어라 |

대상마다 적용하는 카테고리는 다음과 같다.

- spec·plan: 대조, 설계 결함
- 전달 문서: 대조, 독자. 렌더링 산출물은 최종본에 독자(`render`)를 추가한다
- 직접 요청: 사용자가 고른 카테고리
- 반대 근거: 사용자가 주장 반박을 요청할 때 추가한다

**렌즈 입력 형식.** 프롬프트 맨 앞에 아래 세 줄을 쓰고 그 아래에 배경을 적어라. 모드가 하나뿐인 렌즈도 `MODE` 줄은 빼지 마라.

```
MODE: <모드>
TARGET: <대상 파일 경로>
CRITERIA: <기준 파일 경로, 쉼표로 구분. 없으면 none>
```

파일 경로는 실행할 때 구하고, 스킬 본문에 절대 경로를 쓰지 마라. 다른 프로젝트에서는 PC 전역 폴더(에이전트원칙 사본 위치)의 managing-docs·lens-review 사본을 넘겨라. 기준 파일을 못 연 렌즈는 커버리지 공백으로 처리하라. 렌즈는 메인 세션의 대화와 첨부를 보지 못하므로, 대화 근거는 원문 그대로 넣고 이미지·PDF 첨부는 파일 경로를 넘겨라. 요약본은 넣지 마라. 렌즈가 요약을 원문으로 알고 인용하면 인용 확인이 요약과 대조돼 통과하기 때문이다. `render` 모드의 .html 은 대상 파일만 복사한 임시 폴더를 `python -m http.server --bind 127.0.0.1 --directory <그 폴더>` 로 열어 `http://localhost` 주소를 넘기고, 렌즈가 끝나면 서버를 종료하라. .pptx·.docx 는 PDF 로 변환해 넘겨라.

## 절차

1. 대상 유형에 맞춰 「카테고리와 렌즈」에서 카테고리를 정하라.
2. 배정한 렌즈를 각각 한 번씩 실행하라(「실행」).
3. 메인 세션이 모든 렌즈의 지적을 한곳에 모으고 중복 항목을 합쳐라.
4. 「통합과 1차 디펜스」 기준에 따라 지적을 걸러라.
5. spec·plan 은 처분을 마친 뒤 반영하기 전에 맨 끝 줄에 마커를 달아라(「설계 문서」).
6. 남은 지적은 Claude 가 직접 반영하되, 사용자 파일은 「직접 요청」 기준을 따르라. 가치 판단이 필요하거나 되돌릴 수 없는 항목만 사용자에게 보고하라.
7. 보고서에는 렌즈별 지적 수, 기각 수(「통합과 1차 디펜스」의 발견의 요건에서 거른 항목 포함), 기각 목록(지적 요약 한 줄과 기각 근거 위치, 요건 미달 항목은 `요건 미달: <빠진 칸>`), `read` 가 빈 렌즈를 적어라. 기각 수는 작성자 편향을 살피는 지표다.
8. 설계를 그르치는 지적이 남았을 때만 대상별로 바뀐 절에만 1회 다시 리뷰하라. 배경 자료는 수정본 기준으로 새로 챙기고, 이후에도 남은 지적은 사용자에게 넘겨라.

## 실행

- 에이전트를 한 번 부를 때 렌즈 하나만 실행하라. `subagent_type` 값은 `disciplined-coder:<렌즈 이름>` 이다.
- 렌즈는 대상당 한 번씩만 실행하고 동시 실행은 4개 이하로 제한하라. 2026-11-16 PC 메모리 부족 이후 사용자가 정한 상한이다. 한 단계의 에이전트는 10개 이하로 제한하고, 제외한 대상은 산출물에 적어라.
- 응답이 없거나 형식이 틀린 렌즈는 1회만 재실행하고 그 사실을 기록하라. Agent 도구를 쓸 수 없으면 리뷰가 불가능하다고 사용자에게 알리고 마커를 달지 마라.
- 옛 렌즈 비교 기록이 3건 쌓이기 전까지는 첫 spec·전달 문서에서 태그 `archive/v1-final` 의 옛 형식·화면·정합성 렌즈 정의도 한 번씩 실행해, 현행 렌즈가 놓친 단독 발견을 기록하라.
- 지적을 반영한 뒤에는 「설계 문서」의 다시 리뷰를 빼고 같은 대상에 렌즈를 다시 실행하지 마라.
- 대상을 렌즈별로 나누어 맡기지 마라. 겹치는 지적은 통합 단계에서 합친다.
- 스키마 필수 키·인용 문장의 원문 글자 일치·금지어처럼 같은 질문에 답하는 결정론 검사가 있으면 먼저 실행하고, 렌즈에는 남은 판단만 맡겨라. 새 프로젝트·모델·의존성이 드는 검사는 따로 만들지 말고 렌즈 판단에 맡긴 뒤 판단 항목이라고 기록하라.
- 렌즈 정의의 tools 에 Agent 가 없어 렌즈는 서브에이전트를 못 연다. 렌즈가 `notes` 에 추가 확인 사항을 남기면 같은 대화에서 이어 물어라.
- .pptx·.docx 를 PDF 로 변환하려 오피스를 COM 으로 실행할 때는 `kw-doc-formats` 절차를 따르라. 별도 조치 없이 실행하면 사용자가 열어 둔 다른 문서가 저장 확인 없이 닫힌다.

## 통합과 1차 디펜스

이 절차는 여기가 소유한다. 렌즈 출력의 칸 목록과 렌즈별 `type` 값은 `scripts/lens_contract.json` 이 소유한다.

**통합.** 지적마다 출처 렌즈 이름을 `source` 에 적고, 같은 곳을 같은 이유로 지적한 항목은 합쳐라. 배정한 렌즈가 결과를 내지 않았으면 커버리지 공백으로 기록하라. `doc` 모드에 타입 표를 넘겼는데 `lens-grounding` 의 `doc_type` 이 null 이면 빈 결과를 판정으로 쓰지 말고 미실행으로 쳐라. `lens-readability` 의 `purpose` 가 null 일 때도 같다.

**발견의 요건.** 지적 위치(파일과 문장), 상대편(불일치하는 코드·파일·문장·URL·`conversation`), 지금 어떤 상태인지(`consequence`)를 빠짐없이 갖춘 지적만 발견으로 올려라. `lens-readability` 는 상대편 대신 `suggestions` 를 돌려주므로 원본을 열어 읽어라.

**1차 디펜스.** 적대 렌즈(`lens-adversarial`·`lens-rebuttal`·`lens-readability`)의 지적마다 원문(대상 문서의 다른 문장)·코드·사용자 원문(대화와 지시)으로 반박해 보라. `lens-adversarial` 지적은 공격받은 대상 자체(문서 문장이나 `artifact` 모드의 해당 코드)로는 기각하지 말고, 짝 문서·다른 코드·사용자 원문으로만 기각하라. 독자 렌즈의 `suggestions` 도 반박 대상이며, `references/style-attacks.md` 의 「판정 기준점」·「과잉 지적 반례」로도 반박하라.

- 근거 파일과 문장을 직접 열어 실제로 그렇게 적혀 있는지 확인하라.
- 지적한 문제가 그 근거에서 실제로 이어지는지 따져라.
- 다른 지적이나 문서에서 이미 해결했는지 살펴라.

원문 위치로 뒷받침되는 반박만 기각으로 인정하고, 그 위치를 기록의 기각 근거 칸에 적어라. 위치를 대지 못하면 기각하지 마라. 메인 세션의 동의 여부가 아니라 근거가 서는지만 따져라. 근거는 틀렸는데 우려가 타당해 보이면 직접 확인하라.

**대조 렌즈의 확인.** `lens-grounding` 지적에는 반박하지 마라. 출처와 다른 점을 작성자 주장으로 반박하면 출처가 작성자 판단에 묻히기 때문이다. 인용 위치에 실제로 그렇게 적혀 있는지와 지적한 결과가 그 근거에서 나오는지 두 가지만 확인하고, 하나라도 틀리면 그 위치를 기각 근거에 적어 기각하라.

**반박 결과의 인용 확인.** `lens-rebuttal` 지적은 사용자에게 넘기기 전에 `counterpart` 구절이 원문에 있는지 검증하라. URL 은 WebFetch 로 열고, PDF 본문이 안 읽히면 내려받아 텍스트를 뽑아라. `kofia.or.kr` 와 하위 주소는 열지 마라. 상대편이 URL 인 지적의 처분은 `사용자` 다. 구절이 원문에 없는 지적만 "인용 확인 실패"로 기록하고 숨겨라. 원문을 열지 못한 지적은 숨기지 말고 "확인 불가" 건수와 URL 을 보고서에 한 줄로 적어라. 렌즈의 `queries` 는 사내 식별 낱말 목록과 대조한 결과를 기록하라.

## 기록

결과 파일은 `managing-docs` 「기록 파일 이름 규칙」대로 이름 지어 남겨라(spec·plan 은 `review`, 문서 검진은 `check`). 렌즈 원본은 받는 대로 같은 이름 폴더에 저장하라. 기록에는 실행한 렌즈·모드, "렌즈를 한 번씩만 실행했다" 문구(재실행 시 그 사실), 커버리지 공백, 옛 렌즈 비교 결과(실행 시 단독 발견), 기각 수, 선행연구 실행 여부와 판정 이유, 아래 표를 넣어라.

| 지적 | source | 위치 | 처분 | 기각 근거 |
|---|---|---|---|---|

처분 칸에는 `반영`·`기각`·`사용자` 중 하나를 쓴다. 기각한 항목은 기각 근거 칸에 반박 원문 위치(파일·문장, 코드, 사용자 원문)를 적고, 나머지는 `-` 를 넣어라. 커밋한 기록은 봉인되므로 수정하지 마라. 반영하며 바뀐 설계의 근거는 고친 문서 본문에 남겨라. 반영 도중 끊겨 재개할 때는 기록 표와 문서를 대조해 누락된 지적을 찾아라.

## 직접 요청

사용자가 렌즈 검토를 요청하면 확인을 묻지 말고 바로 실행하라. 대상 유형을 알 수 없을 때만 실행 전에 물어라. 사용자가 검진을 맡긴 파일은 `reading-docs.md` 「마크다운 초안과 퇴고」의 사용자 파일 조건 안에서만 고쳐라.

| 요청 | 카테고리 |
|---|---|
| 적대적 검토 | 설계 결함(spec·plan 은 `design`, 코드·실험 결과는 `artifact`) |
| 근거 확인, 형식 검토 | 대조(`doc`) |
| 가독성·문체, 디자인 검토 | 독자(글은 `text`, 화면은 `render`) |
| 반박, 주장을 대상으로 한 적대적 검토 | 반대 근거 |
| 렌즈 이름 지정 | 그 렌즈 |

결정 근거나 선행 사례 조사는 `researching-prior-art` 가, 제품 코드의 런타임 LLM 출력 검증 설계는 `review-llm-calls` 가 맡는다.

**주장 반박의 준비.** 실행 전에 반박할 주장을 원문 문장 그대로 뽑아 적고, 각 주장이 기대는 다른 주장과 근거 구절을 붙인 전체 목록을 사내 식별 낱말 목록(고객·거래 상대방·사내 시스템 이름)과 함께 한 번에 넘겨라. 주장 간 의존 관계를 한 렌즈가 같이 봐야 전제까지 반박할 수 있기 때문이다. 실행할 때는 검증 검색어가 외부 검색 서비스 로그에 남는다는 점을 사용자에게 한 줄로 알려라.

## 설계 문서

`docs/superpowers/specs`·`plans` 에 spec·plan 을 작성하면 훅이 이 절차를 지시한다. 사용자가 상시 요청해 둔 절차이므로 승인 없이 바로 실행하라. `CRITERIA` 값으로 `lens-adversarial`(`design`)에는 짝 문서를, `lens-grounding`(`spec`)에는 선행 결정과 검증할 사실을 넘겨라. 렌즈를 실행한 뒤에는 결과를 기다려 같은 턴 안에 처분까지 마치고, 끝나기 전에 턴을 넘기지 마라(Stop 게이트가 차단한다).

**선행연구.** spec 이 처음 시도하는 과제이고 실현 여부가 불확실하면 묻지 말고 `researching-prior-art` 를 실행하라. 기존 작업을 자동화·정리하는 spec 과 plan 에는 실행하지 마라. 무승인 실행은 하위 질문이 4개 이하일 때만 허용하며, 세부 규칙은 `researching-prior-art` 「발동과 기록」을 따른다. 웹 내용이 문서를 저절로 고치지 않도록 선행연구 발견은 반영하지 말고 사용자에게 보고하라. 마커를 단 뒤 선행연구 결과가 도착해 사용자에게 올릴 발견이 생기면 마커의 `passed` 를 `escalated` 로 고쳐라.

**마커.** 처분을 마치면 반영보다 먼저 문서 맨 끝 줄에 마커를 달아라. 사용자에게 올린 항목과 커버리지 공백이 모두 없으면 `<!-- spec-review: passed -->`, 하나라도 있으면 `<!-- spec-review: escalated -->` 를 쓴다. 날짜·개수는 빼고, 반영 내용은 마커 위에만 적어 마커가 끝 줄로 남게 하라. 반영보다 마커를 먼저 달아야 훅이 재발동하지 않는다. Stop 훅은 마커 유무만 보고 턴당 한 번만 차단하므로 리뷰 없이 마커만 달지 마라.

**다시 리뷰.** 반영 결과 동작이나 계약이 달라졌고 남은 지적 중 설계를 그르치는 항목이 있을 때만 다시 리뷰하라. 이때는 바뀐 절과 그 절을 참조하거나 그 절이 참조하는 절만 살펴라. 다시 리뷰하지 않기로 정했으면 그 판단을 수정한 문서 본문에 남겨라. 사용자가 다시 리뷰를 요청하면 따르라.

**서브 세션.** `nested-orchestration` 의 서브 세션도 이 절차를 따르되, 사용자에게 올릴 항목은 리포트에 적어 현재 세션으로 넘겨라.

## 전달 문서

외부 전달 문서와 .html·.pptx·.docx·.pdf 산출물은 사용자가 검진을 요청하거나 외부에 공개하기 직전에만 검진하라. 고객·외부에 보낸다고 한 문서는 Claude 가 완성한 시점을 공개 직전으로 보고 묻지 않고 검진하라. 저장소에 커밋하는 작업 문서는 대상에서 뺀다. 독자(`text`)에는 마크다운 초안(공개 직전이면 최종본에서 다시 추출한 마크다운)을, 독자(`render`)에는 최종본을 넘겨라. 원본은 「직접 요청」과 같은 조건에서만 고쳐라. 사용자가 결론 반박을 요청한 보고서·제안서에는 반대 근거를 추가하라. 처음 시도하는 방법의 효과나 실현 가능성을 주장하는 제안서·검토 자료에는 `researching-prior-art` 를 실행하라(하위 질문 4개 이하면 묻지 않는다).

**고치지 않는 요소.** 지적을 반영할 때 아래 항목은 건드리지 마라. 수정이 필요해 보이면 사용자에게 알려라.

- 사용자가 지정한 형식·발신 주체·문장
- 숫자·부호·고유명사·식별자와 수치의 관계
- 완화 표현과 조건절(`대체로`·`다만`·`~라면`)
- 직접인용

반영 절차는 `managing-docs` 의 `references/reading-docs.md` 「마크다운 초안과 퇴고」를 따르라. 외부 공개 문서에는 결론을 앞에 두고 용어를 풀어 쓰며, 분석 노트를 그대로 붙이지 마라.
