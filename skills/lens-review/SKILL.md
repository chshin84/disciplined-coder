# lens-review — 카테고리 적대 리뷰와 1차 디펜스

렌즈는 `agents/lens-*.md`에 정의된 읽기 전용 에이전트다. 이 스킬은 세 진입점(직접 요청·설계 문서·전달 문서)에서 렌즈를 고르고 실행해 지적을 거르는 절차를 소유한다. 기록 파일 경로와 이름은 `managing-docs` 「기록 파일 이름 규칙」을 따른다.

## 카테고리와 렌즈

이 표는 여기가 소유한다. 렌즈를 합치면 판정이 오염되는 세 조건(적대 자세가 대조 판정에 섞임, 출처를 본 렌즈가 맥락 없는 독자를 흉내 못 냄, 웹 권한을 필요한 렌즈에만 허용)으로 나눴다.

설계 결함·반대 근거·독자 렌즈는 적대 자세로 공격하고, 대조 렌즈는 출처와 다른 점만 건조하게 보고한다. 모든 렌즈는 지적마다 원문 위치와 근거를 돌려준다.

| 카테고리 | 렌즈 | 모드 | `CRITERIA` 로 넘기는 자료 |
|---|---|---|---|
| 대조 | `lens-grounding` | `spec`(spec·plan), `doc`(문서), `runtime`(LLM 출력) | 출처(선행 결정·이전 spec·검증할 사실·관련 파일·근거 대화 원문)와 형식 계약(사용자 지정 형식·양식, `skills/managing-docs/references/reading-docs.md`, README면 `skills/domain-readme/SKILL.md`). `doc`이면 문서 타입 표 `skills/managing-docs/SKILL.md` |
| 설계 결함 | `lens-adversarial` | `design`(spec·plan), `artifact`(코드·실험 결과·테스트 출력) | 짝 문서(plan이면 spec)와 선행 결정 |
| 반대 근거 | `lens-rebuttal` | `claim` | 근거 자료. 주장 목록은 「직접 요청」대로 배경에 넣어라 |
| 독자 | `lens-readability` | `text`(글), `render`(화면) | `references/style-attacks.md` 하나. 목적 한 줄(읽는 사람과 할 수 있어야 하는 작업)은 배경에 넣고 출처·대화는 넘기지 마라. 대화에서 확인되지 않으면 짐작하지 말고 사용자에게 물어라 |

대상별 카테고리는 다음과 같다.

- spec·plan: 대조, 설계 결함
- 전달 문서: 대조, 독자. 렌더링 산출물이면 최종본에 독자(`render`)를 추가한다
- 직접 요청: 사용자가 요청한 카테고리
- 반대 근거: 사용자가 주장 반박을 요청할 때 추가한다

**렌즈 입력 형식.** 프롬프트는 아래 세 줄로 시작하고 그 아래에 배경을 적어라. 모드가 하나인 렌즈에도 `MODE` 줄을 넣어라.

```
MODE: <모드>
TARGET: <대상 파일 경로>
CRITERIA: <기준 파일 경로, 쉼표로 구분. 없으면 none>
```

경로는 실행 시점에 도출하고 스킬 본문에 절대 경로를 적지 마라. 다른 프로젝트에서는 PC 전역 폴더(에이전트원칙 사본 위치)의 managing-docs·lens-review 사본을 넘기고, 기준 파일을 열지 못한 렌즈는 커버리지 공백으로 처리하라. 렌즈는 메인 세션 대화·첨부를 받지 못하므로 대화 근거는 원문 그대로, 이미지·PDF 첨부는 파일 경로를 넘겨라. 요약은 넣지 마라. 요약을 원문으로 알고 인용하면 인용 확인이 요약과 대조해 통과하기 때문이다. `render`의 .html은 대상 파일만 복사한 임시 폴더를 `python -m http.server --bind 127.0.0.1 --directory <그 폴더>`로 열어 `http://localhost` 주소를 넘기고 끝나면 서버를 종료하라. .pptx·.docx는 PDF로 내보내 넘겨라.

## 절차

1. 대상 종류로 「카테고리와 렌즈」에서 카테고리를 골라라.
2. 「실행」대로 렌즈마다 1회 실행하라.
3. 메인 세션에서 모든 렌즈 지적을 한 목록으로 모으고 중복을 합쳐라.
4. 「통합과 1차 디펜스」대로 지적을 선별하라.
5. spec·plan이면 처분 뒤 반영 전에 마지막 줄에 마커를 적어라(「설계 문서」).
6. 남은 지적은 Claude가 반영하되 사용자 파일은 「직접 요청」대로 따르라. 가치 판단이 필요하거나 되돌릴 수 없는 항목만 사용자에게 올려라.
7. 보고에 렌즈별 지적 수, 기각 수(「통합과 1차 디펜스」 발견의 요건 탈락 포함), 기각 목록(지적 한 줄과 기각 근거 위치, 요건 미달은 `요건 미달: <빠진 칸>`), `read`가 빈 렌즈를 적어라. 기각 수는 작성자 편향 감시 지표다.
8. 다시 리뷰는 설계를 틀리게 만드는 지적이 남았을 때만 바뀐 절에 대상마다 1회 실행하라. 배경 자료는 고친 문서 기준으로 새로 준비하고, 뒤에도 남은 지적은 사용자에게 올려라.

## 실행

- 에이전트 호출 하나에 렌즈 하나만 실행하라. `subagent_type`은 `disciplined-coder:<렌즈 이름>`이다.
- 렌즈는 대상마다 1회만, 동시 4개 이하로 실행하라. 2026-11-16 PC 메모리 부족 뒤 사용자가 정한 상한이다. 한 단계 에이전트는 10개 이하로 두고 제외한 대상은 산출물에 적어라.
- 응답이 없거나 형식이 틀리면 1회 재실행하고 기록하라. Agent 도구가 없으면 리뷰 불가라고 사용자에게 알리고 마커를 남기지 마라.
- 옛 렌즈 비교 기록 3건이 쌓이기 전까지 첫 spec·전달 문서에서 태그 `archive/v1-final`의 옛 형식·화면·정합성 렌즈 정의도 1회씩 실행해, 현행 렌즈가 놓친 단독 발견을 기록하라.
- 반영 뒤 같은 대상에 렌즈를 재실행하지 마라. 「설계 문서」의 다시 리뷰만 예외다.
- 렌즈끼리 검토 대상을 나눠 배정하지 마라. 중복 지적은 통합에서 합친다.
- 같은 질문에 답하는 결정론 검사(스키마 필수 키, 파일 내 인용 문구 일치, 금지어)를 먼저 실행하고 렌즈에는 남은 판단만 맡겨라. 새 프로젝트·모델·의존이 필요한 검사는 만들지 말고 렌즈 판단으로 둔 뒤, 판단이라고 기록하라.
- 렌즈는 서브에이전트를 호출하지 않는다(정의의 tools에 Agent가 없다). 렌즈가 `notes`에 추가 확인 사항을 남기면 같은 대화로 이어 물어라.
- .pptx·.docx를 PDF로 내보내려고 오피스를 COM으로 실행할 때는 `kw-doc-formats` 절차를 따르라. 별도 조치 없이 실행하면 사용자가 열어 둔 다른 문서가 저장 확인 없이 닫힌다.

## 통합과 1차 디펜스

이 절차는 여기가 소유한다. 렌즈 출력 칸 목록과 렌즈별 `type` 값은 `scripts/lens_contract.json`이 소유한다.

**통합.** 지적마다 출처 렌즈 이름을 `source`에 적고, 같은 곳을 같은 이유로 지적한 항목은 합쳐라. 배정한 렌즈가 결과를 내지 않았으면 커버리지 공백으로 기록하라. `doc` 모드에서 타입 표를 넘겼는데 `lens-grounding`의 `doc_type`이 null이면 빈 결과를 판정으로 쓰지 말고 실행하지 않은 렌즈로 처리하라. `lens-readability`의 `purpose`가 null이어도 같다.

**발견의 요건.** 지적 위치(파일과 문장), 상대편(불일치하는 코드·파일·문장·URL·`conversation`), 현재 영향(`consequence`)을 모두 댄 지적만 발견으로 올려라. `lens-readability`는 상대편 대신 `suggestions`를 내므로 원본을 직접 열어 확인하라.

**1차 디펜스.** 적대 렌즈(`lens-adversarial`·`lens-rebuttal`·`lens-readability`) 지적마다 원문(대상 문서의 다른 문장)·코드·사용자 원문(대화와 지시)으로 반박을 시도하라. 다만 `lens-adversarial` 지적은 공격받은 대상 자체(문서의 해당 문장, `artifact` 모드의 해당 코드)로 기각하지 말고 짝 문서·다른 코드·사용자 원문으로만 기각하라. 독자 렌즈의 `suggestions`도 대상이며 `references/style-attacks.md`의 「판정 기준점」과 「과잉 지적 반례」로도 반박하라.

- 근거 파일과 문장이 실제로 그렇게 적혀 있는지 열어 확인하라.
- 지적한 결과가 그 근거에서 도출되는지 확인하라.
- 다른 지적이나 문서가 이미 처리했는지 확인하라.

원문 위치로 받쳐지는 반박이 서면 기각하고 그 위치를 기록의 기각 근거 칸에 적어라. 위치를 대지 못하는 반박으로는 기각하지 마라. 메인 세션의 동의 여부가 아니라 근거 성립만 따져라. 근거는 틀렸는데 우려가 맞아 보이면 직접 확인하라.

**대조 렌즈의 확인.** `lens-grounding` 지적에는 반박을 시도하지 마라. 인용 위치에 실제로 적혀 있는지, 지적한 결과가 그 근거에서 도출되는지만 확인해 둘 중 하나라도 성립하지 않으면 그 위치를 기각 근거에 적고 기각하라. 출처와 다른 점을 작성자 주장으로 반박하면 출처가 작성자 판단에 덮이기 때문이다.

**반박 결과의 인용 확인.** `lens-rebuttal` 지적은 사용자에게 보이기 전에 `counterpart` 구절이 원문에 있는지 확인하라. URL이면 WebFetch로 열고, PDF 본문이 읽히지 않으면 내려받아 텍스트를 추출하라. `kofia.or.kr`와 하위 주소는 열지 마라. 상대편이 URL인 지적의 처분은 `사용자`다. 구절이 원문에 없는 지적만 "인용 확인 실패"로 기록하고 숨겨라. 원문을 열지 못하는 지적은 숨기지 말고 "확인 불가" 건수와 URL을 보고에 한 줄 적어라. 렌즈의 `queries`는 사내 식별 낱말 목록과 대조해 결과를 기록하라.

## 기록

결과는 `managing-docs` 「기록 파일 이름 규칙」대로 저장하라(spec·plan은 `review`, 문서 검진은 `check`). 렌즈 원본은 받는 즉시 같은 이름 폴더에 저장하라. 기록에는 실행한 렌즈와 모드, "렌즈를 한 번씩만 실행했다" 한 줄(재실행했으면 그 사실), 커버리지 공백, 옛 렌즈 비교(실행했으면 단독 발견), 기각 수, 선행연구 실행 여부와 판정 이유, 아래 표를 적어라.

| 지적 | source | 위치 | 처분 | 기각 근거 |
|---|---|---|---|---|

처분은 `반영`·`기각`·`사용자` 중 하나다. 기각이면 기각 근거 칸에 반박을 받친 원문 위치(파일과 문장·코드·사용자 원문)를 적고, 나머지에는 `-`를 적어라. 커밋된 기록은 봉인되므로 고치지 마라. 반영으로 바뀐 설계 근거는 고친 문서 본문에 적어라. 반영 중 중단된 뒤 재개하면 기록 표와 문서를 대조해 미반영 지적을 찾아라.

## 직접 요청

사용자가 렌즈 검토를 요청하면 묻지 말고 실행하라. 대상 종류를 구분할 수 없을 때만 실행 전에 물어라. 사용자가 검진을 맡긴 사용자 파일은 `reading-docs.md` 「마크다운 초안과 퇴고」의 사용자 파일 조건대로만 고쳐라.

| 요청 | 카테고리 |
|---|---|
| 적대적 검토 | 설계 결함(spec·plan은 `design`, 코드·실험 결과는 `artifact`) |
| 근거 확인, 형식 검토 | 대조(`doc`) |
| 가독성·문체, 디자인 검토 | 독자(글은 `text`, 화면은 `render`) |
| 반박, 주장을 대상으로 한 적대적 검토 | 반대 근거 |
| 렌즈 이름 지정 | 지정한 렌즈 |

결정 근거·선행 사례 탐색 요청은 `researching-prior-art`가, 제품 코드의 런타임 LLM 출력 검증 설계는 `review-llm-calls`가 맡는다.

**주장 반박의 준비.** 실행 전에 대상에서 반박할 주장을 원문 문장 그대로 하나씩 적고, 각 주장이 전제하는 다른 주장과 근거 구절을 붙여 목록 전체와 사내 식별 낱말 목록(고객·거래 상대방·사내 시스템 이름)을 한 번에 넘겨라. 한 렌즈가 주장 간 의존을 함께 봐야 전제도 반박할 수 있기 때문이다. 실행할 때 검증 검색어가 외부 검색 서비스 로그에 남는다고 사용자에게 한 줄 알려라.

## 설계 문서

`docs/superpowers/specs`·`plans`에 spec·plan을 쓰면 훅이 이 절차를 지시한다. 사용자가 상시 요청한 절차이므로 묻지 말고 실행하라. `lens-adversarial`(`design`)에는 짝 문서를, `lens-grounding`(`spec`)에는 선행 결정과 검증할 사실을 `CRITERIA`로 넘겨라. 렌즈 실행 뒤에는 결과를 기다려 같은 턴에 처분까지 마치고, 끝나기 전에 턴을 종료하지 마라(Stop 게이트가 차단한다).

**선행연구.** spec이 아직 시도하지 않은 새로운 작업을 다루고 실현 가능성이 불확실하면 묻지 말고 `researching-prior-art`를 실행하라. 이미 하던 작업을 자동화하거나 정리하는 spec·plan에는 실행하지 마라. 묻지 않는 실행은 하위 질문 4개 이하일 때만이며, 규칙은 `researching-prior-art` 「발동과 기록」이 정한다. 웹 내용이 문서를 자동으로 바꾸지 않도록 선행연구 발견은 반영하지 말고 사용자에게 올려라. 마커 뒤에 결과가 도착해 올릴 발견이 생기면 마커의 `passed`를 `escalated`로 바꿔라.

**마커.** 처분을 마치면 반영 전에 문서 마지막 줄에 마커를 적어라. 사용자에게 올린 항목과 커버리지 공백이 없으면 `<!-- spec-review: passed -->`, 있으면 `<!-- spec-review: escalated -->`다. 반영은 마커 줄 위에만 써서 마커가 마지막 줄로 남게 하라. 날짜·개수는 넣지 마라. 반영보다 먼저 마커를 적어야 훅이 재발동하지 않는다. Stop 훅은 마커 유무만 보고 턴당 1회만 차단하므로 리뷰 없이 마커만 달지 마라.

**다시 리뷰.** 반영으로 동작·계약이 바뀌었고 설계를 틀리게 만드는 지적이 남았을 때만 다시 리뷰하라. 바뀐 절과, 그 절을 참조하거나 그 절이 참조하는 절만 보라. 다시 리뷰하지 않기로 했으면 그 판단을 고친 문서 본문에 적어라. 사용자가 요구하면 따르라.

**서브 세션.** `nested-orchestration` 서브 세션도 이 절차를 따르되, 사용자에게 올릴 항목은 리포트에 적어 현재 세션에 넘겨라.

## 전달 문서

남에게 전달할 문서와 .html·.pptx·.docx·.pdf 산출물은 사용자 요청이나 외부 공개 직전에만 검진하라. 고객·외부에 보낸다고 밝힌 문서는 Claude가 완성한 때를 공개 직전으로 보고 묻지 말고 검진하라. 저장소에 커밋하는 작업 문서는 대상이 아니다. 독자(`text`)에는 마크다운 초안을(공개 직전이면 최종본에서 다시 추출한 마크다운을), 독자(`render`)에는 최종본을 넘겨라. 원본 수정은 「직접 요청」 조건대로만 하라. 사용자가 결론 반박을 요청한 보고서·제안서는 반대 근거를 추가하라. 새 방법의 효과나 실현 가능성을 주장하는 문서(제안서·검토 자료)인데 아직 시도하지 않았으면 `researching-prior-art`를 실행하라(하위 질문 4개 이하면 묻지 않는다).

**고치지 않는 요소.** 지적을 반영할 때 아래 요소는 고치지 마라. 수정이 필요하면 사용자에게 알려라.

- 사용자가 지정한 형식·발신 주체·문장
- 숫자·부호·고유명사·식별자와 수치 사이의 관계
- 완화 표현과 조건절(`대체로`·`다만`·`~라면`)
- 직접인용

반영 절차는 `managing-docs`의 `references/reading-docs.md` 「마크다운 초안과 퇴고」를 따르라. 외부 공개 문서는 결론을 먼저 두고 용어를 풀며, 분석 노트를 그대로 붙이지 마라.
